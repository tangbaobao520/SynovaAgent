## 项目身份（每次重读 — 源自 CLAUDE.md §项目身份）

SynovaAgent 是一个驻扎企业的 AI 诊断系统。
诊断是手段，增长才是目的。
核心问题：这家企业的增长卡在哪里？现在该做什么？
Agent，不是 ChatBot。驻扎企业，持续观测，主动发现，自动诊断，给出行动建议，跟踪执行。

目标: 成为组织诊断的 AWS。每个新客户、新行业、新数据源 → 加文件即可，不改代码。
能文件化的必须文件化。不能文件化的必须有明确的扩展点。

### 三层解耦体系

**纵向解耦：五层物理隔离**
代码按 L1-L5 架构分层，每层只与相邻层通信。L1 交互层不知道 L4 用什么数据库，L3 洞察层不知道 L5 数据存在哪。换底层存储，上层零改动。pre-commit 物理阻断跨层 import——L2→L4 的代码提交不进去。

**横向解耦：11 个独立 Monorepo 包**
五层内部拆为独立包：@synova/sog-core（本体图类型）、@synova/sentinel-engine（哨兵调度）、@synova/expert-platform（专家加载）、@synova/connector-registry（数据连接器）。每个包接口边界明确，拆卸一个不影响其余 19 个。核心包已落地运行；已存在的功能规划从 src/ 迁移到独立包；未来新增须遵循此结构。

**扩展解耦：文件驱动，不改代码**
新增能力靠文件，不靠改代码：
- 新 AI 专家 = 新建目录 + 10 个 Markdown 文件 → 自动注册到 ExpertDispatcher
- 新诊断哨兵 = 加 xxx-sentinel.ts → builtins 自动扫描加载
- 新行业 = 加行业目录（基准数据+阈值+案例库）→ 1-2 天上线，零 TypeScript 改动
- 新本体实体类型 = 加 JSON Schema 文件

流程约束: V4.2.9 — task brief 6 字段强制 + 免疫系统 + plan.json + 8 组物理阻断 + Plan-Actual 闭合 + engine-core 清零 + 时间戳顺序检查。

## Q2: 范围 — 正确的最简方案是什么？

**做什么：**
1. JWT 认证中间件 `src/middleware/auth.ts`
   - 使用 Node.js built-in `crypto` HMAC-SHA256（零依赖）
   - 签发、验证、解码
   - Token payload: `{ sub, role, orgId, iat, exp, jti }`
   - 自动续签支持
   - 撤销检查（SQLite `token_blacklist` 表）
   - JWT_SECRET 缺失时降级到 devMode + log.warn

2. RBAC 扩展 `src/middleware/rbac.ts`
   - WorkspaceRole 增加 `'ga'`
   - `canAccessWorkspace()`: GA = admin 读权限（全可见）
   - `canModifyWorkspace()`: GA 不可修改（403 Forbidden）
   - `extractRbacContext()`: 支持从 JWT context 和旧 token 格式

3. Auth 路由 `src/routes/auth.ts`
   - `POST /api/auth/login` — 登录获取 JWT（demo: 按 role/orgId 签发）
   - `POST /api/auth/refresh` — 刷新 token
   - `POST /api/auth/revoke` — 撤销 token（企业主专属）

4. Server.ts 集成
   - 替换内联 auth（注释旧代码，接入 JWT 中间件）
   - 注册 auth 路由
   - 保持 whitelist 豁免

5. 测试 `src/middleware/auth.test.ts` + `src/middleware/rbac.test.ts`
   - JWT sign/verify/expired/revoked/invalid
   - GA 角色权限（可读不可删）
   - 降级路径（无 JWT_SECRET 时）

**不做什么：**
- ❌ OAuth/OIDC 集成（v2）
- ❌ 公钥/私钥非对称加密（v2）
- ❌ 前端登录页面（Phase 0.5）
- ❌ refresh token 轮换（v2）
- ❌ 多因子认证（v2）
- ❌ GA 行为监控中的通知触发（Phase 0.4）
- ❌ 修改 packages/graph-store/（Phase 0.2）
- ❌ 审计日志（Phase 0.3）

## Q3: 验收 — 入口 → 交互 → 结果

入口（用户从哪触发）：
  `POST /api/auth/login` 获取 JWT → 携带 `Authorization: Bearer <jwt>` 访问受保护 API

处理（中间经过哪些步骤）：
  1. `auth.ts` JWT 中间件验证 token 签名、过期、是否被撤销
  2. 提取 `{ role, userId, orgId }` 注入请求上下文（runWithContext）
  3. `rbac.ts` 中间件根据 role 判断读写权限
  4. 如果 role=ga，读操作放行，写操作（delete）403

结果（最终展示在哪）：
  API 响应：
  - GA token → `GET /api/workspaces` → 200（工作区列表）
  - GA token → `DELETE /api/workspaces/xxx` → 403 Forbidden
  - 撤销 token → `GET /api/workspaces` → 401 Unauthorized
  - 过期 token → `GET /api/workspaces` → 401 Unauthorized
  - 无 token → `GET /api/workspaces` → 401 Unauthorized
