## Q1: 调研 — 业界最佳实践 / Anthropic 决策链 / memory 历史教训
### a) 业界最佳实践
分布式锁/租约（lease）系统与 CI 并发控制（GitHub Actions concurrency group、Kubernetes Lease）的共识：
**锁必须有过期或显式释放，且释放状态存于共享的权威存储，而不是锁持有者的本地副本**。
本仓现状恰好相反：判定源是「brief 文件文本」+「gitignore 掉的本地 registry」——既不共享也无过期。
### b) 顶级团队怎么做
- 失败安全方向：**释放是降低保护的动作 → 判定必须 fail-closed**（拿不到证据 = 不放行），与 `staging_guard` 既有的 fail-open（registry 缺失 → degraded pass）方向相反，须在代码里显式区分这两类降级。
- 单一事实源：判定逻辑只写一处，调用方 import，禁止复制粘贴口径。
### c) memory / 仓内历史教训
- `staging_guard.py:64-67` 注释记 D329 自查发现的设计缺陷：认领制必须放在 own_set 放行**之前**，否则 write-set 预登记会"洗白"他人文件 → 本卡的释放维度也必须放在**放行之前**，且**不能**因为已释放就跳过后续 registry 判定。
- `resolve-commit-brief.sh:68-76`（D718）记：曾因候选池太窄导致认领恒空 → 回退到无关 brief → 误阻断。本卡改候选池必须保持"宁窄勿错"的同向收紧（剔除已释放 brief 只会让候选更准，不会误伤）。
- `resolve-commit-brief.sh:204-207`（D718）记：共享文件被多个 brief 同时认领是常态，同数裁决曾让陈旧 brief 恒胜 → 误阻断。本卡「完成即释放」是该缺陷的根因级修法。
- 铁律 24/31（异常必须 log + degraded 传播）、铁律 47/48（契约优先 + 测试非空壳）、铁律 0-2（测试先行 + 接线验收）。

### Q1c) 决策参考系
**参考：第一性原理 + Anthropic 工程基线 + 仓内实证 + 收敛检查**
1. **第一性原理**：认领制的目的是「防两个 session 同时改同一文件」。任务已完成 → 不存在并发写者 → 该认领没有保护价值，只有副作用。故「完成即释放」是把机制收敛到其**唯一本质**上。
2. **Anthropic 工程基线**：① 隔离——释放状态放共享权威存储（git 跟踪的 `task-state/`），不放 gitignore 的本地 registry，也不放 brief 文本；② fail-closed——释放判定拿不到证据时不释放；③ 机器可验契约——判定结果带 `basis` 字段（凭什么释放），可被测试与审计核。
3. **仓内实证（实测，非推断）**：见下方"被否决的方案"——把 `gen-cto-health.py` 的 D393 全量派生口径直接拿来判释放，实测会把**进行中的 D711 / D819**（`git log` 含 `(D711)` / `(D819)` 但 `status=claimed`）判成"已完成"→ 释放它们会**真实破坏并发保护**（违反场景 B）。该口径必须收窄。
4. **收敛检查**：三参考系同指一个答案——**以 task-state 的显式 `status` 声明为自动释放依据（card 口径 {impl_done, audited}），以显式释放台账兜住其余情况，两者都在 git 跟踪的 `task-state/` 内**。故直接执行，不升级创始人。

**被否决的方案（实测数据，留证）**：D393 全量派生（`git log --all` 含 `(D#)` 即 impl_done）→ 失效认领数从 16 涨到 **24**，多出的 7 个含 **D711（claimed，进行中）** 与 **D819（claimed，进行中）**。释放它们是安全倒退。
