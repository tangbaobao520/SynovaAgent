## Q1: 调研 — 业界最佳实践 / Anthropic 决策链 / memory 历史教训
### a) 业界最佳实践
- **权威状态必须来自不可静默改写的事实源**。git 里唯一不可静默改写的事实源 = **已提交对象**（工作树/索引
  都可被任意进程改写且不留痕）。CI 系统（GitHub Actions concurrency、Buildkite）判断"任务是否结束"一律
  读 **已提交的** 状态/事件，从不读工作区文件——工作区是"意图"，提交是"事实"。
- 审计留痕的通行做法：**不可否认的释放记录（who / why / when / on-what-basis）**，且非所有者操作必须
  给出显式理由（Kubernetes 的 `--force` 需 `--reason`，git 的 `-m` 强制要求说明）。

### b) 顶级团队怎么做
- fail-closed 方向性：**释放是降低保护的动作 → 拿不到证据一律不放行**（D839 已确立，本卡保持）。
- 判定源分级：可信度高的证据源（已提交）优先，本地/未提交证据源**不得**单独解锁。
- 降级必须可见（铁律 11/24/31）：拿不到证据 ≠ 静默按未释放处理，须让算子看见"为什么没解锁"。

  - 正当场景：已提交 `impl_done` → `status=warn` / exit 0 + 释放理由；
  - `release` 台账记录含 `by`/`reason`/`at`/`basis_at_release`/`owner_at_release`（真落盘，可 `cat` 核）。

## 契约（铁律 47：先落契约，再写码）
```
_read_committed_json(repo, rel: str) -> (data|None, err|None)
  @input  仓库根（Path|str）+ 仓库相对路径（如 "task-state/D846.json"）
  @output (dict|None, None) 命中并解析成功；否则 (None, err 字符串)
  @degraded err 语义: "ENOENT:HEAD"  = HEAD 中无此文件（正常默认，非告警）
                      "git show ... rc=N" = git 层失败（仓库不可读等）
                      "JSONDecodeError: ..." = 已提交内容损坏（**必须告警**，铁律 24 区分 ENOENT）
  @exit   不抛异常（调用方决定语义）；git 超时 60s
task_status(repo, task_id) -> (status|None, degraded_reason|None)
  @input  repo + 任意含 D# 形态字符串
  @output 已提交 task-state/<D#>.json 的显式 status（str）
  @degraded 无 D# 形态 / HEAD 无此文件且工作树也无 → (None, err)（fail-closed，不当"已释放"）
            HEAD 无此文件但工作树有（未提交的卡）→ (None, "未提交（HEAD 无 …）")
            工作树 status ∈ RELEASED_STATUSES 而 HEAD status 不在 → (HEAD status, "工作树 status=X 与已提交 status=Y 不一致 → 不作为释放依据")
  @exit   不抛异常
load_ledger(repo) -> dict
  @output {"version":1,"releases":{...}}；读取仍走工作树（显式算子通道，见威胁模型）
  @degraded 台账文件不可读/损坏 → 空台账 + stderr 告警（fail-closed 不释放）
is_released(repo, task_id, ledger=None, archived=None) -> dict
  @output {"task_id","released","basis","detail","degraded"}
          basis ∈ {"ledger","task-state:<st>","session-archived",""}
  证据 1 ledger: 需要 rec["released"] 为真 **且** by/at/reason 均非空；缺凭证 → 不作证据（degraded 点名）
                 台账文件与 HEAD 有差异（记录未提交）→ 仍释放，但 degraded=True + detail 标注"未提交"
  证据 2 task-state: **已提交** status ∈ RELEASED_STATUSES("impl_done","audited")
  证据 3 session-archived: 本地 registry archived（gitignore，最弱源，已登记残余）
  @degraded 任一证据源不可读/不一致 → degraded=True + detail（铁律 11/24/31），**released 保持 False**
  @exit   不抛异常（调用方 staging_guard 亦包一层 fail-closed）
release_task(repo, task_id, reason, by) -> dict
  @input  task_id（D#）、reason（释放理由，非 owner 必填非空）、by（操作者标识，必填非空）
  @output {"ok":True,"task_id","ledger","record":{...}} 记录含
          {released,reason,by,at,basis_at_release,owner_at_release,lock:"pending"（D847 填）}
  @degraded by 为空 → ok=False（"操作者标识为空"）；非 owner/owner 不明且 reason 为默认或空 → ok=False（附可执行提示）
  @exit   写台账失败 → ok=False（**禁静默吞**）；CLI: ok=False → exit 2（契约不满足），成功 → exit 0
CLI 退出码（ctrl-tower-change 模式 1 三态）:
  0 = 成功（status 已释放 / release 成功 / scan 完成）
  1 = 业务否定（status 未释放 / release 任务号非法）
  2 = 契约不满足（仓库根不可识别 / 参数非法 / 台账写入失败或被拒）
```

## 威胁模型（K3 L4 建议②：新解锁路径的证据源谁能写、能否无痕伪造、拿不到证据是否 fail-closed）
| 证据源 | 谁能写 | 能否无痕伪造 | 本卡处置 |
|---|---|---|---|
| `task-state/<D#>.json` status | 任何本地进程（工作树/索引）／提交者（HEAD） | **改工作树或索引：能（K3 + 自验实证，零痕迹）**；改 HEAD：不能（进 git 历史 + PR 审查） | **闭合**：只认 `git show HEAD:`；工作树/索引与 HEAD 不一致 → degraded + 不释放（夹具 ①②⑤） |
| `task-state/claim-releases.json`（显式台账） | 任何本地进程（工作树） | **能**（直接写 JSON） | **部分闭合**：① 记录必须携带 `by/at/reason` 凭证否则**不作证据**（夹具 ③）；② 记录未提交（与 HEAD 有差异）→ 释放照旧但 **degraded=True + detail 显式标注"凭证在 git 历史中不可核"**（夹具 ④，把"无痕"变成"门禁输出里可见"）；**残余**：本地进程仍可写**带凭证**的假记录 → 显式登记，建议后续单开卡（方案：台账记录也只认 HEAD，代价见"被否决的方案 A"的死锁） |
| `.codex/control-tower/session-registry.json` archived | 任何本地进程 | **能**（且该文件在 `.gitignore:58`，永不进 git 历史） | **不闭合**（本卡范围外）：D839 派单明确保留该证据源（"或该 session 记录已归档"）；已在文件头与本节显式登记为**最弱证据源**，建议 CTO 裁决是否下线或改 git 跟踪 |
| `task-state/D<self>.json` 被他人暂存 | 任何本地进程 | 暂存他人卡本身不触发门禁（K3 §① 次级路径） | 不在本卡范围（D839 已知，提交路径有缓解） |
- **拿不到证据时**：全部路径 fail-closed（`released=False` → `staging_guard` 仍 block / exit 1）；降级信息经
  `res["degraded"]` + `detail` 显式传播（铁律 11/24/31），不静默。
- **总体威胁模型前提**（沿用 K3 §① 判断）：控制塔假设**本地 agent 非对抗 + PR 人工审查**；本卡目标是
