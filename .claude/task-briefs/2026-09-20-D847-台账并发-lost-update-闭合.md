## Q1: 调研 — 业界最佳实践 / Anthropic 决策链 / memory 历史教训
### a) 业界最佳实践
- **原子替换（tmp+rename）只解决"写一半被读到"，不解决"读-改-写丢更新"**（POSIX rename 语义）；
  丢更新必须靠**互斥**（锁）或 **CAS/乐观重试**。Kubernetes Lease / etcd 的做法：临界区 + 租约 + 过期回收。
- 文件锁的**正确获取**必须用原子原语：`O_CREAT|O_EXCL`（`flock` 语义），而不是"先 exists() 再写"
  （check-then-act = TOCTOU）。过期锁要能被回收，否则持锁进程崩溃 = 永久死锁。
- 锁不可得时的行为必须显式：要么阻塞到超时，要么拒绝执行；**绝不"假装成功"**（宁可失败也不静默丢写）。

### b) 顶级团队怎么做
- 临界区粒度 = **整个读-改-写**（不是只包 rename）；写临时文件名**每进程唯一**（共享 tmp = 竞态）；
- 锁超时/回收策略显式声明（我们的 `timeout_sec` = 过期阈值，崩溃残留锁可被回收）；
- 失败可观测：锁争用超时/降级写入都要留信号（铁律 11/24/31）。

### c) memory / 仓内历史教训
- `session_registry.py:79`：D209 的 `write_lock.acquire` TOCTOU 被显式记下却留着 → 本卡是它的**根因修复**，
  修好同时让 `session_registry` 的多进程互斥真正成立（共享同一实现）。
- `tests/control-tower/test-write-lock.py:94-109`：只读锁目录用例当前**在干净 HEAD 上即报错**
  （`acquire()` 内 `lock_path.exists()` 抛 PermissionError，未捕获 → 违反 D209 §5 "锁目录不可用 → degraded"）。
  本卡顺手修成契约（OSError → degraded allow + 显式告警），不动该测试文件（不在写集）。
- 自验（verifier-1）实证的第二故障模式：`save_ledger` 的共享 tmp 路径 `task-state/claim-releases.json.tmp`
  → 被别的进程 replace 掉后 `os.replace` 抛**未捕获 FileNotFoundError** → 进程 rc≠0；
  而**丢写的进程自己仍打印 `✅ 已释放` 且 rc=0**（静默丢写，最坏的一类）。
  实测 40 轮 × N=8：干净轮次 0、丢写 40/40、崩溃 20/40。
- 铁律 24/31（降级不静默/传播）、铁律 47/48（契约优先 + 非空壳测试）、ctrl-tower-change 模式 1/5。

### Q1c) 决策参考系
**参考：第一性原理 + Anthropic 工程基线 + 仓内实证 + 收敛检查**
1. **第一性原理**：台账是**共享可变状态的读-改-写**。并发的正确性只能由"临界区内完成整个 RMW"保证；
   原子替换解决的是可见性（半写），锁解决的是互斥（丢更新）——两者不可互相替代。
2. **Anthropic 工程基线**：① 复用既有机制（不新造锁）；② 锁获取必须原子（O_EXCL）；③ 失败显式
   （超时 → 拒绝写 + 报错；锁目录不可用 → degraded allow + 告警，符合 write_lock 既有 D209 契约）；
   ④ 崩溃可恢复（过期锁回收，无永久死锁）。
3. **仓内实证（实测，非推断）**：
   - 先红（本卡夹具，见回报原始输出）：基线跑 N=8 并发 ×2 轮 → 台账记录数 **<** 释放数 且存在 rc≠0 ——
     两类失效同时命中（与自验 40/40、20/40 同族）。
   - 被否决的方案 A（乐观 CAS 重试，不引入锁）：需要在 `os.replace` 前做"内容未变"校验，
     POSIX 无 `rename-if-unchanged` 原语 → 仍需锁或轮询比对，等价于自己造一个更脆的锁；
     且违反 D839 派单"复用同目录既有机制"。
   - 被否决的方案 B（把台账改成 append-only JSONL，天然免丢更新）：台账现为**单对象 JSON**，
     已被 `load_ledger` / 夹具 / 人读流程依赖；改格式会扩大爆炸半径（跨 3 个消费点），且 K3 只要求并发安全。
     记录为后续可选演进（遗留清单）。
4. **收敛检查**：三参考系同指一个答案——**复用 `write_lock.py` 并把它修成真原子，把整个 RMW 放进临界区，
   锁失败显式拒绝**。故直接执行，不升级创始人。

## 任务追加（CTO 裁决折入，2026-09-20）：事实源不变量 —— 调用者环境不得换掉被判定的仓库
来源：自验第二轮对 `13a12923`（D846）实测出的真 fail-open（**非 K3 报告记载**）。
- 现象：`GIT_DIR=<外部仓>/.git python3 staging_guard.py --session-id D902 --staged docs/x.md`
  → `status=warn degraded=false exit 0`，他人认领被解锁；被守护仓库 `git status` 干净、零提交、无痕。
- 根因：`_read_committed_json()` 的 `git -C <repo> show HEAD:<rel>` **继承调用者环境**；`-C` 只改工作目录，
  `GIT_DIR` 等仍能换掉"读哪个仓库"。D846 把证据源从工作树搬到 HEAD，但"HEAD 属于哪个仓"仍由环境决定
  → 文件级无痕路径封住了，**仓库级无痕路径还开着**。
- 本卡处置：所有 git 子进程改用 `_git_env()`（剔除**全部 `GIT_*`**，不只 `GIT_DIR`）——覆盖
  `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/`GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES`/
  `GIT_COMMON_DIR`/`GIT_NAMESPACE` 等一切能改变"读哪个仓库/哪些对象/哪个索引"的变量；
  剔除后若 git 找不到仓库 → 显式失败 → **fail-closed（阻断）**，方向正确。
  同族加固：`write_lock` 的模块解析**钉死在本文件所在目录**（`_pin_own_dir_on_path()`），
  不接受调用者 `PYTHONPATH` 注入同名模块。
- 同类面排查结论（要求 3）：`claim_release.py` 内仅剩 3 处读环境——
  ① `_git_env()` 自身（清洗器）；② `SYNO_CLAIM_LOCK_WAIT_SEC`（测试注入缝，只改等待时长，不改语义）；
  ③ `SYNO_AGENT`（`--by` 自我声明身份，非事实源；非 owner 反而更严）。
  **无其他"调用者环境决定事实源"的点**（已 grep `os.environ` / `subprocess.run` 全量核对）。
- 夹具：组 ⑪ —— 外部仓 HEAD 里 D901=impl_done（对照：直接读外部仓 → released）；
  逐个注入 5 个敌意变量 → **仍 exit 1（不释放）**；`GIT_DIR` 指回本仓 → 行为不变；
  端到端 guard + `GIT_DIR=<外部仓>` → **仍 block**。


## 契约（铁律 47：先落契约，再写码）
```
不变量（D847-追加）: **释放判定读哪个仓库，由函数入参 repo 决定，不由调用者进程环境决定。**
  实现 = 所有 git 子进程显式传 `env=_git_env()`（剔除全部 `GIT_*`）+ 保留 `-C <repo>`；
  模块解析（write_lock）钉死本文件所在目录（不取调用者 PYTHONPATH）。

WriteLock.acquire(file_path, owner="agent") -> dict      # 行为加严，返回形状不变
  @output {"acquired": True, "lock_id": str} | {"acquired": True, "lock_id": "", "degraded": True}
          | {"acquired": False, "reason": str}
  @实现   原子获取: os.open(lock_path, O_CREAT|O_EXCL|O_WRONLY, 0o644) → 写 pid/timestamp/owner
          已存在: 过期(_is_expired) → unlink 后重试一次；未过期 → acquired=False（reason 点名）
  @degraded 锁目录不可创建 / 锁文件 OSError（含只读目录 PermissionError）→ acquired=True + degraded=True
            （D209 §5 既有契约，本卡把它从"抛异常"修成"按契约降级"）
  @exit   不抛异常（全部 OSError 归入 degraded 分支）

claim_release.save_ledger_locked(repo, mutate_fn) -> dict
  @input  mutate_fn(ledger: dict) -> dict（锁内执行的纯修改）
  @output {"ok": True, "ledger": {...}, "lock": "held"|"degraded:<原因>"}
        | {"ok": False, "code": 2, "error": str}
  @degraded ① 锁降级（目录/文件不可用）→ ok=True + lock="degraded:<原因>" + stderr 告警（不静默）
            ② 争用超时（> LEDGER_LOCK_WAIT_SEC=15s）→ ok=False（**拒绝写入**：宁可失败也不丢记录）
            ③ write_lock 模块不可 import → ok=False + 明确报错（机制缺失不静默降级为无锁写）
  @exit   不抛异常（内部 OSError 全部转 ok=False）
release_task(...) -> dict   # 契约同 D846，新增：写失败时 error 来自 save_ledger_locked
CLI 退出码: 0 成功 | 1 业务否定（task_id 非法）| 2 契约不满足（凭证被拒 / 锁争用超时 / 写入失败）
```

## 威胁模型（本卡新引入的失败模式面）
| 面 | 处置 |
|---|---|
| 并发写丢失记录（K3 P1-3） | 整个 RMW 进 `O_EXCL` 互斥临界区 → 序列化，无 lost-update（夹具断言 count==N） |
| `acquire()` 的 TOCTOU（D209 遗留） | 改原子 `O_EXCL`；两进程不再能同时"成功"（夹具断言 N 进程 rc=0 且记录不丢） |
| 共享 tmp 路径被并发 replace | pid 唯一 tmp 名 + 锁内写（双重消除） |
| 持锁进程崩溃 | 锁文件带 timestamp，超 `timeout_sec=30` 视为过期 → 回收后重试（夹具：timestamp=0 的残留锁 → 下一次 release 仍成功） |
| 锁争用超时 | **拒绝写入** + exit 2（禁静默丢记录） |
| 锁目录不可用（只读/权限） | 按 D209 契约 degraded allow + `lock="degraded:…"` + stderr 告警（显式可见，不静默） |
| 拿不到锁机制（write_lock 缺失） | 拒绝写入 + 明确报错（不静默退回无锁 RMW） |
