0 Part 0: 产品灵魂 - 核心逻辑、专家生态、模板进化

在深入代码缺陷和架构细节之前,必须先理解这个产品为什么存在、它要解决什么问题、以及它的护城河在哪里。所有的技术设计、模块化拆分、执行路线,都服务于这个核心逻辑。

0.1 为什么存在:行业痛点

核心洞察:大多数公司请不起顶级咨询公司,请到了也未必合适。

中小咨询公司只能看到组织的局部,诊断开方片面。
传统咨询最大的问题是基于时点的方案,不是运行时的动态实时方案--企业花了很多钱,实际解决问题的有限。
技术环境在变,组织架构在变,人员工具在变,但咨询报告交上去就定格了。

基于这个时代背景和技术能力,未来的组织一定是人 + Agent 的组织。

SynovaAgent 的核心定位:部署在企业本地的、实时运行的组织医生。

不是聊天机器人。不是报告生成器。不是一次性工具。是一个持续感知、持续诊断、持续出方案的系统。

0.4 商业闭环:行业专家生态

护城河不是技术,是"行业隐性知识 + 持续进化"的组合。

大厂有技术但没有这些知识。
中小咨询公司有知识但没有持续进化的能力。
LLM 有通用能力但给不出行业特有的深度判断。
Synova 把这三者的短板补上。

LLM 训练数据是"通用常识"--所有公司都能用,不构成竞争壁垒。

真正的壁垒是行业老兵 20 年积累的"隐性知识"。

问题 A 出现时,LLM 基于统计推断根因是 B。但一个在制造业干了 20 年的老兵一眼就知道根因是 D。这个 D 不在任何公开数据集里,只在老兵的脑子里。

0.4.1 第一层:激活专家 - 从 0 到 1

不是给专家写代码的工具。他们不懂技术,也不想学。

是一个让行业专家用自然语言或简单表单就能贡献行业知识的入口:

行业专家进来 → 选择行业(制造业) → 选择场景(人员流失率高) → 描述问题:"我们厂的问题不是工资低,是排班不合理,老员工夜班太多" → 系统自动提取: 症状节点:人员流失率高 根因节点:排班制度不合理(而非 LLM 推断的"薪酬竞争力不足") 边类型:TRIGGERS(排班制度 → 人员流失) 置信度:高(来自 20 年经验) 行业标签:制造业 → 存入行业本体模板库 v1.0
角色需求系统设计
行业专家不懂技术,但有行业经验自然语言/表单入口,系统自动提取结构化知识
审核专家验证他人贡献的知识多专家交叉验证机制,置信度评估
系统自动提取结构化知识LLM 辅助提取:症状→根因→边→标签→置信度

0.4.2 第二层:模板进化 - 从 1 到 ∞

从业 20 年的专家的经验,有隐性知识可复用,但也有一些经验是过时的。

过去的技术环境和现在不同,和未来更不同。不能用孙子的带兵和练兵方法来指导现代的战争,但他的智慧可以用。

系统需要区分两类知识:

  • 原理层(why) - 为什么排班不合理会导致人员流失。timeless,可能长期有效。
  • 方案层(how) - 具体怎么排班。随技术、法规、市场变化可能过时。

0.5 产品定位一句话总结

把麦肯锡级的组织诊断能力 + 行业老兵的隐性知识 + 持续进化的系统,做成一个部署在企业本地的 AI Agent,让 5-300 人团队也能负担得起,并且越用越准。

技术架构:L1 交互层 → L2 编排层 → L3 分析层 → L4 本体层 → L5 数据层。
所有开发--适配器、定时任务、连接器、工具注册、扩展机制、专家平台--都是为了服务 L1-L5 核心逻辑。
L4 本体层是核心(RDF 三元组 + 双时序永不删除 + EntityRegistry),L5 数据层是入口(OntologyAdapter 接口 → OntologyEvent 事件管道),L2 编排层是中枢神经(六阶段状态机 + 事件驱动)。

1.2 Critical 缺陷(阻塞级)

#C1 - streamWithToolLoop 双重 LLM 调用
src/agent/conversation.ts
每条用户消息调用 LLM 两次:先 stream() 获取文本回复,再 chat() 带 tools 检测工具调用。
后果:API 成本翻倍;stream 和 chat 结果可能不一致;用户看到的流式内容与最终工具调用不匹配。
修复:统一为单次 chat() 调用,从结果中提取文本做流式输出。预估 2-3 小时。
#C2 - 首条消息后输入框可能锁死
src/tui/chat.ts - onSubmit 回调
streaming 状态 + focus() 异常可能导致用户无法发送第二条消息。等待期间无任何反馈,120 秒超时期间用户可能以为卡死。
修复:添加"处理中"状态提示。预估 30 分钟。

🔒 架构决策冻结(2026-06-03 确认)

决策 1:L1-L5 五层解耦架构(权威技术架构)
L1 · 交互层:SSE 对话 | Cytoscape.js 图可视化 | 报告仪表板 | 飞书/钉钉/企微 IM
L2 · 编排层:六阶段状态机(不变) + 持续后台分析 + 事件驱动实时分析 + SSE 流式推送
L3 · 分析层:6 专家子 Agent(ontologyPatch 输入) + 29 计算模块 + 事件处理器管道 + 模板进化引擎
L4 · 本体层:GraphStore(可替换后端: SQLite → SurrealDB) + RDF 三元组 + 双时序(永不物理删除) + EntityRegistry
L5 · 数据层:OntologyAdapter 接口 + 飞书/GitHub/Jira 适配器 + OntologyEvent 事件管道
全貌报告(ARCH-20/21)的 L1-L5 为唯一权威技术架构。编码智能体必须按照此架构执行。
注意:L2 编排层是独立层,不是交互层的一部分。专家 Agent 在 L3 内部,不是独立层。

决策 2:领域包拆分是硬性要求
engine-core 的 297 文件必须按领域拆分为独立的 npm 包(@synova/sog-core、@synova/diagnosis-engine 等)。
每个包有独立的 package.json、独立版本、独立测试。
这是明确要求,不是建议。编码智能体必须执行拆分。

决策 3:知识摄取(Knowledge Ingest)是必需能力
用户上传组织文档(PDF/DOCX/Excel)→ 自动解析 → 提取实体和关系 → 构建 SOG 本体。
诊断基于事实而非记忆。矛盾检测依赖文档数据与访谈数据的对比。
这是明确要求,不是可选功能。编码智能体必须在 Phase 2 完成接线。

决策 4:Connector-Registry 是平台基石("组织管理的 AWS")
双向集成平台标准:我们适配所有 SaaS/Agent(飞书/ERP/OA/NemoClaw),同时开放标准让第三方接入我们。
企业接入第三方 SaaS 时自动获得诊断能力;第三方 SaaS 接入 Synova 后自带组织诊断能力。
这不是"两个适配器文件",是整个平台的能力集成边界。编码智能体必须按此规格设计。

决策 5:ToolRegistry 是动态能力注册中心,不是静态本地函数表
当前 26 个工具全是本地函数,无法连接外部系统。必须扩展为多执行模式(local/connector/remote-agent/http)。
Connector 和 Agent 框架启动时自动注册自己的工具到 ToolRegistry。
专家 Agent 没有工具调用能力就无法完成实际诊断工作。编码智能体必须在 P1 修复时同步扩展。

决策 6:架构必须支持运行时无限扩展
SOG 本体(节点/边类型)、专家 Agent、诊断模块、工具、技能、Connector--全部必须支持运行时扩展。
企业部署后按实际业务需要按需加载扩展,无需改核心代码、无需重新编译、无需重新部署。
扩展通过声明文件(JSON/YAML)+ 实现文件(TS/JS)+ 注册接口完成,有完整的生命周期管理。
当前架构只有扩展的"想法",没有扩展的"机制"。编码智能体必须建立运行时扩展注册中心。

决策 7:Expert-Platform 行业专家贡献平台是护城河
LLM 训练数据是通用常识,不构成竞争壁垒。真正的壁垒是行业老兵 20 年积累的"隐性知识"。
必须建立一个让不懂技术的行业专家用自然语言就能贡献知识的入口。
专家贡献的不是代码,是行业本体模板(症状→根因→边→置信度→行业标签)。
商业闭环:专家贡献→诊断更准→用户更多→更多数据验证模板→模板进化→诊断更准→吸引更多专家。
编码智能体必须在 P1 完成基础框架。

决策 8:本体模板必须有持续进化能力
行业专家的经验有隐性知识可复用,但部分经验会随技术环境变化而过时。
系统必须区分原理层(why/timeless,如"排班不合理导致人员流失"的原理)和方案层(how/context,如具体排班方案)。
模板进化引擎:用真实诊断结果持续检验模板有效性,自动标记有效/部分有效/待验证/失效。
模板变化时自动推送给贡献者复核,确认过期时标记为"历史参考",原理层保留为智慧。
编码智能体必须在 P1 同时完成模板进化引擎基础框架。
结论:ARCH-20/21 的 L1-L5 架构设计是正确的，所有差距项已在本报告中裁决。
主要差距不在设计,而在执行——engine-core 中已有大量能力实现,但没有接线到 synova-agent 的对话流。
现在架构设计、模块化拆分、专家生态、模板进化都已明确为硬性要求,编码智能体按此执行即可。
