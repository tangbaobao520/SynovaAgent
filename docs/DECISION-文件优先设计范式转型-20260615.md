> 状态：已决策，待实施
> 基于：OpenClaw vs Synova-Agent 深度对比报告 + 与创始人对齐讨论

## 一、起源：一次对比带来的认知跃迁

2026-06-15，Claude Code 完成了 OpenClaw 与 Synova-Agent 的深度对比报告（[COMPARISON-OpenClaw-vs-SynovaAgent-20260615.html](COMPARISON-OpenClaw-vs-SynovaAgent-20260615.html)）。

报告的技术结论是：**两个系统定位不同，各有所长。**

但创始人黄学松在阅读报告后，提出了一个超出技术对比的洞察——OpenClaw 的设计哲学不是技术选择，是**权力分配**：

> *"我认为这个设计哲学，恰恰就是他可以让无数用户可以独立创造的乐趣——这种极其方便的无限拓展和创造，让他成为 GitHub 历史增长最快的应用。"*

这个直觉触及了本质。本文档记录从此处产生的范式转型决策。

## 二、重新理解 OpenClaw 成功的原因

### 2.1 表面原因 vs 深层原因

| 表面解释 | 深层解释 |
|---------|---------|
| Agent 运行时性能好 | **创造的门槛降到了写文件** |
| Gateway 架构先进 | **谁都可以创造 Agent、创造技能** |
| MCP 协议标准化 | **配置像代码一样可管理、可分享** |
| 社区活跃 | **因为用户不仅是消费者，也是生产者** |

OpenClaw 增长快不是因为技术比别的框架好。是因为它重新定义了 **"谁有资格创造"**。

### 2.2 新旧模式的创造权对比

| 维度 | 传统 Agent 框架（代码优先） | OpenClaw（文件优先） |
|------|---------------------------|---------------------|
| 创造 Agent | 写 TypeScript 类 + 注册 | 写 IDENTITY.md + SOUL.md |
| 创造技能 | 实现插件接口 | 写 SKILL.md（自然语言） |
| 配置系统 | 环境变量 / 数据库 | openclaw.json |
| 修改行为 | 改代码 → 编译 → 重启 | 改文件 → 立即生效 |
| 参与者 | 开发者 | **任何人** |

OpenClaw 的成功不是一个技术突破，是一个**社会学突破**——它把 AI Agent 的创造权从开发者还给了用户。

### 2.3 "配置即代码"的通俗解释

创始人提到不太理解"配置即代码"。这里做一个彻底的通俗解释：

**环境变量方式（Synova 当前）：**
```bash
export LLM_API_KEY=sk-xxx
export LLM_MODEL=deepseek-chat
export PORT=18789
```
→ 配置散落在 shell 脚本、系统服务、部署流水线里。改过什么？谁改的？改之前是什么？全凭记忆。改崩了回不去了。

**OpenClaw 的 openclaw.json：**
```json
{
  "gateway": { "port": 18789 },
  "models": {
    "providers": {
      "deepseek": { "apiKey": "sk-xxx" }
    }
  }
}
```
→ 一个文件管所有。可以 `git commit`。可以 `diff` 看到改了什么。可以 `openclaw.json.last-good` 回滚。

**"配置即代码"的实际含义：**

| 环境变量 | 配置即代码 |
|---------|-----------|
| 在哪里？ | 在脑子里 / 在文档里 | 在文件里 |
| 谁改过？ | 记不清了 | `git log` 可查 |
| 改了什么？ | 不知道 | `git diff` 可见 |
| 改崩了之后？ | 手动回忆找回 | 回滚版本 |
| 能不能 Review？ | 不能 | 可以 PR Review |
| 团队怎么同步？ | 口头传播 | 版本库共享 |

**"配置即代码"不是说配置要写成代码，是说配置应该像代码一样被严肃管理。** 有版本、有审计、有回滚、有 Review。

## 三、Synova 现有的设计哲学：发生了什么问题

### 3.1 当前状态：创造权高度集中

在 Synova 当前的架构中，几乎所有可定制的东西都在代码里：

| 要做什么 | 当前怎么做 | 需要谁 |
|---------|----------|-------|
| 加一个新专家 | expert-registry.ts + DataAccessPolicy + system prompt | TypeScript 开发者 |
| 改专家诊断风格 | 改硬编码在代码里的 system prompt | TypeScript 开发者 |
| 改测量器阈值 | 改代码常量 / 数据库 | 开发者 / DBA |
| 加行业知识 | INSERT INTO knowledge_base | 有 DB 权限的人 |
| 调整 FDE 工作流 | 改 routes + engine-core | TypeScript 开发者 |
| 客户定制诊断维度 | 改代码 | TypeScript 开发者 |

**每一条路径都假设用户是开发者。** 而 Synova 的目标用户是 FDE（前线部署工程师）——他们懂企业诊断、懂行业，但很多不是 TypeScript 开发者。

**这是个错配。** 我们已经把诊断方法论文本化了（八维初诊框架、7 位专家理论、六维混合组织能力模型），但这些方法论的落地路径仍然需要写代码。知识在文档里，但把知识放进系统需要工程师。

### 3.2 对产品增长的限制

如果每个客户定制都要 FDE 回来找开发改代码：

```
客户有特殊需求 → FDE 提交需求 → 开发排期 → 改代码 → 部署 → 客户验证
                                     ↑
                              这步就是瓶颈。
                              开发者数量有限，
                              排期有优先级，
                              小需求被大需求挤掉。
```

这意味着：
- **FDE 的创造力被开发者的产能限制了**
- **客户定制响应速度 = 开发排期速度**
- **系统越用，定制需求越多，积压越严重**

**这个模式跑不动。** 在 5-300 人企业这个市场，客户需求多样性极高，不可能靠开发团队一个个适配。

### 3.3 对生态能力和数据飞轮的限制

当前的知识积累只有两种方式：
1. 开发者写代码（慢、贵、不可持续）
2. FDE 在八维访谈中口述记录（不可结构化的知识进了 SessionStore 而不是本体层）

行业经验真正进入系统的方式是第 1 种——开发者写代码。这意味着行业贡献者的范围被限制在"懂 TypeScript 的组织诊断专家"这个极小集合里。

## 四、新设计哲学：从"Agent = 代码"到"Agent = 文件"

### 4.1 核心转变

**之前：** Agent 的行为定义在代码里。改行为 = 改代码。

**之后：** Agent 的行为定义在文件里。改行为 = 改文件。

```
旧模式：
  System prompt = 代码（src/l1/l0-global-prompt.ts）
  专家定义 = 代码（expert-registry.ts + 硬编码 prompt）
  测量器配置 = 代码 + 数据库
  知识 = 数据库 / API 返回

新模式：
  专家定义 = .md 文件（文件系统）
  测量器配置 = .yml 文件（文件系统）
  知识 = .md 文件（文件系统）
  系统配置 = .json 文件（文件系统）
  ↑
引擎启动时扫描文件目录，运行时读文件，文件变了 Agent 变了。
```

### 4.2 遵循的原则

```
1. 引擎读文件，不读代码
   → 运行时行为由文件决定，不是由代码分支决定

2. 文件变了 = Agent 变了
   → 不需要重启进程，不需要重新编译

3. 写文件 = 创造/定制
   → FDE 写文件不需要 TypeScript 知识

4. 引擎核心不变，壳层文件可变
   → 核心引擎用代码维护（质量、安全、性能）
   → 行为定义用文件维护（灵活、可定制、可扩散）
```

### 4.3 不是照搬 OpenClaw

OpenClaw 的文件优先是单人单 Agent。Synova 是 7+ 专家 + 25 测量器的企业诊断系统。所以 Synova 的"文件优先"多了一层控制：

```
OpenClaw 版本：
  文件 → 直接注入 system prompt（给 LLM 读）

Synova 版本：
  文件 → 引擎解析 → 注入各专家上下文（给引擎 + 专家读）
          ↑ 多了一层"解析编排"
```

这个区别意味着：

- OpenClaw 的文件 = 给 LLM 的自然语言指令
- Synova 的文件 = 给引擎的结构化配置 + 给 LLM 的领域知识

**多了一层控制，但也多了一层表达能力。** 不再是"文件内容直接进 prompt"，而是"文件内容经引擎理解后，分配到最合适的专家上下文"。

## 五、具体要做的事

### 5.1 三层文件体系

#### 第一层：专家 = 文件

把专家的定义从 TypeScript 代码移到文件系统。

```
synova-agent/expert/
├── strategy/                  ← 战略专家
│   ├── IDENTITY.md            ← 角色定义
│   ├── SOUL.md                ← 诊断风格 + 方法论
│   ├── TOOLS.md               ← 可用工具列表
│   ├── RULES.md               ← 诊断规则 + 评分指南
│   └── KNOWLEDGE.md           ← 依赖的领域知识
├── org/                       ← 组织专家
│   └── ...
├── finance/                   ← 财务专家
│   └── ...
└── ... (7+ 专家)
```

**谁可以创造/修改专家？** FDE。

FDE 不需要写 TypeScript。FDE 写 Markdown，跟写八维初诊访谈记录一样——是"写文档"而不是"写代码"。一个懂行业有经验但没有技术能力的人也能做 FDE——这是产品定位中就写明的承诺。

#### 第二层：测量器配置 = 文件

把测量器的阈值、频率、信号路由从代码/数据库移到文件系统。

```
synova-agent/measurers/
├── 现金流健康.yml
│   ---
│   dimension: D1             # 所属维度
│   frequency: weekly         # 巡检频率
│   baseline_window: 90d      # 基线窗口
│   threshold: 0.15           # 异常阈值
│   signal_routing: finance_expert  # 异常发往哪个专家
│   ---
├── 协作健康度.yml
│   ---
│   dimension: D2
│   frequency: daily
│   baseline_window: 30d
│   threshold: 0.3
│   signal_routing: org_expert
│   ---
└── ...
```

**谁可以改测量器配置？** FDE 和企业主。

企业主不需要写代码，但可以在看板里拖拽"我这家公司的告警灵敏度"。底层存的就是这个 YAML。

#### 第三层：行业知识 = 文件

把行业知识从数据库移到文件系统。

```
synova-agent/knowledge/
├── 月子中心行业/
│   ├── 竞争格局.md            ← 行业老兵写的 markdown
│   ├── 关键财务指标.md
│   ├── 常见风险模式.md
│   ├── 客户需求变化趋势.md
│   └── 区域差异特征.md
├── 跨境电商/
│   ├── 税务合规框架.md
│   ├── 物流瓶颈分析.md
│   └── 平台政策风险.md
├── SaaS 企业/
│   └── ...
└── ...
```

**谁可以贡献行业知识？** 任何有行业经验的人。

FDE 在服务客户过程中积累的行业经验，写成 Markdown 文件，经审核后进入共享知识库。这是数据飞轮的入口。

### 5.2 核心引擎需要新增的组件

| 组件 | 功能 | 优先级 |
|------|------|--------|
| **FileScanner** | 启动时 + /api/reload 时扫描文件目录，建立索引 | P0 |
| **ExpertFileLoader** | 解析 IDENTITY.md / SOUL.md / TOOLS.md → 注册到 ExpertRegistry | P0 |
| **MeasurerConfigLoader** | 解析 YAML 配置 → 注册到 ModuleRegistry | P0 |
| **KnowledgeFileImporter** | 解析知识 Markdown → 写入本体层知识条目 | P1 |
| **FileWatcher** | 开发模式下监听文件变更自动热加载 | P2 |

### 5.3 需要移除/保留的现有组件

**保留（核心引擎，不文件化）：**
- ExpertDispatcher 并行执行引擎
- ToolGuardrails 安全机制
- Sentinel + CronScheduler 调度框架
- GraphStore 本体层读写接口
- 交叉验证引擎
- QualityFirewall

**逐步文件化（从代码移到文件）：**
- 各专家的 system prompt → SOUL.md / RULES.md
- 各测量器的配置 → .yml 文件
- 行业知识 → knowledge/ 目录下 .md 文件
- 客户专属配置 → clients/{clientId}/ 目录

### 5.4 变革后各角色的创造路径

| 角色 | 现在能做什么 | 文件化后能做什么 | 创造门槛 |
|------|------------|---------------|---------|
| **FDE** | 用操作台启动诊断 | 写专家文件、改测量器阈值、加行业知识 | 从"需要工程师配合"到"自己搞定" |
| **行业老兵** | 只能给 FDE 提需求 | 直接写 KNOWLEDGE.md 贡献行业知识 | 从"请你帮我加"到"我自己写" |
| **企业主** | 看诊断报告 | 看报告 + 调自己企业的测量器敏感度 | 从"被动接收"到"主动参与" |
| **开发者** | 什么都要写 | 只维护核心引擎，壳层由文件驱动 | 从"啥都干"到"只干最难的" |

## 六、分阶段实施路线

### Phase 0：范式验证（现在 — 2026-07-15）

**目标：** 用 1 个专家验证"文件定义行为"成立。

**具体：**
1. 选一个相对简单的测量器专家（如现金流测量器），把它从代码定义移到 YAML 配置 + 行为文件
2. 写一个 FileScanner 的原型，扫描后注入到 ModuleRegistry
3. 验证：在 YAML 里改了 threshold，再调 POST /api/reload，系统行为确实变了
4. 验证：FDE 写一个 SOUL.md，专家的诊断风格确实变了（不经过开发）

**失败条件：** 如果 FDE 改文件后无法立即感知效果，说明文件化架构有问题，需要重新设计文件加载/注入方式。

### Phase 1：文件加载引擎（2026-07 — 2026-09）

**目标：** 实现文件加载基础设施，覆盖三层文件体系。

**具体：**
1. FileScanner：启动扫描 + /api/reload 热加载
2. ExpertFileLoader：解析 SOUL.md / IDENTITY.md / TOOLS.md / RULES.md → ExpertRegistry
3. MeasurerConfigLoader：解析 .yml → ModuleRegistry
4. KnowledgeFileImporter：解析 .md → 本体层知识条目
5. 所有 7+ 专家的定义从代码迁移到文件

### Phase 2：生态工具（2026-09 — 2026-12）

**目标：** 让 FDE 和行业老兵可以独立使用。

**具体：**
1. CLI 工具：`synova expert create` / `synova measurer list` / `synova knowledge add`
2. 专家文件模板生成器：交互式引导 FDE 创建新专家
3. 知识文件的格式校验和预览
4. FDE 工作台集成：在操作台 UI 里直接编辑专家文件

## 八、为什么现在要这样做

1. **Synova 的产品定位就是"让有行业经验、有客户资源但没有技术能力的人也能做 FDE"**。文件优先是这个定位的工程落地。不是可选的，是产品承诺的一部分。

2. **生态和数据飞轮需要一个低门槛的贡献入口**。如果知识的产生要经过开发者，飞轮转不起来。文件优先让行业老兵可以直接贡献——他们是飞轮的核心驱动力。

3. **CLAUDE.md 铁律 39（五层架构边界）为文件化提供了架构基础**。当前五层解耦使得替换"壳层"不需要动核心引擎。核心引擎在代码中保持安全稳定，行为定义在文件中保持灵活可扩展。

4. **现在改比以后改成本低**。当前专家定义还在拼装阶段（数据层+逻辑层+prompt 层未完全解耦），还有违规需要修。等全部硬编码稳定后再拆，成本更高。

5. **OpenClaw 用这个模式在 1 年内从 0 做到 GitHub 增长最快**。虽然 Synova 做的是垂直领域而不是通用平台，但"降低创造门槛"这个底层逻辑是通用的。

---

## 九、核心原则（不可妥协）

```
1. FDE 写 Markdown 不等于 FDE 写代码
   → 文件模板必须足够简单，FDE 只需要填空和写自然语言

2. 改文件 5 分钟内必须生效
   → /api/reload 必须在 5 秒内完成热加载

3. 文件出错不影响引擎运行
   → 文件解析失败 → 降级使用默认值 + 告警，不崩溃

4. 文件是"配置 + 知识"，不是"脚本"
   → 文件不执行代码。执行路径始终由核心引擎控制

5. 引擎的职责是读文件、解析、注入
   → 引擎不写文件、不修改文件。写入是人的工作
```

## 附录：与创始人对谈关键摘录

**问：** "配置即代码"这个概念不太好理解？

**答（转述）：** 配置即代码不是说配置要写成 TypeScript。是说配置应该像代码一样被管理——有版本、可审计、可回滚、可 Review。环境变量相当于把配置写在脑子里，文件相当于把配置写在纸上让团队都能看。

**问：** 文件优先设计哲学的关键是什么？

**答（转述）：** 不是技术选择，是权力分配。OpenClaw 把"创造"的权力从开发者还给了用户。当创造的门槛降到写文件，用户量就不受开发者供给限制了。

**问：** Synova 套用这个哲学要注意什么？

**答（转述）：** OpenClaw 的文件直接给 LLM 读。Synova 的文件给引擎读，引擎再决定怎么给专家用。多了一层控制，也多了一层表达能力——不再是"文件内容直接进 prompt"，而是"文件内容经引擎理解后分配到最合适的专家上下文"。
