一、产品的起点 ✅ 已定稿

1.1 企业永远的需求是什么

按照克里斯坦森的"需要完成的任务"（JTBD）理论：企业"雇佣"任何东西——咨询、培训、软件、方法论——都是为了完成一个任务：增长。达成业务目标。

但企业每天进行无数活动：

  • 有些在推动增长目标（应该识别并加强）
  • 有些在拖慢增长（流程低效、协作断裂、决策卡壳）
  • 有些本身成了阻塞点（关键人离职、技术债堆积、现金流缺口）
  • 有些在积累风险（单点依赖、市场盲区、合规隐患）

企业家和管理层天天泡在这些活动里，很难看清全景——哪些在推、哪些在拖、哪些快炸了。

Synova 要回答的核心问题：这家企业的增长卡在哪里？现在该做什么？

1.2 定位：Agent，不是 ChatBot

Synova 是一个 Agent（智能体）——它驻扎在企业内部，持续观测、主动发现问题、自动诊断根因、提出可落地的方案、跟踪执行效果。它替企业干活。

不是 ChatBot。区别：

ChatBotAgent
交互方式用户问一句，它答一句驻扎在企业里，主动观测、主动诊断
工作模式被动响应持续运行，7×24 小时
输出一段文字回答诊断报告 + 行动建议 + 执行跟踪
市场竞争遍地都是，没壁垒系统性诊断能力 = 壁垒
用户价值省了搜索和整理的时间帮企业看清增长卡点、做更准确的决策

1.3 能力的层次：核心 vs 支撑 vs 基础设施

支撑 7 维度监测 × 25 哨兵 × 8 专家推理 7 个监测维度（增长动力/组织能力/人+Agent/软件生态/软件-Agent适配/战略健康/风险预警）统一了"我们看什么"。每个维度下 3-7 个哨兵，一个 compute() 函数支持两种模式——FDE 按需诊断 + Cron 定时巡检。8 专家消费信号池中的异常信号，启动推理。

二、用户角色 ✅ 已定稿

2.1 FDE（Forward Deployed Engineer）= 直接用户

Synova 的直接使用者是 FDE（前线部署工程师）。

FDE 是这么一类人：

  • 在某个行业有长期经验积累
  • 手里有企业客户资源
  • 自己能搞定客户沟通、取得信任、做初步判断
  • 但缺乏系统性诊断工具——靠经验能感觉到"这个公司有问题"，但无法系统地诊断出问题在哪、根因是什么、怎么解决

为什么需要 FDE 这个角色：真正的咨询，大部分时间花在沟通和建立信任上。纯 Agent 跟客户直接对话，在目前阶段信任度还不够。FDE 补上这个缺口——人跟人建立信任，Agent 在背后提供系统性能力。

但传统 FDE 很难养：行业对 FDE 的能力要求太高，薪酬也高，一般只有大厂才养得起。Synova 要做的，就是把 FDE 本来需要做的事情工程化，做成产品的一部分——让有行业经验、有客户资源但没有技术能力的人也能做 FDE。

一个 FDE 用 Synova 服务 10-20 家长稳客户，就能活得比打工好。这是 Synova 的商业价值基础。

2.2 FDE 的三类来源

  1. 创始团队自己（黄学松）——手上有资源、有意向客户，产品跑通后立刻能用
  2. 行业老兵转型——在某个行业干了很多年，懂业务但缺系统性工具，借助 Synova 可以独立服务客户
  3. 中小咨询公司——在组织管理/营销/财务/自媒体等垂直领域有客户基础，用 Synova 补全诊断维度、提升获客和服务能力

2.3 企业主 = 最终受益者

企业主是 Synova 最终且唯一的服务对象。 前期 FDE 在中间做翻译和导入——建立信任、完成初次部署。但 Synova 的最大价值不在于 FDE 永远做中间桥梁，而在于：

  • FDE 完成第一次部署和导入后，企业最好指派一个人负责对接 Synova——这个人可以是老板自己、高管、或有执行力的中层
  • 这个人不需要是 FDE——不需要行业咨询能力，不需要自己去诊断。他只需要跟进系统给出的信号和报告，协调内部资源去执行
  • 这样才能发挥产品最大性能——系统 7×24 监测，企业内部有人响应。FDE 变成定期回访和深度诊断的角色，而不是日常信使

FDE 的长期角色从"翻译桥梁"转变为"深度诊断 + 长期陪跑"——日常的信号和报告企业自己看，重大的战略决策和复杂诊断 FDE 介入。

企业主自助完成初次部署是远期目标——当前阶段企业主需要 FDE 引导才能完成导入。但部署之后，企业主直接作为受益者和系统交互的场景必须在产品设计中预留。

2.4 FDE 建设者角色

FDE 不仅是 Synova 的使用者，也是共建者：

  • 在使用过程中纠正诊断（这个判断不对，实际情况是……）
  • 补充行业经验（这类企业通常还有这个问题你们没覆盖到）
  • 这些反馈会进入 Synova 的本体层，优化诊断能力
  • 一个 FDE 的经验沉淀下来，所有 FDE 都受益

三、理论基础与可行性 ✅ 已定稿

3.1 企业持续成长的条件

Synova 的目标不是做组织诊断。诊断是手段，目的是增长——识别增长的阻力点，找到卡住的地方，给出能落地的行动建议。组织诊断之所以重要，是因为一个简单的前提：没有好的组织，不可能有长期稳定的增长。增长需要的不是一次性冲刺，是组织能持续运转、持续适应、持续产出。这就是为什么我们必须研究组织能力——不是为了学术，是为了增长。

一切不能帮助客户实现增长的咨询或工具，生命力都有限。只有能帮助客户实现增长的，才有长期价值。

我们的理论基座——杨国安（2009）提出的企业持续成功 = 战略 × 组织能力——是 Synova 逻辑的起点。十七年过去，AI 和人机协作已经根本性改变了组织的运行方式。我们的判断是：公式本身依然生效，但"组织能力"的内涵必须彻底重构。AI 的加入让这个公式从静态模型变成了动态闭环。

以下从五个层次拆解。

第一层：公式本身——乘法逻辑依然成立

"战略 × 组织能力"的核心洞见是：两者是乘数关系，不是加数关系。战略再正确，组织能力为零，结果就是零。反过来，组织能力再强，战略错了，也是南辕北辙。

这个底层逻辑在任何时代都成立。AI 来了，它改变的是"战略"和"组织能力"各自的内容，不是它们之间的乘数关系。无论有多少 AI Agent、多少数据管道、多少自动化，只要一个组织还在竞争，它就需要回答"往哪走"（战略）和"能不能走到"（组织能力）。

第二层：战略一端——AI 让战略周期急剧缩短，但战略本身更重要了

传统战略规划以年为单位。但 AI 让市场变化加速，数据让竞争动态实时可见。一个战略的有效期可能从三年缩短到半年。

但这并不意味着"不需要战略了"。恰恰相反：当环境变化越快，清晰的战略方向越重要。没有方向的组织，AI 会让它更快地撞上墙——因为 AI 会加速执行，加速消耗资源，加速暴露战略缺陷。

7 Powers 理论（我们的战略诊断基石）在 AI 时代变得更加锋利：

  • 规模经济：AI 让固定成本（模型训练、数据管道）占比更高，规模效应更强。
  • 网络效应：AI 产品天然适合数据飞轮，赢者通吃更明显。
  • 流程优势：AI 驱动的流程可以被复制吗？如果可以，就不是壁垒；如果不可以（如专属数据 + 专属本体），就是最强的壁垒。
  • 反定位：大厂有通用 AI，但无法做垂直诊断——这正是 Synova 的反定位。

所以战略这一端，公式不变，但诊断工具必须升级——从"静态竞争分析"变成"动态壁垒监测"。

第三层：组织能力一端——必须从"人的能力"升级为"人+AI 的联合能力"

这是公式最需要重构的地方。杨国安提出的"杨三角"是：员工能力、员工思维、员工治理。这三个支柱在纯人类组织中成立，但在人+AI 混合组织中，每一根支柱都需要扩展。

员工能力 → 组织能力谱系
不再是"员工会不会做"，而是"整个组织（人+Agent+工具）能不能完成这个任务"。诊断维度从"技能培训"变成"人机协作深度 L0-L4"、"能力图谱（谁/什么提供什么能力）"、"Token 消耗效率"。
员工思维 → 意图对齐度
不再是"员工愿不愿做"，而是"人、Agent、组织目标是否指向同一方向"。一个 Agent 的系统 prompt 里写的是"最大化用户满意度"，而组织的战略目标是"最大化利润"——这就是意图偏差。goal-alignment.ts 正是为这个设计的。
员工治理 → 协作协议完备性
不再是"组织让不让做"，而是"三类交互（人-人、人-Agent、Agent-Agent）是否有清晰的协议"。权限边界、信息共享规则、决策升级路径——这些是混合组织的"操作系统"，缺失任何一个都会导致摩擦。

此外，还需要新增杨三角没有的维度：

  • 组织弹性边界：Agent 的动态创建/销毁/租用
  • 混合信任模型：人对 Agent 的校准信任、Agent 间信任链
  • 集体学习速率：人教 Agent、Agent 教人、组织知识沉淀的速度

结论：组织能力的内核从"人"变成"人+AI"，杨三角扩展为"组织能力谱系 × 意图对齐度 × 协作协议完备性"。公式结构不变，但变量的计算方式彻底变了。

第四层：AI 让公式从"静态模型"变成"动态闭环"

在传统咨询中，"战略 × 组织能力"是一次性诊断——顾问来了，拍个片子，给出建议，走了。但 AI 让这个公式变成了持续运行的动态系统：

  • 战略不再是写在 PPT 里的方向，而是可以通过本体图（Goal 节点、ALIGNS_WITH 边）实时反映在资源分配和决策模式中。
  • 组织能力不再是访谈中的主观评分，而是通过飞书、Jira、GitHub、财务数据的实时信号（跨部门 @ 频率、工单交付周期、PR 评审时间）持续量化。
  • 两者的匹配度不再是顾问的判断，而是引擎每月自动跑的交叉验证——战略说往东，组织实际往西？矛盾自动标注，推送到 CEO 看板。

这就是"组织数字孪生"的最终意义：让"战略 × 组织能力"从理念变成可运行、可验证、可进化的操作系统。

第五层：对 Synova 的意义

  1. 理论基座依然稳固。不需要推翻重来，但需要明确："杨三角"是组织能力的起点，不是终点。我们在其基础上做了"混合组织能力三角"的扩展，这在理论和工程上都更先进。
  2. 诊断引擎天然适配这个公式。战略端有 7 Powers + 战略姿态识别 + Goal 节点对齐度分析。组织端有混合组织能力三角 + 25 个哨兵 + SOG 本体。两者在证据池中交叉验证，矛盾自动标记——这正是"乘法"的工程实现。
  3. 定位差异化更清晰。传统咨询公司还在用 Excel 和 PPT 做静态诊断，我们交付的是持续运行的数字孪生。AI 让这个公式从"咨询方法论"变成"基础设施"。

核心方法论：六维混合组织能力模型 v0.1

基于上述实证发现和对 9 个已有替代模型的语义聚类分析，提出 Synova 的核心诊断方法论。这六个维度回答同一个问题："这个组织能不能支撑长期增长？"

这是 Synova 人+Agent 混合组织理论和实践的起点——不是最终答案，是等待真实数据验证的工作假设。六维框架是主干，混合组织能力三角（组织能力谱系 × 意图对齐度 × 协作协议完备性）是核心创新，杨三角和组织行为学作为理解"人"这一侧的辅助参考。

#维度核心诊断问题与混合组织能力三角的对应
D1 目标对齐 人和 Agent 追求的目标一致吗？Agent 的目标函数与组织目标是否存在隐性偏移？ ← 员工思维（愿不愿意）→ 碳硅双向目标函数对齐

六条核心假设

  1. 目标对齐假设：混合组织的失效首先发生在目标对齐层——D1 是最优先的诊断入口。
  2. 能力拓扑假设：组织能力不是"人+Agent"的简单叠加，而是特定组合在特定任务上的匹配质量。
  3. 协作回路假设：持续有效的协作需要双向反馈回路（人→Agent + Agent→人），断掉的回路是早期信号。
  4. 治理缺口假设：大多数 Agent 部署存在"治理真空"——Agent 在运行但没有委托章程、护栏或审计。D4 缺口是最危急的安全风险。
  5. 认知健康假设：无干预的人+AI 系统趋于同质化——D5 是早期预警。同质化不崩溃但会缓慢侵蚀组织的创新能力。
  6. 适应速率假设：组织进化必须快于 Agent 能力进化，否则 Agent 会跑在治理能力前面。D6 测量这个速率差。
诚实标注：六维框架是理论推导的 v0.1，不是已验证的模型。六个维度的结构效度（它们是否真的独立？）需要至少 30 个团队的真实数据做因子分析验证。跨行业/跨规模的适用性未知。最重要的未知问题——"认知健康的正常范围"和"进化适应性的测量方法"——只能通过 Synova 自己的部署数据来回答。详见研究报告第七章"未解问题清单"。

3.3 为什么 Synova 能比人更精准地发现问题

不是因为我们 AI 比会计师懂财务、比 HR 懂组织。是因为三件事叠加：

1 全量数据
传统咨询靠访谈和问卷（抽样 + 主观），Synova 拿的是企业的真实流转数据——谁跟谁协作、决策卡在哪、钱漏在哪、代码质量如何。数据颗粒度和客观性不在一个量级。
2 多专家交叉验证
单一看一个信号可能是噪音。但财务专家发现现金流异常 + 组织专家发现某团队离职率攀升 + 技术专家发现该团队负责的系统近期大量报错 → 这不是噪音，是这个团队要出问题。单个专家的判断力可能不如人类专家，但多个专家的交叉验证叠加全量数据，系统比任何一个人类专家都更全面。
3 不会漏
人盯数据会累、会忘、会有盲区。Agent 不会。几百上千个信号同时监测，每个异常都被追踪、关联、评估。人的工作记忆只能同时处理 4-7 个信息块，但企业的数据碎片有几百上千个——这不是 AI 替代人，是让 AI 做人做不了的事。
Synova 提供洞察。人类做决策。

3.5 市场定位与竞争防御：反定位 + 低端颠覆 + AI 大厂防御

Synova 的市场定位不是凭空选的，背后有两条战略理论作指引。这两条理论解释了"为什么别人不做"和"为什么我们能做"。

理论一：反定位（Counter-Positioning）—— 赫尔默《战略 7 力》

反定位的核心逻辑：新进入者采用一种更优越的商业模式，但现有巨头无法模仿——因为模仿会破坏它们现有的利润结构。

理论二：低端颠覆（Low-End Disruption）—— 克里斯坦森《创新者的窘境》

低端颠覆的核心逻辑：现有玩家聚焦在利润最高的高端市场，忽视了"看起来不够赚钱"的中低端市场。颠覆者从低端切入，逐步向上移动。

玩家为什么不做/做不好这个市场
顶级咨询（麦肯锡、贝恩）5-300 人企业的客单价不够，他们的模型根本服务不了这个区间——不是不想做，是经济模型不允许
大厂（Palantir、Salesforce）太小、太分散，不是他们的目标市场
小咨询公司在做了，但技术上限低——没有 AI 能力，靠个人经验，质量不稳定，很多企业被割韭菜
SaaS 工具（钉钉/飞书后台）只给数据不给洞察，没有诊断能力——这是两类产品
Synova从 5-300 人的中低端市场切入（顶级咨询看不上，小咨询做不了的区间）。用 AI Agent 做诊断 = 系统化 + 便宜 + 持续。一旦模型成熟，向上扩展到更大企业是自然路径。
战略结论：Synova 不是一个"更便宜的麦肯锡"——它是一个麦肯锡不能做的商业模式（反定位），从他们看不上的市场开始（低端颠覆）。两条理论都支持：这个市场窗口是真实的。

第三层：AI 应用爆发的时代，生存空间在哪。

当下的 AI 应用爆发类似于 1995 年的互联网——基础设施层被巨头占据，但应用层会有成千上万个垂直玩家。不是每个应用都会被大厂吃掉。判断一个垂直 AI 应用能不能活，看三个条件：

  1. 是否需要专有数据？ 是——Synova 依赖企业诊断数据积累飞轮。通用模型做不到。
  2. 是否需要领域方法论？ 是——八专家、七维度、八维初诊框架不是"问 ChatGPT"能替代的，它们是专门为组织诊断设计的推理结构。
  3. 是否有切换成本？ 是——持续监测 + 历史积累 + 工作流嵌入，企业不会轻易换。

三个条件全部满足 = 垂直 AI 应用可以独立生存，不被大厂吃掉。

战略结论（补充）：AI 大厂不是 Synova 的直接威胁。反定位理论同样适用于他们——他们做平台、我们做垂直应用，这是不同的物种。真正的风险不是"大厂做了这件事"，是"我们做得不够深"——如果在自己的垂直领域，积累的数据、方法论、客户关系都比不上一个通用模型 + prompt，那才说明我们的护城河没建立起来。

3.6 逻辑链总结

理论基础：企业持续成功 = 战略 × 组织能力（杨国安，2009）。公式本身在 AI 时代依然成立，但"组织能力"的内涵必须重构——从"人的能力"升级为"人+AI 的联合能力"。杨三角扩展为"组织能力谱系 × 意图对齐度 × 协作协议完备性"，并新增组织弹性边界、混合信任模型、集体学习速率三个维度。AI 让这个公式从静态模型变成动态闭环——战略通过本体图实时反映，组织能力通过持续信号量化，两者的匹配度由引擎自动交叉验证。

技术可行性：Palantir 的碎片拼图原理（缩小到企业规模可行）→ 全量数据 + 多专家交叉验证 → 比任何单一视角更精准。

竞争可行性：价值网络理论（克里斯滕森）→ LLM 大厂的战略焦点不在垂直诊断，应用大厂的财务增长逻辑不匹配这个市场 → 不是大厂不能做，是它们不会做。反定位（赫尔默）→ 如果做也是附加功能，深度打不过垂直系统的专注。

信任可行性：四层沙箱隔离 → 租户隔离 + 数据出境控制 + 连接器沙箱 + Synova 行为边界 → 不是"我们不会乱来"，是"系统不允许任何人乱来，包括我们自己"。FDE 面对面建立信任 → 部署在企业可控环境。

结论：Synova 在理论、技术、竞争、信任四个维度上都成立。不是因为我们 AI 比人强，是因为碎片拼图 + 多专家交叉验证这件事，人脑天然不如系统。而这个系统所在的垂直市场，被大厂的价值网络天然地让出来了。

3.7 数据信任的解法

Synova 能不能工作，取决于企业愿不愿意把数据交出来做诊断。企业担心三件事：

  1. 数据会不会泄漏给竞争对手？（租户间隔离）
  2. 敏感信息会不会被送到外部？（数据出境控制）
  3. Synova 有了全量数据后，会不会乱来？（行为边界）

以下从竞争防御、沙箱隔离、FDE 生态三个角度回答。

3.6.1 竞争防御：为什么大厂不会构成威胁

核心概念来自克里斯滕森《创新者的窘境》里的价值网络（Value Network）——大企业不进入某个市场，不是因为"不能做"，而是因为在它们的价值网络里，这是理性的不选择。

LLM 大厂（OpenAI / Anthropic / Google）

LLM 大厂Synova
竞争维度参数规模 × benchmark × 通用推理能力领域知识 × 诊断方法论 × 企业数据积累
战略目标AGI / 下一代模型 / 开发者生态组织诊断这个垂直场景
增长引擎API 调用量 × 模型能力代际提升诊断精度 × 客户数量 × 数据飞轮
为什么不做几百人企业的组织诊断数据，对万亿参数模型几乎没有训练价值。投入资源做垂直诊断 = 偏离战略焦点。不是"看不上"，是不在它们的价值网络里。

应用大厂（腾讯 / 阿里）

应用大厂Synova
增长要求腾讯年增 10% ≈ 需要几百亿新收入不需要对几百亿的财务增长目标负责
企业服务策略大企业（五百强）、通用场景（云/OA/CRM）、平台级产品5-300 人企业、垂直诊断、独立产品
成本结构数千人产研团队、大规模基础设施小团队，聚焦一个场景
为什么不做5-300 人企业的组织诊断市场，对不上腾讯/阿里的年增长目标。投入一个产研团队做这件事，机会成本太高。即使做企业服务，他们做的也是大企业和通用平台。这不是傲慢——是每一个管理良好的企业都会做的理性决策。

如果他们在企业微信/钉钉里加一个"组织诊断"功能呢？

那就是通用产品的附加功能，不是独立的垂直诊断系统。区别：

大厂的附加功能Synova
方法论通用框架，套模板八专家 × 七维度 × 八维初诊框架，专门为组织诊断设计
数据积累不深耕这个场景，无法建立垂直数据飞轮每诊断一家企业，本体层积累更多行业模式
人员网络没有 FDEFDE 面对面建立信任、解释诊断结果
迭代方向服从通用产品路线图唯一的 focus，所有迭代服务于诊断精度
竞争结论：用克里斯滕森的话说——大企业把"不够大"的市场让给了新进入者，这不是疏忽，是价值网络决定的理性选择。Synova 的护城河不是"大厂不能做"，是"大厂不会做，因为对不上它们的增长逻辑"。如果它们真的做了——附加功能的深度永远打不过垂直系统的专注。

3.6.2 沙箱隔离：四层防御架构

企业主真正关心的是："你把我的全量数据拿走了，我怎么相信你不会乱来？"

四层防御，每一层保护的对象不同：

层保护什么攻击面当前状态
第一层：租户隔离 客户 A 的数据绝不能出现在客户 B 的诊断里 数据串租户 ⚠️ DB 层 org_id 过滤已实现；运行时容器级隔离待建设
第二层：数据出境控制 敏感数据不被送到外部 LLM PII/薪酬/密码流向外部 API ⚠️ DataBoundary 四级分级已实现；未在所有 LLM 调用路径强制
第三层：连接器沙箱 外部连接器不攻击 Synova 恶意连接器通过飞书/Git 接口入侵 ✅ connector-sandbox.ts 已实现（三级沙箱 + 4 道门禁 + 7 步审计）
第四层：Synova 行为边界 Synova 自己不越界——全量数据在手，不做不该做的事 AI 擅自执行越权操作 📐 设计规范（见下方）；运行时强制执行待建设

第四层详解：Synova 行为边界。 这一层是信任模型的最高潮——最可怕的不是外部攻击，是有全量数据的 AI 自己做了不该做的事。

约束规则
决策权边界 Synova 可以：分析 → 建议 → 预警
Synova 不可以：自动执行（改组织架构、调整薪资、删除数据……）
原则：建议归 AI，决策归人。
数据访问范围 有全量数据 ≠ 每个专家每个时刻都能看全量
→ 八专家各自只看诊断该维度的必要数据
→ 营销专家不需要看具体员工薪酬
→ 组织专家不需要看原始 IM 消息内容
输出脱敏 诊断报告给企业主看，不意味着原始数据裸奔
→ "某团队离职率攀升" 不是 "张三李四要离职"
→ "现金流存在季节性波动" 不是 "3 月 15 日账户余额 XXX 元"
操作分级 自动执行：哨兵告警、数据采集、指标计算 → Synova 自主
FDE 确认：初诊报告发送、诊断结论发布 → 人审核
企业主确认：组织变革建议、人员调整建议 → 最高决策权
沙箱结论：信任的基础不是能力，是边界。Synova 对自己做了最严格的约束——不是"我们不会乱来"，是"系统不允许任何人乱来，包括我们自己"。第一至三层保护客户数据不被外部获取，第四层保护客户不被 Synova 自己的能力伤害。

FDE（Field Diagnostic Engineer）是连接 Synova AI 能力和企业客户的桥梁。AI 做诊断，FDE 做面对面——信任是人与人建立的。

5.2 八维初诊框架

八维度在两个阶段是同一套内容，执行方式不同：

  • Phase 0（当前）：FDE 以八维度为采访提纲，面对面访谈企业主。采访结束上传记录文档，Synova 做文档解析 + 八维度结构化提取。不做实时对话。
  • Phase N（远期）：客户自部署后，Synova 通过实时对话（复刻 Novis L0 模式）主动引导八维度采集。LLM 加载八维度到 System Prompt，逐维引导对话，显性展示覆盖进度。

这八个维度来自 Novis L0 对话引擎的六维度诊断框架（任务目标/业务价值/现状起点/资源约束/风险瓶颈/成功标准），针对 Synova 组织诊断场景新增市场定位和数字底座两个维度。

与八专家的关系：八维度是信息采集框架（"我们需要了解什么"），八专家是分析推理系统（"这些信息意味着什么"）。八维度采集的信息分发到八位专家并行分析，交叉验证后生成诊断报告。基础设施提供的持续数据（哨兵定时模式 7×24 监测）补充和验证初诊信息。

5.2.1 Phase 0：文档上传 → 八维度提取 → 初步诊断

FDE 采访客户后，将记录文档（.txt / .md / .docx / 录音转文字）上传到 Synova。系统执行三步处理：

步骤做什么输出
1. 文档解析 读取文档内容，不做判断——纯文本提取 清洗后的纯文本
2. 八维度提取 LLM 按八维度分类提取关键信息。每个维度独立提取——同一段文字可能同时关联多个维度（比如"我们预算紧张，只有 5 个人"同时包含资源约束和现状起点）。
每个维度输出：提取到的具体内容、置信度、该维度是否足够支撑诊断		 结构化采集结果
+ 覆盖度报告（✅ 4/8 够用，⚠️ 2/8 信息偏弱，❌ 2/8 缺失）
3. 补充 & 启动诊断 覆盖度不足的维度 → FDE 手动补充（或重新上传补充材料）。信息齐备后 → FDE 点击"启动诊断" 八专家并行分析 → 综合摘要 + 各专家基础报告

八维度提取的 System Prompt 参考 Novis L0 的设计模式：每个维度的提取问题来自八维初诊框架定义表（§5.2），LLM 被约束为"只提取、不编造"，未覆盖到的维度显式标注"信息不足"而非用猜测填充。

覆盖度可视化：提取完成后，FDE 看到的是显性的维度覆盖状态——哪些维度信息够了可以启动诊断，哪些还需要补充。这和 Novis L0 对话中用户看到的 coveredDimensions 是同一种设计：不让用户猜"系统还需要什么"，直接告诉用户"还差什么"。

5.3 现场演示的核心原则

  • 过程可见：客户能看到专家正在工作——不是黑盒，是透明的思考过程
  • 有深度：跨维度交叉验证，不是单维度问答
  • 有惊喜：客户必须看到一些他之前没意识到的东西。这是最好的体验——客户当场就信了
  • 先证明价值，再谈部署：不是先卖软件再证明价值，是先让客户看到价值，再谈怎么部署

5.4 诊断的诚实边界

这是 Synova 能不能被信任的关键——不是技术问题，是产品诚信问题。

初诊演示基于有限信息（FDE 访谈时能记录的、能问到的信息有限——任何人去做这个询问诊断，信息都会不全面），所以诊断报告结论是有限的：

"这是基于有限信息的初步判断，不够全面，仅作参考。"

部署后，补充各方信息数据之后，诊断必须有质的提升。但不同维度的诊断有不同的节奏：

节奏诊断类型原因要求
可以立即做 营销方案、初步风险识别、知识整理、技术债务扫描 数据到了就能跑，不需要长期趋势 数据接入后即可输出
需要运行一段时间 组织能力评估、财务健康深度分析 需要趋势数据，不能靠单点快照。组织越大，越不能轻易调整——诊断必须建立在充分观测之上 至少运行 2-4 周，积累足够数据点后再出深度报告
需要客户补充数据 战略分析（本地竞争格局、区域市场数据、资源约束等） LLM 推理无法精准获得这些信息——比如一家月子中心，LLM 推理不出当地其他月子中心的情况。必须客户自己补充。不补充就必须承担报告不完整的后果 明确列出"我们还需要哪些数据"→ 客户补充 → 才能完成该维度诊断
不能轻易做 战略定位建议、组织架构变革建议 战略不能通过和老板做几轮对话就定下来——这太不负责。科学框架必须完备：PEST+CC 看方向 → 波特三部曲看竞争 → 7 力看壁垒 → 资源约束看可行性 → 财务支撑看可承受性 必须是全维度数据齐备 + 充分运行时间 + 客户确认后才输出

5.5 每个专家必须有一套科学方法论

这套方法论必须：

  • 有理论依据：不能是"AI 觉得这样好"。每个结论必须能追溯到具体的分析框架和证据
  • 随行业变化：制造业的战略分析方法和服务业不同。月子中心、SaaS 公司、餐饮连锁——用的是不同的分析参数
  • 随企业阶段变化：初创期的组织诊断和成熟期不同。5 人团队和 500 人团队的组织问题不能同一套标准
  • 明确告诉客户：这个诊断基于什么数据、用了什么方法、局限在哪

（各专家方法论细节参见后续章节，此为大框架）

模式 A：FDE 操作台模式 B：客户决策者界面模式 C：全员知识问答
谁在用FDE企业主 / 高管企业所有员工

6.1 模式 C 的工作机制

Synova 拥有企业全量数据——这个事实本身就意味着它是企业的专有知识库。如果数据全在系统里，但员工还是到处找人问"那个文档在哪""上次那个决策是什么""这个流程谁审批"，那就浪费了。

模式 C 不是知识管理专家一个人回答。它负责整理和沉淀知识——把企业里流转的信息结构化，人也能读、Agent 也能读。但知识管理专家的 prompt 不是用来做通俗解释的。

员工问问题时，系统做两件事：

  1. 权限判断（安全层）：这个人能问这个吗？识别员工岗位，匹配访问权限
  2. 专家路由（L2 编排层）：根据问题类型调度对应专家——
    • 财务问题 → 财务专家用知识库内容回答
    • 组织问题 → 组织专家回答
    • 技术问题 → 技术专家回答
    • 营销问题 → 营销专家回答
    • ……以此类推

同一个知识库，不同专家用不同的方式讲给人听。 财务专家能把现金流异常讲成老板听得懂的话，营销专家能把定位问题讲清楚。每个专家的 prompt 不同、表达能力不同、面向的受众不同。

6.2 三种模式的分阶段落地

  • 第一阶段（当前）：只做模式 A。FDE 操作台是唯一交互入口。
  • 第二阶段（部署后）：加上模式 B。客户决策者有自己的看板。
  • 第三阶段（部署后 + 知识积累充足）：加上模式 C。企业全员知识问答，权限 + 专家路由双控制。

7.2 第二层：本体层 —— 为什么需要它

原始数据是碎片。聊天记录是一堆文本，审批流是一堆时间戳，财务表是一堆数字。

Palantir 的逻辑：单个碎片没意义，但把碎片按人和人的关系、事和事的关系拼成一张图，模式就出来了。

本体层做的事情：把所有数据映射成"谁"和"谁跟谁的关系"。 这是 Synova 能工作的前提——不把碎片拼成图，专家 Agent 看到的就是噪音，不是信号。

比喻：医院

用一个比喻来理解整个系统：

  • 本体层 = 医院的电子病历系统。它存储患者的全部数据：CT 片、化验单、病史、用药记录。它不诊断，只记录和关联。
  • ~25 个哨兵 = ~25 种检查。血常规检查、心电图、CT 扫描——每个哨兵针对性地查一个方面。它们不负责最终判断，只负责发现和报告异常。
  • 8 位专家 = 8 个科室的医生。心内科医生不会自己去拍 CT，但他会开 CT 检查单，看 CT 结果，结合心电图和血常规综合判断。单个检查异常可能不是问题，多个检查同时指向同一个器官——这才是有意义的诊断。

    8 位专家：收到信号 → ReAct 推理 → 交叉验证 → 综合诊断
        ↓
    FDE 收到警报 + 综合诊断报告

哨兵与专家的分工：

  • 哨兵：计算、检测、量化。回答"有没有异常？数据偏离了多少？"——这是数学问题。Cron 哨兵 7×24 自动巡检，FDE 哨兵在诊断时按需调用。
  • 专家：解释、关联、判断。回答"这个异常意味着什么？跟其他信号有关系吗？该不该行动？"——这是判断问题。

7.4 第四层：怎样才能"永远是第一个发现问题的"

三个条件缺一不可：

1 数据持续流入
IM、文档、ERP、财务——所有的数据源不断同步。没有数据盲区。数据断层 = 诊断盲区。
2 本体层持续更新
新的数据进来，不是堆在那里，而是立刻映射成节点和边——新加入一个员工、一个团队改了结构、一个项目的依赖变了——本体层实时反映企业的真实状态。本体层滞后 = 诊断过时。
3 哨兵持续运行
25 个哨兵在调度框架的管理下运行——高频信号（关键人依赖、协作密度、集成断点）每日巡检，中频信号（现金流、Agent 渗透率）每周巡检，低频信号（战略 7 Power 耐久度、利润池迁移）每月或每季度巡检。哨兵停了 = 问题在变大但没人知道。

三个条件同时成立，"第一个发现"就不是口号，是数学上的必然——哨兵比人醒得早。

八、L2 编排层 & L3 洞察层 ✅ 已定稿

8.1 L2 调度原则：规则 vs LLM 的分工

能确定的用规则，不确定的用 LLM。规则保证准确性和可预期性，LLM 处理规则覆盖不了的模糊场景。

场景驱动方式为什么
哨兵定期检查数据 规则（定时器） 不需要 LLM 判断"要不要查现金流"——每隔 N 分钟跑一次就是
哨兵发现异常 → 通知哪个专家 规则（预定义映射） 现金流异常 → 财务专家，协作密度骤降 → 组织专家。不是 LLM 判断的事，是预定义的
FDE 手动启动诊断 规则 FDE 明确说了"跑全维度诊断"，不需要 LLM 猜意图
模式 C 员工提问 → 路由到哪个专家 规则 + LLM 混合 "这个月花了多少钱"→ 规则匹配到财务专家。"为什么我们这个项目总是延期"→ LLM 判断可能涉及组织+技术
多专家交叉验证后的综合判断 LLM 驱动 三个信号指向同一个团队，意味着什么？需要判断力，不是规则能写的
专家 ReAct 循环中的推理 LLM 驱动 需要解释信号意义、关联证据、决定要不要行动

8.2 工具调用：专家决定用什么工具，调度层做权限拦截

工具选择权在专家手里。 L2 调度层不可能比财务专家更懂该查什么财务指标，也不可能比战略专家更懂该调什么竞争数据。

但调度层控制三件事：

1 权限
这个工具在这个客户能不能调？由 DataAccessPolicy 控制——每个专家有预设的允许维度、禁止字段、匿名化规则。
2 安全
同一个工具+参数失败 5 次 → 封掉。同一个结果返回 5 次 → 封掉（死循环检测）。ToolGuardrails 做这件事。
3 资源
单次诊断最多 3 轮工具调用。单次工具调用超时 60 秒强制终止。ToolLoopExecutor 做这件事。

8.3 哨兵 vs 专家 Agent —— 计算与判断的分工

哨兵和专家不是同一种东西。哨兵做计算（数学），专家做判断（推理）。

哨兵（~25 个）专家 Agent（8 个）
干什么计算、检测、量化——"有没有异常？偏离了多少？"解释信号意义、关联多个信号、判断要不要行动
按需模式FDE 启动诊断 → 哨兵.compute(teamId) → 结果进诊断报告消费诊断报告 → 推理 → 输出诊断结论
定时模式Cron 触发 → 哨兵.compute(teamId) → 对比基线 → 超阈值发信号消费信号池中的异常信号 → 启动推理
需要 LLM 吗不需要——这是数学，不是判断需要——这是判断，不是数学
走 ReAct 循环吗不走走（think → act → observe）
代码哨兵 = 一个 compute() 函数，两种调用模式。Cron 哨兵 7×24 自动巡检，FDE 哨兵在诊断时按需调用。调度框架（CronScheduler + SentinelRunner）负责定时触发 + 基线对比 + 阈值判断 + 信号路由。

比喻：

  • 哨兵是检查仪器——能做血常规、心电图、CT。可以医生要求做（按需模式），也可以 ICU 监护仪持续监测（定时模式）。同一台仪器，两种用法。
  • 专家是医生——读检查报告，看监护仪上的告警，综合判断"这个病人要怎么办"。

协作流程：

  1. 调度框架按频率（日/周/月/季）触发各维度哨兵的 compute()
  2. 哨兵查本体层数据 → 对比基线 → 超阈值发信号入池
  3. 信号聚合引擎消费信号池 → 交叉关联（三个信号指向同一团队）→ 路由对应专家
  4. 专家收到信号，启动 ReAct 循环——调工具查更多数据、调本体层看关联节点
  5. 多个专家指向同一实体 → L2 触发交叉验证，综合判断 → 推送给 FDE

九、五层依赖规则 ✅ 已定稿

9.1 总原则

只能向下依赖相邻层，不允许跨层跳级。每条依赖是单向的——下层永远不会 import 上层。

9.2 依赖矩阵

L1 交互L2 编排L3 洞察L4 本体L5 数据
L1-✅ 调用❌❌❌
L2类型-✅ 调用只读查询❌
L3❌❌-✅ 读写❌
L4❌❌❌-✅ 调用
L5❌❌❌❌-

✅ = 允许运行时调用。❌ = 禁止。类型 = 只允许 import type。只读 = 允许查询不允许写入。

9.3 逐层规则

L1 交互层 → 只能依赖 L2
允许：调用 L2 接口（启动诊断、查询状态、获取报告）。使用 L2 的类型定义。
禁止：直接 import L3（专家/哨兵）、L4（GraphStore/KnownledgeStore）、L5（数据库驱动/连接器）。禁止自己写 SQL。
为什么：方向盘和仪表盘——告诉调度中心"要做什么"，看调度中心返回"结果是什么"。不应该知道专家怎么工作、数据存在哪。
当前违规：routes/review.ts、routes/sessions.ts 直接 import better-sqlite3 写 SQL。routes/knowledge.ts 直接 import L4 的 KnowledgeStore。
L2 编排层 → 只能依赖 L3（+ L1 类型 + L4 只读）
允许：调用 L3 接口（启动专家、路由信号、触发哨兵巡检）。读取 L3 返回的诊断结果。import type L1 的 ViewAdapter 接口。只读查询 L4——展示组织现状给 L1 看时，L2 可以直接从 L4 读，不需要启动专家。这是"查询"和"诊断"的区别。
禁止：直接写 L4——诊断结果的写入必须走 L3，L2 不直接改本体层数据。直接 import L5（数据库驱动/连接器）。自己写 SQL。
当前违规：diagnosis-launcher.ts 直接 import 并运行时调用 L4 的函数。synova-agent.ts 直接 import better-sqlite3 管理数据库连接。
L3 洞察层 → 只能依赖 L4
允许：从 L4 的 GraphStore 查询节点和边。通过 L4 的接口写入诊断结果。使用 L4 的类型定义。
禁止：直接 import L5（数据库驱动/连接器）。自己写 SQL 查数据库。直接调 HTTP 端点获取数据（应调 L4 的内部接口）。
关键：L4 提供给 L3 的东西必须是接口，不是 SQL。L3 调用 graphStore.queryNodes(...)，不知道也不关心底层是 SQLite 还是别的。换数据库 L3 不受影响。
当前违规：knowledge-agent.ts 自己写 SQL——db.prepare('SELECT ... FROM agent_sessions')。还有一处用 HTTP fetch 调 L4 的 API 端点。
L4 本体层 → 只能依赖 L5
允许：使用 L5 的存储后端接口（StorageBackend）。使用 L5 的连接器获取原始数据。
禁止：包含业务逻辑或诊断判断。import L1/L2/L3 的任何东西。"看懂"数据——L4 只管存，不管数据是什么意思。现金流数据的节点和边它存着，但"现金流异常"是 L3 哨兵算出来的。
当前违规：graph-store.ts（engine-core）的 SQLiteGraphStore 直接写 SQL DDL，绕过 StorageBackend 注入。pipeline-config.ts 含 ENGINE_PORT 等 L1/服务器配置。
L5 数据层 → 不依赖任何上层
允许：数据库驱动、文件系统、外部 API。连接器（飞书、GitLab、金蝶……）。提供接口给 L4 调用。
禁止：import L1/L2/L3/L4 的任何东西。包含业务逻辑。知道"数据用于什么"——快递员不需要知道包裹里是什么。

9.4 知识管理专家的特殊设计

知识管理专家比较特殊——它在后台工作，需要扫描全企业的数据来整理知识。但它不需要 L5 权限，工作在 L3 通过 L4 的接口即可完成所有工作。

两种读者的需求不同：

  • Agent 读者：需要精准检索、关系链接、结构化查询。知识条目必须在 L4——和节点、边存在同一张图上。
  • 人类读者：需要自然语言解释。但模式 C 下，员工提问 → 权限判断 → 路由到对应专家 → 专家用知识库内容用自己的 prompt 翻译成人话。所以知识条目不需要本身是"人话"，只要能被专家读懂、翻译出来就行。

结论：知识专家在 L3，通过 L4 的接口工作。零 L5 权限。架构解耦一分没破。

知识专家的工作流程：

  1. 每隔一段时间，调 L4 的 listNewContent(since) 看看有什么新材料
  2. 发现新的会议纪要、决策记录、诊断报告 → 结合本体层上下文（谁说的、属于哪个团队、关联哪个项目）→ LLM 提取关键知识点
  3. 调 L4 的 upsertKnowledge(entry) 把结构化知识条目写回本体层，同时 link 到相关节点
  4. 检测到和已有知识冲突的新信息 → 标记给 FDE 确认
  5. 其他专家被问到问题时，调 L4 的 searchKnowledge(query) 找到相关条目，用自己的 prompt 翻译成通俗回答

L4 需要承载三类数据：

数据类型说明例子
组织图谱14 节点 + 10 边——企业的骨架张三（人）→ 属于 → 研发部（团队）
原始内容聊天记录、文档、报告——知识的原材料"Q3 战略会议纪要：决定放弃 B 端……"
知识条目从原始内容中提取的结构化知识——知识的成品。每条 link 到相关节点「Q3 战略决策：放弃 B 端聚焦 C 端」（关联：决策节点 #142、项目 App 2.0）

知识专家之所以能在 L3 正常工作而不需要 L5 权限，前提是 L4 的接口足够丰富。当前 L4 的查询能力不足以支撑知识专家的需求——所以它才被迫自己写 SQL。修的方向不是给知识专家开 L5 后门，是补齐 L4 的接口。

十一、存储抽象与数据飞轮 ✅ 已定稿

11.1 存储抽象：把"用什么存"和"怎么查"分开

当前问题：L4 的 SQLiteGraphStore 直接写死了 SQLite——表怎么建、SQL 怎么写，全硬编码。L4 和 SQLite 绑定太紧——换数据库就得把 L4 所有 SQL 重写。

正确设计：

L4（GraphStore 接口）← 只定义"能做什么"：queryNodes、createEdge、traverse……
    ↓ 接口
L5（存储适配器）    ← 实现"怎么存"
    ├─ SQLite 适配器
    ├─ PostgreSQL 适配器
    └─ 未来可能是别的

GraphStore 接口不知道底层是 SQL 还是别的。换了数据库，L4 以上所有代码不受影响。

当前已有 StorageBackend 接口（在 engine-core 的 storage.ts 里），但 SQLiteGraphStore 没用它——接口画好了没接线。

11.2 数据飞轮：用户使用即贡献

每多一个客户，Synova 就比 LLM 更聪明一分。

ChatBot 每轮对话从零开始，LLM 知道什么它就知道什么。Agent 驻扎在企业里，每服务一个客户，行业知识就沉淀一分。服务 10 家月子中心以后，Synova 对月子中心行业的理解超过了任何公开 LLM。

飞轮逻辑：

客户使用 Synova 诊断
    ↓
诊断过程中补充了本地市场数据（比如四川月子中心竞对详情）
    ↓
企业独有数据 → 锁在本地，永不出门
行业情报数据 → 脱敏后进入共享知识库
    ↓
下一个同行业客户部署 Synova
    ↓
系统已有该行业知识 —— 比 LLM 更精准、更本地化
    ↓
新客户在此基础上补充更多情报
    ↓
平台越来越精准 —— 飞轮转起来了

"使用即贡献"——客户在获取诊断价值的同时，帮助平台变得更精准。FDE 是飞轮的第一推动力。

11.4 脱敏规则：保上下文标签，不保原始身份

脱敏不是简单去地名。地理位置是模式有效性的关键变量——成都和杭州都是新一线，可以互比。成都和县城不能比。标签越丰富，模式越精准。

要保护的不能丢的
企业名称、人名、具体客户名单、未公开财务数字城市级别、区域、行业、消费水平、竞争密度

脱敏示例：

  • 原始："成都 XX 月子中心在武侯区，价格 5 万，30 间房，老板是张三"
  • 脱敏后："新一线城市、西南区域、成熟商圈，月子中心价格约 5 万，30 间房规模"
  • 成都和杭州可比（同为新一线），成都和县城不可比（标签不匹配）

11.5 安全防线：三关不可绕过

1 客户显式确认
系统提示"以下信息将被脱敏后加入行业知识库，帮助同行业其他企业的诊断更准确。是否同意？"——客户逐条选择哪些可以共享。不默认同意。
2 最小聚合阈值
同一行业至少 3 家企业的数据，才生成行业洞察。1 家的数据不够——这本身就防追踪。
3 FDE 最终审核
脱敏后的行业知识由 FDE 最终审核——判断是否准确、是否可能泄露、是否值得发布。FDE 是飞轮的质量守门人。

12.1 Agent 如何进化

数据飞轮解决"行业知识越来越准"。Agent 进化解决"Agent 本身的能力越来越强"——系统越用越聪明，不只是数据在涨。

进化维度机制触发方式
诊断方法论升级 从多家客户的诊断结果回溯——发现某行业用某种分析框架更准 → 自动调整该行业的方法论权重 FDE 确认 + 平台审核
专家 prompt 优化 记录每次诊断的实际产出质量（FDE 评分 + 客户采纳率）→ 回溯什么 prompt 产出更好 → 版本化迭代 FDE 确认后升级
哨兵阈值调优 误报太多 → 自动建议调高阈值。漏报（被 FDE 或客户手动发现的问题）→ 建议调低阈值或加新哨兵 FDE 确认
FDE 纠正反馈闭环 FDE 标记"这个判断不对，实际情况是……" → 系统记录纠正 → 影响后续同类判断。纠正样本越多，类似错误越少 每次纠正自动累积
新专家/新哨兵的自动建议 系统发现某类问题反复出现但无专家覆盖 → 建议"可能需要增加一个 XX 专家来处理这类问题" FDE 审核决定

12.2 上下文分配：从 8 个专家到 60 个

1M token 看着大，但如果把 60 个专家的 prompt + 工具定义 + 知识库 + 对话历史全塞进一个上下文，1M 也不够。

核心原则：不是所有专家同时在工作。

阶段谁在工作上下文用量
日常（99% 时间）~25 个哨兵定时模式运行（不需要 LLM）
2-3 个专家因收到信号被激活		极低：每个激活的专家是独立的 LLM 调用，各用各的上下文
FDE 启动全维诊断8 个专家并行运行中等：每个专家独立调用。交叉验证时走"综合器"——只给摘要，不给全量
未来 60 个专家同时同上——99% 时间只有少数激活同上的模式。60 个专家的 prompt 不塞在一起——只有激活时才加载

上下文分配策略：

每个激活的专家拿到一个"上下文包"：
  ├─ 固定部分：自己的 system prompt + 工具定义 + DataAccessPolicy
  ├─ 动态部分：本次信号/问题的相关数据 + 相关知识条目
  ├─ 历史部分：该专家最近几次对该客户的判断摘要（不是全量历史）
  └─ 交叉部分：其他专家发来的交叉验证信号（摘要，不是全量报告）

综合器（跨专家交叉验证时）：
  ├─ 只收各专家的摘要（每个 200-500 字）
  ├─ 不含原始数据、不含完整推理过程
  └─ 综合器的上下文 < 50K tokens

12.3 多 Agent 记忆管理

8 个专家扩展到 60 个，各自的记忆不能混淆。三个层次分开处理：

记忆类型存在哪怎么用怎么不混淆
专家私有记忆 该专家对该客户的独立会话记录——锁在 L5 SessionStore，按 (expertType, clientId, userId) 隔离 "上次我为这个客户诊断时，发现现金流异常是因为应收账款周转慢了 15 天" 三键隔离：哪个专家 × 哪个客户 × 哪个用户。财务专家的记忆永远不会跑到组织专家的会话里
共享记忆（本体层） L4 本体层——所有专家都能查图 任何专家需要了解"当前组织状态"时，调 L4 查询。比如"张三属于哪个团队？他最近参与了什么项目？" 读权限：所有专家都能查。写权限：只能写自己维度的节点（防止覆盖冲突）
知识记忆（知识库） L4 知识条目——知识专家整理后写入，所有专家可查 "Q3 战略决策是放弃 B 端聚焦 C 端"——任何需要这条背景的专家都能搜到 知识专家统一管理写入，避免多专家各自写导致冲突

速度保证：分层缓存

专家查记忆时：
  热记忆（最近 7 天相关）→ 上下文里直接用（0ms）
  温记忆（30 天内相关）→ RAG 检索，取 top-5 最相关的（< 200ms）
  冷记忆（历史归档）  → SQLite FTS5 全文搜索（< 500ms）

不是每次启动都查全量——分层后大部分查询命中热/温记忆，速度不受记忆总量影响。

12.4 一对多对话：一个 Synova 对接上百个员工

员工级别不需要安装任何客户端。飞书/企微就是客户端。需要解决三个子问题：

一、身份识别

飞书/企微来的消息，天然带了发送者的企业身份——员工 ID、部门、职级。这是 API 原生能力。

部署时 FDE 帮企业做一次映射：飞书组织架构 → Synova 本体层节点。之后每次员工发消息：

飞书消息 → user_id=xxx，部门=市场部，职级=经理
    ↓ Synova 身份映射
本体层查到：李四（市场部经理），权限级别 = manager，关联项目 = 双十一营销

二、对话隔离

100 个人同时问，不是挤在一个群聊里——是每人跟 Synova 的私聊。飞书 Bot API 的私聊模式天然隔离。每个 user_id 对应独立的会话上下文。

三、权限过滤（最难的部分）

同一个问题，不同人问，不同答案——不是"能不能答"，是"给多少细节"。

李四（市场部经理）问："公司 Q3 营销花了多少钱？"
    ↓ L2 路由 → 财务专家
    ↓ L4 查全量数据：Q3 营销总花费 500 万，线上 300 万……
    ↓ 权限过滤器：李四是市场部经理 → 可以看营销费用全量
    ↓ 回答："Q3 营销总花费 500 万，线上 300 万（抖音 120 万、小红书 80 万……），线下 200 万"

实习生问同样的问题：
    ↓ 权限过滤器：实习生 → 只能看汇总
    ↓ 回答："Q3 营销总花费 500 万。如需了解分项数据，请联系你部门的经理。"

限制不在回答阶段——在查询阶段。 本体层每条数据有 accessLevel 标签。权限过滤器在查 L4 时自动注入 FilterClause，专家拿到的已经是权限过滤后的数据。

RBAC 数据粒度：

角色数据粒度
Admin (CEO/老板)明细——每一笔花费的源头，所有维度的全量数据
Manager (部门负责人)分项——知道自己部门的数据，看不到其他部门的
Employee (普通员工)汇总——知道大数，看不到分项和细节
Viewer (实习生/外部)仅公开——汇总级别，连历史趋势都不给

完整链路：

企业飞书/企微
    ├─ 李四（市场部经理）→ 私聊 Synova
    ├─ 王五（研发工程师）→ 私聊 Synova
    ├─ 赵六（财务总监）  → 私聊 Synova
    └─ ……（上百人）
        ↓ 每条消息携带：user_id + 部门 + 职级
    L1 交互层（飞书 Bot Adapter）
        ↓ 身份映射 + 会话创建/恢复
    L2 编排层
        ↓ 意图路由 + 权限预检
    安全层（AuthProvider + RBAC + DataBoundary）
        ↓ 注入 FilterClause
    L3 专家 → L4 本体层查询（数据在查询阶段已被过滤）
        ↓
    回答 → 飞书 API → 员工看到

12.5 并发与 LLM 限流

100 人同时问，不是 100 个 LLM 同时跑。但峰值确实可能撞上——周一早上 30 个人同时问"这个月目标是什么"。

四层削减：

1 语义缓存（挡掉 50%+ 的问题）
● 重复问题："公司这个月营收多少"——每天 10 个人问 → 缓存 5 分钟
● 相似问题："营收多少"和"这个月赚了多少"→ 语义相似度 > 0.9 命中缓存
● 不缓存的：个性化问题（"我的报销到哪了"）、新问题
效果：企业中高频重复问题占比高，语义缓存能挡掉一半以上的 LLM 调用。
2 请求队列 + 优先级
高峰期 30 人同时在等 → 不是 30 个 LLM 同时跑 → 进入队列：
● 老板的问题 → 高优先级
● 诊断/决策相关 → 高优先级
● 普通查询 → 正常优先级
● 闲聊 → 低优先级
同时最多跑 N 个 LLM 调用（N = API 限制 - 1，留一个给哨兵）。排队中的用户看到"正在处理，预计等待 X 秒"。
3 预计算 + 主动推送
哨兵跑完产生的信号和报告，直接推送给相关的人——不用等他们来问。"你的项目 Q3 目标进度落后了 15%，以下是分析……"——主动推送比被动问答更能体现 Agent 价值。
4 降级回答
队列太深或 API 限流时，非关键问题降级：
● 返回最近缓存（标注"X 分钟前的结果"）
● 返回结构化数据而非自然语言——不需要 LLM
● 推迟复杂分析："这个问题需要深度分析，已加入批处理队列，明早给结果"

实际负载模型：

100 人同时在用
    ↓
50% 命中语义缓存 → 秒回，不走 LLM，零成本
30% 简单查询 → 队列排队，几秒内 LLM 回复
15% 复杂分析 → 高优先级处理，十几秒内专家回复
5% 深度诊断 → 批处理，异步返回结果（通知用户"明早出结果"）
    ↓
LLM API 实际并发：同时最多 3-5 个调用
100 人 ≠ 100 倍 LLM 成本

13.1 设计原则

架构设计往前看三步，代码实现只写一步。
不为优雅牺牲简单性，不为未来过度设计现在。

13.2 存储格式：Typed ID 轻型结构

选 Typed ID 结构化 JSON，不选三元组具体化（Assertion 模型）。

理由：企业诊断 80% 的查询是"张三最近有什么决策？"——按实体节点查关联记忆。一条 SQL 完成的事，拆成 6 条 triples 后再拼回去——每一次读写都在为优雅付费。等需要跨记忆推理链（因果追溯）时再升级，不破坏现有结构。

字段类型说明

typeenumdecision / finding / signal / context / action
dimensionenumstrategy / org / finance / tech / marketing / action

entitiesarray[{type: "DecisionNode", id: "142", name: "Q3 战略决策"}] — 可解析的 Typed ID，非字符串标签

public_summarystring给交叉验证时其他专家看的摘要（不含敏感细节）
confidence0-1AI 生成 0.7，哨兵信号 0.6，FDE 手记 0.95

source_expertstring哪個专家产生/拥有这条记忆
client_idstring所属客户

什么时候升级到三元组具体化：当需要跨记忆推理链时（"Q1 决策 A → Q2 发现 B → Q3 决策 C 修正 B"），Typed ID 的 links 数组可平滑升级——不推翻现有结构。

13.3 隔离机制：记忆视图（Memory Views）

选记忆视图方案。命名图留给 SurrealDB 迁移时一起做。

L4 提供 3 个查询接口，每个专家调用时 L2 自动拼接对应的查询条件：

1. getPrivateMemories(expertType, clientId, entityIds[])
   → WHERE owner_expert = ? AND client_id = ? AND entity_id IN (...)

2. getSharedMemories(clientId, dimension?, entityIds[])
   → WHERE visibility = 'shared' AND client_id = ? (+ dimension filter)

3. getKnowledgeMemories(clientId, query)
   → WHERE visibility = 'knowledge' + 语义搜索

交叉验证时的可见性控制：

  • 专家 A 引用专家 B 的发现 → 只能看到 public_summary + confidence + entities
  • 不能看到 detail（完整推理过程）
  • 如需深入验证 → 调 request_cross_validation(detail)，记录审计，且需 B 的 DataAccessPolicy 允许
  • public_summary 由 LLM 在生成记忆时自动生成

13.4 检索：实体优先，语义回退，时间衰减打分

第一优先：实体关联检索（覆盖 80% 查询，< 10ms）

专家查"张三" → L4 从本体层查张三的关联记忆
  ├─ 直接关联：张三的决策、信号
  ├─ 1 跳关联：张三所在团队的相关记忆
  └─ 合并去重 → 按 relevance_score 排序

回退：混合语义检索（覆盖 15% 查询，< 200ms）

结构化查询无结果 → 走语义 RAG
  ├─ sqlite-vec 本地向量嵌入（all-MiniLM-L6-v2，零外部依赖）
  ├─ 融合评分：final = α×cosine + β×relevance×exp(-λ×days_ago)
  └─ 返回 top-10

Token 控制：检索结果只传 summary + confidence + entities。Agent 需要详情时调 fetch_memory_detail(memory_id) 按需加载。35 条 × 100 字 = 3500 tokens，远低于上下文限制。

14.1 架构前提

哨兵和哨兵不是两套系统。它们是同一个 compute() 函数在两种调用模式下的不同表现。本章描述的每个"哨兵"，同时支持：

  • 按需模式：FDE 启动诊断 → compute(teamId) → 结果进诊断报告

14.2 设计原则

7 个维度是经过推理的固定框架。每个维度下的哨兵数量由"需要监测什么"决定，不由现有模块数量决定。
分层调度，不是一起跑。能确定的用规则，不确定的用 LLM。
高频信号（日度）优先建设，低频信号（季度）逐步补齐。

16.1 总原则

金字塔原理：结论先行，逐层展开。每层的第一句是该层的核心结论。每层只传达一个核心信息——后面的内容是证据，不是新话题。读者可以在任何一层停下来，他已经得到了这一层最重要的东西。

不知道就说不知道。数据不足的维度标注"当前数据不足以支撑结论"，不是假装全知。诚实比完美更能建立信任。

引入任何概念必须先解释。管理学、经济学的术语可以用，但第一次出现时必须用人话解释。Synova 的内部技术术语（哨兵、六缝隙、D1-D6、信号池）永远不出现在报告中。报告是给企业主看的，不是给工程师看的。

评分永远配趋势。单一数字没意义——"组织能力 6.2"无法判断好坏。必须同时展示：6.2 在 6 个月前是 5.1（在改善）还是 7.8（在恶化）。

报告是对话的起点，不是终点。客户收到报告后可以跟 Synova 对话修改——调深度、调风格、去敏感数据、翻英文版。

十八、专家方法论 ⏳ 初步定稿，待创始人细化和确认

18.1 战略专家

理论基础：三层战略诊断模型（详见 §3.2）→ 第一层市场引力（波特五力 + PEST + CC + 利润池迁移）→ 第二层竞争力量（7 Powers 量化引擎）→ 第三层战略-组织匹配。

核心原则：一个企业不可能同时拥有七种力量。战略专家的第一步不是计算，是判断哪些力量适用于这家企业——由企业生命周期、行业类型、业务模式共同决定。不适用的力量不算分、不报警、不出现在诊断报告里。该追求的没建立是盲区，不该追求的没建立是常识。

工作流程

Step 0: 企业画像判定（规则引擎，不需要 LLM）
  输入：企业规模 / 成立年限 / 行业分类 / 业务模式
  输出：力量适用性清单（该企业适用 3-5 个力量）
  逻辑：§3.2 力量适用性矩阵

Step 1: 第一层 — 市场引力（可立即执行）
  4 个哨兵：市场规模与增速 / 波特五力量化 / 利润池迁移 / 客户需求变化
  数据源：行业报告 + 公开数据 + 上市公司财报
  输出：赛道健康度评分 + 利润池位置

Step 2: 第二层 — 竞争力量量化（需要运行一段时间积累数据）
  对 Step 0 确定的适用力量清单，逐一运行量化：
    存在判定 → 强度评分 → S 曲线位置判定
  不适用的力量跳过，在报告中标注"不适用（行业/阶段原因）"
  输出：
    - 适用且健康（绿灯）
    - 适用但衰退（黄灯，需干预）
    - 适用但缺失（红灯，战略盲区）

Step 3: 第三层 — 战略-组织匹配（消费 D2-D5 诊断结果）
  战略需要的组织能力 vs 组织实际能力 → 差距诊断
  输出：匹配 / 部分匹配（标注具体缺口）/ 缺失（标注风险）

四档节奏

节奏做什么方法
可以立即做第一层：赛道初步判断 + 力量适用性判定。行业规模、增速、集中度、利润池位置。PEST + CC + 波特五力 + 利润池迁移。4 个第一层哨兵用公开数据即可计算。力量适用性矩阵由规则引擎直接判定。
需要运行一段时间第二层：适用力量的量化评估。每条力量的强度评分 + S 曲线位置 + 趋势方向。财务数据 + 运营数据 + 时间序列。7 个力量量化器各自需要不同数据源（财务表/CRM/运营数据/专利库/NPS）。单个快照不可靠——需要趋势。
需要客户补充数据本地竞争格局：区域市场竞对数量/价格/定位/客户重叠度。品牌溢价验证：客户访谈或问卷调查。客户补充本地情报。不补充就标注"缺失本地竞对数据，以下结论基于公开数据"。
不能轻易做战略定位建议、赛道转换建议、组织能力重构建议。必须全维度数据齐备 + 充分运行时间 + 战略-组织匹配诊断完成 + 客户确认。战略不能通过几轮对话定下来。

19.1 信号分流：谁决定要不要通知专家

不是每个哨兵信号都值得叫醒专家。L2 的信号路由器做三级分流（规则驱动，不是 LLM）：

信号级别条件处理
低单哨兵单次触发、偏离量小、置信度低只记录，不通知专家。累计 N 次后自动升级
中偏离量超过阈值、或连续 2-3 次触发通知对应维度专家。专家自己做判断
高多个哨兵信号指向同一个实体、或偏离量极大立刻触发交叉验证——相关专家全部激活
紧急现金流断崖、关键系统宕机、合规红线触发直接告警 FDE，不等专家判断

信号路由器是规则，不是 LLM。哪个哨兵→哪个专家是预定义的映射表。只有模糊场景（信号跨三个维度、映射表没覆盖）才丢给 LLM 判断。

19.2 专家收到信号后：不是逐条处理，是看信号间的关系

专家收到的是一批信号的集合，不是一个信号触发一次 ReAct：

财务专家本轮收到的信号批次：
  ├─ 现金流异常（来自实时哨兵，已连续 3 天触发，严重度↑）
  ├─ 应收账款周转率下降（来自周度哨兵，本周首次）
  └─ SaaS 订阅闲置率 30%（来自软件生态哨兵，月度，低优先级）

财务专家启动 ReAct：
  Think   → 这三个信号有关联吗？应收账款↓ + 现金流紧张 → 可能同一件事
  Act     → 调 L4 查更多数据：应收账款明细、客户付款记录、最近大额支出
  Observe → 三个大客户同时延迟付款 + 一笔未预见的设备采购 → 不是系统性问题是偶发
  Decide  → Finding：现金流紧张是偶发，非结构性。置信度 0.7。建议跟进大客户回款

19.3 多专家交叉验证：信号汇聚到综合器

L2 持续监测：多个专家的 Finding 是否指向同一个组织实体？

L2 检测到：
  财务专家 Finding："现金流异常，应收账款周转率下降 15%"
  组织专家 Finding："研发部协作密度连续 3 周下降"
  技术专家 Finding："研发部负责的核心系统近期报错增加"
      ↓ 三个 Finding 都指向：研发部
      ↓

综合器：
  不是又一个专家——是跨专家信号汇总器，规则触发

      ↓

20.7 Anthropic 的核心纪律（整个 Phase 0-3 不破）

  1. 一次只动 1 个模块。换一个、验证一个、commit 一个。不是批量重构。
  2. 规则用编译器阻断。 Sentinel 接口上线 → 旧 DiagnosticModule 注册 = 编译错误。
  3. Feature Branch 强制。 feat/sentinel-system、fix/layer-violation——每个 Phase 内独立分支。
  4. 垂直切片交付。 每个 slice = 触发点 → 数据流 → 用户可见的结果。不等"全部做完"。
  5. 接线审计是硬门禁。 声称完成前 grep 确认新函数名出现在生产入口文件中。
  6. pre-commit 零容忍。 as any、Mock/TODO、console.log 敏感数据、空 catch——阻断。
