1. LLM Provider 韧性（6/10 → 目标 8/10）

已有：重试中间件+3态断路器+Provider Chain顺序回退（10个Provider）+健康矩阵+LLM缓存+成本追踪+7场景故障恢复。缺失：多key池轮换（Hermes差异化TTL 401→5min/429→1hr）、并发租约管理、OAuth凭据存储和刷新。

2. 安全与沙箱（4/10 → 目标 7/10）

已有：3层文件守卫+AES-256-GCM凭据加密+连接器沙箱+追加型审计日志+PII脱敏S1-S4+数据库加密。缺失：无运行时工具执行沙箱（OpenClaw Docker/SSH 隔离）、无工具调用循环检测（Hermes ToolCallGuardrailController 三模式）。

3. IM 平台接入（3/10 → 目标 7/10）

结构性问题："有和无"的差距

Hermes 有 10 个平台适配器 + 统一消息标准化 + 投递路由。Synova 只有飞书 webhook 能端到端工作。WeCom 是死桩。需要 Hermes 式的 BasePlatformAdapter 架构。

4. 测试与评估（5/10 → 目标 7/10）

OpenClaw 有场景驱动的 JSONL 回放测试 + Frontier harness。Synova 的 E2E 测试在 CI 中被跳过。需要为哨兵 compute 函数和专家推理建立 JSONL 回放测试。

5. 上下文管理（3/10 → 目标 7/10）

最致命的技术差距之一

Hermes 的 ContextEngine ABC 定义了完整生命周期+13个压缩特性。Synova 的 context-compressor.ts 只有3种策略+201行+纯机械拼接。RUNTIME-EXCELLENCE-IMPL Phase 3.3 已规划增强。追加：借鉴 Hermes 完整的 ContextEngine ABC 架构。

6. 记忆系统（5/10 → 目标 7/10）

AgentMemoryStore（6种记忆类型+FTS5+TTL+版本链+租户隔离）在结构化事实记忆方面领先。缺失：CJK分词器配置+向量嵌入语义记忆。RUNTIME-EXCELLENCE-IMPL Phase 5.2 已规划双FTS5索引。

7. 可观测性（3/10 → 目标 6/10）

已有 Prometheus 指标+结构化日志。缺失：OpenTelemetry 分布式追踪+内存压力监控+诊断支持包。RUNTIME-EXCELLENCE-IMPL Phase 5.3-5.4 已规划部分。

8. 插件扩展（4/10 → 目标 6/10）

Manifest 驱动架构工作正常但本质是配置加载器。Synova 不需要第三方插件市场——文件驱动已满足需求。差距在工程成熟度（无热加载、无能力注册）。

9. 部署与打包（4/10 → 目标 6/10）

Electron+系统托盘+Docker+CI 5并行Job。缺失：无自动CD管线+无多架构Docker+无auto-update集成。

10. Loop Engineering — 产品闭环

重要修正：之前将开发工程质量工具链误认为产品循环能力。Loop Engineering 在 Synova 语境中是"企业问题从发现到解决的完整闭环"。

薄弱环节

  1. 执行跟踪→验证效果的闭环接续：对接人在行动项里标记"已完成"，但哨兵不会自动复查。需要人工触发下一轮诊断。
  2. 升级链：数据驱动的 7-14-28 天自动升级——设计已出但未实现。这是"对接人忽略→企业主看到"的最后防线。
  3. 全链路可视化：GA 出了方案→对接人执行了→哨兵验证了效果→"看到一个完整问题从发现到解决"的体验不存在。

11. 无 GA 场景与 GA 纠错可靠性

没有 GA 时循环如何闭合

GA 的职责无 GA 时的替代机制
审阅专家结论数据自动验证：哨兵复查时指标改善→自动提升置信度权重。指标未改善→标记"建议人工复核"。
行业经验补充行业模板替代：extensions/industries/{name}/ 下的 thresholds.json、facts.json。用"群体的经验"弥补个体的缺失。
确认方案交付对接人直接确认。置信度标记降低一级，哨兵复查频率提高一倍（3天而非7天）。

GA 纠错本身是错的怎么办

GA 纠错是叠加层——不覆盖原结论。哨兵复查发现"GA 纠错后指标反而恶化"→ 自动回滚纠错，恢复原始结论，降低该 GA 对该哨兵的置信度。GA 的每一次纠错都在被数据验证。连续 3 次被数据证伪→通知企业主。

12. 无数据时循环如何启动

循环的真实起点不是哨兵，是数据接入。数据不进来怎么办？

第一屏用户填三件事→Synova 用行业模板做初步诊断。行业模板是"先天免疫"——不需要宿主提供抗原，系统自带。第一次有数据→行业阈值替换为实际阈值。第二次有数据→BaselineStore 建立基线。第三次有数据→哨兵可对比基线检测偏移。数据越积越多，循环越来越快，诊断越来越准。

13. 多线路并行循环 — Plus 版本差异化

一个企业内存在多条问题闭环同时运行。这是 Synova Plus 版本的核心差异化能力。

Synova 的护城河总结

相对所有对标项目，Synova 最独特的优势是企业级问题闭环——发现→诊断→方案→执行→验证→免疫。这不是技术栈的差异，是产品品类定义的根本性差异。对标项目是通用 Agent 框架，Synova 是领域 Agent。通用框架的循环是技术循环（会话持续、崩溃恢复、工具安全），Synova 的循环是业务循环（问题从发现到解决的全过程闭环）。

补充分析：免疫细胞 — 问题闭环的物理载体

"得一种病，产生一个抗体。" 这个免疫学的核心原理，在 Synova 体系中体现为：每解决一个企业问题，系统就沉淀一组数据记录。这些数据记录就是"免疫细胞"——下次同样模式出现时，系统自动识别并快速响应。

人体免疫 vs Synova 免疫

免疫学概念人体Synova
病原体病毒/细菌企业问题（现金流异常、人员流失、信息失真...）
先天免疫固有免疫细胞（巨噬细胞、NK细胞）行业模板通用检测（thresholds.json、facts.json）
适应性免疫T细胞/B细胞识别特异性抗原8位专家按需唤醒，识别问题模式
抗体免疫球蛋白（IgG/IgM/IgA）数据记录（enterprise_fact / threshold_adjustment / user_correction / industry_pattern）
记忆B细胞长期留存，再次遇到同样抗原→快速产生大量抗体AgentMemoryStore 持久化 + 版本链
免疫记忆终身免疫（如水痘）或逐年衰减（如流感）数据驱动的诊断精度随使用时间持续提升

一个问题的完整免疫闭环

【母婴用品公司 — Q3 应收账款异常】 1. 哨兵 F1 发现异常 应收账款周期：28天 → 51天 (+82%) → 先天免疫响应：行业模板显示母婴行业 Q3 均值 25-35 天，当前超过 2σ → 推送对接人 + GA 2. 专家诊断 finance 专家：根因=客户A采购系统迁移导致付款中断 strategy 专家交叉验证：非系统性风险，属于单一客户临时异常 → 适应性免疫：识别出"单一客户临时异常"模式（非"行业性回款恶化"） 3. 方案执行 + 哨兵验证 方案：临时缩短客户A付款周期 执行后：51天 → 38天 → 31天（恢复正常） 4. ═══ L0 进化引擎产生抗体 ═══ ① enterprise_fact（事实抗体） 写入 AgentMemoryStore type:'enterprise_fact' key: 'financial.baseline.receivable_cycle' value: { baseline: 28, q3_adjusted: 38, source: 'verified' } → 效果：下次哨兵运行时，Q3基线自动调整为38天，不再误报 ② threshold_adjustment（阈值抗体） 写入 AgentMemoryStore type:'threshold_adjustment' sentinelId: 'F1', newThreshold: { critical: 1.6, warning: 1.0 } reason: 'Q3备货季应收周期天然延长10-15天，GA确认非风险信号' → 效果：下次Q3时，F1哨兵的告警阈值自动使用季节性阈值 ③ user_correction（纠错抗体） 写入 AgentMemoryStore type:'user_correction' claim: 'F1应收周期异常=critical' correction: '季节性因素未纳入。Q3备货季属于正常商业行为' confidence: 0.9, source: 'ga:zhang_san' supersededBy → 指向原 ExpertReport → 效果：下次同行业客户出现类似模式时，系统提示季节性因素 ④ industry_pattern（行业抗体 — 需要 ≥3 个同行业客户触发） GlobalAnalyzer 聚合 3+ 母婴客户的 Q3 数据 写入 extensions/industries/maternal-infant/patterns.json { pattern: 'q3_receivable_extension', sentinels: ['F1'], adjustment: 'critical_threshold * 0.8 during Q3', evidence_count: 3, confidence: 0.85 } → 效果：下一个母婴客户注册时，自动加载此模式。先天免疫强化。 5. 下一次（另一家母婴客户 — Q3） 哨兵 F1 运行 → 读取 enterprise_fact（该客户自己的基线） → 读取 threshold_adjustment（该客户自己的季节性阈值） → 读取 industry_pattern（母婴行业的共同经验） → 综合判断：Q3应收周期延长属于已知季节性模式，非风险信号 → 不产生告警 ← 这就是"免疫"的效果 6. 免疫衰减（如果不再更新） TTL 机制：如果该模式连续 2 年未触发 → industry_pattern 标记为 'stale'，置信度衰减 → GA 收到提示："母婴行业 Q3 季节性模式已 2 年未验证，需要重新确认吗？"

免疫细胞不是代码，是数据

L0 进化引擎不产生新代码——它产生新的数据记录。这些数据记录存储在 AgentMemoryStore 中，被哨兵和专家在后续诊断中自动读取。这就是为什么"不需要多个 Synova 实例"——抗体是数据层的，不是代码层的。orgId 隔离确保企业 A 的抗体不污染企业 B 的诊断。industry_pattern 是匿名聚合统计，同行业共享但不泄露个体数据。

抗体类型总览

抗体类型存储位置作用域产生条件TTL
enterprise_factAgentMemoryStore（orgId隔离）单个企业用户纠错含具体数据 / 方案执行后指标改善永久（版本链保留）

共享规则

抗体类型产生循环可见范围隔离机制
enterprise_fact任意循环全企业所有循环无隔离——企业事实是全公司共享的真相层。财务循环更新的 Financial.cash 值，战略循环在分析扩张可行性时自动读取。这是"单一事实来源"原则。
threshold_adjustment任意循环全企业所有循环无隔离——哨兵阈值是全局参数。财务循环调整了 F1 的 critical 阈值，组织循环中如果碰巧引用了 F1 数据，也会自动使用新阈值。但部门级自主调整需要本部门负责人确认（防止跨部门阈值污染）。
user_correction产生它的循环该哨兵的所有循环按哨兵 ID 隔离。财务循环中对 F1 的纠错，组织循环不直接使用——但组织循环如果也触发 F1 告警，系统会引用该纠错记录作为"上次此哨兵被纠错过"的提示。
industry_pattern同行业 ≥3 个企业同行业所有企业的所有循环匿名聚合统计。母婴客户 A 的 Q3 季节性规律和母婴客户 B 的数据合并为统计值（中位数、p25、p75），不包含任何个体原始数据。新母婴客户 C 的财务循环自动加载此模式。

关键设计：抗体不跨企业共享（除 industry_pattern 的匿名聚合外）

企业 A 的 enterprise_fact 不会被企业 B 读取。企业 A 的 threshold_adjustment 不会影响企业 B 的哨兵阈值。这是 orgId 隔离的铁律——隐私是免疫系统的边界。

唯一的例外是 industry_pattern——它是匿名聚合统计量（"母婴行业 Q3 应收周期中位数为 38 天，n=5"），不包含任何单个企业的原始数据。这是 L0 进化层第三层（全局进化）的设计原则。

跨循环抗体冲突处理

如果财务循环产生的 enterprise_fact 和组织循环产生的 threshold_adjustment 对同一个哨兵给出矛盾的信号怎么办？不冲突——enterprise_fact 更新的是"这个企业的真实基线是多少"，threshold_adjustment 更新的是"这个哨兵的告警阈值应该是多少"。两者是互补的，不是矛盾的。但如果两个循环各自调整了同一个哨兵的阈值，以最后调整时间为准，并在 AgentMemoryStore 中保留完整调整链（版本链），GA 和企业主可以回溯审查。
