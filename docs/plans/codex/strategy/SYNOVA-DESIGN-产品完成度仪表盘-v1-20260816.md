## 〇、创始人的一句话定义（本设计的北极星）

> **"产品 = N 条能力线。每条线写死'到 100% 的定义'（验收点清单）。进度条 = 被证据验证的验收点比例。所有线到 100% 且经 K3 复核 = v1 产品完成。"**

## 一、核心概念：线 → 验收点 → 证据（三层结构）

```
产品
 ├─ 线 01 桌面端线          （能力域，用户可感知，不是技术层）
 │    ├─ 验收点 01-1: 双击 exe 能装、能启动        ← 证据: 场景 GS-01 绿 + 安装实测记录
 │    ├─ 验收点 01-2: Mac 版安装包可用             ← 证据: 场景 GS-01(Mac) 绿
 │    └─ 验收点 01-3: 服务自启、开窗即用           ← 证据: 场景 GS-01 绿 + 日志
 ├─ 线 06 首次诊断线
 │    └─ ...
 └─ 线 11 人才循环线（联邦进化已降 v2+ 扩展线）
```

| 层 | 定义 | 谁维护 | 更新频率 |
|----|------|--------|---------|
| **线** | 一个用户可感知的能力域（大白话名字 + 一句话价值） | 创始人定，Harness 起草 | 季度评审 |
| **验收点** | 该线"完成"的一条可验证定义（每条必须能绑定证据） | Harness 起草，创始人批准 | 里程碑 |
| **证据** | 机器事实：场景绿 / 测试绿 / K3 复核 / 门禁绿 / 人工演示核验记录 | 自动（calc-progress.py 扫描） | 每次交付后 |

**核心诚实规则（防数字游戏，本设计第一红线）**：
> **只有带证据的验收点才算"已验证"。** agent 说"做了"不算；代码提交了不算；D# 合并了不算。证据 = 可 grep、可重跑、可复核的物理事实（对齐 K3"物理事实优先"方法论，你们被"声称完成"伤过 8 次以上）。

## 二、线分解方法论（线数由产品自然结构决定，不预设数字）

### 2.1 方法论（v1.1：从"拍 20 条"改为"标准聚类涌现"）

> **第一性原理**：线的数量不是拍脑袋的，是"完整产品 = 什么"的投影。产品定义来自三份现成权威：**C线 33 项标准**（用户可感知的价值承诺）、**权威文档 01-18**（能力模块）、**用户旅程**（安装→首诊→监测→报告→告警→进化）。线 = 这三者的自然聚类。

| 规则 | 说明 |
|------|------|
| 线 = 用户可感知的能力域 | 不按技术层（L1-L5）切，按"老板能感知的承诺"切：装得上、诊断得出、报告看得懂、告警收得到…… |
| **线由标准聚类涌现** | 初稿生成法：33 项 C线标准 → 按"同一用户承诺"聚类 → 每簇 = 一条线候选 → 对照权威文档模块校验 → 得线集初稿。**线数是结果，不是前提** |
| 聚类粒度校验 | 一条线 1-3 个月内可做完（超过拆细，不到 1 个验收点并入邻线）——这是唯一的人为约束，保证进度条有意义 |
| 线之间不重叠 | 同一验收点只属一条线（防重复计分）；有争议归"主线" |
| v1 线集锁定 | v1 线集 = v1 产品完成标准；新需求开 v2+ 扩展线，不污染 v1 进度 |
| 线集可改 | 增/删/拆/并 = 改 yaml，进度自动重算；改线集是**产品定义决策，只有创始人能拍板** |

## 三、进度计算规则（诚实核心）

### 3.1 公式

```
线进度 % = 已验证验收点数 / 总验收点数 × 100
产品总进度 % = Σ(线进度 × 线权重) / Σ线权重        （默认等权；yaml 可配价值权重）
```

### 3.2 验收点的证据类型（决定"算不算数"）

| 证据类型 | 来源 | 有效期 | 说明 |
|---------|------|:---:|------|
| [场景绿] | golden-scenarios/evidence/ | 14 天 | 代码变更后需重跑（过期自动转黄） |
| [测试绿] | vitest 全量/CI job | 14 天 | 全量测试通过记录 |
| [K3复核] | K3 审计报告 | 至下一轮审计 | 独立第三方核验，权重最高 |
| [门禁绿] | pre-commit/pre-push 记录 | 永久 | 过程性证据，单独标注 |
| [人工演示核验] | 创始人确认记录（页面勾选+日期） | 里程碑 | 只用于"演示/可读性"类验收点，且必须附演示记录 |

### 3.3 诚实规则（写进 calc-progress.py 的硬逻辑）

1. **声称无效**：验收点只有证据文件存在且未过期才计"已验证"；无证据 = 未验证 = 不计分。
2. **代码变更自动失效**：calc 扫描 git 最近变更涉及某线模块 → 该线"场景/测试类"证据标记"待重跑"（黄色），不自动继承旧绿。
3. **验收点措辞变更自动失效**（K3 20b）：calc 对比 yaml git 历史——验收点 desc 措辞变更（删除量化指标/"支持X"→"部分支持"/"完成"→"基本"）→ 该点自动回 🟡 重验，禁止"改宽标准保绿"。
4. **线 100% 的特殊门槛**：一条线声明 100% = 全部验收点证据有效 **且** K3 对该线做了全量复核（20c 硬触发）——**开发者自报的 100% 无效**（这是防"最后 10% 烂尾"的物理闸门，你们被 placeholder 假成功伤过）。
5. **百分比只显示整数**，不显示"99.5%"这类假精确。

### 3.4 信息层级：git 和 K3 听谁的？（v1.1 新增——创始人问"应该听谁的"）

> **结论一句话：存在性听 git，正确性听 K3。两者冲突时，K3 是最终裁判。**

| 层 | 信息源 | 回答什么问题 | 角色 |
|----|--------|------------|------|
| L0 | **git** | 代码在不在？变没变？提交/合并了吗？ | **存在性传感器**——进度计算的基础事实 + 变更检测（代码一变，相关证据自动失效） |
| L1 | **机器验证**（场景/测试/门禁） | 跑起来对不对？ | **执行证据**——可重跑、可复核 |
| L2 | **K3 审计** | 这段代码到底对不对？ | **正确性裁判**——最终权威，一票否决 |

**验收点判定状态机（写进 calc-progress.py）**：

```
未提交/未合并（git 无）        → ⚪ white（不计分）
已合并但机器验证红 / K3 否决    → 🔴 red（不计分）
机器验证绿但 K3 未审 / 证据过期 → 🟡 yellow（不计分！——等 K3 这关）
机器验证绿 + K3 复核通过        → 🟢 green（计分；背书 = K3 复核记录或创始人演示核验记录）
```

> 四值对齐 K3 R5 反向契约：`status` 只取四值；`k3_verdict`（pending / pass:<报告ID> / fail:<报告ID>）单独字段记录背书来源；stale（代码变更待重跑）归入 yellow。

**为什么 K3 是最终裁判（而不是 git 或测试）**：git 只证明"代码存在"，测试只证明"写测试的人认为对"——你们的历史（8 次以上声称 vs 现实）证明这两者都可能骗人；K3 零上下文独立复核是唯一被反复验证能抓到真相的关卡。**所以进度条上任何一个"绿"都必须能指到 K3 复核或创始人演示核验；没有 K3 背书的绿 = 黄（待裁判），永远不算数。**

### 5.3 全流程自动化架构（v1.1 新增——创始人问"整个流程能不能自动化"）

> 目标：**创始人和开发者都不做任何"更新仪表盘"的手工动作。** 一切触发式自动化，复用现有基建（GitHub Actions / cron / 控制塔生成器），不新建系统。**决策信息全部落在页面本身（创始人电脑前跟进，不推送、不摘要、不依赖任何聊天工具）。**

| # | 自动化环节 | 触发方式 | 产出 |
|---|-----------|---------|------|
| A1 | **证据失效检测** | post-merge hook / PR 合并事件：涉及线模块的 diff → 自动标相关验收点 stale | 进度页自动变黄（防假绿） |
| A2 | **机器验证入库** | CI 绿（vitest/场景回归）→ 结果写 evidence/ | 测试/场景证据自动更新 |
| A3 | **待办自动聚合** | 每周五 cron + 任意审计报告提交后 | todos.yaml 自动刷新（5 源抓取） |
| A4 | **进度重算** | 每周五 cron + 任何上述事件 | product-progress.json 自动更新 |
| A5 | **页面生成（含周报区块）** | A4 后自动 | 产品进度页更新：线进度/待办/待裁决置顶区/周报区块（页面即真相，创始人打开即见最新） |
| A6 | **K3 报告自动解析（双向契约 R6）** | K3 报告提交（.md 同目录同名 .json，schema 由 K3 标准定义，含每验收点判定数组）→ A6 按**同一 schema** 解析 | K3 判定自动写入状态机（status 四值 + k3_verdict）；解析失败显式 degraded（铁律 24/31）；**A6 自身是被审计对象**（K3 维度 18④ 解析对账） |
| A7 | **K3 复核任务书派发（逢绿必验）** | 转绿声明即入待验池（自动检测 yaml status 变更）→ 最近批次生成 K3 复核任务书（含证据包路径；双周兜底批） | **不设攒量门槛**（K3 维度 17 定稿）；线首达 100% → 20c 全量复核硬触发 |
| A8 | **待裁决置顶区** | A4 后自动从 cockpit-override.yaml 提取 | 页面顶部固定"需要创始人"区（选项+建议+理由），打开即见，无需查找 |

**自动化程度对照表**：

| 环节 | 自动化 | 谁触发 | 创始人的手动动作 |
|------|:---:|--------|----------------|
| 线集定义 | 初稿自动生成，**定稿需创始人** | Phase 0 评审 + 季度 | 唯一"产品定义"手动点 |
| 进度计算/待办/页面 | ✅ 全自动 | cron + git 事件 | 无 |
| K3 审计 | 派发/解析自动；**审计本身 K3 执行** | A7 自动派发 | 无 |
| 演示核验类验收点 | 半自动 | 创始人页面勾选 | 勾选 + 附演示记录（30 秒） |
| 卡点裁决 | 半自动 | A8 待裁决置顶区（页面顶部固定） | 30 秒判断题 |

> 手动点收敛到 3 个：**产品定义评审（季度）、演示核验勾选（偶尔）、卡点裁决（每周几分钟）**——其余全部自动。
