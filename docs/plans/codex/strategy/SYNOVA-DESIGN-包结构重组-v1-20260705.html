Synova 包结构重组方案
v1.0 · 2026-07-05 · 从产品哲学推导的最终包结构

摘要：从 13 个包精简为 9 个包。核心原则：可插拔的做成包，不可替换的留在 src/，文件驱动的继续文件驱动。新增 workspace-agent 包承载被动模式——让企业员工日常向 Synova 提问，就像现在他们问豆包和 DeepSeek 一样。区别是 Synova 知道这家企业的数据。
---

一、为什么调整

1.1 产品定位的变化

Synova 当前的定位是"企业 AI 免疫系统——组织数字孪生诊断 + 持续增长导航系统"。这是一个主动模式的定义：哨兵定时扫描 → 信号聚合 → 专家诊断 → 报告。

但真实世界中，企业员工日常遇到工作中的问题——"这笔费用归哪个科目""这个客户的账期和同类客户比如何""上次被压制的那个提案现在怎样了"——他们问的是豆包、DeepSeek、ChatGPT。这些通用 AI 不了解这家企业、不了解这个行业、不了解老板的偏好。但它们快、免费、随时可用。

Synova 了解一切——但没人问它。因为所有人对 Synova 的认知是"做诊断的体检仪"。它不是日常工作中随叫随到的助手。

这不是技术问题，是产品形态问题。Synova 应该有两种工作模式：

模式触发深度耗时场景
被动模式员工随时提问图查询 1-2 跳 + 基线对比秒级财务归账、销售查客户、产品经理问定价、CEO问提案进展
主动模式Cron 定时 + FDE 按需哨兵扫描 → 信号聚合 → 专家推理 → 诊断报告分钟级月度诊断、关键人风险、NCI非共识检测

两种模式用同一张因果图、同一套本体层、同一个进化引擎。区别只是深度和触发方式。

1.2 包拆分的产品哲学

不是"每个模块一个包"，而是"只有明确可插拔边界的才做成包"：

问自己三个问题如果答案是 YES如果答案是 NO
1. 这个模块的实现在未来会换吗？（存储、日志、LLM Provider）做成包不拆
2. 这个模块需要被多个渠道复用吗？（Electron + IM + API 共用对话引擎）做成包不拆
3. 这个模块的新增能力必须改 TypeScript吗？还是加文件就够了？（哨兵、专家、行业模板）做成包文件驱动即可

按这个标准，原来计划的 21 个包中：

  • 哨兵引擎、专家平台不应是包——它们已经是文件驱动的。extensions/sentinels/ 和 expert/ 加文件即可扩展，打包反而是退步。
  • ConversationEngine 必须是包——它需要被 Electron 桌面端、IM 网关、API 三路复用。
  • WorkspaceAgent 必须是包——它是被动模式的全新入口，面对 1-N 用户并发，需要独立的上下文管理和速率限制。

2.2 每个包的边界和职责

包层级性质对外接口可替换？
logger 基础 可插拔基础设施 createLogger(name) ✅ 换 pino → winston 不影响业务
error-types 基础 可插拔基础设施 DiagnosticAgentError, PermissionDeniedError, CircuitBreakerError ✅ 纯类型合约
llm-providers 基础 可插拔基础设施 LLMProvider 接口, createProvider(config) ✅ 换 DeepSeek → OpenAI → 本地模型
sog-core L4 核心武器 — 不可替换 SOGNodeType, SOGEdgeType, ResourcePool, Activity, Outcome 等类型定义 ❌ 产品级合约。29实体+16边是 Synova 的本体层标准
graph-store L4 可插拔基础设施 createSynovaGraphStore(db), GraphStoreReader, queryNodes/queryEdges/deleteNode/deleteEdge ✅ SQLite → PostgreSQL → 图数据库
knowledge-ingest L4 可插拔基础设施 readFileContent(path), extractEntities(text) ✅ 换文档解析引擎
evolution L0 核心武器 — 不可替换 SessionLearner, OrgAdapter, GlobalAnalyzer, RuleVersionManager ❌ Synova 越用越准的核心机制
extension-registry 横向 可插拔枢纽 ExtensionRegistry, ConnectorRegistry（合并后） — 扩展机制本身就是可插拔的
conversation-engine L2 核心武器 — 多渠道复用 ConversationEngine, processMessage(), ExpertDispatcher ❌ 多 Agent 协作编排是 Synova 的核心
workspace-agent L2 核心武器 — 被动模式入口 WorkspaceAgent, answerQuestion(question, context) ❌ "企业 AI 大脑"的日常消费界面

2.3 为什么 conversation-engine 必须是包

当前 src/agent/conversation-engine.ts 是一个 757 行的单体文件，和 TUI、Electron、IM 代码混在一起。三种渠道各写了一套调用逻辑。独立成包后：

Electron 桌面端 ──→
IM 飞书网关    ──→  @synova/conversation-engine  ──→ ExpertDispatcher
REST API       ──→                                  ──→ GraphStore
                                                     ──→ LLM Provider

一套引擎，三路复用。不再需要在每个渠道重复实现消息处理、上下文管理、按需唤醒专家。

2.4 为什么 workspace-agent 必须是包

被动模式不是"诊断的简化版"，而是一个全新的产品维度。它解决的核心问题是：

  • 1-N 用户并发：50 个员工同时提问，不能每个问题都启动完整诊断管线。workspace-agent 需要独立的上下文管理——每个用户的对话是独立的，但共享同一张因果图。
  • 秒级响应要求：员工不会等 2 分钟。L1 → L5 全管线走一遍太久。workspace-agent 走的是轻量路径：理解意图 → 图查询 1-2 跳 → 基线对比 → 自然语言回答。
  • 数据飞轮：每个提问都在产生信号。财务最关心什么？销售最焦虑什么？这些提问本身就是 NCI 的燃料。被动模式是主动模式的数据燃料。

技术上，WorkspaceAgent 是一个薄层：

用户问题 → LLM 意图识别 → GraphTraversal 1-2 跳 → TemporalBaseline 对比
         → 组装自然语言回答 + 数据引用

它依赖 @synova/graph-store（查图）、@synova/sog-core（类型）、@synova/evolution（行业基线）、@synova/llm-providers（LLM）。它不做哨兵计算、不做专家推理、不做报告生成——那是主动模式的事。

五、Loop Engineering 项目身份更新

5.1 AGENTS.md 项目身份（替换当前 L159-188）

## 项目身份

**产品**: Synova — 企业的 AI 免疫系统。一个驻扎在企业内部的 AI，有两种工作模式：
1. **被动模式**（日常 AI 助手）：员工随时向 Synova 提问工作相关问题——财务归账、销售查客户、产品经理问定价。秒级响应，基于企业专有数据和因果图谱。
2. **主动模式**（深度诊断）：Cron 定时触发哨兵扫描 → 信号聚合 → 专家推理 → 诊断报告 → 方案生成。分钟级完成。

**定位**: 独立 Agent 进程，通过 HTTP API + Electron 桌面端 + IM 网关（飞书/企业微信/钉钉）对外服务。
**市场**: 5-1000 人团队的 AI 免疫系统。GA（增长分析师）为可选中间层。

**三大核心系统**:
1. **WorkspaceAgent 被动问答** — 日常工作中的 AI 助手，基于因果图谱 + 企业专有数据的实时问答
2. **Sentinel 主动诊断** — Cron 定时扫描 + FDE 按需触发，哨兵 → 专家 → 方案 → 跟踪
3. **Evolution 进化引擎** — 越用越准，跨客户积累行业知识

**五层 + L0 架构**:
```
L0 进化    → packages/evolution/ (SessionLearner / OrgAdapter / GlobalAnalyzer)
L1 交互    → routes/ (API), electron-renderer/ (桌面), IM 网关
L2 编排    → packages/conversation-engine/ (多Agent对话), packages/workspace-agent/ (被动问答)
              orchestrator/ (SubAgentCoordinator, ModuleRunner)
L3 洞察    → l3/ (ExpertDispatcher, ExpertAutonomy, QualityFirewall)
              sentinel/ (Runner, SignalAggregator, Registry, 62哨兵)
              expert-platform/ (ExpertStore, Validator)
L4 本体    → packages/sog-core/ (类型定义), packages/graph-store/ (图存储)
              l4/ (GraphBridge, EntityResolver, GraphTraversal, temporal-baseline)
              evidence/ (Collector, Corroboration, EvidenceStore)
L5 存储    → store/ (SessionStore, SQLite, SchemaMigration)
              cron/ (CronScheduler, 持久化作业)
```
横向: packages/extension-registry/ (扩展注册, 含 connector-registry)
基础: packages/logger/, packages/error-types/, packages/llm-providers/
安全: security/ (PIIScrubber, DataBoundary)

**架构规则**: 只能向下依赖相邻层。L1禁触L3/L4/L5。L2禁触L4/L5。pre-commit check-architecture.sh 检测跨层违规。
**文件驱动原则**: 哨兵/专家/行业/模式/进化配置均通过 JSON/Markdown 文件扩展，不改 TypeScript。
**包原则**: 只有明确可插拔边界或多渠道复用的模块才做成独立包。其余留在 src/ + extensions/。

5.2 LOOP.md 活跃循环更新

新增一条循环：

| **WorkspaceAgent Monitor** | 实时 | 每次被动模式问答 | 提问统计 + 高频问题 Top-N + 未被回答的问题队列 | active |

这个循环的用户可见价值：GA 和企业主可以看到"这个月员工问得最多的问题是什么"——这是 NCI 的实时数据燃料。
