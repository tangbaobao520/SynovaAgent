三、P0 致命差距 — v1 交付前必须补齐

以下 6 项缺任何一项，应用在生产环境中都会不可接受地失败。

3.1 启动恢复

对标: OpenClaw main-session-restart-recovery.ts (284行)

启动时扫描会话表中 status='active' 的会话→标记为 interrupted→3秒延迟后遍历→读取最后20条消息→判断可恢复性→可恢复则注入恢复消息→恢复成功更新 status。3次失败标记 status='failed' 通知用户。同样扫描 ExpertDispatcher 中未完成的专家推理重新排队。新建 src/services/restart-recovery.ts，修改 synova-agent.ts start()。6h。

3.2 优雅关闭

对标: OpenClaw active-sessions-shutdown-tracker.ts (54行)

维护 ActiveSessionTracker。关闭时通知所有活跃对话→保存诊断检查点→关闭LLM连接→关闭DB→退出。最大等待30秒，超时写入紧急检查点强制退出。新建 src/services/graceful-shutdown.ts，修改 synova-agent.ts stop()。4h。

3.3 消息投递可靠性

对标: OpenClaw session-delivery-queue-recovery.ts (220行)

MAX_RETRIES=5，退避=[5s,25s,2m,10m]。per-entry去重。崩溃后首次即时重试。超限移到失败队列。排干60秒时间预算。ENOENT安全。新建 src/services/delivery-queue.ts 和 src/l4/delivery-queue-store.ts。SQLite持久化。6h。

3.4 卡住会话检测

对标: OpenClaw diagnostic-stuck-session-recovery.runtime.ts (220行)

诊断运行>5分钟无新Phase→判定卡住。LLM调用>120秒无响应→判定卡住。AbortController.abort()中止。飞行中去重。结果写入AgentMemoryStore。Cron每60秒检测。新建 src/services/stuck-session-detector.ts。4h。

3.5 WAL降级

对标: Hermes hermes_state.py apply_wal_with_fallback()

尝试PRAGMA journal_mode=WAL。捕获"locking protocol"错误→降级DELETE模式。每个DB路径只警告一次（去重）。功能继续正常，仅并发性能降低。修改 graph-store.ts 和 engine-context.ts 的pragma调用。2h。

3.6 全局兜底

对标: OpenClaw unhandled-rejections.ts

process.on('unhandledRejection'): 区分fatal/non-fatal。fatal记录堆栈→优雅关闭→退出码1。non-fatal记录警告→继续。process.on('uncaughtException'): 一律fatal。修改 server.ts createServer() 注册全局处理器。2h。

四、P1 高优先级差距

以下6项不会导致立即崩溃，但严重降低可靠性和安全性。

4.1 速率限制

对标: OpenClaw 3层速率限制

L1 固定窗口: 纯内存，consume()返回{allowed,retryAfterMs,remaining}。100请求/分钟/用户。L2 认证: 滑动窗口per{scope,clientIp}，失败锁定300秒，127.0.0.1豁免。L3 LLM调用: 20次/分钟/orgId，超限排队。新建 src/middleware/rate-limit.ts。4h。

4.2 自动更新

对标: OpenClaw update-startup.ts

electron-updater库。启动时检查+每24h周期检查。下载→校验→提示重启。重启前保存activeOrgId、最后消息ID、未读通知数，重启后恢复。4h。

4.3 配置恢复

对标: OpenClaw io.observe-recovery.ts (600行)

健康指纹SHA-256+字节数。可疑检测: 大小下降>50%或JSON解析失败。自动恢复: 复制.bak→活跃配置→归档覆盖版本→审计。known-good提升。密钥占位符检测。新建 src/services/config-recovery.ts。4h。

4.4 进程隔离

对标: OpenClaw 5条lane+命令队列

3条lane: Main(对话), Cron(哨兵), Expert(专家推理)。每条内部串行，lane间并行。关闭期间拒绝新任务。超时自动杀。新建 src/infra/command-lanes.ts，修改 synova-agent.ts。6h。

4.5 Schema迁移

对标: Hermes _reconcile_columns() + SCHEMA_VERSION=13

版本号在schema_version表。所有DDL集中管理。reconcile()对比现有列和规范列→ADD缺失列。命名约定: migrate{From}To{To}。新建 src/store/schema-migration.ts。4h。

4.6 上下文压缩增强

对标: Hermes context_compressor.py

副模型用便宜LLM做摘要。失败冷却600秒。压缩时创建child_session_id父链。工具输出裁剪作为预通行。token预算尾部保护。修改 src/orchestrator/context-compressor.ts。6h。

五、P2 中期差距 — v1.1

凭据池轮换: 多key池，401/402/429自动轮换。修改 providers/registry.ts。4h。

内存泄漏监控: 每5分钟RSS日志。不可用时禁用。新建 src/services/memory-monitor.ts。2h。

关闭取证: 信号+/proc快照+父进程树+负载均值。修改 server.ts。2h。

双FTS5(CJK): unicode61+trigram。修改 agent-memory-store.ts。3h。

六、值得借鉴的架构模式

6.1 Hook系统作为集成架构（claw-code）

3个生命周期事件: PreToolUse/PostToolUse/PostToolUseFailure。每个钩子是shell命令，JSON stdin→stdout。退出码0=允许，2=拒绝。可返回updatedInput。应用于诊断工具的PreToolUse/PostToolUse、哨兵的PreScan/PostScan、GA纠错的PreCorrection/PostCorrection。

6.2 快速路径启动（claw-code）

12阶段BootstrapPhase枚举。每个fast-path可在到达MainRuntime前早期退出。应用于健康检查、状态查询、缓存报告。

6.3 工作区指纹隔离（claw-code）

FNV-1a 64位哈希→派生会话目录。不同工作区物理隔离。跨工作区恢复需验证。应用于orgId→FNV-1a哈希→派生存储路径。

6.4 原子JSONL转录持久化（claw-code）

write_atomic+旋转(256KB上限，最多3个)。forward-compatible加载。应用于对话转录替代全量SQLite消息存储。

九、第一小时体验：信任不是展示功能，是展示理解

9.1 第一屏是对话的开始，不是自我介绍

用户在焦虑，不是来听AI夸自己。重新设计的第一屏：Synova先听，再工作。

你好，我是 Synova 我是你企业的 AI 免疫系统。 我能持续观测你的财务、组织、市场数据， 在问题刚冒头的时候发现它， 帮你找到增长瓶颈，制定可落地的方案。 我驻扎在这台电脑上。你的数据不会上传到任何云端。 让我们开始吧。先告诉我三件事： 1. 你的企业叫什么？ 2. 你是做什么的？ 3. 现在最让你头疼的是什么？ [开始]

三句话建立信任：能力认知（"AI免疫系统"=巡逻+早发现+早修复）、安全认知（"数据不离开这台电脑"——第一屏回答最大恐惧）、行动引导（三个问题，30秒填完）。如果用户犹豫——"我不知道你能分析什么"——Synova回应："没关系。你告诉我你在担心什么，我来判断我能帮到什么。或者拖一份报表进来，我从数据开始。"

9.2 没有数据也能工作：行业基准作为"先天免疫"

用户回答三件事→Synova用行业模板做初步扫描→后台Level 4诊断→10分钟后托盘弹出"初步诊断完成。发现了3个需要关注的问题。"Codex做不到——它不会在没有代码时帮你写代码。但Synova可以在没有数据时用行业基准做判断。这是免疫系统的体现——不需要宿主主动提供抗原，系统自带先天免疫。

9.3 自由对话的响应者：host专家

日常对话中，谁在回答？不是领域专家——是host专家（主持人/调度者）。host是第9位专家：始终在线，用户和专家团队的唯一接口。领域专家从不直接和用户对话——被host按需唤醒，产出ExpertReport后由host转述。host的5个文件在expert/host/下，文件驱动注册。所有7个领域专家改为background。详见HOST-EXPERT-DESIGN.md。

9.4 信任是3次正确推送累计的

前三次推送用户会怀疑。Synova的应对不是提高阈值减少误报——是对每条推送提供完整追溯链：

应收账款周期从28天→51天(+82%)。客户A：32天→74天(+131%)←主要贡献者，原因：采购系统迁移(来源：6月15日邮件)。客户B/C正常波动。结论：问题集中在客户A，非系统性风险。

用户看完不一定行动——但会对Synova产生信任。下一次打开更快。第三次直接点确认。

9.5 右栏：上下文感知，角色定制

GA选中工作区→右栏三个标签：行动跟踪/哨兵数据/落地模式。对接人选中工作区→右栏行动清单+目标进度+关联影响。企业主→飞轮仪表盘（极简）。部门负责人→关联影响+跨部门背景。实现：rightPanel = renderPanel(userRole, currentContext)。详见PRD v3.0 §4.3。

十、超越 Codex 的独特体验

10.1 多Agent的"思考可见性"

Codex显示"Thinking..."。Synova显示：

Synova 正在分析... ✅ 财务顾问 — 已完成 (1.2s) 初步判断：应收账款异常，非系统性风险 🔄 战略顾问 — 交叉验证中... 正在对比行业数据：母婴行业平均回款周期 ⏳ 组织顾问 — 等待中 财务和战略确认后再评估团队影响

不是loading spinner——是实时专家协作视图。多Agent系统的天然优势。

10.2 GA：人类顾问的"增强"而非"替代"

GA的核心价值：AI做不了的事。GA发现母婴行业Q3是备货季，应收周期本身就长10-15天。AI没考虑季节性。GA纠错"季节性因素未纳入"→进入L0进化→下次同行业自动加入季节性因子→GA把经验写成落地模式JSON→下一个母婴客户自动受益。AI学到了GA的一次判断。Codex没有这个闭环。

10.3 安静模式

一键静音至明早8:00。持续性告警自动降频（每天→每周摘要提及）。连续3次忽略同类推送→系统询问"以后减少？"。AI要知道自己的位置——是辅助者，不是催促者。

10.4 回忆模式

"三个月前发现应收账款周期延长至59天。4月5日确认方案。5月降至38天，6月降至31天。6月15日标记已解决。"不是LLM记忆——是AgentMemoryStore+版本链+企业事实层。

10.5 预判模式

用户在看Q2财务数据。Synova底部浅色提示："按当前趋势，Q3可能出现类似去年Q4的现金流缺口。要不要做对比分析？"用户没有提问，Synova主动提供了洞察。工程基础：哨兵持续运行→BaselineStore历史基线→上下文匹配→历史相似模式→预判。

10.6 后发优势

Codex花了一年做SSE重连、命令面板、会话持久化。我们知道终点在哪——第一天就做。后发不是劣势，是直接跑过去不用摸索。

十一、告警升级链：不以人的承诺为准，以数据的变化为准

11.1 核心矛盾

对接人忽略推送可能因为忙，也可能因为问题暴露的是他自己的失职。他有动力让问题消失。但免疫系统不能因为某个器官不配合就不报告感染。

11.2 升级由数据驱动

风险=影响范围×恶化速度×不可逆程度。推送升级不由对接人点击行为决定，由哨兵客观指标决定。应收账款连升3周→无论他点了多少次"我知道了"→第4周自动升级给企业主。

11.3 升级链

阶段触发动作
首次检测风险指数超阈值推送部门负责人+对接人
7天复查哨兵自动复查改善→降级周报备注。持平→升级风险。恶化→推企业主+GA
14天复查仍无改善推企业主+GA+周报显著标注
28天复查仍无改善GA必须人工介入，联系企业主

不再有"点击确认后停止"的路径。对接人唯一能让告警停止的方法是真正解决问题——哨兵下次扫描数据好转。

11.4 周报是安全网，不是汇总

老板的周报只含三件事：恶化中的、被忽略的（14天无人响应）、跨部门扩散的。正常的、已处理的、部门内已确认的——不进入。
