## 0. 研究背景

### 0.1 为什么需要这次研究

Synova当前的47个哨兵和约100个compute函数是从技术能力出发构建的——"我们能算什么"。但Synova真正的核心用户不是老板（老板一个月看一次诊断报告就够了）——是中层管理者。他们每天在做大量判断，信息永远不完整。拿下中层，才是产品真正进入企业、转换成本真正建立起来的关键一步。

这次研究的目的是：**从中层管理者的JTBD（需要完成的任务）出发，重新定义哨兵和compute函数体系。** JTBD在前，哨兵在后。不预设任何数字——不从"47个哨兵"或"100个compute函数"出发。数量从研究过程中自然收敛。

### 0.2 核心约束

- **不预设任何数字。** JTBD数量、因果信息需求数量、哨兵数量、compute函数数量——全部从研究过程中自然收敛。该是多少就是多少。
- **JTBD在前，哨兵在后。** 不是"我们有什么哨兵所以能服务什么JTBD"——是"中层有什么JTBD所以我们需要什么哨兵"。
- **正交性约束前置。** 不是设计完了再检查是否有重复——正交性是设计过程中的强制约束。

## 1. 研究目标

### 1.1 最终产出

**文档一：哨兵×compute函数×JTBD映射表**
每个哨兵→几个compute函数→数学公式→消费的边参数→图遍历路径→数据可得性→服务的JTBD→服务的角色→行动建议映射→对抗性边界条件。

**文档二：JTBD×因果信息需求矩阵**
每个JTBD→类型(预测/诊断/干预)→需要的因果信息(标准化语法)→[前提假设]→时间约束(实时/周/月)→数据源覆盖度→数据可得性复核标记→对应哨兵→中层可控性→行动映射→决策反馈需求→主动触发器标记。

**文档三：跨场景JTBD重叠度分析报告**
Jaccard相似度矩阵 + 核心角色JTBD跨行业通用性判定 + 对Synova产品形态的建议。

**文档四：语义对齐测试集**
16条边参数的查询测试用例 + 各路独立完成的输出 + 偏差报告。

**文档五：对抗性验证报告**
每个compute函数的3个历史案例回测结果 + 至少1个模糊案例的特别分析。

### 1.2 产出存放位置

所有研究产出存放在 `docs/plans/codex/jtbd-research/` 目录下。按文档管理规范命名。

## 3. 前置Gate

### Gate 1：JTBD语义等价判定矩阵（第一阶段启动前完成）

**为什么需要：** 6个场景独立穷举的JTBD在汇合时，哪些是"同一件事的不同表述"、哪些是"完全独立的需求"——没有预定义的判定标准，"自然收敛"就是"谁写文档谁决定"。

**判定逻辑（三步法）：**
1. 核心决策动词是否相同？（"分配"vs"预测"vs"诊断"）
2. 作用对象是否相同？（客户/渠道/产品/人员/资金）
3. 信息缺口是否同源？（都是沿PRODUCES边汇聚→可能同一类）

三步判定后分类，分类后再去重。

**产出：** JTBD语义等价判定矩阵文档。

### Gate 2：跨场景JTBD重叠度分析（第一阶段完成后触发）

**为什么需要：** 如果不同场景下同一角色的JTBD重叠度>0.7——核心JTBD是跨行业通用的，Synova可以做通用产品。如果<0.3——"通用中层诊断系统"是伪命题，必须走行业深度定制路线。这个判断直接决定Synova的产品形态和商业模式。

**方法：** 计算不同场景下同一角色的JTBD Jaccard相似度。输出相似度矩阵 + 判定建议。

**产出：** 跨场景JTBD重叠度分析报告（文档三）。

### Gate 3：语义对齐测试集（第三阶段启动前完成）

**为什么需要：** 如果只是"各路负责人开个会统一文档"——理解偏差在并行压力下会被成倍放大。测试集是工程上唯一可行的对齐验证方法。

**方法：** 构建一组包含所有16条边参数的查询测试用例。各路负责人独立完成测试集，输出结果偏差必须<5%。未通过的路，不允许进入并行阶段。

**产出：** 语义对齐测试集 + 偏差报告（文档四）。

## 4. 第一阶段：JTBD独立穷举 + 类型分类 + 角色标注

### 步骤1.1：场景锚定
JTBD穷举锚定在3个代表性行业×2个规模=6个场景。每个场景下独立穷举，不交叉。
- 消费品—中小（20-99人）/ 中大（100-499人）
- 制造—中小 / 中大
- SaaS—中小 / 中大

### 步骤1.2：JTBD独立穷举
先不按角色分——先穷举中层需要完成的决策型JTBD。每个JTBD用标准化句式描述：**"我需要[做什么决策]，但我不确定[什么信息]"**。不预设数量上限。

### 步骤1.3：JTBD类型分类
每个JTBD标注类型：
- **预测型：** "下个季度E区域能完成多少销售" → 需要因果边的趋势外推、时序基线、行业对标
- **诊断型：** "为什么A客户的复购率在下降" → 需要因果边的断裂检测、多边联合推理
- **干预型：** "如果延期C客户的账期，现金流会怎样" → 需要因果边的反事实模拟、调节因子计算

JTBD的类型决定了需要哪类compute函数，不是JTBD本身。

### 步骤1.4：角色标注
每个JTBD标注：哪些角色执行它（可多选）、每个角色各自需要什么信息维度。同一个JTBD"评估新市场机会"——CFO需要ROI和现金流，产品经理需要技术可行性和用户需求，销售VP需要渠道和客户关系。不是3个不同的JTBD——是同一个JTBD的3个信息维度。

### 步骤1.5：跨角色协同JTBD独立标注
识别需要两个以上部门同时协同的JTBD。例如"销售VP决定给大客户延期账期←→CFO需要同时评估现金流风险"。

### 步骤1.6：跨场景JTBD重叠度分析（Gate 2）
计算不同场景下同一角色的JTBD Jaccard相似度。输出相似度矩阵 + 判定建议。

### 步骤1.7：JTBD语义等价判定矩阵应用
将步骤1.1-1.5产出的JTBD汇合，按Gate 1定义的判定矩阵进行语义等价分类和去重。

## 5. 第二阶段：因果信息需求推导 + 标准化

### 步骤2.1：建立标准化语法
每条因果信息需求必须用以下格式表达：

```
JTBD-XXX {需要[某个实体的][某个边参数][在某个时间窗口内的][某个聚合方式][与某个基准对比]}
         [前提假设: XXX]
```

例如："需要[A客户]的[PRODUCES.marginal_contribution][过去3个月的][趋势][与B客户对比] [前提假设: A客户订单模式未发生结构性变化]"——可验证、可编码。

当前提假设被触发时，系统主动推送："你之前的决策依据正在失效，请重新评估。"

### 步骤2.2：逐JTBD推导因果信息需求
对第一阶段产出的所有JTBD，用标准化语法逐一推导。每个JTBD标注：
- **时间约束：** 实时（秒级）→ 轻量查询。周（小时级）→ 多边推理。月（半天）→ 全图遍历+三阶推理。
- **中层可控性：** 0=无权改变/1=可影响/2=可调整/3=可直接决策。可控性=0的需求筛掉。
- **可行动性：** 知道了这个信息后，中层能做的具体动作是什么。
- **数据源覆盖度：** 涉及几个数据源？在锚定场景中的可用性和同步状态？

### 步骤2.3：行动映射
每个因果信息需求，附加"输出→行动建议映射"。不是"边际贡献下降"——是"建议将A客户的优先级从P0下调到P1，将释放的销售资源分配给边际贡献更高的B客户"。

### 步骤2.4：决策反馈闭环需求标注
对每个干预型JTBD，标注"决策效果追踪需求"——"上次我调整了D渠道预算，这个渠道的转化率改善了吗？"

### 步骤2.5：主动触发器机制
对每个干预型JTBD，标注"主动触发器"——决策执行后，系统主动监控关键指标，偏离预期时自动告警+建议重新调整。这是建立中层转换成本的核心。

### 步骤2.6：数据可得性复核
所有数据可得性标注完成后，由覆盖所有锚定场景的研究员逐条复查。标记所有"不确定可得性"的数据需求。标记为"不确定"的，对应compute函数标注"需GA手工采集"，而非"自动可得"。

## 6. 第三阶段：因果信息需求→哨兵+compute函数映射（多路并行）

### 步骤3.0：语义对齐测试集（Gate 3）
构建包含所有16条边参数的查询测试用例。各路负责人独立完成测试集，输出结果偏差必须<5%。未通过的路，不允许进入并行阶段。产出文档四。

### 步骤3.1：正交性约束清单（并行前强制定义）
- 同一个因果参数只能由一个compute函数负责提取。
- 如果需要不同的聚合方式（按客户群/按Activity/按时间窗口），那是同一个compute函数的不同调用参数，不是两个compute函数。
- 正交性判定标准："图遍历路径+聚合方式"是否相同——不是"是否源自同一条边的同一组参数"。

### 步骤3.2：多路并行执行
多路并行。每路负责2-3个中层角色的哨兵+compute函数映射。每条因果信息需求→判定由哪个哨兵提供→需要几个compute函数。每个compute函数标注：
- 数学公式
- 消费的边参数
- 图遍历路径
- 数据可得性（自动/GA手工/企业补充）
- 输出→行动建议映射
- 时间约束下的计算路径复杂度

### 步骤3.3：对抗性边界条件
每个compute函数必须通过至少3个历史案例的回测验证：
- 1个成功案例
- 1个失败案例
- **至少1个"当时信息极度模糊、但事后被证明正确/错误"的模糊案例**（如2010年的特斯拉、2015年的拼多多）

产出文档五。

---

## 7. 第四阶段：汇合 + 去重 + 正交性检验

各路产出汇合。去重——同一个因果信息需求是否被不同路重复分配了compute函数。正交性检验——按照第三阶段的约束清单，检查是否有违规。JTBD类型检验——预测型和诊断型的compute函数是否被混用。跨角色协同检验——协同JTBD的因果信息是否在两个角色的映射中都得到了覆盖。

最终产出文档一（哨兵×compute×JTBD映射表）和文档二（JTBD×因果信息需求矩阵）。
