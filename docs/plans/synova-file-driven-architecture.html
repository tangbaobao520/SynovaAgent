1. Anthropic 决策思维：我们如何思考这项工程

原则 1：找到根因，用一个机制防一类错。
18 个维度的硬编码共享同一个根因——能力定义和消费逻辑耦合在一起。解耦方式是统一扩展点注册协议 + 属性驱动消费。做对了这个，18 个维度的改造只是同一模式重复应用 18 次。
（对齐 V3.1 设计哲学：从"每犯一错加一脚本"→"找到根源，用一个机制防一类错"）
原则 2：先设计验证标准，再设计实现。
"无线拓展"是可证伪的命题。最终验收：签下一个虚拟行业（pizza-chain），不修改任何 .ts 文件，系统启动后专家能正确诊断该行业的组织健康度。这个测试在每个 Phase 交付后都要跑，不是最后才跑。
原则 3：按依赖关系排执行顺序，不按理想排。
v1.0 按商业优先级排（P0→P1→P2），但工程上被依赖的必须先做。引擎迁移 Claude 的建议更务实：先做"今天就能做、零依赖"的（i18n、报告模板、框架库、通知），再做需要对接的（哨兵、规则），最后做引擎耦合的（连接器、数据源）。见 1.2 执行顺序。
原则 4：安全边际——每一步可回滚，每一层可降级。
迁移期间同时支持旧代码路径和新文件路径。每个维度由 feature flag 控制（默认新路径），出问题一键切回旧路径。迁移完成后删除旧代码 + flag。
（对齐铁律 31：降级信号传播）
原则 5：物理强制，零 AI 自律。
pre-commit 硬阻断：manifest 声明了但文件不存在 → 拒绝提交。标签值不在 tags.json → 拒绝提交。新增 engine-core 引用 → 铁律 46 阻断。
（对齐 V3.0：pre-commit 从 5 项扩至 8 项，全部 <8s）

3b. 三层粒度模型：专家 → 哨兵 → 计算

2026-06-22 已决策。 这不是"建议"——这是架构约束。所有哨兵重构必须遵循此模型。
专家 — 领域
解读 N 个哨兵的 Finding
→
哨兵 — 子领域
综合 M 个指标，判断"这个子领域出问题没有"
→
计算 — 指标
纯数学，盯一个数

哨兵边界规则

哨兵 = "可以独立说'这里出问题了'的最小子领域"。不是整个领域（太粗），不是一个指标（太细）。
太粗 ❌正确 ✅太细 ❌
一个哨兵盯整个财务成本哨兵、收入哨兵、现金流哨兵各自独立一个哨兵只算毛利率
输出："财务有点问题"输出："成本结构恶化，具体是 X/Y/Z"输出："毛利率跌了 2%"(本身不值得告警)

以财务专家为例

财务专家
  ├── 成本哨兵 → Finding: "成本结构恶化，固定成本占比上升"
  │     ├── 毛利率变化率          ← 计算（纯数学）
  │     ├── 固定/变动成本比       ← 计算
  │     └── 人均成本趋势         ← 计算
  ├── 收入哨兵 → Finding: "收入增长放缓，客户集中度危险"
  │     ├── 收入增长率
  │     ├── 客户集中度
  │     └── 客单价趋势
  ├── 现金流哨兵 → Finding: "现金流紧张，跑道 3 个月"
  │     ├── 现金跑道
  │     ├── 应收逾期率
  │     └── 经营现金流 vs 净利润
  └── 利润哨兵
        ├── 利润率变化
        └── 毛利率 vs 行业基准

与当前代码的关系

当前 12 个哨兵都是 1:1（一个哨兵 → 一个 compute 函数）。这不是设计意图——是 engine-core 遗留的粗糙实现。重构策略：

  1. 按子领域合并哨兵（如合并多个财务相关指标 → 4 个财务哨兵）
  2. 旧哨兵中没价值的砍掉
  3. 先做哨兵结构，再逐步填充 compute 文件（不需要一次填满）

4.3 统一加载引擎：ExtensionLoader

基于已有但零接线的 packages/extension-registry/（已实现 discover() + hotload() + manifest.json 发现 + 动态 import() + 生命周期管理）。

class ExtensionLoader<T> {
  constructor(
    private baseDir: string,                    // 如 "extensions/llm-providers"
    private manifestType: string,               // 如 "llm-provider"
    private registry: Registry<T>,              // 目标注册表
    private validator: (m: Manifest) => ValidationResult[]
  ) {}

  async scan(): Promise<LoadResult>;           // 先读 manifest → 按清单加载 → 校验 → 动态 import → 注册
  async hotReload(name: string): Promise<void>; // 热加载单个扩展
  async unload(name: string): Promise<void>;   // 卸载单个扩展
}

关键行为：

  • 先读 manifest，再按清单加载 — 不无限制扫描目录
  • 单个失败不阻塞 — 每个扩展独立 try/catch，失败降级 + 告警，不阻止启动
  • 依赖拓扑排序 — 解析 requires 字段，按依赖顺序加载
  • 校验失败 → 不注册 — manifest 非法、entryPoint 缺失、类型不匹配 → 记录错误，跳过

7.1 哨兵子领域拆分

  2. 旧哨兵中没价值的砍掉
  3. 先做哨兵结构（manifest + aggregate），再逐步填充 compute 文件（不需要一次填满）

哨兵文件结构：

extensions/sentinels/cost-health/
├── manifest.json        ← schedule, thresholds, expert: "finance", computes 列表
├── computes/            ← N 个计算指标（纯数学函数）
│   ├── gross-margin.ts
│   ├── fixed-variable-ratio.ts
│   └── cost-per-head.ts
└── aggregate.ts         ← N 个指标 → 1 条 Finding ("成本结构恶化，具体是 X/Y/Z")

7.2 compute 函数重写 + L3→L5 架构修正

→
