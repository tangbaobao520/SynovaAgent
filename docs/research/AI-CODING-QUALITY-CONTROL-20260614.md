# AI 编码质量控制系统 — 问题、方案、优化方向

> 2026-06-14 | 征求外部专家建议

---

## 背景

SynovaAgent 由一个 AI 编码智能体（Claude Code）独立开发。仓库约 10 万行 TypeScript，五层架构（L1 交互 → L2 编排 → L3 洞察 → L4 本体 → L5 存储），包含哨兵监控系统、6 位专家 Agent、组织数字孪生引擎等。

**核心困惑**：AI 写代码极快，但会系统性地跳过关键步骤——不读设计文档、不追踪接口、凭记忆做假设。这些错误在测试和类型检查中不会被发现（逻辑正确但架构错误、数据流断裂），需要人来纠正。

---

## 一、已发现的具体问题

### 问题 1：跳过文档和设计

AI 收到"做 X"的指令后直接写代码，不读全量对齐手册、不查接口定义、不追踪数据流。

**真实案例**：
- AI 说"接"，立刻写了 4 个文件的代码。事后发现：调用的接口签名记错了、推荐的专家类型和现有系统的枚举值不匹配、engine-core 的拆分状态没有确认。
- AI 多次提及"Novis 前端"作为结果呈现方案——但 Novis 项目已暂停，SynovaAgent 是纯 API 服务，根本没有前端。
- AI 声称哨兵系统"可以工作了"，但哨兵产出的发现只存在内存中，从未暴露给任何用户——信号聚合引擎算完就扔，专家系统根本不知道有信号。

### 问题 2：求快导致的质量下降

AI 在"直接做"模式下犯错率远高于"先查再做"模式。具体表现：
- 不 grep 函数签名，凭记忆写调用
- 不读五层架构约束，L1→L3 跨层调用
- 不听工作流提醒（CLAUDE.md 写了但被忽略）
- 不填 task brief（任务启动文档）

### 问题 3：AI 自律不可靠

CLAUDE.md 里写了"每次接受任务前先跑 task-start.sh"，但 AI 有选择性地执行。文字指令不能替代物理阻断。

---

## 二、已实施的解决方案

### 方案 A：Git Hook 物理强制（提交前阻断）

**pre-commit**（33 项硬阻断）：
- `as any` 零容忍、Mock/TODO 残留、CJS require、`.only()`/`.skip()`、空 catch 无 log
- Task brief 不存在 → 拒绝提交
- SPEC.md 缺失 → 拒绝提交
- 新文件未接线 → 拒绝提交
- 所有脚本的 `exit 0` 逃生舱和 `timeout` 超时放行已删除

**pre-push**（6 道门禁）：
- 决策树 + tsc + vitest + 铁律全量 + 接线审计 + 架构边界

### 方案 B：Claude Code Hook 物理阻断（写代码前阻断）

**PreToolUse hook**（匹配 `Edit|Write`）：
- 无今日 task brief → 拒绝执行写操作（exit 1）
- 例外：允许写 `.claude/task-briefs/`（创建 task brief 本身）

**PostToolUse hook**：写代码后持续提醒

**SessionStart hook**：会话开始时检查 task brief

### 方案 C：Task Brief 升级为迷你设计文档

每次写代码前必须填写的 6 个必填字段（全部由 PreToolUse hook 强制非空）：

1. **项目身份**（固定头部，每次重读）— 含五层架构 + 完整数据流图
2. **本任务在哪一层** — L1-L5 层级标注，跨层风险
3. **文档引用** — 全量对齐手册具体节号
4. **接口审计** — 从代码 grep 的函数签名（格式：`文件名:函数名(参数) → 返回类型`）
5. **数据流** — 输入→处理→输出（必须含 `→` 箭头）
6. **用户旅程** — 谁→什么场景→看到什么结果

## 三、仍存在的局限

### 局限 1：Hook 只能验证格式，不能验证真实性

AI 完全可以在 6 个字段里写出看起来很对的内容——而不真正去读那一章、不真正 grep 接口、不真正追踪数据流。Hook 检查的是"有没有文本"和"有没有 `→` 箭头"，检查不了"你说的函数签名是否真的存在于代码中"。

**Hook 消除了最低级的问题（跳过步骤），但管不了"假装做对了"。**

### 局限 2：pre-commit 是最后一道防线，但不是写代码时的防线

AI 可以不填 task brief 写代码——Hook 只阻止 Write 工具的执行，但 AI 可以通过对话中的伪代码、设计讨论等不触发 Write 的方式来推进。而且如果 AI 从始至终都不 commit，pre-commit 永不会触发。

### 局限 3：没有"预验证"

AI 写了一个函数、改了 3 个文件——只有到 commit 时才会被质量门禁拦截。如果 AI 在中间步骤就做错了（比如函数签名记错了），要到很后面才会发现。

### 局限 4：错误分类不够细

当前错误全走 `log.error` + `degraded: true`，但调用方无法根据错误类型做差异化恢复。已有铁律 32 要求错误包装为 `.code` + `.phase` + `.retryable` 的子类，但覆盖率不足。

## 四、可考虑的优化方向

### 方向 1：接口审计自动化

`generate-task-brief.py` 可以自动搜索关键字，将可能的函数签名预填入 task brief。AI 不需要"凭记忆"，但需要"确认"。

```
# hook 自动执行：
grep -rn "export.*function\|export.*class" src/ | grep -i "<关键字>"
→ 预填入接口审计区域
# AI 的责任从"回忆接口"降为"确认接口"
```

### 方向 2：接口审计反向验证

PreToolUse hook 读取 task brief 中写的函数签名，逐一 grep 确认是否真的存在于代码中。如果 AI 写了假的函数名 → 拒绝放行。

### 方向 3：增量验证（写一步验一步）

不是 commit 时才验证，而是每写一个文件就自动验证：
- `PostToolUse` (Write) → 自动 `tsc --noEmit` 检查新文件
- 跨层引用检测在每个 Write 后立即运行
- 自动运行与该文件相关的测试

### 方向 4：任务自动切片

AI 说"接线"，系统自动拆成 4 步：
```
① 读取 ExpertDispatcher 接口签名 → 填入 task brief
② 读取 SignalAggregator 输出格式 → 确认转换函数
③ 写转换函数 spec
④ 写代码
```
每步之间有物理停顿（需要填 task brief 字段），阻止 AI 直接跳到第 ④ 步。

### 方向 5：历史错误模式匹配

维护一个"AI 曾经犯过的错"模式库，在 task brief 阶段自动匹配：
```
如果 task 涉及"接线" → 提醒: "历史上 4 次接线失败（ViewAdapter/Phase0Engine/ModuleRunner/GraphBridge），每次都是组件建好了但从未被调用"
如果 task 涉及"新建 API" → 提醒: "历史上 sentinel findings API 暴露了内部 L3 信号给 L1，正确的做法是先经过专家层"
```

### 方向 6：代码审查前置

在 commit 前，利用另一个 AI 实例（或同一个 AI 的审查模式）做一次快速审查。本项目的 28 个 skills 中已有 `code-review` 和 `security-review`，但没有自动触发。

## 五、核心问题（求专家意见）

1. **AI 编码智能体的"求快"倾向是 prompt 层面的问题还是架构层面的问题？** Task Brief + Hook 的组合已经尽可能物理强制了，但 Hook 只能验证格式，验证不了 AI 是否真的"思考了"。

2. **有没有更好的"写代码前"阻断机制？** 我们目前的 PreToolUse hook 检查 task brief 的格式完整性，但有没有办法验证 AI 是否真的读了指定文档、追踪了实际接口？

3. **你应该在什么时候介入审查？** 项目创始人不是技术人员，无法审查代码。当前的设计是让 AI 自己验证自己——这是不是根本性矛盾？

4. **有没有我们没有考虑到的更优方案？** 不限技术栈、不限工具。
