二、每个维度的端到端数据链

D1 目标对齐（Goal Alignment）

核心问题：人和 Agent 追求的目标一致吗？

数学公式：
组织目标向量 G = {g₁, g₂, ..., gₙ}（从 OKR/战略文档 NLP 提取）
团队 A 执行向量 Eₐ = {e₁, e₂, ..., eₙ}（从资源分配比例近似）

对齐度 = cosine(G, Eₐ) = G·Eₐ / (|G| × |Eₐ|)
→ 1.0 = 完全对齐，0.0 = 不对齐，负值 = 方向相反

跨层级衰减率 = 对齐度ₗₐᵧₑᵣ / 对齐度ₗₐᵧₑᵣ₋₁
衰减率 > 20%/层 → 战略传递存在系统性障碍

碳硅对齐度（Synova独有）：
Agent 目标向量 A = NLP(system_prompt + 护栏配置)
人-Agent 对齐度 = cosine(E_team, A)
→ 低分 = Agent 在追求和团队不一致的目标
数据源采集方式处理输出
OKR/KPI 文档task-system-collector 读取LLM NLP 提取目标维度 → 向量 G目标对齐度评分(0-10)
衰减热力图（哪层断了）
碳硅偏差报告
团队资源分配数据task-system-collector各维度资源占比 → 向量 E
Agent system promptagent-audit-collector 读取LLM 提取隐式目标 → 向量 A
员工自评survey-collector"你的工作目标是什么" → 感知目标向量

测量器 compute()：

compute(teamId):
  1. 加载 G = loadOKRVectors(teamId)
  2. 加载 E = loadExecutionVectors(teamId)
  3. 加载 A = loadAgentGoalVectors(teamId)  // 如果有 Agent
  4. 计算对齐矩阵: 每对 Gᵢ, Eⱼ 的 cosine
  5. 检测衰减层: 对 adjacent(layer_i, layer_{i+1}) 计算衰减率
  6. 碳硅对齐: 对每个有 Agent 的团队计算 cosine(E, A)
  7. 输出: { score, decayHeatmap, carbonSiliconGap, confidence }

D2 能力分布（Capability Topology）

核心问题：什么能力由谁持有？谁在什么任务上更可靠？

数学公式：
任务需求矩阵 R(n×k)：n 个任务需要 k 种能力
能力供给矩阵 S(m×k)：m 个人/Agent 在 k 种能力上的水平

匹配质量 = Σᵢ maxⱼ(cos(Rᵢ, Sⱼ)) / n
→ 1.0 = 每个任务都有完美匹配的执行者

能力缺口 gapⱼ = Σᵢ(rᵢⱼ × 权重ᵢ) - max(s₁ⱼ, ..., sₘⱼ)
→ 正 = 缺能力，负 = 冗余

比较优势 CA(Agent,Task) = Agent成功率 / 人类成功率
→ >1 = Agent 优势（该任务给Agent），<1 = 人类优势

能力分布熵 = -Σ(pⱼ × log(pⱼ)) / log(k)
→ 1.0 = 均匀分布，→ 0.0 = 集中在少数人（关键人依赖）
数据源采集方式输出
技能矩阵（自评+绩效）survey-collector + HR系统能力拓扑图
缺口热力图（哪个能力最缺）
任务分配优化建议（谁该做什么）
关键人依赖预警
项目任务分配记录task-system-collector
Agent 任务成功率agent-audit-collector（日志分析）
Agent benchmark 数据agent-audit-collector（定期读取）

D3 协作动力学（Collaboration Dynamics）

核心问题：人和 Agent 的协作回路完整吗？委托率健康吗？

数学公式：
协作网络 G=(V,E)，V=人+Agent，wᵢⱼ=单位时间协作次数

网络密度 = 2|E| / (|V|×(|V|-1))
→ 过高 = 过度协作 → 过低 = 孤立

聚集系数 Cᵢ = 邻居间连接数 / 最大可能连接数
→ 高 = 信息局部快速传播但可能形成小团体

HITL回路完整度 = 人→Agent指令频率 × Agent→人反馈频率
AI2L回路完整度 = Agent主动传递信息次数 / Agent总行动次数
回路完整度 = min(HITL, AI2L)

委托率 = Agent自主完成任务数 / 总任务数
→ 健康区间 0.3-0.6（行业依赖），>0.8 = 技能退化风险，<0.1 = 未利用
数据源采集方式输出
飞书/IM消息日志feishu-message-collector协作网络拓扑图
回路完整度评分
委托率趋势 + 健康区间判断
过度协作/协作不足标记
任务系统（任务分配+完成）task-system-collector
Agent调用日志agent-audit-collector
Agent→人反馈记录agent-audit-collector

D4 治理结构（Governance Architecture）

核心问题：Agent 的决策边界清晰吗？失效时谁负责？

数学公式：
决策延迟 T_d ~ Exp(λ)，λ = 1/E[T_d]
→ λ > 1/week = 流畅，λ < 1/month = 瓶颈

组织内耗 = 平均审批节点数 × (被推翻决策数 / 总决策数)
→ 高内耗 = 决策权过于集中或冗余

委托章程完备度 = 有明确边界的Agent数 / 总Agent数
边界定义：操作范围 + 金额上限 + 否决机制 + 审计日志
→ < 50% = 治理真空（最危急）

审计覆盖率 = 有完整审计日志的决策 / 总决策数
→ < 80% = 存在不可追溯的决策
数据源采集方式输出
审批系统日志agent-audit-collector治理健康度评分
治理真空红色告警(完备度<50%)
决策瓶颈定位
审计盲区清单
Agent 护栏配置agent-audit-collector（直接读取）
Agent 决策日志agent-audit-collector
组织架构图GraphStore 读取

D5 认知健康（Cognitive Health）

核心问题：输出多样性是否在健康范围？是否存在多样性坍塌？

数学公式：
输出主题分布 P = {p₁, p₂, ..., pₙ}（n=时间窗口数）

Shannon熵 H = -Σ(pᵢ × log₂(pᵢ))
标准化多样性 = H / H_max，H_max = log₂(n)
→ >0.7 = 健康，<0.3 = 多样性坍塌预警

Jensen-Shannon散度：JSD(P||Q) = ½KL(P||M) + ½KL(Q||M)
→ 随时间减小 = 团队输出趋于同质化

认知偏移检测：如果 KL(P_当前 || P_基线) > 阈值
→ 输出分布显著偏移 → 检测方向（同质化 or 创新）

过度委托率 = 人类直接编辑量 / (编辑量 + Agent生成量)
→ 持续下降 = "人的笔生锈了"，<0.1 = 认知能力退化信号
数据源采集方式输出
文档/消息/报告feishu-message-collector + 文档系统多样性评分(0-10)
坍塌预警（JSD下降趋势）
人机创作比率趋势
认知偏移方向 + 幅度
编辑日志（人 vs Agent）task-system-collector
Agent 输出日志agent-audit-collector

D6 进化适应性（Evolutionary Fitness）

核心问题：组织的学习速度跟得上 Agent 能力的进化吗？

数学公式：
α_org = 1 / E[T_recover]
T_recover = 外部变化→组织恢复稳态的天数

α_agent = (Benchmarkₜ - Benchmarkₜ₋₁) / 30天

适应速率比 = α_org / α_agent
→ >1.0 = 组织跑在Agent前面（健康）
→ <1.0 = Agent跑在组织前面（治理风险积累）
→ 趋势下降 = 组织正在被甩开

变革准备度 = 成功完成的结构性变化数 / 最近12个月

Agent能力漂移 = KL(实际行为分布(t) || 期望行为分布(t₀))
→ 持续增大 = Agent行为偏离初始配置，需重新校准
数据源采集方式输出
组织变更记录（时间戳）GraphStore + task-system-collector适应速率比（核心指标）
Agent甩开组织的红色告警
变革准备度趋势
Agent能力漂移检测
Agent benchmark数据（月度）agent-audit-collector
Agent行为日志agent-audit-collector
组织架构变更频率GraphStore

三、数据管线设计

3.1 四个 Collector 的接口定义

interface OrgCapabilityCollector {
  /** 采集器名称 */
  name: string;

  /** 采集数据源 */
  collect(teamId: string, sinceISO: string): Promise;

  /** 支持的维度（哪些 D 需要这个数据） */
  serves: ('D1'|'D2'|'D3'|'D4'|'D5'|'D6')[];

  /** 采集频率建议 */
  frequency: 'daily' | 'weekly' | 'monthly';
}

interface CollectorPayload {
  teamId: string;
  collectedAt: string; // ISO-8601
  /** 结构化记录（按数据类型分） */
  records: {
    messages?: MessageRecord[];
    tasks?: TaskRecord[];
    okrs?: OKRRecord[];
    agentConfigs?: AgentConfigRecord[];
    agentLogs?: AgentLogRecord[];
    surveys?: SurveyRecord[];
    orgChanges?: OrgChangeRecord[];
  };
  /** 采集元数据 */
  meta: {
    dataSource: string;
    dateRange: { from: string; to: string };
    completeness: number; // 0-1，数据完整度
    errors: string[];
  };
}

五、测试策略

5.1 铁律 29：指标验证

在进入任何优化循环之前，每个维度的评分公式必须通过双样本验证：

维度确认应一致的两个样本确认应不一致的两个样本
D1同一团队的OKR和资源分配（应高度对齐）不同事业部的目标向量（应明显不同）
D2同一角色的两个人（能力应接近）研发 vs 销售（能力向量应正交）
D3同一项目组的两个子团队（协作密度应接近）紧密协作团队 vs 独立工作团队
D4两个都有完整护栏的Agent（完备度应都高）有护栏 vs 无护栏的Agent
D5同一行业两个相似规模团队（多样性应在同一区间）高度自动化团队 vs 纯人类团队（前者应更低）
D6同一时期成立的两个团队（适应速率应接近）频繁重组团队 vs 常年稳定团队

门禁：一致样本得分差异 < 1.0，不一致样本得分差异 > 3.0 → 指标有效。否则不进入优化循环。

六、和现有系统的集成

6.1 和七维度测量器的关系

六维模型（D1-D6）是组织能力领域的核心方法论。七监测维度中的 D3（人+Agent混合组织） 直接映射到六维模型，D2（组织能力）部分映射。

六维模型 (理论)                    七监测维度 (工程)
─────────────────                  ─────────────────
D1 目标对齐        ───────────→ D2 组织能力（目标对齐度测量器）
D2 能力分布        ───────────→ D2 组织能力（能力缺口测量器）
D3 协作动力学      ───────────→ D2 组织能力（协作健康度/决策质量/注意力）
                   ───────────→ D3 人+Agent（协作质量/混合信任）
D4 治理结构        ───────────→ D3 人+Agent（Agent治理相关）
D5 认知健康        ───────────→ D3 人+Agent（认知多样性/技能迁移）
D6 进化适应性      ───────────→ D3 人+Agent（Agent渗透率/能力缺口）

6.2 和组织专家 Agent 的关系

组织专家 Agent 消费六维模型的诊断结果，执行 LLM 推理：

六维测量器（纯计算）→ 输出数值评分
        ↓
组织专家 Agent（LLM推理）→ 解释数值含义
        ↓
交叉验证（多专家）→ 综合诊断
        ↓
FDE 看到报告

七、未解问题的工程化处理

未解问题（从研究报告 §7）工程化处理
结构效度：D1-D6 是否真的独立？ Phase 3 做因子分析。在此之前，6 个维度分别评分但不强制独立性假设——允许维度间存在合理相关
跨文化有效性：中国/韩国/欧美的权重是否不同？ 权重设计为企业画像的函数（行业+规模+地区），保持可配置。Phase 3 收集不同市场数据后调整
组织规模效应：5人 vs 500人 vs 5000人 每个维度的阈值和健康区间按规模分组。小团队 D4（治理）要求更低，D6（适应性）权重更高
Agent 能力水平的调节 Agent benchmark 作为 D2 和 D6 的调节变量输入。Agent 越强，D4（治理）的紧迫性越高
D5 正常范围的未知 Phase 1-2 不做硬阈值——只报告趋势和相对位置。Phase 3 有足够数据后建立基线
因果 vs 相关：好治理导致好绩效 or 反之？ Phase 3 纵向跟踪——同一组织的治理改善后绩效变化 → 提供因果证据（非RCT级别但足够用于产品）
