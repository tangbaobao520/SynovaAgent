## 〇、一句话定义（不变的三层粒度）

**专家 → 哨兵 → 计算（compute）**：一个专家管 N 个哨兵；一个哨兵含 N 个 compute 指标。
**哨兵 = 可独立告警的最小子领域**；**compute = 纯数学函数，不碰数据库**。
**判据（本件新增，取代"文件齐即完整"）**：**十环全通 + 每环有穿生产入口的证据**。

## 二、哨兵的四类角色（保留旧权威口径，补判据）

| 类型 | 数量（旧） | 职责 | 本件新增判据 |
|---|---|---|---|
| **诊断型** | 26 | 发现异常 → 触发诊断 | 必须能在 `sentinel_tickets` 产出工单 |
| **导航型** | 3（**短板**） | 跟踪执行 → 辅助决策 | 必须有"执行跟踪"信号（旧文档记"执行跟踪/假设监控仍为空"） |
| **混合型** | 12 | 诊断 + 导航 | 两类信号都要能产出 |
| **专项型** | 9 | 特定理论框架 | 需标注理论来源（旧文档 §七 学术基础） |

**立法**：角色是**产品语义**，不是技术分类 ⇒ 每类**必须至少有一条穿生产入口的产出判据**，否则该哨兵**不得计入任何类型的"完成数"**。

## 三、注册体系：**统一为单入口**（旧权威的明确待办，今日仍未完成）

**旧权威原文（`:29-48`）**：
```
路径1: builtins.ts → 扫 src/sentinel/adapters/*-sentinel.ts（5 个旧版哨兵，全部 @deprecated）
路径2: file-driven-loaders.ts → 扫 extensions/sentinels/*/manifest.json（主力）
路径3: runner.ts → 运行时再次 loadSentinels()（冗余）
⇒ 同一哨兵可能被注册两次；「三重注册入口需要统一为文件驱动模式」
```
**今日实测**：`src/sentinel/adapters/` **5 个文件仍在**（`cash-flow` / `cpc` / `goal-alignment` / `integration-health` / `helpers`）；`registerBuiltinSentinels()` 返回 `undefined`（**未定因**，探针不足）。

**裁决**：
1. **唯一入口 = 文件驱动**（`extensions/sentinels/*/manifest.json`）。「一切皆插件」的物理体现就是**只加目录、不改代码**。
2. **`src/sentinel/adapters/` 5 个 @deprecated 哨兵 → 裁剪**（不"救活"）。依据：旧文档标注全 @deprecated + 院方禁令 4「**不要顺手修注册 bug 就宣布'第二套哨兵活了'**（修 1 行能让键名对上 3 个）」。
3. **去掉路径 3（runner 运行时重复加载）**，改为复用已注册表。
4. **验收**：`§七 A5 — 只加一个目录、不改一行代码 → 跑通十环`。

## 四、**计算结果存储**（院方设计，本件采纳；创始人裁定 A）

> **⚠️ 缺口定性**：旧权威三件（哨兵体系 / 数据层 L5 / 进化体系）**零命中"计算结果/指标值/时序"** ⇒ **证实"从未设计过计算结果的存储"**。院方实测同结论：「compute 输出 —— **无表、无写入，产出即弃**」「哨兵 finding —— `src/store/` 零写入点」。

### 4.1 时序表 `measurements`（append-only）

```sql
CREATE TABLE measurements (
  entity_id    TEXT NOT NULL,   -- 谁：org / 客户 / 业务单元
  metric_id    TEXT NOT NULL,   -- 什么指标：runway_months / gross_margin …
  value        REAL NOT NULL,   -- 值（单位由 metric_id 定义承载）
  computed_at  TEXT NOT NULL,   -- **算出来的时刻**（不是写入时刻）
  run_id       TEXT NOT NULL,   -- 哪一次运行算出来的
  source       TEXT NOT NULL,   -- erp / manual / sentinel:<id> / compute:<fn>
  input_digest TEXT NOT NULL,   -- 输入快照摘要
  def_version  TEXT NOT NULL    -- 指标定义/公式版本
);
CREATE INDEX idx_measurements_entity_metric_time ON measurements(entity_id, metric_id, computed_at);
```
**四条纪律（缺一不成立）**：
| 纪律 | 防什么 |
|---|---|
| ① **只追加不修改**（禁 UPDATE/DELETE；修正走新行+版本） | 防"事后把数改对"——**可改的时序不是时序** |
| ② **必须带 `run_id`** | 防"这个数哪来的"说不清（异常值不可重放/归因） |
| ③ **必须带 `input_digest`** | 防"两个不可比的数被拿来比"（同公式不同输入 ⇒ 差值无意义） |
| ④ **`def_version` 必填** | 防"公式一改，历史序列断层"（否则跨版本趋势 = 两种算法混一条线） |

**反例（不得进本表）**：原始事件流（属 `session_events`）｜诊断结论文本（属报告/台账）。
**未验证前提**：45 哨兵 × 频率 × N 客户的规模与保留策略（院方反例③，**必须实测**）。

### 4.2 「基线」一词的裁定（创始人 2026-09-25：**基线 = 指标值**）

| 概念 | 载体 | 修订 |
|---|---|---|
| **指标基线/对比** | **`measurements`**（本件新建） | **"基线"一词的唯一指代** |
| 告警计数统计 | `sentinel_baselines`（现值：`finding_count/critical_count/warning_count`） | **改名 `sentinel_alert_stats`**（一词一义） |

**⚠️ 独立缺陷（实测，无论改名与否都要修）**：`src/agent/post-diagnosis-processor.ts:272` 调 `record('org-baseline-' + teamId, [])`（**传空数组**）⇒ **每次诊断都写一条 `finding_count=0` 的伪基线** ⇒ **该表数据已被零值污染**，即使只做计数对比也不可信。

## 五、正向信号（`excellence` 阈值）——**恢复这条被搁置的设计**

**旧权威 §二点五**（明标"这不是代码现状，是产品设计层面的待修正项"）：
> 「哨兵目前只做一件事：检测指标是否低于阈值 → 触发告警。**这是"坏消息机器"**……产品三个类比（免疫系统／驻扎的麦肯锡／最强大脑）**都需要这个能力**」

**裁决：采纳并升为本版必做**，理由：它直接支撑产品定位（否则"最强大脑"不成立）。
**落地**：① `thresholds` 增 **`excellence`** ② `severity` 由 4 值扩为 5 值：`emergency|critical|warning|info|**positive**` ③ `SentinelCheckResult` 增 **`positiveFindings`**，路由到"亮点专家"（分析"为什么这么好"+复制建议）。
**首批 6 个**（旧文档指定）：`unit-economics`(LTV/CAC>5)｜`customer-demand-shift`(NDR>120%)｜`revenue-health`(增速>行业均值×2)｜`capital-efficiency`(ROIC−WACC>10%)｜`talent-density`(高绩效占比>80%)｜`routine-diffusion`(最佳实践采用率>90%)。

## 六、调度语义（**与"持续观测"定位冲突，需创始人裁**）

| 源 | 每月 | 每周 | 每日 | 每6h | 其他 |
|---|---|---|---|---|---|
| 旧权威（2026-07） | 42 | 9 | 3 | 2 | 4 |
| **今日实测（45 个）** | **34** | 5 | 2 | 2 | 2 |

**冲突**：产品定位是「**驻扎企业、持续观测、主动发现**」，而 **3/4 的哨兵每月只跑一次** ⇒ **异常发现延迟最长 30 天**。
**待裁（创始人）**：这是**刻意**（业务数据按月更新，跑更勤没意义）**还是缺陷**（应日级/事件级）？
**技术侧已具备的条件**：`src/cron/scheduler.ts` 支持 `triggerType='cron'|'event'|'hybrid'`（**hybrid = cron 安全网 + event 加速器**）⇒ 若裁定"要更快"，**不需要新造机制**。

## 七、本体—哨兵接口：**统一命名（历史矛盾原文）**

**旧权威 §四 原文**：
> 「`store.queryNodes('Person', {teamId})` 用**旧 SOG 枚举**类型名；`traversal.traverse([teamId], ['DEPLOYS','FUNDS'])` 用**新 JSON 边名** ⇒ **两套命名体系在同一个 aggregate 中共存**」
> 「**14 个哨兵使用的类型名（Goal/Product/Capability 等）不在旧 SOG 枚举中**」

**院方实测印证**：45 个注册哨兵中**仅 4 个声明 `dependsOn.nodeTypes`，且值都是 `Financial`** —— 而 **`Financial` 不在本体 29 类里**。

**裁决**：
1. **本体是唯一命名源**：`extensions/ontology/`（节点类 / 边类）为唯一事实源；哨兵的 `dependsOn.nodeTypes` **必须在该源中存在**，否则**判红**（可用现有 ontology 校验器）。
2. **未声明依赖的哨兵**必须**显式标 `none`**（不得留空 ⇒ 空 = 无法判定）。
3. **`queryNodes` 与 `traverse` 用同一套命名**；迁旧类型名（Person/Financial…）到本体类，或明确登记"历史别名→本体现名"映射表。
