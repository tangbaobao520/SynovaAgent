一、总体定位对比

维度OpenClawSynova-Agent
产品定位 通用 AI Agent 运行时框架 — "All your chats, one OpenClaw" 组织数字孪生诊断 + 持续增长导航系统 — Agent 不是 ChatBot
目标用户 个人开发者 / 团队 / 企业 — 通用对话 Agent FDE（前线部署工程师）+ 企业决策者 — 垂直领域诊断
架构模式 Gateway 单进程 + 文件系统 workspace + MCP 扩展 Express HTTP + MCP + 五层架构（L1-L5）+ 本体层
技术栈 Node.js + JSON-RPC 2.0 + WebSocket + SQLite TypeScript + Express + SQLite + better-sqlite3 + tsx
模型 多提供者（DeepSeek / OpenAI / Anthropic 等），插件式 多提供者（12 种，自动检测链），主 DeepSeek V4
成熟度 生产级 — 2026.6.6，npm 包，ClawHub 生态 13K+ Skills 开发中 — 核心能力就绪，少量违规待修，哨兵基线管理待建设
核心哲学 "Text > Brain" — 文件优先，配置即代码 "增长是目的，诊断是手段" — 五层架构解耦，理论驱动
两个系统定位差异显著：OpenClaw 是通用 Agent 运行时基础设施，Synova 是垂直领域的专业诊断 Agent 系统。但 OpenClaw 在 workspace 文件体系、渐进式技能加载、会话持久化设计上有大量值得借鉴的模式。

二、部署方式

2.1 整体对比

维度OpenClawSynova-Agent
启动入口 openclaw gateway run — CLI 启动网关进程 npm run dev → src/index.ts → Express HTTP 服务
进程模型 单 Node.js 进程，WebSocket Gateway 为中心（默认 18789） 单 Node.js 进程，Express HTTP 为中心（默认 3000）
配置方式 openclaw.json — JSON 配置文件，支持 CLI 命令修改 环境变量驱动，无中心配置文件
持久化 SQLite 全局状态 + 每个 Agent 独立 DB 文件 SQLite 统一数据库，SessionStore + GraphStore + EvidenceStore
服务化 支持 Scheduled Task 系统服务，开机自启 Docker Compose 容器化部署
热加载 POST /api/reload 支持配置和 Agent 热加载 不支持运行时热加载（需重启进程）
CLI 能力 ~60 个子命令，覆盖全部管理场景 CLI 仅用于终端对话模式，无管理命令
网络模式 loopback/lan/tailnet — 灵活绑定模式 Express 绑定，无专用网络配置层
🏆 OpenClaw 优势 — 值得学：
  • 配置即文件：openclaw.json 集中管理，CLI 命令直接修改，比环境变量更可审计
  • 热加载 API：Agent 部署后可调 /api/reload 生效，不重启进程
  • 服务化支持：Scheduled Task 安装，Windows 环境原生支持
  • CLI 体系：60+ 子命令覆盖完整管理面，降低了运维心智负担

三、Agent 运行时架构

维度OpenClawSynova-Agent
运行时核心 Gateway — WebSocket 消息中心，路由 + 会话 + 工具 + 事件分发 ConversationEngine — 对话引擎，内含 ToolLoopExecutor + DiagnosisLauncher + OntologySyncer
Agent 定义 文件系统 Workspace（SOUL.md / AGENTS.md / IDENTITY.md / TOOLS.md） Programmatic — SynovaAgent 类，构造函数注入 DB + EngineContext
消息流 Channel → Gateway → Agent Session → LLM → Tool Loop → Reply → Channel HTTP/MCP/CLI → ConversationEngine → Phase State Machine → Expert Dispatcher → Reply
LLM 调用 通过 openclaw.json 的 models 配置，支持 provider 插件 通过 providers/ 目录，自动检测链覆盖 12 种 provider
Harness 类型 内置 OpenClaw Harness + Codex Harness Runtime（外部适配） 自有 ConversationEngine + ToolLoopExecutor，纯自主实现
多会话 原生支持 — session 按 workspace:channel:userId 隔离 支持 — SessionStore 管理，但对话恢复机制待建设
状态序列化 每轮自动持久化到 JSONL 文件 ConversationEngine 的 serialize() / fromState() 可用于恢复

🏆 OpenClaw 优势 — 值得学：
  • Workspace 文件即 Agent： 创建新 Agent = 创建目录 + 写文件。比代码注册制更轻量
  • Gateway 中心化路由： 统一的消息入口，Channel/Session/Tool 解耦清晰
  • 多 Session 原生支持： 每个 Session 独立序列化到 JSONL，天然支持并行对话
  • 插件化的 Model Provider： 通过 plugins 注册模型提供者，比硬编码检测链更可扩展
🏆 Synova 优势 — 保留：
  • 五层架构严格解耦： L1-L5 强制分层 + pre-commit 物理阻断跨层调用
  • Expert 并行验证体系： 7+ 专家 Promise.allSettled 并行 + 交叉验证，架构远超 OpenClaw 的单 Agent
  • Sentinel 定时哨兵： 主动监测而非被动响应——这是 Agent 不是 ChatBot 的关键区别
  • Observability： AgentObserver + EventBus + HookRunner，可观测性设计更完整

🏆 OpenClaw 优势 — 值得学：

  • Phase 动态上下文： Phase 0 的维度覆盖追踪是垂直场景特有的优势
  • L0 全局降级策略注入： 所有系统提示中嵌入 degraded 模式，OpenClaw 无对应

维度OpenClawSynova-Agent

5.1 关键对比：Tool Profiles vs ToolGuardrails

功能OpenClaw Tool ProfilesSynova-Agent ToolGuardrails
按场景限权 ✅ 4 个预设 Profile（minimal/coding/messaging/full） ⚠️ HookRunner pre-exec 拦截 + DataAccessPolicy
死循环检测 ❌ 无内置 ✅ 5 次相同错误阻断 / 5 次相同结果阻断
并行控制 ❌ 无 ✅ ParallelGate — 读并行，写串行
数据安全 ✅ <untrusted_tool_result> 包裹 ⚠️ PIIScrubber + DataBoundary（但未在所有路径强制）
审计 ❌ 无 Tool 执行审计 ✅ EventBus onToolExecuted + HookRunner audit
工具可见性 ❌ 所有工具全暴露 ❌ 所有工具全暴露（无专家级隔离）
🏆 OpenClaw 优势 — 值得学：
  • Tool Profiles 按场景限权： 相比 Synova 的全量暴露，OpenClaw 按使用场景（编码 / 消息 / 最小）限权更实用
  • MCP 原生命令管理： openclaw mcp 命令查看/配置 MCP Server，比代码配置更易用
🏆 Synova 优势 — 保留：
  • ToolGuardrails 完整： 故障阻断 + 死循环检测 + 串行/并行分离 + pre/post hooks — 比 OpenClaw 精细得多
  • Expert 级别工具隔离： 各专家有独立的 DataAccessPolicy，限制可见范围
  • 各专家独立工具可见性： 理论设计（见 10.5 节），OpenClaw 无此能力

6.3 Synova 的 Sentinel 体系

Synova-Agent 的 Cron/Sentinel 体系有比 OpenClaw 更深的架构设计：

组件功能状态
CronSchedulersetTimeout + SQLite 驱动，5 字段 cron 解析✅ 已实现
SentinelRunner通用执行器：调用 compute() → 对比基线 → 超阈值发信号入池⚠️ 已实现（基线管理待建设）
25 个测量器7 维度 × 3-7 测量器，每个测量器一个 compute()✅ 24 个 compute() 实现
信号聚合引擎消费信号池 → 交叉关联 → 严重度升级 → 路由专家⚠️ 骨架就绪
信号→专家路由表预定义映射（现金流异常→财务专家）❌ 待建设
对比结论： OpenClaw 的 HEARTBEAT.md 模式——Agent 自主决定何时巡检——更灵活，适合通用场景。Synova 的 Cron + Sentinel 体系——系统强制定时巡检——更可靠，适合诊断场景。
二者不互斥，可以融合。

9.2 值得学习的 OpenClaw 记忆模式

📝 "Text > Brain"： Agent 被明确教导"如果想记住什么，写到文件里。心里记的笔记不会跨重启存活"。这不是技术约束，是产品层面的认知设计。
📝 Heartbeat 记忆维护： Agent 在空闲心跳时主动：读取近期 daily notes → 提炼到 MEMORY.md → 移除过时信息。这是记忆的自动"断舍离"。
📝 安全隔离规则明确： AGENTS.md 写明 "MEMORY.md 只在主会话加载 — 绝不在群聊/共享上下文中加载"。不是技术隔离，是 prompt 层面的安全策略。
🏆 对 Synova 的借鉴：
  1. 将 AgentMemoryStore 纳入 Agent 自主工具，让 Agent 可以主动管理记忆（OpenClaw 的 memory_search/memory_get）
  2. 引入记忆"断舍离"循环 — 定期由系统（而非 FDE）清理过期/低置信度记忆
  3. Expert 私有记忆的 visibility 控制（来自 Synova 13.3 节的设计，但尚未实施到 ToolRegistry）

13.5 关键发现：两个系统可以融合

一个重要的发现： OpenClaw 和 Synova-Agent 的定位不是竞争关系，而是互补关系。

OpenClaw 提供了成熟的通用 Agent 运行时基础设施：

  • Gateway 消息路由 + 多 Channel 接入 + 会话管理 + 文件系统 Agent 定义
  • 渐进式技能加载 + Tool Profiles + 上下文预算追踪
  • ClawHub 分发生态 + CLI 管理体系

Synova-Agent 提供了 OpenClaw 完全没有的深度诊断能力：

  • 7+ 专家并行 + 交叉验证 + 信号聚合引擎
  • Sentinel 定时哨兵 + 25 测量器 + 基线异常检测
  • 本体层（组织数字孪生）+ 证据置信度体系
  • Phase 状态机 + 8 维度覆盖追踪
战略建议： Synova-Agent 不应重写 OpenClaw 已有的基础设施能力（Gateway、CLI、热加载、上下文压缩）。
而是应把 OpenClaw 的成熟模式设计到 Synova 中，同时保持 Synova 独有的诊断方法论优势。
甚至可以考虑：Synova 作为 OpenClaw 的一个 Skill/MCP Server 运行？
这样 Synova 获得 OpenClaw 的 Channel 接入 + 会话管理 + CLI 管理，
OpenClaw 获得 Synova 的组织诊断 + 专家系统能力。

13.6 Synova 独有的核心壁垒（OpenClaw 无法复制的）

能力为什么 OpenClaw 做不到
7+ 专家并行交叉验证 OpenClaw 没有"团队"概念，Agent 是单体的。要复制这个能力需要重写多 Agent 协作层
Sentinel 定时监测 + 25 测量器 OpenClaw 的 HEARTBEAT.md 靠 Agent 自主，没有系统的异常检测 + 信号聚合
本体层（组织数字孪生） 14 节点类型 + 10 边类型的图模型是专门为组织诊断设计的，OpenClaw 无此抽象
八维初诊框架 垂直领域方法论积累，纯通用框架无法替代
FDE 生态 + 数据飞轮 人的网络 + 行业数据积累，技术无法替代
五层架构物理执法 pre-commit 38 项硬阻断，架构违规被物理阻断 — 这是工程文化，不是功能

13.7 总结

OpenClaw 是通用 Agent 基础设施领域的优秀产品。它的 workspace 文件体系、渐进式技能加载、上下文预算追踪、CLI 管理体系是 Synova 可以直接借鉴的设计模式。

Synova-Agent 在垂直诊断领域已建立了明确壁垒。 五层架构、7+ 专家系统、Sentinel 哨兵、本体层数字孪生——这些是 OpenClaw 不具备也无法轻易复制的核心能力。

建议的融合方向： Synova 吸收 OpenClaw 在通用 Agent 运行时上的最佳实践，但保持自己的诊断方法论优势。不必"追赶"OpenClaw 的通用能力——通用能力俯拾皆是，垂直诊断能力才是真正的护城河。
