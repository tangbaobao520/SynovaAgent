第一步：五问决策

在写一行代码之前，先回答五个问题。按顺序问，遇到 NO 就停，修好再往下。

Q1: Does it work? — 当前系统提示词能正常产出诊断吗？

→ PARTIAL. ConversationEngine 的 STABLE_LAYER 能用（180字），但太薄。ExpertRegistry 的 6 个 prompt 运行时能加载，但输出质量受限于共享模板。问题不在崩不崩溃，在能跑不代表跑得对。

结论：YES for runtime, NO for quality. 但Q1的"it works"指能否运行——能。继续。

Q2: Any blocked commits? — 有什么堵住了不能提交的？

→ NO. 当前没有 blocking commit gate。expert-registry.ts 的修改是独立文件，不阻塞其他模块。ConversationEngine 的 STABLE_LAYER 也是独立修改。

结论：NO。继续。

Q3: Critical bugs in existing prompts? — 现有 prompt 有没有会导致错误诊断的致命问题？

→ YES. 三个致命问题：

  1. 6个专家 prompt 80%相同 → 战略和营销共用一套模板 → 他们产出的分析实际上没有区分度 → 交叉验证失去意义
  2. 没有降级处理 → 如果 query_knowledge 查不到数据，专家静默返回空 → FDE 不知道"这个结论没有数据支撑"
  3. 没有"不可做的事" → 财务专家可能在没有足够数据时下结论 → 报告里出现虚假精度

结论：YES。必须先修再动别的。

第二步：Anthropic 排序

基于 Q3=YES（存在致命问题）、Q4 和 Q5 尚未检查，按 Anthropic 逻辑：先修最可能产生错误诊断的，再做体验优化。

最终优先级

🔴 P0 — 修致命问题（Q3）

专家 prompt 同质化、无降级处理、无行为边界。这是当前最可能产生错误诊断的根因。

🟡 P1 — 补用户可见缺口（Q4）

四层报告规范、品质门禁、L0全局身份、L1对话层。FDE 能感受到的差异。

🔵 P2 — 建基础设施（Q5）

SKILL.md 文件、工具三段式、PKB 格式化、MCP 接入。这些是"做了更好但不做也能用"的。
