总体评价：Synova 是一个工程基础扎实的项目。专家 Agent 系统（ReAct 循环 + 6 专家并行 + QualityFirewall）和工具/Skill 机制（JSON Schema 注册 + MCP 桥接 + 7 步安全审计）已达到生产级质量。可靠性基础设施（重试、熔断、超时守卫、降级信号传播）覆盖面广。主要问题集中在三层：(1) 五层架构存在跨层违规——L3 直接写 SQL、L1 路由直接导入 better-sqlite3；(2) HTTP SSE 诊断路径有单点故障（依赖外部 @synova/diagnosis-engine 包）；(3) 安全检查发现 .env 文件包含真实 API 密钥且部分路由缺少租户隔离。

HTTP SSE routes/diagnosis.ts EngineCoreVendorAdapter → 外部 DiagnosisOrchestrator ❌ 无 GraphBridge / 社区报告 / 实体解析 API 集成

4.4 缺失 / 桩 / 断链

  • [CRITICAL] 缺失：HTTP 诊断路径无后处理
    EngineCoreVendorAdapter.runConsultation() 返回后不调用 DiagnosisLauncher 的 GraphBridge/community reports/entity resolution。外部 API 用户得不到完整的诊断结果持久化。
  • [CRITICAL] 单点故障：@synova/diagnosis-engine
    整个诊断流程依赖 packages/diagnosis-engine 透传包 + packages/engine-core。如果包解析失败，POST /api/diagnosis/consult 直接抛异常。当前该包仅有 2 个源文件且全是 re-export。
  • [HIGH] 死代码：src/orchestrator/diagnosis-orchestrator.ts
    定义了完整的 DiagnosisOrchestrator<C,T> 但从未被生产代码使用。实际使用的是 @synova/diagnosis-engine 中的同名类。两个类存在但仅一个在用。
  • [HIGH] 死代码：SubAgentCoordinator.dispatch() 从未调用
    src/orchestrator/subagent-coordinator.ts:78 的 dispatch() 方法（并行运行 6 专家）在 HTTP 路径中从未被调用。专家调度必须在 @synova/diagnosis-engine 内部完成。
  • [MEDIUM] 脆弱的相对路径导入
    src/adapters/engine-core-adapter.ts:48-51 import ... from '../../packages/engine-core/src/pipeline/diagnosis/gap-recorder' — 绕过包管理器
    src/agent/builtin-tools.ts:11 import ... from '../../vendor/pandoc-skill/synova-tools' — 同上
  • [LOW] ZERO Stubs/TODOs/Mocks
    39+ 生产路径文件全部为真实实现。这是项目质量的重要正面信号。

代码质量高、零桩代码、所有函数真实实现。但双路径架构导致能力不对称，HTTP SSE 路径缺少后处理。外部包依赖是单点故障。
