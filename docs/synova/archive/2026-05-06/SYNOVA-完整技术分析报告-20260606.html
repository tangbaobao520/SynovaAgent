SynovaAgent 完整技术分析报告 2026-06-06

一句话定位

SynovaAgent 是一个内置 7 个专家（6 诊断 + 1 知识库）的 AI Agent 系统，通过 L5→L4→L3→L1 的数据到洞察管线，为企业提供持续的组织诊断和增长导航。对标 Microsoft GraphRAG 的知识图谱设计 + 六阶段诊断方法论 + 增长导航闭环。

1. 项目本质：从代码看它是什么

SynovaAgent 不是一个"接 LLM 的聊天应用"。从 src/ 下 170+ 个 TypeScript 文件的代码可以明确判断：

1.1 核心流程

  1. Phase 0：顾问式访谈 — IntentRouter 9 分支意图分类 + DimensionRegistry 6 维诊断地图 + 假设驱动追问。LLM 是访谈主持人，维度覆盖和进度由规则引擎控制。
  2. Phase 1-5：六阶段诊断流水线 — 数据采集 → 假设生成 → 根因分析 → 报告生成 → 交付。6 个专家 Agent 并发分析（战略/组织/财务/技术/营销/行动），每个专家有独立的 DataAccessPolicy 权限控制。
  3. 图谱蒸馏 — GraphBridge 6 个 upsert 方法将诊断结果自动写入本体图（对标 Microsoft GraphRAG），实现诊断→知识的自动转化。
  4. 增长导航（GNS v2.0） — 诊断后的持续追踪：目标监控 + 告警规则引擎 + 每日简报 + 提议→确认闭环。

3. 核心竞争力分析

3.1 咨询方法论的工程化编码

不是"让 AI 自由发挥做顾问"，而是把管理咨询的标准工作流写进了代码：

  • 意图路由 9 分支：LLM 分类 4 种诊断意图 + 5 种非诊断意图，每种对应不同对话策略
  • 维度注册表：追踪 6 个诊断维度的 uncovered → partial → covered 状态转换
  • 假设驱动追问：系统提示明确要求"形成假设时标注'我的判断是……'，并邀请反驳'但我可能判断错了'"
  • 每问必带"为什么"：提示中强制"追问时解释：我想了解___，因为这会影响___"

3.2 六类专家 + ReAct 自主权引擎

专家领域数据权限匿名化规则
🧠 strategy战略对齐、资源分配、使命目标6 维度人名→角色标签
👥 org团队结构、协作模式、信息流5 维度人名→角色标签
💰 finance成本、收入、ROI、预算、财务风险5 维度禁止字段: 人名/邮箱/电话
🔧 tech工具链、技术债务、自动化5 维度无限制
📣 marketing定位、差异化、竞争格局5 维度禁止: 薪资/成本数据
⚡ action优先级、可行性、紧急度5 维度无限制
📚 knowledge后台知识引擎（不参与诊断）检索/沉淀/验证/文档管理

每个专家有 ExpertAutonomyEngine 实现 ReAct 循环（Think → Query(权限检查) → Observe → 循环），智能终止条件：信息增益为零 / finalize 信号 / 最大 5 轮。

3.3 证据引擎 + 可溯源诊断

  • EvidenceCollector：Phase 0 自动采集用户每句话作为证据
  • CorroborationEngine：数值比较 + LLM-as-judge 语义交叉验证
  • ConfidenceScorer：来源分级（Human 0.8 > Document 0.7 > Connector 0.6 > Diagnosis 0.5 > LLM 0.3）+ 时间衰减（30 天半衰期）
  • QualityFirewall 四道检验：证据引用真实性 → 置信度阈值 → 跨专家矛盾检测 → 证据时效性
  • 诚实标记（NRA-03）：checkHonestyMark() 检查所有发现是否有 evidenceRefs

3.4 系统壁垒

核心竞争力不是单一技术，而是"管理咨询方法论 × 多专家协同推理 × 结构化知识图谱 × 证据溯源体系"四层叠加形成的系统壁垒。单独做其中任何一块都不构成壁垒，但整合成一个完整的 Agent 系统后，复用成本极高。

4. 三个项目的协调者机制对比

4.1 claw-code（Claude Code 转写）

路由方式：纯关键词 token 匹配

PortRuntime.route_prompt() 将用户输入 token 化，与所有命令/工具的 name + source_hint + responsibility 元数据做 token 匹配打分。显式命令（/开头）直接 score=100。无 LLM 参与。coordinator/ 子系统已被归档。

架构本质：单 Agent + 关键词路由器。没有多专家协调。

4.2 Hermes

路由方式：LLM 自主决定（function calling）

没有独立的"路由器"。LLM 看到所有工具定义，自己决定调用哪个工具。有 delegate_task 工具可 spawn 子任务，但"是否 delegate、delegate 给谁"仍是主 LLM 决定的。没有独立的调度器 Agent。

架构本质：单 Agent + LLM-as-router。没有多专家协调。

4.3 SynovaAgent

路由方式：分散在三处，各管各的

场景判定机制LLM？问题
Phase 0 访谈IntentRouter 9 分支是generateResponse 有硬编码 fallback
Phase 1-5 诊断SubAgentCoordinator 全调度否6 专家全跑，不筛选，浪费
知识问答qa-router 关键词匹配否不走专家系统
主动提议无—没有实现

4.4 关键发现

claw-code 和 Hermes 都是单 Agent 架构，不需要"谁来回答"的协调者——因为只有一个 Agent。

SynovaAgent 的 7 专家场景完全不同，需要一个统一的 ExpertRouter。

建议：ExpertRouter 三层路由

class ExpertRouter {
  route(input, phase, context) {
    // 第 1 层：Phase 上下文强约束
    if (phase === 0) return { experts: [], mode: 'none' };
    if (phase >= 2) return { experts: ALL, mode: 'all' };
    
    // 第 2 层：关键词快路径（借鉴 claw-code token matching）
    const fast = keywordMatch(input);
    if (fast.confidence > 0.8) return fast;
    
    // 第 3 层：LLM 分类（借鉴 Hermes LLM-as-router）
    return await llmClassify(input, context);
  }
}

5. 当前代码层面的关键风险

致命 engine-core 是单点黑盒依赖，路径脆弱

../server/vendor/@synova/engine-core/，772 个文件，位于 synova-agent 父目录。GraphStore、DiagnosisOrchestrator、FederalReporter 全部依赖它。路径结构在 CI/CD 中不一致则系统直接无法启动。

致命 ProposalManager 完全内存态，重启即丢失

GNS v2.0 核心：所有待处理提议、用户拒绝后的 24h 抑制状态、7 天超时……全是 new Map()。服务重启全部丢失。对比 ExpertStore 已经迁移到 SQLite，ProposalManager 还没修。

致命 6 个 GraphBridge upsert 只有 1 个在生产中接线

代码注释标注：KeyPersonRisk ✅ 生产调用，HONA/FinancialImpact/CapabilityGap/SevenPowers/CPC ⏳ 已测试，待诊断模块接入。数据管道不完整。

高风险 数据库加密密钥有硬编码 fallback

'synova-dev-secret' 作为最后 fallback 密钥。

高风险 AlertRuleEngine 冷却期内存态 + 单 SQLite 无多租户隔离

重启后告警风暴 + SQLite 在几十个组织并发时性能瓶颈。

中风险 LLM 调用成本不可控 + 测试覆盖不均衡 + 无用户认证

单次诊断 30-50 次 LLM 调用无预算上限。213 测试重度偏向架构审计。认证只有一个静态 token。

6. TUI 渲染 Bug 分析

Bug 1：叠词（"你你好好，，我我是是"）P0

根因：双写路径。

conversation-engine.ts 第 528-531 行的 display() 函数同时调用了：

const display = (token: string) => {
    onToken(token);                        // → chat.ts callback → app.chat.appendToken()  [第 1 次]
    this.viewAdapter?.appendToken(token);  // → TuiViewAdapter → app.chat.appendToken()   [第 2 次]
};

而 chat.ts 第 207 行已经把 TuiViewAdapter 注入到 conversation engine，第 493-499 行又传了 onToken 回调——两条路径最终都调用同一个 app.chat.appendToken()，每个字符被写入两遍。

修复：删除 display() 中的 this.viewAdapter?.appendToken(token)（因为 onToken 回调已做相同的事），删 1 行。

Bug 2：蓝色分隔线P1

根因：app.ts 用独立 blessed.box（width:1, content:'│', fg:'black'）手动画分隔线。neo-blessed 对单字符 box 的 fg 处理不可靠，'black' 在某些终端映射为蓝色。

修复：删除独立 divider box，改用 panel border 或父布局自然间隔。

Bug 3：格式乱、消息截断P1

根因：finishStreaming 中 contentLines.splice(agentIdx + 1) 索引可能偏移 + wrapText 500 次迭代上限 + 流式/终态渲染不一致。

8. 增长导航（GNS v2.0）架构分析

8.1 完整闭环

Phase 0: 顾问式访谈（意图路由 + 6维覆盖 + 假设驱动追问） ↓ Phase 1-5: 六阶段诊断（6专家并发ReAct + 证据交叉验证 + 质量防火墙） ↓ 图谱蒸馏: GraphBridge 自动写入 6 类诊断数据到本体图 ↓ 增长导航（GNS v2.0）: ├── 目标追踪（Goal 节点 + progress 更新） ├── 告警监控（AlertRuleEngine 自动触发 + 冷却期防骚扰） ├── 每日简报（BriefingGenerator 每天 19:00 推送到 IM） └── 人机协同（ProposalManager 提议→确认→执行→抑制闭环）

8.2 核心组件

组件代码位置核心逻辑
ProposalManager src/l2/proposal-manager.ts 提议生命周期: proposed→confirmed/rejected/opinion/expired。拒绝后 24h 抑制同类。7 天超时自动过期。有 getConfirmationRate() 追踪用户采纳率。
BriefingGenerator src/l3/briefing-generator.ts 每天 19:00 从 GraphStore 拉取 Goal/Risk/Process 节点，生成执行摘要+目标进度+活跃告警+遗留问题+推荐动作。

维度级别用途

9.4 安全设计亮点

  • 权限过滤不经过 LLM：getCurrentFilterClause() 在 L3 工具执行时通过 AsyncLocalStorage 获取，LLM 不知道被过滤了多少数据
  • 请求级上下文：L1 routes 设置 → L3 tools 读取，不通过 LLM 参数传递
  • 审计全覆盖：查询、写入、权限变更全部记录到 knowledge_audit 和 permission_audit_log
  • 领域安全策略：finance 强制 restricted 敏感度，不可降级；marketing 默认可共享
  • 团队知识隔离：add_pkb_entry 支持 global/team 归属，员工问答自动按团队过滤

9.5 当前缺口

  • qa-router.ts 的 buildAnswer 返回 prompt 字符串但未真正调用 LLM
  • TUI 完全没有知识库管理界面
  • 飞书 openId 和知识库 accessTeamId 的映射只是硬编码（roles: ['employee']），未动态获取

结论

SynovaAgent 的架构设计非常完整——五层架构、多专家系统、证据溯源、知识图谱、增长导航闭环——都体现了深厚的行业理解和工程纪律。

当前阶段的核心问题是"架构搭完了但业务链路还没完全闭合"：6 个 GraphBridge upsert 只接了 1 个，ProposalManager 还是内存态，TUI 有渲染 bug。建议优先完成：

  1. 修复 TUI 渲染 bug（叠词 + 分隔线 + 格式，0.5 天）
  2. ProposalManager 持久化（修致命 bug，2 天）
  3. Agent 驾驶舱布局重构（建立产品视觉基调，5 天）
  4. ExpertRouter 协调者（补完多 Agent 调度的核心缺陷，3 天）

以上 4 项合计 10.5 天，完成后系统的核心链路就能从"能跑"变成"完整可用"。
