新增模块只需要加一行

不需要写新的测试文件，不需要配新的 CI 步骤。在 WIRING_REGISTRY 数组末尾加一个 entry，接线测试自动验证。接线验证变成了纯数据驱动的配置。

四、WIRING_REGISTRY 设计详解

这是整个套件的灵魂。一张表替代了 25 条铁律中关于接线的所有人工检查。

4.1 接线的四个等级

状态含义CI 处理示例
critical 必须接线但当前零引用 ❌ 阻断 PR FederalReporter, createOrchestrationWiring, TemplateValidator
wired 已正确接线 ✅ 通过 EngineCoreVendorAdapter, ExpertDispatcher, EventStore
known-broken 已知未接线但有记录 ⚠️ 不阻断 GraphBridge 5/6, CorroborationEngine
optional 建设中或可选组件 ✅ 信息性 AgentObserver, ConnectorPipeline

4.2 接线测试的工作方式

// 02-wiring-audit.test.ts — 25 行核心逻辑
for (const entry of WIRING_REGISTRY) {
  if (entry.status === 'critical') {
    test(`${entry.moduleName} 接线`, () => {
      const refs = countReferences(entry.moduleName, entry.expectedEntries);
      expect(refs).toBeGreaterThan(0); // ❌ 如果零引用, 测试失败
    });
  }
}

// countReferences: 扫描入口文件, 统计模块名出现次数
function countReferences(name: string, entries: string[]): number {
  for (const entry of entries) {
    const content = fs.readFileSync(entry, 'utf-8');
    total += (content.match(new RegExp(name, 'g')) || []).length;
  }
  return total;
}

八、与现有测试体系的关系

❌ 不替代

本套件不替代现有 60 个测试文件、445 个测试用例。单元测试仍然是验证函数逻辑正确性的主要手段。

✅ 互补

本套件解决单元测试无法覆盖的 3 个维度：接线（是否被调用）、架构（是否在正确层级）、安全（是否静默降级）。

两者的关系：

现有测试 (445 个):  验证"做对了"
  ↓
@synova/test-kit:   验证"做了" + "做在了对的地方" + "没做错的事"

具体:
  现有测试 →  ConversationEngine.processMessage() 返回正确回复
  test-kit  →  ConversationEngine 被 CLI/TUI/Server 入口引用
               ConversationEngine 不直接 import L4
               ConversationEngine 的 catch 块不空吞
