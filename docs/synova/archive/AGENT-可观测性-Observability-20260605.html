Agent 可观测性技术报告

5 个 Agent 框架的深度研究 · 2026-06-05

核心结论：MCP 不能一统天下 + OpenClaw 已有官方可观测性插件

MCP 是请求-响应模式，Agent 调用 Server 的工具，Server 不能被动观察 Agent。完整的 Agent 监测需要两层架构：

  1. MCP 用于 Agent → Synova 的通信（Agent 查询诊断数据）
  2. 平台原生的观测机制用于 Synova → Agent 的观测（收集 Agent 活动）

一、各框架可观测性能力全景

框架观测机制被动/主动集成方式

- openclaw-observability：20 个钩子（LLM调用/工具调用/子Agent/会话/安全扫描），内置面板

二、MCP 协议的边界（重要）

MCP 能做什么 vs 不能做什么

能力MCP 可以？
Agent 调用 Synova 的工具（查询诊断数据）✅ 核心能力
Synova 主动告诉 Agent 信息（推送通知）✅ 通过 Notifications 机制（Server → Client 的单向推送）
Synova 被动观察 Agent 的全部行为❌ 不能。MCP 只有 Agent 调用 Server，Server 不能看到 Agent 在做什么
Agent 主动向 Synova 汇报活动✅ Agent 调用 report_activity 工具
批量获取 Agent 的历史活动❌ 不能。MCP 无历史数据查询

MCP 的正确使用方式

Agent ↔ MCP ↔ Synova
  │               │
  │  调用工具      │  查询诊断数据
  │ ─────────→   │
  │               │
  │  接收通知      │  推送异常预警
  │ ←─────────   │
  │               │
  │  主动汇报      │  调用 report_activity
  │ ─────────→   │（Agent 端实现，非 MCP 标准能力）

MCP 本身不能做"监测"。它是"通信协议"，不是"观测协议"。
Agent 的观测需要各平台的原生机制（插件/钩子/回调）。

三、OpenClaw 官方可观测性插件（关键发现）

这是最大的发现——OpenClaw 官方已经做了我们需要的东西

插件 1：openclaw-observability

安装：openclaw plugins install openclaw-observability
采集：20 个钩子（LLM 调用/工具调用/Agent 生命周期/会话/上下文压缩/Gateway 事件）
存储：嵌入式 DuckDB（零配置）或 MySQL/RDS
面板：内置 http://localhost:18789/plugins/observability
安全扫描：
  - L1 正则规则（15 条）：密钥泄露、危险命令、prompt 注入
  - L2 行为链检测（2 条）：读敏感文件后外传、工具返回注入后执行
脱敏：存储前自动遮罩 API Key、密码、Token
缓冲：可配置的批量大小和刷新间隔

插件 2：diagnostics-otel（OpenTelemetry）

内置 OpenClaw v26.2.19+，配置即用：
{
  "plugins": { "entries": { "diagnostics-otel": { "enabled": true } } },
  "diagnostics": {
    "enabled": true,
    "otel": {
      "endpoint": "https://your-otlp-endpoint",
      "protocol": "http/protobuf",
      "serviceName": "openclaw-gateway"
    }
  }
}
输出：Metrics + Traces + Logs via OTLP

对我们的意义：

  • OpenClaw 生态（含 QClaw/AtoClaw/EasyClaw 等封装品）如果继承了这些插件，我们就直接可用
  • 不需要自己开发观测机制——消费 OTLP 数据 或 读取 observability 插件的 DuckDB
  • 如果某家封装砍掉了这些插件，那是他们的兼容性问题

五、集成复杂度矩阵

框架基础活动上报完全被动观测被封杀风险推荐方式
OpenClaw（含官方插件）低 安装插件即可低 消费 OTLP/DuckDB🟢 无（官方插件）消费 OTLP 数据
OpenClaw（无插件/封闭版）中 需适配定制 API中 需看封闭程度🟡 看厂商逐个适配
Claude Code中 MCP report_activity高 仅日志事后分析🟢 无MCP + 日志轮询
Hermes中 Plugin + HTTP中 Plugin 回调🟢 无Plugin
LangChain低 handler 一行代码低 被动采集全部🟢 无BaseCallbackHandler
CrewAI低 callback 一行代码中 有限事件🟢 无task_callback
AutoGen低 hook 注册低 事件监听🟢 无agent_event hook

六、开发指引

Phase 1（P1，下个迭代）：OpenClaw + LangChain

1. 实现 OTLP 数据消费端
   读取 OpenClaw diagnostics-otel 输出的 Metrics/Traces
   解析 Agent 活动 → 创建/更新 SOG 的 AGENT 节点

2. 实现 SynovaCallbackHandler（Python）
   from synova_telemetry import SynovaHandler
   chain = create_chain(callbacks=[SynovaHandler()])
   通过 HTTP 向 Synova 上报活动

3. SOG 写入 AGENT 节点
   节点类型已存在：SOGNodeType.AGENT
   边规则已存在：INTERACTS_WITH / BELONGS_TO / DEPENDS_ON / OWNS / PROVIDES / CONSUMES

Phase 2（P2）：Claude Code MCP + Hermes Plugin

4. MCP Server（复用工具的 MCP Server 能力）
   提供 report_activity 工具供 Agent 调用
   提供 query_diagnosis / get_org_health 供 Agent 查询

5. Hermes Plugin
   注册 conversation 回调，上报活动摘要到 Synova

6. 日志轮询器
   读取 Claude Code 和 Hermes 的日志文件
   解析工具调用模式 → 映射到 SOG

七、结论

  • MCP 不能一统天下——它是通信协议，不是观测协议。Agent 监测需要各平台的原生观测机制
  • OpenClaw 官方插件是我们最大的利好——openclaw-observability + diagnostics-otel 已经覆盖了 OpenClaw 生态的大部分需求
  • LangChain/CrewAI/AutoGen 等开发框架——通过 callback/handler 机制，一行代码即可接入
  • Claude Code 和 Hermes——MCP + 日志轮询，覆盖面有限但足以感知 Agent 存在和活跃度
  • 所有数据最终统一进入 SOG，6 个专家 Agent 用同一套 query_sog_graph 工具分析 Agent 团队和人类团队
