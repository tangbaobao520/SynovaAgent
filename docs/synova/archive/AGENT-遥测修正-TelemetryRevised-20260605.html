AI Agent 监测技术方案（修正版）

全部从外部观测，零代码注入，不被任何 Agent 框架封杀 · 2026-06-05

⚠️ 上一版方案的核心错误

我错误地假设了可以在 OpenClaw 内部注入 Hook 插件。这在实际中不可行：

  • QClaw / AtoClaw / EasyClaw 是商业产品，不可能允许第三方 inject hook
  • 即使对开源 OpenClaw，要求客户修改部署配置来适配我们的监测也是不可接受的
  • 上游 OpenClaw 项目如果认为我们的插件是"后门"，完全可以合入检测逻辑阻断

修正原则：一切从外部观测，不修改、不注入、不侵入目标系统。

一、可行方案：4 条外部观测通道

通道方式被封杀风险适用对象
1. 文件系统观测读取 Agent 的工作目录、配置文件、日志文件🟢 零风险OpenClaw / Claude Code / Hermes / 所有本地 Agent
2. 进程观测通过 OS 进程 API 监测 Agent 进程状态🟢 零风险所有本地 Agent
3. MCP 协议观测Synova 作为 MCP Server 注册到 Agent 的 MCP 配置中🟡 低风险（按用户的意愿配置）支持 MCP 的 Agent（Claude Code、OpenClaw 等）
4. API 代理观测Agent 的 LLM API 调用经过 Synova 代理 → 可观测调用模式🟡 中风险（需要客户配置代理地址）所有 LLM Agent

二、详细方案

2.1 文件系统观测（最通用、零风险）

适用于所有 Agent 类型

每种 Agent 在工作时会留下文件痕迹。Synova 作为同一台机器上的另一个进程，可以读取这些文件：

Agent 类型可读取的文件/目录可采集的信息
OpenClaw 生态~/.openclaw/agents/ 下每个 Agent 的目录Agent 名称、角色、所属团队、使用的工具列表、技能列表
（在 Novis 的 bridge/workspace-scanner.ts 已有扫描逻辑）
Claude Code~/.claude/cache/changelog.md
~/.claude/cache/ 下的 session 日志		对话轮次、工具调用记录、token 消耗、报错信息
Hermessession 日志文件（JSON 格式）
skills/ 目录（技能使用记录）		完整会话记录、工具调用链、技能使用统计
具体实现（Synova 侧）：

// 定时扫描已知 Agent 的工作目录

    ['openclaw', ['~/.openclaw/agents/']],
    ['claude-code', ['~/.claude/cache/']],
    ['hermes', ['~/.hermes/sessions/']],
  ]);

  async scan(): Promise<AgentDiscovery[]> {
    const agents: AgentDiscovery[] = [];

    // 扫描 OpenClaw 工作目录
    const openclawAgents = await this.scanOpenClaw();
    agents.push(...openclawAgents);

    // 扫描 Claude Code 缓存（检查是否有活跃进程）
    if (await this.isProcessRunning('claude')) {
      agents.push(await this.scanClaudeCode());
    }

    // 扫描 Hermes 日志
    if (await this.isProcessRunning('hermes')) {
      agents.push(await this.scanHermes());

2.2 进程观测

简单有效，不依赖任何 Agent 配置

// 通过 OS 进程 API 发现正在运行的 Agent
// 不需要任何 Agent 方的配合

class ProcessObserver {
  async discoverAgents(): Promise<DiscoveredAgent[]> {
    const processes = await this.listProcesses();
    const agents: DiscoveredAgent[] = [];

    for (const proc of processes) {
      // OpenClaw 进程特征
      if (proc.name.includes('openclaw') || proc.cmd.includes('openclaw')) {
        agents.push({ framework: 'openclaw', pid: proc.pid, ... });
      }
      // Claude Code 进程特征
      if (proc.name.includes('claude')) {
        agents.push({ framework: 'claude-code', pid: proc.pid, ... });
      }
      // Hermes 进程特征
      if (proc.name.includes('hermes')) {
        agents.push({ framework: 'hermes', pid: proc.pid, ... });
      }
      // 通用 Agent 进程特征
      if (this.isLikelyAgent(proc)) {
        agents.push({ framework: 'unknown', pid: proc.pid, ... });
      }
    }

    return agents;
  }

  // 监测进程级指标
  async getAgentMetrics(pid: number): Promise<AgentMetrics> {
    return {
      cpu: await this.getProcessCpu(pid),
      memory: await this.getProcessMemory(pid),
      uptime: await this.getProcessUptime(pid),
      threadCount: await this.getThreadCount(pid),
    };
  }
}

2.3 MCP 协议观测（最优雅、Agent 主动配我们）

如果客户主动配置，这是最好的方式

MCP（Model Context Protocol）是 Agent 获取外部能力的标准协议。支持 MCP 的 Agent（Claude Code、OpenClaw 等）可以通过配置文件注册 MCP Server。

// 客户在 Agent 的 MCP 配置中注册 Synova 作为数据源：
// 这不是"注入"，是 Agent 框架原生支持的扩展方式

// ~/.claude/settings.json 中的 MCP 配置
{
  "mcpServers": {
    "synova-observer": {
      "command": "npx",
      "args": ["@synova/mcp-observer"],
      "env": {
        "SYNOVA_ENDPOINT": "http://localhost:3000"
      }
    }
  }
}

// OpenClaw 的 skills/ 目录中安装 synova-observer skill
// 不需要修改 OpenClaw 核心代码

// Synova 作为 MCP Server 提供以下工具供 Agent 调用：
tools:
  - report_agent_activity:  // Agent 主动向其汇报行为（可选）
      description: "Agent 向 Synova 报告自己的活动摘要"
      parameters: { ... }

// Synova 作为 MCP Server 也提供资源供 Agent 读取：
resources:
  - synova://org-health      // 当前的诊断结果
  - synova://team/{id}/risk  // 特定团队的风险分析

关键：这不需要 Agent 框架的配合。 MCP 是开放协议，任何 Agent 框架只要支持 MCP，就可以配置这个 Server。没有任何封杀风险——因为这是 Agent 框架原生设计用来加载外部能力的方式。

2.4 API 代理观测（可选的深度观测）

如果客户愿意配置，可以采集到最详细的 Agent 行为数据

// 客户的 Agent 调用 LLM API 时，将 endpoint 指向 Synova 的代理端口
// Synova 记录调用模式后，转发到真正的 LLM API

Agent → Synova Proxy → LLM API (DeepSeek/OpenAI)
         │
         ├── 记录：模型、token 数、耗时、频率
         ├── 记录：工具调用模式（从请求中提取 tool_calls）
         └── 记录：错误率和重试模式

这可以采集到：
  - 每个 Agent 的 LLM 消耗（Token/成本）
  - 每个 Agent 的工具调用频率和模式
  - Agent 的"决策速度"（从输入到工具调用的延迟）
  - Agent 的故障模式（什么场景下频繁出错）

但这种方式需要客户主动修改 Agent 配置——适用性不如文件系统观测。

三、观测数据的融合与使用

4 条通道采集的数据 → AgentTelemetryCollector → SOG 写入 → 专家分析
         │
         ├── 文件系统发现 Agent → SOG createNode(AGENT)
         ├── 日志解析工具调用 → SOG createEdge(INTERACTS_WITH / DEPENDS_ON)
         ├── 进程监控指标 → SOG updateNode props(cpu, memory, uptime)
         └── MCP/API 数据 → SOG createEdge(CONSUMES → FINANCIAL)

然后：
  - 组织专家用 query_sog_graph 分析 Agent 团队协作模式 ← 和人类团队一样
  - 技术专家用 assess_automation_level 评估 Agent 效率 ← 复用现有工具
  - 执行专家用 track_outcome 追踪 Agent 任务完成率 ← 复用现有工具

四、与上一版方案的核心区别

维度上一版（错误）本版（正确）
对 OpenClaw 生态在 OpenClaw 内部注入 Hook 插件从外部读取 ~/.openclaw/agents/ 目录 + 进程监测
对 Claude CodeMCP 桥接 + 日志轮询✅ 相同（MCP 和日志都是外部观察）
被封杀风险高——任何版本升级都可能阻断🟢 零——不修改任何目标代码
客户配合度高——需要客户部署我们的插件🟢 零——开了 Synova 就能自动发现，MCP 是可选项
实现复杂度低——有现成的 Hook 接口中——需要解析多种文件格式
