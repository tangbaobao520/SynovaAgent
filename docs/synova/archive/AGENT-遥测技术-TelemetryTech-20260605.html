AI Agent 团队监测技术方案

覆盖 OpenClaw 生态 / Claude Code / Hermes / 主流 Agent 框架 · 2026-06-05

核心思路：不依赖 Agent 框架主动上报，由 Synova 通过 Hook/Log/API 三通道采集

不能假设 Agent 框架会主动配合我们。需要一套被动采集 + 主动发现的监测架构：

  1. 主动发现：扫描环境中正在运行的 Agent 进程和配置文件
  2. Hook 注入：对 OpenClaw 生态，通过插件系统注入监测钩子
  3. 日志采集：对不开放 Hook 的系统，通过解析日志文件采集
  4. API 桥接：对提供观测 API 的系统，通过 API 拉取数据

一、OpenClaw 生态（包括 QClaw / AtoClaw / EasyClaw 等封装品）

最佳覆盖——因为 OpenClaw 有完善的 Hook 系统

OpenClaw 的 synova-plugin/hooks/ 提供了 5 个可注入的钩子点。这些国内厂商封装的版本（QClaw、AtoClaw、EasyClaw）都基于 OpenClaw 内核，hook 系统应该兼容。

钩子位置可采集的数据当前状态
agent_turn_preparesynova-plugin/hooks/agent-turn-prepare.tsAgent 接收到的用户输入、当前会话摘要✅ 已存在
before_tool_callsynova-plugin/hooks/before-tool-call.tsAgent 调用了什么工具、参数是什么、目标是什么✅ 已存在（含 MUTATING_TOOLS / CRITICAL_TOOLS 分类）
subagent_spawningsynova-plugin/hooks/subagent-spawning.tsAgent 创建了子 Agent、子 Agent 的角色和任务✅ 已存在（含团队上下文注入）
agent_endsynova-plugin/hooks/agent-end.tsAgent 的输出结果、任务耗时、使用 token 数✅ 已存在

植入方案：Synova Observer Plugin

// 写一个 synova-plugin 包，注入到 OpenClaw 实例中
// 不修改 OpenClaw 核心代码，通过插件机制接入

synova-observer-plugin/
├── index.ts                    // 注册所有钩子
├── hooks/
│   ├── agent-discovery.ts      // 发现新 Agent → emit OntologyEvent: node_created
│   ├── tool-call-observer.ts   // 采集工具调用 → emit OntologyEvent: edge_created
│   ├── communication-observer.ts // 采集 Agent 间通信 → emit OntologyEvent: edge_created
│   └── subagent-observer.ts    // 采集子 Agent 创建 → emit OntologyEvent: node_created
├── collector.ts                // 将采集的事件批量写入 Synova L5 EventBus
└── synova-client.ts            // 与 Synova Agent HTTP API 通信

采集的数据流：
OpenClaw Hook → Observer Plugin → Synova HTTP API → L5 EventBus → SOG GraphStore
                                                                  │
                                                   AGENT 节点写入 SOG 本体
                                                   Agent 消息映射为 INTERACTS_WITH 边
                                                   工具调用链映射为 DEPENDS_ON 边
                                                   任务委派映射为 BELONGS_TO 边

可采集的指标

维度指标采集方式
Agent 基础信息Agent ID、角色、模型、Provider、创建时间、所属团队agent_turn_prepare + 配置文件扫描
工具调用工具名、调用频率、成功率、平均耗时、参数分布before_tool_call + after_tool_call
Agent 通信消息收发频率、通信模式（委派/广播/协商）、响应时间harness/cross-team-router.ts 的审计日志
子 Agent创建数量、执行时长、成功/失败率subagent_spawning + agent_end
资源消耗Token 消耗、API 调用次数、执行时间agent_end 的 token 统计
协作网络Agent-Agent、Agent-人 之间的交互图综合所有数据，映射为 SOG 图

二、Claude Code

Claude Code 不开放 Hook 系统，但可采集日志和子进程

Claude Code 是本地运行的 CLI 工具，没有插件机制。但有 3 条通道可以采集：

通道方案可采集的数据
1. 日志文件读取 ~/.claude/cache/changelog.md 和 session 日志对话轮次、工具调用记录、报错信息
2. 子进程监控监控 Claude Code 的 child_process.spawn() 调用执行的命令、文件操作、API 请求
3. MCP 桥接Claude Code 支持 MCP 服务器，Synova 可作为 MCP server 注册通过 MCP 协议上报工具调用信息

推荐方案：MCP 桥接 + 日志轮询

1. Synova 作为 MCP Server 注册到 Claude Code 的 ~/.claude/settings.json 中
   当 Claude Code 调用 Synova 的 MCP 工具时，我们能感知到"这个 Agent 在工作"

2. 定期扫描 Claude Code 的 session 日志目录
   解析日志中的工具调用模式 → 映射为 SOG 的 TOOL 节点和 DEPENDS_ON 边

3. 通过 Claude Code 的进程信息识别运行状态
   ps aux | grep claude → 是否正在运行、运行了多久

三、Hermes

Hermes 有完善的 Background Review 架构，可以复用

Hermes 的 background_review.py 本身就是一种"自我监测"——回合后启动分支 Agent 审查对话。这个审查机制可以被 Synova 借用。

Hermes 组件监测价值
agent/conversation_loop.py 的回合日志每轮对话的 token 消耗、工具调用、耗时
agent/tool_executor.py 的调度记录工具并行度、失败率、调用链
agent/memory_manager.py 的记忆刷新Agent 记住了什么、遗忘了什么
agent/trajectory.py 的轨迹记录完整的决策路径

推荐方案：日志解析插件

Hermes 的日志是结构化 JSON（通过 hermes_logging.py），可以直接解析：
1. 让 Synova 读取 Hermes 的日志目录
2. 解析 session 文件中的 tool_call 和 tool_result 记录
3. 提取 Agent 行为模式 → 映射为 SOG 的 AGENT 节点和 INTERACTS_WITH 边

Hermes 的特色数据是"技能使用模式"——Agent 创建了什么技能、技能使用频率和成功率。
这直接映射到 SOG 的 SKILL 节点（如果未来扩展）或 CAPABILITY 节点。

推荐方案：统一 Agent Telemetry Collector

五、SOG 对 Agent 团队的表达

当 Agent 数据采集进来后，SOG 可以表达以下场景：

SOG 中的 Agent 团队表达：

AGENT(Claude Code)                                          ← Agent 节点
  ├── BELONGS_TO → TEAM(Engineering)                        ← 属于哪个团队
  ├── DEPENDS_ON → TOOL(GitHub CLI)                          ← 依赖什么工具
  ├── INTERACTS_WITH → AGENT(Hermes) [via MCP]              ← 和哪个 Agent 通信
  ├── INTERACTS_WITH → PERSON(张三) [via code review]        ← 和哪个人类协作
  ├── PROVIDES → CAPABILITY(Code Review)                     ← 提供什么能力
  └── CONSUMES → FINANCIAL(API Cost)                        ← 消耗什么资源

AGENT(Hermes)
  ├── BELONGS_TO → TEAM(Platform)
  ├── DEPENDS_ON → TOOL(Web Search)
  ├── DEPENDS_ON → AGENT(Claude Code) [sub-agent]            ← 子 Agent 关系
  └── OWNS → PROCESS(Onboarding)                            ← 拥有什么流程

当这些数据在 SOG 中建立后，现有的 6 个专家 Agent 可以用同一个
query_sog_graph 工具分析 Agent 团队——就像分析人类团队一样。

六、总结：各生态监测方案对比

生态推荐接入方式可采集程度实现难度优先级
OpenClaw 生态
OpenClaw / QClaw / AtoClaw / EasyClaw		Hook 插件注入🟢 完整（5 个钩子点）低（已有 hook 系统）P1
Claude CodeMCP 桥接 + 日志轮询🟡 中等（仅外部观测）中P2
Hermes结构化日志解析🟡 中等（日志丰富但无 Hook）中P2
LangChain/CrewAI/AutoGen/OpenAI SDKTelemetry SDK 插入🟢 完整（回调机制）中P2

建议执行顺序：

  1. P1 先做 OpenClaw 生态的 Hook 插件——这是最直接、覆盖最广的，而且我们已经有 Novis 的 OpenClaw 实例可以测试
  2. P2 然后做 Claude Code MCP 桥接——目前使用量最大的独立 Agent 工具
  3. P2 再做 统一 Telemetry SDK——覆盖其他 Agent 框架
  4. P3 最后做 Hermes 日志解析
