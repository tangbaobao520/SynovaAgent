⚡ 核心结论：基础设施已补齐 60%，但 3 个关键工具仍未实现

相对文档撰写时，编码 AI 已完成：工具并行执行 ✅ / 文件安全门禁 ✅ / 工具循环保护 ✅ / 工具操作分类 ✅ / 子进程隔离 ✅。但最关键的 query_sog_graph（替代硬编码 QueryAPI）和 search_web（行业搜索）仍未实现。专家 Agent 仍然只能通过 4 个硬编码方法查图。

二、核心差距：专家能做的事 vs 需要做的事

2.1 专家应该能做什么

专家需要的能力当前有吗？
战略专家查行业数据、分析竞争格局、评估市场定位、趋势分析❌ 4 个工具全返回 "interview_required"
组织专家查团队结构、协作网络、汇报链、识别信息孤岛⚠️ 能查图，但数据来自哪儿？飞书连接器返回空数组
财务专家分析成本结构、ROI、预算分配、财务风险❌ 3 个工具全部 interview_required
技术专家分析技术栈、代码健康度、自动化水平、技术债务⚠️ 能查到图里的 TOOL 节点，但 GitHub 连接器还没接
市场专家竞品分析、渠道效率、获客成本、市场定位❌ 返回硬编码 mock 数据
执行专家行动项优先级、进度追踪、效果验证❌ 3 个工具全是文本分析，无真实数据源

2.2 当前专家 Agent 的 ReAct 循环做了什么

专家 ReAct 循环（当前）：
  Think → "我需要查一下跨部门协作"
  Act → executeQuery('findDiagnosticPaths') → 参数硬编码为 ('Risk', 'Person')
  Observe → 得到结果
  Think → "让我看看子图"
  Act → executeQuery('summarizeSubgraph') → 参数硬编码为 ('root', 3)
  ...
  5 轮后 → finalize → 输出一段文本假设

问题：专家不能自主选择查什么、不能查不在硬编码列表里的东西、不能对比两个团队、
      不能查趋势、不能看文档、不能做计算。

│   ├── browser_tool.py          ← 浏览器自动化

│   ├── code_execution_tool.py   ← 代码执行沙箱

│   └── ...

每个工具：
  - 独立的 .py 文件
  - 有明确的 name / description / input_schema
  - 通过 ToolRegistry 注册（和我们的 ToolRegistry 同一个模式）
  - 有安全门禁（哪些工具能并行、哪些需要审批、哪些有副作用）

4.2 最紧急的 3 个工具（P0，本月必须做）

工具 1：query_sog_graph — 替代当前硬编码的 QueryAPI

名称: query_sog_graph
描述: 查询组织本体图，支持按节点类型/属性/关系过滤
参数:
  nodeType?: string    // Person/Team/Risk/Goal/...
  filters?: object     // 属性过滤
  edgeType?: string    // BELONGS_TO/INTERACTS_WITH/...
  maxDepth?: number    // 遍历深度
  aggregator?: string  // count/sum/avg 聚合
返回值: { nodes: [...], edges: [...], summary: "..." }

这个工具替换当前 executeQuery() 中的 4 个硬编码方法。
让专家能自由查询 SOG 图。

工具 2：search_web — 行业信息搜索

名称: search_web
描述: 搜索行业信息、竞品数据、市场基准
参数:
  query: string        // 搜索关键词
  maxResults?: number  // 结果数

战略专家用它查"研发团队平均规模"，财务专家用它查"行业利润率基准"。

工具 3：read_document — 读取已上传的文档

名称: read_document
描述: 读取用户上传的组织文档内容
参数:
  docId: string        // 文档 ID
  maxLength?: number   // 最大读取长度

组织专家用它看组织架构 PDF，财务专家看财务报表。

五、根本问题：数据没进来，工具再强也没用

提醒

工具能力升级的前提是数据管线已接通。如果你的飞书连接器还返回空数组、SOG 图里没有真实数据、知识摄取还没接，给专家再多的工具也只是让他们对着空数据库做分析。

执行顺序应该是：

第一步：飞书连接器通了 → SOG 有真实数据
第二步：给专家 query_sog_graph 工具 → 专家能查真实数据
第三步：给专家 search_web + read_document → 专家能查外部信息
第四步：更多高级工具

六、与 Claude Code 的对比

维度Claude CodeSynova 专家
工具调用方式LLM 自主选择工具 + 参数硬编码 switch-case，4 种固定调用
工具参数完全动态，LLM 生成完全固定，代码硬编码
工具搜索LLM 可浏览所有可用工具的描述专家只知道 4 个函数名
循环控制内置循环检测 + 护栏✅ ToolGuardrails 已实现
结果处理自动截断 + 持久化 + 安全检查原始 JSON 直通
并行能力Agent 工具可独立并行✅ runAllExperts() 并行执行
权限控制permission allowlistDataAccessPolicy 字符串匹配

结论：我们的专家 Agent 的工具系统需要一次架构升级——从"硬编码 4 个查询"到"通过 ToolRegistry 注册动态工具集"，然后专家通过标准化的工具调用来完成分析工作。这和 Hermes 的模式一致，复用已有的 ToolRegistry 基础设施即可。
