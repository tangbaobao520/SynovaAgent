⚠️ 核心结论：严重架构断层 — "两层编排系统"并存但互相隔离

L2 层存在两套完整的编排系统：

  • 系统 A（生产中的）：ConversationEngine（568行）直接驱动对话循环、Phase 0、工具调用，是实际在运行的编排引擎
  • 系统 B（废弃的）：DiagnosisOrchestrator + PhaseStateMachine + ModuleRunner + SubAgentCoordinator（~600行合计）是一套完整的通用编排框架，但从未接入生产路径

更严重的是，ConversationEngine 引用 L4 函数时只导入了类型而非函数（generateCommunityReports、resolveEntitiesL3），运行到对应路径会直接崩溃。

2. 状态机正确性与韧性分析

2.1 生产中的状态流转

ConversationEngine 的状态是轻量的、内联的 Phase 0 → Phase 1-5 链，没有显式的状态机：

用户输入 │ ▼ IntentRouter.classify() │ ├── 非诊断意图 → 直接回复 │ └── 诊断意图 │ ▼ Phase 0: 结构化访谈 │ intentRouter + dimensionRegistry │ readyToAdvance? → 至少 3 轮 + 覆盖 ≥4 维度 │ ▼ Phase 1-5: DiagnosisLauncher.startDiagnosis() │ → engine-core DiagnosisOrchestrator (动态 import) │ → L4 GraphBridge (upsertFromKeyPersonRisk) │ → EvidenceManager (证据收集) │ ▼ syncToSOG() → .catch(() => {}) ← 静默吞异常！

2.2 异常场景分析

场景当前行为问题
LLM 调用超时抛异常 → 错误返回用户无重试、无降级
Phase 0 LLM 失败catch 块返回"分析异常"信息对话直接中断，用户得不到部分结果
Phase 1-5 诊断失败fire-and-forget catch用户诊断状态丢失，无通知
工具执行错误ToolLoopExecutor 返回错误对象给 LLMLLM 可能自己恢复，这是正确的
进程崩溃（SIGKILL）全部丢失无持久的诊断状态
并发诊断请求每个请求独立 ConversationEngine 实例无隔离问题，但资源开销大

2.3 状态机缺陷总结

  1. 无持久状态： ConversationEngine 是内存中的，进程重启后所有对话和诊断状态丢失
  2. 无显式状态枚举： PhaseStateMachine 有完整的 idle→running→paused→completed→aborted 状态机，但 ConversationEngine 根本不使用它
  3. Phase 0→1 过渡测试不足： readyToAdvance 的条件（round≥3, coveredCount≥4）没有考虑行业维度扩展后比例变化
  4. 中断处理缺失： 用户中断诊断时，没有清理正在进行 LLM 调用的 AbortController

4. Hook 系统性能与死锁风险

4.1 当前 Hook 系统实现

HookRunner（143行）实现了 4 类钩子：

  • PreToolUseHook：工具调用前执行（权限校验、输入修改）
  • PostToolUseHook：工具调用后执行（证据收集、审计）
  • PostToolUseFailureHook：工具调用失败后执行
  • ModifyToolInput：修改工具输入（管道模式）

4.2 性能评估

场景当前实现风险
大量 Hook 注册（10+）简单 for 循环执行无：JS 同步循环没有性能问题
Hook 超时阻塞无超时机制中：如果某个 hook 是异步的（如网络请求），会阻塞整个工具调用链
Hook 异常catch 后继续执行后续 hook✅ 正确的隔离设计
Hook 顺序注册顺序⚠️ 未定义严格顺序契约，可能产生意外交互

4.3 流式路径的 Hook 缺失（关键 Bug）

streamWithToolLoop() 完全跳过了 hookRunner 和 eventBus： 
// tool-loop-executor.ts 中
async callLLMWithTools(messages) {  // ✅ 使用 hooks
  hookRunner.runPreToolUse(input);
  // ...执行工具...
  hookRunner.runPostToolUse(result);
}

async streamWithToolLoop(messages) { // ❌ 绕过 hooks
  const { provider, messages, toolRegistry } = this.ctx;
  // 不引用 hookRunner 或 eventBus！
  const res = provider.stream(messages, cb, opts);
  // 流式处理工具调用时无权限检查/审计/降级信号
}

这意味着流式 API 调用路径没有任何权限检查、审计日志、降级信号传播。这是 P0 级别的安全缺陷：攻击者可以通过流式 API 绕过所有安全控制。

5. 会话压缩语义保真度

5.1 当前压缩算法

SessionManager.compact(threshold = 0.5):
  1. 估计当前 token 数
  2. 如果超过阈值的 50%，触发压缩
  3. 从最早的 message 开始删除，直到 token 数 < 50%
  4. 被删除的 "light_compress" 消息生成摘要
  5. 摘要作为 system message 保留

5.2 语义保真度评估

信号类型压缩后是否保留说明
用户信息（基本信息）⚠️ 部分压缩为摘要，具体细节丢失
诊断矛盾信号❌ 可能丢失矛盾存在于两轮对话之间，压缩只保留摘要而非矛盾对
置信度数值❌ 丢失数值在 summarization 中变为文字描述，无法做数学运算
证据引用❌ 丢失消息中包含的证据 ID 引用在压缩时没有被结构化保留
工具调用/结果对⚠️ 有保护boundary protection 防止拆散 tool_use/tool_result 对
时间戳❌ 丢失压缩后的消息失去了原始时间信息

5.3 推荐压缩策略

// 结构化压缩（保留关键信号）
interface CompressedSegment {
  kind: 'diagnostic_signal';
  signals: Array<{
    type: 'contradiction' | 'insight' | 'metric';
    content: string;
    confidence: number;
    timestamp: string;
    evidenceRefs: string[];
  }>;
}

interface StructuredCompressionInput {
  originalMessages: Message[];
  keepToolPairs: boolean;  // 保留工具调用对
  preserveSignals: boolean; // 提取关键信号而非普通摘要
}

// 输出：
// 1. 原始消息（保留最近的 N 轮）
// 2. 结构化信号摘要（取代纯文本摘要）
// 3. 工具调用对（保持完整的 tool_use→tool_result 关联）
