1.2 三大断层

断层 1：图存储未被诊断管线调用。6 个诊断模块（hona、cpc、key-person-risk、capability-spectrum、financial-impact、seven-powers）全部使用各自独立的数据访问模式（内存 Map、全局 getter、参数传递、关键词启发式），没有任何模块调用 GraphStore 的 createNode/createEdge/queryNodes/traverse。GraphStore 是一个"存在但无人使用的图书馆"。
断层 2：图构建依赖手动触发。当前唯一的图写入路径是 POST /api/ontology/ingest → 文件读取 → 实体提取 → SOG 映射。没有从诊断流程（Phase A 角色推导 → Phase B 基因组蒸馏 → 证据收集）自动构建本体的管线。每次诊断产出的结构化洞察未沉淀为可复用的本体节点和边。
断层 3：图查询未面向诊断场景优化。现有 GraphQuery 提供的是通用图算法（最短路径、度中心性、社区检测），但诊断场景需要的语义查询（如"找出所有与关键人才风险相关的路径"、"显示团队协作协议的薄弱环节"）需要跨维度遍历、子图摘要、异常模式识别——这些都没有封装成诊断专用的查询 API。

2.2 Palantir OAG (Ontology-Augmented Generation) — RAG 的企业级升级

Palantir 2024 年确立了 OAG 三大工具范式，这是对普通 RAG "检索文档片段"模式的根本性升级：

工具类型能力对 SynovaAgent 的启示
Data Tools LLM 通过 Ontology 检索实时业务对象（非文档片段），语义搜索（embedding + KNN）在 Object 空间进行 诊断 Agent 应查询 GraphStore 节点而非文本 chunk → GraphRAG 替代文本 RAG
Logic Tools LLM 调用预测模型、优化器、业务规则（如 Prophet 时间序列预测 14 天订单量） 诊断 Agent 应能调用 financial-impact.ts 预测模型、key-person-risk.ts 风险模型 → Tool-use 绑定诊断模块
Action Tools LLM 触发受控业务操作（创建采购订单、更新库存），含细粒度权限 + 完整审计血缘 诊断 Agent 应能触发 Auto-Action 执行（非仅建议）→ 受控 Write-back

2.3 关键启示：从"只读图谱"到"可执行本体"

核心差距：SynovaAgent 当前的本体是一个"只读知识图谱"（存储事实、查询关系），但 Palantir 的本体是一个"可编程数字孪生"（不仅能描述现状，还能执行操作、模拟未来、学习决策结果）。这是 L4 层升级的根本方向。

Palantir 模式的三个可迁移原则：

  1. 虚拟映射（Virtual Mapping）：Ontology Object 不存储数据副本，而是映射到底层数据源的实时视图。SynovaAgent 应让 GraphStore Node 成为诊断模块输出的"虚拟聚合视图"，而非冗余存储。
  2. Action 作为一等公民：Action 不是"附加功能"，而是与 Object/Link 同级别的本体原语。SynovaAgent 应将 Auto-Action 注册为 SOG Action 类型，纳入 Schema 治理。
  3. OAG 替代 RAG：LLM 不应从文档片段检索上下文，而应从本体图中检索结构化事实 + 关系 + 历史轨迹。这需要 GraphRAG 或等价机制。

1. GRAG: Graph Retrieval-Augmented Generation arxiv 2405.16506

Authors: Yuntong Hu, Zheng Zhang 等 (多个机构联合)
2024年5月发布

核心问题：传统 RAG 从向量数据库中检索文本片段，无法利用知识图谱中的结构化关系。现有 GraphRAG 系统在检索子图时面临效率瓶颈——在大图中检索相关子图是 NP-hard 问题。

GRAG 解决方案 — 分治子图检索：

  1. Divide 阶段：将大规模 KG 按社区结构（Leiden 算法）划分为多个重叠子图（overlapping subgraphs），每个子图独立索引
  2. Conquer 阶段：查询时并行检索 Top-K 相关子图（而非全图遍历），通过 embedding 相似度匹配
  3. Merge 阶段：将检索到的子图片段与 LLM 上下文窗口对齐，生成增强回答

4 种子图检索策略：

  • Entity-based：从查询中提取实体，检索包含这些实体的子图
  • Relation-based：识别查询中的关系类型，检索包含该关系模式的子图
  • Topic-based：将查询 embedding 与子图的主题摘要 embedding 做相似度匹配
  • Hybrid：上述三种策略的加权融合

对 SynovaAgent 的应用：当前 GraphSearchDatahub 的 searchAcrossLineage 使用 BFS + 简单文本 .includes()——这正是 GRAG 要替代的 naive 方案。应实现：Leiden 社区检测将诊断组织图分片 → 查询时并行检索相关社区子图 → 子图嵌入与查询语义匹配。

2. Graph-R1: Agentic GraphRAG via End-to-End RL arxiv 2507.21892

Authors: Haoran Luo, Haihong E 等 (北京邮电大学 + NTU + NUS)
2025年7月发布 | Code: github.com/LHRLAB/Graph-R1

核心创新：第一个将 DeepSeek-R1 的强化学习范式引入 GraphRAG 的工作。将图检索建模为多轮 Agent-环境交互（think → retrieve → rethink → generate loop）。

技术方案：

  • 轻量知识超图（Knowledge Hypergraph）：用超边连接多个实体（n-ary relations），比传统二元边更丰富
  • GRPO (Group Relative Policy Optimization)：统一的奖励机制，同时优化生成质量 + 检索相关性 + 结构可靠性
  • Agent-Environment Loop：Agent 先"思考"需要什么信息 → 从超图中检索 → 反思检索结果是否充分 → 决定继续检索还是生成最终答案

对 SynovaAgent 的应用：诊断编排器（DiagnosisOrchestrator）的 6 个 Phase 当前是线性执行。Graph-R1 的 Agent-Environment 循环提供了更好的范式：Phase 执行 → 从本体图检索相关事实 → 反思（是否需要更多证据？）→ 决定进入下一 Phase 还是回到证据收集。

3. GraphRAG-R1: Process-Constrained RL for GraphRAG arxiv 2507.23581

Authors: Chuanyue Yu, Kuo Zhao 等
WWW 2026 已录用

核心创新：针对多跳推理场景，提出过程约束的结果导向 RL。与 Graph-R1 互补——后者关注 Agent 框架，本文关注检索过程的质量控制。

关键技术：

  • PRA (Progressive Retrieval Attenuation)：鼓励"必要的检索"同时惩罚"浅层检索"——检索太浅则推理解不够深，检索太深则可能过度思考
  • CAF (Cost-Aware F1)：平衡模型性能与计算成本，防止 over-thinking
  • 三阶段训练：cold start → PRA reward → CAF reward，逐步引入约束
  • 混合图文检索：同时利用图结构 + 文本内容

对 SynovaAgent 的应用：PRA 机制可用于优化诊断 Agent 的"检索深度"——不同于关键人才风险可能只需 1-hop（直接关系），评估协作协议完备性（CPC）可能需要 3-hop 以上的多跳推理。CAF 的"成本感知"精神可借鉴：不同诊断模块的 LLM 调用次数应与其价值成正比。

4. DEG-RAG: Denoising KGs for RAG arxiv 2024/2025

Authors: Yilun Zheng, Dan Yang 等 (NTU + 南京大学 + Mila)
Code: github.com/157114/Denoise

核心发现 — "Less is More"：LLM 自动构建的知识图谱含有大量噪声（冗余实体、错误关系），删除约 40% 的实体和关系后，QA 性能反而提升。

DEG-RAG 两大技术：

  1. 实体解析（Entity Resolution）：
    • Blocking：语义聚类 / 实体类型分组 / 共享邻居结构 → 三种策略减少两两比较
    • Matching：TransE / DistMult / ComplEx / R-GCN / Qwen3-Embedding → 多种嵌入方法识别等价实体
    • Merging：合并到规范表示 → 简单合并优于添加同义边
  2. Triple Reflection：识别并移除错误/过时的三元组关系

关键发现：

  • 类型感知 Blocking 是最有效的策略
  • 传统 KG 嵌入（TransE等）在实体解析任务上不输于 LLM 嵌入
  • 邻居相似度有时优于自身特征相似度

对 SynovaAgent 的应用 — 极高优先级：当前 EntityRegistry L2 使用 Jaccard 模糊匹配——DEG-RAG 证明这不足以处理 KG 噪声。应实现：Blocking（SOG 类型分组天然提供）→ Embedding Matching（可用 sentence-transformers）→ Triple Reflection（定期扫描矛盾三元组）。删除噪声后诊断质量反而更高。

5. Microsoft GraphRAG: From Local to Global arxiv 2404.16130

Authors: Darren Edge, Ha Trinh, Jonathan Larson 等 (Microsoft Research)
2024年4月 | GitHub 20,000+ Stars | 工业级参考实现

核心架构：

  • 索引阶段：文本分块 → LLM 抽取实体+关系 → 实体消歧合并 → Leiden 层次社区检测（通常 4 层 C0-C3）→ 为每个社区预生成 LLM 摘要（Community Reports）
  • Local Search：提取查询实体 → 图遍历邻居 → 检索原始文本块 → 合成答案。适合精准事实查找
  • Global Search：混洗社区摘要 → 并行 Map-Reduce → LLM 打分(0-100) → 聚合 → 最终答案。适合跨文档主题合成
  • DRIFT Search（2024年10月）：融合 Global + Local，Primer(全局) + Follow-Up(局部) 两阶段，全面性胜 Local 78%，多样性胜 Local 81%

对 SynovaAgent 的应用 — 极高优先级：Microsoft GraphRAG 的社区摘要 + 两级搜索架构是诊断报告生成的最佳范本：

  • Global → 全貌诊断报告：用社区摘要生成"这个组织的五大结构性问题是什么？"——对应 FullDiagnosisReport 的 Executive Summary
  • Local → 模块级诊断：用局部图遍历生成"关键人才风险的根因是什么？"——对应各诊断模块的详细分析
  • Leiden 社区检测：自动发现组织的"隐形团队"——不按正式汇报线、而是按实际协作模式划分的群体

6. LLM + Enterprise KG: Sensigrafo Enrichment Frontiers in AI, 2024

Authors: Luca Mariotti, Veronica Guidetti 等 (Expert.AI + Università di Modena)
Open Access | DOI: 10.3389/frai.2024.1460065

工业实践核心：基于 Expert.AI 的商业 KG 产品 Sensigrafo（一个包含 350,000+ 概念、700,000+ 关系的大规模多语言知识图谱），探索 LLM 如何辅助 KG 丰富化。

关键方法：

  • Relation Extraction：用 adapter-based fine-tuning（非全参数微调）在 Sensigrafo 上做关系抽取
  • NER + Distant Supervision：利用已有 KG 三元组自动生成训练数据的弱标签
  • Human-in-the-Loop：LLM 生成候选三元组 → 领域专家审核 → 审核结果反哺模型（主动学习循环）
  • 隐私与碳足迹：在工业环境中优先使用中小模型（而非 GPT-4）以减少延迟、成本和碳排放

对 SynovaAgent 的应用：Sensigrafo 的"已有 KG → 弱标签训练 → LLM 增强 → 人工审核 → 反哺模型"闭环，直接适用于我们的诊断→本体自动化管线。关键启示：不需要 GPT-4 做 KG 构建，专业微调的小模型在领域 KG 任务上可能更优。

7. EKG Engineering Process (AAAI 2024 Spring Symposium)

Authors: Emanuele Laurenzi, Adrian Mathys, Andreas Martin (FHNW Switzerland)

6 步企业 KG 工程流程：(1) 需求分析 → (2) 本体设计 → (3) 数据源映射 → (4) LLM 辅助抽取 → (5) 质量验证 → (6) 部署与维护。在瑞士某大型企业（匿名化数据）上验证，设计科学方法论（文献综述 + 专家访谈）。

启示：这 6 步流程可作为我们 SOG 模板开发的标准化工程流程。

8. CSGAT: Contextual Semantics GAT for Entity Resolution (Nature Scientific Reports, 2025)

Authors: Xiaojun Li, Shuai Fan 等 | Code: github.com/xhtech2024/csgat

三层混合架构：Transformer 自注意力（token 级特征） → 属性级注意力（跨属性语义层次） → GAT 图注意力（残差向量）。在 Amazon-Google 和 BeerAdvo-RateBeer 数据集上显著超越基线。

启示：EntityRegistry L3 语义匹配可采用类似架构——用 Transformer 编码实体属性文本 → GAT 编码实体在图中的邻居结构 → 融合得分做实体链接。

9. GraphER — GDD meets GNN (arxiv 2410.04783)

Authors: Junwei Hu, Michael Bewong 等

GDD (Graph Differential Dependencies) + GNN 混合方案：4 步流水线——GDD 辅助表示学习 → LSH 分桶 → 候选剪枝 → GDD 确认匹配。在 17 个图数据集 + 7 个关系数据集上 vs 10 个 SOTA 方法，全面领先。

启示：GDD 是一种可解释的规则——"如果两个实体的属性/邻居满足某种差异模式，则它们匹配"。这比纯 Jaccard 匹配更适合企业场景，因为规则可审计、可解释。

10. 3K: Knowledge-Enriched Digital Twin Framework (ACM IoT 2024)

Authors: Erkan Karabulut, Paul Groth, Victoria Degeler (University of Amsterdam)

神经符号 DT 框架："3K" = Knowledge Representation + Knowledge Discovery + Knowledge-enriched Inference。在图谱上运行关联规则挖掘（ARM）+ 去噪自编码器处理高维传感器数据 → 语义关联规则 + 本体公理 → 可解释的异常检测与决策。

启示：3K 的"本体公理 + 数据挖掘规则 → 可解释推理"架构，直接适用于我们的 GraphMonitor——当前只做边缘权重监控，可以用 ARM 发现更复杂的异常模式。

11. iText2KG: Incremental KG Construction with LLMs (WISE 2024)

Authors: Yassir Lairgi, Ludovic Moncla 等

零样本增量式 KG 构建：4 模块架构——Document Distiller（提取关键信息） → Incremental Entity Extractor（增量实体抽取，避免重处理） → Incremental Relation Extractor（增量关系抽取） → Graph Integrator（冲突解决 + 合并）。

启示：增量式构建避免了每次新诊断都重建全图的成本，适合我们的"每次诊断只产出增量洞察"的模式。

4. 挑战1：本体图自动构建管线

当前状态：图构建完全依赖 POST /api/ontology/ingest 手动触发。诊断流程（6 个 Phase、6 个模块）产出的结构化洞察从未自动沉淀为本体节点。

4.1 方案：诊断→本体 自动蒸馏管线 (Pipeline → Graph Bridge)

核心思路：在诊断 Assembler (diagnosis-assembler.ts) 的每个模块计算完成后，自动将结构化输出写入 GraphStore。不是"运行完诊断再手动导入"，而是诊断即本体构建。

5. 挑战2：EntityRegistry 三级解析落地

当前状态：L1（8 条确定规则）✅、L2（Jaccard 模糊 + 内存队列）✅、L3（语义匹配）❌ 未实现。L2 的 review 队列在内存中，服务重启即丢失。

5.1 L3 语义匹配方案

参考 CSGAT 和 DEG-RAG 的论文方案，L3 不从头训练 GNN，而是采用轻量级嵌入匹配：

L3 语义匹配流程：
  实体A (name + type + props) + 邻居子图 (1-hop)
    │
    ├─ 文本嵌入：all-MiniLM-L6-v2 编码 [type + name + JSON.stringify(props)]
    ├─ 图结构嵌入：1-hop 邻居的类型分布向量 (14维，每个SOGNodeType计数)
    │
    └─ 融合得分 = 0.6 × cosine(文本嵌入) + 0.4 × cosine(邻居分布)
       如果得分 > 阈值(0.85) → 自动合并
       如果得分在 [0.65, 0.85] → 进入 L2 review 队列
       如果得分 < 0.65 → 不合并

5.1.1 L2 队列持久化

新增 API：GET/POST /api/ontology/entity-review — 前端审核界面读取/确认/拒绝合并建议

7. 挑战4：本体图质量保障与进化

7.1 DEG-RAG 风格质量保障

参考 DEG-RAG 的核心发现（删除 40% 噪声反而提升性能），建立持续质量保障机制：

7.1.1 三元组反思 (Triple Reflection)

定期扫描（每 24h 或每次诊断后）：
  [ ] 矛盾检测：同一对节点存在互斥的边（如既是 BELONGS_TO 又是 OWNS 反向？）
  [ ] 冗余检测：同一对节点存在多条相同类型的边 → 合并
  [ ] 孤立检测：没有任何边连接的节点 → 标记为候选删除
  [ ] 违反 Schema：边端点组合不在 EDGE_ENDPOINT_MAP 中 → 标记为异常
  [ ] 时间异常：valid_to < valid_from → 标记为数据错误

7.1.2 质量仪表盘

指标计算方式告警阈值
Schema 合规率有效边 / 总边数< 95% → 警告
孤立节点比例无边节点 / 总节点数> 10% → 警告
实体冗余度重复实体对 / 总实体对> 5% → 警告
矛盾三元组数互斥边长对数> 0 → 信息
图密度实际边数 / 可能边数< 0.01 或 > 0.5 → 警告

8.2 评估：SQLite vs Neo4j vs graphology

维度SQLite (当前)Neo4jgraphology (JS)
部署复杂度零依赖需独立服务npm install
图遍历应用层 BFS原生图引擎原生图算法
查询语言SQL（手动 JOIN）Cypher（图查询 DSL）JS API（编程式）
多跳查询性能O(n²) SQL JOINO(n) 索引邻接O(n) 邻接表
持久化原生原生仅内存
社区检测需自实现GDS 库内置 Louvain
运维成本零高零
结论：维持 SQLite + 应用层图算法。原因：(1) Neo4j 增加运维复杂度，违反铁律"简单优先"；(2) 企业诊断场景的图规模（<10K 节点，<50K 边）SQLite BFS 完全可处理；(3) 社区检测等高级算法可通过 graphology 作为计算库补充（读入内存→计算→结果写回SQLite），无需替换存储层。

9. 挑战6：性能与可扩展性

9.1 当前性能基准预估

操作数据规模预估耗时瓶颈
createNode单节点< 1msSQLite INSERT
BFS traversal (depth=3)1000 节点~10ms应用层 N+1 查询
shortestPath1000 节点, 5000 边~50msBFS 队列 + SQL 查询
社区检测1000 节点~200ms随机化模块度优化
全量诊断+图写入6 模块并行取决于 LLM 调用LLM 延迟 >> 图操作

9.2 优化策略

  1. 读缓存：GraphStore 查询结果缓存（LRU, TTL=60s），诊断报告渲染期间图不变化
  2. 批量写入：诊断完成后统一 flush 图变更（而非每个模块单独写入），减少 SQLite 事务开销
  3. 图算法外包：复杂图计算（Leiden、Betweenness Centrality）外包给 graphology → 内存计算 → 结果写回 SQLite
  4. 懒加载子图：前端拓扑视图按需加载（只取当前视口的 2-hop 子图），而非全图
  5. SurrealDB 评估推迟：当前规模不需要。当节点 >50K 或边 >200K 时再评估迁移
