附录 C：OpenClaw/Hermes 沙箱与连接器模式借鉴

基于 server/src/ 全部相关代码的深度审计 · 2026-06-04

⚡ 最重要的发现：OpenClaw 当前没有 OS 级沙箱

OpenClaw 的 Agent/技能隔离全部是文件系统和协议级别的——每个 Agent 有独立的目录（~/.openclaw/agents/{teamId}/{agentName}/），技能有 allowedTools 白名单，但没有子进程、容器或 VM 级别的隔离。OpenClaw 的 harness-orchestrator.ts 甚至注释承认 checkConcurrencyLimit 永远返回 true、auditCrossTeamOperation 是 no-op。

这意味着 Synova 提出的子进程隔离方案实际上比 OpenClaw 的当前工程状态更先进。OpenClaw 有价值的借鉴在于沙箱的权限模型设计和安全审计流程，而不是底层隔离技术。

🏗️ 架构边界约束（铁律 39）

以下所有建议必须严格遵守五层架构边界，每层只与相邻层通信：

L1 交互 → L2
L2 编排 → L1 + L3
L3 洞察 → L2 + L4
L4 本体 → L3 + L5
L5 存储 → L4

L5 连接器的沙箱策略、安全审计、工具拦截全部在 L5 内部完成。
L2 只需要调用 connector.executeTool()，不需要知道沙箱等级。
L3/L4 完全不知道 L5 的存在。

架构对照：OpenClaw vs Synova L5

OpenClaw 的职责划分与 Synova 完全不同——OpenClaw 是 Agent 运行时框架，Synova 是组织诊断引擎。但 Sandbox 的模式设计可以移植：

  CloudTrip 7-Step Static Audit                      →  (连接器代码安全扫描，L5 内部)

关键原则：所有沙箱逻辑都封装在 L5 内部，不向 L2/L3/L4 暴露任何沙箱细节。L2 的 ToolRegistry 只需要知道"执行 connnector 模式工具"时，调用 ConnectorRegistry.executeTool()。至于 executeTool 内部有没有做权限检查、有没有记录审计日志——L2 不需要知道。

一、OpenClaw 沙箱模型详解

1.1 三级沙箱等级

OpenClaw 在 protocol-engine/mode-presets.ts 和 types/template.ts 中定义了三级沙箱：

等级含义适用场景数据限制
full完全隔离未经审核的技能、来源不可信的连接器禁止访问 credentials/personal_data/internal_decision_logs
semi半隔离（默认）经过安全审计的技能、受信任的连接器限制敏感数据类别
none无隔离核心系统组件无限制

对 Synova L5 连接器的启发

// 在连接器注册时声明沙箱等级
interface ConnectorSandboxConfig {
  level: 'full' | 'semi' | 'none';
  restrictedDataCategories: Array<'credentials' | 'personal_data' | 'financial' | 'internal_decision_logs'>;
  allowedTools: string[];     // 该连接器可调用的工具白名单
  allowedEndpoints: string[]; // 该连接器可访问的外部端点白名单
}

// 默认值（semi 级别）
const DEFAULT_CONNECTOR_SANDBOX: ConnectorSandboxConfig = {
  level: 'semi',
  restrictedDataCategories: ['credentials', 'personal_data'],
  allowedTools: [],
  allowedEndpoints: [],
};

1.2 安全审计四门禁

OpenClaw 的 marketplace/skill-registry.ts 在安装任何技能前执行 4 道安全门禁：

门禁 1: 分数门禁 — securityReport.score >= 70
门禁 2: 来源门禁 — 不在 blocklist 中
门禁 3: 源等级门禁 — sourceTier !== 'speculative'
门禁 4: 能力匹配门禁 — tool capability 不超过声明范围

通过 4 门禁 → 正常安装
疑似恶意（score 70-84）→ sandboxLevel = 'full'
良性（score >= 85）→ sandboxLevel = 'semi'
明确恶意 → 拒绝安装

安全审计检查的具体模式（来自 services/skill-security-audit.ts）：

检查项严重等级检测内容
MCP 危险工具P0rm -rf, curl|sh, shell.exec, child_process.exec
远程下载+执行P0curl | bash, wget && sh, eval with fetch
凭据窃取P0cat ~/.aws, printenv AWS_, .env exfiltration via webhook
文件系统危险操作P1rm -rf /etc, ../../ 路径穿越
网络不安全P1rejectUnauthorized: false
Eval/FunctionP0eval(), new Function(), setTimeout(string)

1.3 工具调用拦截链（before_tool_call）

synova-plugin/hooks/before-tool-call.ts 实现了工具调用前的协议强制拦截：

// 变异操作分类
const MUTATING_TOOLS = new Set(['exec', 'write', 'web_search', 'bash', 'sessions_spawn', ...]);
const CRITICAL_TOOLS = new Set(['exec', 'bash', 'shell']);

// 按协作模式执行不同策略
switch (protocolConfig.mode) {
  case 'iron_captain':
    mutating tools → 需要指挥者审批（block / requireApproval with 30s timeout）
  case 'hub_spoke':
    critical tools from non-hub agents → 需要审批
  case 'consensus':
    critical tools → 需要多数同意
  case 'collaborative':
    无限制（默认）
}

二、连接器/工具注册模式

2.1 ToolDefinition 接口

// synova-plugin/types.ts — OpenClaw 的工具定义
interface ToolDefinition {
  name: string;              // 工具名（全局唯一）
  description: string;       // LLM 理解的用途描述
  inputSchema: Record<string, unknown>;  // JSON Schema
  execute(params: Record<string, unknown>, ctx: ToolContext): Promise<ToolResult>;
}

interface ToolContext {
  agentId: string;
  sessionId: string;
  teamId: string;
}

type ToolResult = { content: Array<{ type: string; text: string }> };

2.2 实际注册示例（synova 知识工具）

// synova-plugin/tools/register-knowledge-tools.ts
api.registerTool('synova_read_entity', {
  name: 'synova_read_entity',
  description: '读取指定 SOG 实体的属性',
  inputSchema: {
    type: 'object',
    properties: {
      entityId: { type: 'string', description: '实体 ID' },
      graph: { type: 'string', description: '图名称' },
    },
    required: ['entityId'],
  },
  execute: async (params, ctx) => {
    // 调用 synova-agent HTTP API
    const res = await fetch(`http://localhost:3000/api/ontology/graph/${params.graph}`);
    return { content: [{ type: 'text', text: await res.text() }] };
  },
});

2.3 Executor 注册模式（CronScheduler）

// services/cron-scheduler.ts — 按 kind 分派的执行器注册
const executors = new Map<CronJobKind, ExecutorFunction>();

function registerExecutor(kind: CronJobKind, executor: ExecutorFunction): void {
  executors.set(kind, executor);
}

async function executeJob(job: CronJob): Promise<void> {
  const executor = executors.get(job.kind);
  if (!executor) throw new Error(`未知任务类型: ${job.kind}`);
  await executor(job.params);
}

// 通过闭包将 connector 的 executeTool 映射到统一接口
registerExecutor('feishu_sync', async (params) => {
  await feishuConnector.syncMembers(params.orgId);
});

四、跨层数据流（确保边界清洁）

L2 ToolRegistry.execute(name, params)
  │
  ├─ executionMode === 'local'    → 直接执行 handler ✅ L2 内部
  │
  ├─ executionMode === 'connector' → ConnectorRegistry.executeTool(name, params)
  │                                    │
  │                                    ▼
  │                               ┌─ L5 边界 ──────────────────────────┐
  │                               │                                     │
  │                               │  ConnectorRegistry.executeTool()    │
  │                               │    ├─ 1. 检查 allowedTools ✅      │
  │                               │    ├─ 2. 检查 sandboxLevel ✅       │
  │                               │    ├─ 3. 检查 operationType ✅      │
  │                               │    ├─ 4. 审计日志记录 ✅            │
  │                               │    ├─ 5. spawn 子进程（如需要） ✅   │
  │                               │    └─ 6. 执行实际工具 ✅            │
  │                               │                                     │
  │                               └─────────────────────────────────────┘
  │
  └─ executionMode === 'http'     → fetch(endpoint) ✅ L2 内部

L2 只需要做一件事：把执行分派到对应的模式处理器。
L5 内部的沙箱逻辑对 L2 完全透明。L2 不需要 import 任何 L5 的类型。

五、模块化设计：L5 沙箱模块的包边界

@synova/connector-registry/     ← 独立 npm 包
├── types.ts                    ← SynovaConnector 接口（统一接口）
├── registry.ts                 ← ConnectorRegistry（含沙箱执行链）
├── sandbox.ts                  ← 沙箱策略（等级/分类/拦截）
├── audit.ts                    ← 审计日志扩展
└── index.ts                    ← 公开 API

公开 API（index.ts 导出）：
  SynovaConnector       ← 连接器接口
  ConnectorRegistry     ← 注册中心
  ConnectorSandboxLevel ← 沙箱等级枚举
  ConnectorAuditLog     ← 审计日志

不导出（内部实现）：
  executeTool() 内部的拦截链
  sandbox 策略细节
  子进程管理

最终建议

  1. 子进程隔离方案不变——OpenClaw 也没有 OS 级沙箱，子进程方案已经比 OpenClaw 当前状态更进了一步
  2. 采纳 OpenClaw 的沙箱等级模型——在 ConnectorConfig 中加入 sandboxLevel: 'full' | 'semi' | 'none'
  3. 采纳工具调用拦截链——在 ConnectorRegistry.executeTool() 前加入中间件检查
  4. 采纳安全审计四门禁——安装连接器前执行安全评分 + 4 道门禁
  5. 扩展 PIIScrubber + DataBoundary——增加 restrictedDataCategories 机制
