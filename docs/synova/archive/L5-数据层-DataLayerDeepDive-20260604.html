2. 连接器架构深度分析

2.1 当前架构的问题

当前 DataConnector 接口（src/connectors/types.ts）定义如下：

interface DataConnector {
  readonly name: string;
  readonly platform: string;
  healthCheck(): Promise<{ healthy: boolean; error?: string }>;
  fetchMessages(orgId, since, until?): Promise<ConnectorMessage[]>;
  fetchMembers(orgId): Promise<ConnectorMember[]>;
  fetchEvents(orgId, since, until?): Promise<ConnectorEvent[]>;
  mapToOntology(messages, members, events, orgId): OntologyMapping;
}

这个设计有三个致命缺陷：

  1. 统一的数据模型假设：GitHub 的数据（commits、PRs、issues）和飞书的消息根本无法用同一个 ConnectorMessage 表示。GitHub 没有"消息"只有事件，飞书没有"拉取"(fetch) 只有 Webhook 推送。
  2. 拉取模式而非推送模式：所有数据获取都是同步的 request/response 模式，不支持 Webhook、CDC（变更数据捕获）或流式订阅。
  3. 无增量同步契约：since/until 参数是 string 而非标准化的 checkpoint 机制。重启后如何恢复上次同步位置？没有定义。

2.2 对标 Airbyte 和 Singer 的最佳实践

行业标准参考：Airbyte 的 Connector Development Kit (CDK) 定义了 3 层架构：Source (数据源) → Stream (增量/全量) → Record (统一记录)。Singer 定义 tap → target 协议。两者都支持 config.json + catalog.json + state.json 三文件运行时配置。

推荐的 Synova Connector SDK 三层模型：

// Layer 1: Source — 数据源连接和认证
interface ConnectorSource {
  name: string;
  platform: string; // 'feishu' | 'github' | 'jira'
  configSchema: JSONSchema; // 运行时验证配置
  checkConnection(): Promise<HealthCheckResult>;
}

// Layer 2: Stream — 数据流定义（每个源可以有多个流）
interface ConnectorStream {
  name: string; // 'messages' | 'members' | 'calendar_events'
  syncMode: 'full_refresh' | 'incremental';
  cursorField?: string; // 增量同步的游标字段
  supportsWebhook?: boolean;

  read(checkpoint?: string): AsyncIterable<Record>;
  // 支持 Webhook 的源还可以实现：
  subscribe(webhookUrl: string): Promise<void>;
}

// Layer 3: Transform — 从源格式到 SOG 本体映射
interface ConnectorTransform {
  mapToSOG(records: Record[]): OntologyMapping;
  // 支持字段级映射和转换
  schemaMapping?: Record<string, string>; // source_field -> sog_field
}

3. 事件管道架构

3.1 当前状态

事件管道为零。 目前没有任何消息队列、事件总线或发布/订阅系统。数据获取（如果能工作的话）是同步的：请求→响应→处理→存储。这对于单租户、小数据量的场景尚可接受，但当：

  • 多种连接器同时推送数据（Webhook）
  • 知识摄取和诊断管线需要异步处理
  • 多个专家 Agent 需要观察数据变更事件

时，没有事件管道会成为架构瓶颈。

3.2 NATS JetStream 评估

推荐：嵌入式 NATS JetStream。对于 on-prem 部署（不可引入外部依赖），NATS 可以嵌入式运行（nats-embedded 或同进程 nats-server）。相比 Kafka（需要 Zookeeper）和 RabbitMQ（需要 Erlang VM），NATS 是唯一可以在单进程嵌入的成熟消息系统。

4. 安全沙箱

4.1 当前安全基础

当前安全模块 (src/security/index.ts) 包含：

  • ✅ PermissionPolicy：基于 orgId 白名单的权限检查
  • ✅ AuditLog：SQLite 持久化的审计日志
  • ✅ PIIScrubber：中文手机号、身份证、邮箱等 PII 检测/脱敏
  • ✅ DataBoundary：数据敏感性分类

但没有任何连接器沙箱——连接器运行在 Agent 主进程中，拥有相同的文件系统、网络和系统调用权限。

4.2 沙箱技术选型

技术隔离级别启动时间资源开销Node.js 兼容推荐？
WASM (WebAssembly)进程级<1ms极低✅ 原生支持🥇 首选
Docker 容器OS 级1-5s高(每个容器 50-200MB)⚠️ dockerode❌ 太重
gVisor内核级2-10s高❌❌ 过于复杂
VM (Firecracker)硬件级~100ms中❌❌ 超出需求
子进程 + seccomp系统调用级~10ms低✅ child_process🥈 备选
WASM 沙箱的局限：WASM 在 Node.js 中执行意味着连接器必须编译到 WASM 或使用 WASM 兼容的运行时（如 wasmtime 或 WasmEdge）。对于 TypeScript 连接器来说，这意味着需要用 Component Model 或额外的适配层。一个更实际的方案是子进程 + 资源限制（cgroup/RLIMIT）作为第一阶段，WASM 作为第二阶段。

4.3 推荐的沙箱架构（两阶段）

Phase 1（近期）：子进程沙箱

// 每个连接器在独立子进程中运行
const { spawn } = require('child_process');

function runConnectorInSandbox(connectorId: string, task: ConnectorTask): Promise<ConnectorResult> {
  return new Promise((resolve, reject) => {
    const child = spawn(process.execPath, ['connector-worker.js'], {
      env: {
        CONNECTOR_ID: connectorId,
        CONNECTOR_CONFIG: encrypt(JSON.stringify(task.config)),
        // 仅注入必需的环境变量
        NODE_OPTIONS: '--max-old-space-size=128', // 128MB 内存限制
      },
      stdio: ['pipe', 'pipe', 'pipe'],
      timeout: 30_000, // 30s 超时
    });

    // 发送任务
    child.stdin.write(JSON.stringify(task));
    child.stdin.end();

    // 读取结果
    let output = '';
    child.stdout.on('data', chunk => output += chunk);
    child.on('close', code => {
      if (code !== 0) reject(new Error(`连接器退出: code=${code}`));
      else resolve(JSON.parse(output));
    });
  });
}

5. 知识摄取深化

5.1 当前状态

当前知识摄取（src/ingest/index.ts）支持 PDF/DOCX/Excel 的文本抽取，依赖 @synova/knowledge-ingest 包。但：

  • 入口文件仅 53 行，基本是委托给 engine-core 的 adapter
  • 不支持视觉解析（组织结构图、流程图被当作纯文本处理）
  • 不支持 .msg（Outlook 邮件）、.vsd（Visio 流程图）等企业专有格式
  • 不支持扫描件 OCR

5.2 视觉解析方案

对于组织结构图（图片或 PDF 中的图表）的解析，推荐使用多模态 LLM（如 GPT-4V）的视觉能力：

1. PDF/图片 → 多模态 LLM (视觉输入)
2. LLM 输出结构化组织数据 → JSON
3. JSON → SOG 节点/边 (Person, Team, ReportsTo)
4. 人工校验 → 确认/修正 → 写入 GraphStore

对于企业专有格式：

  • .msg (Outlook 邮件)：使用 msg-parser 或 python 的 extract-msg 提取发件人/收件人/主题/正文
  • .vsd (Visio 流程图)：使用 apache poi 或 python 的 vsdx 库提取形状/连接线
  • .mm (MindManager/XMind)：使用 xmind-parser 提取节点和层级关系
