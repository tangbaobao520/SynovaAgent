L5 数据层综合研究报告

Synova 组织智能诊断系统 · 2026-06-04 · RESEARCH-L5-DATA-LAYER-DEEP-DIVE

⚠️ 核心结论：L5 存在"三层代码，零层打通"的结构性断裂

L5 数据层拥有 三套并存的代码体系，但没有一套能把数据从外部系统送到 L4 本体层：

层次位置内容接线状态
层 1engine-core pipeline/diagnosis/OntologyAdapter + AirbyteOntologyAdapter + NATS 管线（590 行）❌ 所有适配器返回 mock 数据。NATS 管线完整但从未被 synova-agent 调用。
层 2@synova/connector-registryConnectorRegistry + DataConnector（getTools/connect/disconnect/executeTool）❌ 接口设计干净，但零个连接器实现它。没有飞书、没有 GitHub、没有 Jira。
层 3synova-agent src/connectors/旧版 DataConnector（fetchMessages/fetchMembers/fetchEvents）+ Feishu/NemoClaw stubs❌ 两套 DataConnector 接口并存且签名不同。Feishu/NemoClaw 全部返回空数组。

关键发现：engine-core 的 NATS 管线（nats-ontology-pipeline.ts）包含了完整的发布→流→消费→GraphStore 写入端到端设计，甚至有死信队列和重试策略，但"NATS"关键字在 synova-agent 代码库中出现零次。

执行摘要

L5 数据层的现状可以概括为：架构设计意图是 Palantir 级别的，工程实现是 Phase A 存根级别的。

好消息是设计质量很高——OntologyAdapter 对齐了 Airbyte 协议、NATS 管线有 DLQ 和健康检查、ConnectorRegistry 有完整的生命周期管理、PIIScrubber 和 DataBoundary 的基础设施已存在。坏消息是没有任何一条数据通路能真正从外部系统流到 SOG 本体。

以下是五个核心问题的逐项分析。

一、连接器架构完备性

1.1 当前状态

1.3 推荐方案：统一到 Airbyte 协议

engine-core 已有的 AirbyteOntologyAdapter 接口（见 airbyte-ontology-adapter.ts）是三个接口中最成熟的——它对齐了 Airbyte 的 4 方法协议：

AirbyteOntologyAdapter (engine-core 已有设计，推荐保留)
├── spec(): ConnectorSpecification          ← 连接器声明：名称、参数 schema
├── check(): AirbyteConnectionStatus       ← 健康检查
├── discover(): AirbyteCatalog              ← 数据源结构发现
└── read(): AsyncIterable<OntologyEvent>    ← 流式/批式读取

这个接口的优势：

  • 支持批处理和流式：read() 返回 AsyncIterable，上游可以决定是一次性拉完还是流式消费
  • 自描述：spec() 告诉系统这个连接器需要什么配置、输出什么数据
  • 模式发现：discover() 让系统不需要预知数据源结构
  • Airbyte 兼容：未来可以复用 Airbyte 生态的 3000+ 连接器

对应的，需要废弃 synova-agent 侧的旧版 DataConnector（src/connectors/types.ts 第 53-61 行的 fetch 模式），将所有连接器统一到 AirbyteOntologyAdapter 接口。

from abc import ABC, abstractmethod
from typing import AsyncIterable, Dict, Any, Optional

class ConnectorSpec:
    name: str
    label: str
    config_schema: Dict  # JSON Schema
    supported_streams: list[str]  # 'members' | 'messages' | 'events' | ...

class ConnectorStatus:
    healthy: bool
    error: Optional[str]
    latency_ms: Optional[int]

class Record:
    stream: str     # 'members' | 'messages' | ...
    data: Dict
    emitted_at: str

class ConnectorBase(ABC):
    @abstractmethod
    def spec(self) -> ConnectorSpec: ...
    @abstractmethod
    def check(self, config: Dict) -> ConnectorStatus: ...
    @abstractmethod
    def discover(self, config: Dict) -> list[str]: ...
    @abstractmethod
    def read(self, config: Dict, streams: list[str],
             state: Optional[Dict] = None) -> AsyncIterable[Record]: ...

    # 框架提供的通用功能
    def map_to_sog(self, records: list[Record]) -> OntologyMapping: ...

2.4 NATS 配置最佳实践（on-prem）

# 嵌入式 NATS 配置（单节点，同进程运行）
嵌入式模式 (nats-embedded 或同进程 nats-server):
- 无需单独启动 NATS 服务
- 数据持久化到 SQLite 同目录下的 nats/ 子目录
- 进程退出时自动清理

Stream 配置:
- 名称: SOG_EVENTS
- 存储: file
- 保留: limits (max_bytes: 1GB, max_age: 7d)
- 副本: 1（单节点不需要 Raft）
- 去重窗口: 2min

Consumer 配置:
- Ack 策略: explicit
- MaxDeliver: 3
- AckWait: 30s
- MaxAckPending: 100（背压控制）

3.4 推荐的 Phase 1 子进程沙箱

// TypeScript 侧：沙箱化的子进程管理
class SandboxedConnectorProcess {
  private proc: ChildProcess;
  private config: ConnectorConfig;

  async run(command: string, params: unknown): Promise<unknown> {
    // 1. 创建临时目录（连接器用完即销毁）
    const tmpDir = fs.mkdtempSync(path.join(os.tmpdir(), 'synova-connector-'));

    try {
      // 2. 限制子进程资源
      this.proc = spawn('python3', ['-m', `synova_worker.${this.config.name}`], {
        env: {
          CONNECTOR_ID: this.config.id,
          // 只传递连接器自身需要的凭证
          CONNECTOR_CONFIG: encrypt(this.config.credentials),
          // 不传递任何系统环境变量
        },
        cwd: tmpDir,
        stdio: ['pipe', 'pipe', 'pipe'],
        timeout: 30_000,
      });

      // 3. 发送请求 + 读取结果
      this.proc.stdin.write(JSON.stringify({ command, params }));
      this.proc.stdin.end();
      const output = await this.readOutput();

      return JSON.parse(output);
    } finally {
      // 4. 清理临时目录
      fs.rmSync(tmpDir, { recursive: true, force: true });
    }
  }
}

3.5 凭证管理

// 加密凭证存储（替代 .env 明文）
class CredentialVault {
  private key: Buffer;  // 派生自主密码

  constructor(orgId: string) {
    // 主密码存储在 OS Keychain / 环境变量
    this.key = deriveKey(process.env.SYNOVA_MASTER_SECRET, orgId);
  }

  // 加密存储凭证到 SQLite
  store(connectorId: string, credentials: Record<string, string>): void {
    const encrypted = this.encrypt(JSON.stringify(credentials));
    this.db.prepare('INSERT INTO connector_creds (id, encrypted) VALUES (?,?)')
      .run(connectorId, encrypted);
  }

  // 运行时解密，仅子进程启动时使用
  retrieve(connectorId: string): Record<string, string> {
    const row = this.db.prepare('SELECT encrypted FROM connector_creds WHERE id=?')
      .get(connectorId) as { encrypted: string };
    return JSON.parse(this.decrypt(row.encrypted));
  }
}

四、知识摄取

🏗️ 架构定位：知识摄取属于 L5

知识摄取和连接器是 L5 的两条并行数据入口，输出相同的 OntologyEvent，通过相同的事件管道进入 L4：

连接器（L5）：外部 API → 适配器 → read() → AsyncIterable<OntologyEvent> → NATS → L4
知识摄取（L5）：文件上传 → 解析器 → extract() → AsyncIterable<OntologyEvent> → NATS → L4
                                                                              ↑
                                                                      L4 只消费事件
                                                                      不关心数据来源

L3/L4 完全不需要知道数据是从飞书来的还是从 PDF 来的。知识摄取的所有代码都在 L5 内部。

与 L4 的边界

知识摄取（L5）的输出是 OntologyEvent，通过 NATS 事件管道进入 L4。L4 的 NatsGraphStoreConsumer 消费这些事件并写入 GraphStore。L4 不需要知道这些事件是来自飞书连接器还是来自文件上传——同一管道、同一格式、同一消费者。

如果 L4 需要查询某份文档的原始内容（如"这个 Person 节点来自哪个 PDF 的哪一页"），通过 L4 的 DOCUMENT 节点属性反查，不走 L5。

五、连接器生态与市场

5.1 当前状态

连接器市场目前是一个想法，零代码实现。当前只有架构设计文档中提到了 Connector-Registry 的"双向集成平台"定位，但发布的渠道、打包方式、版本管理、安全扫描全部不存在。

5.2 差距分析

维度当前状态目标状态缺口
连接器分发无打包为 Wheel/镜像 → 注册中心 → 客户端安装全缺
版本管理无SemVer + 兼容性验证 + 灰度发布全缺
安全扫描无CI/CD 自动密钥扫描 + 漏洞扫描 + 签名全缺
开发者文档无连接器开发教程 + API 参考 + 示例全缺
安装方式手动复制文件一键安装来自 Connector Registry全缺

5.3 推荐：3 阶段建立连接器生态

Phase 1（3-6 个月）— 内部 5 个连接器
  目标：飞书、GitHub、Jira、钉钉、金蝶
  发布方式：内置在 synova-agent 代码库中
  开发者：内部团队
  无需市场基础设施

Phase 2（6-12 个月）— 官方连接器 SDK + 文档
  目标：允许第三方公司开发连接器
  交付物：
    - Connector SDK（Python + spec/check/discover/read）
    - 连接器模板仓库
    - 开发教程 + 示例
    - CI/CD 验证工具
  发布方式：连接器作为 Python wheel 包分发

Phase 3（12+ 个月）— 连接器市集
  目标：开放生态，第三方发布
  基础设施：
    - OCI 兼容注册表（Harbor）存储连接器镜像
    - 安全扫描（Trivy + 密钥扫描）
    - 签名（Cosign/Sigstore）
    - 版本管理（SemVer + 兼容性检查）
    - 在 UI 中集成连接器浏览/安装
