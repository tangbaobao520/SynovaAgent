📋 核心结论

SynovaAgent 默认使用 DeepSeek，但当前代码对 DeepSeek V4 的架构特点几乎没有针对性优化。最大的损失是前缀缓存（Prefix Cache）——如果能达到 99% 的命中率，输入 token 成本可降低 50 倍（从 $0.14/1M 降到 $0.0028/1M）。当前诊断流程每次重建 Prompt，缓存命中率估计低于 20%。

此外，deepseek-chat 和 deepseek-reasoner 模型名已于 2026 年 7 月 24 日停用，必须迁移到 deepseek-v4-pro / deepseek-v4-flash。

2. 前缀缓存（Prefix Cache）优化——最大的成本杠杆

2.1 DeepSeek 前缀缓存的工作原理

DeepSeek V4 对请求的 字节前缀 做哈希缓存。如果两个请求的前 N 个字节完全相同，共享的 KV cache 部分不重复计算，价格降低 50 倍（$0.14→$0.0028/1M tokens）。

2.2 诊断流程中的缓存分析

当前 Prompt 构建（缓存命中率 ~20%）：
┌──────────────────────────────────────────────┐
│ System Prompt（含动态时间戳、会话 ID）       │ ← 每次不同，缓存 MISS
│ Tool Definitions（稳定）                      │
│ 对话历史（不断增长，每次不同）                │
│ 当前用户输入                                   │ ← 必然不同
└──────────────────────────────────────────────┘

优化后 Prompt 构建（目标缓存命中率 ~95%）：
┌──────────────────────────────────────────────┐
│ IMMUTABLE PREFIX（固定哈希）                 │ ← 缓存 HIT
│   System Prompt（无动态字段）                │
│   Tool Definitions（固定顺序）               │
│   Few-shot Examples（固定）                   │
├──────────────────────────────────────────────┤
│ APPEND-ONLY LOG（每轮追加）                  │
│   Assistant turn 1 + Tool result 1           │
│   Assistant turn 2 + Tool result 2           │
│   ...（只追加，不修改前面）                   │
├──────────────────────────────────────────────┤
│ VOLATILE SUFFIX（不影响缓存）               │
│   当前用户输入                                 │
└──────────────────────────────────────────────┘

2.3 缓存优化的三个原则

  1. 不可变前缀（Immutable Prefix）：Session 开始时固定 system prompt + tool definitions + few-shot examples。不要在 system prompt 中注入时间戳、用户名、随机 ID 等动态字段。
  2. 只追加日志（Append-Only Log）：对话历史只能追加，不能重写或重新排序。即使需要截断上下文，也要截断中间部分，保留前缀完整。
  3. 动态字段移出 prefix：时间戳、会话 ID 等动态字段放在最后一条 user message 之前，不影响前缀。

2.4 预计成本节省

场景当前（20% 缓存命中率）优化后（95% 命中率）节省
每次诊断（~50K 输入 tokens）$0.0070 - 0.0014 = $0.0056$0.0028 × 95% + $0.14 × 5% = $0.0097~5 倍

2.5 具体代码修改建议

// ConversationEngine 中实现不可变前缀

// 1. 在 Session 开始时冻结 system prompt
class ConversationEngine {
  private immutablePrefix: string = ''; // 构造时生成，永不改变

  constructor() {
    // 生成不可变前缀
    this.immutablePrefix = this.buildImmutablePrefix();
  }

  private buildImmutablePrefix(): string {
    return [
      SYSTEM_PROMPT,           // 固定的 system prompt（无动态字段）
      TOOL_DEFINITIONS,        // 固定的工具定义
      FEW_SHOT_EXAMPLES,       // 固定的 few-shot
    ].join('\n');
    // ⚠️ 不能包含: 时间戳、会话 ID、用户名
  }

  // 2. 每轮消息追加到日志
  private appendOnlyLog: Message[] = [];

  // 3. 提交给 LLM 时拼接
  private buildMessages(userInput: string): LLMMessage[] {
    return [
      { role: 'system', content: this.immutablePrefix },
      ...this.appendOnlyLog,   // 只追加，不修改
      { role: 'user', content: userInput },
      // ⚠️ 不在 system prompt 中注入动态字段
      // 如果需要时间上下文，放在 user message 中
    ];
  }
}

4. Strict Mode 工具调用

4.1 当前工具调用格式的问题

当前工具参数使用 OpenAI JSON-in-string 格式，没有 schema 验证：

// 当前: LLM 可能返回不符合 schema 的 JSON 参数
"arguments": "{\"query\": \"...\"}"  // 如果有拼写错误，直接失败

// 启用 Strict Mode（beta）:
// DeepSeek 服务端验证参数符合 JSON Schema
// 不符合 schema 的调用在服务端就被拒绝，不浪费一次工具执行

4.2 启用 Strict Mode 的方法

// 需要将 base_url 改为 beta 端点
const BASE_URL_BETA = 'https://api.deepseek.com/beta';

// 在 tool definition 中添加 strict: true
const toolDef = {
  type: 'function',
  function: {
    name: 'search_knowledge',
    strict: true, // ← 启用服务端验证
    description: '搜索知识库',
    parameters: {
      type: 'object',
      properties: {
        query: { type: 'string' },
        maxResults: { type: 'integer', minimum: 1, maximum: 20 }
      },
      required: ['query'],
      additionalProperties: false // ← strict mode 要求
    }
  }
};

5. Thinking Mode + 工具调用集成

5.1 DeepSeek V4 的推理保留特性

当使用了工具调用时，DeepSeek V4 会在多轮对话中保留推理内容（reasoning_content）。这意味着：

  • 专家 Agent 的 ReAct 循环（Think → Act → Observe）可以利用跨轮的推理历史
  • 后续请求必须包含前一轮的 reasoning_content，否则 API 返回 400 错误

5.2 对 ExpertAutonomyEngine 的修改

// ExpertAutonomyEngine 需要保留 reasoning_content

interface ReActTurn {

  reasoningContent?: string;   // ← 新增

// 在提交下一轮时，必须包含 reasoning_content
const messages: LLMMessage[] = [
  ...previousTurns.map(t => ({

    content: t.assistantResponse,
    reasoning_content: t.reasoningContent,  // ← 必须有

6. 诊断流程的缓存优化架构

当前（低效）:
Session 1: [system: 含时间戳] [tools] [history] → 缓存 MISS
Session 2: [system: 不同时间戳] [tools] [history] → 缓存 MISS
Session 3: [system: 再次不同时间戳] [tools] [history] → 缓存 MISS

优化后（高效）:
Session 1: [IMMUTABLE PREFIX] [消息 1] [消息 2] → 前缀 HIT
Session 2: [IMMUTABLE PREFIX] [消息 1] [消息 2] [消息 3] → 前缀 HIT
Session 3: [IMMUTABLE PREFIX] [消息 1] [消息 2] [消息 3] [消息 4] → 前缀 HIT
           ↑ 完全相同的前缀字节序列，100% 缓存命中
