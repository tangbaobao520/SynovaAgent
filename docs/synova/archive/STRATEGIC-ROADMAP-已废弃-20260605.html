一、产品核心定位

定义：部署在企业本地的、实时运行的组织医生。不是聊天机器人，不是报告生成器，不是一次性工具。是一个持续感知、持续诊断、持续出方案的系统。

不是是
飞书聊天记录分析器多源数据交叉验证引擎（飞书只是第一个数据源）
AI 对话机器人六阶段状态机驱动的诊断系统（LLM 只是推理引擎）
一次性咨询报告持续运行的组织数字孪生（SOG 双时序）
SaaS 工具On-prem 部署，数据主权是价值

类比：Palantir（国家安全领域）→ Synova（组织健康领域）。

Palantir: 卫星照片 + 通信拦截 + 金融交易 + 线人报告 → 交叉验证 → 情报
Synova:   飞书聊天 + GitHub commit + Jira ticket + 财务数据 → 交叉验证 → 诊断

二、核心价值（始终坚守，不可妥协）

  1. 证据溯源不可妥协——每条诊断结论都有来源。宁缺毋滥。
  2. 五层架构边界纪律——L1 不知道 L3，L5 不知道 L2。允许各层独立演进。
  3. 降级透明——不行就是不行，不假装行。铁律 11+31 是 40 条中最重要两条。
  4. 数据主权——客户的数据永远是客户自己的。联邦进化必须有差分隐私。
  5. 中文优先——LLM Prompt 永远保留中文（中文组织数据分析精度最高）。UI 和错误消息未来可加英文版。

三、产品护城河（按不可复制性排序）

护城河为什么难复制
1. SOG 组织本体图（14 节点 + 10 边 + 双时序 + RDF 三元组）数据建模的工程量和组织理论的知识密度。不是代码，是做出来的数据基础设施。
2. 多源交叉验证的信任飞轮企业采购 AI 的第一障碍是信任。有了 3 个以上数据源在 SOG 上交叉后，诊断精度产生质变。
3. 85 个可计算认知框架从 102 个审计清洗到 85 个，有严格准入准出门禁。不是列表，是可工程化的知识库。
4. On-prem + 数据主权中国大客户的第一关是数据不出内网。我们从第一天就是 on-prem 架构。
5. DeepSeek 成本优势V4 Flash $0.14/1M + Prefix Cache $0.0028/1M = 比 GPT-4o 便宜 18-900 倍。

5.2 LLM Provider 策略

默认：DeepSeek V4 Flash（¥0.14/1M input，Prefix Cache ¥0.0028/1M，1M 上下文，中文原生优势）。

锁定风险：不担心。 优化在 Provider 层内部完成，上层通过 LLMProvider.chat()/stream() 接口调用。切换 Provider 只需新写一个实现类。详见 PROVIDER-COMPATIBILITY-STRATEGY.html。

5.3 架构模式：模块化单体 + Python 侧车

不是微服务。 微服务解决了我们当前没有的问题（大规模团队协作部署），引入了我们承受不起的复杂度（客户 IT 维护 7 个服务）。

TypeScript 主进程 (Express)
  ├── 所有编排、分析、本体逻辑
  ├── 通过 child_process.spawn('python3', ...) 按需启动 Python 侧车
  └── 用完即销毁，不占常驻内存

Python 侧车职责：
  ├── 连接器执行（飞书/GitHub/Jira SDK）
  ├── 知识摄取（PyMuPDF/python-docx/...）
  └── 远期：中文 NLP、因果推断

5.4 连接器接口：统一到 Airbyte 协议

决策：以 AirbyteOntologyAdapter（spec/check/discover/read）为标准接口，废止另两套并存的 DataConnector 接口。详见 L5-CONNECTOR-ARCHITECTURE.html。

七、交付纪律（铁律执行版本）

方向 5：AI Agent 团队可观测性

背景：客户的团队中可能有 AI Agent（OpenClaw 生态/Claude Code/Hermes/LangChain/CrewAI 等），我们需要能像诊断人类团队一样诊断 Agent 团队。

关键发现：

  • OpenClaw 已有官方可观测性插件——openclaw-observability（20 个钩子 + 内置面板 + 安全扫描）和 diagnostics-otel（OTLP Metrics/Traces/Logs）。我们直接消费 OTLP 数据或 DuckDB 即可，不需要自己开发观测机制。
  • MCP 是通信协议，不是观测协议。MCP 用于 Agent ↔ Synova 的双向通信（Agent 查询诊断数据、Synova 推送预警），不能替代平台原生的观测机制。
  • LangChain/CrewAI/AutoGen 等框架——通过 callback/handler 机制，一行代码即可接入。
  • 所有数据进入 SOG——与人类团队共享同一套分析管线，6 个专家复用 query_sog_graph 工具分析。

架构：

Agent Telemetry Collector
├── OpenClaw: 消费 OTLP / 读取 observability 插件 DuckDB
├── Claude Code: MCP report_activity + 日志轮询
├── Hermes: Plugin 回调 + HTTP 上报
├── LangChain/CrewAI/AutoGen: CallbackHandler 一行代码
└── → 统一写入 SOG 的 AGENT 节点 + 边

上线顺序：

  1. P1 OpenClaw OTLP 消费 + LangChain CallbackHandler
  2. P2 Claude Code MCP + Hermes Plugin
  3. P2 统一 SDK 覆盖其他框架

参考：

  • OpenClaw: openclaw-observability 插件 / diagnostics-otel 插件
  • LangChain: BaseCallbackHandler 文档

十二、讨论中沉淀的关键认知

  1. "不是低频需求，是传统供给太差导致的需求压抑。"——乔布斯做 iPhone 前没人觉得自己需要智能手机。组织诊断不是不需要，是之前没有付得起、看得懂的方案。
  2. "飞书只是之一，不是全部。"——飞书是第一个数据源，不是最后一个。当 5 路、10 路数据在 SOG 上交叉时，洞察质变。
  3. "未来的组织一定是人 + AI Agent 混合的。"——SOG 的 AGENT 节点类型从第一天就在那里，不是后来补的。
  4. "三层代码，零层打通"——L5 最核心的结构性问题。engine-core 有完整的 NATS 管线 + OntologyAdapter + Airbyte 接口，synova-agent 侧有 FeishuConnector 存根，ConnectorRegistry 有干净的生命周期管理——但没有任何一条数据通路能真正把数据送到 SOG。
  5. "编码智能体最大的弱点不是代码质量，是接线。"——CLAUDE.md 记录了 6 次同类事故。代码写得很好但没被任何生产路径调用。接线验证必须是硬门禁。
