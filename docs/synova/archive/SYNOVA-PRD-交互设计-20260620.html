术语说明

GA（增长顾问，Growth Advisor）：本文档中 GA 指 Synova 的增长顾问角色。GA 不是传统意义上的工程师或软件操作员——GA 是拥有多年行业经验的专家，借助 Synova 的系统能力将自己的经验放大、服务更多客户。GA 的核心能力是行业判断（用经验校准 Synova 的分析）和客户信任（建立长期关系、推动方案落地），而非技术部署。稍加培训即可上手。GA 替代了早期版本中使用的 FDE（Frontline Deployment Engineer）一词，因为 Synova 的 GA 角色定位与 Palantir 的 FDE 有本质区别：不需要技术背景，不需要编写代码或配置系统，需要的是行业经验和客户关系。

对接人：企业内部的日常联系人，负责在 GA 交付方案后跟进执行。不需要行业经验或诊断能力，只需协调内部资源执行 Agent 的建议。

一、产品定位：数字化麦肯锡，不是 ChatBot，不是 SaaS，不是 BI

1.1 一句话定义

Synova 是一个驻扎在企业内部的数字化麦肯锡咨询师 Agent。它持续观测企业全量数据，主动发现问题，自动诊断根因，提出可落地的方案，跟踪执行效果。最终决策永远是人做的——Synova 是辅助决策，不是替代决策。

1.2 与竞品的本质区别

类别代表产品核心能力Synova 不做什么
编程 AgentCodex, Claude Code, OpenClaw写代码、部署、自动修复不执行任务——只告诉人该做什么
ChatBotChatGPT, 通用对话 AI一问一答，文本生成不做通用闲聊——对话始终在诊断上下文中

SaaS 管理工具Jira, Salesforce任务管理、客户关系不做项目管理——只跟踪建议的执行效果

1.3 三大核心能力

能力架构层Agent 做什么人做什么
发现问题L4 + Sentinel + Signal Aggregator交叉关联多个信号，浮现真实风险。不是"指标跌了"，是"三个信号指向同一个结构性问题"确认 Agent 的发现是否重要

四、左栏：工作区列表

一个工作区 = 一个需要解决的问题。来源：Agent 诊断自动创建（每次诊断 5-8 个）、人手动创建、Agent 从长期遗留复活。

每条显示：🔴🟡✅（优先级）+ 一句话概括 + 最后更新时间。排序按"需要人关注的程度"——🔴 最高，📋 最低。当前工作区高亮。

新建交互

Agent: "你发现了什么问题？"
人: "订单量涨，但毛利率跌。"
Agent: "收到。我先扫描……初步判断：毛利率下跌与原料成本上涨有关，但定价没同步调整。要我创建新工作区深入分析吗？"

不是空容器——Agent 在创建工作区前已完成预分析。这是 Agent 与项目管理工具的本质区别。

五、中栏：对话区

对话是 Agent 的交付室——人和 Agent 在这里共同审阅判断、讨论分歧、修正方案、最终确认执行。每一轮对话的产出不是文本，是结构化判断的状态变化。

六、上下文管理

6.1 设计前提：一个工作区 = 一个上下文窗口

Synova 的交互模型中，每个工作区是一个独立的上下文窗口。工作区天然限制了上下文膨胀率——每个工作区的对话通常在 5-10 轮内完成（根因确认 -> 纠正 -> 方案确认 -> 关闭），不会无限增长。部门工作区（配置相关的深入讨论）可能会超过 30 条的信息交互，但仍然有限。

因此上下文管理的核心问题不是"在巨大的对话中保存信息"，而是：工作区内对话的压缩不能丢失已确认的结构化判断，以及工作区之间的已确认判断如何被互相引用。

6.2 工作区内部：结构化判断永不丢，对话细节可丢

当前 conversation-engine 采用 sliding-window 策略（30 条消息后截断），这会导致 FDE 的纠正、已确认的判断在压缩后丢失。在 PRD 工作区模型下，压缩策略改为：

策略当前状态
（sliding-window）		目标状态
（结构化判断可保持）
压缩触发时机消息数 > 30 条时自动触发消息数 > 30 条时自动触发（不变）
保留的信息system prompt + 最近 20 条消息。前面的消息全部丢弃system prompt + 本工作区已确认的判断清单 + 最近 5 轮对话
摘要策略无摘要——直接截断已确认判断以结构化形式保留。对话历史用 summary 压缩为一条 system 消息
已确认的判断来源不存在AgentMemoryStore 中 type=enterprise_fact，标记本工作区 ID。每次用户"采纳"后自动写入。压缩时通过 workspaceId 加载

压缩后的上下文格式：

[本工作区已确认的判断]: - 根因: 采购流程临时异常（FDE 纠正后确认） - 建议: 暂不催收，下月复查 - 置信度: 78% [对话摘要]: 财务专家分析了应收账款周期数据，用户补充了采购系统迁移背景。 Agent 修正根因判断。战略专家交叉验证了市场影响。

6.3 工作区之间：跨工作区的已确认判断引用

不同工作区处理不同的问题，但同一个企业的问题之间经常存在关联。"现金流预警"和"人员扩张效率低"可能源于同一个结构性原因。工作区之间的信息流动不需要传递完整对话历史——只需要传递已确认的结构化判断。

跨工作区引用机制：

  1. 每个工作区关闭时，该工作区的已确认判断存入 AgentMemoryStore，标记 type=enterprise_fact 和 orgId=workspaceId
  2. 新工作区打开时，Agent 自动从 AgentMemoryStore 中加载相关的已确认判断——通过该工作区的领域标签进行语义搜索匹配
  3. 匹配结果以"[来自 XX 工作区] 根因: XXXXX"的形式注入新工作区的对话上下文
  4. Agent 在跨工作区判断不一致时（如工作区 A 认为"人员流失原因：薪酬无竞争力"，工作区 B 认为"薪酬在行业中等偏上"），主动标记冲突并提示用户

这避免了"为了跨工作区一致而缓存全部历史对话"的工程负担。跨工作区传递的永远只是结构化的事实，不是整个对话历史。

11.1 GA 的角色定义

GA（增长顾问，Growth Advisor，全称 Growth Advisor，文档中统称为 GA）不是 Synova 的操作员，不是技术工程师——不需要编写代码或配置系统，稍加培训即可上手。GA 是拥有多年行业经验的专家（老兵）。他们借助 Synova，可以让自己的行业经验服务更多客户，创造更多收入。Synova 为 GA 提供他们不具备的全方位诊断和监督能力；GA 为 Synova 带来客户、和客户沟通、并且用自身经验优化本体图、行业哨兵、行业知识库。两者的关系是乘法：GA 的经验 × Synova 的系统能力 = 一个人能服务 10-20 个客户的产能。

16.1 设计目标

每次提问时，Agent 自动根据提问者的角色套用权限过滤。角色分为三级：

16.4 回答格式

Agent 的每条回答包含三部分：

  1. 答案：对问题的直接回答。简洁到一句话内。
  2. 数据来源："数据来源: 2026年7月 CRM 系统。最近更新: 昨天 14:30。"
  3. Agent 的判断（可选）：如果问题涉及诊断性质的判断，Agent 附上自己的分析。"同行业平均客户流失率是 4%，你是 7%。我的判断：你需要关注客户留存策略。要展开分析吗？"

16.5 与工作区的联动

如果人在知识问答中发现了一个需要深入处理的问题，可以一键转化为工作区。Agent 自动将问答的上下文注入新工作区的对话中。

十六、多媒体数据支持（远期架构）

17.1 当前状态

doc-extractor.ts 当前仅支持文本类文档：PDF、Word、Excel、飞书文档、访谈记录。不支持语音、图像、视频。V1 阶段文本数据已覆盖 80% 的诊断场景，多媒体数据为远期能力。

17.2 理论价值

企业最丰富的信息不在文档里——在会议录音、门店照片、工厂视频、销售电话录音里。三例说明：

  • 语音：销售和客户的通话录音 -> 转文字 -> 情绪分析 -> "最近三个月客户对定价的负面情绪从 12% 上升到 34%"
  • 图像：零售门店的货架照片 -> OCR + 视觉识别 -> "竞品 X 在你的 5 个门店中占据了比上月更多的货架空间"
  • 视频：工厂生产线的监控视频 -> 动作识别 -> "生产线 B 的停工时间比上月增加了 22%"

17.3 架构扩展点

多媒体数据在进入 Synova 的诊断管线之前，先经过独立的处理器转为文本 + 结构化元数据。转换后，下游管线（DocExtractor -> KnowledgeStore -> Sentinel -> Expert）无需任何修改——它对 Synova 来说就是和文本数据一样的结构化信息。

十八、企业事实层——专家回答一致性的基础

18.1 问题本质

如果 Agent 在 3 月的诊断中说"你的收入确认采用完工百分比法"，但在 6 月的讨论中因为训练数据的干扰而退化到"按发票日期确认收入"，那么企业不会信任 Agent。企业需要的是：对已经确认的事实，Agent 必须始终保持一致——直到企业正式变更了制度。

18.2 企业事实层

企业事实层（Enterprise Fact Layer）是存储在 AgentMemoryStore 中的动态知识库。每项事实包含版本演化的完整历史。Agent 在每次推理和对话中，自动获取当前有效版本作为推理的硬约束。

企业事实层示例： 收入确认方式: v1 (2025-Q2): 完工百分比法 | superseded_by v2 (2026-Q1): 按里程碑确认（董事会决议 2026-01-15） [当前有效版本] 绩效考核工具: v1 (2023): 无体系 | superseded_by v2 (2024-Q1): KPI 考核体系 | superseded_by v3 (2026-Q1): KPI + OKR 混合体系（HR 改革方案 2026-02-01） [当前有效版本] 组织架构: v1 (2024): 职能制 | superseded_by v2 (2026-01): 事业部制，3个事业部 [当前有效版本]

18.3 关键设计

设计说明
版本企业事实层是动态的。任何事实变更时，新版本 superseded_by 旧版本。旧版本不删除——保留历史供追溯
当前有效版本Agent 推理时始终使用最新的、未被 superseded 的记录。不需要在每次推理时"回忆"或"检索"——这是硬约束而非软提示
变更来源老板在飞书中确认"我们下季度开始用 OKR"、GA 在诊断中发现并更新、对接人在日常使用中标记、Agent 在下一次哨兵扫描中检测到变化并建议更新
注入方式每次诊断/对话的 System Prompt 顶部自动注入当前有效版本的摘要。Agent 必须基于这些事实推理——如果推理结果与事实矛盾，Agent 不能自行修改事实，而是标记为"建议调整公司的 XX 制度"作为新的发现
追溯性老板问"我们上次改考核制度是什么时候？"——Agent 沿着 superseded_by 链展示完整的变更历史和每次变更的原因

18.4 技术实现

基于现有代码：AgentMemoryStore 新增 type=enterprise_fact 记忆类型。每条记录包含：

字段说明
id唯一标识。跨版本不变
category领域分类（finance/hr/strategy/tech/marketing）
value事实内容。如"KPI + OKR 混合体系"
version版本号。自增
superseded_by被哪个版本替代。null = 当前有效
change_reason变更原因。如"董事会决议 2026-01-15"
changed_by变更来源。如"老板飞书对话 2026-01-16"
effective_from生效日期

十九、诊断节奏与建议边界

19.1 问题本质

真正的管理顾问不会看完数据就给建议——他们会判断"建议的时机是否成熟"。同样的数据，对不同规模、不同阶段的企业，建议的力度和节奏应该不同。Synova 已经有了 STAGE_LOGIC.md（按企业规模调整测量工具）和 SCALE_MODEL.md（规模只影响输出颗粒度），但缺少的是"建议力度"的控制——不是"能不能诊断"，而是"能不能建议"。

19.2 各专家的建议节奏

战略顾问

数据充分度建议力度示例
仅有 8 维度初诊数据仅方向性判断。不说"你应该进入 X 市场"，说"有三个可能的方向，分别需要验证以下信息""你的竞争护城河不够坚固。建议深入分析：1) 本地竞争格局（需实地调研）, 2) 客户流失的真正原因（需客户访谈）。有这些数据之前，不建议做战略转向。"
有行业数据 + 客户基本数据给出分析结论，标注置信度。方案附带"需要验证的假设"清单"基于已有数据，你的定价偏低，损失约 15% 毛利。但需要验证：客户对提价的敏感度。建议选 2 个非核心客户试点提价 10%，观察流失率。"
有全量数据 + 竞品数据 + 客户调研给出完整方案。包含具体行动、时间线、风险预案"经三个月试点，提价 10% 的客户流失率仅 3%（预期 8%）。我建议：全线提价 8-12%，按客户分级差异化定价。详细方案见附件。"

组织顾问

企业规模建议力度原则
小于 50 人可以建议调整架构小企业组织调整成本低，可以快速试错
50-150 人指出问题，但不直接建议调整架构"我观察到协作摩擦。但目前的数据不足以支撑架构调整的建议——需要更深入的跨部门访谈。"
150-500 人极其谨慎。只在不调整就无法增长时才建议。始终提供不调整架构的替代方案作为优先选项"三个部门存在严重协作断裂。但我不建议你重组——在你们当前规模下，重组本身就是最大的风险。替代方案：建立跨部门协调机制，暂不动架构。"
大于 500 人只指出可量化的问题。架构调整建议必须附带：1) 不调整架构的替代解决方案, 2) 调整的风险清单, 3) 分阶段实施路线图"你在三个维度上低于同行业基准。建议优先级：1) 跨部门协调（低风险），2) 如 6 个月后无改善，调整汇报线（中风险），3) 不推荐全面重组（高风险）。"

财务顾问

数据长度建议力度
小于 3 个月历史只做诊断，不给方案。"我需要至少 6 个月财务数据才能给出可靠的融资建议"
3-6 个月趋势分析 + 风险预警。方案标注"待更多数据验证"
大于 12 个月 + 行业基准完整的融资/成本优化方案。附带财务模型和敏感性分析

技术顾问

数据充分度建议力度
无代码仓库访问只做通用建议。不推荐具体工具或架构
有代码仓库 + 小于 3 个月数据指出技术债热点。不推荐大改动
有全量数据 + 行业基准具体的技术债清偿路线图。区分"紧急修复"和"计划重构"

19.3 通用原则

  1. 数据不足时，说"我不知道"，不说"我猜"。明确列出需要什么数据才能做判断，不基于训练数据填空白。
  2. 建议越重大，替代方案越多。重大建议（组织重组、战略转向、大额融资）必须附带至少一个不采取此行动的替代方案供对比。
  3. 置信度低的判断，不转化为行动建议。置信度低于 60% 的判断只作为"发现"报告，不进入"建议"列表。
  4. 规模越大，建议越保守。大企业的决策成本高、影响面广。同样的问题在小企业可以直接建议调整，在大企业需要分层逐步推进。
  5. 所有建议标注"这是事实还是推断"。每条结论附标签：数据事实 / 专家推断 / 预测假设。不让推断包装成事实。

19.4 技术实现

基于现有 STAGE_LOGIC.md（每个专家的规模自适应规则）和 SCALE_MODEL.md（六阶段模型）扩展。每个专家的 RULES.md 中新增"建议节奏"章节，Agent 在推理时自动根据数据充分度和企业规模选择建议力度。

二十、从 Claude for Financial Services 借鉴的设计模式

本章记录从 Anthropic 开源项目 Claude for Financial Services（https://github.com/anthropics/claude-for-financial-services）的代码审计中提取的可借鉴设计模式。该项目的架构与 Synova 不同（它是固定工作流的金融分析 Agent，Synova 是自适应诊断 Agent），但它在三个方面的设计值得纳入 Synova 的工程规范。

20.1 专家输出 Schema 验证

当前问题

ExpertDispatcher 当前使用 EXPERT_REPORT_SCHEMA 强制专家输出 JSON，但无 schema 验证。如果某个专家的 JSON 多了字段、类型错误（string 应为 number）、或缺少必填字段，下游的 EvidencePool 和 ReportBuilder 不会知道，运行时可能出现类型错误或数据缺失。

参考实现

Claude for Financial Services 中，每个子 Agent 在 agent.yaml 中声明 output_schema，父 Agent 拿到结果时通过 schema 校验保证数据格式。

参考文件: D:\Git项目研究\financial-services-main\managed-agent-cookbooks\pitch-agent\subagents\researcher.yaml（L42-68）—— output_schema 定义示例

# Claude for Financial Services 的 output_schema 示例 # 来源: researcher.yaml output_schema: type: object required: [target, comps] additionalProperties: false properties: target: { type: string, maxLength: 64, pattern: "^[A-Za-z0-9 ._-]+$" } comps: type: array maxItems: 30 items: type: object additionalProperties: false properties: ticker: { type: string, maxLength: 12, pattern: "^[A-Z.]+$" } metric: { type: string, maxLength: 32, pattern: "^[A-Za-z0-9 /_-]+$" } value: { type: number } precedents: type: array maxItems: 30 items: type: object additionalProperties: false properties: target: { type: string, maxLength: 64, pattern: "^[A-Za-z0-9 ._-]+$" } acquirer: { type: string, maxLength: 64, pattern: "^[A-Za-z0-9 ._-]+$" } ev: { type: number } multiple: { type: number }

实施建议

  1. 为每个专家定义严格的输出 Schema。在 expert/*/RULES.md 中或独立的 expert/*/OUTPUT_SCHEMA.md 中定义。格式使用 JSON Schema 或 Zod。
  2. 在 ExpertDispatcher 的输出注入 schema 验证层。专家返回 JSON 后，在进入 EvidencePool 之前做一次校验。校验失败时让专家重试（最多 2 次）。每次重试附带前一次的校验错误信息，帮助专家修正。
  3. Schema 中包含必填字段、类型约束、枚举值、最大长度。例如财务专家的输出必须包含 cashFlowRatio: number (0-5)，不允许返回 cashFlowRatio: "健康"。
  4. 新增专家时必须先定义 Schema，再实现逻辑。Schema 作为专家输入输出的合同，确保新增专家不会引入下游不兼容的数据格式。

20.2 共享知识的单源同步机制

当前问题

专家的共享知识（财务比率、行业基准、诊断框架）分散在 8 个专家的 KNOWLEDGE.md 中。finance/KNOWLEDGE.md 和 strategy/KNOWLEDGE.md 可能各自维护了一份"现金流健康评分标准"，如果修改其中一个，另一个不会自动同步，导致诊断结论不一致。

参考实现

Claude for Financial Services 中，每个 skill 只在一个地方维护——vertical-plugins/*/skills/*/ 是唯一真源。agent-plugins/*/skills/*/ 中的副本是自动同步过来的。修改 skill 只需修改真源，然后运行 sync-agent-skills.py 自动同步到所有依赖该技能的 Agent。

实施建议

  1. 识别专家 KNOWLEDGE.md 中的重叠内容。审计 8 位专家的 KNOWLEDGE.md，找出重复出现的内容（财务比率标准、行业基准数据、AARRR 漏斗定义等）。
  2. 将重叠内容提取到 knowledge/shared/ 目录。每个共享知识一个文件。例如 knowledge/shared/cash-flow-benchmarks.md（现金流健康基准）、knowledge/shared/industry-benchmarks-manufacturing.md（制造行业基准）。
  3. 专家的 KNOWLEDGE.md 改为只引用不复制。"关于现金流健康的判断标准，参见 knowledge/shared/cash-flow-benchmarks.md。"——而不是在自己的文件中复制一份。
  4. 新增 scripts/sync-expert-knowledge.sh。运行该脚本时，检查所有专家的 KNOWLEDGE.md 中引用的共享知识是否与 knowledge/shared/ 同步。不同步时报错并提示运行 sync。

20.3 Agent 配置化注册

当前问题

ExpertDispatcher 在代码中硬编码了 8 位专家的调度逻辑（src/l3/expert-dispatcher.ts L484-489）。如果有人想加第 9 位专家（例如"供应链顾问"），他需要修改 ExpertDispatcher 的代码。如果有人想在某次诊断中跳过某位专家，也需要修改代码。这导致专家数量的增加和编排逻辑的调整都变成了一次代码变更，而不是一次配置变更。

参考实现

Claude for Financial Services 中，每个 Agent 通过 agent.yaml 声明式配置：包含使用的模型、system prompt 文件路径、tools、skills、子 Agent。Agent 的加载和执行逻辑和具体的 Agent 配置解耦——新增一个 Agent 只需要新增一个目录和一份 yaml 文件，不需要改执行引擎的代码。

  2. ExpertDispatcher 改为从配置加载，而非代码硬编码。读取 expert/expert-registry.yaml，根据配置决定哪些专家参与本次诊断。新增专家时只需添加配置条目，无需修改调度代码。

  4. 保留现有专家 IDENTITY.md / SOUL.md / RULES.md / TOOLS.md / KNOWLEDGE.md / THEORY.md / STAGE_LOGIC.md / CROSS_EXPERT.md 的目录结构。配置化注册是最外层添加的声明层，不改变专家内部的文件结构。
