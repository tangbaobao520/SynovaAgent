一、产品定位：数字化麦肯锡

1.1 一句话定义

Synova 是一个驻扎在企业内部的数字化麦肯锡咨询师。它持续观测企业全量数据，主动发现问题，自动诊断根因，提出可落地的方案，跟踪执行效果。最终决策永远是人做的——Synova 是辅助决策，不是替代决策。

1.2 本质区别：多 Agent，不是单 ChatBot

Agent 数量118+ 专家 Agent 并行协作
主动性被动，一问一答被动，等待指令主动巡逻，发现问题后自动推送
记忆会话级（关闭即丢失）项目级企业级持久记忆 + 跨会话进化
输出文本代码 + 文本结构化判断 + 因果推理 + 可执行方案 + 状态变更
专业知识通用知识编程知识8 个垂直领域专家（战略/组织/财务/技术/营销/商业模式/行动/知识）

1.3 交互核心原则

#原则说明
1Agent 主动，人被通知Agent 主动发现问题并推送。人不需要每天登录系统。
2分层信息，逐层深入摘要层 → 卡片层 → 对话层。不是一次性堆砌所有数据。
3对话是交付方式，不是产品本身分析由机器独立完成，但判断的说服、方案的协商、执行的推动——只能在对话中完成。
4多专家透明协作用户只看到一个 Synova。后台 8 位专家按需唤醒。每条判断标注贡献专家，但不抢占对话主导权。
5不替人决策专家结论冲突时，呈现双方论据，让人选择。不替人做价值判断。
6专家池可扩展新增专家 = 加目录 + 5个Markdown文件 + keywords配置。路由逻辑不变。从8个到20个专家的迁移成本为零。

1.4 Synova 的两层价值：诊断 + 落地

Synova 不只是"帮你发现问题"。发现问题只是第一层。第二层是把诊断结论转化为可落地的 Agent 方案。这两层对应同一个骨架：agent + skill + data。

层次诊断层（我们在做的）落地层（新增）
agent8 位专家按需唤醒，分析企业数据，找出增长瓶颈帮企业识别：哪些工作可以被 Agent 替代？哪些必须人做？→ 产出 Agent 适用性扫描报告
skill46 哨兵 + 专家工具，自动计算 61 个指标帮企业识别：哪些重复流程可以封装成 skill？依赖什么工具？→ 产出 skill 清单和接入方案
data哨兵读取 GraphStore 本体数据，产出 Finding帮企业整理数据：什么格式？缺什么字段？如何最小成本让 Agent 读懂？→ 产出字段映射和数据补齐方案

和传统咨询的本质区别：传统咨询给完方案就走，效果靠企业自觉。Synova 的哨兵持续监控——"三个月前落地的审批自动化 skill，效果在衰减了，因为供应商那边的数据格式变了"——主动发现，主动提醒，持续跟踪。GA 不是"给完方案就撤"，是用诊断数据来证明这个 skill 为什么需要，用 L0 进化来验证这个 skill 落地后的效果。

二、用户角色与权限模型

角色核心能力对 Agent 的使用可见范围数量级
企业对接人执行力 + 内部协调。不需要行业经验。收到推送 → 审阅方案 → 确认或调整 → 推动落地与自己部门相关的哨兵信号和专家结论。跨部门数据仅聚合值。每企业 1-5人
GA (Growth Advisor)行业经验 + 诊断判断力。上传客户数据 → 审阅和纠正所有专家判断 → 多轮讨论 → 确认交付方案该客户的所有数据、所有专家结论、历史诊断记录。少量，一人服务 10-20 客户
企业主决策权。不需要操作界面。定期收到执行摘要。V2 阶段可通过简化视图查看健康评分。企业全量数据聚合。飞轮仪表盘 + CEO摘要。每企业 1人
部门负责人本部门管理权。与自己部门相关的对话。可独立与 Synova 协作处理部门级问题。本部门完整数据。跨部门仅聚合值。随企业规模
权限自动注入: 每次对话时，Agent 根据登录身份自动注入权限过滤。不依赖人手动选择角色。不同角色对同一问题的回答粒度不同——CEO 问"现金流健康吗"→ 回答"当前充足，但6个月后存在缺口风险"。CFO 问同样的问题 → 回答包含具体数字和趋势对比。

三、核心交互：对话优先 + 专家透明

3.1 设计哲学

用户始终在一个对话界面中与 Synova 交互。他不需要打开多个窗口、不需要手动选择专家、不需要学习任何内部术语。对话是唯一的交互入口。

但他应该可以感知到背后有多个专家在协作——不是通过界面复杂度，而是通过回答的质量、深度和可追溯性。当他问财务问题时，他得到的是财务专家的深度分析；当他追问战略影响时，战略专家无缝接管。这个切换对用户是透明的。

3.2 三种界面形态

形态适用角色交互方式优先级
Codex 式对话界面 (Electron 桌面应用)GA、企业对接人对话为主，左侧工作区列表，右侧可展开的专家面板和行动跟踪P0 — 核心产品界面
IM 接入 (飞书/钉钉/企业微信)企业主、部门负责人、普通员工在 IM 中 @Synova 提问，Agent 在 IM 中回复。主动推送也走 IM 通道P1 — 降低使用门槛
终端 TUI开发阶段调试现有 ink 组件保留，仅用于内部开发和演示P3 — 不对客户交付

3.3 对话界面的关键交互

专家身份标识（折叠，不抢占注意力）

每条 Agent 回复的末尾，默认折叠显示参与分析的专家。点击可展开查看每位专家的方法论和置信度：

Synova 你的现金流在过去两个季度持续收紧。 根因是应收账款周期从30天延长到59天—— 主要因为客户A的采购系统迁移导致付款流程中断。 建议：与客户A协商临时缩短付款周期， 同时在下一份合同中加入逾期罚息条款。 ▸ 财务顾问主导 · 战略顾问交叉验证 · 置信度 78% [展开查看分析依据] [追问战略影响]

专家冲突时的呈现

当两个专家的判断矛盾时，不模糊化处理。结构呈现双方论据，让决策者选择：

Synova 关于市场扩张的可行性，专家意见存在分歧： ■ 战略顾问：应该现在扩张 论据：市场窗口正在关闭，竞品已进入。 延迟6个月将失去先发优势。 置信度：72% ■ 财务顾问：现金流撑不住 论据：扩张需要6个月现金储备，当前仅3个月。 如果客户A的回款再延迟，缺口达40%。 置信度：85% 这是需要你来做的决策。我的分析不能替你做价值判断—— 但我可以提供每个选项的概率和后果： [先保现金流，暂缓扩张] [先扩张，寻求短期融资]

四、专家按需唤醒机制

4.1 核心原则

不是每次对话都调用所有专家。专家按需唤醒，协作完休眠。专家池可以无限扩展而不增加单次对话的复杂度。

4.2 三层唤醒机制

用户输入: "为什么现金流在恶化？" │ ▼ Layer 1: 关键词匹配 (0ms, 0次LLM调用) ├─ strong关键词 "现金流" → 直接唤醒 finance专家 └─ 路由完成，进入Layer 1响应 │ ▼ (如果Layer 1无匹配) Layer 2: 轻量意图分类 (1次LLM调用, 小模型, <0.5s) ├─ 返回: { primary: "finance", secondary: ["strategy"], confidence: 0.9 } └─ 如果 confidence < 0.6 → 降级为 knowledge 兜底 │ ▼ (专家推理过程中触发) Layer 3: 专家自主调度 └─ ExpertReport.crossReferences: [{expertType:"strategy", reason:"验证战略影响"}] → 系统自动唤醒 strategy 专家 → 异步执行，不阻塞当前对话 → 结果作为"补充分析"追加
层级机制延迟LLM调用命中率
Layer 1关键词匹配 (DEFAULT_DOMAIN_KEYWORDS)0ms0~70%
Layer 2轻量LLM意图分类<500ms1 (小模型)~25%
Layer 3专家自主调度 (crossReferences)异步按需~5%

4.3 追问时的专家延续

用户追问时，自动保持上一轮的专家上下文。不需要重新路由：

追问类型行为
用户追问同一话题 ("那应收账款的具体数据呢？")继续由上一轮的主责专家回答，不重新路由
用户质疑 ("这个判断不对，我们现金流很好")主责专家重新评估 + 自动唤醒交叉验证专家复核
用户切换话题 ("那战略方面怎么办？")Layer 1/2 重新路由 + 上一轮专家的结论作为 context 注入新专家

4.4 专家池扩展

新增一个专家（如供应链专家）的步骤：

  1. 创建 expert/supply_chain/ 目录，填写 5 个 Markdown 文件
  2. 在 expert-registry.yaml 中加一行配置
  3. 在 domain-keywords.ts 中注册 supply_chain 的关键词
  4. 重启生效。路由逻辑零改动。

从 8 个专家到 20 个专家，路由代码一行不改。Layer 2 的 LLM 分类器从 Registry 动态读取可用专家列表，自动扩展候选池。

4.5 身份感知回答

同一个问题，不同角色提问，回答的粒度和内容不同。这不是事后过滤——是专家推理时就已经根据调用者身份调整了分析深度和可见数据范围。

角色问"现金流健康吗？"得到的回答
企业主"当前充足，但6个月后存在缺口风险。主要原因是应收账款周期从30天延长到59天。建议关注客户A的回款进度。GA 最近下调了融资约束哨兵的告警阈值——[查看详情]。"
→ 完整数据 + 趋势预测 + GA操作提示
CFO (部门负责人)"应收账款周期59天（行业平均30天），每月延迟回款约120万。根因是客户A采购系统迁移。建议临时缩短付款周期 + 下份合同加入逾期罚息。"
→ 本部门完整数据 + 跨部门聚合
市场总监 (部门负责人)"当前现金流紧张，主要受应收账款影响。市场部暂无直接财务风险，但如扩张计划需要额外预算，建议与 CFO 讨论时机。"
→ 本部门视角 + 跨部门聚合值
普通员工"公司目前财务状况稳定。如有具体费用相关的问题，建议咨询你的部门负责人。"
→ 无具体数字，无趋势分析

实现机制

用户提问 → Layer 1/2: 专家路由 (与身份无关，路由逻辑一致) → Layer 2.5: 身份注入 (在system prompt中注入用户角色和可见数据边界) → 专家推理 (基于过滤后的数据和权限约束生成回答) → 回答生成 (不同角色看到不同粒度)

身份注入在 Layer 2 和 Layer 3 之间完成。路由逻辑不受身份影响——CFO 和市场总监问同一个问题，都会路由到 finance 专家。但 finance 专家收到的 system prompt 中包含了"当前提问者是 CFO，你有权访问完整财务数据"或"当前提问者是市场总监，财务数据仅提供聚合值"。

五、对话中的多专家协作

5.1 专家生命周期

闲置 ──(用户提问/哨兵告警)──► 唤醒 │ ▼ 分析中 (独立LLM调用, 自己的system prompt) │ ▼ 出结论 (ExpertReport) │ ┌─────────────┼─────────────┐ ▼ ▼ ▼ 结论被采纳 结论被质疑 需要其他专家 → 休眠 → 重新分析 → crossReferences → 唤醒协同专家 → 交叉验证 → 休眠

5.2 专家的"沉默"机制

不是所有专家都应该在对话中说话：

专家说话规则
strategy, finance, org, tech, marketing, business_model前台专家。被唤醒后可主动在对话中发言。用户可见。
action延迟专家。在所有前台专家完成分析后自动唤醒。综合所有结论，产出行动清单。不说话——只在右栏行动跟踪中产出结构化条目。
knowledge后台引擎。永远不直接与用户对话。在后台持续将信息结构化存入知识库，供其他专家在推理中查询引用。仅在 qa-router 按需调度时提供检索结果。

5.3 专家间通信协议

专家之间不通过 LLM 自由对话——那会导致不可控的幻觉。通信是结构化的：

通信方式格式示例
交叉引用ExpertReport.crossReferences[]{expertType:"finance", reason:"需要验证战略方案的资金可行性", priority:"critical"}
冲突标记ExpertReport.conflictingSignals[]{dimension:"市场扩张", myFinding:"应该扩张", potentialOpposingExpert:"finance", reason:"现金流限制"}
企业事实更新AgentMemoryStore (type:enterprise_fact)finance 更新了 Financial.cash 的值 → 所有其他专家下次读取时自动获得新值

5.4 结论追溯

任何一条 Agent 判断，用户都可以追问来源：

用户："这个判断哪来的？" Synova： 这条判断来自财务顾问的推理链： 1. 数据事实：应收账款周转天数 59天 (来源: ERP系统, 7月数据) 2. 对比基线：行业平均 30天, 你三个月前是 28天 3. 根因分析：客户A的采购系统迁移 → 付款流程中断 (来源: 客户A的项目通知邮件, 6月15日) 4. 影响计算：每月延迟回款约 120万, 占月现金流的 15% 方法论：KZ融资约束指数 + 现金流压力测试 置信度：78% (中等偏高 — 因客户A的恢复时间存在不确定性)

六、四级响应模型

6.1 为什么需要分级响应

不是每次对话都需要专家推理。把 LLM 调用当免费资源，50个员工同时对话会瞬间打爆 API 限额。分级响应的本质是：把昂贵的 LLM 推理留给真正需要深度分析的问题，日常信息查询走缓存和检索。

级别触发条件专家调用响应时间适用场景
Level 1: 即时回答信息查询、哨兵缓存命中0 次 LLM<1s"上个季度客户流失率是多少？" "报销流程是什么？"
Level 2: 单专家分析因果推理、简单判断1-2 次2-5s"为什么现金流在恶化？" "市场定位需要调整吗？"
Level 3: 多专家协作用户主动要求深度分析、GA发起诊断、用户质疑Level 2结论2-4 次5-15s新工作区创建、跨领域问题分析
Level 4: 全量诊断Cron定时、GA主动发起、哨兵检测到critical信号8+ 次后台1-5min周度/月度完整诊断。异步执行，完成后推送

6.2 LLM 调用队列

┌─────────────────────────┐ │ LLM Call Queue │ │ 全局最大并发: 8 │ └──────────┬──────────────┘ │ ┌──────────────────────┼──────────────────────┐ │ │ │ Level 1 (0 calls) Level 2 (1-2 calls) Level 3-4 (queued) 直接返回缓存 优先级: HIGH 优先级: NORMAL 不限流 限流时排队 后台异步执行

一个50人企业，日均专家级LLM调用预估：

类型日均次数LLM调用
信息查询 (Level 1)~2000
简单分析 (Level 2)~2020-40
深度分析 (Level 3)~36-12
全量诊断 (Level 4)1次/周8 (后台)
日均LLM调用总数~30-50次

DeepSeek 的 50 并发限制绰绰有余。即使企业规模扩大到 200 人，日均调用量约 200 次，单 provider 仍然可承受。

七、多员工并发与企业规模弹性

7.1 会话模型

Synova 实例 (1个) │ ├─ 共享企业上下文 (GraphStore + AgentMemoryStore + 哨兵缓存) │ └─ 所有专家、所有会话读取同一份企业数据 │ └─ 一次全量诊断(Level 4)的结果，所有会话可见 │ ├─ 会话1 (CEO) ─ messages[] 独立 ├─ 会话2 (CFO) ─ messages[] 独立 ─ 权限: 财务完整,人事聚合 ├─ 会话3 (市场总监) ─ messages[] 独立 ─ 权限: 市场完整,财务聚合 └─ ... 更多会话

对话历史隔离：每个员工有自己的 messages[]，互不可见。
企业事实共享：哨兵运行结果、专家结论、企业事实层——全公司共享，一套数据。
权限注入：不同角色的会话看到不同粒度的同一份数据。CEO 看到具体数字，部门负责人看到聚合值。
专家是共享资源：不跟任何会话绑定。专家推理结果写入 AgentMemoryStore，任何会话都可以引用。

500+人按事业部拆 GraphStore 租户 + 共享专家引擎按 orgId 路由

拆的是数据隔离，不拆专家能力。专家引擎是共享的，跨事业部的问题仍然可以被检测。按部门部署只在 500+ 人规模才需要，且是数据隔离驱动的，不是性能驱动的。

十、上下文管理：共享历史 + 专家视角过滤

10.1 共享对话历史

一个工作区内，所有专家共享同一份对话历史。finance 专家说完后 strategy 专家接管——strategy 能看到 finance 之前的所有分析和用户对 finance 结论的反馈。不会出现"刚才财务顾问已经确认的数据，战略顾问又问一遍"。

10.2 专家视角过滤

共享历史中的每一条消息，根据当前活跃专家的身份进行视角过滤：

消息内容finance 看到的strategy 看到的
用户上传了 ERP 导出数据完整财务字段可见仅聚合财务指标可见
finance 专家确认现金流缺口 40%完整推理链可见结论 + 置信度可见，计算细节折叠
用户说"市场部觉得定价没问题"全文可见全文可见

这不是安全权限（那是 RBAC 的事），是认知负荷管理。strategy 专家不需要看 KZ 指数的完整计算过程，只需要知道 finance 的结论和置信度。

10.3 压缩策略

当对话轮次超过阈值时，不简单地滑动窗口丢弃旧消息。而是保留结构化结论，压缩对话原文：

  • 专家已确认的结论 → 永久保留，压缩为一句摘要
  • 用户已确认的事实 → 永久保留，同步写入企业事实层
  • 对话原文 → 超过 20 轮后，仅保留最近 5 轮完整原文，其余保留摘要
  • 跨工作区引用 → 被引用工作区的核心结论自动注入当前对话上下文

十一、GA 管理界面

11.1 GA 的核心职责

GA (Growth Advisor) 是拥有行业经验的专家，借助 Synova 将经验放大、服务更多客户。GA 的核心能力是行业判断（用经验校准 Synova 的分析）和客户信任（建立长期关系，推动方案落地）。GA 不是技术操作员，不需要编写代码或配置系统。

11.2 GA 工作流

1. 客户导航 → 选择客户或新建 2. 数据导入 → 上传企业数据（文件/API/手动输入） 3. 触发诊断 → Level 4 全量诊断（异步后台运行） 4. 审阅结论 → 查看所有专家的分析报告 5. 纠错和讨论 → 标记错误判断，与专家对话修正 6. 确认交付 → 生成客户报告，推送企业对接人 7. 持续跟踪 → 监控执行进度，接收哨兵异常推送

11.3 GA 的多专家监督视图

GA 界面中有一个专家仪表盘，展示最近一次诊断中所有专家的工作状态：

11.5 GA 行为监控与主动告警

Synova 不会等企业主自己发现问题。GA 的任何可疑行为，系统主动通知企业主和企业对接人。无论 GA 是平台方人员还是第三方，出现严重违规行为都会通知 Synova 官方。

恢复机制

GA 做了有问题的事 → Synova 自动检测 → 实时通知企业主 + 企业对接人 → 严重级别: 同步通知 Synova 官方 → 企业主登录 → 查看完整审计日志（按时间线排列，不可删除） → 企业主判断: ├─ 误操作 → 回滚到该操作之前的快照 │ (L0 rule-version-manager 支持) │ └─ 恶意行为 → 撤销该 GA 的所有访问令牌（一键操作） 锁定该 GA 操作期间的数据（不删除，标记"待审核"） Synova 官方后台标记该 GA 账号状态 → 如为平台方 GA: 内部调查 + 重新分配客户 → 如为第三方 GA: 永久封禁 + 通知受影响的其他客户

关键设计：GA 的所有写操作都有叠加层——纠错不覆盖原结论，阈值调整不删除旧阈值，数据更新保留版本链。这意味着任何 GA 操作都可以被回滚，且回滚不会丢失原始数据。企业主永远拥有最终数据主权。

方案是活文档，不是静态报告

传统咨询交付 PDF——三个月后无人记得。Synova 的方案是可跟踪的活文档：

  • 方案里的每个 skill 对应右栏的一个行动项，有状态（待执行/执行中/已完成/效果衰减）
  • 哨兵自动对比落地前后指标——"审批流程落地前协作摩擦指数 0.7，当前 0.3"
  • 效果衰减时主动告警——"三个月前落地的审批自动化 skill，效果在衰减"
  • 落地后产生的新数据反哺 L0 进化——该企业的落地经验沉淀为行业知识，服务下一个同行业客户

十三、企业事实层

企业事实层是专家回答一致性的基础。设计保持不变，根植于 AgentMemoryStore (L4) 的 enterprise_fact 类型 + 版本链。

v2.0 新增: 每条事实标注来源专家（哪个专家在什么时间、基于什么证据确认的）。当事实被新诊断推翻时，自动标记 supersededBy，保留完整变更历史。多专家对同一事实有分歧时，不覆盖——并存，标记为"待 GA 裁决"。

十五、企业内部知识库

保留 v1.9 设计。Synova 部署在企业内部，天然就是企业的知识中枢。任何员工在任何界面都可以向 Synova 提问，Agent 根据提问者的角色自动过滤可见范围。回答包含三部分：① 直接答案、② 数据来源和时间、③ Agent 的判断（可选，涉及诊断时附加）。

v2.0 新增: 知识库查询结果自动标注"此信息由 knowledge 专家检索，最近更新于 X 天前"。如果 knowledge 专家发现高频查询的企业信息尚未结构化，自动生成知识条目草稿，提交 GA 审核。

十六、多专家记忆系统

16.1 记忆归属

AgentMemoryStore 当前已有 MemoryType: fact / preference / decision / pattern / entity / enterprise_fact。v2.0 新增专家归属——每条记忆标注来源：

字段示例
source'expert:finance', 'expert:strategy', 'user_feedback', 'sentinel:F1'
tags['diagnosis:d_20260701', 'confidence:0.85', 'cross_validated:strategy']

16.2 记忆生命周期

事件记忆操作
专家产生新结论 (confidence ≥ 0.7)写入 type:'expert_finding'，TTL=下次同维度诊断
用户纠错某结论写入 type:'user_correction'，关联原 finding。原 finding 的 confidence 被调整
新诊断推翻了旧结论旧 finding 标记 supersededBy → 新 finding。保留完整推理链
同一专家连续 3 次被纠错同类型问题触发 L0 进化：该专家的 RULES.md 或阈值被提议调整

记忆归属是进化的前提。没有归属，进化引擎无法判断"是 strategy 专家的判断需要校准，还是 finance 专家的阈值需要调整"。

十七、工具调用的专家隔离

17.1 问题

每个专家在 expert-registry.yaml 中声明了自己的工具列表。但当前实现中工具注册是全局的——任何专家理论上可以调用任何工具。这导致 strategy 专家可能调用 cashflow_analysis 读取财务明细——既是安全问题，也是认知污染（strategy 不应该看到原始财务数据）。

17.2 隔离方案

级别规则
工具声明每个专家在 expert-registry.yaml 中声明 tools: [cashflow_analysis, unit_economics]。未声明的工具不可调用。
数据权限工具返回的数据根据调用专家的 DataAccessPolicy 自动过滤。finance 专家调用 cashflow_analysis → 返回完整财务数据。strategy 专家调用同一工具 → 返回聚合值。
跨专家工具调用strategy 专家可以在 ExpertReport.crossReferences 中请求 finance 专家调用 cashflow_analysis——但不是 strategy 自己调，是调度系统将请求转发给 finance 专家执行，结果注入 strategy 的下一轮推理。

十九、诊断节奏与建议边界

19.1 不替人决策

保留 v1.9 的设计。Synova 的输出是结构化选项 + 概率 + 后果，不是"你应该做 X"。尤其是：

  • 涉及人的决策（裁员、调岗）→ 只提供数据和影响分析，给选项，不给裁决
  • 涉及战略方向的决策 → 提供多个 Scenario 的对比，不推荐单一方案
  • 涉及法律/合规的决策 → 标记"需要专业法律意见"，不提供判断

19.2 诊断频率

诊断类型频率触发方式
日常哨兵巡逻每小时Cron 自动
Level 4 全量诊断每周一次（默认）Cron 自动 + GA 手动触发
专项深度分析按需用户对话中触发（Level 3）

不会每天轰炸用户。只有真正的异常才会主动推送到人。

二十二、验收标准

22.1 核心体验验收

  1. 按需唤醒: 用户问财务问题时，只有财务专家被唤醒。用户问战略问题时，战略专家接管。整个对话过程中最多 2 位专家并行。永远不会出现 8 个专家同时回答一个简单问题。
  2. 专家透明: 每条 Agent 回复可追溯到贡献专家及其置信度。用户不需要知道"ExpertDispatcher"这个词，但需要知道"这个判断谁做的、有多可靠"。
  3. 冲突呈现: 两个专家判断矛盾时，不模糊处理。同时呈现双方论据和置信度，让人选择。
  4. 对话不中断: Level 3/4 的专家调度是异步的。用户不会看到"正在等待战略顾问分析..."的加载条。回答先出，补充分析后追加。
  5. 多员工隔离: CEO 和 CFO 同时对话，互不干扰，互不可见对方的历史。但两者看到的企业数据是同一份。

22.2 规模验收

  1. 10 个专家: 将专家池从 8 个扩展到 10 个（新增供应链专家 + 法务专家），路由代码零改动。新专家通过 Layer 1 关键词匹配自动激活。
  2. 50 个并发用户: 50 个员工同时对话，最长响应延迟不超过 5 秒。LLM 调用队列不溢出。
  3. 10 个企业客户: 一个 GA 同时管理 10 个客户。切换客户时，专家上下文完全隔离，企业数据不串。

22.3 部署验收

  1. 零命令安装: 下载安装包 → 双击 → 填写企业名称和行业 → 开始使用。全程无终端。
  2. IM 自助绑定: 老板在飞书中扫码 → 自动绑定 → 立即可以 @Synova 提问。
v2.0 设计基线: 本 PRD 定义了 Synova 多 Agent 交互的完整体验。实现时不需要一次完成所有 Phase。Phase 1-3（按需唤醒 + 分级响应 + 专家透明）是最小可行产品，做完即可交付第一个 GA 试用。后续 Phase 根据反馈迭代。
与 v1.9 的关系: v1.9 是单 Agent 对话诊断的产品设计。v2.0 保留了其中仍然正确的部分（产品定位、用户角色、事实层、知识库、建议边界、文件化扩展），重写了基于多 Agent 架构的核心交互（对话中的专家协作、按需唤醒、四级响应、上下文管理），新增了多 Agent 特有的设计（专家生命周期、沉默机制、通信协议、记忆归属、工具隔离、规模弹性）。
