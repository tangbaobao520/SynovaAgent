战略复盘：失败 × 成功 × 核心价值

2026-06-04 · 对 SynovaAgent 产品战略的真实评估

这不是一个技术分析。这是我们对自己产品最诚实的审视。

一、如果项目失败，最大的原因会是什么？

🥇 原因 #1：产品假设了一个不存在的高频场景

"持续运行的组织医生" vs "一次性的组织咨询报告"

这是最大的 existential risk。组织诊断是一个低频、高客单价的行为——传统咨询公司卖的是"一年一次的报告+工作坊"。Synova 的产品定位是"持续运行的数字孪生"，但如果用户想不到"每天上去看一下"，它就退化成了一个漂亮的 API 后端。

类比：卖了一台跑步机给用户，用户用它挂了一周衣服。跑步机功能完好，但用户不需要每天跑步。

验证问题：用户每周打开几次？每次看什么？什么事件会触发他回来？如果这三个问题答不上来，产品就是工具不是习惯。

🥈 原因 #2：5 个数据源 → 0 个真实数据

核心护城河是"多源交叉验证"，但连接器全是存根

当前 5 个连接器（飞书、GitHub、Jira、NemoClaw、财务）全部返回 []——Phase A 存根。产品最大的差异化能力是"飞书聊天+GitHub commit+Jira ticket 在你组织本体图上交叉验证"，但用户永远看不到这个能力兑现。

如果你去跟客户 demo，只能展示"这是我们的 SOG 架构"（一张架构图），而不是"这是你们团队的真实数据呈现出的诊断结论"。

最痛心的失败路径：代码写了很多、架构设计很完美、但用户的数据从未真正流入过系统。然后创始人问"为什么用户不用"，答案是"因为用户看不到自己的数据"。

🥉 原因 #3：技术完美主义 → 产品交付延迟

铁律 40 条很好，但如果每次提交要跑 10 道门禁，交付速度会被自己拖死

当前有 pre-commit（6 道硬阻断）、commit-msg 格式检查、pre-push（tsc + vitest + iron-laws）。加上铁律 0-2 要求 spec → test → impl → wire → review → merge。对于一个 0.1.0 版本的产品来说，这个流程可能太重了。

风险在于：团队花了 80% 的时间在满足流程要求上，只有 20% 的时间在真正构建用户需要的功能。然后竞争对手用 Python 脚本三天就接了一个飞书连接器，你用 TypeScript + 4 道审计 + 接线验证花了三周。

🏅 原因 #4（隐藏）：LLM 成本被低估

六阶段诊断 × 5-15 次 LLM 调用 × 每天 3 次自动诊断 = 每天 $3-6/客户

如果一个客户每月支付 $200，LLM 成本占 $30-60（15-30%），毛利率 70-85%。这对 SaaS 来说是健康的。但如果客户只有 50 人团队呢？$200 的 ARPU 可能过高。如果降到 $50/月，LLM 成本就吃掉 60-100%——不经济。

Prefix Cache 优化（50 倍降价）能缓解这个问题，但也只能缓解。单位经济模型（unit economics）需要仔细验证。

🎯 综合失败概率评估

失败原因概率可预防？建议行动

二、如果项目成功，最可能的因素是什么？

🥇 成功因素 #1：组织本体图（SOG）是真正的护城河

14 种节点 + 10 种边 + RDF 三元组 + 双时序——这不是随便能复制的

SOG 不是一个"知识图谱"的营销词汇。它是一个真实可运行的、有严格 schema 的、针对组织诊断场景设计的本体系统。当一个客户的飞书聊天记录、GitHub commit、Jira ticket、财务报表都在同一个图里用同一种数据模型表达时——这就是数据网络效应。

竞争对手可以做一个 AI 诊断工具。但要做一个能同时在组织图里表达"张三是李四的上级"、"前端团队的技术债务高"、"Q2 研发成本增长 20%"——并且在它们之间找到 causal link——这就是另一个量级的事情。

SOG 是 3 年内最难复制的东西。不是因为它用了什么尖端技术，而是因为数据建模的工程量和组织理论的知识密度。

🥈 成功因素 #2：多源交叉验证的信任飞轮

不是"AI 说的"，是"数据说的"

企业采购 AI 产品的最大障碍是信任。"你怎么证明你的诊断是对的？"

Synova 的回答是：每条结论都有证据链。"我们发现团队协作有问题——因为飞书聊天记录显示跨部门消息回复率低（37%）、GitHub 显示跨团队 PR review 周期长（平均 4.2 天 vs 同部门 1.5 天）、Jira 显示依赖阻塞频繁（每周 3.2 次）。"

这个信任飞轮是自我加强的：

  1. 第一次诊断 → 用户验证发现是否准确
  2. 准确 → 用户信任并采纳建议
  3. 采纳后改善可测量 → 用户对下一次诊断更有信心
  4. 更多数据接入 → 诊断更精确 → 飞轮加速

🥉 成功因素 #3：On-prem 部署 + 数据主权

中国 SaaS 市场的一个残酷现实是：大客户要求私有化部署

Synova 从第一天就是 on-prem 架构。SQLite、嵌入式 NATS（未来）、无外部依赖。这不是一个"我们之后可以私有化"的承诺——这是一个已经实现的架构特性。

对于金融、政府、国央企客户来说，这可能是采购决策的第一关。数据不出内网=可以买。数据出内网=不能买。很多 AI 产品在第一关就被淘汰了。

🏅 成功因素 #4：DeepSeek 的经济学

V4 Flash：$0.14/1M input tokens + 1M 上下文 + 中文原生优势

如果 Synova 构建在 GPT-4o 上（$2.50/1M input），每次诊断的 LLM 成本是 $0.05-0.10。在 Flash 上加上 Prefix Cache（$0.0028/1M 命中），每次诊断的成本降到 $0.001-0.005——相差 50 倍。

成本优势 = 定价优势 = 更大的目标市场。50 人的小团队 $50/月也覆盖得了 LLM 成本。

三、哪些是我们始终坚守的长期价值和核心？

🛡️ 核心价值 #1：证据溯源不可妥协

"每条诊断结论都有来源"

这是产品最核心的信任机制。任何时候都不应该出现"AI 幻觉式诊断"——专家 Agent 说"团队有问题"，但说不清数据来源。必须每条 hypothesis 都能追溯到：

  • 哪条聊天记录？
  • 哪个 GitHub commit？
  • 哪个 Jira ticket？
  • 置信度多高？
  • 有没有其他专家的矛盾信号？

不能妥协的场景：如果为了省成本，跳过 EvidenceStore 直接让 LLM 给出结论——这就破坏了信任飞轮。宁可诊断慢一点、贵一点，也不能丢失证据链。

🛡️ 核心价值 #2：五层架构的边界纪律

L1 不知道 L3 的存在，L5 不知道 L2 的存在

铁律 39（五层架构边界）不是文档里的装饰——它是保证系统长期可维护性的核心设计原则。当有一天系统扩展到 100 万行代码时，如果有人试图从 TUI 直接调 SQLite，架构纪律会阻止他。

这个纪律允许：

  • L1（交互层）全部重写（从 TUI 到 Web 到 IM）不影响下层
  • L4（本体层）的存储从 SQLite 换成 SurrealDB 不影响上层
  • L3（分析层）的专家算法可以独立演进

🛡️ 核心价值 #3：降级透明

不行就是不行，不假装行

铁律 11 和 31（静默降级禁止 + 降级信号传播）可能是 40 条铁律中最重要的两条。当一个模块出问题时：

  • 不能悄悄返回 null
  • 不能返回 mock 数据
  • 不能假装"可能可以"
  • 必须打日志
  • 必须传播 degraded 标记
  • 前端必须展示 DegradedBanner

这在企业级产品中是信任的基础。IT 负责人宁愿看到一个"专家 Agent 不可用"的警告，也不愿看到一个看起来正常但实际上错了的诊断报告。

🛡️ 核心价值 #4：用户数据主权

客户的 data 永远是客户的，不进我们的训练集

这是 On-prem 部署的必然推论，但也是产品道德层面的选择。联邦进化（差分隐私 + 安全聚合）不是为了技术炫技——它是让产品既能从全局学习中受益，又不必牺牲任何客户的数据隐私。

不能妥协：

  • 即使技术上很难，联邦进化也必须实现差异化隐私
  • 绝不能出现"收集客户数据训练模型"的商业模式
  • 数据清洗、脱敏、隔离是产品能力的一部分，不是之后加的

🎯 一句话总结核心价值

Synova 不是一个 AI 产品，是一个基于多源数据证据的组织诊断系统。 AI 是推理引擎，不是数据来源。 证据是核心资产，不是模型参数。 架构纪律是长期保证，不是开发负担。

四、对创始人的最终建议

如果时间只剩 3 个月如果时间有 12 个月
  1. 做出一个飞书生产连接器（3 天）
  2. 用真实数据跑通一个诊断（3 天）
  3. 找到 3 个客户的真实团队跑一遍（2 周）
  4. 验证"用户每周回来一次"的假设（4 周）
  1. Prefix Cache 优化降成本（2 天）
  2. GitHub + Jira 连接器（1 周）
  3. 前端图可视化（1 周）
  4. 架构稳定性修复（2 周）
  5. 然后回到左栏的第 3-4 步

注：以上分析基于 2026-06-04 的代码审计和架构研究。失败概率是估算，不是预测。SOG 的设计质量和铁律体系是真实优势，不是自我安慰。
