SynovaAgent 技术栈语言方案与交付计划

目标：本月交付第一个客户（100人企业，含生产/销售/运营团队）
原则：渐进式改造，不推倒重来。能用 TypeScript 做完的先用 TS，Python 只用在 TypeScript 生态明显欠缺的地方。

一、五层架构语言决策总表

层模块语言理由
L1 交互层
 Web 对话界面（SSE）TypeScriptExpress 路由 + 内联 HTML，TS 天然适合
 TUI（neo-blessed）TypeScript已有实现，继续维护
 图可视化（Cytoscape.js）TypeScript前端库，必须是 JS/TS
 IM 适配（飞书/企微）TypeScriptHTTP Webhook，TS 足够
 报告仪表板TypeScript前端 HTML 渲染
L2 编排层
 六阶段状态机TypeScript核心流程控制，TS 类型安全优势
 ConversationEngineTypeScript已有 568 行实现，继续演进
 事件总线 (EventBus)TypeScript轻量内存事件，TS 足够
 HookRunnerTypeScript同步钩子链，TS 足够
 SSE 流式推送TypeScriptExpress SSE，TS 标准模式
 SessionManager 压缩TypeScript纯逻辑算法
L3 分析层
 6 专家 Agent（ReAct 循环）TypeScript核心逻辑已有，调 LLM API 为主
 ExpertAutonomyEngineTypeScript已有实现，LLM 调用驱动
 QualityFirewallTypeScript规则校验，TS 足够
 29 计算模块TS + Python简单规则 TS，统计分析 Python
 因果推断（Gear 3）Pythonstatsmodels，TS 无替代
 社区检测（Leiden）Pythonnetworkx，当前 TS 实现只做了 Phase 1
 模板进化引擎TypeScript状态管理 + 规则引擎，TS 足够
L4 本体层
 SOG Schema（14 节点 + 10 边）TypeScript已有 @synova/sog-core 包
 GraphStore（SQLite）TypeScriptbetter-sqlite3 同步操作性能好
 EntityResolverPython 逐步迁移中文 NLP：当前 Jaccard 不可靠，先用拼音编码垫底，长期用 sentence-transformers
 诊断图查询（BFS/社区）TypeScript查询逻辑，TS 足够
L5 数据层
 飞书连接器Python已有官方 Python SDK（feishu），TS 版手动 fetch 效率低
 GitHub 连接器PythonPyGithub SDK 成熟
 Jira 连接器Pythonjira 库成熟
 知识摄取（PDF/DOCX/Excel）TypeScript 首发可用 @synova/knowledge-ingest 现有 TS 实现先跑通，后续 Python 优化
 SessionStore（SQLite）TypeScript已有实现✅
 StorageBackendTypeScript已有实现✅
跨层支撑
 ToolRegistryTypeScript已有实现，需扩展多执行模式
 Extension RegistryTypeScript已有 @synova/extension-registry 包骨架
 Connector-RegistryTypeScript + Python注册中心 TS，具体连接器 Python
 Provider 层（LLM）TypeScript已有实现✅
 错误类型枚举TypeScript已有实现✅
 监控/指标TypeScript已有 MetricsCollector✅

四、Docker 部署规格

# Dockerfile
FROM node:20-slim AS base

# 安装 Python 3.12 + 依赖
RUN apt-get update && apt-get install -y python3.12 python3-pip
COPY requirements.txt /app/
RUN pip3 install -r /app/requirements.txt

# 安装 Node 依赖
COPY package.json package-lock.json /app/
RUN npm ci --production

# 复制代码
COPY . /app/
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s \
  CMD curl -f http://localhost:3000/health || exit 1

CMD ["node", "dist/index.js"]

六、哪些模块先用 TypeScript 跑通，后续再迁 Python

原则：本月交付优先，不在第一个版本中引入 Python 的模块先 TypeScript 简单实现。
等产品有真实用户跑起来后，分批迁移到 Python 获得更好的性能和生态。
模块本月策略后续迁移到 Python 的时机
知识摄取（PDF/OCR） 用现有 @synova/knowledge-ingest TS 包 当需要扫描件 OCR 或复杂版式解析时
实体解析（中文） 拼音编码 + 编辑距离（TS，2 小时实现） 当 Jaccard 替代性能不足时 → sentence-transformers
社区检测 现有 TS 简化版 Leiden（已实现） 当 O(n⁴) 查询慢到用户能感知时 → networkx
因果推断 LLM-as-Causal-Engine（Prompt 工程） 当需要统计显著性时 → statsmodels Granger
飞书连接器 直接用 Python，SDK 太成熟了不等了 —

八、需要你决策的事

⏳ 本月交付前的关键选择：
  1. 飞书连接器先用 Python 做（推荐）还是等 TypeScript SDK 成熟？
    → 我用 Python 做，3 天交付。如果用 TS，SDK 需要手动封装 API，2 周都未必稳定。
  2. 知识摄取是优先做 PDF 上传，还是先接飞书文档？
    → 建议先做 PDF 上传（通用），飞书文档 API 对接放入第 2 个月。
  3. 客户的生产/销售/运营团队——他们主要是中文数据还是中英混合？
    → 影响实体解析方案选型。纯中文用拼音编码就够，中英混合可能需要 sentence-transformers。
  4. 客户有没有 IT 支持？还是说部署全靠我们远程协助？
    → 影响 Docker 部署方案复杂度。如果有 IT，可以给 docker-compose + 部署文档。如果没有，可能需要提供远程桌面协助。
