稳定性与可靠性评估

SynovaAgent 组织智能诊断系统 · 2026-06-04 · 故障模式与性能基线

⚠️ 核心结论：产品稳定性评分 2/10 — 零灾难恢复，零持久化状态，多处资源泄漏

当前系统在以下灾难性场景中完全无防护：进程崩溃后内存状态全丢失（活跃诊断、证据、专家贡献全部消失）、数据库损坏无恢复措施（也无备份）、有状态操作不支持重入（activeConsultations Map 没有重启后的恢复路径）。唯一值得肯定的是异常处理模式（多数 try/catch 有日志）和审计日志已实现 SQLite 持久化。

3. 内存与资源泄漏审查

3.1 逐项泄漏风险

组件泄漏风险严重程度
EventBus.on() 订阅者on() 返回 unsubscribe 函数，但调用者可能忘记调用 → 订阅者持久存在中
Rate Limiter Map每 30s 清理过期条目。如果大量不同 IP 在 30s 窗口内访问，Map 会持续增长中
Active Consultations Map客户端断开连接后条目不清理（没有监听 close 事件）高
SSE 连接客户端断开后没有清理 Response 对象 → 内存中残留大量写入流高
Cron Scheduler每次 schedule() 创建 timer → timer 被 scheduleNextTick 替换，旧 timer 通过 clearTimeout 清理——设计正确低
DiagnosisOrchestrator 实例Map 在诊断完成后 delete 条目，但如果 Promise 未正确 resolve/reject，条目残留中
Express 路由闭包每个请求创建闭包，请求完成后 GC 回收——标准 Express 行为，无泄漏低
globalThis.__synovaAlerts全局数组，无上限增长——每次推送 alert 都 append，从不清理高

3.2 活跃诊断泄漏修复方案

// 当前：客户端断开后 activeConsultations Map 条目不清理
// 修复：监听 close 事件

// routes/diagnosis.ts 第 148-152 行
const active: ActiveConsultation = {
  consultId, teamId, phase: 0, aborted: false,
  orchestrator, events: [],
};
activeConsultations.set(consultId, active);

// 添加断线清理
req.on('close', () => {
  active.aborted = true;
  // 延迟删除（给最终事件有时间推送）
  setTimeout(() => {
    activeConsultations.delete(consultId);
  }, 5000);
});
