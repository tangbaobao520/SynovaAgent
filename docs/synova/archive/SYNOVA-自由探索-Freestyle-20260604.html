自由探索研究报告

SynovaAgent 组织智能诊断系统 · 2026-06-04 · 可观测性、CI/CD、合规与隐藏假设

⚠️ 核心结论：产品面临的最大风险不是技术，而是"产品-市场-渠道"三角

在阅读了整个代码库后，最大的担忧不是 L4 三大断层或 L5 连接器存根——这些都是可工程化解决的问题。最大的风险是：产品假设了一个还没有真实用户验证的使用场景。组织诊断是一个低频、高客单价的行为，而 Synova 的定位是"持续运行的组织医生"——如果用户想不到"每天上去看一下"，产品就变成了"一次性咨询报告"。

1.2 推荐的 OTel 架构

// Phase 1: 关键诊断流程手动打点（无 OTel SDK，最小依赖）
// 每个诊断阶段作为一个 span
interface DiagnosticSpan {
  traceId: string;
  spanId: string;
  parentSpanId?: string;
  name: string;              // "diagnosis-phase-0", "llm-consult", "graph-query"
  startTime: number;
  endTime?: number;
  status: 'ok' | 'error' | 'degraded';
  attributes: Record<string, string | number>;
}

// 在 ConversationEngine 中注入 tracing
class TracedConversationEngine extends ConversationEngine {
  async processMessage(input: string): Promise<ProcessResult> {
    const span = this.tracer.startSpan('process-message', { input });
    try {
      const result = await super.processMessage(input);
      span.end({ status: 'ok' });
      return result;
    } catch (err) {
      span.end({ status: 'error', error: err.message });
      throw err;
    }
  }
}

3. 多语言支持技术方案

3.1 当前状态

全部代码硬编码中文：TUI 界面、LLM Prompt、内联 HTML、日志消息、错误文案。

3.2 分阶段多语言方案

阶段内容范围技术方案
Phase 1UI 文本 i18n前端界面、TUI 界面、错误消息i18next + 中文/英文 JSON 资源文件
Phase 2LLM Prompt i18n诊断 Prompt、Expert PromptPrompt 模板按语言切换（建议保留中文 Prompt 作为主版本）
Phase 3用户内容语言检测输入识别 + 输出语言匹配内容语言自动检测，输出回应用户语言
重要决策：LLM Prompt 的语言 中国团队的组织数据主要用中文表达。LLM Prompt 用中文可以获得更好的诊断精度（减少翻译损失）。建议：Prompt 全程保留中文，UI 界面独立 i18n。英文版本的用户数据也以中文 Prompt 分析，但 UI 展示翻译为英文。

4. 行业合规性要求

行业核心要求当前合规状态需要的工作
金融数据本地化、操作审计、加密存储⚠️ 部分合规AuditLog 已有 ✅；数据分类已有 ✅；需加密静态存储（SQLite 加密）
医疗HIPAA（美国）/ 等保（中国）❌ 不合规需要 BA 协议、更严格的访问控制、数据最小化
政府物理隔离、等保三级❌ 不合规需要完全离线部署、无外部 LLM 调用、国家密码算法
欧盟GDPR：可解释权、删除权、数据可移植⚠️ 部分合规诊断结果需要可解释的推理链 ✅；需实现"被遗忘权"（删除用户所有数据）
On-prem 部署是最好的合规特性。Synova 的数据一直留在客户网络内，不需要通过 SOC2/ISO27001 认证（除非客户要求）。这降低了初期合规成本。但一旦客户要求认证，当前架构需要较大调整。

5. 真实发现：代码中隐藏的最大问题

5.1 工程文化问题

  1. "写完了但没接" 的根因：铁律 1-7 和接线铁律的存在本身就是一个信号——接线失败发生了至少 6 次，且每次都通过"单元测试绿了"来验证完成。这表明团队（包括 AI 编码者）倾向于认为"组件通过单元测试 = 任务完成"，忽略了组件最终需要被用户使用。
  2. 两层编排系统的存在：DiagnosisOrchestrator + PhaseStateMachine + ModuleRunner 等 ~600 行代码是一个完整的通用编排框架，但 ConversationEngine 完全不使用它。这意味着要么是设计方向变更（从通用编排到轻量对话引擎），要么是并行开发的两条线从未合并。无论哪种，~600 行死代码需要处理。
  3. DRY 原则被违反：ConversationEngine 的 Phase 0 逻辑是 Phase0Engine 的"内联复制"。两个功能相似的实现并存，但都不完整。

5.2 对创始人的反馈

建议 STOP 做的事：
  • 停止不接线就声称"完成"——接线验证和单元测试一样重要
  • 停止创建"以后再说"的存根——FeishuConnector 的 119 行代码中 117 行是类型声明 + 注释 + 骨架，实际 fetch 全是空数组。这是视觉上的"完成"但实质上是零交付
  • 停止平行建设两套编排框架——选定一个方向，删除另一个
建议 START 做的事：
  • 先让一个诊断走得通：从"用户输入组织名称"→"飞书取数据"→"SOG 建图"→"专家分析"→"产出报告"的全链路，哪怕是最粗糙的版本。这比 10 个完美但分离的模块有价值 10 倍
  • 写一个用户旅程测试：模拟"CTO 登录→输入团队名→看到诊断报告"的完整流程。这个测试通不过 = 产品不可用
  • 决定 L4 是核心还是备胎：当前 SOG（14 节点 + 10 边 + 双时序）的设计质量很高，但代码中的使用率极低。要么把它做深（所有诊断数据都写入图，所有专家查询都读图），要么承认它只是文档中的一个设计愿景

5.3 被低估的风险

风险为什么被低估实际影响
LLM Provider 依赖"有很多 Provider 可以切换"每个 Prompt 都是针对 DeepSeek 优化的，换到其他模型需要重新调参。Model Gateway 的设计不错，但 prompt 的依赖更深
中文 NLP 评估指标"Jaccard 可以用"铁律 29 已明确警告 Jaccard 对中文语义一致性检测接近随机。但 entity-resolver.ts 仍在使用。这不是"之后优化"的问题——这是当前所有实体解析结果都不可信
"持续诊断"的资源消耗"诊断是 API 调用"每个完整的六阶段诊断需要 5-15 次 LLM 调用（$0.5-2/次）。如果 200 人团队每天触发 3 次自动诊断，每天 LLM 成本 $3-6 美元（约 $100-200/月）。这是可接受的，但如果乘以 1000 个客户，基础设施成本会快速上涨
数据输入质量"连接器能拿到数据"飞书/GitHub/Jira 的数据本身是混乱的、不一致的、充满噪声的。组织结构图可能过时 6 个月，GitHub commit message 可能是 "fix bug"，Jira ticket 可能长期无人更新。连接器只是第一步，数据清洗和标准化是隐藏的巨大工程

7. 建议做的 3 件事

  1. 立刻写一个"用户旅程测试"：不通过不能声称 v0.1.0。这个测试应该启动服务、发送诊断请求、验证 SSE 流式收到事件、查询 SOG 图确认节点已创建。这是铁律 3 的实现。
  2. 做一次"LLM Provider 兼容性测试日"：用 DeepSeek、OpenAI、通义千问、GLM 分别跑同一个诊断用例，看结果是否一致。这会揭示出多少 Prompt 是 Provider 特定的。
  3. 删除或接线所有死代码：Phase0Engine、DiagnosisOrchestrator、LLMPhaseExecutor、ModuleRunner、SubAgentCoordinator。要么删除，要么接线到 ConversationEngine。当前 5 个组件共存但都不完整的状态是最坏的中间态。
