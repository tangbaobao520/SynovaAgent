## L4 防线缺口收割

> "本次发现的问题（若有），控制塔哪一道防线本该拦住？为什么没拦住？缺什么？"

### 发现 1: python 失效时门禁静默漏拦，且测试在该环境下假绿（4 过/2 败之外的真实提交场景 = 直接放行）

**本该拦住的防线**: 铁律 24（异常处理审计——catch 必须 log + degraded）+ 铁律 48（测试非空壳）。
**为什么没拦住**: ①`|| echo 0` 把"检查未执行"与"检查通过=无真实认领"压缩成同一个 0，fail-open 设计吞掉了执行失败信号；②测试的 assert_exit 只断 exit code，测试 runner 无前置依赖自检（command -v python3），依赖缺失时用例 1/3 失败信息被误读为"代码 bug"而非"环境失效"；③D329 的 PYBIN 修复用 `command -v` 探测存在性，但存在≠可用（Windows Store stub 损坏场景仍静默）。
**缺什么**: ①GENUINE 检查的三态输出（1=真实认领 / 0=无认领 / 显式 degraded=检查未执行）——python 退出码非预期时必须显式告警；②测试 runner 的前置依赖自检，依赖缺失时整套测试显式 FAIL 而非逐个用例误判。

### 发现 2: DS4/DS7 自报与物理证据不符（豁免覆盖 2/4 声称 4/4；pre-commit 通过无记录声称"全过"）

**本该拦住的防线**: task brief Done 标准的 verify 命令机制（DS1-DS7 每条带 verify）+ 铁律 0-2 接线验收。
**为什么没拦住**: verify 命令只断言"脚本 exit 0"，不断言"声称的覆盖项 ↔ 实际用例"的映射——DS4 的 verify 是跑同一个不含 Revert/无暂存用例的脚本，verify 通过 ≠ 声称成立。DS7 的 verify（跑 pre-commit-check.sh）在提交时点之后无法回验，bypass.log 是唯一的持久证据而它缺条目。
**缺什么**: ①Done 标准的"声称覆盖项 → 测试用例编号"显式映射检查（自报无法自证，这正是 D202 交叉对比存在的理由）；②post-commit 的记录存在性对账——每次 commit 后校验 bypass.log 是否追加了对应条目，缺失即告警。

### 发现 3: bypass.log 记录空窗内发生提交（ea1cb71 落窗），执行证据链断裂无人发现

**本该拦住的防线**: 控制塔执行记录机制（pre-commit-check.sh → bypass.log）。
**为什么没拦住**: 记录机制依赖 hook 真实执行——hook 未触发/异常/--no-verify 时无记录，且无任何对账方发现"有 commit 无记录"。
**缺什么**: git log vs bypass.log 的定期对账检查（可入 CI 或 cron）：每个新 commit 必须在 bypass.log 有对应 COMMITTED/BLOCKED 条目，缺失即 P1 告警。
