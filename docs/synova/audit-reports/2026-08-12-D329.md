### 发现 1: tag V4.7.1 指向被历史重写抛弃的孤儿提交（f685fa0），发布锚点与分支内容断裂

**本该拦住的防线**: 版本编排机制（D319 git-tag-auto：commit 后自动打 tag）。
**为什么没拦住**: auto-tag 在 f685fa0 提交时（20:52）正确触发；但随后发现首提交漏了 `git rm --cached .claude/current-brief`（dev doc §3.1 配套操作），于是改写历史重提交为 dc369fd（22:40）——**重写动作没有任何机制去检测"已有 tag 指向被抛弃的提交"**。pre-commit 12 组不管 tag，pre-push 3 项不管 tag 祖先关系。
**缺什么**: tag-祖先校验门禁（pre-push 或 CI）：`git merge-base --is-ancestor $(git rev-list -1 <最新tag>) HEAD` 为假 → 告警/阻断；或 auto-tag 侧增加"tag 后禁止 amend/重写本批次提交"的物理提示。

### 发现 2: dc369fd（改写后的提交）无 bypass.log 记录——同型证据缺口第二次发生

**本该拦住的防线**: 控制塔执行记录机制（pre-commit-check.sh → bypass.log）+ D328 审计 L4 收割 #3 提出的对账建议。
**为什么没拦住**: D328 审计（同日早些时候）已明确指出"git log vs bypass.log 无对账方"，建议未落地，24 小时内同一缺口再次吞掉证据（这次是改写提交）。记录机制依然只在 hook 真实执行时写入，改写/补提交是否走 hook 无从证实。
**缺什么**: 对账机制仍未建立——每个新 commit 必须在 bypass.log 有对应条目，缺失即告警（可入 CI 或 cron 的 `git log` × `bypass.log` HASH 集合差检查）。**建议升级优先级：同一缺口连续两个任务复现，已符合"防线系统性失效"特征。**

### 发现 3: resolver `--session` / current-brief.<sid> 机制完整、测试齐全，但生产零调用——"接线验收"在 dev doc 层面就写浅了

**本该拦住的防线**: 铁律 0-2 Step 5 WIRE CHECK（新 export 必须有生产调用方）+ dev doc §5 接线要求。
**为什么没拦住**: dev doc §5 对接 current-brief.<sid> 的验证标准是"attach.py 写入 + .gitignore 忽略 + resolver 读取"——三条都物理为真，门禁全过，但没有任何一条要求"**至少一个生产调用方传 `--session`**"。实现满足了写浅的验收标准，机制事实上闲置（attach 写了 7 个文件也无人读）。这不是实现偷工，是**验收标准的系统性盲区**：接线检查只验"能力存在"，不验"能力被消费"。
**缺什么**: WIRE CHECK 标准升级——新机制必须列出 ≥1 个生产路径调用点（测试调用不计入），dev doc §5 模板与 pre-commit 组 4（接线完整性）都应加入"消费者 grep"维度。
