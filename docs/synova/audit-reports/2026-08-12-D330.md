## L4 防线缺口收割

> "本次发现的问题（若有），控制塔哪一道防线本该拦住？为什么没拦住？缺什么？"

### 发现 1: bypass.log 证据链缺口连续第三个任务复现（4-5 个提交无记录），且发生在"hook 记录机制确认在线"的同一晚

**本该拦住的防线**: 控制塔执行记录机制（pre-commit/post-commit → bypass.log）+ D328/D329 两份审计报告的 L4 对账建议。
**为什么没拦住**: 对账建议两次入报告、两次进"CT 队列"，但队列没有物理执行体——没有脚本在"有 commit 无记录"时告警。21:24 D331 的 BLOCKED 还在写日志，21:40 D330 的 COMMITTED 就消失——说明记录不是"机制坏了"，而是**存在一条不产生记录的合法提交路径**（无论它是 --no-verify、绕过 post-commit 的工具，还是 hook 环境差异），而没有任何对账方去发现它。
**缺什么**: 不再建议"排队"，直接给出最小物理实现：CI 或 cron 跑 `comm -23 <(git log --format=%H -20 | sort) <(grep -oE 'HASH=[a-f0-9]{40}' .claude/bypass.log | cut -d= -f2 | sort)`——输出非空即告警。**这已是第三次：防线失效本身应升级为 P0 级流程事项。**

### 发现 2: resolver exit 1 承载两种语义（正常无 brief / 执行失败），修复降级诚实性时引入误标告警

**本该拦住的防线**: 铁律 32（错误分类强制：.code/.phase/.retryable）的设计意图。
**为什么没拦住**: 铁律 32 约束的是 TS 侧 Error 子类；shell 侧没有对应的错误分类契约——resolver 头部注释明写"无可用 brief → exit 1"，但 rc=1 同时也表达"python 死了"。D330 捕获 rc 时无法区分两者，只能选择"都当失败提示"（现状）或"都当无 brief 静默"（修复前）。
**缺什么**: shell 组件的最小错误分类契约——resolver 差异化退出码（0=有 brief / 2=无 brief / 1=真失败），一行改动，消除二义。

### 发现 3: 用例 10 标题声称"仍拦截 exit 1"、断言却是 exit 0——测试语义与测试行为脱节

**本该拦住的防线**: 铁律 48（测试非空壳）+ Agent 自检 5 问。
**为什么没拦住**: 现有检查只验证"断言存在且真实执行"，不验证"用例标题/注释声称的行为 = 断言的行为"。实现者在发现 resolver 先死后正确地修正了断言（degraded + exit 0），但标题和头注释停留在原设计意图——测试通过，语义漂移无人发现。
**缺什么**: 测试评审/自检增加一项："用例标题 = 断言行为"一致性——尤其是 red 基准用例，标题描述的就是被防的事故，标题失真 = 防线自述失真。
