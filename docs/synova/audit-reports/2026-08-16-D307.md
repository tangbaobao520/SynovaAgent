## 六、L4 防线缺口收割

> "本次发现的问题，控制塔哪一道防线本该拦住？为什么没拦住？缺什么？"

### 发现 1：已审计产物的未审计双版本自由流通（P1-1）

**本该拦住的防线**: memory/dual-source-fraud 教训 + 审计报告入库规范（docs/synova/audit-reports/ git 跟踪）
**为什么没拦住**: v1 虽已入库（5b78a1c），但同一扫描任务在不同 worktree 的**二次执行**产出 v2 时，没有任何机制对账"同路径报告的 verdict 是否漂移"——扫描/审计类产物的正确性锚定在执行时的物理证据上，重复执行产生不同结论本应触发复核，现实中两个版本各自流通互不感知。
**缺什么**: 同路径报告类产物的**双版本对账**——凡 docs/synova/audit-reports/ 下文件出现第二个版本（不同 worktree/分支），入库前必须 diff verdict 计数并附变更理由；未审计版本不得进入任何可合并分支。

### 发现 2：证据链记录滞留工作副本不提交（P1-2/P2-1）

**本该拦住的防线**: D331 check-bypass-log 对账（pre-push 门禁 7）
**为什么没拦住**: 门禁读的是**工作副本** bypass.log——补记写在工作副本即放行，但没有任何机制要求该记录随提交传播。bypass.log 是 tracked 文件，其记录层却在各 worktree 各自为政（主仓/wt-d307/wt-scan 三份内容互不相同），每台机器独立拦一次、补一次、放一次。
**缺什么**: ① 证据记录（含补记）的**随提交要求**——完成推送的 session 必须把 bypass.log 变更一并提交；② 补记强制 BACKFILL 标记（与真实 COMMITTED 记录可区分）；③ 或门禁改读"全 worktree bypass.log 并集"（机制较重，次选）。

### 发现 3：生产首跑缺失被测试通过掩盖（P2-6）

**本该拦住的防线**: 铁律 7（Done 标准：结果可见）+ DS 验收设计
**为什么没拦住**: DS4 接受"测试覆盖 finish 路径"作为完成证据，生产真实 finish 被显式推迟（"留待扫描任务收尾后执行"）但**没有 backlog 条目、没有 deadline、没有跟踪**——推迟即遗忘。与 D366 审计 L4 发现 2（闭环 schema 建成但零数据流转）同根：代码真实 ≠ 能力被真实使用过。
**缺什么**: 交付报告中凡"留待后续执行"的推迟项，必须同步落 backlog 文件（含触发条件与 owner）；或对这类能力增加"生产首跑证据"DS——首次真实 finish 执行后回写一条记录闭环。
