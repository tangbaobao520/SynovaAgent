## 六、L4 防线缺口收割

> "本次发现的问题，控制塔哪一道防线本该拦住？为什么没拦住？缺什么？"

### 发现 1：stream 混流——故障注入测试缺"失败时间点"维度（P1-1）

**本该拦住的防线**: CT-30 故障注入契约（dev doc §4 RED 场景）+ 铁律 48 边界条件
**为什么没拦住**: 交付的 17 个测试（含"stream failover"用例）的故障注入全部发生在**首 token 之前**（连接级/立即抛错）——这恰是 chain stream 能正确处理的唯一时间窗。失败时间点维度（连接前 / 首 token 后 / onComplete 前）不在任何测试契约模板里，而 chain 的 `onToken` 直通实现注定了中途失败必混流。
**缺什么**: 故障注入测试契约增加**失败时间点枚举**——凡 stream/分页/批量类接口的降级测试，必须覆盖"部分数据已交付后失败"场景；此类接口的 failover 语义（重试=内容重来）需在契约层显式定义"混流是否可接受"。

### 发现 2：K3 自身误判——"不存在"与"未接线"的区分（审计侧收割）

**本该拦住的防线**: K3 审计协议项 1（接口真实性）的 grep 验证规范
**为什么没拦住**: 扫描审计时我用 `fallback` 单一关键词 grep src/providers/，1 处注释命中即得出"failover 代码不存在"；但 createProviderChain 用的是 "chain/尝试下一个" 词汇，CircuitBreaker 用的是 "CircuitBreaker"——**关键词未覆盖近义实现词汇**，且未追 `createProviderChain` 的调用方清单（零生产调用方 = 未接线，而非不存在）。功能结论侥幸正确（生产确无 failover），机制判断错误。
**缺什么**: K3 审计协议增补一条：能力存在性判定前，grep 关键词必须含**近义词簇**（如 failover|chain|circuit|retry|切换|降级）；且"零生产调用方的已实现能力"必须单独立项为"建成未接线"（铁律 37 死代码视角），不得并入"不存在"。本次 D363 dev doc 的修正（§2 实测 + §7 自检"不是照抄 K3"）是该机制的正面样本。

### 发现 3：任务 ID 复用（P2-1）

**本该拦住的防线**: TASK-ROUTING / session registry 的任务 ID 分配
**为什么没拦住**: D363 先被用于"审计登记"提交（5b78a1c，08-14），后被分配给"LLM failover"任务（08-16）——ID 分配无唯一性校验，证据链（bypass.log TASK_ID 索引）与仪表盘按 ID 对账时两任务混同。
**缺什么**: 任务 ID 分配处的唯一性检查（注册新 ID 前 grep 既有 brief/提交/bypass.log 是否已占用）。
