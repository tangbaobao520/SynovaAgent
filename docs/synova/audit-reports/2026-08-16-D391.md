## 三、关键发现详述

### P1-1 federated 兜底 = 写入即蒸发，201 假性成功（归因: implement）

`a60e45f:src/routes/admin-knowledge.ts:53-55`：
```ts
function getPipeline(): FederatedPipeline {
  return federatedPipeline ?? new FederatedPipeline();
}
```
- `FederatedPipeline` 状态存于**实例内内存 Map**（src/services/federated-pipeline.ts:53 `private store: Map<string, FederatedKnowledge> = new Map()`）。
- 生产环境 `setFederatedPipeline` **无任何调用方**（`git grep` 全 src/ 仅定义处）→ 模块级 `federatedPipeline` 永远 null → **每个 handler 调用都 new 一个新实例**。
- 后果：`POST mark-shareable` 写入实例 A（响应后销毁）→ 201 Created；随后 `GET federated/pending` 读全新实例 B → 永远空列表。**恒 503 被换成了恒空——且返回成功，比 503 更具欺骗性**（铁律 5"后端能力 ≠ 用户可用功能"+ 铁律 11 静默降级精神）。
- **T6b 测试把该缺陷写成规格**："不注入 → 200 空列表"被断言为正确行为（admin-knowledge.test.ts T6b）。
- 修复一行：`federatedPipeline ??= new FederatedPipeline()`（惰性单例），并加"写后读回"跨请求持久性断言。getStore 同款建议（每请求 `new KnowledgeStore(getDatabase())` + initSchema DDL 重跑，功能正确但有开销，P2-2）。
- 注：knowledge 审批三个端点（pending/approve/reject）走 DB，不受此缺陷影响——它们是本修复的真实收益面。
