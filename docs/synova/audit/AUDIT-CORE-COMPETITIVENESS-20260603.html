执行摘要

本次审计覆盖 synova-agent（23K 行）和 @synova/engine-core（vendor，305 文件，~35K+ 行）两个代码域。核心结论：Synova 的五层架构设计文档（ARCH-20/21）是高质量的，但代码实现与设计文档之间存在严重偏差。

主要发现：

  • ⚠ L4→L5 层间违规：synova-agent 的 L4 代码（l4/graph-bridge.ts）直接调用 L3 的 CLI (cli.ts) 逻辑，L2 编排层（conversation-engine.ts）绕过 orchestrator 直接调用了动态 import 的 L4 图查询。跨层调用链条至少有 3 处未通过抽象接口。
  • ⚠ SOG 双时序实现不完整：graph-store.ts 的 valid_to/valid_from 在 schema 中有定义，但 deleteNode() 方法在软删除 triples 的同时 物理 DELETE 了 graph_nodes 行（第 267 行）——违反了 SOG 架构的"永不删除"原则。
  • ⚠ 交叉验证引擎不存在：没有独立的 CorroborationEngine 类。证据矛盾检测仅存在于一个 O(n²) 的简单置信度差值比较（evidence/index.ts），没有 LLM 验证、没有证据链追踪、没有跨维度交叉验证。
  • ⚠ 联邦进化系统虽完整但未接线：FederalReporter、GlobalAggregator、RuleDeployer、RuleUpdater 代码完整（差分隐私、签名验证、灰度分组全部实现），但它们从未被任何入口调用——生产代码中没有一个 import 或 schedule 这些类的实例。
  • ⚠ engine-core 作为 vendor 包过于庞大：305 文件全部在一个单体包内，无 npm 子包拆分。synova-agent 通过 file:../server/vendor/... 直接引用，导致跨包依赖全部通过相对路径（../../pipeline/diagnosis/graph-store）完成，独立发布不可行。

总体评级：38/100 — 架构设计存在严重断层，核心竞争力实现不完整。需立即修复 7 个 Critical 问题方可进入下一阶段开发。

第一部分：五层架构合规性

1.1 L2 编排层 vs L3 分析层边界

CRITICAL ARCH-VIOL-001: ConversationEngine 绕过 orchestrator 直接调用诊断模块
src/agent/conversation-engine.ts:567 — DiagnosisOrchestrator 动态 import 来自 engine-core
L2 的 ConversationEngine.startDiagnosis() 使用 await import('../../../../server/vendor/.../diagnosis-orchestrator') 直接加载 L3 的诊断编排器。正确的路径应是 L2 → L2 的 Phase0Engine/ModuleRunner → 通过 SubAgentCoordinator 代理到 L3。当前代码绕过了自身 synova-agent 的编排层组件（orchestrator/diagnosis-orchestrator.ts 和 module-runner.ts），直接跳到 engine-core 的 L3。
证据：第 567-570 行——import('../../../../server/vendor/@synova/engine-core/src/pipeline/diagnosis/diagnosis-orchestrator')。注意这是运行时动态 import，不经过 TypeScript 的模块解析路径。
修复要求：L2 必须通过 SubAgentCoordinator 接口调用 L3，禁止 L2 代码直接动态 import L3 类。
HIGH ARCH-VIOL-002: L3 的 SubAgentCoordinator 存在于 synova-agent 而非 engine-core
src/orchestrator/subagent-coordinator.ts — 存在于 L2 目录
子 Agent 调度器（SubAgentCoordinator）存在于 synova-agent 的 src/orchestrator/ 目录，但它应属于 L3 分析层（engine-core）。L2 的编排组件（orchestrator/）应只包含 ModuleRunner、PhaseStateMachine、HookRunner 等流程控制组件，而不应包含专家子 Agent 的调度和策略逻辑。
证据：src/orchestrator/subagent-coordinator.ts 导入了 ExpertAutonomyEngine（L3 组件）、QualityFirewall、DataAccessPolicy。它还包含了 6 个子 Agent 的完整 Prompt 构建逻辑——这全部是 L3 的职责。
修复要求：将 SubAgentCoordinator 移至 engine-core 的 L3 层，L2 只保留调用接口（interface 或抽象类）。

1.2 L3 分析层 vs L4 本体层边界

CRITICAL ARCH-VIOL-003: L3 诊断模块直接读取原始数据源（绕过本体层）
engine-core/src/pipeline/diagnosis/airbyte-ontology-adapter.ts（整个文件）
Airbyte 适配器（FeishuAirbyteAdapter, GitAirbyteAdapter）直接从数据源适配器读取原始格式数据，然后尝试写入本体图。它们的 airbyteOntologySync() 方法应该只向 L4 输出标准化的 OntologyEvent，但实际代码中包含了数据格式转换、节点创建和边缘创建的逻辑——同时跨越了 L4 和 L5 的职责。
证据：FeishuAirbyteAdapter 和 GitAirbyteAdapter 被 engine-core 的 index.ts 直接导出（第 685 行），意味着 L3 可以直接调用它们。再看调用链：assembleFullDiagnosis() → 直接访问数据源。
修复要䏡：Airbyte 适配器应被严格隔离到 L5 边界，只向 L4 输出 OntologyEvent。L3 模块只能通过 GraphStore 接口访问数据。
HIGH ARCH-VIOL-004: EvidenceManager 绕过本体图直接访问 GraphStore
engine-core/src/pipeline/diagnosis/evidence-manager.ts:58-80
syncEvidenceToGraph() 方法直接调用 this.graphStore.createNode() 和 this.graphStore.queryNodes()，没有通过 L4 的 GraphBridge 或 ReportGraphAdapter 接口。证据管理属于 L3，直接操作图存储违反了 L3→L4 的单向边界。
证据：第 58-80 行——证据被直接写成 Event 节点，并使用 queryNodes 检查维度。正确的路径是 L3 EvidenceManager → L4 GraphBridge.upsertEvidence() → GraphStore。
修复要求：EvidenceManager 应通过 GraphBridge（L4 接口）写入图，禁止直接引用 GraphStore。

1.3 L4 本体层 vs L5 数据层边界

MEDIUM ARCH-VIOL-005: ontology-adapter.ts 同时在两重职责
engine-core/src/pipeline/diagnosis/ontology-adapter.ts — ingestDocument()
ingestDocument() 函数同时承担文档解析（L5 职责）和图节点创建（L4 职责）。它没有通过适配器接口将原始文档转换为标准 OntologyEvent。
证据：该函数直接从文档内容提取字段，然后调用 graph.createNode()。正确的设计是：文档解析器 → OntologyEvent → GraphStore。

全部 engine-core 文件

证据：grep 发现 ../../sog/sog-core-schema 被 10+ 个诊断文件引用。

3.1 多源交叉验证 实现度: 25%

CRITICAL CV-001: 无独立的 CorroborationEngine 类
src/evidence/index.ts:48-101 + engine-core（无对应文件）
核心竞争力要求"从多个独立数据源自动发现指向同一结论的信号"。但代码中没有 独立的 CrossValidationEngine 或 CorroborationEngine。现有实现只有：
(a) src/evidence/index.ts 中的 CorroborationEngine.detectContradictions()——O(n²) 双循环，仅比较置信度差值 > 0.3。

两种实现都不是真正的交叉验证——没有 LLM 验证信号语义一致性，没有证据链追踪，没有跨维度的概率校准。第一个只是简单置信度比较，第二个只是"API 是否可达"。
核心竞争力 1 的核心能力缺失。诊断结论本质上仍是单一数据源推测，而非多源交叉验证。
HIGH CV-002: Phase 3 根因分析中未调用任何交叉验证
engine-core/src/pipeline/diagnosis/ — 整个 Phase 3 链路
assembleFullDiagnosisV3() 或同类的 Phase 3 函数在生成根因假设时，没有调用交叉验证逻辑。证据链只依赖于单个数据源的单次置信度评分。
证据：引擎中不存在"至少 3 个独立数据源"的硬性门禁。铁律要求 minSources = 3 在实际运行中未被强制检查。

3.2 组织本体图 (SOG) 实现度: 55%

CRITICAL SOG-001: deleteNode() 物理删除节点（违反"永不删除"原则）
engine-core/src/pipeline/diagnosis/graph-store.ts:262-267
SOG 架构要求"永远不物理删除节点/边，只能通过 valid_to 软删除"。但 deleteNode() 方法的实现是：
第 265 行：this.db.prepare('UPDATE graph_triples SET valid_to=? WHERE ...').run(...) ✅ 对 triples 做了软删除
第 267 行：this.db.prepare('DELETE FROM graph_nodes WHERE id=? AND graph=?').run(id, graph) ❌ 从 graph_nodes 表物理删除
物理删除后，getNodeAtTime() 将无法追溯历史节点，双时序功能失效。这违反了 SOG 的核心架构原则。
HIGH SOG-002: 多租户 graph 参数检查不一致
engine-core/src/pipeline/diagnosis/graph-store.ts
createNode() 和 createEdge() 有 if (!graph) throw ... 的强制检查（第 83、150 行），但 queryNodes() 的 graph 参数是 graph?: string（第 136 行）——可选。如果调用方忘记传 graph，查询结果可能跨租户。
证据：queryNodes 的 graph 参数为可选。第 140 行的 SQL 未强制过滤 graph = ?。
HIGH SOG-003: synova-agent 的 L4 组件未使用 engine-core 的 GraphStore
src/l4/graph-bridge.ts — 重新定义了 GraphStore 接口
synova-agent 的 src/l4/graph-bridge.ts 第 19-34 行重新声明了 GraphStore 接口（完整的 14 个方法签名），与 engine-core 的 graph-store.ts 中的 GraphStore 接口完全平行。两个接口从未被验证是否一致。
证据：graph-bridge.ts 第 19-34 行——export interface GraphStore { createNode(...); createNodes(...); ... }。这 100% 是 engine-core graph-store.ts 接口的复制品。
如果 engine-core 的 GraphStore 接口变更（如添加参数或修改方法签名），synova-agent 的 L4 层不会获得任何编译错误，运行时可能静默失败。
MEDIUM SOG-004: Q: queryNodes 在多租户场景中的 graph 过滤
engine-core/src/pipeline/diagnosis/graph-store.ts
确认：queryNodes 和 queryEdges 在多租户模式下对 graph 参数的过滤不一致。
查询逻辑分析：queryNodes 的 condition builder 中没有加入 AND graph = ? 的条件。需要更仔细的 SQL 分析确认。但 createNode() 强制 graph 不可为空（第 83 行），而 queryNodes() 的 graph 是可选参数（第 136 行），这会潜在导致调用方绕过租户隔离。
如果调用方未提供 graph，查询会返回所有租户的节点——这是跨租户数据泄漏风险。
