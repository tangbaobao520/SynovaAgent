二、架构差距（根本性问题）

2.1 状态管理

Synova tui-v2 — ❌ React 状态 + 全局变量

// 三套状态并存:
// 1. React useState (TuiState)
const [state, setState] = useState<TuiState>(...);

// 2. 模块级全局变量
let accumulatedThought = '';    // thinking.ts
let thoughtExpanded = false;
let spinnerTimer = null;

// 3. Map ref (可变引用)
const expertStatusMapRef = useRef(new Map());

// 4. status bar 独立管理
process.stdout.write(...);  // 直接写 stdout

CodeWhale — ✅ 单向数据流 + 状态机

// 1. 唯一事件源: UiEvent 枚举
enum UiEvent {
  KeyPressed(char),
  PromptSubmitted(String),
  ResponseDelta(String),
  ToolStarted(String),
  ToolFinished(String),
  Tick,
}

// 2. 纯函数 reducer
impl UiState {
  fn reduce(&mut self, event: UiEvent) -> Vec<UiEffect>
}

// 3. UI 是无状态的渲染函数
fn render(state: &UiState) -> Frame

// 4. 测试覆盖所有状态跃迁
fn test_tool_finished_clears() { ... }
fn test_job_progress_clamps() { ... }

❌ Critical: tui-v2 的 4 套并行状态管理

  1. React useState — TuiState 大对象，每次 setState 全量重渲染
  2. 模块级全局变量 — thinking.ts 的 accumulatedThought / spinnerTimer 是全局可变状态，多会话时竞态
  3. useRef 可变容器 — expertStatusMapRef 绕过 React 状态管理
  4. 直接写 stdout — 部分状态通过 process.stdout.write 直接输出，绕过 ink 渲染管线

后果：无法预测哪个状态是真实的。setState 和 process.stdout.write 可能冲突。全局变量在并发场景下泄漏。

2.2 事件驱动 vs 直接调用

Synova tui-v2 — 事件和直接调用混用

// 部分通过 EventBus（正确方式）
const unsub = eventBus.on('expert.status_changed', handler);

// 部分通过直接函数调用（错误方式）
adapter.showUserMessage(text);
engine.processUserInput(text);

// 部分通过 ref 直接修改
convRef.current!.getToolRegistry()!.register(tool);

// 部分通过全局桥接
(globalThis as any).__synovaAlerts = { pushAlert }; // 全局变量!?

CodeWhale — 统一 UiEvent + UiEffect

// 所有外部输入变成 UiEvent
fn handle_key(event: KeyEvent) -> UiEvent;
fn handle_prompt(text: String) -> UiEvent;
fn handle_tick() -> UiEvent;

// 所有 UI 输出变成 UiEffect
enum UiEffect { Render, PersistCheckpoint, EmitStatusLine };

// 测试驱动: 输入事件 → 断言状态 + 断言效果
let state = UiState::default();
let effects = state.reduce(UiEvent::PromptSubmitted("hello".into()));
assert_eq!(state.pending_tasks, 1);
assert!(effects.contains(&UiEffect::Render));

三、具体技术债务

3.1 全局变量竞态（Critical）

变量文件类型风险
accumulatedThoughtlib/thinking.ts:14模块级 let多会话时泄漏
spinnerTimerlib/thinking.ts:18模块级 let (setInterval)资源泄漏, 内存泄漏

expertStatusMapRefchat.tsx:111useRef Map与 React 状态不同步

3.2 运行时崩溃风险（High）

chat.tsx 第 160 行：getGlobalScheduler 调用 db，但 db 可能已被关闭

const scheduler = getGlobalScheduler(db);
// ↑ 如果 shutdown 先被触发，db.close() 后此定时器还在运行

chat.tsx 第 119-131 行：异步 initConversationEngine 在组件卸载后仍执行

useEffect(() => {
  initConversationEngine(currentProvider).then(ok => {
    // 如果组件已卸载，setState 调用 no-op 但代码仍执行
  });
}, []);

chat.tsx 第 272 行：writeFileSync 写入 .env 文件时无锁

fs.writeFileSync(envPath, envContent);
// ↑ 多个 TUI 实例同时配置可能覆盖

3.3 缺少测试（Critical）

  • tui-v2 零测试文件
  • lib/streaming.ts 的 StreamingPipeline（205 行）——最复杂、最易出错的模块——零测试
  • lib/thinking.ts 的 spinner/展开/折叠——涉及全局变量——零测试
  • hooks/use-event-bus.ts 的 8 种事件订阅——零测试
  • CodeWhale tui-core 有 25+ 测试覆盖所有状态跃迁，我们 0

3.4 demo.tsx 的模拟流式有定时器泄漏（Medium）

// demo.tsx:65
const timer = setInterval(() => { ... }, 30);
// ↑ 组件卸载时不清除（useEffect 无 cleanup）

3.5 组件通信混乱（Medium）

  • app.tsx 和 chat.tsx 是两套独立的 App 入口，但代码重复（index.ts vs app.tsx vs chat.tsx 都有主初始化逻辑）
  • app.tsx 通过 setViewAdapter 桥接引擎，chat.tsx 通过 convRef + initConversationEngine，两套机制
  • 同一份 UI 组件（Header/ChatPanel/SidePanel）被 app.tsx 和 chat.tsx 和 demo.tsx 分别使用，但 props 输入源不同

五、改进优先级

P0 — 本周

  1. 消除全局变量：thinking.ts 改写为 React Hook（useThinking），全局变量 + setInterval 改为 state + useEffect
  2. 补流式输出测试：lib/streaming.ts 的 3 个类（LineBuffer/StreamChunker/CommitTicker）写单元测试，共 8-10 个用例
  3. chat.tsx 卸载保护：useEffect 返回 cleanup，取消已发出的异步操作
  4. demo.tsx 定时器清理：useEffect 加 cleanup

P1 — 下轮

  1. 统一 app.tsx 和 chat.tsx：消除两套入口的代码重复，合并为单一 App 组件 + 配置注入
  2. 用 EventBus 替代直接调用：chat.tsx 中所有直接修改 convRef 的逻辑改为 emit 事件
  3. 补 use-event-bus 测试：模拟 EventBus.emit → 断言 state 变化

P2 — 长期

  1. 引入单向数据流：借鉴 CodeWhale 的 UiEvent/UiEffect/Reducer 模式
  2. 多面板导航：从固定 70/30 分栏改为可切换的面板系统
  3. 主题系统扩展：使用 ThemeProvider 上下文替代 getTheme() 全局函数
  4. 可配置键绑定：从硬编码改为配置文件 + 默认值
