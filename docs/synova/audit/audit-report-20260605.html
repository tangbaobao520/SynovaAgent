六、优先修复清单

🔴 P0 — 零测试覆盖

位置：全局  |  影响：无法保证代码正确性，重构风险极高

建议：优先为 PhaseStateMachine、EventBus、ExpertDispatcher、GraphBridge 编写单元测试。目标覆盖率 ≥ 60%。

🔴 P0 — L5 连接器存根

位置：connectors/feishu.ts, connectors/nemoclaw.ts  |  影响：Phase 1 数据采集完全不可用，诊断流程断裂

建议：实现飞书 Python 连接器实际 API 调用，或提供 mock 数据验证管线端到端通畅。

🔴 P0 — server.ts God File

位置：server.ts (350+ 行)  |  影响：直接 import L1-L5 所有实现类，违反分层原则

建议：提取为 app-bootstrap.ts (组件初始化) + app-routes.ts (路由注册) + app-scheduler.ts (定时任务)。

🟠 P1 — L1 路由直接调用 L5

位置：server.ts POST /api/connector/sync  |  影响：绕过 L4 本体层，破坏架构分层

建议：通过 L4 GraphBridge 或 L2 编排层中转连接器管线调用。

🟠 P1 — traceId 未实际生成

位置：orchestrator/wiring.ts, orchestrator/diagnosis-orchestrator.ts  |  影响：可观测性形同虚设，无法追踪调用链

建议：使用 crypto.randomUUID() 在请求入口生成 traceId，贯穿所有事件和日志。

🟠 P1 — EventBus 订阅者泄漏

位置：orchestrator/event-bus.ts  |  影响：长期运行时订阅者累积，内存泄漏

建议：添加 unsubscribe() 返回值的使用检查，或实现订阅者 TTL。

🟠 P1 — GraphStore 批量操作无事务

位置：l4/graph-bridge.ts  |  影响：批量 upsert 部分失败时数据不一致

建议：使用 better-sqlite3 的 db.transaction() 包裹批量操作。

🟡 P2 — 单例模式过度使用

位置：~15 个文件使用全局单例  |  影响：测试困难，状态隔离差

建议：改为依赖注入，通过构造函数传递实例。保留单例仅用于日志和配置。

🟡 P2 — 连接器无自动重试

位置：l5/connector-pipeline.ts  |  影响：临时网络错误导致同步失败

建议：添加指数退避重试 (参考 ExpertDispatcher 的 runWithRetry)。

🟡 P2 — 导出规范不统一

位置：orchestrator/, l3/, l4/ 缺少 index.ts  |  影响：深层 import 增加重构成本

建议：为每个子目录添加 index.ts 统一导出公共接口。

🟡 P2 — LLM 调用无结果缓存

位置：全局  |  影响：相同查询重复调用 LLM，增加成本和延迟

建议：添加语义缓存层 (如 gpt-cache 模式)，对相同/相似查询返回缓存结果。

🔵 P3 — Provider 模板代码重复

位置：providers/deepseek.ts, providers/openai.ts, providers/gateway.ts  |  影响：维护成本高

建议：提取 OpenAI-compatible 基类，各 Provider 仅差异化部分。

🔵 P3 — file: 本地包引用

位置：package.json  |  影响：无法独立版本管理，CI/CD 复杂

建议：发布到私有 npm registry 或使用 monorepo (pnpm workspace)。
