一、产品定位

Synova 是一个 Agent，不是 ChatBot，不是 SaaS，不是 BI。

它驻扎在企业内部，持续观测全量组织数据，主动发现问题，自动诊断根因，提出可落地的方案，跟踪执行效果。最终决策永远是人做的——Synova 是辅助决策，不是替代决策。

核心能力

能力Agent 做什么人做什么
发现问题交叉关联多个信号，浮现真实风险。不是"指标跌了"，是"三个看似无关的信号指向同一个结构性问题"确认 Agent 的发现是否重要、是否需要立即处理
提出方案从根因推导到行动，告诉人为什么这样做、预期效果是什么。有因果逻辑的方案，不是模板化的建议列表确认方案是否可行、是否适合当前组织现实。补充 Agent 看不到的背景信息
执行监督持续跟踪：建议被执行了吗？效果如何？自动对比上次建议 vs 当前现实更新执行状态。对无效的方案说"这个方向不对"

三、系统架构：五层闭环

数据从底部流入，人在顶部做决策，方案执行结果回流到数据层，形成持续闭环。

L1 交互层

GA 审阅修正 / 对接人执行跟踪 / 部门独立工作区 / 老板邮件+飞书摘要 / 76 个 API 端点 / MCP 协议服务。三栏界面：左栏工作区列表、中栏对话、右栏行动跟踪。

↓ 决策下达 ↑ 执行结果反馈
L2 编排层

ConversationEngine 管理诊断对话流程。每个问题 = 一个独立工作区，工作区之间不混淆上下文。SessionManager 处理上下文压缩——已确认的判断永不丢失，对话细节可丢弃。跨工作区相关判断自动引用。

↓
L3 洞察层

7 维度 x 26 哨兵，定时扫描 OR GA 按需触发 8 位专家并行推理。信号聚合引擎交叉关联异常信号。证据池交叉验证。每位专家输出经 Zod schema 校验方可进入下游。

8 位专家：战略（7 Powers+投融资）、组织（Bus Factor+协作）、财务（现金流+单位经济）、营销（AARRR+品牌定位）、技术（技术债+迁移）、商业模式（Canvas+定价）、行动（优先级排序）、知识（后台引擎，不直接对话）

↓
L4 本体层

SOG（Strategic Organization Graph）v1.0——组织数字孪生的开放标准。17 种节点类型、14 种边类型、52 条边端点规则。

Person / Agent / Team / Goal / Revenue / Cost / Customer / Risk / Tool / Skill / Document / Knowledge / Artifact / Routine / Product / Task / Constraint

↓
L5 数据层

企业全量数据：飞书聊天记录 / 财务系统 / CRM / 组织架构 / 文档 / 会议录音。存储：SQLite / AgentMemoryStore / KnowledgeStore（FTS5 全文索引 + RBAC 权限过滤）。

方案执行 ↑ 行动项写入 L5 → 反馈闭环：执行结果 = 新数据 -> 再次诊断 -> 对比效果 → 进入下一循环

工程质量

  • 五层架构边界：L1 只调 L2，L2 只调 L3，依此类推。pre-commit check-architecture.sh 物理阻断跨层调用。
  • 46 条铁律，5 项物理阻断：as any = 0（零容忍，47 次历史事故教训），空 catch 有 log + degraded，secrets 扫描，新文件有测试，新 export 有调用方。提交耗时 <5s。
  • Agent 自检 5 问：每次写完代码自动回答：接线检查、异常处理、类型安全、测试覆盖、残留清理。

四、对话与上下文管理

Synova 的对话不是 ChatGPT 式的通用聊天。每段对话有明确的上下文的上下文——哪个客户、哪个工作区、哪些判断已确认、哪些企业事实不可更改。

三层上下文结构

层级内容技术实现
会话上下文企业基本信息：行业、规模、阶段、历史诊断记录KnowledgeStore + GraphStore。每次对话自动注入
主题上下文当前工作区的判断卡片、对话状态、已确认的方案SessionStore + AgentMemoryStore
判断上下文单条判断的根因、证据链、修正历史、置信度变化AgentMemoryStore (type=decision)

工作区模型

每个问题 = 一个独立工作区。工作区天然限制了上下文膨胀率——大部分工作区在 5-10 轮对话内完成（根因确认 -> 方案确认 -> 关闭）。部门工作区（配置讨论）可能超过 30 条，但工作区之间不混淆上下文。

  • 工作区内部压缩：已确认的判断永不丢失（从 AgentMemoryStore 加载 type=enterprise_fact）。对话历史压缩为摘要。使用 summary 策略替代 sliding-window。
  • 跨工作区引用：工作区 B 打开时自动从 AgentMemoryStore 加载工作区 A 的相关判断。"在现金流工作区中已确认采购流程异常是临时性的——新工作区直接继承这个结论。"
  • 企业事实层：不被遗忘的动态知识。收入确认方式、考核工具、组织架构——每次 Agent 推理时自动注入系统 prompt 顶部，永不丢失。变更时记录完整版本历史和变更原因。

五、交互设计：三栏布局

GA 和对接人都使用三栏布局，差异在于 GA 多了客户导航和数据导入入口。

左栏：工作区列表
当前企业的所有问题。按优先级排序 ↑ 每个显示：状态图标 + 名称 + 最后更新时间
中栏：对话区
Agent 每次回复 = 结构化判断（根因/建议/置信度） + 行动按钮。GA 确认或对话修正。Agent 根据上下文自动调用相关专家
右栏：行动跟踪
目标跟踪（公司目标+进度）、增长卡点（当前活跃问题）、长期遗留（有意识推迟的问题+复活条件）

GA 的完整工作流

  1. 初步调研：GA 按 8 维度框架（任务目标 / 业务价值 / 现状起点 / 资源约束 / 风险瓶颈 / 成功标准 / 市场定位 / 数字底座）调研企业
  2. 输入诊断：上传调研数据，Synova 调用 8 位专家并行分析，输出各专家独立报告 + 综合报告
  3. 审阅修正：GA 逐条审阅 Agent 判断。有疑问的展开对话——"你分析现金流根因是应收账款，但你没看到客户刚换了采购系统"——Agent 重新推理后更新判断
  4. 方案交付：GA 将最终方案交付给企业对接人。此后 GA 转为定期回访角色
  5. 异常介入：Synova 7x24 监测。方案效果不达预期或对接人未按时响应时，通知 GA 介入

老板信箱

老板不需要打开 Synova 的界面。老板的界面是收件箱——每周一封摘要邮件 + 异常情况下即时推送。老板在飞书中与 Synova 对话即可调整信息密度：

  • "本周信息太细了，只给我看红色的" -> Agent 调整阈值
  • "我出差两周，推送暂停" -> Agent 进入休假模式
  • "现金流预警有更新吗？" -> Agent 回复最新数据

7.2 SOG 本体 v1.0——为什么 17 个节点

SOG（Strategic Organization Graph）是组织数字孪生的底层标准。每个节点类型对应一个必须独立测量的诊断维度。

节点类型诊断价值
Person / Agent / Team三种执行单元必须区分——否则无法识别哪些工作应该由 AI 替代、哪些应该由人来完成
Goal / Routine / Artifact组织实际在做什么（Routine） vs 应该做什么（Goal） vs 做出来什么（Artifact）。三个节点的交叉分析可以发现目标-执行-产出之间的断裂
Revenue / Cost / Product / Customer商业模型的基础要素。区分 Customer 和 Revenue 才能分析客户集中度风险
Tool / Connection / Task软件生态 + Agent 适配的诊断基础。Tool 是有什么系统，Connection 是它们怎么连，Task 是人在做什么
Document / Knowledge / Skill知识管理的三要素——Knowledge 是结构化沉淀，Skill 是团队能力，Document 是载体
Risk / ConstraintRisk 是已知风险，Constraint 是硬约束（预算/法规/资源）。D7 风险预警的直接消费层

总结

Synova 是一个已经拥有完整架构、工程基础扎实的 AI 诊断系统。它瞄准的是一个被大厂系统性忽视的市场（5-1000 人的成长型企业），用 Agent 替代传统咨询的基础工作，让成长型企业花得起、用得上。

产品定义（全量对齐手册 22 章 + PRD 21 章）、工程实现（102k 行代码 + 540 测试）、交互设计（三栏布局 + GA 工作流 + 老板信箱）——三个层面都有了结构化的交付物。正在从产品阶段走向商业验证阶段。
