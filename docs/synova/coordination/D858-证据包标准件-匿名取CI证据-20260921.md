# D858 / L4-3：CI 执行证据包标准件（匿名可核通道）

> 卡：D858（K3 审计 `docs/synova/audit-reports/2026-09-20-K3-D854.md` 的 L4 防线缺口收割 ③）
> 日期：2026-09-21 ｜ 执行：队长（并行 CTO session）实测
> 结论一句话：**匿名（无 token）能拿到 job 级 `::warning`/`::error` 的正文（含测试失败摘要），拿不到完整 job 日志**；完整日志要么交付方带 token 取并归档进仓库，要么用归档件（匿名可读）。**且匿名通道有 60 次/小时的配额上限。**

---

## 1. 问题（K3 实测 403 的复现）

```
$ curl -s -o /dev/null -w "http=%{http_code}\n" \
    https://api.github.com/repos/tangbaobao520/SynovaAgent/actions/jobs/106101388445/logs
http=403
```
`/actions/jobs/<job_id>/logs` 需要鉴权 → 匿名审计拿不到完整日志。K3 因此只能靠"提交间因果差分"定位失败点（其报告 §2 已披露）。

## 2. 三条通道（实测）

| 通道 | 鉴权 | 实测 | 能拿到什么 | 拿不到什么 |
|---|---|---|---|---|
| **A 匿名 annotations API** | 无 | `http=200`（配额内） | 每个 check-run 的 `warning`/`failure` 注解正文（`::warning`/`::error` 由 workflow 命令生成，含测试失败摘要） | 完整日志、绿腿上的普通 `echo` 输出 |
| **B 仓库归档件（推荐给批量审计）** | 无 | `raw.githubusercontent.com` → `http=200` | 交付方归档的日志片段 + sha256（可校验） | 未归档的部分 |
| **C jobs/logs API + 仓库归档** | **需 token** | `http=200`（本地 GITHUB_TOKEN） | 完整 job 日志（GB 级） | 匿名审计无法直接用 |

### 通道 A：一条命令（复制即用）

```bash
SHA=<commit_sha>; R=tangbaobao520/SynovaAgent; curl -s "https://api.github.com/repos/$R/commits/$SHA/check-runs" | python3 -c "import sys,json;[print('%s\t%s\t%s'%(c['id'],c['name'],c['conclusion'])) for c in json.load(sys.stdin)['check_runs']]" | while IFS=$'\t' read -r id name concl; do echo "== [$concl] $name"; curl -s "https://api.github.com/repos/$R/check-runs/$id/annotations" | python3 -c "import sys,json;[print('   ',a['annotation_level'],'|',a['title'],'|',(a['message'] or '')[:180]) for a in json.load(sys.stdin) if a['annotation_level']!='notice']"; done
```

**示例输出（真实，2026-09-21 02:05 抓取，配额未耗尽时；下文逐字摘自原始输出）**

`SHA=cc4e4166`（main，K3 报告入库点）→ 该 commit 的 CT Gate 腿为 **success（绿腿）**，annotations 仍可匿名取到告警正文：

```
== [success] Control Tower Gate Tests (ubuntu-latest)
    warning |  | Node.js 20 is deprecated. ...
    warning | canary-drift | 71 个测试不在 CI canary 清单:   tests/control-tower/attach.test.sh,  tests/control-tower/backup-db.test.sh,  tests/control-tower/ban-stash.test.sh,
== [failure] generate
    warning |  | Node.js 20 is deprecated. ...
    failure |  | Process completed with exit code 2.
```

红腿（PR #682 `#3912`，check_run `106093359089`，2026-09-20）匿名可得**失败断言正文**——这正是 K3 当年只能靠差分推理的东西：

```
$ curl -s https://api.github.com/repos/tangbaobao520/SynovaAgent/check-runs/106093359089/annotations
  failure |  | Process completed with exit code 1.
  warning | canary-drift | 68 个测试不在 CI canary 清单:   tests/control-tower/attach.test.sh, ...
  failure | tests/project/gen-project-board.test.sh |  ✅ ...挂进账本| ... ||PASS=94 FAIL=1|
```

### 通道 A 的硬限制（必须写进审计协议）

```
$ curl -s -D - https://api.github.com/rate_limit | grep -i x-ratelimit
x-ratelimit-limit: 60
x-ratelimit-remaining: 0
x-ratelimit-used: 60
x-ratelimit-reset: 1789930853   → 2026-09-21T03:00:53+08
```
- 匿名配额 = **60 请求/小时/IP**；`commits/<sha>/check-runs` + N 个 `annotations` = N+1 次请求 → 一个 12 job 的 run 就吃掉 13 次。
- 配额耗尽后同一命令返回的是**限流错误对象**（python 侧会报 `TypeError: string indices must be integers`）→ **审计脚本必须显式判 `annotation_level` 字段存在性，把限流报成 degraded，不得静默当成"无告警"**（这正是铁律 11 的形态）。
- 绿腿上的普通 `echo`（非 workflow 命令）**不进 annotations** → 只能靠通道 B/C。

## 3. 标准件（交付方必须附，K3 审计可直接核）

每次交付涉及 CI 运行时，证据包**至少**含以下 6 项：

| # | 项 | 形式 |
|---|---|---|
| 1 | `head_sha` / `run_id` / `job_id`(check_run_id) / `conclusion` | 文本，逐 job 一行 |
| 2 | 归档日志片段 | `docs/synova/product-lines/evidence/<任务号>-ci-<run>-<job>.log`（只追加；含失败/告警上下文，建议 grep 关键行而非整份日志） |
| 3 | 片段 sha256 | `shasum -a 256 <归档件>`，写进证据 md |
| 4 | 匿名复现命令 | 上面通道 A 的一条命令 + `raw.githubusercontent.com/.../<归档件>` 的匿名取用命令 |
| 5 | 命令的原始输出 | 直接粘贴，不许概括 |
| 6 | 已知局限 | 配额、绿腿非注解输出、被 `\|\| true` 吞掉的退出码等 |

### 通道 B 的取用与校验（匿名）

```bash
# 取归档片段（无 token）
curl -s https://raw.githubusercontent.com/tangbaobao520/SynovaAgent/<branch>/docs/synova/product-lines/evidence/<file>.log | shasum -a 256
# 与证据 md 中登记的 sha256 比对 → 一致即未被篡改
```

### 通道 C（交付方，带 token 取完整日志）

```bash
TOKEN=$(grep -E '^\s*GITHUB_TOKEN:' ~/.dsh/.credentials.yaml | sed 's/.*GITHUB_TOKEN:[[:space:]]*//' | tr -d '\r\n')
curl -sL -H "Authorization: token $TOKEN" \
  "https://api.github.com/repos/tangbaobao520/SynovaAgent/actions/jobs/<job_id>/logs" -o /tmp/job.log
grep -n "canary\|漂移\|FAIL" /tmp/job.log        # 只归档命中片段，控制仓库体积
```

**通道 C 实例（本标准的对照组）**：job `106106947784`（main `272dbd82` 的 CT Gate ubuntu，`success`）→ 完整日志 94,077 字节，sha256 `9ffab4760ba73caec4bf0ae32f6f8d9644075c6cba6a9736eb99a04ec20e6527`；关键行：
```
L831  ── canary 漂移对账 (D526) ──
L832    测试文件总数: 729 | canary 清单: 41 项
L833  ⚠ 漂移: 71 个 .test.sh 不在 CI canary 清单（…）
L905  ##[warning]71 个测试不在 CI canary 清单:   tests/control-tower/attach.test.sh, …
```
→ 同一告警在**通道 A（annotations）与通道 C（日志）双向可见**，即本标准的两条通道互为交叉验证。

## 4. 本卡（D858）如何用

- **P2「绿腿可见」**：用通道 A 在本卡 PR 的 CT Gate 腿（绿）上取 `canary-drift` 告警正文 → 附带 run/job id + 原始输出（见 `D858-P2-绿腿可见证据-20260921.md`）。
- **L4-3 落库**：本文件即标准件正文；本卡自身的 run/job id、归档片段、sha256 在 P2 证据文件里登记。
- **给审计协议的建议（报 CTO 决定，不自行改审计标准）**：把"交付方附 CI 证据包（6 项）"写入交付要求；审计侧优先用通道 B（匿名、可校验、无配额），通道 A 作抽查。
