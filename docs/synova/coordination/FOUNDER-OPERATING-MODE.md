# 创始人操作模式 v1.1 — 产品场景完成制 + 创始人驾驶舱

> **状态**: 提案（DRAFT）| 2026-08-16 | 作者: DeepSeek Harness
> **v1.1（2026-08-16）**: 创始人指示升级——驾驶舱主视图 = **产品完成度仪表盘**（线 × 进度条 × 待办，见关联文档）；本文件 §二组件2 的场景级视图降为"证据层"说明。**完成判定以产品完成度仪表盘设计为准。**
> **用途**: 给没有技术背景的创始人一套"保证项目完整开发出来"的操作模式。
> **修订规则**: 需创始人批准，走 PR 入库（对齐 MULTI-AGENT-COLLAB.md §六）。
> **定位**: 不推翻现有控制塔/门禁/K3 审计体系，只在其上增加一层"产品真值层"。
> 参考系: 第一性原理（创始人要什么：项目真能跑、能看见、能控制方向）+ Anthropic（fail-closed、机器可验）+ DeepSeek（最少机制）。

## 一、现状诊断 — 为什么"过程全绿"却"产品没通"

### 三个物理事实（全部来自 K3 审计，非推测）

| # | 事实 | 证据 |
|---|------|------|
| 1 | **控制塔 20/20 在线、门禁全绿、140+ D# 任务 97% 提交**，但 K3 全链路审计 **FAIL（0/3 贯通）**——客户/资本/人才三循环端到端全断 | DASHBOARD-CN vs [AGENT-CAPABILITY-FULL-CHAIN-AUDIT-20260813](../audit-reports/AGENT-CAPABILITY-FULL-CHAIN-AUDIT-20260813.md) |
| 2 | **声称-现实差距反复出现**：每次 K3 审计都发现"声称完成、实际断裂"（manifest 死代码、Market≠Client、placeholder 假成功、铁律 38 packages 盲区 81 处） | [AUTHORITY-DEVIATION-REGISTRY-v2](../research/AUTHORITY-DEVIATION-REGISTRY-v2.md) + [AUDIT-FINDINGS-LEDGER](AUDIT-FINDINGS-LEDGER.md) 模式 M1-M8 |
| 3 | **创始人的时间被消耗在协调细节**：派活、看 PR、点合并、读审计结论、裁决技术选项——没有一处告诉他"产品到底能不能演示、第一个客户什么时候能用" | FOUNDER-GUIDE-MERGE.md 现状 |

### 根因（第一性原理）

- 现有体系把"开发过程"管理得极好（任务、门禁、审计），但**完成判定 = 过程合规**（提交过、门禁过、审计过），**不是产品场景跑通**。
- 最有力的证据：**D255 Electron 打包 ✅ 已提交，但"双击 exe → 30 分钟 → 首诊报告"这条 C 线 R1/R3 承诺的产品旅程从未端到端实测**（C线第四章标 📊/⚠️）。
- K3 的 T2/T3 实验证明了真相：L3 计算能力是真的，断点在数据进出两端——**这类问题只能靠"真跑一次"发现，靠文档和静态检查发现不了**。

## 二、新模式：产品场景完成制

### 核心转变（三条）

| 从 | 到 |
|----|----|
| 完成 = D# 任务提交 + 门禁绿 | 完成 = **黄金场景端到端跑通 + 证据入驾驶舱** |
| 验收 = agent 自述 + K3 事后审计 | 验收 = **机器可复现的场景回归**（K3 审计升级为"真值复核"） |
| 创始人 = 协调者（点按钮、读报告） | 创始人 = **驾驶者**（定目标、看驾驶舱、裁决卡点） |

### 组件 1：黄金场景集（Golden Scenario Suite，GSS）

把"用户能看见的完整旅程"固化为**可运行、可断言、可出证据**的脚本。每个场景对应 C 线 33 项标准中的若干项。

首批 8 个场景（对齐 K3 全链路审计 + C线重定义 + INTERFACES-STRATEGY P0）：

| ID | 场景（用户语言） | 数据准备 | 断言（转绿条件） | 对应标准 | 当前状态 |
|----|----------------|---------|----------------|---------|:---:|
| GS-01 | 首诊旅程：新装 exe → 问卷 → 3 天出首份诊断 → 命中老板盲区 | 无数据（问卷路径） | 首诊报告产出 + ≥1 条"老板确认盲区" | S3-1/R1、S2-3/R3、S0-1 | 🔴 未测 |
| GS-02 | 客户循环：CRM 数据 → Client 节点 → customer-demand-shift 哨兵 → 报告 | crm-standard.json | 类型/属性契约对齐 + 哨兵产出 critical | S1-1/S1-4 | 🔴（K3: 断在 L5/L4） |
| GS-03 | 资本循环：ERP 数据 → Financial → cash-runway → 告警工单 | erp-standard.json | 属性名对齐 + manifest 挂载 + 阈值触发 | S1-1/S1-4 | 🔴（K3: P0-1/P0-2） |
| GS-04 | 人才循环：HR 数据 → Person → key-person-risk | hr-standard.json | People→Person 收敛 + 哨兵产出 | S1-1/S1-4 | 🔴（K3: 断在 L4） |
| GS-05 | 哨兵告警闭环：阈值 → 工单 → 推送（去重有效） | 注入越阈 fixture | sentinel_tickets 表有行 + 去重键稳定 | S0-3、N14 | 🔴（P0-1 + D354） |
| GS-06 | 进化闭环：GA 纠错 → 规则更新 → 下次诊断变好 | 反馈注入 | loop-3/5 真实执行体 + 规则变更可验证 | S5-1/R6 | 🔴（N13 P0） |
| GS-07 | 数据安全：脱敏 + 权限 + 本地部署数据不出门 | 敏感数据注入 | PII 脱敏 + 越权拒绝 | S3-3 | 🟡 部分 |
| GS-08 | 报告可读：一页纸结论先行 + 手机端 + 10 分钟复述 | GS-01 产物 | 报告结构断言 + 移动端渲染 | S2-1/R5、S0-4 | 🟡 部分 |

**GSS 的规则**：
1. 每个场景一个脚本目录 `scripts/golden-scenarios/GS-XX/`，含 `run.sh`（启动服务→喂数据→触发→断言）+ `expect.json`（断言清单）。
2. **证据产物**：每次运行产出 `evidence/GS-XX-<date>.png/json`（截图 + 结构化结果），入 `docs/synova/golden-scenarios/`（git 跟踪）。
3. **红线**：场景断言必须是机器判定（exit 0/1），禁止"人工看看差不多"；任何一步 agent 手工操作 = 未转绿。
4. 转绿优先级 = C 线演示叙事优先级（R1/R2/R3/R6 对应场景先行）。

### 组件 2：创始人驾驶舱（Founder Cockpit v1）

一页纸 HTML（由脚本自动生成，复用控制塔生成器思路），只有三块，**全部大白话、零技术术语**：

```
┌─────────────────────────────────────────────┐
│ Synova 驾驶舱 — 今天  场景转绿 2/8  卡点 2 个   │
├─────────────────────────────────────────────┤
│ ① 产品真值（按场景）                          │
│    客户循环 🔴 → 卡在"CRM 数据进不来"         │
│    首诊旅程 🔴 → 未测（缺安装包实测）          │
│    每条场景 = 证据链接（截图/JSON）可点开      │
├─────────────────────────────────────────────┤
│ ② 开发流（四态）                             │
│    待派发 3 件 → 进行中 2 件 → 待合并 1 件 → 待审计 0 件 │
├─────────────────────────────────────────────┤
│ ③ 需要创始人（今天只做这些）                  │
│    A. 裁决：N14 去重窗口（建议已给，30 秒）    │
│    B. 合并：PR #xxx（CI 绿，点两个按钮）       │
└─────────────────────────────────────────────┘
```

**规则**：
- 驾驶舱由 Harness 维护生成脚本，数据源 = GSS 运行结果 + git 事实 + K3 审计结论（自动区）+ 创始人待裁决清单（手动区）。
- **待裁决项必须自带"选项 + 建议 + 一句话理由"**（对齐 K3 原则"只出分析，不替创始人决策"——但建议必须给，否则创始人无从裁）。
- 语言红线：不出现 D#、门禁组号、git hash、P0/P1 等术语；用"卡在哪 / 需要你做什么 / 证据在这"。

### 组件 3：场景驱动派活 + 完成定义升级

- 派活模板（创始人一句话，Agent 自动展开）：
  > "任务：让【场景 GS-0X】转绿。遵守 MULTI-MACHINE-PR-WORKFLOW 的 PR 工作流。完成 = 场景断言 exit 0 + 证据入驾驶舱。"
- **完成标准三件套**（写进 dev doc，替代"声明式完成"）：
  1. 代码提交且门禁绿（现有流程保留）
  2. **对应场景回归 exit 0**（新增，硬门禁）
  3. 证据产物入驾驶舱（新增）
- 回归频率：场景对应模块每次 PR 合并后自动跑；全量场景每周五跑一次（对齐 T-2 周/月/季节奏，控制成本）。

### 组件 4：K3 审计升级（真值复核，不增加 K3 负担）

- K3 现行 L1-L4 审计保留不变（红线不动：Harness 不碰审计脚本、不写审计标准）。
- 新增一条**输入材料**：任务关联场景的 `evidence/GS-XX-*.json`——K3 复核"声称转绿"是否与证据一致（机器证据优先，正好对齐 K3 的"物理事实优先"方法论）。
- K3 审计报告增加一行：**场景状态复核**（该任务对应的场景在 K3 独立重跑后是否仍绿）。
- 效果：K3 从"审代码"升级为"审产品真值"，且**不增加 K3 的审计步骤**——只是把材料从"7 项"变"7+1 项"。

## 六、创始人日常（这套模式对你的全部要求）

**电脑前跟进（页面即真相，不推送、不摘要）**：打开产品进度页（每周五自动更新，随时打开即见最新）——
1. 每条线的进度条到哪了？（产品真在变好）
2. 卡点在哪？（谁卡住了、为什么——全量信息都在页面，不靠任何推送）
3. 需要我裁什么？（页面顶部"待裁决"置顶区，每项都有建议，30 秒内可裁）

**每周（10 分钟）**：点 2-3 次 Merge（PR 链接，看绿勾勾）+ 裁 1-2 个决策 + 看产品进度页周报区块。

**需要你做的全部事情，就这三件：定目标（要哪些线到 100%）→ 看进度页（确认在推进）→ 裁决（卡点决策）。**
