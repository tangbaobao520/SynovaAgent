创始人驾驶舱模式已定稿（2026-08-16，创始人批准）：产品完成度仪表盘 = 26 条能力线 × 验收点 × 证据；黄金场景（GSS）作为验收点的证据引擎。实现由 DeepSeek Harness 执行（Phase 1：product-lines.yaml + 三个脚本 + 产品进度页 + 自动化 A1-A8）。

## 三、任务（3 件必做 + 1 件可选）

### 任务 1：定稿审计维度 16-20 的标准

对每个维度给出：**审什么**（对象+范围）、**判定规则**（怎么算过——物理可执行，如 grep 什么、跑什么、exit 码）、**触发频率**（什么时候审）、**分级归属**（P0/P1/P2 判据）。

| 维度 | 提案要点（供 K3 定稿） |
|------|----------------------|
| 16 场景断言质量 | GSS 每条断言是否可 grep 产品物理输出；恒真/空壳断言；负向断言存在性 |
| 17 场景转绿复核 | "转绿"声明 ↔ evidence 文件 ↔ K3 干净快照独立重跑（T1）三对照 |
| 18 驾驶舱真值复核 | cockpit-state.json 与 evidence + git 事实一致；绿≠K3 复核红 |
| 19 新门禁 fault injection | 场景回归接入门禁后注入故障（破坏断言/断库）验证真拦截 |
| 20 进度真度审计 | 20a 抽样核验"声称已验证"验收点 / 20b 验收点措辞防软化 / 20c 线首次 100% 全量复核 / 20d 总进度加总一致性 |

### 任务 2：给出 AUDIT-PROTOCOL.md 的修订方案

新增维度如何落位由 K3 定（例：L1 代码审计扩为 16 项？还是新开一层"真值审计"？报告模板加"场景状态复核/进度复核"节？）。产出修订提案，创始人批准后入库。

### 任务 3：定义进度真度审计的抽样规则

每条线抽多少个"声称已验证"验收点、按什么标准选、多久全量一次、单次成本上限（参考：每次 ¥5-20 的量级约束）。

### 可选任务 4：给实现方的"审计可复核性"反向契约

K3 对 Harness 实现方的要求（例：evidence 文件必须机器可解析、K3 重跑命令必须一行可执行、证据必须含环境指纹——Win/Mac/时间）。这是 K3 对实现方的约束，不是实现方自定。
