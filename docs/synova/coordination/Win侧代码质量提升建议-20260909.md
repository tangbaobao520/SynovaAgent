## 四个可落地任务（按优先级）

### 🥇 W-1 证据命令机器化（消灭唯一系统性短板）

**实测缺陷**：W2 DS4 引用不存在的测试文件（`tests/agent/diagnosis-launcher.test.ts` 实测 "No test files found"）；W4 DS1 声称 grep "0 命中"实测 2 命中。

**落地**：
1. dev doc 的每条 DS 证据命令必须在**干净 clone** 里原样跑一遍再合并 spec
2. 把证据命令做成 `verify-dXXX.sh` 随 spec 入库，CI 原样执行——命令从"文档里的字符串"变成"CI 里的工件"
3. spec 自检清单加机器可查项：**"每条 verify 命令已在本分支 CI 实跑过"**（看 job 日志，不看自述）

### 🥈 W-2 消灭写操作吞错（C2 唯一实质扣分点）

**实测缺陷**：W1 `updateUser` 内部 catch 吞错返 void（user-store.ts:218-224），accept 绑定在持久化失败时照样返回 `linked:true`（enterprise.ts:241）。

**落地**：
1. 立可扫描规则：**副作用写方法禁止 void 返回 + 内部 catch 静默**——返回 `{ ok, error? }`，调用点必须消费
2. 配 AST 级门禁（检测"写方法签名 void 且含 catch"），存量清单化、新增即红
3. 调用方对"更新是否生效"有疑问时回读验证（update 后 queryByEmail 断言 orgId 已变）

### 🥈 W-3 分支覆盖准出（缺口全在"没写的分支"）

**实测缺陷**：W1 的 ACCOUNT_DISABLED 分支（enterprise.ts:230-232）零测试；W4 映射表 10 条只测 3 条。

**落地**：
1. 对本次改动文件启用 `vitest --coverage` 的 branch 阈值（改动文件 branches ≥ 阈值才准合并）
2. 把"每个新增分支要么有测试、要么显式标注豁免理由"从文化变成数字
3. 警惕空壳测试：覆盖门禁必须配"断言强度"抽查（只调用不断言的用例不计数）

### 🥉 W-4 保优势（不要丢）

W1 的测试形态（真实 HTTP 全链路 + 7 段断言）定为 Win 线模板。C6 卫生你们是赢的——保持。
