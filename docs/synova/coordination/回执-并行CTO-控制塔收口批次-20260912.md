## 二、逐任务结论

### D706 — 提交链静默丢删除项（P1）

- **根因（实测，**推翻派单初判**）**：`synova-commit` L600/L602/L693/L695 用 `git commit -m msg -- <pathspec>`。该形式走 git **部分提交机制**（对匹配路径用**工作区内容**内部重算）。当路径满足「索引已删除 + `.gitignore` 命中 + 磁盘仍存在」（D665 摘除 gitlink 的真实形态）时内部 add 因 ignored 跳过 → 删除不进提交；其它路径有变更 → git 仍 `exit 0` 报「提交完成」→ 提交后 git 用新 HEAD 回填索引 → **暂存态被静默销毁**。
- **派单假设被证伪**：派单认为缺陷在**失败回滚路径**。实测——门禁失败分支只在 `:763` 追加 bypass.log 后 `exit 1`，**不触碰索引**；跨调用复现证明拒绝后暂存态完好。丢失发生在**成功路径**。
- **修法**：① 索引精确提交（`git commit` 无 pathspec/-a）② `--files` 前置断言 staged ⊆ FILES ③ 提交后不变量校验，不一致 → `exit 1` + 点名差异 + **撤销提交 + 还原索引**（防「报告失败但提交已进历史」的假阻断）。
- **验收**：沙箱复现 `git ls-tree` 1→0；`synova-commit.test.sh` **17/17 绿**；同测试跑 `origin/main` 原版 **6 红**（反向验证）。
- **附带发现**：`git add <gitignore 命中路径>` 必然拒绝 → 旧写法使 `--files` 模式**无法表达** D665 型摘除（已一并修）。

## 八、CI 基础设施实测观察（影响所有在途 PR，建议登记）

**冲突期的 PR 不会产生任何 workflow run。** 本批实测：四个 PR 在 `mergeable_state=dirty`（与 main 冲突）期间 push **零 run、零 check-run**（`actions/runs?head_sha=<sha>` 返回 0），表现为「CI 卡住」的假象；把 `origin/main` 合并进各分支（拉平基线）后，run 立即被创建。

- **后果**：PR 会被误判为「CI 一直在排队」，实际是**没触发**；若只看「有没有红」，会得到「没有红 = 没问题」的**假绿结论**。
- **另**：`fix/*` 分支的 push **不触发** workflow（`on.push.branches` 只含 `main`/`feat/*`），run 仅由 `pull_request` 事件产生——所以在冲突期，push 之后确实一个 run 都不会有。
- **建议**：① 派单/工作流加一条「PR 是否已产生 check-run」的自检；② 或把 `fix/*` 加入 `on.push.branches`（两侧都可触发，代价是多一轮 run）。
