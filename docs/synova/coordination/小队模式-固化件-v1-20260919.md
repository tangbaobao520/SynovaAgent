> **依据**：创始人 2026-09-19 指令「把本次实验发现的问题固化成流程，把遇到的问题固化成必须遵守的机制」
> **来源**：D819 试点（三人小队：规格/编码/自验；K3 队外）——实测数据见 `docs/plans/2026-09-19-D819-自验记录.md` 与 PR #646/#647
> **性质**：**机制**。每条都有「物理检查方式」与「落地状态」两栏——**状态为"未落地"的条目，现在只是纪律，不是门禁**（这句话本身就是在防"文档说了但没接上"）

## 一、六条必须遵守的机制（本次实测暴露的坑 → 规则）

### M1 · 一队一工作树（隔离）
- **坑**：队员共享同一个工作目录（DSH 官方限制：不提供 worktree / 文件锁）；试点时主工作区带着**别的 session 的 76 个改动**，若直接开工必然污染他人。
- **规则**：**任何小队开工前，必须由队长为整队创建并声明一个专用工作树**（路径 + 分支），且该工作树**不得**是任何在飞 session 的工作区。
- **物理检查**：`check-team-protocol.sh --worktree <path>` → 断言 ① 路径存在且是 git worktree ② 其分支 ≠ 主工作区分支 ③ 主工作区 `git status` 的改动**不被本队写集覆盖**。
- **落地状态**：**未落地**（脚本待建，见 D837）

### M2 · 写集互斥（队长分配 + 开工前宣告）
- **坑**：官方明确「写集只是提示」；本次规格队员在**写码前**列出 4 处冲突（类型文件未列、禁碰文件必须改、别人的证据文件会被重写、旧测试把缺陷锁死）——**这是本模式最大的价值来源，也是最大的风险面**。
- **规则**：① 每张队内任务必须声明 `write_scopes`，**两两不得重叠**（含前缀包含关系）；② 规格交付件**必须含「写集冲突清单」一节**（本次靠它提前暴露 4 处）；③ 队长负责裁决并**在收尾检查最终 diff**。
- **物理检查**：`check-team-protocol.sh --scopes <json>` → 断言无重叠/无前缀包含；`check-spec-sections.sh <规格文件>` → 断言含「写集冲突清单」节。
- **落地状态**：**未落地**（待建，D837）；**规格模板已固化**（本 PR 第二件）

### M3 · 审计留队外，队内只能说"自验"
- **坑**：队员无法被指定预设 → 「审计员」只能是"同一个会话里被要求只看不写的队员"，**独立性弱于独立会话 + 独立克隆**。
- **规则**：① **K3 永不入队**（创始人 2026-09-19 裁决）；② 队内该角色叫「自验」，其结论**只允许两种措辞**：`可提请独立审计` / `退回（附理由）`；③ 出现"审计通过/审计合格"等措辞 = 违规。
- **物理检查**：`check-team-protocol.sh --selfverify <record>` → 命中禁用词（`审计通过|审计合格|已通过审计`）即 fail；缺必备结论词即 fail。
- **落地状态**：**未落地**（待建，D837）；**本条的措辞口径已在 D819 自验记录中执行**

### M4 · 指令不得与工具链默认副作用冲突
- **坑**：我给队员写「不要 push」，而 `synova-commit` **自带 push** → 两名队员都如实报了偏差；根因在指令方。
- **规则**：① 涉及**否定式操作**（不要 push / 不要提交某文件 / 不要改 X）时，必须先核对工具的默认副作用；② 派单模板新增**必填节「工具副作用核对」**；③ 冲突时**以工具链为准**，执行方须如实报告偏差。
- **物理检查**：`check-dispatch-refs.sh` 扩展一条：派单/小队指令中出现"不要 push"类字样**且**同时指定用 `synova-commit` → fail。
- **落地状态**：**未落地**（待建，D837）

### M5 · 证据文件写入归属（防提交态漂移）
- **坑**：D817 的用例每次运行都重写 `evidence/D817-capture-20260918.json` → **提交态会漂移**（该文件现在内容已与"修复前"的语义不符）；跨任务重写别人证据会打架。
- **规则**：① 证据文件必须**按任务号命名**（`<D#>-capture-<date>.json`）或置于**按任务分的子目录**；② **禁止**一个任务的测试写入另一个任务命名的证据文件；③ 定时重写型证据须在卡里声明"本文件会被测试重写"。
- **物理检查**：`check-team-protocol.sh --evidence-ownership` → 扫测试源码里的 `evidence/...` 写路径，断言其文件名含**本任务号**（或落在本任务子目录）。
- **落地状态**：**未落地**（待建，D837）

### M6 · 任务归属必须由队长收尾（官方不自动释放）
- **坑**：DSH 官方限制——"不会自动释放 owner"：队员闲置/中断/失败都不释放任务归属。
- **规则**：队长在每支队伍收尾时必须：① 逐张确认任务状态（`completed` 或显式 reopen/重派）；② 产出**三件交付**给主线 CTO：**最终 diff / 自验结论 / 遗留清单**。
- **物理检查**：`check-team-protocol.sh --closure` → 对给定队伍的 task 列表断言无 `pending/in_progress` 残留；三件交付缺一即 fail。
- **落地状态**：**未落地**（待建，D837）

## 二、队长归属（CTO 决定，依据本次实测）

**结论：以后每任务小队由「并行 CTO session」当队长。**

| 候选 | 判定 | 依据（本次实测） |
|---|---|---|
| 主线 CTO（本 session） | **不采纳** | 本次实证：整晚只能盯一条链 → 队列/看板/其他派单**全部停摆**（创始人 2026-09-19 指出：做 lead 就一次只能做一个任务，不能并行） |
| 编码 session | **不采纳** | 自验独立性下降（同一条线自己判自己）；且它是产物作者，不能同时当验收者 |
| 规格 session | **不采纳** | 它不管证据与验收，收尾三件交付（diff/自验/遗留）它拿不全 |
| **并行 CTO session** | **✅ 采纳** | 本来就负责控制塔/派单/验收口径，立场独立于编码线；且主 CTO 释放出来继续把控全局 |

**配套约束**：① 一名队长**同一时间只带一支队**；② 队长**不得**同时是被审方；③ 队长收尾必须交齐三件交付（M6）；④ **K3 永远在队外**（M3）。
