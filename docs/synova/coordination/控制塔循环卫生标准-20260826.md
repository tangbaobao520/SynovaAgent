# 控制塔循环卫生标准（D535，2026-08-26）

> 服务对象: 控制塔长跑脚本（gen-task-board / generate-dashboard / gen-cto-health / founder-truth / attach 等）+ 防跑偏 guard（staging_guard / incident-loop）。
> 目的: 防时间黑洞（D529: CI 挂起 10 分钟无输出）+ 防跑偏信号断流（拦截事件不沉淀 = 学习闭环死）。
> 借鉴: DSH `dsh-tool-call-timeout-policy`（声明式 timeoutMs + 执行端 deadline enforce）+ `dsh-repeat-tool-reminder`（同工具重复调用阶梯提醒，advisory only）——**理念融入现有 guard，不新建机制**（派单防膨胀约束）。

## 1. subprocess 超时契约（借鉴 DSH timeout-policy：预算声明处，执行端 enforce）

- 所有控制塔脚本的 `subprocess.run/check_output` 必须带 `timeout` 参数（**默认 30s**，按需收紧——长任务收紧到 5-10s，重任务可放宽但必须显式声明）。
- 超时 → `except subprocess.TimeoutExpired` → **log + 显式降级**（铁律 11/24，不静默，不吞错）。
- 执行端统一 enforce 的落点 = 每个调用点的 `timeout=` 参数（脚本自包含，无共享 runner）。
- 验证（grep 物理可查）——排除 import 行、注释行、fire-and-forget（`[sys.executable,...], stdout=DEVNULL`）:

```bash
grep -rnE "subprocess\.(run|check_output|Popen)\(" scripts/control-tower/*.py \
  | grep -vE "timeout=|stdout=subprocess\.DEVNULL|import subprocess" || true
# 期望: 零结果（所有真实 subprocess 调用均带 timeout）
```

- 已知基线缺口（2026-08-26 实测，非本任务引入，不属写集不修）: `attach.py:203`（`_rev` 内 `subprocess.run([git, "rev-parse", ...])` 无 timeout）——本地 git rev-parse 挂起风险极低，待后续任务补。

## 2. 重复事故提醒（借鉴 DSH repeat-tool-reminder）

- `incident-loop.py record` 同 id 重复 → 返回 `duplicate` + `repeat_count` + `reminder` + `last_recorded`（非静默——D535 改造，修复前静默返回 duplicate）。
- reminder 语义: "该事故已重复出现 N 次（上次 T）——检查是否机制未闭环"。
- 调用方（synova-commit 等）收到 reminder → 打印 ⚠ 提醒（**不阻断**，advisory only——决策留给模型，对齐 DSH repeat-tool-reminder 明令）。
- 阈值阶梯: 首条 record 无提醒；二次起每次提醒（计数含 log 中同 id 历史行 + 本次）。

## 3. 防跑偏信号接线（学习闭环活起来）

- **staging-guard block（synova-commit）→ `incident-loop.py record`**——并行冲突拦截事件自动沉淀（D535 接线，之前 incident-loop 零生产调用方，学习闭环是死的）。
- incident id 按天聚合: `staging-block-YYYYMMDD`（当天多次 block 幂等合并，repeat_count 递增 → 频发提醒；跨天 id 含日期天然隔离，次日重新计数）。
- fail-open: incident-loop 不可用（python 缺失/脚本异常）→ 显式提示不阻断主流程（铁律 24/31，拦截语义不变仍 exit 1）。
- `verify` 命令用于闭环案例验证（INC-20260802-stash 等），已内嵌 timeout=10。
