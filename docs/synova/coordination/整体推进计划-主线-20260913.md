## 〇、这份文档为什么存在

创始人的原话：「**我要的不是凭借记忆，而是你真的能做到遵照你写出来的这些原则行事。**」

本文档把"原则"变成**可检查的约束**：每条原则 → 一个机器消费点（门禁/脚本/门禁字段）→ 违反即阻断。
**凭记忆 = 每天重新决定一次要不要遵守**；本文档 = 把决定固化一次。

## 一、主线定义（唯一口径，不因谁吵得响而变）

**产品主线 = 让产品成立的最小可信闭环，三件事：**

| 主线支柱 | 含义 | 对应验收 |
|---|---|---|
| **① 能被装起来用** | 桌面端线 1 走到 100% | 线 1 的 1-1…1-8 全部 verified |
| **② 报告可溯源** | 证据链接通（采集→落库→引用） | 一条诊断报告能溯源到 ≥1 条原始证据 |
| **③ Agent 能主动** | D-1 状态驱动通知模型落地 | 8-6 契约 + loader + 通知链跑通 |

**判据（每次派单前必答）**：
> **这件事让 ①/②/③ 中的哪一项前进？** 答不上来 → **标为 `infra:<理由>`**，且计入基础设施工时。

**非主线的都是支撑**（控制塔、门禁、看板、审计吞吐）——**它们合法，但不许超 25% 产能**。

## 三、三阶段推进（退出条件写死）

### 阶段 1｜止血：事实可见 + 清空欠账（T+0 ~ T+3 天）
- 看板真相源三层修复（线级状态派生 + verdict 维度 + 失败可见）
- CTO 健康看板修复（崩溃 + FAIL 判定）
- D738 基线棘轮（CI 转绿）
- D735 Stage 2（bypass 出库切换）
- 早期队列 PR 全部收口（无 open 积压）
- 批 C：merge queue（`merge_group` + 一键回滚）
**退出条件**：仪表盘数字 = 真相源数字；**零 PR 积压**。

### 阶段 2｜主线攻坚：线 1 → 100% + 证据链接通（T+3 ~ T+10 天）
- 1-5 双引导收敛实施（Win，spec 已在 main）
- **1-4 重打新产物 + 证据落盘**（Mac，含 `[preload-check] OK` 原始日志入 git）
- 1-2 / 1-6 Win 环境阻塞补测（人工桌面会话）
- 1-8 复验（K3，绑新产物）
- **D728 + D729(Win 部分) 证据链接线**（Win，一次扩写集 + 中间态护栏）
**退出条件**：**线 1 = 100%**；报告能溯源到 ≥1 条原始证据（贴命令）。

### 阶段 3｜产品闭环（T+10 ~ T+20 天）
- D-1 通知模型落地（8-6）
- 哨兵真实数据流（表建了但空着 → 真实数据）
- L1 未闭合项 9 → 0
- 技术债按域清（57 处 locale、测试 hermetic 等）

## 五、原则 → 机制（11 条，机器执行）

| # | 原则 | 机制 | 落点 | 违反时 |
|---|---|---|---|---|
| 1 | 派单必须基于本计划 | 派单文档必须写 `依据计划: v1.0@<hash>`；hash 不等于当前文件 hash → 拒 | pre-dispatch-check 第⑩项 | 阻断 |
| 2 | 主线优先 | brief 必填 `## 主线贡献: line-1/1-4` 或 `infra:<理由>` | pre-commit 组 6 | 阻断 |
| 3 | 基础设施 ≤25% | `mainline-ratio.py` 统计 → 超线写周报并告警 | 周报/定时任务 | 告警+解释 |
| 4 | 派单前复核 | `pre-dispatch-check.sh` 九项 + 派单文档须内嵌复核输出节 | 门禁 | 阻断 |
| 5 | 域归属 | `ownership.yaml` + `check-ownership.py`（已入 main）；brief 必填 `## 域` | pre-commit | 阻断 |
| 6 | 写集租约（两活跃会话交集须空） | `check-write-set-lease.sh` 登记+比对 | 派单时 + PreToolUse | 阻断 |
| 7 | 同域并行度 = 1 | 同 #6 + PR 预算门禁（已入 main） | 派单/提交 | 阻断 |
| 8 | 声称必有物理证据 | 交付须含「声称 ↔ 命令+原始输出」表；无证据=未完成 | 验收（CTO/K3 逐条跑） | 退回 |
| 9 | **测量有效性自检** | `measure.sh`（pipefail + 按扩展名选解释器 + `core.quotepath=false`）；证据行须带其 marker | 复核/验收 | 证据无效 |
| 10 | 不欠账 | `check-debt-free.sh`：存在 >24h 的 CI 红 PR → 拒发新派单 | 派单时 | 阻断 |
| 11 | 看板=真相源 | `check-board-consistency.sh`：FAIL/未审计项必须在看板呈现为失败 | CI | 红 |

**已落地 3 条**（#5 域归属、#7 PR 预算、#4 复核脚本）；**本周内落 4 条**（#1/#2/#6/#10）；其余按阶段排。

## 六、任务看板如何跟踪（已核实路径）

```
task-state/D###.json  ──(dsh/plugins/task-board-adapter/lib/sync.js)──▶  看板（Host 账本 ~/.dsh/ledger）
        ▲                                                                       │
        └────────────── 主线任务 = brief 的 `## 主线贡献` 字段 ◀───────────────────┘
```

- **适配器在本仓**（`dsh/plugins/task-board-adapter/`）→ 可修可测（D741 已定位其 verdict 维度缺失，修复在阶段 1）
- **跟踪口径**：每个 D# 的 brief 带 `## 主线贡献` → 看板可按"主线/基础设施"分组显示
- **周报数字**：主线 verified 点数、基础设施工时占比、阻塞项

## 七、创始人如何在不信任我的前提下检查我（三个硬痕迹）

1. **每个提交的 brief 是否有 `## 主线贡献` 字段** —— 缺 = 违规

3. **周报两个数字**：主线 verified 点数（起点 **1**）、基础设施占比（起点 **65%** → 目标 <25%）
   —— **连续两周不动 = 我失职的硬证据**
