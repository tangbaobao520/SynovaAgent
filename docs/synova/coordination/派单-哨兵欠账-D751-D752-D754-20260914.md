## 一、D751｜「新增生效」硬断言（P1 · 根）

**是什么**：我们宣称「文件驱动：加一个哨兵/专家就生效」。但**没有任何断言**证明「新增 → 被路由到 → 被调用 → 结果进报告」。
**实证**：45 哨兵中 8 个从未进类型网无人发现；D750 的错路由长期在产。→ **漏声明不报错 = 静默失效**。

**交付**：一个端到端断言（测试或 check 脚本），夹具为"新增的一个哨兵"：
1. 被 loader 发现（`loadSentinels()` 含该 id）
2. 被路由到（其 manifest.expert 出现在聚合信号的 `recommendedExperts` 中，或 `findSignalRoute` 命中）
3. 结果进报告/派发（`runner.ts` 的 targetExperts 含它）
**写集白名单**：`tests/sentinel/**`（新增测试）、`src/sentinel/**`（仅在需要注入缝时改动，且每处 ≤5 行）
**红区**：`scripts/audit/`、`.github/workflows/ci.yml`、`extensions/sentinels/**`（数据侧属 Win，本单不动）
**验收（可跑）**：
- `npx vitest run tests/sentinel` → 新增断言通过
- **反向验证**：把该哨兵的 `manifest.expert` 删掉 → 断言必红（证明断言真在读声明，不是空跑）
**回报格式**：命令 + 原始输出 + 改动文件行数

## 二、D752｜哨兵类型网登记改硬门禁（P1）

**是什么**：`src/sentinel/types.ts` 用静态 `import type` 做编译期登记，但**不加也能跑** → 软约束，实测 **8/45 未登记**（含 `cash-runway`、`competitive-moat`、`key-person-risk`、`revenue-health`、`sentinel-pricing-strategy` 等）。
且 `types.ts` 引用 38 个目录，**含已归档的 `_extinct`**。

**交付**：
1. 硬门禁（check 脚本 + 测试）：`extensions/sentinels/*/manifest.json` 的每个哨兵，必须有对应的类型登记；缺失 → **非零退出并点名**
2. 归档目录豁免规则（`_extinct` 等 `_` 前缀）显式化，写入脚本注释与测试
3. 补登记 or 显式记录豁免（**不许静默跳过**：要么登记，要么写明豁免理由）
**写集白名单**：`src/sentinel/types.ts`（仅补登记）、`scripts/control-tower/**`（新增 check 脚本）、`tests/control-tower/**`、`tests/sentinel/**`
**红区**：同上
**验收**：门禁跑当前仓库 → 点名未登记项；**反向验证**：删掉一个已有登记 → 必红

## 三、D754（Mac 半）｜runner 注释去漂移（P2）

**是什么**（实测）：
1. `src/sentinel/runner.ts:74-78` 注释原文「无限扩展：**加新哨兵时在 config 中声明路由**」——但实测 **0/45 哨兵声明 `route`**，实际全走 layer 默认映射
2. `src/sentinel/runner.ts:77` 注释称下游 `VALID_EXPERTS` 会把失效路由过滤成空 —— **实测不成立**（那是另一个机制）

**交付**：把注释改成**与实现一致的事实描述**（写清真实的优先级链：manifest `route` > layer 默认映射；以及真正发生的失效模式）。**不改路由实现**（改实现另有其单）。
**写集白名单**：`src/sentinel/runner.ts`（仅注释）
**验收**：`grep -c '声明路由' src/sentinel/runner.ts` → 0（旧表述已消失）；且注释描述的机制有对应代码可指（贴 file:line）
**Win 半（manifest 声明 route）**：见 §四
**注**：若执行方判断"显式声明 route"才是正解，**不要在本单实现**——上报 CTO，另单。
