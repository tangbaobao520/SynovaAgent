## D706：synova-commit 部分提交回滚吞删除项（P1）

**目标**：任何经 synova-commit 的提交，其**实际进入提交的文件集合**必须与提交时暂存区声明一致；发现不一致必须**阻断**（不得静默提交不完整树）。

**依赖**：无

**已实证的复现路径（本单提供，执行方须先复现再修）**：
1. 暂存一个文件删除（`git rm --cached <path>`，路径同时被 `.gitignore` 命中、磁盘仍存在）
2. 走 synova-commit 提交；若该次提交因门禁失败被拒（D328 认领对账等）
3. 下一次经 synova-commit 提交时，该删除项**已从暂存区消失**，提交树与提交消息声明不符（实证：`9aabd581` 声称摘除 10 个 gitlink，`git ls-tree -r HEAD | grep -c '^160000'` 仍为 10；补救见 `638bfb5b`）
4. 沙箱对照实验已证明 `git commit -m msg -- <pathspec>` 本身**可以**携带删除项 → 缺陷在**失败回滚路径**，不在 pathspec 语义本身

**spec 必答题**：
1. 失败回滚路径究竟在哪一步丢失暂存态？（给 file:line + 复现脚本；不许用"疑似/可能"结论）
2. 修法选型：① 提交前后校验 staged 集合一致性（不一致即 exit ≠0 + 点名差异）② 删除类路径改全索引提交 ③ 两者结合——选哪个？为什么？（铁律 0：先对齐再动手）
3. 回归测试如何覆盖"第一次被拒 → 第二次提交"这个跨调用场景（`tests/control-tower/synova-commit.test.sh` 现有断言是否够？不足则补哪条？）
4. 修完后如何证明"改 A 不断 B"：现有 synova-commit 的 13 项门禁、auto-tag/session 分支豁免、bypass 登记是否受影响？（给实测证据）

**验收**（物理可复现，禁止文档声称）：
- 复现脚本 A：修复前 → 提交树与声明不符（贴 `git ls-tree` 前后对比）；修复后 → 阻断 + 点名差异
- `bash tests/control-tower/synova-commit.test.sh` → exit 0，且新增断言在**移除修复代码后必红**（反向验证，防假绿）
