## 卡 1｜D790 A1 度量口径修复（执行方：并行 CTO｜域：mac）

**问题**：`scripts/product-lines/calc-progress.py` 的失效规则按**日期**比较「证据日期 vs 该线模块最后提交日」→ **同日提交即判 stale**。实证：2026-09-15 深夜 #538（21:41 提交）吞掉线1 六个点，次日重跑又全部吐回 → **完成度数字随"跑的时间点"跳变**（08:00 与 22:00 两个数）。

**做什么**：
1. 改为**比时间戳**：证据记录的生成时间 vs 该线模块最后一次提交时间；`证据时间 > 提交时间` 才算 fresh。TTL 14 天规则与「证据须晚于代码」的**意图不变**。
2. 逐行 diff 证明**未改**其他判分逻辑（TTL、六态、兑换口径、权重）。
3. 加测试：同日先后两种情形（证据在提交后 → fresh；证据在提交前 → stale）+ 边界（同秒）+ 降级（缺时间戳字段 → 显式 degraded，不静默当 fresh）。
4. 修完跑 `bash scripts/product-lines/refresh-all.sh`，给出**点级 before/after 对照**（哪些点从 stale → pending_k3，为什么）。

**硬约束**：不改 TTL 数值；不改兑换口径；不动 `rerun-evidence.sh`（D774 已交付）；写集机器生成；单域 mac；PR ≤12；改 `scripts/product-lines/**` → 按 D534 写 `memory/notes/` Note 并在 commit 引用；提交走 `synova-commit`。
**验收**：测试全绿 + 点级 before/after 对照 + 同一天不同时点跑两次 → 六态**一致**（这才是本卡的靶心）+ 逐行 diff 证明未改其他判分。
**提审**：落地后交 K3（改的是创始人看的那个数字 → 必须独立审）。
