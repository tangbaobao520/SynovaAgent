# 派单：批十一 —— P0-1+P0-2（工具 schema 进请求体 + tool_call 配对）+ T-D3（删会话级联）

> **依据计划: v1.2@4e46603f**（`docs/synova/coordination/整体推进计划-主线-20260913.md`，CTO 派单时实测哈希）

## 〇、为什么是这两张

1. **P0-1+P0-2 是"产品能不能成立"级**（总纲判据 B/A）：今天出站 body **没有 tools**，模型永远不知道有工具可用 → **工具循环在生产里根本进不去**；而任务书已确认 **P0-1 一直掩盖着 P0-2**（配对错误的雷）——**两张必须同时修**，只修一张模型仍收到结构非法的工具对话。
2. **T-D3 是全清单里性价比最高的一档（1–3 天）**：清理函数**已经写好**，只是**没人调用**；报告列表 SQL **不 join 会话表** → 删了会话，报告仍能被列出（含完整一页纸）。这是**客户数据资产 + 隐私承诺**问题（判据 D）。

## A. 两张卡（照总纲 §五 8 字段格式）

### D819 P0-1+P0-2：工具 schema 进请求体 + tool_call 配对
- **缺口**：① 出站请求体无 `tools`（模型不知道有工具）② assistant 消息丢 `tool_calls`、tool 消息用**随机 UUID** 当 `tool_call_id`（模型收到的工具对话结构非法）。
- **判据**：**B / A**（产品核心交互不成立）。
- **DSH 参考**：无（这是自研缺陷补齐；DSH 的对照物是 P0-4 的运行时断言）。
- **借鉴什么**：不借鉴代码；**照 DSH 的纪律**——"机制要在生产入口可验证"（由 D817 的出站抓取点提供）。
- **不借鉴什么**：不改 provider 契约语义（`ChatOptions.tools` 保持原样）；不引入新依赖。
- **落地位置（CTO 实测）**：
  - `src/providers/base.ts` —— body 组装处（当前只含 `model / messages / temperature / max_tokens / reasoning_effort / stream`）**漏了 `tools`**。
  - `src/agent/tool-loop-executor.ts:131-134` —— push 的 assistant 消息**只有 `role` + `content`**，`tool_calls` 被丢。
  - `src/agent/tool-loop-executor.ts:153` 及同型处 —— tool 消息 `tool_call_id: crypto.randomUUID()`，**未使用模型给的 `tc.id`**。
- **方式**：**自建**（零依赖；纯接线，约 30–60 行改动 + 测试）。
- **验收标准**（穿真实生产入口，复用 D817 的假上游抓取点）：见 §B。
- **依赖**：**D817**（假上游 + 生产入口 harness）。
- **工作量**：**1–3 天**。

### D820 T-D3：删会话不删诊断报告
- **缺口**：`deleteSession` 只删 `agent_messages` + `agent_sessions`；`deleteDiagnosisCheckpoints` **已存在但零调用者**；报告列表 SQL **不 join 会话表** → 删会话后报告仍在、仍可经 API 列出。
- **判据**：**D**（客户数据资产；若对外承诺过"彻底删除"则升 P0）。
- **DSH 参考**：无。
- **借鉴什么**：无（自研缺陷）。
- **不借鉴什么**：不做"软删除"替代（承诺的是彻底删除则须真删）。
- **落地位置（CTO 实测）**：`src/store/session-store.ts` —— `deleteSession`（只删两表）、`deleteDiagnosisCheckpoints`（零调用）、`listDiagnosisReports` 的 SQL（`WHERE phase = 5`，无会话过滤；调用方 `src/routes/diagnosis.ts:947`）。
- **方式**：**自建**（成本极低——函数已存在）。
- **验收标准**：见 §B。
- **依赖**：无（可立刻开工）。
- **工作量**：**1–3 天**。

## B. 验收（全部穿真实生产入口；禁 grep 命中、禁 mock 管线）

| 卡 | 验收项 | 判定方式 |
|---|---|---|
| D819 | 出站体含 tools | D817 假上游抓到 `body.tools`，断言长度 == 本轮注册工具数（**不是 undefined**） |
| D819 | assistant 带 tool_calls | 第二轮请求里 `role='assistant'` 的消息含 `tool_calls[]`（`id`/`name`/`arguments` 齐） |
| D819 | 配对合法 | 每条 `role='tool'` 消息的 `tool_call_id` ∈ 前一条 assistant 的 `tool_calls[].id` 集合（**不得再出现随机 UUID**） |
| D819 | 端到端 | 假上游脚本化返回一次 tool_call → 断言工具被真实执行，且第二轮请求配对合法 |
| D819 | P0-1 证词翻转 | D817 交付的 `it.fails`（"出站体含 tools"）**翻转为通过** → 删除该 `it.fails`，改成正向断言 |
| D820 | 级联删除 | 建会话 → 跑诊断落报告 → 删会话 → 断言 `diagnosis_checkpoints` **无残留行** |
| D820 | API 层不可见 | 断言报告列表 API（`GET /api/diagnosis/reports`）**查不到**已删会话的报告 |
| D820 | 反向（不误删） | 未删会话的报告仍可正常列出 |

## C. 红线

1. **不改 provider 契约语义**：`ChatOptions.tools` 的输入/输出/降级契约不变（铁律 47）；`convertTools` 若被启用，必须写明"哪些 provider 支持、不支持时如何降级（显式 log + degraded，铁律 11/24）"。
2. **不在 `src/**` 加测试专用分支/开关**（同批十红线）。
3. 不碰 `scripts/audit/**`、`scripts/control-tower/**`。
4. **D819 必须两张一起修**（只修 P0-1 会让模型收到结构非法的工具对话——这正是任务书说的"P0-1 掩盖了 P0-2"）。
5. 行号基于 `origin/main`（批十合入后），**开工第一步重新核行号**。
