## 〇、为什么是这五件（CTO 判断，不是按谁吵得响排）

前一批把「看得见的问题」清掉后，暴露出**一个产品级空洞和两个体系级缺陷**：

1. **证据层是空心的**（D725 spec 实测）：`evidence` 表在生产库**不存在**、`EvidenceStore` 零生产实例化、`expires_at` 零写入方 → D717 的清理作业跑在自建空表上。
   **这不是配置问题**：我们的产品卖点是「报告可溯源」，而**证据根本没落库**。D-1 状态驱动通知模型（创始人亲裁）也建立在「证据状态」之上 → **这是当前最高优先级的实现项**。
2. **一个 brief 声明，四道门禁四套解析口径**（我亲历 + D718 独立复现同一现象）：G12 认一行一文件、D708 不拆「、」、CI 棘轮要 merge-base 三点差、staging-guard 认领为空时回退猜 brief → 全队列被格式问题堵死。
3. **门禁只覆盖「提交方」，不覆盖「后来落进来的人」**（D716 impl session 亲历 + D726 session 亲历）：D537 拦住了提交者，却没拦住另一个 session 的提交落到别人分支上（M8 变体）。

**排序原则**：产品空洞（证据链）> 体系缺陷（门禁口径/隔离）> 小修（死码/死键）> 审计。
