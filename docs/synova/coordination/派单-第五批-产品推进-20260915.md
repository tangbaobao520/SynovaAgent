### 1% 的真相（三条，结论完全不同）

1. **96 个点从没交证据** = 真实产品缺口，占 59% —— 这部分只能靠开发推进。
2. **34 个点证据已在手上，只差审计** = 变现问题。K3 跑完就能把进度从 1% 抬到 ~20%。
3. **29 个点证据过期** = **结构性易腐**：`scripts/product-lines/calc-progress.py:67 EVIDENCE_TTL_DAYS = 14` —— 证据超 14 天作废；
   且「证据日期之后该线 modules 有 git 变更」也作废（`scripts/product-lines/calc-progress.py:33`（A1））。团队每天在提交 ⇒ **没有重跑机制，数字永远涨不上去**。

**这是本批最重要的判断**：产品完成度上不去，主因不是代码量，是**证据链没有流水线**。
不建重跑机制，第一批做完的成果两周后照样变 stale（做过等于没做）。

## 二、本批判断（为什么这样排，为什么不做别的）

1. **最高价值 = 线 1 走到「创始人双击安装包 → 装好 → 自启 → 开窗即用」**：它是 ① 的 done_definition，
   也是「产品真的存在」的唯一证明。1-5 实现已合，剩下的是产物 + 证据 + 审计。
2. **第二价值 = 把已有证据变现 + 建重跑机制**：这是**同等人力下唯一能立刻抬高完成度**的动作，
   而且建一次长期受益（否则每 14 天腐坏一轮）。
3. **第三价值 = 补 ③ 支柱的薄处**：线 7/8 的 stale 重跑就能点亮一部分；线 16/17 需要真实接线（N13 断裂是 P0）。
4. **不做**：不新开方向、不做 DSH 卡驱动的排期（B 卡排在 CTO 域/空闲窗口，按序跑，不挤占主线）；
   不做「为凑数字而降低证据标准」（14 天 TTL 与 A1 必须保留）。

## 六、派单内部一致性自检

- **域与执行方**：A2/D5/E 组的落点域按 `ownership.yaml` 实测（`src/cron`/`src/mcp` = mac；`src/**` 其余 = win），代行期执行方统一 Mac，域声明不变
- **并行度不冲突**：同域组串行；B/C/F 属不同域可与主线并行 → 任意时刻 ≤2 张卡在跑
- **依赖无环**：A3 ← A2 ← A1；B2 ← B1；B3 ← B1；D1/D3/D4 ← 各自 spec；E2(D763) 与 D3 同域 → 串行，不得并行
- **无互斥表述**：本单未对同一路径同时要求「必红」与「变绿」
- **与已交付不撞车**：1-5 已合（#538）；D712/D716 证据批已交付；B-01/03/04/05/07/09/10 卡已交付 → 本批不含
- **可测口径**：每个 A/D 组的验收都要求「原始输出入 git」，无证据 = 未完成（计划 §五 原则 8）
