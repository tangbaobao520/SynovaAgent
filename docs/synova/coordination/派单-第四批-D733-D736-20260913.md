## 〇、CTO 的可行性判断（先给结论，再说理由）

### 创始人原意 vs 我的判断

| 创始人设想 | CTO 判断 |
|---|---|
| 5 条一起派给并行 CTO，一次做完 | **不可行 → 拆三批**：批 A（D733+D734）现在做；批 B（D735+D736）批 A 合入后；批 C（merge queue）单独，CTO 亲盯 |

### 为什么（三条硬理由，带数据）

**理由 1：五条的爆炸半径差异极大，不能用同一批节奏。**

| # | 事项 | 爆炸半径（实测） | 风险 |
|---|---|---|---|
| 1 | merge queue | **改分支保护 + 所有 workflow 需加 `merge_group` 触发** → 出错则**全仓库无法合 PR** | **极高** |
| 2 | `bypass.log` 出库 | **17 个脚本消费它**（CTO 实测 `grep -rln bypass.log scripts/` = 17） | **高**（我上一条估为"低"是错的，**更正**） |
| 3 | `ownership.yaml` + CODEOWNERS | 纯新增（1 新文件 + 1 改文件 + 校验脚本） | 低 |
| 4 | PR 预算门禁 | 纯新增（1 检查脚本 + 接线） | 低 |
| 5 | 测试 hermetic 化 | 跨多个测试文件改造 | 中 |

**理由 2：把「改门禁」和「改合并路径」放同一时段 = 自毁逃生通道。**
批内若同时改 merge queue（合并路径）与其它门禁，一旦前者的 workflow 触发条件写错，PR 检查不再触发 → 我们**既不能合也不能回滚**。今天的教训（域内并行度=1、小爆炸半径）正是针对这种情形。

**理由 3：Flash 快 ≠ 会自己收敛范围。**
一次性给 5 条，最可能产出是「5 个半成品」或「1 个巨型 PR」——而**巨型 PR 正是第 4 条自己要禁止的形态**（自相矛盾）。模型再快，也不会替你决定边界；边界必须由 CTO 在派单里写死。

### 分批与解锁条件

```
批 A（现在）  D733 ownership + D734 PR 预算门禁      ← 纯新增、零外溢，可并行
      ↓ 合入 main
批 B          D735 bypass.log 出库 + D736 测试 hermetic ← 均改动既有资产，需迁移期
      ↓ 合入 main
批 C          merge queue（不派单，CTO 亲做 + 回滚开关） ← 改合并路径，单独时段
```

## 一、D733｜🧭 并行 CTO：ownership 机器化 + CODEOWNERS 全量化（P0）

**背景（实测）**：域划分只写在 `docs/synova/coordination/TASK-ROUTING.md`（**纯 Markdown，零机器消费者**）；`CODEOWNERS` 仅 26 条规则，**Win 域是按排除法定义的**（"`src/` 除 sentinel/cron/mcp"）→ `src/` 下 **439 个 ts 文件绝大多数无机械归属**。后果：CTO 今天**两次派错线**（D728/D729 写集落在 Win 域却派给 Mac）。

**交付**：
1. `docs/synova/coordination/ownership.yaml`（**新建**）— `glob → owner`（mac / win / k3），含默认规则与例外，来源必须逐条对齐 `TASK-ROUTING.md` §31-38
2. `.github/CODEOWNERS`（改）— 由 ownership.yaml 生成或严格对齐；**Win 域必须显式列出**（不能只靠排除法）
3. `scripts/control-tower/check-ownership.py`（新建）— 输入「文件列表 + 声明 owner」→ 越域即非零退出（三态）
4. `scripts/control-tower/pre-dispatch-check.sh`（改）— 第⑤项接上 check-ownership：**派单写集越域即红**
5. `tests/control-tower/ownership.test.sh` + `pre-dispatch-check.test.sh`（补用例）— 含**今天两次真实错误**的回归用例

**写集白名单**：`docs/synova/coordination/ownership.yaml`、`.github/CODEOWNERS`、`scripts/control-tower/check-ownership.py`、`scripts/control-tower/pre-dispatch-check.sh`、`tests/control-tower/ownership.test.sh`、`tests/control-tower/pre-dispatch-check.test.sh`
**红区（禁碰）**：`scripts/audit/`、其它 session 在途文件、`.github/workflows/ci.yml`
**验收（可跑）**：
- `python3 scripts/control-tower/check-ownership.py src/server.ts --owner mac` → **非零**（server.ts 是 Claude 专属）
- `python3 scripts/control-tower/check-ownership.py src/evidence/x.ts --owner mac` → **非零**（Win 域）
- 反向验证：把 ownership.yaml 的默认规则删掉 → 上述两条**必须变绿**（证明校验真在读它），再还原
**回报格式**：三项命令的原始输出 + 改动文件行数

## 二、D734｜🧭 并行 CTO：PR 预算门禁（P1）

**背景**：冲突概率 ∝ 改动大小 × 分支存活时间。今天 D721 一个 PR 背三类门禁问题挂半天；K3 审计分支落后 main 差点回退他人成果。

**交付**：
1. `scripts/control-tower/check-pr-budget.sh`（新建）— 校验：① 变更文件数 ≤ 上限（默认 12）② **变更只落在一个域**（调 D733 的 check-ownership）③ 分支落后 main 超 N 个提交 → 警告（防"落后分支直接合"）
2. 接线：`scripts/pre-commit-check.sh` 新增一组（条件跳过，保持 <1s）或 CI quality job 一步 —— **由执行方给出取舍理由**，写进 PR 描述
3. `tests/control-tower/pr-budget.test.sh`（新建）— 三路径断言（通过 / 越预算红 / 跨域红）
**写集白名单**：`scripts/control-tower/check-pr-budget.sh`、`scripts/pre-commit-check.sh`（仅新增一组）、`tests/control-tower/pr-budget.test.sh`
**红区**：`scripts/audit/`、`ci.yml`（#520 刚改过，避免撞车）
**验收**：`bash tests/control-tower/pr-budget.test.sh` 全绿 + 用**本 PR 自身**跑一次（若自身超预算 → 必须拆 PR，不许调高上限）

## 四、批 C：merge queue — **不派单，CTO 亲做**

**为什么单列**：改分支保护 + **所有 workflow 必须支持 `merge_group` 事件**（否则队列中的检查不触发，等于把合并通道锁死）。一旦写错，全仓库无法合 PR。
**已核可行**：main 现有 **12 项必需检查** + `enforce_admins=true` + 禁 force push/删除 → 基础齐备。
**要求**：① 先加 `merge_group` 触发到全部 workflow 并验证 ② 再开队列 ③ 保留**一键回滚**（关队列即回旧流程）④ 首次启用只放 1 个 PR 试用

## 五、质量把控（针对 Flash：快但不会自己收敛）

| # | 措施 | 为什么 |
|---|---|---|
| 1 | **每项独立 PR**（禁合并成一个大 PR） | 大 PR 是冲突源，且违 D734 自己 |
| 2 | **每项必做反向验证**（还原修复 → 必须红） | 防"写了但没接线"的假绿 |
| 3 | **写集白名单**（越域即拒） | 替代 CTO 人脑判域 |
| 4 | **Done 必须可跑命令** | 可证伪，不接受文字声称 |
| 5 | **不给它发明设计的空间**：参照实现/文件位置已在派单里给死 | Flash 适合执行不适合设计边界 |
| 6 | **逐项回报，不等全做完** | 早暴露，早纠偏 |
| 7 | **红区明列**（`scripts/audit/`、他人在途文件） | 红线不碰 |

**汇报要求**：每项完成后回报「声称 ↔ 物理证据（命令 + 原始输出）」表；**无证据的声称按未完成处理**。
