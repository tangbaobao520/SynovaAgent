# 控制塔版本管理规范

> 2026-08-23 建立 | 归属: CTO (dsh-cto) | 触发: 创始人指出 D506/D507/D508 三批门禁改版未升版本号（CT-42 教训第二次违反）

## 一、铁律（每次改版必须执行）

1. **任何控制塔行为变更必须 bump 版本**（PATCH 起步；新机制/新门禁组 = MINOR）——版本文件头部契约原文
2. **bump 与代码同 commit**（VERSION.md + version.log + 改动代码一个提交）
3. **bump 必须同 commit 打 tag**（synova-commit 自动；手动 git commit 场景：`git tag V<x.y.z> && git push origin V<x.y.z>`，否则 push 被 D319 拦）
4. **一处定义三处同步**：`.codex/control-tower/VERSION.md`（人类可读记录）+ `.codex/control-tower/version.log`（机器可读）+ git tag

## 二、什么算"行为变更"（必须 bump 的清单）

| 变更类型 | 级别 |
|---|---|
| 门禁判定逻辑变化（新增/修改检查规则） | PATCH/MINOR |
| 新增机制/组件/门禁组（如 --check、worktree 门禁） | MINOR |
| bug 修复不改语义（注释/文案） | 可不 bump |
| 工作流脚本行为变化（synova-commit/pre-push/hooks） | PATCH 起步 |

## 三、bump 流程（3 步）

```bash
# 1. VERSION.md 顶部插入新条目（含变更明细/验证/作者，格式见 V4.9.0 条目）
# 2. version.log 追加 JSON 行
# 3. 与代码改动同 commit 提交；合并 main 后打 tag
git tag V4.9.0 && git push origin V4.9.0
```

## 四、历史检讨（为什么今天才建这份规范）

- V4.8.0（08-15）之后，D467 挪 CI、D501 as-any 排除、D503 G12 时区、D506/D507/D508 批次——**六批行为变更全部未 bump**
- 根因：bump 靠记忆无物理强制。**待办（CT 队列）**: pre-commit 增加版本守卫——改 scripts/control-tower/ 或门禁脚本且 VERSION.md 无 bump → 硬阻断（物理强制，不靠自觉）

## 五、改 scripts/ 需认领 brief（D515 项10 / Codex P5）

G12（Task Scope 一致性）会拦截"暂存文件不在任何 brief Q2 范围内"的提交——**改 scripts/ 下的门禁/工作流脚本同样需要先认领 brief**：
1. `bash scripts/workflow/task-start.sh "任务描述"`，在 Q2 写集里列出全部要改的 scripts/ 文件；
2. 若被 G12 拦截，报错会列出越界文件——把对应文件补进 Q2 或移出暂存区。
Parallel 纪律（worktree 隔离 / 多 session 提交互斥）另见 PARALLEL-DISCIPLINE.md。

## 六、API 只允许传输，禁止 API merge（M15，D520 立）

**GitHub REST API 只允许 push 传输**（blob/tree/commit/ref 用于推送新文件）；**禁止用 API 做 merge 提交**——merge 必须走 git 本地（三方合并语义）或 GitHub PR merge 按钮。
- 违反 = 数据丢失级事故：**D509、D516 两次实证**（API merge 选错 base 树，直接覆盖他人交付，D481/D482 被覆盖后需人工 restore）。
- 根因：API 绕过 git 三方合并语义，无冲突检测、无共同祖先意识。

### 涉及树的写入后必做冒烟终验

任何经 API/git 对树的写入（推送/合并/restore）后：
1. `git diff <上一个已知好commit>..HEAD --stat` —— 核对只含预期变更；
2. 关键文件 `grep` 特征串（如刚交付的函数名/章节标题）——确认内容未被覆盖丢失；
3. 异常立即停手回报告，禁止"顺手修"。
