## 一、要解决的问题（实测，不是推测）

1. CTO 的派单文档复核**只是习惯**：`pre-dispatch-check.sh` 只在人工想起来时跑，没人跑也不会拦。
2. 该脚本曾在第②项崩溃（`$st（` 全角边界，D771 修）→ 第一遍复核结论**不完整**却看起来"跑过了"。
3. 复核结论依赖**跑它时的工作树**：工作树落后 main 时，plan 哈希与 task-state 集合都是旧的 → 假红/假绿（批五派单首轮即遇到：plan 报 v1.0@0b5c396a，实际 main 是 v1.2@8d331729）。

## 二、交付物（三项，缺一不可）

### 1. pre-commit 新门禁：派单文档强制复核
- 落点：`scripts/pre-commit-check.sh` 新增一组（沿用现有组号风格，建议「组 14/14: 派单文档复核」或并入现有组 6 的兄弟检查——**由你判断，但要写清接线理由**）
- 触发条件（条件跳过，保持 <1s）：staged 文件里有 `docs/synova/coordination/派单-*.md`
- 动作：对每个命中的派单文档跑 `bash scripts/control-tower/pre-dispatch-check.sh <doc>`；**非 0 退出 → 阻断**，输出里点名是哪几项没过
- 三态：`exit 0` 通过 / `exit 1` 有问题 / `exit 2` 环境降级（脚本缺失、无 git）→ 降级按现有惯例（本地软提示、CI strict 硬阻断），**不许静默当绿**
- 注入缝：提供 `SYNO_PRE_DISPATCH_DOCS`（或等价）覆盖被检文档集合，供测试注入
- 性能：条件跳过 + 单文档 <3s；**绝不把 pre-commit 拖过 60s**（V4.5.1 教训：超时 = 用户 --no-verify = 门禁链失效）

### 2. 测试（`tests/control-tower/` 下新增或扩展，覆盖正常/降级/边界）
- 绿：合格派单文档 → exit 0
- 红：故意写一个缺「依据计划」或缺自检段的文档 → 阻断并点名
- 降级：脚本缺失/无 git → exit 2 且**显式留痕**（不静默）
- 忽略：非 `派单-*.md` 的文档变更 → 跳过（不误拦）
- 生产接线检查：grep 新门禁在 `scripts/pre-commit-check.sh` 里真被调用（铁律 0-2 WIRE CHECK）

### 3. CTO 交付三件套固化（文档，双写）
- `.claude/skills/cto-handover/SKILL.md` **与** `.dsh/skills/cto-handover/SKILL.md`（**逐字一致**，组 13 硬阻断）新增一节：
  - **规则 1**：任何交付物（派单文档 / 计划变更 / 脚本 / 预设）**交付前必须过对应复核**：派单 → `pre-dispatch-check.sh`；控制塔脚本 → 该脚本的配对测试 + `pre-commit-check.sh`；技能 → `sync-dsh-skills.sh --check`。**没跑 = 没交付**（汇报里贴原始输出）。
  - **规则 2**：复核必须在**与 origin/main 同步的 worktree** 上跑（`git fetch --all` 后）；工作树滞后 → 假红/假绿，复核无效。
  - **规则 3**：**汇报必须包含「可直接转发给对应 session 的指令全文」**——执行方拿到即能开工，不需要再问（创始人 2026-09-15 要求）。
- 版本行 / 变更记录同步更新（技能自带版本号则 +1）

### 附：① 项已知假阳性（实测输入，必须在门禁里处理）

2026-09-15 三次实测：`pre-dispatch-check` 的 ①（任务号真实性）会把**规则/决策引用型 D#** 也当成任务号点名：
`D336`（TASK-ROUTING 的审计红线编号）、`D734`（PR 预算门禁编号）出现在派单正文里但它们不是任务。

要求：新门禁要么
- (a) 区分「任务引用」与「规则/决策引用」（例如只校验出现在 **任务表格行** 或带「任务/卡（D#）」标记的编号），或
- (b) 引入显式旁路标记（如 `规则:D336` / `参见 D336` 不参与校验），并在文档里写清规则；
两者选一即可，但**必须写测试覆盖**（正例：任务号缺 task-state → 红；反例：规则引用 → 不红）。
不做这一步，门禁上线第一天就会拦掉所有引用了历史决策号的派单文档（假红即噪音，噪音导致绕过）。
