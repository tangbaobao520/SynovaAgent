> 卡号: D924 | 域: mac（控制塔 / CI） | 状态: 已实现 | 生效: 2026-09-23
> 检查器: `scripts/control-tower/check-subprocess-protocol.sh` | 夹具: `tests/control-tower/check-subprocess-protocol.test.sh`
> 存量清单: `scripts/control-tower/subprocess-protocol-baseline.txt`（ratchet）

---

## 1. 问题

子进程（`curl` 等）的 **stdout 是单一语义通道**。当调用方需要在一次子进程调用里同时取回
**负载**（HTTP 响应体）与**元数据**（HTTP 状态码）时，一种常见但脆弱的做法是：

把元数据以**哨兵标记**（如 `__STATUS__:`）追加到负载流尾部，再用字符串分割还原。

**为什么坏**：分割的前提是"负载里不含该哨兵"。而这个前提**不可控**——HTTP 响应体由远端决定，
它可以合法地包含任意字符串，包括 `__STATUS__:`。一旦包含：

- 分割段数从 2 变成 ≥3；
- 取 `parts[1]` 当状态码 → 拿到的是**响应体里的内容**；
- 取 `parts[0]` 当负载 → 正文被**截断**在哨兵出现的第一个位置。

即：**正确性依赖一个攻击者/第三方可控的假设**。

## 2. 活证据（修复前，机械复现）

被测代码（修复前的对外行为）：

```
scripts/golden-scenarios/common/assert.ts:101
```

探针环境：本地 `python3 http.server` 返回 200，正文 `{"note":"__STATUS__:999","ok":true}`。

**红态（旧形态，字节级原始输出）**

```
0000000    {   "   n   o   t   e   "   :   "   _   _   S   T   A   T   U
```

```
stdout = '200'(3 字节) ; body = '{"note":"__STATUS__:999","ok":true}'   ← 完整
```

## 3. 协议条款

| 条款 | 内容 |
|------|------|
| **P1** | 子进程 stdout **只承载一个语义通道**。 |
| **P2** | 需要在同一次子进程调用中取回「负载 + 元数据」时，**必须分流**：负载走 `-o <临时文件>`（或独立 fd），元数据走 stdout（`-w` 模板**只放** `%{...}` 变量）。 |
| **P3** | **禁止**把元数据以自定义哨兵标记追加进 stdout 再用字符串分割定位。 |

**临时文件要求**：路径必须由语言运行时提供的临时目录 API 拼装（Node: `os.tmpdir()`；
Python: `tempfile`），**禁止硬编码 `/tmp`**（Windows 无此路径）。用后必须清理。

**参考实现**（`scripts/golden-scenarios/common/assert.ts` 的 `runHttp`）：

```ts
const bodyPath = path.join(os.tmpdir(), `synova-http-body-${process.pid}-${Date.now()}.tmp`);
try {
  const r = childProcess.spawnSync('curl', ['-sS', '-o', bodyPath, '-w', '%{http_code}', url], { ... });
  const status = Number((r.stdout || '').trim() || 0);      // 分流后 stdout 只含状态码
  const fileBody = fs.existsSync(bodyPath) ? fs.readFileSync(bodyPath, 'utf-8') : '';
  return { status, body: r.stdout === '' ? '' : fileBody + '\n' };   // 见 §5 字节级兼容
} finally {
  fs.rmSync(bodyPath, { force: true });
}
```

## 4. 检查规则

### R1 哨兵混流
**命中条件**：同一行同时含 —— ① `curl` 的写出口旗标（`-w` / `--write-out`）；② 引号内出现自定义哨兵
（正则 `__[A-Z][A-Z0-9_]*__`）。

### R2 哨兵分割解析
**命中条件**：同一行按自定义哨兵做字符串分割 —— 点 `split(` / `awk -F` / `IFS=`。

### 排除面（不排除即误报）
| 代号 | 排除条件 | 依据 |
|------|---------|------|
| **EX1** | 行含 bash here-string 记号（三个左尖括号） | 那是**输入重定向**，不是子进程 stdout 捕获；实测该记号与哨兵/分割的**零重叠**（见下） |
| **EX2** | 行含 `-o` / `--output` 旗标（**R1 专用**） | 负载已分流到文件 ⇒ stdout 只剩元数据 ⇒ **合规形态**；实测 `.sh`+`.ts` 口径**同行同时含 `-o` 与 `-w` 的 27 处**，不排除即 27 处误报 |

### 扫描面
仅**可执行源码**：`.sh .bash .ts .tsx .js .mjs .cjs .py .yml .yaml`；跳过二进制、`node_modules`、
`vendor`、`dist`、`build`、`.git`、`.codex`、`.synova-wt-*`。
文档（`.md`）不扫：文档**引用**坏形态是正当的（本规范 §2 自身即引用），协议约束的是代码。

## 5. 字节级兼容：body 末尾的 `\n`（遗留产物，显式保留）

**背景**：旧形态 `-w '\n__STATUS__:%{http_code}'` 的 `\n` 前缀被 `split` 留在了 `parts[0]`，
因此旧 `body` = **响应体原文 + 1 个 `\n`**。分流后若直接返回文件原文，body 会**少 1 字节** = 对外行为变更。

**实测（同一探针，两形态对照）**：

```
/plain (正文以 \n 结尾):
  旧 body = '{"ok":true,"note":"hello"}\n\n'
  新 body = '{"ok":true,"note":"hello"}\n' + '\n'  →  同上
/marker (正文无尾换行):
  旧 body = '{"note":"'                            ← 错乱
  新 body = '{"note":"__STATUS__:999","ok":true}\n'
```

**决定（D924）**：**保留**该 `\n`（`body = 原文 + '\n'`；stdout 为空时 `body = ''`，与旧形态一致）。
理由：它是修复前的**对外行为**；静默改语义会污染黄金场景历史判定的可比性
（`assert.ts` 的 `body` 被 `contains` / `notContains` 子串断言消费，`:189` / `:191`）。

**失效条件（何时可撤掉这个 `\n`）**：
1. 全部 `expect.json` 中 `http` 型断言的 `contains`/`notContains` 完成**重新基线**（逐条确认不依赖尾随 `\n`），**且**
2. 该变更随一次显式记录的行为变更卡（含 K3 复审）落地，**且**
3. `tests/control-tower/check-subprocess-protocol.test.sh` 用例 10 的
   `K924 字节级兼容` 源码护栏同步移除（不得只删其一）。
> 截至 2026-09-23T16:51:32+0800 测量：8 个 `GS-*/expect.json` 中 `http` 型断言与
> `contains`/`notContains` 的**组合命中数为 0**，但**这不构成可撤依据**——重新基线是逐条动作，不是一次 grep。

```
@input   — [--dir <路径>] [--baseline <文件>] [--verbose]
           注入缝（测试用）: SYNO_SUBPROC_GREP / SYNO_SUBPROC_FIND
@output  — 命中清单 + 末行 "SUBPROCESS-PROTOCOL: OK|VIOLATION(n)"

@degraded— 扫描器不可用 → exit 2 + stderr "degraded: ..." + <扫描根>/.codex/.../degraded-events.log
@error   — .code = SUBPROCESS_SCAN_UNAVAILABLE | SUBPROCESS_BASELINE_UNREADABLE
```

**探测可用性而非存在性**（D328 P1-1）：先 `command -v`，再**试运行**（`printf 'probe' | grep -q probe`）。

**ratchet**：`baseline` 列出 `<相对路径>:<规则>` 的历史存量；不在清单内的命中 = 新增违规。
清单**只可缩短**；增长 = 开口子，须 CTO 裁定。

> 同仓不同口径会得到不同数字（113 vs 104，见下"口径陷阱"）。

测量时刻：**截至 2026-09-23T16:51:32+0800**（`date +%Y-%m-%dT%H:%M:%S%z`）。

| 量 | 命令（`.sh`+`.ts` 口径） | 值 |
|----|------------------------|----|
| here-string 记号 | `git grep -c '<<<' -- '*.sh' '*.ts' \| awk -F: '{s+=$NF} END{print s}'` | 82 |
| `curl -o/--output` | `git grep -cE 'curl[^\|]*(-o\|--output)' -- '*.sh' '*.ts' \| awk -F: '{s+=$NF} END{print s}'` | 38 |

| 同行兼含 `-o` 与 `-w` | `git grep -nE 'curl[^\|]*(-o\|--output)[^\|]*-w\|curl[^\|]*-w[^\|]*(-o\|--output)' -- '*.sh' '*.ts' \| wc -l` | 27 |
| `http_code` | `git grep -c 'http_code' -- . \| awk -F: '{s+=$NF} END{print s}'` | 42 |

**口径陷阱（务必同址声明命令）**：
- `git grep -n '<<<' -- . | wc -l` → **104**（按匹配**行**；二进制文件压成 1 行 "Binary file ... matches"）
- `git grep -c '<<<' -- . | awk -F: '{s+=$NF} END{print s}'` → **117**（按每文件计数；`vendor/pandoc-skill/README.docx` 单文件计 14）
- 差 **13** = 该 docx；命令：`git grep -c '<<<' -- '*.docx'` → `vendor/pandoc-skill/README.docx:14`

⇒ 引用计数时**必须**连命令一起写；仅写"全仓 N 处"是不可核的。

## 8. 本规范的失效条件

1. **哨兵形态变化**：检查规则基于哨兵正则 `__[A-Z][A-Z0-9_]*__`。若改用其它分隔标记
   （如 `---MARK---`、`#|#`），R1/R2 将**漏检**。⇒ 新增标记形态时，必须同步扩展
   `SENTINEL_ERE` 变量并补夹具用例（R1/R2 各一条）。
2. **非 curl 子进程**：R1 的旗标识别**只覆盖 `curl`**。若其它工具（`wget`、`gh`、自研 CLI）
   采用同类混流做法，检查器漏检。⇒ 出现首个实例时扩展 `PAT_R1` 并补夹具用例。
3. **扫描扩展名**：仅 `.sh .bash .ts .tsx .js .mjs .cjs .py .yml .yaml`。新增语言（如 `.rb`）
   需加入 `find` 列表，否则该语言代码不受协议约束。
4. **EX2 过宽**：某行若在**无关位置**出现 `-o`（如路径名里），R1 会被误豁免。这是已知精度代价
   （换取 27 处真实误报的消除）；出现实际漏检时，须把 EX2 收紧为"与 `curl` 同命令段的 `-o`"。
5. **本规范整体**：若行业普遍移向"结构化 IPC（JSON 信封 / 独立 fd 协议）"且仓内 curl 调用被
   完全替换，本规范退化为对 `curl` 的历史约束——届时按控制塔既定流程归档（`archived`），
   并同步移除检查器与 CI 登记，**不得只删其一**。
