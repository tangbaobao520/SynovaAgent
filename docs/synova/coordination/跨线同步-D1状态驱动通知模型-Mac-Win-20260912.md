## 一、为什么要同步

D-1 不是「一个去重参数」，而是**通知语义的整体改写**，其落地横跨两条线：
- 哨兵引擎（通知决策、工单状态、升级规则）在 **Mac DSH 编码线**（`src/sentinel/`、`src/cron/`、`src/mcp/`）
- 老板侧的交互入口、周期报告、复盘沉淀、复发识别在 **Win 线**（`src/` 其余 + `extensions/` + `app/`）

若不同步，会出现两种坏结果：① 两线各按自己的理解实现通知语义（同一个问题两种行为）② 写集重叠互相踩（本仓已有 M8 教训）。

## 三、接口契约（先定接口，再各自动手）

**Mac 侧对外提供（Win 可依赖）：**
1. 工单/发现的状态查询与流转：`TicketStatus = open | acknowledged | resolved | dismissed` + `transitionFindingStatus(findingId, to)`（已存在，语义本次不破坏）
2. 通知是否发送的判定结果（含被判定的原因：新发现 / 实质变化 / 升级），供 Win 侧展示与解释
3. 升级事件的产出（含停滞天数、停滞原因字段）

**Win 侧对外提供（Mac 可依赖）：**
1. 老板对「节奏 / 格式」的选择结果 → 写入监测契约（来源：交互入口）
2. 周期报告生成（读 Mac 侧未关闭问题清单）
3. 复盘记录写入（关闭事件触发）

**待定项（需创始人拍板后由 dev-doc 落入 schema）：**
- **契约文件放哪**：建议 `extensions/monitoring-contracts/`（文件驱动、Win 域）——但若 loader 在 Mac，则**契约文件目录 = Win 写集、loader 代码 = Mac 写集**，必须显式声明，否则 verify-parallel 会判写集重叠
- **契约 schema 归属**：建议由 dev-doc 出（单一事实源），Mac/Win 均不得各自扩展字段

## 四、写集边界（硬约束）

- **Mac DSH 编码**只碰：`src/sentinel/`、`src/cron/`、`src/mcp/`
- **Win** 只碰：`src/`（除上述三目录）、`extensions/`、`app/`、`packages/`、`synova_worker/`
- **共享但不可双写**：`extensions/monitoring-contracts/`（暂定 Win 域，Mac 只读）、`extensions/sentinels/`（Win 域，Mac 只读）
- 任一侧若判断需要动对方目录 → **停手，报 CTO 与创始人**（不得自行跨界）
- 依赖关系：Win 的「周期报告」依赖 Mac 的「未关闭问题清单」接口；Mac 的「契约 loader」依赖 dev-doc 的 schema。**先定 schema，再并行实现**，避免互相等待

## 五、时序建议

1. **先**：dev-doc 出契约 schema（含字段、示例、默认值）
2. **并行**：Mac 做接线（步 1）+ 升级规则；Win 做交互入口（步 2）
3. **再**：Mac 出契约 loader；Win 出周期报告（步 3）
4. **最后**：复盘沉淀 + 复发识别（步 4）
5. 每步独立 PR；跨线依赖在 PR 描述里显式声明
