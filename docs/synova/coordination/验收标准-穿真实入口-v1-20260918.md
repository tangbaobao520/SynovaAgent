## 一、产品完成的判据（三条件同时成立）

| 条件 | 内容 |
|---|---|
| **A · 能力面** | 29 条线的关键能力被实现（各线验收点） |
| **B · 接线段** | 每个能力域 `wired = true` —— **由不变量（P-2）保证** |
| **C · 验证段** | `testedThroughEntry = true` ＋ **至少一次客户侧验证** —— **由验证基建（P-3）保证** |

> **「线全绿 ≠ 产品完成」**：线只能回答"有没有这个能力"，回答不了"这能力真的能用吗"。

## 二、五态（取代百分比）

| 态 | 判定 | 判定手段 |
|---|---|---|
| **缺** | 无实现 | 代码检索（唯一允许静态判定的态） |
| **写了没接** | 有实现、无接线 | **运行时不变量**（不是 grep） |
| **接了跑不通** | 有接线、起不来 | 冒烟启动 |
| **能跑未验证** | 能起、未穿真实入口 | e2e |
| **健康** | `live && testedThroughEntry` | 二者皆真 |

**报告口径**：`N 个健康 / M 个写了没接 / K 个缺` —— **离散计数，不用百分比冒充完成度**。

## 三、三层各自的验收方式（不得互串）

| 层 | 验收方式 | ❌ 不合格 | ✅ 合格 |
|---|---|---|---|
| **能力线** | 穿真实入口的集成用例 | "表已创建" | "跑一次真实哨兵，断言新增一行且 value 非空" |
| **前提清单** | **反向验证**（证明"不做会怎样"） | "支持 HTTP_PROXY 环境变量" | "只允许代理出网的环境跑真实调用成功，**且直连会失败**" |
| **线外工作项** | **三问自查** | "函数已被调用" | "注入 3 期历史后跑哨兵，断言 finding 含 trend 且方向正确" |

## 四、三问自查（每个工作项完成时必答，答不出 = 不算完成）

1. **谁调用它？** —— 给出**调用点 `文件:行`**，不接受"应该会被调用"。
2. **有没有一条测试穿过真实实现？** —— 不是 fake provider 顶替、不是 mock 管线。
3. **如果它明天被删掉，什么会坏？** —— 答不出来 = 没接线。

## 五、四条禁止（写进派单与规格的硬约束）

| 禁止 | 理由（实证） |
|---|---|
| ❌ 用 grep 命中当"完成" | 已发生 **9 次**"grep 通过但没接线"；门禁组 4 失效即此因（4a 只查"符号被引用"、4b 只查 3 个入口文件、且**只查本次新增文件**） |
| ❌ 用"文件已创建/表已建/字段已加"当验收 | 同型：`agent_metrics` 表结构索引齐全但**全树零写入者** |
| ❌ 在 `src/**` 加"测试专用开关"来让验收通过 | 会让生产代码带上测试分支；正确做法是走既有配置缝 |
| ❌ 为了变绿放宽排除清单（CI exclude / vitest config） | 放宽的是判定能力本身 |

## 六、四类验收样板（照抄即可）

| 类型 | 合格写法 |
|---|---|
| 存储类 | 跑一次真实哨兵 → 断言该表新增一行且 `value` 非空、`org_id` 正确 |
| 接线类 | 注入 3 期历史测量值后跑哨兵 → 断言 finding 的 payload 含 `trend` 字段且方向与注入数据一致 |
| 机制类 | 故意破坏该不变量（临时改一行）→ 断言流程**失败**而非静默通过 |
| 代理类 | 在只允许代理出网的环境跑一次真实 LLM 调用 → 断言成功**且直连会失败** |

## 九、小队模式（每任务一临时小队）的额外要求

> 依据：`docs/synova/coordination/小队模式-固化件-v1-20260919.md`（M1–M6，源自 D819 试点实测）

1. **一队一工作树**（M1）：队伍开工前须声明专用工作树路径与分支，且不得是任何在飞 session 的工作区。
2. **写集互斥 + 规格必含「写集冲突清单」**（M2）：队内任务 write_scopes 两两不得重叠（含前缀包含）；规格交付件缺该节 = 交付不完整。
3. **审计留队外**（M3）：K3 永不入队；队内角色称「自验」，结论只允许 `可提请独立审计` / `退回（附理由）`；出现"审计通过/审计合格"即违规。
4. **指令 ≠ 工具副作用**（M4）：派单/小队指令中的否定式要求必须先核对工具默认副作用（例：`synova-commit` 自带 push）；冲突时以工具链为准。
5. **证据写入归属**（M5）：证据文件按任务号命名或按任务分子目录；禁止跨任务重写他人证据文件；会被测试重写的证据须在卡里声明。
6. **队长收尾三件**（M6）：最终 diff / 自验结论 / 遗留清单，缺一不算收尾；队内任务逐张收口（官方不自动释放归属）。
7. **队长归属**：由**并行 CTO session** 担任（主线 CTO 只做全局把控与派单）。

> **⚠️ 落地状态**：上述 1–6 的**物理门禁**尚未落地（`scripts/control-tower/check-team-protocol.sh`，卡 D837）——**在它落地前，本章是纪律，不是门禁。**

## 十一、验收判定只有三态（创始人 2026-09-20 裁决）

> **「有条件通过」= 未通过。** CTO 不得以"有条件通过"放行任何交付，也不得据此启动下一批任务。

| 判定 | 含义 | 后续动作 |
|---|---|---|
| **通过** | 条件全部满足、证据齐、独立审计结论到位 | 可进下一批 |
| **退回** | 任一必交件缺失 / 数字与实测不符 / 条件未闭环 | **该件**先闭环再复验（闭环前不计入"已交付"、不得对外称通过）；**但不得因此冻结与之无依赖的其它任务** |
| **关闭** | 任务取消（须写理由码） | — |

**闭环定义**：每条条件必须有自己的**卡片/编号**、**责任人**、**可验证的完成证据**；CTO 逐条复验通过后，整件才转"通过"。
**禁止**：把条件写在汇报里就算闭环；把"待审计"当"已审计"；把未闭环件列入"已交付"；用"有条件通过"这种中间态放行。

**并行纪律（创始人 2026-09-20 追加）**：退回**只约束该件自身**，不约束全局。
- **有依赖** → 老实串行（谁等谁的接口 / 文件 / 结论）；
- **无依赖** → **照常并行开工**，不因为某件未闭环就把整条产线停住；
- 判断依据只有一条：**两件之间是否真的互相依赖**，不是"有没有未闭环件"。
