# A线 产品完整性缺口审计 — 研究方案 v1.2

> 2026-08-01 | 定位：以四条件（A/B/C/D）为骨架，系统性核对"权威文档承诺 vs 代码现实"，产出可排期、可复现、证据分级的 P0/P1/P2 缺口清单

---

## 零、研究背景

1. **项目阶段**：17 份权威文档完成，开发者任务地图 v2 已过时（D281–D285 等已完成），控制塔 V4.5.1 门禁 17/17，但控制塔自诊断本身失真（信号文件被删、完成度引擎批量误判）——"文档说 100% 但现实不是"的教训要求一次独立证据审计
2. **总计划驱动**：世界级产品研究总计划 G1–G6 假设（结论真实性、Agent 自主性、无数据诊断、交付物、进化飞轮、自诊断失真）需要证据验证/推翻
3. **演示压力**：盛和塾 8 月演示需要"哪些缺口演示前必修"的可信答案

## 一、研究问题

- **Q1 现状**：四条件各自的真实完成度、关键链路、证据是什么？
- **Q2 缺口形态**：每缺口属于"没写 / 写了没接 / 接了没验 / 文档已废弃"哪一类？
- **Q3 致命性**：哪些是演示前必修（P0）？判定依据是什么？
- **Q4 地图更新**：任务地图 v2 哪些已完成/过时/新增？如何衔接？

## 二、定位、边界与定义冻结

**做什么**：证据审计（只读）、四态分级、证据强度标注、P0/P1/P2 清单、任务地图差异表、G1–G6 验证。

**不做什么**：新功能设计、代码修改、控制塔修复（已转交）、实现 direction-monitor/middle-evolution/N13/NCI（只定案）。

**定义冻结条款**：四条件定义在审计期间冻结，审计只回答"当前系统是否满足当前定义"。审计结束后若发现定义本身有缺陷，由创始人+GA 确认是否修订——审计结论本身不用于重新定义条件。

## 三、审计目标与方法

### 3.1 文件范围（不限于 src/.ts）

| 类别 | 路径 |
|------|------|
| 代码 | src/（routes/agent/sentinel/l3/l4/loops/cron/store/services）、electron-main.ts、server.ts |
| 专家配置 | expert/*/manifest.json + RULES/THEORY/TOOLS/IDENTITY/PROMPT |
| 本体定义 | extensions/ontology/（manifest.json、edge-types、node-types、field-mappings） |
| 哨兵配置 | extensions/sentinels/*/manifest.json（存在则审，不存在=发现项） |
| 剧本/Skill/行业 | playbooks/*.yaml、extensions/skills/*/SKILL.md、extensions/industries/*/ |
| 前端资产 | app/*.html、app/js/*.js、app/css/*.css |
| 测试资产 | tests/（含 golden-cases fixture）、tests/ci/ |

原则：审计所有影响系统行为的文件；目录不存在本身即发现项。

### 3.2 四态判定

- ✅ **存在且接线**（证据强度≥中）
- ⚠️ **存在但未接线或半成品**
- ❌ **不存在**
- 📄 **文档承诺已废弃/文档滞后**——先查后续文档修正、废弃决策记录、GA 确认；确认后标"文档滞后，待更新"，不是代码缺陷

### 3.3 证据强度分级

| 级别 | 定义 |
|------|------|
| **S 强** | 端到端链路追踪完成（入口→产出全路径可验证） |
| **M 中** | grep 到明确调用方，且调用方在依赖图中可达 |
| **W 弱** | 仅 import/类型引用，未找到实例化或调用 |
| **推测** | 仅凭文件名/模块名推测——不得进入正式报告 |

约束：P0 判定不得以 W 弱证据或推测为唯一依据；正式报告只收 S/M/W，推测单独记录为"待查线索"。

### 3.4 可复现性

- 审计脚本固化为 `_tools/audit-grep.sh`：所有搜索模式写入脚本，不手动拼命令
- 每次审计记录：commit hash + 工作区状态快照（git status 摘要），报告头部必附
- 每项三态判定附完整 grep 命令 + 文件范围
- 机制：以工作区现状为被审计事实，同时用 git HEAD 双核对区分"未提交删除/新增"，不 stash（避免破坏他人未提交工作）

## 四、研究任务（前置 + 5 章）

- **前置 0｜审计工具固化**：audit-grep.sh + 证据日志模板 + 提交哈希记录
- **第一章｜条件A 部署独立**：多租户隔离强度、权限矩阵、安装引导、启动链路
- **第二章｜条件B 诊断自主**：哨兵真实注册数定案、direction-monitor/middle-evolution/NCI 接线定案、loop-4/5 处理器、无人值守链路端到端
- **第三章｜条件C 结论有用**：黄金数据集 CI 执行、报告可读性、GA 验证闭环、N13 回流链、Goal/Proposal 消费链
- **第四章｜条件D 持续运行**：重启/停机/故障恢复、Cron 持久化、备份/升级回滚、长期运行验证
- **第五章｜缺口分级与地图更新**：P0 初判 + 任务地图 v2 差异表 + G1–G6 验证

## 五、分级矩阵

| 维度 | 档位 |
|------|------|
| 影响面 | 单点 / 单模块 / 核心链路 / 全系统 |
| 阻塞程度 | 可绕过 / 阻塞单功能 / 阻塞核心链路 / 阻塞启动 |
| 演示可见度 | 不暴露 / 可能暴露 / 必然暴露 |

**P0** = 影响面≥核心链路 + 阻塞程度≥阻塞核心链路 + 演示可见度≥可能暴露
**P1** = 影响面≥单模块 + 阻塞单功能及以上，但演示不必然暴露
**P2** = 其余（影响面单点、可绕过、演示不暴露）

**演示可观察性两阶段**：第五章产出 P0 初判（基于现有演示材料推断触达清单）；P0 终判在 B 线演示剧本产出后进行——只列演示脚本实际触达的功能点，未触达的自动降级。

## 六、分治边界条件

出现以下任一情况，暂停当前章节，同步后再定下一步：
1. 问题使后续章节审计范围失去意义
2. 问题修复预计 >1 天工作量且影响演示（需创始人确认是否转入排期）
3. 问题揭示前面章节的审计方法存在系统性缺陷

## 八、验收标准

1. 四条件各有定量完成度 + 四态证据表（每行：文件:行号 + 证据强度 S/M/W + grep 命令）
2. 哨兵数量之谜查清，给出真实生效注册数与机制
3. direction-monitor / middle-evolution / N13 / NCI 各有定案
4. P0/P1/P2 按矩阵量化判定；P0 附"演示可见性"证据；无 W/推测支撑的 P0
5. 任务地图 v2 差异表（已完成/过时/新增）
6. G1–G6 逐一标注验证/推翻/待数据，更新总计划
7. 每份报告头部含 commit hash + 工作区快照；同 commit 重跑审计脚本结果一致
8. 📄 状态只用于"文档滞后"发现，不混入"代码缺陷"

## 九、研究局限与对抗性验证

**局限**：只读静态审计（不跑全量测试）；接线判定依赖 grep 证据；效果性承诺只能验证机制存在性，效果真实性标注"待客户数据验证"。

**对抗性验证**：每个 P0 反向质询"若不影响演示，错在哪"；四态强制带证据；每章自检 5 问；推测一律隔离不入报告。
