## 1.0 全包族总览

Harness 是约 200 个包（group/pkg 两级）的 monorepo，分 12 大组。核心分层：

| 分组 | 包数（估） | 职责 | 与 Synova 关系 |
|------|:---:|------|---------------|
| core | 7 | 产品 API 脊柱：session / agent / agent-loop / tools / system-prompt / scope | Synova 的 ConversationEngine + L2 编排 |
| llm | 5 | 模型适配 seam + DeepSeek/PiAI 提供者 + 重试 + token 计费 | Synova 的 providers/（DeepSeek/OpenAI/Gateway） |
| session | 12 | 事件溯源持久化（jsonl/sqlite）+ 投影 + 标题 + 遥测 | Synova 的 SessionStore（L5） |
| subagent | 10 | 子 Agent seam：acp/claude-code/codex/dsh-sdk/fork/spawn 多后端 | Synova 的 SubAgentCoordinator |
| sandbox | 4 | 进程沙箱（landlock / windows-acl） | Synova 的 security/DataBoundary |
| workflow | 4 | 模型写脚本、fan-out 子 Agent | Synova 无对应（❌） |
| goal / schedule / feedback / spill | 11 | 目标 / 调度 / 反馈 / 溢出 | Synova 的 Goal / 六循环 / N13 / 溢出循环 |
| hooks | 3 | Claude Code / Codex 桥接 | Synova 无对应（❌） |
| skill / mcp / plan / todo / guard | 12 | 技能 / MCP / 计划 / 待办 / 循环卫生 | Synova 的 Skill-Tool 体系（部分） |
| client/ui | 40+ | Web 前端 + 全部 UI 组件 | Synova 的 app/（report/dashboard） |
| typert / sdk / api / acp | 12 | 类型图 / RPC / BFF / ACP 协议 | Synova 无对应（❌） |

**关键结论**：Harness 的能力面远宽于 Synova，但**它没有任何"领域知识"**——没有因果本体、没有诊断、没有专家、没有增长导航。它是"纯底座"，这是本次战略判断的第一块基石。

## 1.1 Cordis：时空可组合性（范式地基）

来源：[cordis-primer.md](/D:/deepseek-harness/docs/cordis-primer.md) + 36氪对 Cordis 论文的解读。

**五个思想**：

1. **插件**：一个实现 `Service` 的对象（函数带 `inject`/`apply(ctx)`，或 `Service` 子类）
2. **上下文**：服务仓库，插件通过 `ctx.<key>`（如 `ctx.tools`/`ctx.llm`/`ctx.sessions`）找服务，**而非 import 具体实现**
3. **依赖注入**：`inject` 声明所需服务，加载顺序由服务依赖表达，非手动 boot 排序
4. **类型化事件**：TypeScript declaration merging 声明事件，四种分发模式（下表）
5. **可逆副作用**：所有注册（prompt 段/工具 schema/适配器/监听器）走 `ctx.effect()`/`ctx.on()`，卸载可逆回退

**四种事件分发模式**：

| 模式 | await? | 顺序 | 返回值 | 用途 |
|------|:---:|------|:---:|------|
| `emit` | 否 | 注册序观察 | 无 | 广播通知 |
| `waterfall` | 否 | 注册序观察 | 有 | 中间件包装（`next()` 委托 / 不调 `next()` 短路） |
| `parallel` | 是 | 并行 | 无 | 扇出 |
| `serial` | 是 | 注册序 | 有 | 有序执行 |

**"时空可组合性"的严格定义**（36氪引 Cordis 论文）：
- **时间**：插件卸载后，它注册的服务、事件、副作用**随之撤销**
- **空间**：插件声明依赖，其他组件变化时**重新建立协作关系**
- 论文（8-13 预印本）实现含副作用追踪、依赖解析、配置协调、热更新——瞄准"自我演进的 Agent Harness"

**Synova 对照**：❌ 无对应。Synova 的五层架构是"静态分层"（L1-L5 固定依赖），不是"可逆插件组合"。这是 Harness 最根本的范式差异——Synova 扩展靠改代码，Harness 扩展靠挂插件。

## 1.2 无特权核心 + 可替换 loop

来源：core/agent + core/agent-loop README。

- `dsh-agent` 定义 `Agent` 接口 + registry + `agent/*` 事件词汇，**零 loop 依赖**——"the loop is swappable"（loop 可替换）
- `dsh-agent-loop` 是**唯一包含具体 loop 逻辑的包**："This is the only package in the harness that contains concrete loop logic. Everything else is an abstract service or a plugin."
- 模型适配器、工具注册表、session log、agent loop 本身都是插件，任何部分从配置替换
- create/resume 是 **rollback-covered transaction**：构造私有 session/agent/scope → setup → 进 registry → 发 `session/created`+`agent/created` → 才启动 driver；ID 冲突时 loser 回滚全部私有资源

**Synova 对照**：⚠️ Synova 的 ConversationEngine / agent-loop 是特权核心，扩展靠改代码（铁律 39 五层架构是静态层）。Synova 没有"loop 可替换"的概念。

## 1.3 事件溯源 session log（唯一事实源）

来源：core/session + session 包族 + architecture.md。

- Session 是 **append-only `SessionEvent` log**，agent 全部交互历史的唯一事实源
- **LLM 消息历史是"派生"的**：`deriveMessages()` 从 log 投影，不单独保存
- 维护一个 **surface 层**（message-producing events 的有序投影）用于高效派生和压缩
- **Model-visible ⟺ logged**：凡进模型请求的必可从 log 重建，runtime invariant 强制——新增 model-visible 输入必须新增 session event
- fork / resume / transcripts / telemetry / persistence 全部从这条流派生
- 持久化多后端：jsonl（`session-persistence-jsonl`，koffi MoveFileExW 写穿）、sqlite（`session-persistence-sqlite`）
- 遥测：`session-telemetry-otel`（OpenTelemetry）
- 完整事件流可回放（Trajectory 视图），但包含代码/凭证线索/文件内容——可回放提高可审计性也扩大数据面

**Synova 对照**：❌ Synova 的 SessionStore 是普通存储，无"事件溯源唯一事实源 + model-visible ⟺ logged"纪律。这正是 C 线 S3-5（自诊断可信度）、S0（信任建立）的深层根因——没有一条可回放的真相流。

## 1.4 capability seam 三角色

来源：architecture.md + subagent/llm/workflow/sandbox README。

**seam = Service Definition（声明接口）/ Service Provider（实现）/ Consumer（使用）三角色**，缺一不可算 seam。

关键 seam 实例：

| seam | Definition | Provider（可换） | Consumer |
|------|-----------|-----------------|---------|
| llm | `ctx.llm`（流式调用 + 适配器注册） | deepseek / pi-ai | agent-loop、所有插件 |
| subagent | `ctx.subagents` | fork-in-process / spawn-in-process / acp / claude-code / codex / dsh-sdk | tool-subagent、workflow |
| workflow | `ctx.workflowEngine` | worker-thread（未来可换 process/sandbox） | tool-workflow |
| sandbox | `ctx.sandbox` | sandbox-local（landlock / windows-acl） | shell/fs/subprocess 消费方 |
| fs / shell / terminal / web | 各自 seam | local / sandbox / e2b 多后端 | model-facing tools |
| storage | `ctx.storage` | storage-json / storage-sqlite | session 等 |

**"换 provider 换整个产品"**：filesystem 和 subprocess 共享一个执行世界，指向远程沙箱就同时移动 Bash/PTY/LSP，无 provider fork。

**subagent seam 的深度**（远超 Synova）：`start`（one-shot）/ `startContinuable`（可继续子 agent）/ `followup` / `interrupt` / `reportFrom` / `listChildren` / `listDescendants`——支持跨进程、跨产品（claude-code/codex 作为子 agent）、可继续子 agent 的完整生命周期。

**Synova 对照**：⚠️ Synova 有 SubAgentCoordinator / ModuleRunner，但没有"三角色 seam + provider 可换"的统一抽象。Synova 的 providers/（LLM）是 seam 雏形，但 fs/shell/subagent 没有 seam 化。

## 1.5 四种 Agent 模式

来源：36氪 + agent-presets（code/cordis/minimal/standard）。

| 模式 | 工具集 | 用途 | 风险 |
|------|--------|------|------|
| standard | 相对完整 | 日常 Agent 任务 | — |
| minimal | 仅 Shell + 文件编辑 | 基准测试（隔离外围工具差异，直观察模型自主规划/改码/终端） | — |
| PTC（Programmatic Tool Calling） | 模型先生成代码、代码组织多轮工具调用 | 减少往返、降低上下文堆积 | 代码获得更强调度能力，需更强沙箱/超时/配额/权限 |
| creative | Agent 检查运行时、内存中试验 Cordis 插件、组合新运行模式 | 自指式实验，为自我调整留接口 | 距稳定"自我进化"仍有长工程路径 |

**Synova 对照**：❌ Synova 只有一种运行模式（FDE 按需 + Sentinel 定时），无"模式"抽象。PTC 与 creative 值得关注——creative 是"自我演进 Agent Harness"的实验接口，与底座研究"持续学习工程落点在 Harness"直接呼应。

## 1.7 工程化体系

来源：AGENTS.md + package.json。

| 机制 | 内容 | Synova 对照 |
|------|------|-----------|
| Agent Notes 记忆 | `.agents/notes/` 四态（proposed/implemented/archived/rejected），非平凡变更强制带 Note | ⚠️ Synova 有 memory/ + 铁律，但无结构化四态 |
| snapshot 测试 | keyless 回放 + 期望输出对比，模型/用户可见变化强制快照 | ❌ 无对应（Synova 是 vitest 单测） |
| verify-* 门禁全家桶 | 30+ verify 脚本（doc/type/package/note/skill/license 等） | ⚠️ Synova 有 pre-commit 13 组 |
| typert 类型图 | 类型图生成器 + loader + runtime registry | ❌ 无对应 |
| strict:true + 100% 覆盖率门禁 | 每文件 100% 覆盖是 CI gate | ⚠️ Synova 有 strict + 测试门禁，非 100% |
| 克隆检测 | jscpd 跨文件 TS 克隆检测 | ❌ 无对应 |

**Synova 对照总评**：Synova 的工程纪律（铁律 + pre-commit + 接线审计 + 契约门禁）在**防错**维度已到极致，但 Harness 在**可复现性（snapshot）、可审计性（event log）、可组合性（plugin）**三个维度领先——这三者正是"为未来迭代打基本功"的关键。

## 1.8 第一章结论（Synova 战略判断的第一块基石）

1. **Harness 是"纯底座"**：能力面极宽（200 包），但零领域知识——没有因果本体、诊断、专家、增长导航。
2. **范式差距是真实的**：无特权核心 + 事件溯源 + seam 三角色，三者 Synova 都没有，这是结构性差距，不是功能差距。
3. **Synova 的自研通用工程（Loop/控制塔/哨兵调度/契约门禁）已被 Harness 底座"通用化"**——这些不再是护城河。
4. **Synova 的护城河只剩领域深度**：42 边因果本体、7 位专家、25 测量器+20 哨兵、诊断方法论、GA 人机闭环、行业模板、增长导航、无数据诊断——这 8 项 Harness 一个都不提供，且从其定位看不会提供。（"企业多用户"是【双缺】机会——Harness 没有、Synova 也仅设计未全量验证，属差异化方向而非已有护城河。）
