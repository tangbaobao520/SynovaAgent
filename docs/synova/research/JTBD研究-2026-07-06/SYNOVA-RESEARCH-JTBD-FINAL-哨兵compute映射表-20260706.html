二、Compute函数清单

22个新增（21全新 + 1扩展）compute函数，按7层参数架构组织。每个函数定义其数学逻辑、图遍历路径、服务JTBD聚类、时间约束和对抗性边界。

2.1 L1 产出与效率层（8个新增）

L1-01: computeProductionOutput P0

数学公式/逻辑outputVolume = SUM(PRODUCES.产出量); outputValue = SUM(PRODUCES.产出值); yieldRate = 合格产出/总产出; defectRate = 1 - yieldRate
消费的边参数PRODUCES (outputVolume, outputValue, yieldRate, defectRate)
图遍历路径Activity → [PRODUCES] → ResourcePool(产出)
服务JTBD聚类ALLOCATE(Customer/Operation): U-JTBD-0014/0037; DIAGNOSE(Customer/Product): U-JTBD-0079/0081
时间约束实时(小于5m) 到 月(小于4h)，取决于ERP接入延迟
对抗性边界(1) 产出量定义歧义——是否包含返工品？需与MES对齐；(2) 多单位产品无法直接SUM——需标准化为标准工时当量；(3) 自制vs外协的PRODUCES归属——外协产线是否入图？

L1-02: computeCapacityUtilization P0

数学公式/逻辑utilizationRate = 实际产出/理论产能; bottleneckId = argmax(utilizationRate_i); overtimeRatio = 加班工时/标准工时
消费的边参数PRODUCES (产能), CONSUMES (工时)
图遍历路径Operation → [PRODUCES] → ResourcePool(产能) + Operation → [CONSUMES] → ResourcePool(工时)
服务JTBD聚类ALLOCATE(Customer): U-JTBD-0014; CONTROL(Operation): U-JTBD-0170/0174
时间约束实时(小于5m)
对抗性边界(1) 理论产能定义漂移——设备升级后基准未更新；(2) 瓶颈随排程策略动态变化——静态利用率不能反映真实约束；(3) 加班工时来源——考勤系统vs ERP工时汇报口径不一致

L1-03: computeQualityTraceability P1

数学公式/逻辑逆向追溯：质量问题沿PRODUCES/DEPENDS_ON反向至供应商/工序/操作员; cpkByLine = MIN(USL-mu, mu-LSL)/(3sigma); attributionProbability = BayesianUpdate(先验缺陷率, 新批次证据)
消费的边参数PRODUCES (缺陷批次, CPK), DEPENDS_ON (供应商溯源)
图遍历路径Product → [PRODUCES] → 质量问题 → 反向追溯 Supplier/Operation/Resource
服务JTBD聚类DIAGNOSE(Customer/Product): U-JTBD-0081, U-JTBD-0054
时间约束周(小于1h)
对抗性边界(1) 批次追溯粒度不足——ERP只到批次号不到单件；(2) 零缺陷批次的CPK无意义；(3) 来料缺陷vs制程缺陷无法区分时，归因概率坍缩为50%

L1-04: computeFullCostAllocation P0

数学公式/逻辑fullyLoadedCost = 直接材料 + 直接人工 + 制造费用分摊 + 退货成本 + 特殊要求成本; indirectCostShare = 总间接成本 x 驱动因素占比(活动成本法ABC)
消费的边参数PRODUCES (直接成本, 间接成本分摊), CONSUMES (资源消耗驱动)
图遍历路径Product/Order → [PRODUCES] → ResourcePool(成本) + 驱动因素分摊
服务JTBD聚类EVALUATE(Customer/Product): U-JTBD-0119/0121/0122; ALLOCATE(Customer): U-JTBD-0013/0015
时间约束周(小于1h) 到 月(小于4h)
对抗性边界(1) 间接成本分摊的受益原则在共用产线时会崩溃；(2) ABC驱动因素选择的主观性——管理层有动机选有利的驱动因素；(3) 退货/售后成本滞后——本期成本包含上期退货

L1-05: computeMaterialAvailability P1

数学公式/逻辑bomCompleteDate = MAX(各物料最早到齐日期); earliestAvailableDate = MAX(bomCompleteDate, 产线最早排程日); inventoryCoverage = 库存/日均消耗; criticalPathMaterial = argmin_negative_slack(物料交期 - 计划开工日)
消费的边参数PRODUCES (物料产出), FLOWS_TO (采购流程), DEPENDS_ON (BOM依赖)
图遍历路径Product → [DEPENDS_ON] → Supplier → [PRODUCES] → 物料
服务JTBD聚类ALLOCATE(Customer/Operation): U-JTBD-0014/0037
时间约束实时(小于5m)
对抗性边界(1) 供应商承诺交期vs实际交期的系统性乐观偏差；(2) BOM替代料未建模时给出缺料的假阳性；(3) 安全库存设置过低会误判、过高会隐藏真实紧张

L1-06: computeOperationPerformance P0

数学公式/逻辑onTimeDeliveryRate = 准时交付订单数/总订单数; qualityPassRate = 一次合格数/总产出数; complaintCount = COUNT(客户投诉); delayPenalty = SUM(延迟罚款); deliveryTrendSlope = 线性回归(准时率, 最近12月)
消费的边参数PRODUCES (履约指标: 准时率, 合格率, 投诉数)
图遍历路径Operation → [PRODUCES] → 履约指标
服务JTBD聚类DIAGNOSE(Customer): U-JTBD-0079; EVALUATE(Customer): U-JTBD-0123/0124
时间约束周(小于1h)
对抗性边界(1) 准时的定义不一致——客户期望日vs承诺日vs系统录入日；(2) 一次合格率需要MES/ERP联动——单一数据源会低估；(3) 投诉数有季节性——大促后投诉暴增不代表质量恶化

L1-07: computeProductionDifficulty P2

数学公式/逻辑difficultyScore = w1x换线频次 + w2x最小起订量偏离 + w3x特殊工装占比 + w4x工艺步骤数; changeoverCount = COUNT(产线切换)
消费的边参数PRODUCES (换线频次, 起订量, 工装), COUPLES (工艺耦合)
图遍历路径Product/Order → [COUPLES] → Operation 提取工艺难度
服务JTBD聚类DESIGN(Customer): U-JTBD-0164; EVALUATE(Customer): U-JTBD-0124
时间约束月(小于4h)
对抗性边界(1) 权重主观性——需要行业基准校准；(2) 换线频次用于衡量难度——高换线频次可能来自排程优化能力差而非产品本身复杂；(3) 新产品无历史数据

L1-08: computeScheduleImpactSimulation P1

数学公式/逻辑delayChain = 拓扑推演(急单插入后各订单的顺延时差); penaltyEstimate = SUM(受影响的订单罚金x延后概率); capacityRecoveryPlan = 最短时间恢复原计划的加班/外包方案
消费的边参数AFFECTS (插单影响), PRODUCES (排程约束)
图遍历路径Order(急单) → [AFFECTS] → Order(被延期) 模拟连锁影响
服务JTBD聚类ALLOCATE(Customer): U-JTBD-0014; CONTROL(Operation): U-JTBD-0170
时间约束实时(小于5m)
对抗性边界(1) 实际排程有大量隐性缓冲——模拟延期的量级会被高估；(2) 工人对急单的加班意愿不可预测；(3) 模拟结果可能自实现——看了模拟结果后改变行为

2.2 L2 价值流转层（7个新增）

L2-01: computeCustomerProfitability P0

数学公式/逻辑cumulativeProfitMargin = SUM(订单收入 - 全成本) / SUM(订单收入); profitContribution = 该客户利润/总利润; revenueShare = 该客户收入/总收入; costToServe = 售前成本 + 履约成本 + 售后成本
消费的边参数PRODUCES (成本), FLOWS_TO (收入流), BUYS_FROM (订单)
图遍历路径Customer → [BUYS_FROM] → Order → [FLOWS_TO] → 利润
服务JTBD聚类EVALUATE(Customer): U-JTBD-0119/0120; ALLOCATE(Customer): U-JTBD-0012/0013
时间约束周(小于1h) 到 月(小于4h)
对抗性边界(1) 分摊成本法的选择会影响客户利润排名；(2) 战略客户在纯利润排名中会垫底——需复合评分；(3) 新客户LTV的预测误差会被放大

L2-02: computeCustomerValueScore P0

数学公式/逻辑compositeScore = w1x利润贡献百分位 + w2x战略重要性(0-10) + w3x增长潜力(增长率Z-score) + w4x关系依赖度; weights可配置
消费的边参数PRODUCES (利润), DEPENDS_ON (关系依赖), FLOWS_TO (战略价值)
图遍历路径Customer → [PRODUCES] → 利润 + [DEPENDS_ON] → 关系 + [FLOWS_TO] → 战略价值
服务JTBD聚类DESIGN(Customer): U-JTBD-0164; ALLOCATE(Customer): U-JTBD-0010/0012; EVALUATE(Customer)
时间约束月(小于4h)
对抗性边界(1) 权重是政治问题而非技术问题——不同角色需要不同权重向量；(2) 战略重要性的主观评分可能被销售操控；(3) 排名波动——客户可能月月变换分级，需稳定性调整

L2-03: computeChurnDecomposition P0

数学公式/逻辑orderVolumeTrend = 线性回归(月下单量, 12m); ndrDecomposition = Shapley分解(NDR下降中各因素贡献); churnAttributionWeights = {价不善, 质不满, 竞品替代, 业务萎缩, 其他}
消费的边参数BUYS_FROM (下单量趋势), AFFECTS (归因), COMPETES_WITH (竞品替代)
图遍历路径Customer → [BUYS_FROM] → 下单量时序 + 关联竞品/产品使用/履约
服务JTBD聚类DIAGNOSE(Customer): U-JTBD-0079/0080/0082
时间约束周(小于1h) 到 月(小于4h)
对抗性边界(1) 归因权重受数据可用性限制——竞品因素可能因数据缺失而被低估；(2) CORRELATION ≠ CAUSATION——下单量下降与履约延迟相关但不一定是因果；(3) 小样本客户归因不稳定

L2-04: computeAccountReceivableRisk P1

数学公式/逻辑overdueDaysP90 = P90(逾期天数); creditRiskScore = f(逾期历史, 行业信用趋势, 客户规模); 行业信用趋势从外部工商数据/行业指数获取
消费的边参数FLOWS_TO (账期数据), DEPENDS_ON (关系依赖)
图遍历路径Customer → [FLOWS_TO] → 账期数据
服务JTBD聚类ALLOCATE(Customer): U-JTBD-0012
时间约束周(小于1h)
对抗性边界(1) 逾期不一定是风险信号——大客户战略延期不是信用问题；(2) 行业信用趋势数据滞后——外部数据更新周期通常季度级；(3) 中小客户外部工商数据稀疏

L2-05: computeCustomerMigration P1

数学公式/逻辑switchingCostEstimate = 实施成本 + 数据迁移成本 + 培训成本 + 新供应商磨合成本; competitorMigrationRate = 品类内客户转向竞品占比; winBackProbability = Bayesian(历史挽回率, 最近互动信号)
消费的边参数BUYS_FROM (购买行为), COMPETES_WITH (竞品替代)
图遍历路径Customer → [BUYS_FROM] → 品类购买 + [COMPETES_WITH] → 竞品替代
服务JTBD聚类ALLOCATE(Customer): U-JTBD-0008/0017; DIAGNOSE(Customer): U-JTBD-0082

L2-06: computeChannelROI P0

2.3 L3 因果推断层（3个新增 + 1个扩展）

L3-01: computeShapleyAttribution P0

数学公式/逻辑对K个因素计算贡献: phi_i = SUM_{S subset N\{i}} [|S|! (K-|S|-1)! / K!] x [v(S U {i}) - v(S)]; 其中v是指标函数的子集价值
消费的边参数AFFECTS (多因素归因)
图遍历路径事件集 → [AFFECTS] → 结果 → 多因素解耦
服务JTBD聚类DIAGNOSE(Customer/Product/Resource): U-JTBD-0079/0081/0086/0090
时间约束月(小于4h) — 计算复杂度O(2^K)
对抗性边界(1) 因素数量K>10时计算成本爆炸——需特征聚类预降维；(2) 因素间交互效应会使Shapley值解释复杂；(3) 需要反事实基线——没有基线时Shapley分解无意义

L3-02: computeCausalSequence P1

数学公式/逻辑基于First-Mover Principle：在所有偏离指标中，最早偏离时间的指标是root cause候选; causalOrder = TOPOLOGICAL_SORT(因果图, 时序偏离排序); rootCauseProbability = Bayesian网络后验
消费的边参数AFFECTS (因果链), DEPENDS_ON (依赖排序)
图遍历路径时序因果链追溯（First-Mover Principle）
服务JTBD聚类DIAGNOSE(all): U-JTBD-0079/0081/0086; PREDICT(all)
时间约束周(小于1h)
对抗性边界(1) 共同原因——两个指标同时偏离是因为隐藏的第三因素；(2) 观测粒度不足——如果两个偏离在同一周内发生，顺序无法确定；(3) 因果图本身需要预先构建——本体层图结构决定追溯上限

L3-03: computeScenarioSimulation 扩展 P0

数学公式/逻辑扩展：增加蒙特卡洛模拟 + 多因素联动; scenario_i = baseline x (1 + SUM_{factor} delta_i x elasticity_i); 乐观/基线/悲观三场景输出; sensitivityMatrix = 因素elasticity矩阵
消费的边参数AFFECTS, PRODUCES, FLOWS_TO (多因素联动)
图遍历路径蒙特卡洛反事实模拟
服务JTBD聚类DESIGN: U-JTBD-0164/0166; ALLOCATE: U-JTBD-0010/0033; PREDICT
时间约束月(小于4h)
对抗性边界(1) 蒙特卡洛的分布假设——正态假设可能低估尾部风险；(2) 多因素独立假设——实际因素间存在相关性；(3) 模拟精度受输入数据质量驱动——garbage in, garbage out

L3-04: computeInterventionEffect P2

数学公式/逻辑准实验因果推断: effectSize = (干预后均值 - 干预前均值) - (控制组差值); significanceLevel = t-test p-value; syntheticControl = 从对照组构建反事实加权组合
消费的边参数AFFECTS (干预效果)
图遍历路径干预标记 → [AFFECTS] → 指标变化 准实验因果推断
服务JTBD聚类EVALUATE: U-JTBD-0127; CONTROL: U-JTBD-0172
时间约束月(小于4h)
对抗性边界(1) 需要GA手动标记干预事件——标记缺失则函数不可用；(2) 控制组选择的主观性；(3) 混淆因素——干预期间发生的外部事件无法分离

L4-03: computeSubstitutionRisk P1

关键观察

  • ALLOCATE x Customer (8 U-JTBD) 是新增compute函数密度最高的格子——5个新增函数服务这一聚类，核心原因是客户资源分配决策需要客户盈利能力、价值评分、账期风险、全成本、竞品报价五个维度的因果信息。
  • DIAGNOSE x Customer (8 U-JTBD) 依赖L3因果推断层——ShapleyAttribution和CausalSequence是跨格子共享的因果推断引擎，不只服务一个格子。
  • PREDICT x Resource (9 U-JTBD) 是PREDICT类中需求最密集的实体，主要围绕现金流和资金需求预测。
  • CA1（多因素归因哨兵）是跨格子的通用哨兵——它消费L3层的因果推断函数，服务DIAGNOSE和PREDICT的所有实体。

六、诚实声明与局限性

  1. 现有哨兵映射基于代码扫描推断，未经逐一验证。62个扩展目录的哨兵功能是基于目录名和compute函数导入推断的。部分哨兵的内部实现可能与期望功能存在偏差。
  2. 新增compute函数的对抗性边界是理论推演，未经实证测试。对抗性边界条件来自Phase 2因果信息需求分析中的假设反推，需要在实际数据上验证其行为是否如预期。
  3. U-JTBD到哨兵的映射是聚类级映射，非逐条映射。177个U-JTBD中有极个别可能落在聚类边界——某个U-JTBD的因果信息需求横跨多个compute函数域，聚类映射可能掩盖了个别JTBD的覆盖率缺口。
  4. 正交性原则在实际实施中可能因边缘情况而妥协。同一因果参数由单一compute函数负责的原则在某些极端场景下可能产生过大的函数体——需要在实际编码时评估拆分的边际收益。
  5. 数据可得性评估基于Phase 2的自动标注，可能乐观。~47%的B类ND假设"企业系统接口存在"，但实际对接的复杂度和企业IT成熟度差异巨大。
  6. 新增哨兵与现有哨兵的交互效应未建模。同一compute函数被多个哨兵消费时，哨兵间的信号交叉和升级逻辑需要在集成测试中验证。
