## 三、修复路径总纲（按簇，供另案派单）

1. **诊断引擎簇（2.1 #6/7）**: L1 只持有 `l2-interfaces/diagnosis-engine` 类型；引擎实例由 `src/agent/diagnosis-launcher.ts`（L2）构造并经 DI 注入（`app.locals` / bootstrap services）。
2. **哨兵簇（2.1 #1-5/8/12/13）**: `src/agent/sentinel-service.ts` + `sentinel-health-service.ts`（L2，均已存在）为唯一出口；MCP 工具与 server webhook 改为调 L2。MCP `sentinel_run` 内联构造 SqliteGraphStore 的 L4/L5 双重违规随此消除。
3. **图存储/记忆/知识/本体簇（2.2 全部 + 2.3b 全部）**: SqliteGraphStore 构造 + getDatabase 直取 + agent-memory-store/knowledge-store/ontology-loader——统一经 L2 服务（knowledge-bridge-service 模式推广），实例 DI 注入 `app.locals`，L1 只消费注入实例；getDatabase 从 L1 清零（grep 物理验收）。
4. **存储簇（2.3a #1-9/12-15）**: SessionStore「构造」从 L1 移出——L2/bootstrap 组装后注入；L1 侧保留 isSqliteDatabase 谓词 fail-closed 防护。`sessions.ts:11`、`cli.ts:14/21` 静态依赖最优先（编译期硬耦合）。
5. **组合根簇（2.1 #14/15、2.3a #10/11）**: server.ts 作为组合根的 DI 装配集中到 `src/init/`（engine-context 同层），server.ts 本身只留 HTTP 壳；route 业务直调（connector-pipeline）下沉 L2。
6. **TUI/CLI 簇（2.1 #16、2.2 #15、2.3a #1/2/12-15）**: TUI/CLI 启动装配（scheduler/store/sqlite）与 knowledge-agent 注册全部下沉 L2 bootstrap / ConversationEngine 内部。

**治理原则**：先静态后动态（静态=编译期硬耦合，风险最高也该先断）；组合根 DI 类先集中后下沉；每簇一个 FIX 任务，走完整 spec→impl→K3 审计生命周期（D382 审计闭环铁律，禁止折入原任务）。

## 四、门禁修补建议（check-architecture.sh，另案派单——本任务写集外）

4. **fail-open 根除**: 每个 grep 链尾 `|| true` 改为三态退出码（ctrl-tower-change 模式 1：exit 0 通过 / 1 发现问题 / 2 检查自身失败，两者皆阻断）；目录缺失显式告警。

6. **组合根豁免显式化**: server.ts 的 DI 装配行允许豁免，但必须逐行注释 `// DI(组合根)` 且集中到 init/ 后收紧。
