## 一、四维对比

### 维度 1: 协议正确性

| 项 | 手写（迁移前实测） | SDK 1.30.0（迁移后实测） |
|----|------------------|------------------------|
| notifications/initialized | **不处理**（客户端发来落入 JSON 解析循环，产生无 id 消息噪音） | ✅ SDK `setNotificationHandler(InitializedNotificationSchema)` 内建（server/index.js:53 亲证） |
| protocolVersion 协商 | **硬编码 '2024-11-05'**（:320，客户端请求版本被忽略） | ✅ SDK `_oninitialize` 按官方协商算法应答（SUPPORTED_PROTOCOL_VERSIONS） |
| JSON-RPC 错误码语义 | 自造（未知工具返回 `result:{error:...}` 200 语义，不区分 -32601/-32602/-32000） | ✅ 标准映射：schema 校验失败→-32602/-32603 区间（parseWithCompat→ZodError），McpError.code 透传（protocol.js:400-406 `Number.isSafeInteger(error['code'])` 亲证），本任务权限拒绝用 -32000、未知工具 -32601 |
| 非法 JSON 行容错 | catch 后继续（手工处理） | ✅ transport ondata catch → onerror 钩子，进程不崩（S6c 冒烟实证） |
| stdout 纯度 | 靠约定（日志须走 stderr） | ✅ 同约定，SDK 协议输出全部走 transport.stdout；配合 @synova/logger（pino→fd2）S6c 实证零污染 |

**结论**: 手写实现已在三处实际漂移（initialized 通知、版本协商、错误码语义）——审计
"手写实现必然漂移"判断成立。SDK 是协议参考实现，正确性维度压倒性。

### 维度 2: 维护成本

| 项 | 手写 | SDK |
|----|------|-----|
| 协议演进跟进 | 自担（每次 MCP spec 升级手工对齐——initialized/版本协商已漂移即成本实证） | 升级依赖版本即跟进（^1.30.0 semver） |
| server 代码形态 | 349 行单文件：协议循环 + 工具表 + 处理器 + 装配耦合 | index.ts ~90 行纯装配（模式解析/信任声明/错误映射）；工具契约单源 tool-definitions.ts（可单元测试，不 spawn） |
| 测试性 | 只能 spawn 子进程做集成 | 权限模型/处理器纯函数直测（T1-T10，440ms）；协议层才走 stdio 冒烟（S1-S7，~1s） |
| 工具扩展 | 改 TOOLS 数组 + handleToolCall case + 手工保证过滤/权限一致 | 改 TOOLS 一处（permission 元数据驱动过滤与拒绝，零逻辑分叉） |

**结论**: SDK 化后 server 装配层缩至 ~90 行且只做装配；权限/过滤从"手工约定"变"元数据驱动"。
维护成本显著下降。

### 维度 3: 依赖体积

| 项 | 实测值 |
|----|--------|
| @modelcontextprotocol/sdk 运行时依赖 | jsonschema（ajv 类，经 @cfworker/json-schema peer）、zod（peer） |
| 与仓库冲突 | **无**——zod peer `^3.25 \|\| ^4.0` 与仓库 zod 4.4.3 直接兼容（registry 实测 + 本 session `npm install` 实证，零嵌套版本、零 dedupe 冲突） |
| 体积增量 | node_modules 增量 <1MB（纯 JS，无 native 构建 Electron 打包友好） |
| 安装风险 | 本 session 实测唯一环境坑在 npm 缓存属主（`~/.npm/_cacache` root 文件 → EPERM，绕过 `--cache /tmp/npmcache-d595`），与 SDK 本身无关 |

**结论**: 依赖代价小且无版本冲突；对 Electron 打包链无新增负担。

### 维度 4: 迁移风险

| 风险点 | 评估 | 处置（已落地） |
|--------|------|--------------|
| 工具清单/输入 schema 破坏 | 低——零生产消费方（全仓 grep "mcp/index" 亲证零引用，仅文档/测试/自身），接入方按 README 新配置 | tools/list 契约保持 name/description/inputSchema 形状，新增 permission 元数据（纯增量） |
| 哨兵族行为变化 | 中——sentinel_run 修复属**有意的行为修复**（原实现 sentinelId 误当 teamId 实跑全量=语义 bug） | T5 单测收口单哨兵语义；run_all 逐哨兵结果结构化 |
| stdio 帧兼容（旧客户端） | 低——stdio JSON-RPC 按行帧不变；SDK 协商兜住版本差异 | S1-S7 全链路冒烟（真实子进程） |
| 类型安全 | 低 | SDK 类型完备；新代码 as any/as never/as unknown as = 0（CT-46，pre-commit 组 1 可验） |
| 回滚成本 | 低——迁移为单 commit 语义，revert 即回手写实现 | git 历史保留手写实现全貌 |

**结论**: 迁移风险受控且有冒烟兜底；"倾向迁移"的审计预判成立。

## 二、结论

**采纳迁移**（spec §12 决策 3 = B）。四维全部指向同一方向：协议正确性（手写三处实际漂移）
与维护成本（元数据驱动 + 纯函数可测）收益显著；依赖体积代价小且零版本冲突；迁移风险受控
（零消费方 + 冒烟全绿兜底）。收敛检查：Anthropic 工程基线（不手滚协议实现）+ 审计预判
（"倾向迁移（消协议漂移）"）+ 开源实证（SDK=协议参考实现）三方收敛，无分歧。

**安装状态**: ✅ 已实装（`npm install @modelcontextprotocol/sdk@^1.30.0 --cache /tmp/npmcache-d595`
成功，1.30.0 入 dependencies；未静默回退手写 readline——审计可 grep `@modelcontextprotocol/sdk`
package.json dependencies 与 src/mcp/index.ts import 亲证）。

**遗留锚点**: 多轮对话工具（审计缺口③）不随本迁移引入——会话生命周期须与 D587/D588 会话
投影对齐，防"会话语义双轨"（审计 §8.2.2），归 Stage 2 随 `SYNOVA-MCP-CONTRACT` 契约冻结一起设计。
