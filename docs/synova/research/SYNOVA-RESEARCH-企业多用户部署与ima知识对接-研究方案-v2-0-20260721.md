# 企业多用户部署 + ima知识对接 — 研究方案 v2.0

> 补充权威文档09（部署运维） | 2026-07-21
> 定位：解决 Synova 从单机 Demo 到企业级多用户可部署产品的关键障碍

---

## 一、背景与问题定义

### 1.1 客户真实需求

"企业里老板、财务、营销各自下载应用，但看到的是同一家公司的数据。就像飞书——每个人有自己的账号，但大家都在同一个企业里。"企业文档也不能散落在各台电脑上——需要一个统一的文档仓库。

### 1.2 当前状态

现在的 Synova 做不到。auth 是 JWT demo（`routes/auth.ts`：不验密码，手动填 userId+role+orgId）。GraphStore 虽然以 orgId 做租户隔离，但整个系统是为"一个服务端进程对一个人"设计的——SQLite 是单文件数据库，如果每台机器独立跑 Agent 进程，各自的 SQLite 是隔离的，同公司的人看到的数据不一样。

### 1.3 核心矛盾

**数据共享 vs. 独立部署的矛盾。** 如果"每个人单独下载"意味着每台机器独立 Agent + 独立 SQLite → 数据不互通 → 这是同一个公司还是 N 个公司？

唯一正确的架构：**企业局域网内集中部署一个 Synova Server 为唯一真相源，所有团队成员的 Electron 客户端作为瘦客户端通过 HTTP API 远程连接。哨兵、诊断、溢出计算全部在 Server 端执行。**

## 二、解决方案

### 2.1 架构图

```
                    ┌─────────────────────────┐
                    │      ima（企业文档仓库）    │
                    │  战略规划/会议纪要/合同/报表  │
                    │   权限体系：每人可见不同文档   │
                    └───────────┬─────────────┘
                                │ ima API（按用户权限）
                    ┌───────────▼─────────────┐
                    │   Synova Server          │
                    │   (企业局域网内)           │
                    │   synova-agent + SQLite   │
                    │   + CronScheduler         │
                    │   + 哨兵/诊断/溢出计算      │
                    │   + KnowledgeExtractor     │
                    │   + 管理员工作台(Web界面)   │
                    └───────────┬─────────────┘
                                │ HTTP API
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
    ┌──────────┐         ┌──────────┐         ┌──────────┐
    │ 老板      │         │ 财务负责人 │         │ 营销负责人 │
    │ Electron  │         │ Electron  │         │ Electron  │
    │ (本机Server│         │(局域网连接)│         │(局域网连接)│
    │  +客户端)  │         │           │         │           │
    └──────────┘         └──────────┘         └──────────┘
```

- **Synova Server**：企业部署的唯一真相源。哨兵、诊断、溢出计算全部在这里。
- **Electron 客户端**：纯交互层——内置浏览器加载 Web 界面 + 系统托盘/桌面通知/开机自启动等原生能力。不跑诊断逻辑。TUI 保留为开发者调试工具。
- **ima**：企业文档仓库。Synova 以用户级权限读取 ima 文档——每个用户的文档访问范围与 ima 原生权限一致。不出现"财务能看到老板的机密文档"的安全问题。

### 2.2 部署模式

| 模式 | 适用场景 | Server 位置 | 可用性 | 迁移路径 |
|------|---------|------------|--------|---------|
| **单机模式** | 5-20人团队起步，没有IT人员 | 老板的电脑（既是Server也是客户端） | 老板开机在线，关机其他人不可用 | 复制 SQLite + config.yaml 到独立服务器→启动 Agent→所有客户端更新 serverUrl |
| **局域网模式** | 20-100人，有内部网络 | 专用机器/NAS/Linux服务器 | 7×24在线 | — |
| **云端模式** | 分布式团队（未来） | 云服务器 | 7×24在线 | — |

**默认从单机模式起步**。系统在首次启动时引导："这台机器将成为 Synova Server。其他团队成员需要通过局域网连接此机器。如果您希望 7×24 可用，建议后续迁移到独立服务器模式。"升级提示内置在管理员工作台中——当系统检测到超过 3 个活跃用户时，自动建议升级。

### 2.3 需要新增/修改的能力

| 能力 | 现状 | 目标 | 改动范围 |
|------|------|------|---------|
| **企业注册** | 无 | `/api/enterprise/register`：admin 创建企业，生成 enterpriseId + admin 账号 | 新增 `src/routes/enterprise.ts` |
| **管理员工作台** | 无 | Electron 内置 Web 页面：企业信息管理、成员邀请、权限管理、ima 绑定、部署模式切换。只有 admin 角色可见 | 新增 Electron 页面 + API |
| **成员管理** | 无 | admin 邀请成员（邮箱）→ 成员收到邀请链接 → 设置密码 → 产生 userId。角色自动映射 RBAC 五角色 | 新增 CRUD + GraphStore User 节点 |
| **认证升级** | JWT demo，不验密码 | bcrypt 哈希 + JWT 签发。`/api/auth/login` 从 demo 升为生产级 | 修改 `routes/auth.ts` |
| **Electron 连接** | 连 localhost | 启动 → 输入 `serverUrl` + 邮箱 + 密码 → 存储到本地 | 修改 Electron 启动页 |
| **离线缓存** | 无 | 仪表盘数据本地缓存。断网时显示"最后更新：XX时间"。仅缓存聚合数据，不缓存原始数据。 | 新增 Electron 本地存储层 |
| **ima 连接器** | 无 | Synova 注册 ima 为数据源。以**用户级权限**读取 ima 文档——每个用户的文档访问范围与 ima 原生权限一致。不出现跨权限泄露 | 新增 `src/connectors/ima.ts` |
| **ima 认证管理** | 无 | Synova Server 存储 ima API Key（admin 首次配置时输入）。定期检查有效性，过期前提醒更新。连接失败→标记文档"待处理"→主动触达引擎通知管理员 | 修改 `src/connectors/ima.ts` + 主动触达引擎 |
| **知识提取增强** | Knowledge Expert 仅扫描 GraphStore | 增加 ima 数据源。**默认只提取三类文档**：战略规划类、运营数据类、会议纪要类。不提取合同/员工手册。GA 可手动标记需提取的文档。增量同步+变更检测。 | 修改 `l3/knowledge-agent.ts` |
| **文档引用追溯** | 无 | 专家诊断引用的知识条目标注来源："来自 ima 文档《战略规划》第3页"。当原始文档变更时，相关 PKB 条目标记为"需重新验证" | 扩展 PKB 条目的 source 字段 |
| **GA 连接模式** | — | GA **不远程连接**企业 Synova Server。GA 在自己的机器上独立运行 GA 工作台，消费：联邦进化的匿名聚合数据 + 客户主动分享的诊断报告（PDF/HTML 导出）+ 临时安全链接（一次性 token，有过期时间） | 已有 `ga-admin.ts` + `ga-corrections.ts` |
| **数据隔离** | GraphStore 已有 orgId 隔离 | 不变 | 无需修改 |
| **RBAC** | 已有五角色 | 不变 | 无需修改 |

## 三、研究任务（5章）

### 第一章：企业多用户架构
- 服务端集中部署 → 瘦客户端连接
- 企业注册 + 成员邀请 + 认证升级的完整数据流
- 单机模式→局域网模式的迁移路径
- Electron 客户端离线缓存策略（缓存聚合数据 + 断网降级提示）

### 第二章：ima 知识对接
- ima 连接器规范（用户级权限继承——每个用户的文档访问范围 = ima 原生权限）
- ima 认证生命周期管理（API Key 存储/定期校验/过期提醒/失败不阻断系统）
- 知识提取范围与优先级（默认三类+GA手动标记+增量同步+变更检测）
- 文档引用追溯机制（PKB条目标注来源→原始文档变更→标记"需重新验证"）

### 第三章：管理员工作台与客户端改造
- Electron 内置管理员工作台（企业信息/成员邀请/权限管理/ima 绑定/部署模式切换）
- Electron 客户端启动配置页（serverUrl + 邮箱 + 密码登录）
- 多用户登录流程

### 第四章：GA 连接模式
- GA 不远程连接企业 Synova Server
- GA 工作台的数据源：联邦进化匿名聚合数据 + 客户分享的诊断报告 + 临时安全链接
- 与现有 `ga-admin.ts` / `ga-corrections.ts` 的关系

### 第五章：与现有代码对齐
- `routes/auth.ts` 升级方案（demo→生产级）
- 新增 `routes/enterprise.ts`（企业注册+成员管理）
- 新增 `src/connectors/ima.ts`（ima 连接器）
- GraphStore User 节点
- `l3/knowledge-agent.ts` 增强（ima 数据源+文档范围过滤）
- 权威14 MVS 扩展路径标注

## 五、MVS 最小实现边界

MVS 阶段仅需：企业注册 + admin 创建 + bcrypt 密码认证 + 局域网 HTTP 连接 + 单机模式。不需要 ima 集成、不需要成员邀请、不需要 RBAC 细化、不需要离线缓存。

完整的 ima 集成和成员管理作为 MVS 之后的第一个扩展目标。
