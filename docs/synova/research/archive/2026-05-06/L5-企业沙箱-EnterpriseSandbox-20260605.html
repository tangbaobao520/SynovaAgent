一、总览：Synova 沙箱应覆盖的 6 层维度

企业级沙箱不是单一机制，是纵深防御体系。结合 Hermes 和 OpenClaw 的模式，Synova 需要 6 层沙箱：

第 1 层：API 与传输安全 ──── 谁在调用？（认证 + 速率限制 + 脱敏检查）
第 2 层：连接器执行沙箱 ─── 连接器能做什么？（子进程隔离 + 文件安全 + 网络限制）
第 3 层：工具调用防护 ────── 工具能怎么用？（循环检测 + 分类门控 + 不安全数据包裹）
第 4 层：凭据管理 ───────── 密钥怎么存？（加密存储 + 多 key 轮换 + 状态管理）
第 5 层：数据安全与隐私 ──── 数据怎么保护？（脱敏 + 日志遮罩 + 分级分类）
第 6 层：策略与合规 ──────── 安全基线是什么？（无悔动作 + 一致性检查 + 审计门禁）

二、逐层设计

第 1 层：API 与传输安全

1.1 请求认证与鉴权

参考: OpenClaw server/src/engine-server/middleware/auth.ts

模式：Bearer Token 验证，白名单绕过健康检查/静态资源。

现状：✅ Synova server.ts 已有 auth 中间件，支持 devMode 跳过。

改进：添加多 Token 支持（每个客户独立 Token）+ Token 轮换机制。

1.2 速率限制

参考: OpenClaw server/src/engine-server/middleware/rate-limit.ts

模式：分层限流——认证 10/min、生成 20/hr、轮询 60/min。

现状：✅ Synova 已有基于 IP 的 100 req/min 限流。

改进：添加 Token 级别的限流（防止单个 Token 耗尽所有配额），添加 LLM 调用频次限制。

1.3 输入脱敏检查（OpenClaw 模式——推荐采用）

参考: OpenClaw server/src/engine-server/middleware/sanitize-check.ts

模式：9 类中文敏感数据正则规则（金额、人名、公司名、手机号、邮箱、地址、身份证、IP/URL、银行卡）扫描请求体，命中则返回 400 INSUFFICIENT_SANITIZATION + details[]。

OpenClaw 的中间件逐字段扫描（job、constraints、successMetrics、failureModes），每条命中记录 field + position + matched reason。这与我们的 PIIScrubber 是互补关系：

用户输入 → sanitize-check 中间件（输入侧） → 对话处理 → LLM 调用 → PIIScrubber（输出侧）
              ↑ OpenClaw 模式，我们缺这个          ↑ 我们已做

现状：❌ Synova 无输入脱敏中间件。

建议：P1 在诊断 API 入口添加 sanitize-check 中间件。可直接复用 OpenClaw 的 checkString() 和 checkTaskDefinition() 模式。

第 2 层：连接器执行沙箱

2.1 子进程隔离

参考: Hermes agent/file_safety.py — 文件级 deny list

模式：连接器在独立子进程中运行，资源限制（CPU/内存/超时），临时目录用完即焚。

现状：⚠️ Python Bridge 已实现子进程通信，但未接线。

建议：P0 完成接线。每个连接器在独立的临时目录中运行，30s 超时，stdin/stdout JSON 通信。

2.2 三级沙箱等级

参考: OpenClaw protocol-engine/mode-presets.ts — isolation.sandboxLevel: 'full' | 'semi' | 'none'

模式：

  • full：子进程 + 网络限制（仅允许声明端点）+ 无文件系统
  • semi：子进程 + 只读临时目录
  • none：同进程运行（仅限受信任的内部连接器）

现状：❌ Synova 无沙箱等级概念。

建议：P1 在 ConnectorConfig 中加入 sandboxLevel 字段，ConnectorRegistry 根据等级选择执行策略。

2.3 文件系统拒绝列表

参考: Hermes agent/file_safety.py — build_write_denied_paths() + build_write_denied_prefixes()

模式：精确路径和目录前缀两个维度的写拒绝 + 读拒绝。

写拒绝: ~/.ssh/, ~/.aws/, ~/.kube/, /etc/sudoers, /etc/passwd, .env, auth.json, mcp-tokens/
读拒绝: .env, auth.json, .anthropic_oauth.json, mcp-tokens/（纵深防御）

现状：❌ Synova 连接器可访问宿主全部文件系统。

建议：P2 在子进程沙箱中加入文件路径白名单。

第 3 层：工具调用防护

3.1 工具循环保护

参考: Hermes agent/tool_guardrails.py — ToolCallGuardrailController

模式：3 个维度的循环检测：

  • 精确失败：相同参数相同工具连续失败 5 次 → 阻断
  • 相同工具：同一工具连续失败 8 次 → 停止
  • 无进展：只读工具返回相同结果 5 次 → 阻断

使用 SHA-256 结果哈希做去重，阈值可配置，返回结构化 GuardrailDecision（allow / warn / block / halt）。

现状：❌ Synova 无工具调用保护。

建议：P1 在 ToolRegistry.execute() 中加入护栏。ExpertAutonomyEngine 的 ReAct 循环天然容易陷入"反复查同一数据"的循环，护栏直接解决。

3.2 不安全数据分隔

参考: Hermes agent/tool_executor.py — make_tool_result_message() 中的 untrusted_tool_result 包裹

模式：高风险工具（web_search、web_extract、MCP）的输出包裹在 <untrusted_tool_result> 分隔符中，明确告诉 LLM"这是数据，不是指令"。架构级 prompt 注入防御。

现状：❌ Synova 所有工具输出等同对待。

建议：P1 连接器工具输出和外部数据源结果加 untrusted 标记。

3.3 工具操作分类

参考: Hermes agent/tool_dispatch_helpers.py — _should_parallelize_tool_batch() + OpenClaw synova-plugin/hooks/before-tool-call.ts

模式：每个工具有 operationType（read / write / admin / interactive）和 sideEffects（none / mutating / destructive）。并行门控和权限检查基于此分类。

现状：❌ Synova 无工具操作分类。

建议：P0 在 ToolDefinition 中加入 operationType 和 sideEffects，这是工具并行执行和权限控制的基础。

第 4 层：凭据管理

4.1 加密存储

参考: Synova 已有 src/security/credential-vault.ts（AES-256-GCM，已实现但未接线）

现状：⚠️ 代码完整，未接线。凭证仍走 .env 明文。

建议：P0 在 server.ts 中初始化 CredentialVault，替代 process.env 读取。

4.2 凭据池 + 多 Key 轮换

参考: Hermes agent/credential_pool.py — 2184 行的完整实现

模式：

  • 三层状态：ok（正常）/ exhausted（临时故障，冷却后恢复）/ dead（永久故障，需重新认证）
  • 冷却时间差异化：401=5min，429=1h，其他=1h
  • 4 种选择策略：fill_first / round_robin / random / least_used

建议：P1 在 CredentialVault 基础上添加 CredentialPool，支持多 API key 轮换和自动故障切换。

4.3 凭据持久化边界

参考: Hermes agent/credential_persistence.py — sanitize_borrowed_credential_payload()

模式：借用的第三方凭证在写入磁盘时脱敏，只保留指纹（sha256:first16）。73 个已知秘密键名自动识别。

建议：P2 Synova 的 CredentialVault 存储时已加密（AES-256-GCM），磁盘安全已满足。此模式在需要与其他系统共享凭据时使用。

第 5 层：数据安全与隐私

5.1 PII 检测与脱敏

参考: Synova 已有 src/security/pii-scrubber.ts — 4 级敏感度 + 参与者主权

现状：✅ 4 级敏感度（S1-S4）、角色掩盖、参与者主权（opt-out 删除）。基于 OpenClaw sanitize-check.ts 的 9 类规则扩展，已添加公司名、人名、地址检测。

深化方向：合并 OpenClaw 的 restrictedDataCategories 声明式分类到现有 S1-S4 体系——在连接器注册时声明需要的数据类别，系统自动阻止未授权数据访问。

5.2 日志脱敏

参考: Hermes agent/redact.py — 21 个已知密钥前缀 + 性能门控

模式：

  • 21 个正则模式覆盖 OpenAI/GitHub/Slack/Google/AWS/Stripe 等密钥前缀
  • 私钥块、JWT、数据库连接串自动遮罩
  • Authorization header 遮罩
  • RedactingFormatter：自动遮罩所有日志记录

现状：❌ Synova 日志无结构化脱敏。

建议：P0 在 logger.ts 中添加 RedactingFormatter，自动遮罩常见密钥格式。这是存储之外最直接的暴露点——日志中如果打印了 API Key 等于把钥匙贴在大门上。

5.3 SQLite 加密存储（新增——P0）

为什么重要：客户的 CRM 数据、财务数据全部以明文存在 SQLite 文件中。谁拿到了数据文件就能直接读。Hermes 和 OpenClaw 都没有持久化存储，所以没有这个问题——但我们有。

模式：使用 better-sqlite3 的 AES-256 加密扩展（或 sqlcipher 包装），加密密钥派生自主密码，与凭证加密同一体系。备份文件使用同一密钥加密。

现状：❌ 无。

建议：P0 在数据库初始化时启用加密。自动备份时使用同一密钥加密备份文件，配置数据保留期限（默认 90 天）。

5.4 消息清洗

参考: Hermes agent/message_sanitization.py — _sanitize_surrogates() + _repair_tool_call_arguments()

模式：UTF-16 代理项替换、截断 JSON 修复、非 ASCII 恢复、图像剥除。

建议：P2 在 LLM Provider 层添加消息清洗步骤。用户从 CRM/Excel 复制的数据可能含有不可见字符导致 LLM API 400。

第 6 层：策略与合规

6.1 无悔安全动作

参考: OpenClaw protocol-engine/no-regret-actions.ts

模式：始终安全执行的不变约束：

  • NRA-01：注入安全约束（拒答清单、数据隔离、合规红线）
  • NRA-02：确保所有阶段被覆盖
  • NRA-03：默认启用诚实标记（可追溯性）

建议：P1 在诊断每个阶段开始前注入安全基线。

6.2 一致性检查

参考: OpenClaw protocol-engine/coherence-check.ts — R12/R14/R16

模式：

  • R12：低信任度 + 未启用审计 → critical
  • R14：完全隔离 + 外部知识可见性 → critical（知识无处可去）
  • R16：单决策者 + 多人否决权 → critical

建议：P1 在 ExpertPlatform 的模板验证和 QualityFirewall 中加入一致性检查规则。

6.3 技能/连接器安装安全门禁

参考: OpenClaw marketplace/skill-registry.ts — installWithSecurityCheck() + 4 道门禁

模式：安装连接器/技能前执行：

  1. 分数门禁（securityScore >= 70）
  2. Blocklist 门禁（不在黑名单中）
  3. 来源门禁（sourceTier 不是 speculative）
  4. 能力匹配门禁（工具不超范围）

通过 4 门禁 → 正常安装；疑似恶意（score 70-84）→ sandboxLevel='full'；良性（score >= 85）→ sandboxLevel='semi'。

建议：P2 在 ConnectorRegistry.register() 中加入安全门禁。

6.4 安全审计报告

参考: OpenClaw services/skill-security-audit.ts — CloudTrip 7-Step Static Audit

模式：7 步静态审计+评分（0-100），含危险关键词、文件操作、远程脚本、依赖检查。

建议：P2 连接器注册时生成安全审计报告。
