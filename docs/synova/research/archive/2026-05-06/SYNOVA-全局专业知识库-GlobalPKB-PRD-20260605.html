全局专业知识库（Global PKB）

产品需求文档 · PRD V1.0 · 2026-06-05

📌 一句话

专家不背课本，而是带着图书馆进诊断室。全局 PKB 就是这个图书馆——每本书都打好标签，要什么取什么，永远是最新版本。不写入代码，不锁死专家，随生态一起进化。

一、背景与问题

1.1 当前状态

7 个专家 Agent（战略、组织、财务、技术、市场、执行、知识）的诊断能力完全依赖 LLM 的通识推理 + 硬编码在 system prompt 中的少量指引。存在的问题：

  • 知识过时：LLM 训练数据有截止日期，最新的行业基准、法规变化无法感知
  • 知识不精确：LLM 对"制造业平均 OEE 是多少"这类问题只能给大概值，无法给出可验证的基准
  • 知识不通用：每个专家的知识写在各自的 prompt 里，无法跨专家共享
  • 知识不可进化：行业诊断师贡献的新框架、联邦进化发现的新规则，没有入口进入系统
  • 知识不区分场景：几十人的工厂和上市公司的 CFO 看到的是同一套知识体系

1.2 为什么需要 PKB

当前（专家内嵌知识）目标（全局 PKB）
知识写在代码和 prompt 里知识存储在 PKB 中，代码和 prompt 只写检索指令
更新知识需要改代码、重新部署更新 PKB 条目即可，零代码变更
每个专家的知识互相隔离通过标签共享，同一条知识可被多专家使用
行业诊断师无法贡献通过 PKB 管理界面直接添加/审核知识
所有用户看到相同的分析深度根据用户认知水平和企业阶段返回不同层次的知识

二、核心原则

  1. 知识不写入代码——所有诊断相关知识统一存储在 PKB 中，不硬编码在专家 prompt 或模块代码里
  2. 标签驱动检索——每条知识有完整的标签体系（专家、领域、行业、层级等），专家通过工具按标签检索
  3. 按需取用——根据企业阶段、用户认知水平返回合适深度的知识，不堆砌
  4. 开放进化——行业诊断师贡献、联邦进化发现的新规则都进入 PKB，经审核后所有专家可用
  5. 与 SOG 本体对齐——知识条目关联到 SOG 节点类型、边类型、诊断维度，实现知识-数据联动

三、知识条目标签体系

3.1 标签结构

KnowledgeEntry:
  id: string

  # 归属标签——决定谁能用
  expertTypes: ExpertType[]           # 哪些专家可用（空=全局共享）
  diagnosticDimensions: string[]      # 关联的诊断维度
  sogNodeTypes?: SOGNodeType[]        # 关联的 SOG 节点类型
  sogEdgeTypes?: SOGEdgeType[]        # 关联的 SOG 边类型
  industries?: string[]               # 适用行业

  # 内容标签——决定是什么
  type: 'theory' | 'benchmark' | 'rule' | 'threshold' | 'template' | 'case_study' | 'regulation' | 'best_practice'
  content: string                     # 知识内容
  confidence: number                  # 置信度 0-1

  # 层级标签——决定给谁看
  knowledgeLevel: 1 | 2 | 3          # 1=基础 2=专业 3=深度
  targetAudience: string[]            # 目标受众标签

  # 生命周期
  version: string
  status: 'candidate' | 'active' | 'deprecated' | 'archived'
  source: 'methodology_team' | 'industry_diagnostician' | 'federal_evolution' | 'manual_calibration'

  # 溯源
  author: string
  evidenceRefs?: string[]
  validUntil?: string

3.2 三级知识层次（L1/L2/L3）

同一个专家面对不同的用户和企业阶段，应该输出不同深度的分析。PKB 通过在知识条目上标注 knowledgeLevel 实现。

层级定位适用场景财务专家示例
L1 基础层常识级几十人的中小企业主、非财务背景管理者「收入-成本-利润」、「账上现金能撑多久」
L2 专业层框架级有专业基础的 manager、成长期企业杜邦分析、ROI 计算、成本结构拆解
L3 深度层专家级CPA/CFO、成熟期/上市筹备企业DCF 估值、WACC、自由现金流、税务筹划

Agent 通过用户上下文自动选择层级：

query_knowledge({
  expertType: 'finance',
  knowledgeLevel: detectLevel(user),    // 根据用户角色/背景判断
  industry: detectIndustry(org),        // 根据 SOG 数据判断
  question: '公司财务健康吗'
})

关键原则：L1 不是 L3 的简化版，是另一种知识。几十人企业主需要的"财务分析"和 CFA 的知识体系完全不同——不是同一份内容减少了深度，而是完全不同的知识结构。

3.3 知识类型

类型说明示例

五、存储与检索架构

5.1 SQLite 存储

CREATE TABLE knowledge_entries (
  id TEXT PRIMARY KEY,
  expert_types TEXT NOT NULL,           -- JSON 数组
  diagnostic_dimensions TEXT NOT NULL,
  sog_node_types TEXT,                  -- JSON 数组，可为空
  sog_edge_types TEXT,
  industries TEXT,                      -- JSON 数组
  type TEXT NOT NULL,
  knowledge_level INTEGER DEFAULT 2,    -- 1/2/3
  content TEXT NOT NULL,
  confidence REAL DEFAULT 1.0,
  source TEXT NOT NULL,
  version TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  author TEXT NOT NULL,
  evidence_refs TEXT,
  previous_version_id TEXT,
  target_audience TEXT,                 -- JSON 数组
  valid_until TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_kb_experts ON knowledge_entries(expert_types);
CREATE INDEX idx_kb_type ON knowledge_entries(type);
CREATE INDEX idx_kb_status ON knowledge_entries(status);
CREATE INDEX idx_kb_level ON knowledge_entries(knowledge_level);

5.2 检索工具

tool_query_knowledge:
  description: "从全局专业知识库检索诊断所需的理论、基准、规则、案例"
  params:
    expertType: string                 # 当前专家类型
    dimensions?: string[]              # 诊断维度过滤
    types?: string[]                   # 知识类型过滤
    industry?: string                  # 行业过滤
    knowledgeLevel?: 1|2|3             # 知识层级过滤
    nodeType?: string                  # SOG 节点类型过滤
    includeDeprecated?: boolean
    limit?: number

  检索逻辑：
    WHERE (expert_types CONTAINS :expertType OR expert_types = '[]')
      AND status = 'active'
      AND (knowledge_level <= :userLevel OR :userLevel IS NULL)
    ORDER BY confidence DESC, updated_at DESC
    LIMIT :limit

5.3 冲突解决

诊断结论优先级（从高到低）：
  工具实时结果（cross_validate、SOG 查询）
  > 联邦进化规则（confidence >= 0.8）
  > 行业诊断师贡献的基准
  > 方法论团队编写的理论
  > LLM 训练数据中的通用知识

理由：工具结果是"当前病人的体检单"，PKB 是"教科书和行业标准"。
诊断永远信体检单，但教科书告诉你为什么。

六、知识生命周期

candidate（候选）
  │  联邦进化自动发现 / 行业诊断师贡献
  ▼
reviewing（审核中）
  │  方法论团队或审核专家评估
  ├── ✅ 通过 → active（正式）
  └── ❌ 拒绝 → archived（归档，可追溯）
      │
active（正式）
  │
  ├── 被新版本取代 → deprecated（废弃）
  │     ↓
  │  废弃版本保留在库中，通过 previous_version_id 可追溯
  │
  ├── 验证失败（多组织效果不佳）→ 置信度逐步下降
  │     ↓  低于 0.5 → deprecated
  │
  └── 超过 validUntil → 自动标记为 reviewing
        ↓  需要人工确认是否更新

7.1 与系统组件的集成

组件集成方式
专家 Agent（7 个）system prompt 末段增加检索指令，调用 query_knowledge 获取知识。不硬编码任何领域知识。
齿轮6（知识提取）定期扫描 PKB 中 status=candidate 的条目，触发审核流程。
联邦进化新发现的知识自动写入 PKB，status=candidate，source=federal_evolution。
行业诊断师工作台可视化管理界面：浏览、添加、编辑、审核知识条目。标记为 source=industry_diagnostician。
SOG 本体知识条目的 sogNodeTypes/sogEdgeTypes 关联到本体，本体新增类型时 PKB 条目可随之扩展。

八、诊断闭环驱动的知识进化（关键缺漏补充）

🔄 核心逻辑：诊断产生反馈，反馈进化知识，知识提升诊断——形成闭环

知识进化不是独立的知识库运维工作，而是由每一次诊断自动驱动的。每次诊断结束后，诊断结论、QualityFirewall 检验结果、用户确认/拒绝信号、专家间矛盾——都应该回流入 PKB。

8.1 完整闭环链路

诊断执行（L3）
  │
  ├── 6 位专家各自检索 PKB → 产出诊断发现
  ├── ExpertDispatcher 并行执行 → 收集结果
  ├── QualityFirewall 四道检验 → 产出通过/拒绝
  ├── ExpertDispatcher 检测专家间矛盾
  └── 用户对话确认/拒绝 → 收集反馈
       │
       ▼
  诊断结果 + 置信度 + 用户反馈 + 矛盾信号
       │
       ▼
  ⬇️ 回流入 PKB（L4）
       │
       ├── ① 调整引用知识的 confidence
       ├── ② 检测矛盾 → 标记知识冲突
       ├── ③ 发现拒绝模式 → 标记知识老化
       └── ④ 更新框架使用统计

8.2 反馈回流管道（新增 L4 节点）

新增 DiagnosisFeedback 节点，连接诊断结果和 PKB 条目：

interface DiagnosisFeedback {
  id: string;
  consultId: string;                    // 关联的诊断会话
  knowledgeEntryId: string;              // 专家引用的 PKB 条目
  expertType: string;                    // 引用该知识的专家
  diagnosisResult: 'confirmed' | 'rejected' | 'contradicted';
  confidence: number;                    // 该发现的置信度
  userFeedback?: 'useful' | 'useless';   // 用户评价
  firewallResult?: 'passed' | 'rejected';
  firewallReason?: string;
  contradictingExpert?: string;          // 矛盾的另一位专家
  timestamp: string;
}

8.3 4 条反馈回路

回路 1：专家发现 → PKB 置信度调整

专家引用 PKB 的某条 theory/rule/benchmark 产出诊断发现
  → QualityFirewall 检验通过
  → 用户确认发现正确
  → 该条目的 confidence += 0.02（上限 1.0）

相反：
  → QualityFirewall 拒绝（证据不足）
  → 或用户反馈 "无用"
  → 该条目的 confidence -= 0.05
  → confidence < 0.5 → 自动标记 deprecated

实现：齿轮6 定期扫描 DiagnosisFeedback，聚合计算 confidence 调整值。

回路 2：专家间矛盾 → 知识冲突标记

战略专家引用 theory_A 得出结论 X
组织专家引用 theory_B 得出结论 not X
  → ExpertDispatcher 检测到矛盾
  → 写入 DiagnosisFeedback，contradictingExpert=组织专家
  → PKB 记录 theory_A 在场景 X 下与 theory_B 冲突
  → theory_A 在 organization 维度被标记为 "reviewing"
  → 通知管理员审核：theory_A 是否在组织场景下已过时？

实现：expert-dispatcher.ts 中的矛盾检测逻辑（已有）扩展，将矛盾信号写入 DiagnosisFeedback。

回路 3：QualityFirewall 拒绝模式 → 知识老化检测

QualityFirewall 连续 N 次（可配置，默认 5）拒绝基于同一条 threshold 的发现
  → 该 threshold 可能过时了
  → PKB 自动将该条标记为 reviewing
  → 触发管理员通知

实现：齿轮6 统计 DiagnosisFeedback 中 firewallResult=rejected 且引用同一 knowledgeEntryId 的记录数。

回路 4：85 认知框架使用统计

framework-library.ts 中的框架不再静态。
每次专家通过 85 框架注入的分析透镜产出发现时，记录消耗：
  框架匹配频率
  基于该框架的发现平均置信度
  基于该框架的发现用户采纳率

低采纳率框架 → 标记 reviewing
高频 + 高采纳率框架 → 提升优先级

实现：框架使用数据写入 DiagnosisFeedback，齿轮6 每月汇总统计。

8.4 与进化三层次的对应

原有进化层次新增的驱动源效果
L1 对话沉淀 FAQ+ 诊断发现确认 → 知识固化诊断结论直接成为 PKB 知识
L2 实体链接+ 诊断发现的 MENTIONS 边诊断中识别的新实体关系进入图谱
L3 检索调优+ 专家引用准确率 → 检索排序检索结果反映真实诊断效果
