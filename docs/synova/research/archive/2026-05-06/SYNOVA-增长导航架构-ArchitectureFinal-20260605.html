Synova 组织增长导航系统 — 架构方案

最终版 · 2026-06-05 · 取代《战略迭代路线》

📌 核心定位

产品名称：Synova

品类：组织增长导航系统（Organizational Growth Navigation System）

一句话：一个存在于你聊天列表里的增长顾问。不说话时安静采集数据，说话时给你答案。

核心本质：持续采集企业数据、主动对话、实时诊断，帮助客户达成业务目标、规避风险、解决长期问题。

差异化：右边栏（目标/告警/遗留问题）让客户一目了然；每日 19:00 发送完整简报；所有重要变更通过对话确认（三选项）。

目标客户：各类规模企业、咨询公司、行业专家（MVP 先单租户，架构支持多租户扩展）。

〇、用户状态与系统入口

系统根据部署方式有两种进入状态：

状态 A：自助用户状态 B：PDE/咨询师/专家协助
场景用户自己下载部署了 SynovaPDE 或咨询公司或行业专家帮客户部署并初始化
数据状况还没有接入任何数据源数据源已配置完成、SOG 已有初始数据
工作模式先走 Phase 0（六维度诊断访谈），在对话中了解组织基本情况直接进入默认工作循环，不需要 Phase 0
后续用户逐步接入数据源后，自动切换到默认循环持续监测、自动运行

Phase 0 保留了，但不是强制入口。 旧代码中的 Phase 0 逻辑（六阶段诊断的第一阶段）在状态 A 中作为"新用户引导"存在。状态 B 中跳过 Phase 0 直接进入工作状态。

2.2 对话交互核心原则

  • 变更必须确认：Agent 提议对右边栏做任何变更（新增/修改目标、新告警、添加/关闭遗留问题）时，必须在对话框发送提议消息，附带三个可点击选项：✅确认 ❌拒绝 💬提出看法
  • 提议依据透明：消息中必须说明触发原因（数据监测结果或对话上下文）
  • 用户主动操作：用户可通过对话直接要求变更，Agent 同样需二次确认（以提议形式）
  • 无需手动标记：动作完成状态由系统通过数据自动检测，用户不需要"标记完成"

2.3 IM 集成（飞书 + 企业微信）

功能方式
每日简报19:00 推送完整简报（纯文本 + 极简 Markdown，无交互按钮）
告警推送高优先级可单独推送（仅信息，无按钮）
用户反馈用户在 IM 中回复文字 → webhook 接收 → Web 对话中回复
变更确认仅在 Web 对话框提供；IM 不推送确认按钮（避免割裂）

三、L2 编排层

3.1 诊断状态机

默认目标：维护企业健康增长、降低风险。不强制用户设定目标，但允许用户随时通过对话添加。

数据采集 → 信号检测 → 假设生成 → 提议确认（如需变更右边栏） → 执行变更 → 跟踪效果 → 循环

状态类型：Idle → Monitoring → Evaluating → Proposing → Tracking。不暴露给用户。

3.2 变更提议管理器（核心新增）

环节说明
接收提议接收 L3 生成的变更提议（新告警、目标偏差、遗留问题添加/关闭）
发送确认通过 L1 对话框发送提议消息（含三个选项）
等待响应超时（默认 7 天）自动取消或再次提醒
用户确认调用 L4 API 更新右边栏，触发 SSE 推送
用户拒绝记录拒绝原因，可抑制同类提议（可配置）
提出看法反馈给 L3，调整后续诊断权重或暂缓提议

3.3 调度器

触发方式说明
定时（19:00）每日心跳 → L3 全量诊断（增量模式）→ 生成简报 → IM 发送
事件触发L5 规则引擎检测到关键指标骤变 → 立即生成告警提议
用户命令用户对话要求"立即运行诊断"或"发送简报"

四、L3 分析层

4.1 专家子 Agent

6 个专家职责不变，Prompt 调整：

原：分析组织在 X 维度上的健康度

新：基于当前数据，找出可能阻碍业务目标达成或增加风险的信号。输出诊断发现（含描述、置信度、影响强度、建议）

4.2 五齿轮调整

齿轮调整后职责
齿轮1 自主权引擎专家围绕"业务影响"自主探索，信息增益归零时终止
齿轮2 信号融合按影响程度排序，输出 Top N 潜在告警/目标偏差/遗留问题
齿轮3 因果推断量化影响路径："信号 X → 中间变量 Y → 对目标/风险的影响 Z"
齿轮4 质量防火墙校验证据、置信度、时效性、业务相关性
齿轮5 自动探索改为"目标漂移与风险探测"：识别用户行为与目标/健康基线的偏离

4.3 新增模块

  • 简报生成器：每日心跳后，收集 L4 中所有活跃目标、告警、遗留问题、新发现、推荐动作，格式化为 Markdown
  • 提议生成器：将齿轮 2/3 的输出转换为右边栏变更提议，调用 L2 提议管理器

五、L4 本体层：SOG v2.0 扩展

v1.0（14 节点 + 10 边）冻结保留，v2.0 新增类型不破坏现有代码。

七、核心流程示例

7.1 新告警生成并确认

1. L5 检测到线索转化率 2 小时下降 12% → 触发事件
2. L3 齿轮 1-4 生成诊断发现 → 提议生成器创建告警提议
3. L2 提议管理器通过对话框发送：

   "检测到线索转化率 2 小时内从 15% 降至 12%，置信度 85%。
    建议在右边栏添加高优先级告警。
    请选择：✅确认  ❌拒绝  💬提出看法"

4. 用户点击"确认"
5. L2 调用 L4 创建 Alert 节点，status=active
6. L1 SSE 推送 right_column_update，右边栏显示新告警

7.2 每日简报

1. 19:00 调度器触发心跳
2. L3 执行增量诊断
3. 简报生成器从 L4 读取所有目标/告警/遗留问题/新发现
4. 格式化为 Markdown，通过 IM 发送
5. 用户回复"为什么告警优先级这么高？"
6. IM 回调转发给 L1 对话 → Agent 回复解释

7.3 遗留问题自动关闭

1. L5 检测到审批周期恢复正常（2天→1天），持续 3 天
2. L3 提议生成器创建关闭提议
3. L2 对话框发送：
   "销售审批流程优化问题似乎已解决，是否从右边栏移除？"
4. 用户选择"提出看法"："再观察一周"
5. L2 记录看法，提议暂缓，一周后重新评估
