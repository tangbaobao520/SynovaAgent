数据安全深度研究与深化方案

基于 Hermes + OpenClaw 安全模式对比 · 针对真实经营数据保护 · 2026-06-05

⚡ 核心判断：当前安全能力对 MVP 够用，对真实经营数据差 3 个关键能力

我们已经做了文件安全、PII 脱敏、凭证加密、审计日志。但面对客户的真实 CRM 数据、财务数据、业务数据，数据在存储层和传输层都是暴露的——SQLite 文件是明文，日志可能包含敏感信息，网络通信未加密。下面逐项对比 Hermes 和 OpenClaw 的做法，给出深化方案。

维度当前实现状态来源

二、Hermes 有但我们缺的（3 项）

缺失 1：日志脱敏（Log Redaction）

Hermes（redact.py）我们
能力21 个密钥前缀正则 + RedactingFormatter 自动遮罩所有日志❌ 无
覆盖OpenAI/GitHub/Slack/Google/AWS/Stripe/私钥块/JWT/数据库连接串❌ 无
性能O(1) 子串预检 → 无秘密日志行从 5.6μs 降至 1.8μs❌ 无

为什么重要：用户连接 CRM 时会在环境变量或配置中传入 API Key。如果日志中打印了这些信息，就等于把钥匙贴在大门上。Hermes 的 RedactingFormatter 是挂在 logger 上的自动过滤器，不需要每处代码手动调用。

缺失 2：消息清洗（Message Sanitization）

Hermes（message_sanitization.py）我们
能力UTF-16 代理项替换、截断 JSON 修复、非 ASCII 恢复、图像剥除❌ 无

为什么重要：用户从 Excel/CRM 复制的数据可能含有不可见字符或格式错误，直接送到 LLM 会导致 JSON 解析失败或 API 400。清洗层是 LLM 调用前的最后一道防线。

缺失 3：不安全数据分隔（Untrusted Data Wrapping）

Hermes（tool_executor.py）我们
能力高风险工具输出包裹 <untrusted_tool_result> 分隔符❌ 无

为什么重要：连接器从外部系统取回的数据可能含有 prompt 注入攻击。标记为不可信后，LLM 会将其视为数据而非指令。这是架构级防御，不依赖正则。

三、OpenClaw 有但我们缺的（2 项）

缺失 4：输入脱敏中间件（Sanitize Check Middleware）

OpenClaw（sanitize-check.ts）我们
能力9 类正则规则扫描请求体：金额、人名、公司名、手机号、邮箱、地址、身份证、IP/URL、银行卡❌ 无

为什么重要：用户在对话中可能无意输入敏感信息（如"帮我看看王伟的身份证号对不对"）。在数据进入 LLM 之前做一次脱敏检查，与 PIIScrubber 组成双重防御。

缺失 5：无操作审计（数据访问审计）

OpenClaw（mode-presets.ts audit 配置）我们
能力审计日志包含：谁、什么时间、访问了什么数据、操作结果。retentionDays 可配。❌ 只有连接器调用审计，没有数据访问审计

为什么重要：用户需要知道"哪个专家 Agent 在什么时间读了哪些数据"。这是合规要求和信任基础。

四、面向真实经营数据的深化方案

核心原则：数据从采集到存储到传输，全程保护。

采集（L5）           存储（L4）          分析（L3）          展示（L1）
  │                    │                    │                    │
  连接器               SQLite               专家 Agent           Web 界面
  │→ 子进程隔离         │→ SQLite 加密         │→ 清洗后数据        │→ 脱敏后展示
  │→ 网络白名单         │→ 备份加密           │→ 审计日志          │→ 无敏感数据
  │→ 输入脱敏           │→ 自动清理策略       │→ 不可信标记        │→ HTTPS
  │→ PII 过滤           │                    │                    │
  ▼                    ▼                    ▼                    ▼

4.1 存储层加密（P0）

项目说明工时
SQLite 加密存储使用 better-sqlite3 的 AES-256 加密扩展（或 sqlcipher 包装）。加密密钥派生自主密码，与凭证加密同一体系。1 天
备份加密自动备份时使用同一密钥加密备份文件。备份文件放在独立目录。0.5 天
自动清理策略配置数据保留期限（默认 90 天），超过期限的指标/事件数据自动清理。清理前先加密备份。1 天

4.2 日志脱敏（P0）

// 参考 Hermes redact.py 的 RedactingFormatter 模式
// 在 logger.ts 中注入自动脱敏过滤器

export class SynovaRedactingFormatter {
  private static readonly SECRET_PATTERNS = [
    // API Keys
    { pattern: /\b(sk-[a-zA-Z0-9]{20,})\b/g, replacement: 'sk-***' },
    { pattern: /\b(ghp_[a-zA-Z0-9]{36})\b/g, replacement: 'ghp-***' },
    { pattern: /\b(xox[abp]-[a-zA-Z0-9-]{20,})\b/g, replacement: 'xox-***' },
    // JWT
    { pattern: /\b(eyJ[a-zA-Z0-9_-]{10,}\.[a-zA-Z0-9_-]{10,}\.[a-zA-Z0-9_-]{10,})\b/g, replacement: 'eyJ***' },
    // Authorization header
    { pattern: /(Authorization:\s*Bearer\s+)[a-zA-Z0-9._-]+/g, replacement: '$1***' },
    // Private keys
    { pattern: /-----BEGIN (RSA |EC )?PRIVATE KEY-----[\s\S]*?-----END (RSA |EC )?PRIVATE KEY-----/g, replacement: '[REDACTED PRIVATE KEY]' },
    // Database connection strings (mask password part)
    { pattern: /(postgresql|mysql|mongodb):\/\/[^:]+:([^@]+)@/g, replacement: '$1://***:***@' },
    // Connection strings and URLs with embedded credentials
    { pattern: /https?:\/\/[^:]+:([^@]+)@/g, replacement: 'https://***:***@' },
  ];

  static format(level: string, msg: string, ...args: any[]): string {
    let safe = msg;
    for (const { pattern, replacement } of this.SECRET_PATTERNS) {
      safe = safe.replace(pattern, replacement);
    }
    return `[${level}] ${safe}`;
  }
}

4.3 网络隔离 + 连接器最小权限（P1）

项目说明工时
网络白名单每个连接器声明 allowedEndpoints，子进程在启动时注入网络限制（通过 iptables/npf 或环境变量代理配置）。不在白名单内的请求被拒绝。1 天
连接器最小权限声明连接器注册时声明需要的数据范围和操作类型。ConnectorRegistry 在执行前校验权限。0.5 天
数据源连接加密所有外部数据源连接强制使用 HTTPS/TLS。连接器启动时校验证书。0.5 天

4.4 审计增强（P1）

项目说明工时
数据访问审计每次 L3 专家 Agent 查询 SOG 数据时记录：哪个 expert、查了什么类型的数据、返回了多少条。存储到独立的 audit 表。1 天
审计查询 APIGET /api/security/audit?connector=X&action=read 等过滤条件。支持按时间范围查询。0.5 天
审计保留策略可配置 retentionDays（默认 90 天），超期自动归档或清理。0.5 天

六、执行优先级

优先级项目工时保护的数据
P0SQLite 加密存储——磁盘上的数据不再是明文1 天全部经营数据
P0日志脱敏——日志中不出现 API Key/Token1 天凭据
P1输入脱敏中间件——用户输入进 LLM 前脱敏0.5 天用户对话中的敏感信息
P1数据访问审计——谁在什么时间读了什么1.5 天全部经营数据
P1网络白名单 + 最小权限——连接器只能访问声明端点1.5 天外部系统凭据
P2不安全数据分隔——外部数据标记不可信1 天防止 prompt 注入
P2消息清洗——LLM 调用前数据清洗1 天减少 API 错误

一句话建议

先做 SQLite 加密 + 日志脱敏（2 天），这两个是存储和运行时最直接的暴露点。然后做 输入脱敏 + 数据审计（2 天），补齐防御面和可追溯性。
