Synova 是什么

Synova 不是传统咨询服务。传统咨询是"医生模式"——你有问题来找我，我开药方，之后的事不在我的范围。Synova 是"免疫系统"——驻扎在企业内部，7×24小时巡逻监测，第一个发现问题，持续诊断，给出方案，跟踪执行。

对外呈现为三个飞轮的转速仪表盘：价值创造（你在正确的地方创造了价值吗）、价值兑现（你把价值转化成了利润吗）、价值再生（你的组织能持续自我修复吗）。后台是六层诊断架构 + 一个顶层校准框架，共包含数十个可计算的哨兵指标。CEO 只看到瓶颈在哪，追问时展开完整分析，需要时可以钻探到原始数据。

不是把咨询做得更好。是换一个物种。

文档定位：本文档是可执行的技术方案，与白皮书配套使用。读完本文档，开发Agent应当能够：(1) 理解新哨兵在现有架构中的位置；(2) 知道每个哨兵的 compute/aggregate 函数签名、输入输出、本体映射；(3) 知道8位专家如何消费哨兵结果；(4) 开始实现。

架构铁律（CTO签署，零容忍）：每个哨兵自包含在 extensions/sentinels/{name}/ 目录内。禁止跨目录引用计算逻辑。禁止动态 import() 加载 compute 模块。所有 compute 函数通过同目录静态 import 引用。tsc --noEmit 零失败才能合并。违反者代码审查拒绝合并。

  description: string;
  dependsOn: {

interface ComputeResult {
  value: number | Record<string, unknown>;

}

6.1 E1 市场天花板与生命周期 — 产业生命周期判定

// extensions/sentinels/market-lifecycle/computes/lifecycle-stage.ts
import type { GraphStoreReader } from ''../../../../src/sentinel/sentinel-loader'';

export interface LifecycleResult {
  stage: ''introduction'' | ''growth'' | ''shakeout'' | ''maturity'' | ''decline'';
  confidence: number;
  industryGrowthRate: number;
  netEntryRate: number;
}

export function computeLifecycleStage(
  store: GraphStoreReader, teamId: string
): LifecycleResult {
  // 1. 获取同 Market 节点关联的所有企业 FINANCIAL 节点
  const marketNode = store.queryNodes(''Market'', { teamId })[0];
  const competitors = store.queryEdges(''COMPETES_WITH'', { fromId: marketNode.id });
  
  // 2. 计算行业总营收和增长率
  const revenues = competitors.map(e => {
    const fin = store.getNode(e.toId);
    return fin?.props?.amount || 0;
  });
  const totalRevenue = revenues.reduce((a,b) => a+b, 0);
  // (需要历史数据对比 — 从FINANCIAL节点的时间戳字段获取)

  // 3. 应用 Klepper (1996) 判定规则
  // growth > 15% & netEntry > 0 → growth;
  // 5-15% & exits > entries → shakeout;
  // <5% & netEntry ≈ 0 → maturity

  // 4. 返回判定结果 + 置信度
  return { stage: ''growth'', confidence: 0.8, industryGrowthRate: 0.22, netEntryRate: 0.05 };
}

6.2 F1 融资约束指数 — KZ 指数计算

// extensions/sentinels/financing-constraint/computes/kz-index.ts
export function computeKZIndex(finNodes: FinancialNode[]): number {
  // KZ = -1.002×(CF/K) + 3.139×(Debt/TC) - 1.315×(Cash/K)
  // 简化版 (Lamont-Polk-Saá-Requejo 2001)，适合中小企业
  const cf = finNodes.reduce((s,n) => s + (n.props.operatingCashFlow || 0), 0);
  const ppe = finNodes.reduce((s,n) => s + (n.props.netPPE || 0), 0);
  const debt = finNodes.reduce((s,n) => s + (n.props.totalDebt || 0), 0);
  const cash = finNodes.reduce((s,n) => s + (n.props.cash || 0), 0);
  const tc = debt + finNodes.reduce((s,n) => s + (n.props.equity || 0), 0);
  
  const cfRatio = ppe > 0 ? cf / ppe : 0;
  const leverage = tc > 0 ? debt / tc : 0;
  const cashRatio = ppe > 0 ? cash / ppe : 0;
  
  return -1.002 * cfRatio + 3.139 * leverage - 1.315 * cashRatio;
  // 阈值: > 2.0 → 确定受约束; 1.0-2.0 → 可能约束; < 0 → 不受约束
}

6.3 I3 反向定位 — SLM公式计算

// extensions/sentinels/competitive-moat-structural/computes/counter-positioning-slm.ts
export function computeSLM(store: GraphStoreReader, teamId: string): SLMResult {
  // 第一阶段: 四条件检测
  const maxCompetitor = findMaxCompetitor(store, teamId);
  if (!maxCompetitor) return { applicable: false, reason: ''no_clear_incumbent'' };

  const conditions = {
    // 条件1: 巨头核心利润暴露 — 单一业务线利润 > 总利润50%
    profitExposure: checkProfitExposure(maxCompetitor),
    // 条件2: 模式冲突 — 企业BusinessModel vs 竞争者BusinessModel
    modelConflict: checkModelConflict(store, teamId, maxCompetitor),
    // 条件3: 规模不对称 — 企业营收 < 竞争者营收5%
    sizeAsymmetry: checkSizeAsymmetry(store, teamId, maxCompetitor),
    // 条件4: 窗口仍在 — 过去4季度竞争者无类似动作
    windowOpen: checkWindowOpen(store, maxCompetitor),
  };

  const allSatisfied = Object.values(conditions).every(Boolean);
  if (!allSatisfied) return { applicable: false, conditions };

  // 第二阶段: SLM = Om × (OP/NP) × δ
  const Om = getIncumbentProfitMargin(maxCompetitor); // 竞争者旧业务利润率
  const OP_NP = getPriceRatio(maxCompetitor, store, teamId); // 竞争者价格/企业价格
  const delta = estimateCannibalizationRate(store, teamId, maxCompetitor); // 蚕食率
  
  const slm = Om * OP_NP * delta;
  
  return { applicable: true, slm, conditions, confidence: delta > 0 ? 0.7 : 0.4 };
}

九、文件化 vs 代码化 — 架构决策（CTO签署）

架构规则 — 零容忍

  1. 每个哨兵自包含在一个目录内：extensions/sentinels/{name}/
  2. 禁止跨目录引用任何计算逻辑 — 所有 compute 函数通过同目录静态 import 引用
  3. 禁止动态 import() 加载 compute 模块 — 编译器无法验证的路径 = 死链接风险（历史教训：12个哨兵因动态import不存在的模块而失效）
  4. tsc --noEmit 零失败才能合并 — 编译时捕获所有 import 错误
  5. 违反者：代码审查拒绝合并

9.1 设计原则

核心判断："哨兵文件化"的准确含义是——哨兵通过文件系统中的目录和 manifest.json 来声明自己的存在和配置。计算逻辑永远是 TypeScript 代码，组织在可被文件系统发现的目录结构中。

分界线："怎么算"是代码（aggregate.ts + computes/*.ts），"阈值是多少"是配置（manifest.json），"算出来的信号意味着什么"是专家知识（expert/*.md）。

十二、诊断报告呈现结构 — 三层飞轮模型

设计原则：46 个哨兵是诊断引擎的内核，但用户不应该看到 46 个指标。借鉴约束理论（TOC）的诊断流程——体征监测 → 瓶颈定位 → 根因钻探 → 行动处方——诊断报告采用三层结构：前端极简，后端极深。老板看到的是三个飞轮的转速，追问时才展开完整的六层哨兵分析。

12.1 六层 → 三飞轮的聚合映射

46 个哨兵按诊断意图聚合为三个飞轮。每个飞轮的转速 = 该飞轮下所有哨兵得分的加权平均值，权重由该哨兵对增长的"瓶颈贡献度"动态调整。

12.3 行动处方的强制收敛规则

核心原则：无论 46 个哨兵产生多少异常信号，最终给 CEO 的报告只列 1-3 个行动建议。优先级由"影响-紧急矩阵"自动计算。
优先级判定规则输出
P0 — 立即行动瓶颈飞轮中得分为"严重"的哨兵，且该哨兵影响 > 30% 的营收或成本1 个行动建议，带负责人、成功标准、验收时间
P1 — 90 天内瓶颈飞轮中得分为"预警"的哨兵，或非瓶颈飞轮中为"严重"的哨兵最多 2 个行动建议
P2 — 搁置所有其他信号不做行动建议，标注"持续监测"

为什么必须强制收敛：创始人的注意力是最稀缺的资源。如果诊断报告列出 10 个问题，创始人一个都不会解决。只给 1-3 个，他才能行动。

12.4 动态性：持续监测而非一次性诊断

飞轮转速不是静态快照——它是时间序列。每次诊断后，系统记录历史，下一次诊断可以对比趋势：

价值再生飞轮 — 历史趋势
  2026Q1: ██████░░░░ 55%
  2026Q2: ████░░░░░░ 40%  ↓ 下降了 15pp — 恶化加速
  2026Q3: 预测 35%（如果不采取干预）

这种动态性让诊断从"一次体检"变为"持续监护"——这是 AI 原生诊断相比传统管理咨询的核心优势。
