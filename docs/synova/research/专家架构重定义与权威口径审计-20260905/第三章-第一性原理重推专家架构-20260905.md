# 第三章 第一性原理重推专家架构

> 2026-09-05 | 本章是核心裁决：用第一章 8 条准则（G1-G8）+ 第二章证据，重推专家架构目标态

---

## 3.1 三层分层假设的验证

第二章证据证明：代码"事实"已经收敛为三层，只是文档从未说清。

| 层 | 实际代码位置 | 职责 | 对应准则 |
|----|-------------|------|---------|
| 计算层 | `extensions/sentinels/*/computes/` + `src/cycles/*.cycle.json` + `src/loops/direction-monitor.ts` | 确定性计算："数据偏离了什么" | G4 低成本（该算的绝不派 LLM） |
| 推理层 | `expert/`（LLM sub-agent，由 subagent-coordinator 派发） | 非确定性解读："意味着什么、该怎么办" | G2 可信任 + G7 领域深度 |
| 主持层 | `expert/host/`（bg=false，唯一主 agent） | 面向老板：统筹、整合、"增长卡在哪、现在该做什么" | G1 可解释 + G3 可持续 |

**裁决**：三层分层成立，且是正确方向。这不是"要不要分层"的问题，是"文档没把已经存在的分层说清楚"的问题。

## 3.2 专家组织维度：按「问题域」组织（服务老板决策 + 中层核查），不是按循环、也不是按哨兵技术名

### 排除"按循环"（权威文档16 的方案）

权威文档16 把专家命名为 capital-cycle/customer-cycle/talent-cycle，是第一性原理的**误用**：

- 三大循环（资金/客户/人力）是"资源获取→转化→回流"的**因果模型**，属于计算层（方向监测 + 循环模型 + 哨兵 compute 的职责）
- 把"循环"当"专家"（LLM 角色），混淆了"资源流转的计算"和"结论解读的推理"（G4 违反：循环本是确定性计算，却做成 LLM 分析）
- 撞名后果已在第二章证实：capital-cycle 同时是专家名、循环 json（还是 cash-cycle）、方向监测分类（capital）

### 排除"按哨兵"（ARCHITECTURE.md 的方案）

ARCHITECTURE.md 说专家管 N 个哨兵（例：财务专家管成本/收入/现金流哨兵）——方向对（按领域），但粒度错：

- 哨兵是"可独立告警的最小子领域"，有几十个；专家按哨兵组织会太碎，且老板听不懂"哨兵"这种技术名（G1 违反）

### 裁决：按「问题域」组织

专家是**面向老板 + 中层的解读角色**，其组织维度应由"老板能决策、中层能核查"决定。老板的心智模型是"我的钱/客户/人/技术/竞争出了什么问题"；中层的心智模型是"我这个部门的问题，根因在哪、证据是什么、我要怎么查、怎么改"。问题域同时服务这两层：

- 老板按问题域拍板："客户增长出问题了，现在该开拓第二曲线"
- 中层按问题域核查："我是市场负责人，客户增长这个结论的因果链是 E-30 客户集中度 0.82、证据是 CRM 前 3 大客户占 60%——我去核实、去证实"

按问题域组织的真正价值，不只是"老板能懂"，更是**每个职能部门的中层能拿到"和自己有关的因果链 + 证据 + 思维链"**（G8 可核查可下钻）。

推荐问题域（与三循环有映射但命名老板可懂）：

| 问题域 | 覆盖什么 | 与循环的映射 | 示例结论（老板可懂） |
|--------|---------|-------------|-------------------|
| 资金效率 | 现金流、成本、利润、融资、投资 | ≈ 资金循环 | "你的钱卡在应收账期，不是缺订单" |
| 客户增长 | 获客、转化、留存、定价、市场 | ≈ 客户循环 | "你的客户集中度过高，前 3 个大客户占 60% 收入" |
| 组织能力 | 招人、激励、知识、结构、执行力 | ≈ 人才循环 | "你的中层是成本中心，不是利润中心" |
| 技术底座 | 系统、数据、AI 就绪 | 技术（权威文档16 有） | "你的数据散在 5 个系统，没打通" |
| 竞争战略 | 定位、差异化、第二曲线 | 竞争（权威文档16 有） | "你在一个没有护城河的赛道拼价格" |

> 注：这些是"问题域"的候选命名，第五章术语表会正式定词。核心原则是：**专家名=老板的经营语言，不是因果模型的技术名，也不是哨兵的技术名。**

## 3.3 host 角色：唯一主 agent，面向老板的诊断主持人

host（bg=false）在代码里已是唯一常驻主 agent。其职责应明确为：

- **统筹**：决定派发哪些问题域专家（不是"全部始终激活"，而是"按诊断信号按需激活"——省 token，G4）
- **整合**：把各问题域专家的结论 + 循环层的计算证据，整合成"结论先行、证据分层"的报告（G1）
- **对话**：面向老板，回答"增长卡在哪、现在该做什么"，可追问下钻（S0 信任建立）
- **制衡**：在老板冲动决策时客观提醒（S0-3）

这是"驻扎型诊断师"的产品化身，对应底座研究"我们造企业增长医生这辆车"的"医生"角色。

## 3.4 循环专家归层：expert/*cycle* 是「设计残留」，循环归计算层

**裁决**：`expert/capital-cycle`、`expert/customer-cycle`、`expert/talent-cycle` 这三个"循环专家"是 D282 的设计残留，应归计算层或改名，**不作为 LLM 专家派发**。

理由（逐条对准则）：

- 循环的本质是"资源流转的因果模型"，已有真实实现：`src/cycles/*.cycle.json`（cash/customer/talent/product-cycle）+ `src/loops/direction-monitor.ts`（EdgeCategory 偏离分类）+ 哨兵 compute——这是**确定性计算**，不需要 LLM 推理（G4）
- 循环专家的 manifest tools（compute-break-even 等）无对应实现（第二章 §2.5），是旧命名残留——不是"没接好"，是"根本不该存在这层"
- 循环层做的是"算偏离、算溢出"，专家做的是"解读偏离意味着什么"——前者是 compute，后者是 LLM，两者不该同名

**处置**（第五章正式定）：循环概念统一归计算层；expert/*cycle* 的 manifest 要么删除（归 `_deprecated/`），要么改名为问题域专家（如"资金效率专家"），但 tools 必须重新对齐到真实的 extensions compute。

## 3.5 声明式可配置机制（G6，创始人定调）

专家必须是"声明式可调"的分析单元，不是硬编码角色。可配置的四类对象：

| 可配置对象 | 配置在哪 | 调整什么 | 适配谁 |
|-----------|---------|---------|--------|
| 专家 prompt | expert/{域}/prompt 或 manifest | 推理风格、话术、专业深度 | 不同老板（技术派 vs 直觉派） |
| 专家 tools | expert/{域}/manifest.tools | 能调用哪些 compute | 数据完整度不同的企业 |
| 输出结构 | expert/{域}/output-schema | 报告形态（一页纸 vs 分层 vs 对话式） | 老板阅读偏好 |
| 激活策略 | expert-registry.yaml（background/enabled） | 哪些专家常驻、哪些按需 | 企业规模/行业 |

这对应 Synova 既有"文件驱动架构"（ARCHITECTURE.md §5），也对应 DSH 的"一切皆插件 + cordis.yml 配置 + agent preset"（第四章详析）。关键：**改专家不改代码，老板的需求差异通过配置表达，不通过 fork 代码表达。**

## 3.6 专家输出分层：结论树（服务老板决策 + 中层核查）

诊断的**主轴是因果闭环**（观测→归因→判断→跟踪→验证），结论树只是"判断"环节的**呈现方式**——不是诊断工作的骨架，而是"判断结果怎么交到人手里"。诊断产出必须是一个**可下钻的结论树**，同时服务两条腿（决策腿 + 执行腿）：

```
L1 结论层（老板看）     → "增长卡在客户集中度过高，现在该开拓第二曲线"
        ↓ 下钻
L2 根因层（中层看）     → "前3大客户占60%收入，单一客户流失即增长脆弱"
        ↓ 下钻
L3 证据层（执行核查）   → "E-30 客户集中度边=0.82(阈值0.7) + compute-customer-concentration=0.82 + 数据源=CRM 2026 Q2"
        ↓ 下钻
L4 思维链层（中层理解） → "专家推理：客户集中度高 → 流失风险 → 增长脆弱 → 建议第二曲线"
```

四层归属：

| 层 | 产出者 | 服务对象 | 满足准则 |
|----|--------|---------|---------|
| L1 结论层 | host（主持层） | 老板 | G1 可解释 |
| L2 根因层 + L4 思维链层 | 问题域专家（推理层） | 中层/部门 | G8 可核查可下钻 |
| L3 证据层 | 计算层（compute + 因果边 + 数据源） | 执行层核查 | G2 可信任 + G8 |

关键：诊断不是"给老板一份结论"，而是"给老板结论 + 给中层可核查的因果链/证据/思维链"，让结论能下沉到执行——这是昆仑定位 30 万咨询无效果的反面解（老板拿到报告但中层没法执行）。

这对应 C 线 S1-3（因果链）、S2-1（证据分层可点开）、S2-5（可带走性：中层拿去核查），也对应 Harness 的"model-visible⟺logged"与 OpenViking 的"可观测检索轨迹"。

## 3.7 专家架构目标态（本章结论）

```
主持层 host（唯一主 agent，bg=false，常驻）
  │ 统筹 + 输出 L1 结论层（面向老板）
  ▼
推理层 问题域专家（LLM，声明式可配置：prompt/tools/输出结构）
  资金效率 / 客户增长 / 组织能力 / 技术底座 / 竞争战略
  │ 消费循环层信号 + 输出 L2 根因层 + L4 思维链层（面向中层）
  ▼
计算层 循环模型 + 方向监测 + 哨兵 compute（确定性，不跑 LLM）
  资金循环 / 客户循环 / 人才循环（cycles + direction-monitor + 哨兵 compute）
  │ 输出 L3 证据层（可核查）
```

**关键裁决**：

1. 三层分层成立（计算/推理/主持），文档要把已经存在的分层说清楚。
2. 专家按「问题域」组织（老板可懂），不按循环（那是计算层）、不按哨兵（太碎）。
3. 循环归计算层，expert/*cycle* 是设计残留，清理或改名。
4. host 是唯一主 agent，面向老板的诊断主持人，按需激活专家（不是全部始终激活）。
5. 专家声明式可配置（prompt/tools/输出结构/激活策略），改配置不改代码。
6. 专家派发路径必须收敛：当前"三条路径 + 两套 router + 伪专家 dispatch + strategy 旧名残留"（第二章 §2.4/§2.5 复核发现）需收敛为**单一真 LLM 派发入口（ExpertDispatcher）+ 单一路由（l2/expert-router）+ 清理 agent/expert-router 的 MVP 文本 dispatch**。
7. 专家输出是"结论树"四层（结论/根因/证据/思维链），同时服务老板决策（L1）与中层核查（L2/L3/L4）——中层是最大用户群，诊断必须能下沉到执行层的因果链。

## 3.8 交叉验证的升级 + 多岗位部署（2026-09-05 讨论新增）

### 3.8.1 交叉验证从"角色交叉"升级为"因果链交叉"

旧的"多专家交叉验证"（7 个专家各自推理、互相印证）本质是"角色数量的堆叠"，独立性来自人为的角色切分。新架构下，交叉验证升级为三件事：

1. **多因果链收敛验证**：同一现象从资金循环 / 客户循环 / 人才循环三条独立因果链分别推导，收敛到同一根因即验证通过——独立性来自真实的因果结构，不是人为的角色切分。
2. **计算 vs 推理验证**：compute 算出的确定性事实（如客户集中度=0.82 超阈值）与 LLM 推理的判断（"集中度过高导致议价权弱"）互相印证——旧多专家模型没有这一层。
3. **冲突仲裁保留**：`cross-validator` + `conflict-arbitrator` 机制保留，但输入从"专家意见"变成"因果链结论"——当两条因果链给出冲突结论时，裁决"哪条链的证据更强"。

交叉验证的本质是"独立证据的收敛"，新架构把"独立"从"角色"换成"因果链"，收敛得更好、更可信。

### 3.8.2 多岗位部署是自然形态

问题域（资金效率 / 客户增长 / 组织能力）**天然对应不同岗位**：财务负责人对齐资金效率、市场负责人对齐客户增长、HR 对齐组织能力。一个 host 按"岗位身份 + 提问内容"路由到对应问题域因果链，各岗位拿到"和自己业务相关的根因 + 证据 + 思维链"去核查、执行、回流。

权限三层隔离（数据层 / 因果链层 / 结论层），默认按岗位预设 + 超级管理员可调整 + 可审计。

多岗位部署下，交叉验证落地为"各岗位核实自己那条因果链 + host 层收敛"——不同岗位各自证实自己领域的因果，比 AI 内部自说自话更可信（这正是 GA 人机协同的意义）。
