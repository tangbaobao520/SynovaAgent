## 2.2 双权威分叉

### 顶层 ARCHITECTURE.md §4（旧模型）

> 专家（Expert）：一位专家管 N 个哨兵，解读数据、给判断。例：财务专家管成本/收入/现金流哨兵。

证据：`docs/authority/ARCHITECTURE.md` §4（三态=设计权威，但从未更新到 D282 之后，§7 历史演变只写到 2026-06-03）。

- 定义专家按【哨兵/领域】组织，是 L3 洞察层角色
- 无 host 主 agent、无"循环"、无 background 标志，例子还是旧"财务专家"

### 权威文档16（新模型，D282 的设计依据）

证据：`docs/synova/research/权威文档17-自诊断系统-20260729/权威文档17-开发者任务地图-v2-0-20260730.md` L63：`N2 专家迁移 9→7`，`设计依据 | 权威文档16-专家审计报告 §六(最终7位配置) + §七(迁移清单)`。

权威文档16 §六最终 7 位配置：host（主 Agent，始终激活）+ 4 核心专家（资本/客户/人才循环 + 技术，始终激活）+ 2 扩展专家（财务结构/竞争战略，P0 激活）。

### 矛盾

ARCHITECTURE.md 说专家按【哨兵领域】组织；权威文档16 说按【三大循环】组织 + 引入 host 唯一主 agent。两者未对齐，无单一真相源。

## 2.4 设计-实现脱节：循环专家在"真 LLM 派发"被排除，但存在 MVP 文本路径仍路由它们

设计：权威文档16 §六——核心循环专家「始终激活」。

### 真 LLM 派发（两条入口，都排除 background）

- 入口 1：`src/orchestrator/subagent-coordinator.ts:91-92` `getExpertRegistry().listTypes().filter(t => !BACKGROUND_EXPERTS.has(t))` → `ExpertDispatcher.runExpert`
- 入口 2：`src/routes/diagnosis-upload-v2.ts:311` `new ExpertDispatcher(...)` → `runAllExpertsFromInterview` → `runAllExperts`（`src/l3/expert-dispatcher.ts:521-526` 同样 `getBackgroundExperts()` 排除）
- `src/agent/expert-config-loader.ts:117` `getEnabledDiagnosticExperts()` 与 `:125` `getBackgroundExperts()` 是排除逻辑源头

结果：真 LLM 派发只有 `host / finance-structure / competitive-strategy`（bg=false）；资本/客户/人才/技术循环专家（bg=true）不跑真 LLM。

### 第三条路径：MVP 文本派发（非 LLM，仍路由循环专家）——原研究遗漏，本次复核补上

`src/agent/expert-router.ts`（D8c 旧版，与 l2/expert-router 并存）存在独立的 `ExpertRouter.dispatch()`：

- `selectExpert()`（`src/agent/expert-router.ts`）硬编码字符串匹配：`if (s.includes('capital')) return 'capital-cycle'`、`if (s.includes('market')...) return 'customer-cycle'`、`if (s.includes('talent')...) return 'talent-cycle'`——**不经过 background 过滤，仍路由到循环专家**（注释：D491 映射对齐 expert-registry v2.0 的 7 位专家）
- 但 `dispatch()` 的 `buildAnalysis()` 是**文本拼装**（拼 markdown 字符串"基于 N 个信号进行分析"），**不调用 LLM**——这是"伪专家"，路由到了但没做真推理
- 被 `src/agent/cross-validator.ts:155`、`task-decomposer.ts:247`、`main-agent.ts:334/367` 使用

### 结论修正

循环专家（bg=true）的真实状态：**真 LLM 派发（两条入口）排除，MVP 文本派发（agent/expert-router）虽路由但只拼装文本、不做 LLM 分析**。它们既不做真 LLM，也不是真计算层——是"三不管"的设计残留。这与权威文档16「核心专家始终激活」矛盾，且矛盾比原判断更深（不只是"被排除"，而是"被路由到伪专家"）。

## 2.5 专家层与计算层错位（关键证据）

### 专家 manifest 声明的 tools（旧命名）

`expert/capital-cycle/manifest.json`：

- `computes`: COMPUTE-BREAK-EVEN-v1, COMPUTE-DOL-v2, COMPUTE-CAPITAL-ALLOCATION-v1, COMPUTE-NPV-v1, COMPUTE-IRR-v1, COMPUTE-PROFIT-REINVESTMENT-v1（6 个）
- `tools`: compute-break-even, compute-dol, compute-capital-allocation, compute-npv, compute-irr（5 个，与 computes 数组本身就不一致——缺 profit-reinvestment）

### 实际 compute 实现（哨兵/边命名）

`extensions/sentinels/{哨兵}/computes/compute-*.ts` + `extensions/sentinels/shared/computes/{边}/compute-*.ts`：

- 实际存在的：compute-capital-acquisition.ts, compute-capital-source-mix.ts, compute-gross-margin.ts, compute-cash-runway-months.ts, compute-revenue-growth.ts 等
- compute-break-even / compute-dol / compute-npv / compute-irr / compute-hhi 等专家 manifest 声明的工具名，在 extensions 层无对应 .ts 实现（rg 全仓零命中）

### 补充证据：旧专家名 strategy 仍在第三入口残留

`src/routes/diagnosis-upload-v2.ts:312` 的 ExpertDispatcher policies 硬编码 `expertType: 'strategy'`——这是 D282 已删除的旧 9 专家名，仍在 interview 上传路径活着。

### 错位的本质

- 专家 dispatch 不执行 manifest 声明的 tools（专家作为 LLM sub-agent 时由 ExpertAutonomyEngine 读 manifest/prompt，工具列表不是实际 compute 调用链）
- 循环指标的真实计算走：哨兵 compute（extensions/）+ cycles/*.cycle.json（computeOverflow，`src/cycles/overflow-compute.ts:78`）+ direction-monitor（`src/loops/direction-monitor.ts`）
- 观察：要么循环层（哨兵 compute + cycles + direction-monitor）已取代"循环专家做 LLM 分析"的设计；要么 expert/*cycle* 是"设计残留/名义层"。这是第三章要裁决的核心。

## 2.8 第二章结论

1. 「循环」四义 + cash/capital 命名不一，撞名是系统性的，不是单点。
2. 双权威分叉是真实的：顶层 ARCHITECTURE.md 从未更新到 D282，权威文档16 只是被拔高的审计报告。
3. 代码"事实"已经偏离权威文档16：循环专家 bg=true 不跑 LLM，真实计算走哨兵 compute + cycles + direction-monitor。
4. 专家 manifest 的 tools 是"旧命名残留"，与真实 compute 实现彻底错位。
5. 专家派发存在"三条路径 + 两套 router + 新旧专家名混杂"——真 LLM（subagent-coordinator/diagnosis-upload-v2 双入口，排除 background）与 MVP 文本（agent/expert-router，硬编码路由循环专家）并存，且有 strategy 旧名残留。
