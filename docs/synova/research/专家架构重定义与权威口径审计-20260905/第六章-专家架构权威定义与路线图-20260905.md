# 第六章 专家架构权威定义 + 路线图

> 2026-09-05 | 本章产出：可直接作为开发侧新权威的专家架构定义 + 调度模型 + 术语表 + 文档治理路线图

---

## 6.1 专家架构权威定义（最新版）

Synova 的专家体系分**三层**，职责清晰、声明式可配置：

```
主持层  host（唯一主 agent，常驻，面向老板）
  │ 职责：统筹诊断、按需激活专家、整合结论、给"增长卡在哪、现在该做什么"
  │
  ▼
推理层  问题域专家（LLM，声明式可配置，按需激活）
  │ 资金效率 / 客户增长 / 组织能力 / 技术底座 / 竞争战略
  │ 职责：解读信号，给"意味着什么、该怎么办"，交叉验证
  │
  ▼
计算层  资源循环 + 循环模型 + 方向监测 + 哨兵 compute（确定性，不跑 LLM）
  │ 资金循环 / 客户循环 / 人才循环（42 边因果骨架）
  │ 职责：算偏离、算溢出、算指标——"数据偏离了什么"
```

### 三层职责边界（不可越层）

| 层 | 回答的问题 | 确定性 | 成本 | 组织维度 | 输出（结论树） |
|----|-----------|:---:|------|---------|--------------|
| 计算层 | 数据偏离了什么 | 确定性（compute/公式） | 低（不派 LLM） | 按 42 边 + 资源循环 | L3 证据层（可核查） |
| 推理层 | 意味着什么、该怎么办 | 非确定性（LLM 推理） | 中（按需派发） | 按问题域 | L2 根因层 + L4 思维链层 |
| 主持层 | 增长卡在哪、现在做什么 | 整合 + 对话 | 中（常驻） | 唯一主 agent | L1 结论层（面向老板） |

### 诊断产出：结论树（服务分层用户）

诊断产出是**可下钻的结论树**，同时服务决策层（老板）与执行层（中层，最大用户群）：

- L1 结论层（老板）："增长卡在哪、现在该做什么"——短、准、能拍板
- L2 根因层（中层）：按职能归口的根因（财务看财务、市场看市场）
- L3 证据层（执行核查）：因果边数值 + compute 结果 + 数据源
- L4 思维链层（中层理解）：专家推理的中间步骤，可追溯、可证实

中层去核查、去证实 L2/L3/L4，是下一阶段改善的起点——诊断必须能下沉到执行，否则结论束之高阁。

## 6.2 host 角色定义

host = 唯一主 agent，是"驻扎型诊断师"的产品化身。职责：

- 统筹：按诊断信号**按需激活**问题域专家（不是全部始终激活，省 token）
- 整合：把专家结论 + 计算层证据，整合成"结论先行、证据分层"的报告
- 对话：面向老板，可追问下钻，回答"增长卡在哪、现在该做什么"
- 制衡：老板冲动决策时客观提醒（S0-3）

## 6.3 问题域专家定义（声明式可配置）

专家是"面向老板决策 + 中层核查的解读角色"，按问题域组织，声明式可配置四类对象：

| 配置对象 | 配置位置 | 调整什么 | 适配谁 |
|---------|---------|---------|--------|
| prompt | expert/{域}/prompt | 推理风格、话术、专业深度 | 技术派 vs 直觉派老板 |
| tools | expert/{域}/manifest.tools | 能调用哪些 compute（seam 解析，不硬编码） | 数据完整度不同的企业 |
| 输出结构 | expert/{域}/output-schema | 一页纸 / 分层 / 对话式 | 老板阅读偏好 |
| 激活策略 | expert-registry.yaml | 常驻/按需/禁用 | 企业规模、行业 |

关键：改专家不改代码，老板差异通过配置表达（对应 DSH 的 persona + cordis.yml + agent preset，第四章 B2/B3）。

## 6.4 多岗位部署与权限体系（可调整，超级管理员最高权）

多岗位部署是新专家架构的**自然形态**：问题域（资金效率/客户增长/组织能力）天然对应不同岗位。财务负责人对齐资金效率、市场负责人对齐客户增长、HR 对齐组织能力。

**工作方式**：一个 host 统一对话入口，按"岗位身份 + 提问内容"路由到对应问题域因果链，各岗位拿到"和自己业务相关的根因 + 证据 + 思维链"去核查、执行、回流。

**权限三层隔离**（数据层 / 因果链层 / 结论层），且**权限可调整**：

1. 默认按岗位预设：财务→资金效率域，市场→客户增长域，销售→客户增长子链，HR→组织能力域
2. 超级管理员可调整：谁能看什么数据、哪个问题域、全局还是局部结论、只读/可核查/可执行——全部可被超级管理员调整（老板或其授权人）
3. 可审计：权限变更留痕（谁在何时改了谁的权限）

这是 G6 可配置在权限体系上的延伸：权限不是硬编码，而是声明式可调，超级管理员拥有最高调整权。默认预设降低上手成本，可调整适配每个企业的实际岗位与组织架构。

## 6.5 交叉验证与信任可感知

### 6.5.1 交叉验证：从"角色交叉"升级为"因果链交叉"

交叉验证的本质是"独立证据的收敛"，不是"角色数量的堆叠"。新架构的交叉验证 = ① 多因果链收敛（资金/客户/人才三条链独立推导、收敛到同一根因）+ ② 计算 vs 推理验证（compute 事实 vs LLM 判断）+ ③ 冲突仲裁（`cross-validator` + `conflict-arbitrator` 保留，输入从"专家意见"变成"因果链结论"）。多岗位部署下，落地为"各岗位核实自己那条链 + host 层收敛"。

### 6.5.2 信任可感知：证据链是信任来源，不是专家动画

Synova 区别于普通 chatbot 的地方，不在于"背后有专家"，而在于"每句结论都带因果和证据、都能被核实"。信任来自**可核查的证据链**，不是"XX 专家正在思考"的表演式动画（表演式信任一旦被戳穿就崩塌）。

交互层原则：

- 回答自带因果链 + 证据（为什么 + 证据在哪 + 怎么核实），不是一段"看似合理的话"
- 过程透明必须是真过程（真的在调因果边、真的在算指标），不是假动画
- 分角色看不同深度：老板看结论（快，别让他等"思考动画"），中层看因果链 + 证据（要核查）

## 6.8 第六章结论

1. 专家架构 = 三层分层（计算/推理/主持）+ 问题域专家 + host 主 agent，全部声明式可配置。
2. 术语表五词消歧，专家名禁含 cycle。
3. 诊断主轴是因果闭环（观测→归因→判断→跟踪→验证），结论树是"判断"环节的呈现方式。
4. 交叉验证从"角色交叉"升级为"因果链交叉"（多因果链收敛 + 计算 vs 推理 + 冲突仲裁）。
5. 多岗位部署是自然形态，权限三层隔离 + 超级管理员可调整 + 可审计。
6. 信任来自可核查的证据链，不是专家动画；分角色看不同深度（老板看结论、中层看证据）。
7. 文档治理 P0 两项（ARCHITECTURE.md + 权威文档16 拆分），P1/P2 转开发。

## 6.9 落地缺口补充（2026-09-06 全面评估追加）

> 6.8 之前给的是"架构结论"，本节补"落地机制"——开发 session 落地时会被卡住的四个点。

### 6.9.1 系统提示词三层结构 + 专家三层增减

系统提示词不是"一个"，是**三层**：

| 层 | 内容 | 随什么变 |
|----|------|---------|
| 全局层（host） | Synova 使命、通用诊断规则、三层分层约定 | 所有企业一样 |
| 问题域层（专家 PROMPT.md） | 每个问题域的领域知识 + 诊断框架 + 输出要求 | 通用但可配置 |
| 企业/行业层（适配提示词） | 行业知识、企业事实、预算约束、老板偏好 | 随行业/企业增减 |

专家是**三层增减**（文件驱动保留，扩展为三层）：

| 层 | 定义 | 增减方式 |
|----|------|---------|
| 基础问题域专家 | 资金效率/客户增长/组织能力/技术底座/竞争战略 | 内置，所有企业都要 |
| 行业专家 | 制造业→供应链、零售→渠道、外贸→跨境 | 随行业 profile 增减 |
| 企业专家 | 某企业特有领域 | 随企业配置增减 |

旧循环专家 → 新问题域专家的提示词迁移：capital-cycle→资金效率、customer-cycle→客户增长、talent-cycle→组织能力、tech→技术底座、finance-structure→并入资金效率、competitive-strategy→竞争战略、host→保留。旧目录归档 `expert/_deprecated/`，新目录 `expert/{问题域}/PROMPT.md` 新建。

### 6.9.2 多岗位的身份识别与路由

多岗位部署的前提：系统要知道"当前对话的人是谁、属于哪个岗位、能看什么"。缺这一层，多岗位就是空话。设计：

```typescript
interface UserContext {
  userId: string;
  role: 'founder' | 'ga' | 'department-head' | 'employee';
  department?: 'finance' | 'marketing' | 'sales' | 'hr' | 'tech' | 'product';
  /** 可访问的问题域 + 数据层权限 */
  permissions: { domains: string[]; dataLevels: string[] };
}
```

host 路由 = 岗位身份 + 提问内容 → 问题域因果链。已有基础：`src/middleware/auth.ts` + `rbac.ts`（身份认证 + 权限）；需补：岗位→问题域的绑定 + host 的路由决策（复用 l2/expert-router 的 4 层路由，或收敛为单一入口）。

### 6.9.3 因果链交叉验证的落地机制

"因果链交叉验证"的落地，不是推翻 cross-validator，而是**改造它的输入**：

| 现状 | 改造后 |
|------|--------|
| cross-validator 交叉验证"专家意见" | 交叉验证"因果链结论"（资金循环链 vs 客户循环链收敛到同一根因） |
| conflict-arbitrator 裁决"专家分歧" | 裁决"因果链冲突"（哪条链的证据更强） |

落地路径：① 各问题域专家输出带"因果链 ID + 边 ID + 证据"的结构化结论；② cross-validator 改为检查"不同因果链是否收敛到同一根因"；③ conflict-arbitrator 改为"因果链证据强度裁决"。

### 6.9.4 问题域专家 → compute 的 seam 映射

问题域专家要调 compute，但 compute 按"哨兵/边"组织。需要一张"问题域 → compute 清单"的映射表（seam 落地）：

```yaml
# expert/{问题域}/compute-map.yaml
fundamental-efficiency:
  computes: [compute-cash-runway-months, compute-gross-margin, compute-receivable-overdue-rate, compute-cost-per-head]
  edges: [E-13, E-23, E-34]
```

专家 manifest 声明"需要资金效率 compute"，seam 解析到真实 compute 实现（对应第四章 B4 capability seam）。这张映射表是"专家 tools 重对齐"的具体载体，替代当前 manifest 里"compute-break-even 等无实现工具名"的错位。
