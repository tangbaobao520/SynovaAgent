# 第四章 DSH 借鉴评估（含具体理由）

> 2026-09-05 | 对象：本地 `D:\deepseek-harness`（v0.1.0-rc.5，MIT）
> 方法：逐条对照 Synova 专家架构需求（第三章目标态 + 第一章 G1-G8），给"可借鉴/不可借鉴/领域深度不可替代"清单，每条带理由

---

## 4.1 可借鉴（4 项，各带理由）

### B1 subagent seam 多后端 → 专家调度机制

DSH 的 subagent seam（`packages/subagent/`）让一个 agent 通过命名 provider 委托子任务，provider 决定子 agent 跑在本进程/其他进程/未来 transport。支持 acp / claude-code / codex / fork-in-process / spawn-in-process 五种后端。

**理由**：Synova 的 host 派发问题域专家，正是"一主多子"的委托模式。借鉴 seam 化可让专家调度获得两个能力：① 专家 provider 可换（当前 in-process LLM 专家，未来可换跨进程/远程，甚至把某类专家交给 DSH subagent 后端跑）；② 专家按需激活/中断（DSH 的 start/startContinuable/interrupt 生命周期，对应第三章"按诊断信号按需激活专家"）。这直接服务 G4（低成本：按需派发）和 G5（可扩展：加 provider 不改派发逻辑）。

### B2 persona + cordis.yml 声明式配置 → 专家 prompt/tools/激活策略可配置

DSH 的 agent-preset 用 `agent.cordis.yml` 声明式配置 agent 组成：`persona` 插件配身份提示词、`tool-*` 插件配工具、`disabled: !!js 条件` 按环境禁用。改配置不改代码。

**理由**：这正是第三章 G6 可配置的工程范式，且比 Synova 现有 expert-registry.yaml 更完整。借鉴点：① persona 独立成配置项（Synova 的专家 prompt 应独立成可改的配置文件，而非散在 manifest/prompt 文件里无统一约定）；② tools 用插件行声明 + 条件禁用（对应"不同数据完整度的企业启用不同 compute 工具"）；③ preset 概念（不同老板=不同 preset，一套配置切换）。这直接服务 G6 可配置、G5 可扩展。

### B3 agent preset → 老板画像适配层

DSH 有 standard/minimal/cordis/code 四个 preset，同一个 dsh 用不同 preset 就变成不同能力的 agent。

**理由**：Synova 的"适配不同老板"可落地为"老板 preset"——技术派老板（要数据细节）vs 直觉派老板（要结论+故事）vs 外贸老板 vs 制造老板，各是一套专家组合 + prompt 风格 + 输出结构。这是 G6 的产品化表达，也是 B 线"三层共鸣"（不同行业老板共鸣）的技术底座。

### B4 capability seam 三角色 → compute 工具的组织

DSH 的 capability seam = Service Definition / Provider / Consumer 三分离，provider 可换、consumer 不变。

**理由**：Synova 的"专家能调用哪些 compute 工具"可 seam 化——专家（consumer）声明需要"资金效率 compute"（definition），实际由哨兵 compute 或循环模型（provider）提供。这样修复第二章 §2.5 的"专家 manifest tools 与 compute 错位"：不再让专家硬编码工具名，而是声明能力、由 seam 解析到真实实现。服务 G5 可扩展 + 修复错位。

## 4.2 不可借鉴 / 领域深度不可替代（5 项，各带理由）

| # | 能力 | 为什么 DSH 没有/不可借鉴 | 归属 |
|---|------|------------------------|------|
| N1 | 专家组织维度（问题域） | DSH 的 agent 是通用 coding agent，无"资金效率/客户增长/组织能力"这种组织诊断问题域；它的 persona 是"coding agent"，不是"增长诊断专家" | 领域深度 |
| N2 | 三层分层（计算/推理/主持） | DSH 无"循环模型/direction-monitor/哨兵 compute"这种确定性诊断计算层；它的 agent 只有"工具调用"，没有"先算偏离、再解读"的分层 | 领域深度 |
| N3 | 42 边因果本体 + 三循环资源闭环 | DSH 完全没有组织因果图；这是 Synova 诊断的第一性原理，DSH 不提供也不该提供 | 领域深度 |
| N4 | GA 人机协同闭环 | DSH 是通用 agent 框架，无"企业场景的人验证 AI"（GA 验证/否决/仲裁）概念 | 领域深度 |
| N5 | 诊断报告形态（结论先行+证据分层） | DSH 的产物是代码/工具调用/终端输出，不是"一页纸诊断报告 + 证据卡片" | 领域深度 |

## 4.3 借鉴的边界（红线）

1. **借鉴止于"调度机制 + 可配置范式"**（B1-B4），专家组织维度、三层分层、因果本体、GA 闭环、报告形态（N1-N5）是 Synova 领域深度，不照搬 DSH。
2. **不引 DSH 代码依赖**——DSH 是 v0.1.0-rc.5 开发者预览，破坏性变更承诺；借鉴"理念"自研（如 seam 化、声明式配置），不 import DSH 包。
3. **DSH 的 subagent 后端（claude-code/codex）是"委托给外部 agent"**——Synova 的专家是"领域 LLM 分析"，不是"委托给 coding agent"，两者用途不同，不能简单替换。

## 4.4 第四章结论

1. 可借鉴 4 项（B1 subagent seam、B2 persona+声明式配置、B3 preset、B4 capability seam），全部服务"调度 + 可配置"，不碰领域深度。
2. 不可借鉴 5 项（N1-N5）全部是 Synova 的护城河——组织诊断的问题域、三层分层、因果本体、GA 闭环、报告形态。
3. 借鉴的边界清晰：借"怎么调度、怎么配置"（DSH 的工程范式），不借"诊断什么、怎么判断"（Synova 的领域知识）。

这印证了底座研究 08-16 的结论："通用工程借 Harness（调度/配置），领域深度自己做深（诊断知识）"。
