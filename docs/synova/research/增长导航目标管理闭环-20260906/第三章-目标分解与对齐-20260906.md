# 第三章 目标分解与对齐（Decompose + Align + 3 关系）

> 2026-09-06 | 覆盖生命周期第 2-3 环节（分解+对齐）+ MECE 维度三（关系 3 类）
> 核心增量：纵向对齐 + 约束注入（用户强调"市场做营销计划要记住财务预算"）

---

## 3.1 目标分解的本质

目标分解 = 把公司目标（战略意图）分解为部门目标（可执行），再分解为个人任务。分解不是"机械拆数字"，而是"对齐 + 约束"的分解——每个部门目标都要能回答：**它支撑公司哪个目标（纵向）、依赖/支撑哪个部门（横向）、受什么约束（事实层）**。

## 3.2 三个关系（MECE）

| 关系 | 定义 | 检查 | 例子 |
|------|------|------|------|
| 纵向对齐 | 部门目标 ↔ 公司目标（父-子） | 对齐检查 | 市场部"获客 1000"支撑公司"营收翻倍" |
| 横向依赖 | 部门目标 ↔ 部门目标（输入-输出） | 依赖检查 | 市场获客 1000 → 销售转化 100 |
| 约束注入 | 目标 ↔ 企业事实（预算/资源/能力） | 约束检查 | 市场营销计划 ≤ 财务预算 200 万 |

## 3.3 纵向对齐（新增，当前缺失）

部门目标必须能回答"它支撑公司的哪个目标"。设计：

```typescript
interface GoalAlignment {
  /** 上级目标（公司/部门） */
  parentGoalId: string;
  /** 对齐方式：支撑上级的哪个关键结果/指标 */
  supportsKrId?: string;
  /** 对齐强度：直接支撑/间接支撑/不相关 */
  alignmentStrength: 'direct' | 'indirect' | 'unrelated';
}
```

对齐检查：部门目标创建时，系统检查它是否支撑某个上级目标；若"无上级支撑"（孤岛目标），提示"这个目标和公司目标脱节，确认吗？"——防止各干各的。

## 3.4 横向依赖（当前部分实现，需扩展）

`goal-conflict-detector.ts` 已检测部门内 Goal 的维度冲突（direction/resource/timeline/duplicate），但缺"跨部门依赖"（市场获客 → 销售转化）。

设计补充：

```typescript
interface GoalDependency {
  /** 依赖/供给的目标 */
  relatedGoalId: string;
  /** 关系方向：上游供给 / 下游依赖 */
  direction: 'upstream' | 'downstream';
  /** 依赖的量（市场供 1000 线索 → 销售需 100 转化） */
  quantity?: number;
}
```

依赖检查：市场部目标"获客 1000"和销售部目标"转化 100"之间有量级依赖（转化率假设 10%）。系统检查两者是否匹配，若销售目标"转化 200"而市场只供 1000 线索（10% 转化率只够 100），提示"销售目标和市场供给不匹配"。

## 3.5 约束注入（新增，用户强调的核心）

### 本质

企业事实层（权威文档16）里有制度、规则、预算、资源。部门做计划时，系统要**自动注入约束**，防止部门"各干各的、超预算"。

### 约束的来源（企业事实层）

```typescript
interface EnterpriseConstraint {
  id: string;
  type: 'budget' | 'resource' | 'policy' | 'capability';
  /** 预算上限、资源数量、制度条款、能力上限 */
  value: number | string;
  /** 约束作用域：全局/某部门/某项目 */
  scope: { department?: string; goalId?: string };
  /** 来源：老板设定 / 财务制度 / 历史数据推导 */
  source: 'founder' | 'finance-policy' | 'derived';
}
```

### 约束注入的触发时机

1. **目标设定时**：市场部定"营销计划"，系统自动查询财务约束 → 注入"营销预算上限 200 万"，目标若超出则提示。
2. **目标执行时**：执行中预算花超了，方案级哨兵触发偏离告警（接第四章）。
3. **目标调整时**：轻量级再诊断调整方案，约束重新检查。

### 例子（用户给的场景）

市场部要做营销计划对齐公司"营收翻倍"目标，系统自动注入约束：

```
市场部目标：获客 1000（支撑公司营收翻倍，纵向对齐 ✓）
约束注入：营销预算上限 200 万（来自财务制度，企业事实层）
检查：计划预算 250 万 > 200 万 → 系统提示"超出财务预算约束，确认调整还是超预算申请"
```

这就是"市场做营销计划，要记住财务的约束"——约束来自企业事实层，系统自动注入 + 检查。

## 3.6 三个检查（对齐 + 依赖 + 约束）的统一

目标分解时，系统做三个检查，缺一不可：

| 检查 | 检查什么 | 失败时 |
|------|---------|--------|
| 对齐检查 | 部门目标是否支撑上级目标 | 提示"孤岛目标" |
| 依赖检查 | 跨部门目标量级是否匹配 | 提示"供给/需求不匹配" |
| 约束检查 | 是否超出预算/资源/制度 | 提示"超约束，需调整或申请" |

现有实现只覆盖"部门内冲突"（goal-conflict-detector 的 direction/resource/timeline/duplicate），本次研究补齐"纵向对齐 + 跨部门依赖 + 约束注入"。

## 3.7 第三章结论

1. 目标分解 = 对齐 + 约束的分解，不是机械拆数字。
2. 三个关系（纵向/横向/约束）MECE，三个检查（对齐/依赖/约束）缺一不可。
3. 约束注入是本次研究的核心增量：企业事实层（预算/资源/制度）自动注入目标，防止部门各干各的、超预算。
4. 现状缺口：goal-conflict-detector 只做部门内冲突，需补齐纵向对齐 + 跨部门依赖 + 约束注入。
