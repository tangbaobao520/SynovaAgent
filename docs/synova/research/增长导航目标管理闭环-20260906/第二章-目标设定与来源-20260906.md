# 第二章 目标设定与来源（Set + 3 来源）

> 2026-09-06 | 覆盖生命周期第 1 环节（设定）+ MECE 维度二（来源 3 类）
> 核心增量：决策驱动来源的"决策记录"机制（用户强调的重点）

## 2.1 目标设定的本质

目标设定 = 把"企业该做什么"转化为"可度量、可分配、有时限、可追溯来源的目标"。权威文档13 已定义 Goal 的 28 字段 + 7 态状态机，这是成熟地基，本次不推翻，只补"来源"维度。

核心原则（从第一性原理）：**目标是"有依据的"，不是"拍脑袋的"**。每个目标都要能回答"它从哪来、依据是什么、谁来执行、怎么度量"。依据分三类（MECE），对应三个来源。

## 2.2 三个来源（MECE）

| 来源 | 定义 | 触发 | 追溯字段 |
|------|------|------|---------|
| 诊断驱动 | 诊断发现增长卡点 → 转化为目标 | 哨兵偏离/GA 手动触发诊断 | `source.diagnosisReportId`（已有） |
| 决策驱动 | 老板凭直觉/经验定新方向 → 记录决策 → 分解为目标 | 老板主动提出新目标（可能忽略/推翻诊断） | `source.decisionRecordId`（新增） |
| 外部驱动 | 市场变化/客户流失/竞争对手动作 → 逼出目标 | 外部事件触发（大客户流失、对手降价） | `source.externalEventId`（新增） |

## 2.3 诊断驱动来源（已实现，保留）

权威文档13 已实现：诊断建议 → Proposal 三选一 → Goal，`goal-types.ts` 的 source 字段记录 `diagnosisId`。这是"诊断 → 目标"的完整追溯链，保留。

## 2.4 决策驱动来源（新增，用户强调的核心）

### 为什么必须做

真实企业里，老板**常常忽略诊断、凭经验和直觉定方向**。这不是"坏"——老板的直觉有时比数据更快抓住机会。但如果这个直觉不记录、不跟踪、不验证，它就永远是"拍脑袋"，系统无法回答三个月后"当初为什么走这条路、这条路对不对"。

所以决策驱动来源的工程价值是：**把老板的直觉也纳入验证闭环，用结果说话**——系统忠实记录、跟踪、验证老板拍板的新方向，最终回馈"这个直觉对不对"。

### 决策记录的数据结构（DecisionRecord，新增）

```typescript
interface DecisionRecord {
  id: string;
  /** 决策人（老板/创始人） */
  decidedBy: { role: 'founder' | 'ga'; name: string };
  /** 决策时间 */
  decidedAt: string;
  /** 决策内容（一句话方向，如"明年进军东南亚市场"） */
  direction: string;
  /** 决策依据（老板口述的理由，可自由文本） */
  rationale: string;
  /** 与诊断的关系 */
  relationToDiagnosis: 'aligned' | 'overriding' | 'unrelated';
  /** 若 overriding：覆盖了哪条诊断建议 */
  overriddenRecommendationId?: string;
  /** 关联的约束（预算上限/资源，若老板口述） */
  constraints?: { budget?: number; resource?: string };
  /** 分解出的部门目标 */
  derivedGoals: string[];
}
```

### 决策驱动的完整流程

1. **记录**：老板说出新方向 → 系统记录 DecisionRecord（方向 + 依据 + 与诊断的关系）
2. **对齐约束**：系统自动注入企业事实层——"这个方向要花多少钱、受什么约束"（接第三章约束注入）
3. **分解**：决策 → 按部门/角色分解为 Goal（市场部对齐"进军东南亚"，财务部约束"预算 200 万"）
4. **跟踪**：决策衍生的 Goal 进入方案级哨兵追踪（接第四章）
5. **验证**：决策关闭时，验证"这个直觉带来的结果"（接第五章）
6. **回流**：验证结果回流——"老板这个直觉对了/错了"，沉淀为企业决策经验

### 关键：不与诊断对立，而是互补

决策驱动和诊断驱动不是二选一，而是"两个来源都记录、都跟踪、都验证"。诊断说"客户集中度过高，该降集中度"，老板说"我偏要发力大客户"——系统忠实记录老板的决策（relationToDiagnosis='overriding'），跟踪执行，最后验证：是诊断对了，还是老板的直觉对了。**这正是"超越共识"的体现——用结果裁决，而不是用立场裁决。**

## 2.5 外部驱动来源（新增）

外部事件（大客户流失、对手降价、政策变化）逼出的目标，也要记录跟踪。来源追溯到具体事件（`source.externalEventId`），便于事后复盘"这个目标是外部逼的，还是主动定的"。

## 2.6 统一的来源追溯（目标都能回答"从哪来"）

三个来源统一到 Goal 的 source 字段，任何目标都能回答"它从哪来"：

```typescript
source: {
  diagnosisReportId?: string;   // 诊断驱动
  decisionRecordId?: string;    // 决策驱动（新增）
  externalEventId?: string;     // 外部驱动（新增）
}
```

三选一（MECE），一个目标只能有一个来源。这是"决策可追溯、结果可验证、经验可沉淀"的前提。

## 2.7 第二章结论

1. 目标设定的本质是"有依据、可追溯"，依据分三类（诊断/决策/外部，MECE）。
2. 诊断驱动已实现；决策驱动和外部驱动是本次研究新增。
3. 决策驱动的核心是"DecisionRecord"——把老板的直觉纳入验证闭环，用结果裁决对错，这是"超越共识"的工程承载。
