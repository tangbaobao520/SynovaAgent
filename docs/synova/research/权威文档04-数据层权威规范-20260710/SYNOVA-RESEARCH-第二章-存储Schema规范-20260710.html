2.1 四个存储引擎

引擎存储内容强制时间字段对应15概念节点
GraphStore本体层节点+边。所有15个池的数据载体valid_from, valid_to, observed_at
created_at, updated_at		CAPITAL_POOL, HUMAN_CAPITAL_POOL, KNOWLEDGE_POOL, BRAND_POOL, REPUTATION_POOL, DATA_POOL, REVENUE_POOL, SENSING_POOL, 6活动池
SessionStore诊断会话状态+历史。每次诊断的临时状态created_at, completed_at—（会话层，非概念节点）

KnowledgeStore行业基准、GA校准数据、黄金案例valid_from, valid_toExternalBaseline（参照系）

2.2 有效时间语义——强制规则

时序查询强制使用observed_at或valid_from，不是created_at。
created_at是系统写入时间——当数据延迟补录时（6月补录3月数据），created_at=6月但valid_from=3月。如果用created_at计算"过去3个月的趋势"，会得到完全错误的结果。

2.2.1 时间字段定义

字段含义来源
valid_from数据记录的业务有效周期起点源数据日期列 / 用户标注周期
valid_to数据记录的业务有效周期终点valid_from+1周期（默认可由系统推算）
observed_at数据实际被观测/采集的时间点源数据日期列 / 文件上传时间
created_at系统写入时间（事务时间）系统自动生成

2.2.2 数据延迟补偿策略

延迟幅度策略
observed_at与valid_from差距 < 7天正常纳入时序计算，标注late_arrival
差距 7-30天纳入但降低权重（weight=0.5）
差距 > 30天不纳入实时基线计算，仅在历史回测中可用

2.3 数据版本保留策略

层级保留内容策略
Layer 1: 当前+最近3个完整数据：value + source_origin + observed_at + confidence永久保留（用于时序诊断的差分计算）
Layer 2: 更早历史摘要：superseded_at + superseded_by + conflict_resolution压缩保留（不保留完整数据值，仅保留版本切换记录）
Layer 3: GA可配置覆盖Layer 2的默认策略企业级客户可要求"永久保留所有版本"（审计合规需求）
"忠实记录" ≠ "永不删除"。不丢弃真实的历史信号，但不在存储中无限保留所有版本的完整副本。默认保留最近3个完整版本，更早的压缩为版本切换摘要。

2.4 GraphStore节点Schema

每个数据节点 = 概念节点池中的节点类型，携带统一Schema：

字段类型必填说明
node_idstring (UUID)是节点唯一标识
typestring是节点类型（对应概念节点池名，如"CAPITAL_POOL"）
propsRecord<string, unknown>是池属性键值对。对应outcome JSON定义的Schema
valid_fromdatetime是业务有效周期起点（强制）
valid_todatetime是业务有效周期终点（强制）
observed_atdatetime是观测时间点（强制）
created_atdatetime是系统写入时间
source_originstring是数据来源标识
data_versionsarray否多版本数组（有冲突时追加；新版覆盖is_active时旧版移入此数组）
has_conflictboolean否是否存在活跃数据冲突
pii_maskedboolean否是否已对PII字段做脱敏处理
