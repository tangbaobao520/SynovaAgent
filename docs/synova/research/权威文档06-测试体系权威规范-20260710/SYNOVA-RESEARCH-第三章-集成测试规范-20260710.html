3.1 L2a：哨兵接线测试

3.1.1 前置 Phase 0：Traversal 路径 YAML 入库

核心原则：接线测试需要"已知正确的 traversal 路径"作为基准。基准未入库 = 无法判断偏离。Phase 0 的路径 YAML 入库是 L2a 的前置条件。
项目内容
输入来源哨兵权威规范（第一章）中每个哨兵的"可执行路径规范"字段——已定义 DiagnosisContextNode→42 边→compute 的完整链路
输出格式extensions/traversal/{sentinel-name}.yaml——结构化 YAML
路径模板{sentinelName, diagnosisContext→causalEdges[{id, parameters[]}]→compute[{contractId, inputParams[]}]→findingSchema}
产出数量50 个 YAML 文件（对应哨兵权威规范中的 50 个哨兵）

3.1.2 接线测试模板

每个哨兵 1 个集成测试用例，验证以下 5 项：

#验证项通过标准失败时阻断
1L0 存活探针哨兵进程启动 → 消费输入 → 在 30s 内输出符合 Schema 的 Finding阻断
2Traversal 路径匹配代码中的 traversal 路径（哨兵→边→compute）与基准 YAML 一致阻断

3.2 L2b：专家推理验证（新增维度）

3.2.1 为什么需要专家推理验证

诊断质量的灵魂不在 compute 函数里，在专家 Agent 的系统提示词里。compute 输出的是"信号"，专家把信号转化为"诊断结论"。如果提示词设计不当——死锁性偏见、认知嫁接、闭合循环——compute 再正确也是白费。只测 compute 不测专家 = 只验证"系统会不会算错"，不验证"系统会不会想错"。

3.2.2 五个验证维度

维度验证内容故障模式验收标准
1. 角色对齐给定一组 Finding，专家是否只输出自己职责范围内的诊断？角色漂移（组织专家开始做财务分析）角色越界率 <5%
2. 证据链一致性专家 B 引用的证据是否真实存在于专家 A 或上游推理中？认知嫁接（引用了不存在的前序推理）、闭合循环（引用 B→A→B 自循环）证据幻觉率 = 0（零容忍）
3. 输出稳定性同一组 Finding 输入 10 次，专家输出是否一致？LLM 随机性导致诊断摇摆（"上周健康，这周重病"）噪声度 <10%
4. 边界识别当 Finding 不足以支撑诊断时，专家是否输出"信息不足"而非编造结论？幻觉生成（数据不足时强行给出具体结论）"无法判断"率在信息不足场景下 ≥90%
5. 因果推理完整性从 Finding 到诊断结论，因果链是否完整且可追溯？跳跃推理（"毛利率下降，所以应该换 CEO"）每个诊断结论可追溯到 ≥1 条 42 边

3.2.3 专家推理验证集格式

字段内容
验证集 IDEXPERT-VERIFY-{expertType}-{seq}，如 EXPERT-VERIFY-STRATEGY-001
输入一组标准化的 Finding[]（JSON 数组）——模拟 42 边不同边类型的信号组合（单边信号 / 多边交叉 / 信息不足 / 冲突信号）
预期输出诊断结论模板——应包含：核心发现 × 1-3 条 / 每条可追溯到 ≥1 条 42 边 / 置信度 / 不应包含的越界内容
评分规则完全匹配（核心发现+因果链均正确）= 1.0 / 部分匹配（核心发现正确但因果链不完整）= 0.5 / 完全不匹配（方向错误）= 0 / 幻觉（编造不存在的信息）= -1.0（阻断）

3.3 L2c：循环基础设施测试（新增维度）

5 个 Loop Engineering 循环是 Agent 的生命线。以下 4 个验证维度确保循环"能跑通、断了能恢复"。

#验证维度测试方法验收标准
1循环启动mock Cron/事件触发 → 检查循环管理器是否正确启动5 个循环 100% 启动成功。启动失败 → 阻断
2状态机模拟 running→completed / running→failed 转换 → 检查状态是否正确写入状态转换正确率 100%。连续 3 次 failed → 必须触发断裂告警
3三级恢复模拟循环中途中止 → 验证 L1 自动重试 → 若 L1 也失败 → L2 半自动（GA 一键恢复） → 若 L2 也失败 → L3 手动（管理员介入）三级恢复链路完整。L1→L2→L3 升级正确
4依赖传递模拟企业诊断循环完成 → 检查输出是否正确传递到部门导航循环。模拟 GA 校准操作 → 检查 GA 进化循环是否消费了校准数据跨循环数据传递正确。消费者循环在输入到达后 1 分钟内感知
