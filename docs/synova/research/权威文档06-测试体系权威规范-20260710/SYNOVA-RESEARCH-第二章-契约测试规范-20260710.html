2.1 执行顺序（不可颠倒）

核心原则：测试规范不能假设"规范已定义但代码中不存在"的状态。代码和规范必须同步演进。Phase A（补 JSDoc @contract）必须在 Phase B（设计测试蓝图）之前完成。

2.2.2 补全标准

为每个 compute 函数补全以下 JSDoc 标注：

/** @contract {contractId} {version} {input interface} {output interface} {degraded strategy} */
字段格式示例

2.3 Phase B：嵌入式测试蓝图设计（本研究期间，50-60 min）

2.3.1 测试蓝图模板

每个 compute 函数定义以下字段：

字段内容
contractId从 Phase A 的 @contract 标注中提取
输入 fixture（4 组）(1) 正常路径——典型输入，预期正常输出；(2) 边界条件——临界值（如 allocation_ratio=0 或 efficiency_rate=1.0）；(3) 异常降级——触发 degraded 的输入；(4) 时序数据片段——消费时序边参数时强制包含 ≥3 个时间点
预期输出value 范围 + confidence 范围 + degraded 标志 + warnings[] 内容
边界条件什么输入触发降级（如："P≤AVC→BEP 不存在"）

2.3.2 时序 fixture 强制规则

规则：任何消费了携带时序参数的 42 边（具有 window_3m、slope、trend、variance、rate_of_change 等字段）的 compute 函数，其测试 fixture 必须包含一个时间序列数据片段（≥3 个时间点），以验证斜率计算、趋势检测、方差分析等时序逻辑。

违反判定：无时序 fixture 的测试 → 自动扫描脚本判定为"契约不完整"。pre-commit 阶段 阻断。

2.4 自动扫描脚本规范

在现有 check:iron-laws 中增加契约检查：

  1. 扫描 engine-core/src 下所有 .ts 源文件（排除 index/types/d.ts）
  2. 检查每个文件是否包含 @contract JSDoc 标注
  3. 检查对应的 .test.ts 文件是否存在（适配 __tests__/ 子目录或同目录配对）
  4. 检查测试文件中是否包含至少 1 个 expect()
  5. 检查时序 compute 的 fixture 是否包含 ≥3 个时间点数据
  6. 输出"契约覆盖率报告"——contractId 存在率 / 测试文件存在率 / 时序 fixture 存在率
  7. 任何缺失 → 输出具体文件路径和缺失项
