Finding F1: Loop Breakage Patterns Exposed by ROADMAP (6564 lines, selected patterns)
  1. Session lifecycle inconsistency: same session emits completed -> idle -> error -> completed noise. Fix: monotonic sequence + terminal vs advisory classification + dedupe window (ROADMAP 4.5-4.8).
  2. Event source pollution: test/healthcheck events share the same channel as production events, causing false automation triggers. Fix: every event labeled with source kind (live_lane / test / healthcheck / replay / transport) (ROADMAP 4.6).
  3. Startup-no-evidence: worker stalls in vague startup-no-evidence state. Fix: typed evidence bundle + classifier downgrades to specific subclass (ROADMAP 1.6).
  4. Nudge dedupe failure: periodic nudges trigger duplicate follow-ups. Fix: nudge id + acknowledged state (ROADMAP 4.10).
  5. JSON envelope inconsistency: 9 subcommands each have different success fields in --output-format json; only kind is universal (ROADMAP 458).
  6. AGENTS.md not read: hardcoded to only read CLAUDE.md; cross-tool standard files invisible (ROADMAP 459).

A1.2 Hermes Agent -- Session-Level Loop

D:\Git项目研究\hermes-agent-main\agent\conversation_loop.py:263

run_conversation (~3900 lines) drives a single user turn through: model call -> tool dispatch -> retry -> fallback -> compression -> post-turn hooks -> background memory/skill review nudge. Key mechanisms:

  • Post-tool empty response nudge: when the model returns empty response after tool calls, injects synthetic assistant message + user nudge to push the model to continue. Prevents loop breakage on model silence.
  • Interrupt + redirect: user can Ctrl+C or send new message at any time; agent handles gracefully.
  • Auto-compaction: 100K token threshold triggers automatic compression.
  • Iteration budget: max_iterations=90 caps tool-calling loop iterations.
Finding F2: Hermes Loop Breakage Patterns
  • Subagent deadlock: approval callback stored in threading.local(); ThreadPoolExecutor worker threads do not inherit from parent. Without a properly installed non-interactive callback, subagent input() deadlocks against the parent TUI. Fix in delegate_tool.py via ThreadPoolExecutor(initializer=...).
  • Incomplete toolset isolation: DELEGATE_BLOCKED_TOOLS blacklist is static; newly added tools may not be blocked for subagents.

A1.4 Implications for Synova

A1 Implications

  3. Recovery Recipes directly portable: encode LLM timeout / ontology query failure / measurer data-missing as named recipes.

A4.4 Architecture Boundary Enforcement

Common patterns across all three projects:

  • Claw Code: Rust type system + crate boundaries enforce at compile time. Session / Config / Permissions are separate crates; cross-boundary access prevented at build time.
  • OpenClaw: AGENTS.md explicit rules: "Core stays plugin-agnostic", "Plugins cross into core only via plugin-sdk", "No core src/** imports from plugins". pre-commit + CI enforce violations.
  • Hermes: Python module import boundaries + delegate_tool blacklist mechanism.
Finding F5: Synova Five-Layer vs Benchmarked Projects -- Boundary Enforcement Comparison

Synova's five-layer architecture (L1-Interaction L2-Orchestration L3-Insight L4-Ontology L5-Storage) aligns closely with OpenClaw's "Core/Plugin/Channel" layering philosophy. Key differences:

  • OpenClaw enforces boundaries via AGENTS.md documentation + pre-commit scripts (similar to Synova's check-architecture.sh)
  • Claw Code enforces boundaries via Rust compile-time type system (more reliable than scripts but requires compiled language)
  • Synova currently uses bash scripts for cross-layer violation detection -- can upgrade to tsc custom rules (ESLint no-restricted-imports)

Finding F6: The Memory Nudge vs Memory Dreaming Distinction

Two fundamentally different approaches to proactive memory management:

  • Hermes Nudge: turn-count-based, synchronous -- the agent is interrupted mid-conversation to reflect on memory. Low latency but intrusive; risks context pollution.
  • OpenClaw Dreaming: cron-based, asynchronous -- memory processing happens during idle/batch windows using a separate model instance. Zero context pollution of the main agent, but higher latency (next scheduled window).

For Synova: the Sentinel system already uses cron. The "Dreaming" approach is more natural -- periodic background analysis of diagnosis history to identify recurring organizational patterns. But the "Nudge" approach could be useful during FDE sessions: every N measurement cycles, prompt the orchestrator to check if earlier conclusions need updating.

A5.5 Implications for Synova

A5 Implications

  1. PKB (Professional Knowledge Base) design: Synova needs something between Hermes MemoryStore and OpenClaw Dreaming. An "Organizational PKB" that stores: (a) Enterprise-specific diagnosis patterns discovered during FDE sessions, (b) Sentinel-identified recurring anomalies with their resolution history, (c) Expert reasoning traces for future reference. Use OpenClaw's Dreaming pattern: cron-triggered background analysis of accumulated diagnosis history.
  2. Information decay is critical for enterprise diagnosis: organizational states change. A diagnosis pattern from 6 months ago may no longer apply. Implement explicit recency half-life (30 days suggested for organizational data) and max age (90 days).
  3. Auto-write confidence threshold: for automatically writing conclusions to the PKB, use a tiered confidence system: above 0.95 -> auto-write; 0.80-0.95 -> write with human-visible annotation; below 0.80 -> suggest but don't write.
  4. Agent Nudge for diagnosis continuity: during long FDE sessions (multiple measurement cycles), periodically nudge the orchestrator: "We have run N measurement cycles. Are any earlier conclusions contradicted by newer data?" This prevents diagnosis drift.
  5. Skills system for diagnosis workflows: successful diagnosis workflows should be captured as procedural skills. "How to diagnose cash flow issues in a 50-person SaaS company" becomes a reusable skill that new diagnosis sessions can load.
