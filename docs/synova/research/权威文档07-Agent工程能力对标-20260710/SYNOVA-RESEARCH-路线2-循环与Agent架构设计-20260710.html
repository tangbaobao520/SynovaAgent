B1. 出厂内置 Loop Engineering（5个循环）

1.1 设计总则

Synova的循环与Claw Code的OmX工作流层有本质区别：

  • Claw Code OmX：人+Agent交替。人发指令→Agent执行→人审查→Agent修正。循环由人触发，Agent是执行者。
  • Synova Loops：全自动。系统驻扎企业后自主周期性运行，无需人类每轮触发。循环由Cron/事件/数据变更驱动，用户是接收者而非操作员。

1.2 循环一：企业诊断循环（Enterprise Diagnosis Loop）

定位：Synova的最高价值循环。全企业范围的周期性诊断，回答"这家企业的增长卡在哪里？现在该做什么？"

触发条件

触发类型条件频率
Cron 定时默认每14天全量诊断一次（GA可配置7/14/30天）14天
GA 手动触发GA通过 POST /api/diagnosis/start 或 TUI 发起按需
哨兵升级触发P0级哨兵告警 + 3个以上P1告警在同一周期内聚合 → 自动触发诊断事件驱动
重大数据变更本体层关键实体（Revenue/Team/Cost）变化 >30% → 触发缩小范围诊断事件驱动

调度策略

CronScheduler (SQLite持久化) | +-- [每14天] → DiagnosisLauncher.runFullDiagnosis(teamId, scope='enterprise') | | | +-- Phase 0: 界定（结构化卡片问卷，确定诊断焦点） | +-- Phase 1: 采集（runModules() 并行执行25个测量器） | +-- Phase 2: 假设（证据池 → LLM生成3-5个假设） | +-- Phase 3: 根因（规则引擎 + 矛盾检测 + 8位专家ReAct推理） | +-- Phase 4: 报告（模板渲染 → 综合诊断报告） | +-- Phase 5: 交付（LLM行动建议 + 推送外部系统） | +-- SentinelRunner 持续运行（独立于诊断循环） | +-- P0告警 + 3xP1聚合 → 发送 EmergencySignal +-- DiagnosisOrchestrator 收到 EmergencySignal → 提前触发诊断

断裂检测

断裂场景检测方式恢复策略
LLM调用超时/失败Phase 1-5 每个LLM调用有独立timeout（60s）指数退避重试（max 3次），3次失败→该阶段降级，标记 degraded: true

用户交互模式

  • 诊断报告推送：Phase 4完成后，通过 GET /api/sentinel/reports 推送到GA工作区
  • 工单生成：Phase 5中每条P0/P1级发现自动生成 sentinel_tickets 记录，进入中层告警响应闭环

设计决策：诊断循环默认14天

7天过频（数据变化不足以产生新信号），30天过疏（可能错过窗口期）。14天是平衡点。融资/并购/重大战略调整期GA可手动触发高频诊断（最低间隔1天）。

1.3 循环二：部门导航循环（Department Navigation Loop）

定位：产品最高频的使用场景。中层每天都在用Synova——写方案、做执行、做汇报。

触发条件

触发类型条件频率
中层主动输入中层在部门工作区（GET /dept）提交方案草稿或咨询问题按需，预计3-10次/天/部门
方案执行哨兵触发方案级定制哨兵检测到偏离（实际 vs 预期 >20%）事件驱动
主动追问定时器3天/1周前中层询问过决策辅助类问题，到期自动追问定时

三个闭环子链路

  1. 方案评估闭环：中层输入方案 → Synova交叉检查（数据审计+风险扫描+机会扫描+假设压力测试）→ 评估报告 → 中层调整 → v1/v2对比 → 定稿 → 自动注册追踪哨兵 → 持续监控
  2. 日常咨询闭环：自然语言提问 → 问题分类路由（信息查询/推演/诊断/决策辅助）→ 自动调用相应能力 → 输出分析 → 3天后主动追问效果
  3. 告警响应闭环：哨兵告警 → 工单生成 → 中层处置（确认/误报/升级）→ 到期自动检查 → 误报积累≥3 → org-adapter阈值调整

断裂检测

断裂场景检测方式恢复策略
方案解析失败结构化模板匹配率 < 30%LLM fallback（temperature=0），提示中层补充关键字段
交叉检查哨兵数据缺失相关哨兵 latestResult = null触发on-demand哨兵执行，等待≤30s；仍缺失→标注"数据不足"
主动追问无响应追问发出后72h无回复静默标记，不重复追问；1周后记入AgentMemoryStore

设计决策：方案级哨兵定制阈值不污染全局哨兵

方案级哨兵的阈值（如"转化率目标5%"）与全局哨兵阈值隔离。方案执行结束后定制哨兵自动注销。

1.4 循环三：GA进化循环（GA Evolution Loop）

定位：GA（Growth Architect）作为人类审查者，审查Synova的诊断输出、调整系统参数、审批进化提案。

触发条件

触发类型条件频率
每次诊断报告生成后Phase 4完成后自动通知GA审查每14天
GA纠错GA标记某条发现为"不准确"或"不适用"按需
阈值调整提案org-adapter收集到足够证据（同类误报≥3）事件驱动
专家能力审查每30天评估各专家的准确率/置信度校准30天

调度策略（事件驱动审查链）

诊断报告生成 → GA审查界面 (routes/evolution.ts) | +-- GA标记"准确" → feedback-collector (decision: 'confirm') → confidence +0.1 +-- GA标记"不准" → feedback-collector (decision: 'reject') → | | | +-- 积累3次同类型 → org-adapter 生成阈值调整提案 | +-- GA审批通过 → 哨兵阈值上调 | +-- GA驳回 → 记录"需要更多证据"，下次重新评估 | +-- GA补充信息 → 写入 enterprise_fact → 下次诊断自动纳入

GA缺位保护

GA超过30天未审查任何报告 → 触发提醒。超过60天 → 诊断报告自动降级（confidence -0.2，标记"未经GA审查"）。

设计决策：GA审查是"建议性"而非"阻断性"

GA的审查不阻断诊断循环——如果GA不在，诊断仍会继续。与Claw Code哲学一致："人类提供方向，Claw执行劳动"——人类是方向校准者而非瓶颈。

参考来源：Claw Code PHILOSOPHY.md "Humans set direction; claws perform the labor" (D:\Git项目研究\claw-code-main\PHILOSOPHY.md)；Synova GA纠错管道 (src/l3/assumption-monitor.ts)

1.5 循环四：系统自检循环（System Self-Check Loop）

定位：运维级自检——Synova自身的健康监控。不是决策质量的检查（那是E3），而是"系统是否正常运行"。

检查项

检查项频率检测方式告警阈值
LLM Provider可用性每5分钟Health check ping（最小prompt，< 10 tokens）连续3次失败→切换备用Provider
GraphStore连接每5分钟SELECT 1 query失败→立即告警
哨兵执行成功率每小时统计最近1小时内 check() 成功率成功率 < 80% → 告警
Token预算监控每天对比每日token消耗 vs 预算上限日消耗 > 80%预算 → 警告；> 95% → 自动降级至轻量模型
诊断报告队列积压每小时未审查报告数量> 5份 → 提醒GA
证据池新鲜度每天最新证据时间戳> 7天无新证据 → 警告数据管道断裂

系统自检循环不依赖LLM——纯规则+SQL查询。LLM Provider切换通过Provider Gateway（providers/）实现。

设计决策：自检循环独立于诊断循环运行

自检循环有自己的Cron调度表，不和诊断循环共享执行线程。自检失败不影响诊断循环——使用last-known-good配置继续尝试。遵循Claw Code "模块化、独立降级"的原则。

参考来源：Claw Code concept.md "Модульность — общий api" (D:\Git项目研究\claw-code-main\concept.md)；Synova Provider Gateway (providers/)

1.6 循环五：知识积累循环（Knowledge Accumulation Loop）

定位：从每次诊断中提取可复用的模式，构建企业的"组织知识库"。

触发条件

触发类型条件频率
每次诊断完成Phase 4报告生成后，KnowledgeCurator自动提取模式每次诊断后
GA纠错后GA的纠错数据作为高权重学习信号事件驱动
NCI信号生命周期结算信号进入adopted/abandoned终态时提取教训事件驱动
定期知识压缩每30天将碎片化知识压缩为结构化enterprise_fact30天

三层沉淀策略

L1 即时层: session-learner（单次会话内学习） | L2 模式层: KnowledgeCurator（跨诊断提取通用模式）→ 验证：跨3次以上诊断验证稳定性 | L3 持久层: enterprise_fact（永久写入本体层）→ 下次诊断自动注入Expert system prompt

断裂检测

连续3次诊断未提取出任何新知识 → 触发KnowledgeCurator审计。enterprise_fact表30天无新增 → 告警。

设计决策：三层独立运行和降级

L1失败不影响L2，L2失败不影响L3。知识积累是"增值"而非"必需"——诊断循环不依赖知识库即可运行。

参考来源：Synova KnowledgeAgent (src/l3/knowledge-agent.ts)；SessionLearner (packages/engine-core/src/pipeline/diagnosis/session-learner.ts)

B2. 主Agent + 子专家架构

2.1 当前架构与目标架构的差距

当前状态：DiagnosisOrchestrator 通过 ExpertSubAgentExecutor 将8位专家作为独立LLM调用并行执行（Promise.all），各自有独立System Prompt、证据子集、工具白名单。专家报告由 Synthesizer 合成。这是"编排器 + 并行专家调用"，不是真正的"主Agent + 子Agent"架构。

目标状态：L2升级为主Agent——具备任务分解、动态专家路由、交叉验证触发、冲突仲裁、收敛合成的完整决策闭环。

2.2 主Agent的任务分解协议

任务类型需要的专家执行模式示例
全企业诊断8位全部并行，Synthesizer合成每14天定期诊断
部门级诊断3-4位（根据维度自动选择）串行（先财务→再战略→最后合成）市场部Q3投放计划评估
单一维度深度分析1-2位（主+辅助验证）串行（主ReAct→辅助验证）"为什么成本结构恶化？"
哨兵告警响应根据信号路由表预定义映射并行（信号相关专家同步推理）现金流告警→finance+strategy
反事实推演finance+strategy+business_model串行（财务→战略→商业模式验证）"如果预算削减20%会怎样？"

设计决策：任务分解由规则优先，LLM仅处理10%模糊场景

当前SentinelRunner已有信号路由表（signal-aggregator.ts），定义了 sentinelId → experts 的确定性映射。主Agent遵循同样原则：TaskDecompositionTable 覆盖90%场景，只有task type不在表中+dimensions无法确定时才丢给LLM。

参考来源：Synova SignalRoute表 (src/sentinel/signal-aggregator.ts)；信号路由规则 (src/sentinel/runner.ts:29-70)

2.3 专家路由算法

单一专家 vs 多专家协作的决策逻辑

条件路由决策理由
问题仅涉及单一维度（纯财务）单一专家减少token消耗和推理噪音
问题跨2+维度2+专家并行不同维度需要不同领域知识
某专家置信度 < 0.5自动触发辅助专家低置信度说明信息不足
evidencePool证据 >20条单一专家证据本身已足够
evidencePool证据 <5条≥2位专家并行数据稀疏时多角度交叉验证

路由算法（规则优先 + 证据驱动）

function routeExperts(task, evidencePool):
  // Step 1: 规则路由（90%场景）
  ruleResult = TASK_EXPERT_MAP[task.type]
  if ruleResult → return ruleResult

  // Step 2: 证据驱动的动态路由
  dims = extractDimensions(task)
  primary = DIMENSION_EXPERT_MAP[dims[0]]

  // Step 3: 证据稀疏检查
  dimEvidence = evidencePool.filter(e => e.dimension === dims[0])
  if dimEvidence.length < 5:
    return { experts: [primary, getAuxiliaryExpert(dims[0])], mode: 'parallel' }

  // Step 4: 跨维度 → 多专家
  if dims.length >= 2:
    return { experts: [...new Set(dims.map(d => DIMENSION_EXPERT_MAP[d]))], mode: 'parallel' }

  return { experts: [primary], mode: 'single' }

设计决策：路由的"三层fallback"

① TaskDecompositionTable（确定性映射）→ ② 维度→专家映射表 → ③ LLM推理（仅前两层全部未命中）。确保路由可预测、可审计，与Claw Code "显式限制、可审计性"原则一致。

参考来源：Claw Code concept.md "Явные лимиты — сбои предсказуемы" (D:\Git项目研究\claw-code-main\concept.md)

2.4 推理成本预算与动态路由（B2新增）

当前Synova没有明确的推理成本预算机制——每次诊断调用全部8位专家，不分轻重。以下为新增设计。

模型分层策略

层级模型适用场景预估Token
LightDeepSeek-V3-Lite / GPT-4o-mini哨兵信号分类、问题分类路由、简单信息查询、IM消息NCI分类~500 tokens/次
StandardDeepSeek-V3日常诊断、部门方案评估、日常咨询回答、知识提取~2,000 tokens/次
DeepDeepSeek-R1 / o3-mini全企业诊断Phase 2-3、跨维度矛盾仲裁、反事实推演、NCI三级计算~10,000 tokens/次

升级/降级条件

条件动作
Light层分类置信度 < 0.6升级到Standard层重新分类
Standard层诊断发现高严重度矛盾（≥2专家冲突）该矛盾升级到Deep层进行深度推理
Deep层返回置信度 < 0.4标记"超出当前能力"，建议人工审查

月度预算模型（5-1000人企业）

企业规模月Token预算预估月成本（DeepSeek）预估月成本（OpenAI）
5-20人500K~$3-5~$30-50

设计决策：成本预算与诊断质量之间的"弹性降级"

预算紧张时，全企业诊断自动从Deep降到Standard层（在Phase 2-3保持Standard，Phase 0/1/4/5使用Light），而非直接砍掉诊断。这确保"永远有诊断，只是深度不同"。

参考来源：成本模型借鉴Anthropic工程实践中的"资源约束下的弹性降级"模式。Synova现有Provider Gateway已支持多模型切换。

2.5 交叉验证触发条件

当前Synthesizer已有跨专家矛盾检测（crossExpertContradictions），但触发是被动的——所有专家并行跑完后才检测。真正的"交叉验证"需要在诊断过程中动态触发：

触发条件动作输出
单专家置信度在0.4-0.6之间（模糊地带）自动触发第二位专家独立推理同一维度对比两份报告，标注一致点/分歧点
两位专家在同一维度给出方向相反的结论触发冲突仲裁流程（见2.6）仲裁报告 + 置信度调整
某专家标记crossReference（建议其他专家review）被引用的专家追加一轮推理追加报告并入合成
evidencePool中该维度证据>10条但结论高度分散触发第三位专家独立推理三份报告投票或中位数合成

设计决策：交叉验证不是"多跑几次"——它有明确的经济成本

每增加一位交叉验证专家，成本翻倍。因此交叉验证只在"模糊地带"触发——置信度过低或矛盾已显性化时。明确区分"需要更多数据"（触发补充采集）和"需要更多推理"（触发交叉验证）。

参考来源：Synova Synthesizer crossExpertContradictions (packages/engine-core/src/pipeline/diagnosis/synthesizer.ts:30-65)；QualityFirewall 四道检验 (src/l3/quality-firewall.ts)

2.6 冲突仲裁规则

当两位专家给出冲突建议时，仲裁不只是"选置信度高的那个"——需要结构化的收敛逻辑。

仲裁决策树

专家A vs 专家B 冲突 | +-- 两位置信度差距 >0.3? | YES → 置信度高的胜出，但标注冲突（供GA审查） | NO → 进入证据仲裁 | +-- 证据仲裁：谁的evidenceRefs更多且证据更新鲜？ | | | +-- A的证据数量 > B的证据数量*2 → A胜出 | +-- B的证据数量 > A的证据数量*2 → B胜出 | +-- 证据量接近 → 进入领域仲裁 | +-- 领域仲裁：维度归属哪个专家的核心领域？ | finance维度 → financial_analyst 权重 x1.5 | strategy维度 → strategic_analyst 权重 x1.5 | 以此类推... | +-- 如果仍无法裁决 → 触发第三位专家（与两位冲突专家不同领域）仲裁 | +-- 最终结论：标注"多方存在分歧"，列出A/B/C观点，建议GA人工裁决

冲突记录与学习

每次冲突仲裁结果写入 conflict_resolution_log 表。当GA介入裁决后，GA的判断作为正确答案。如果某类冲突反复出现（同维度、同专家对），KnowledgeCurator提取为"已知难题"模式，下次自动应用上次GA裁决的规则。

设计决策：仲裁永不自动"吞噬"分歧——分歧被保留但降噪

与Claw Code OmO的"Architect/Executor/Reviewer disagreement resolution"类似，Synova的仲裁不是消除分歧，而是将分歧结构化为GA可审查的格式。分歧本身是有价值的诊断信号——"专家们为什么在这个问题上达不成共识？"可能揭示更深层的企业问题。

参考来源：Claw Code PHILOSOPHY.md "When Architect, Executor, and Reviewer disagree, OmO provides the structure for that loop to converge" (D:\Git项目研究\claw-code-main\PHILOSOPHY.md)

2.7 收敛机制

当前Synthesizer将6份ExpertReport合成为SynthesisReport，包含：crossExpertContradictions、crossDimensionLinks、expertContributions、LLM合成假设。收敛机制在此基础上增强：

收敛算法

  1. 共识发现：3+位专家在同一维度上的finding statement语义相似度 > 0.7 → 标记为"高共识发现"，confidence取中位数
  2. 差异量化：对每个维度计算专家间的finding confidence方差。方差 > 0.3 → 标记"高分歧维度"
  3. 权重合成：每位专家的contribution weight不是均等的——基于GA历史审查的准确率动态调整（见E2）
  4. LLM最终合成：Synthesizer将上述结构数据+原始报告+证据池输入LLM，生成综合诊断叙述。LLM被要求：优先呈现高共识发现，对高分歧维度标注置信度范围而非单点值，明确说明"这个结论基于哪些证据、哪些是专家推断"

设计决策：Synthesizer的LLM输入不是原始报告全文——是结构化摘要

当前Synthesizer已经做了这一步（buildSynthesisPrompt提取关键字段）。进一步增强：structured summary包含"各专家在该维度的finding对比矩阵"，让LLM从"6篇报告"的阅读变成"1张矩阵表"的阅读，降低LLM遗漏和幻觉。

参考来源：Synova Synthesizer buildSynthesisPrompt (packages/engine-core/src/pipeline/diagnosis/synthesizer.ts:70-120)

B3. NCI Agent自主调度

3.1 NCI三层管道回顾

NCI（Non-Consensus Identification，非共识检测）是一个独立于哨兵体系的三层递进管道：

  1. Phase 0 — 信号捕捉：Signal实体+IM管道+文档管道。捕捉企业内部非结构化信号（IM消息/会议纪要/GA对话/一线反馈）
  2. Phase 1 — 沉默检测：信号生命周期追踪。检测被提出后从未被讨论的信号、被系统压制的信号、僵尸信号（讨论多但零行动）
  3. Phase 2 — NCI计算：三条件验证。认知偏离度 + 成本断裂度 + 价值网络错配度 → NCI综合得分

3.2 沉默扫描的周期策略

扫描类型频率扫描范围触发条件
信号生命周期更新每天所有lifecycle_stage非终态的Signal节点Cron定时（每天凌晨）
沉默检测每周创建>90天且未被任何正式流程引用的SignalCron定时（每周一）
僵尸信号检测每周reference_count>5 且 resource_allocation_delta=0的Signal与沉默检测同批执行
系统性盲区检测每月同类型信号12个月内≥3次被沉默每月1号
事件触发的即时扫描按需IM新消息到达时实时分类 → 如果是非共识信号立即写入事件驱动（IM webhook）

设计决策：信号采集（Phase 0）与沉默检测（Phase 1）异步解耦

IM消息到达时只做轻量分类（<500 tokens），不阻塞消息响应。Signal写入后立即返回。生命周期追踪和沉默检测在独立的Cron任务中执行——确保IM体验不受NCI处理延迟影响。

参考来源：NCI技术开发文档 Phase 0-1 架构 (docs/synova/research/nci/SYNOVA-IMPL-NCI技术开发文档-v1-20260705.md)

3.3 STM_Index的阈值监控

STM_Index（Silence-Through-Muting Index，沉默压制指数）量化组织对非共识信号的压制程度：

STM_Index计算公式

STM_Index = (S_silenced / S_total) * w1 + (S_zombie / S_total) * w2 + BlindSpot_Bonus

其中：
  S_silenced = lifecycle='silenced'的信号数
  S_zombie = lifecycle='zombie'的信号数
  S_total = 所有非终态信号数
  w1 = 0.6（沉默权重）
  w2 = 0.4（僵尸权重，僵尸比纯沉默更严重——说明组织在讨论但不行
动）
  BlindSpot_Bonus = 有系统性盲区警报时 +0.2

阈值与响应

STM_Index级别动作
< 0.15正常无动作
0.15-0.30注意在下次诊断报告"组织健康"板块提及
0.30-0.50警告生成专项报告推送GA；触发org_diagnostician专家深度分析组织免疫系统
> 0.50严重紧急通知GA+企业负责人；标记为P0级组织风险；自动纳入下次FDE诊断的焦点维度

3.4 第一性原理断层扫描的触发条件

"第一性原理断层扫描"是NCI Phase 2的核心——检查主流共识与物理现实之间是否存在结构性脱节。

触发条件（满足任一即触发）

  1. STM_Index > 0.30：沉默压制达到警告级别时，说明可能有系统性的"视而不见"
  2. GA手动触发：GA在审查界面发起"断层扫描"
  3. 定期扫描：每季度自动执行一次全企业断层扫描
  4. 资源分配异常：当CUMULATIVE_LEARNING边检测到某方向的学习速率显著高于当前主攻方向（>2x），但资源分配仍集中在旧方向 → 触发

断层扫描执行流程

触发 → 收集当前企业资源配置数据（销售投入分布/研发预算分布/新业务尝试记录） → 计算认知偏离度：企业行为显示的"共识" vs 基于新技术的物理极限 → 计算成本断裂度：新路线的成本函数是否出现架构级跃迁 → 计算价值网络错配度：是否存在旧系统中的"垃圾"在新系统中是"核心资产" → 三项得分乘积 → NCI综合得分（0-100） → 得分 ≥ 70 → 生成"非共识机会报告"，推送GA → 得分 40-69 → 标记"待观察"，纳入知识积累循环跟踪 → 得分 < 40 → 不报告（避免噪音）

设计决策：NCI不预测"下一个拼多多"，它检测"你的组织在压制什么"

NCI的诚实边界在方案中已明确：不适用于"全新型"非共识（没有任何历史数据的方向）。NCI能做的是：识别企业内部被过滤的信号，计算这些信号和物理现实的结构性差距，输出"你的组织正在过滤掉一个至少值得认真讨论的可能"。

参考来源：NCI非共识检测工程化方案 背景说明 (docs/synova/research/nci/SYNOVA-IMPL-NCI非共识检测工程化方案-v1-20260704.md)

E2. 自我进化与自我修复

4.1 定义区分

运维自检（循环四）："系统是否正常运行？"——LLM在线吗？数据库连得上吗？哨兵在跑吗？

决策质量自检（E2+E3）："系统做出的诊断是正确的吗？"——上次说成本结构有问题，3个月后回头看，成本真的恶化了吗？

4.2 错误根因分类

当Synova做出错误决策（诊断不准确/建议不当），错误被归入以下类别：

错误类别定义示例修正策略
数据不足型证据池数据量或质量不足以支撑判断哨兵数据3个月未更新，诊断基于过期数据标记证据源为不可靠，触发数据管道修复

4.3 决策逻辑修正流程

错误发现（GA纠错 / 3个月后的业务结果与诊断结论不一致） | v 根因分类（自动：规则匹配；模糊场景：LLM辅助） | v 修正方案生成： |-- 数据不足型 → 标记证据源 + 触发补充采集 |-- 规则过时型 → org-adapter 生成阈值调整提案 |-- 专家偏差型 → 调整专家权重（expertContributions.weight） |-- 合成失误型 → 增强Synthesizer的冲突处理逻辑 |-- 领域盲区型 → 标记 + 知识库扩展提案 |-- 本体滞后型 → 本体审查提案 | v GA审批（或自动审批：数据不足型和本体滞后型可自动执行，规则过时型/专家偏差型需GA审批） | v 修正应用 + 验证： |-- 修正后的下次诊断是否在相同维度产出不同结论？ |-- 新结论是否与后来验证的业务结果一致？ |-- 不一致 → 回退修正，保留原配置，升级为"复杂问题"等待GA深度审查

4.4 修正失败回退

回退场景触发条件回退动作
阈值调整反向恶化调整后5次哨兵检测中≥3次误报率反而上升回滚到调整前阈值，标记该调整规则为"禁止自动应用"，等待GA手动配置
专家权重调整后诊断质量下降连续2次诊断GA审查通过率低于调整前水平回滚权重，标记该专家为"权重不稳定"，归档该案例供KnowledgeCurator分析

设计决策：修正策略的"自动审批分级"

不是所有修正都需要GA审批。数据修复和本体更新可以自动执行（因为这些是客观数据问题，不是判断标准问题）。但阈值调整和专家权重调整涉及诊断的"判断标准"——这些必须经GA批准。区分"事实层修正"（自动）和"标准层修正"（需审批），避免系统在无人监督下修改自己的判断标准。

E3. 决策质量自检循环

5.1 两层自检架构

层次检查什么频率检测方式

5.2 决策质量评估的两个数据源

数据源一：GA反馈闭环

GA在审查界面逐条标记诊断发现的准确度（准确/不准确/部分准确），数据写入 feedback-collector。统计指标：

  • 诊断准确率：该周期内GA标记"准确"的finding / 总finding数
  • 严重误报率：P0/P1级发现中GA标记"不准确"的比例
  • 专家个人准确率：按专家维度统计准确率 → 输入到E2的专家权重调整

数据源二：诊断结论与业务结果一致性

这是更客观的验证——不依赖GA的主观判断，而是用3个月后的实际业务数据来验证3个月前诊断的准确性：

诊断结论（T日） 实际业务结果（T+90日） ───────────────────────────────────────────────── "现金流将在3个月内出现危机" vs 90天后现金流实际下降 > 20% → 预测准确 "某部门存在关键人风险" vs 90天后该部门核心人员离职 → 预测准确 "市场定位模糊，需调整" vs 90天后市场份额变化 → 难以直接验证（需GA判断） "成本结构恶化" vs 90天后毛利率变化 → 可量化验证

可量化验证 vs 需GA判断

诊断发现类型验证方式验证周期
财务预测类（现金流/成本/收入）哨兵实际数据对比，自动计算偏差率30-90天
组织风险类（关键人/人才密度）人员变动数据 + 组织结构变更记录90-180天
战略诊断类（市场定位/竞争优势）需GA判断 + 市场份额/竞争格局变化数据辅助180-365天
文化诊断类（信息扭曲/权力僵化）主要依赖GA判断 + NCI信号模式变化辅助180-365天

整体质量持续下降（连续2个季度）综合质量分下降 > 20%触发"系统健康危机"警报——通知GA系统可能需要重大调整（本体更新/模型升级/阈值重构）

设计决策：区分"可自动验证"和"需人类判断"的预测

财务预测（现金流、成本、收入等量化指标）可以用后续哨兵数据自动验证。但战略诊断（"你的市场定位模糊"）3个月后难以用纯数据判断——市场份额变化可能有多种原因。因此决策质量自检不是全自动的——它区分可自动验证的预测（约40%的发现）和需GA判断的预测（约60%）。自动验证结果为GA提供客观锚点，但不替代GA的判断。

参考来源：GA进化循环设计（§1.4）；E2错误根因分类中的"数据不足型"和"规则过时型"均已纳入验证范围

6.3 主Agent在此拓扑中的位置

主Agent（升级后的DiagnosisOrchestrator）不是"一个循环"——它是跨越多个循环的决策中枢：

  • 在企业诊断循环中：主Agent执行完整6阶段诊断流程，调度8位子专家
  • 在部门导航循环中：主Agent的问题分类路由器接收中层输入，按需调度子专家
  • 在NCI调度中：主Agent的哨兵信号聚合引擎消费NCI沉默警报，决定何时触发专家分析
  • 在冲突仲裁中：主Agent执行跨专家矛盾检测和仲裁（见B2.6）
  • 在GA进化中：主Agent接收GA纠错，通过E2修正流程调整自身行为

设计决策：主Agent = 跨越循环的"元调度器"

这借鉴了Claw Code的OmO多Agent协调设计——OmO提供的是"跨Agent的planning、handoffs、disagreement resolution、verification loops"。Synova的主Agent承担类似的角色：它不是8位专家之一，而是"决定何时激活哪些专家、如何组合他们、如何解决他们的分歧"的元层。主Agent不做具体领域推理——那是子专家的职责。

6.5 关键架构原则总结

  1. 循环独立降级：每个循环有自己的Cron/事件触发器、自己的try/catch、自己的degraded标记。循环之间通过共享证据池松散耦合，不通过直接函数调用强耦合。
  2. 规则优先于LLM：路由、分类、阈值判断优先用预定义规则。LLM仅在模糊场景（约10%）介入。符合AGENTS.md铁律精神和Claw Code的"显式限制、可审计性"。
  3. 人类是方向校准者：GA进化循环保持人类对系统判断标准的最终控制。自动修正限于"事实层"（数据修复）——"标准层"（阈值/权重）必须经GA审批。
  4. 通知是结果、不是交互：推送是单向的结果通知，用户去工作区查看详情。与Claw Code "notification routing pushed out of the agent context window"理念一致。
  5. 五循环 + 三自检 = 出厂内置：这些循环不是"可选功能"——是企业部署Synova后立刻开始运行的出厂行为。GA可以调整频率但不能关闭核心循环（企业诊断+系统自检）。
