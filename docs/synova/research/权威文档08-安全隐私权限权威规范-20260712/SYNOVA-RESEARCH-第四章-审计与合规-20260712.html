4.1 审计哈希链

来源：权限研究-技术实现方案-20260707.md（审计哈希链设计）

字段说明
audit_idUUID。每条审计记录的唯一标识
operationSOI ID（如SOI-01 graph.traverse）
operator操作者(role+userId)，来源：auth.ts JWT提取的sub+role
tenant_id操作所在租户。来源：JWT的orgId字段(auth.ts L27)
timestampUTC时间戳。操作发生的精确时间
prev_hash前一条审计记录的SHA-256哈希。形成不可篡改链
current_hash本记录的SHA-256哈希 = SHA256(operation+operator+tenant_id+timestamp+prev_hash+data_snapshot)

4.2 外部完整性担保机制

审计哈希链的"不可篡改"能力依赖于物理存储。如果审计日志和业务数据在同一数据库，数据库被攻破则哈希链也无效。

外部完整性担保：每隔1小时，将当前哈希链的Root Hash发布到外部不可变存储（如AWS S3 Object Lock开启合规模式/阿里云OSS合规保留策略/公开区块链）。即使数据中心的全部数据库被攻破，Root Hash的历史记录在外部不可变存储中仍可验证。任何篡改尝试都因Root Hash不匹配而暴露。
实现：➕需新建RootHashPublisher模块——定时(每小时)计算当前链的Root Hash→签名→发布到外部不可变存储→记录发布交易的ID作为额外的审计证据。

4.3 GDPR/PIPL权利实现

来源：P7(可携带+可删除) + P8(传染性删除) + 技术实现方案的DataExporter/DataPurger接口

4.3.1 DataExporter — 可携带权 (Art.20)

DataExporter.export(tenantId) → {archive: Buffer, manifest: JSON}
查询该租户的全部数据(GraphStore节点+边+SessionStore会话+AgentMemory记忆)→打包为结构化JSON→加密(ZIP+AES-256)→生成manifest(数据清单+导出时间+数据指纹)。
导出隔离验证：确保导出的每一条数据都携带tenant_id={请求的tenantId}，无跨租户泄露。
状态：➕需新建。当前无实现。

4.3.2 DataPurger — 被遗忘权 (Art.17) + 传染性删除

DataPurger.purge(tenantId) → {stages: PurgeStage[]}
阶段1(SafetyLock)：立即可用——将该租户标记为"待删除"状态，禁用该租户的访问，暂停所有哨兵。
阶段2(WaitingPeriod)：7天冷静期——期间该租户的数据不可访问但可恢复。等待数据导出完成。
阶段3(CascadeDelete)：传染性删除——删除源数据(GraphStore节点+边)→删除派生数据(SessionStore会话+诊断报告)→删除哨兵结论(SentinelFinding)→删除知识库引用(KnowledgeStore中该租户的匿名化数据引用)。
阶段4(Verification)：验证删除——检查该租户在所有存储引擎中的残留数据→生成删除证明报告。
状态：➕需新建。传染性删除的逻辑是当前系统完全缺失的能力(P8的数据血缘追踪)。
