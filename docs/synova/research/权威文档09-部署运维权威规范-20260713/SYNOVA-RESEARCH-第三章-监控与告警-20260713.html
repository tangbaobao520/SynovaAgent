第三章：监控与告警

独立看门狗 | 自愈边界+死亡循环防护 | 三层监控 | 系统健康审计 | healthz | Linux降级 | 2026-07-13

3.1 独立看门狗进程

最大的监控盲区就是Agent自身。当Agent进程僵死或断网时，它依赖自身的消息通道去发送告警，这本身就是悖论。看门狗是"谁能给诊断师看病"的唯一答案。
维度规范
运行方式独立于主Agent的极简进程（<500行，零外部依赖）。注册为OS服务（Windows Service/macOS LaunchAgent/Linux systemd user unit）
探测逻辑每5分钟探测 GET /api/healthz（超时10s）。连续3次无响应或返回非200→触发告警
告警方式Windows: Toast通知。macOS: Notification Center。Linux: 降级为stdout+写入~/.synova/logs/watchdog.log；可配置暴露告警端点供Nagios/Zabbix轮询
重启尝试告警后尝试重启主进程（执行启动脚本）。记录重启次数

3.1.1 自愈边界与死亡循环防护

如果导致主进程崩溃的是持久化错误（数据库损坏/配置语法错误），重启会陷入"启动→加载损坏文件→崩溃→被重启"的死亡循环。
退避策略：短时间（10分钟内）连续重启失败≥3次→立即停止重启→触发最终告警（OS原生通知+写入watchdog.log）→在通知中指明问题路径："系统连续3次启动失败。最后一次错误日志：/data/logs/crash-{timestamp}.log。可能需要人工介入恢复。请运行恢复包或联系GA。"
看门狗不应尝试自动修复损坏的数据库或配置文件——这超出它的能力范围。它应清晰地向用户报告"我已无法自愈，需要人工介入"。

3.2 三层监控体系

层级指标采集方式告警阈值
L1 基础设施磁盘使用率/CPU占用/内存占用/进程存活/看门狗心跳OS API + metrics.ts Gauge磁盘>90%→P1告警。看门狗3次无响应→P0告警
L2 应用层哨兵心跳(上次扫描时间)/LLM延迟(p50/p95)/SQLite慢查询(>100ms)/Token消耗/API可用率metrics.ts Counter+Gauge + healthz端点哨兵24h未扫描→P1。LLM p95>5s→P2。Token日消耗>预算120%→P1
L3 业务层诊断质量退化(连续2周期下降)/哨兵误报率/GPI异常波动(周波动>2σ)哨兵准确率统计+GPI计算P0哨兵准确率<60%→暂停推送。GPI波动>3σ→P1

3.3 健康检查端点 GET /api/healthz

检查项判定失败影响
databaseSQLite PRAGMA integrity_check通过整个系统不可用
llm_connectivity最近1小时内至少1次LLM调用成功诊断不可用，哨兵可运行
last_sentinel_run最近24小时内至少1个哨兵执行成功哨兵可能中断
disk_free_gb剩余空间>1GB备份和写入可能失败
data_freshness最近7天内有新数据接入诊断基于过时数据
watchdog_alive看门狗最近5分钟内探测成功系统监控失效

所有检查项独立status，单点故障不影响整体健康状态。返回格式：{"status":"degraded","checks":{"database":"ok","llm_connectivity":"ok","last_sentinel_run":"ok","disk_free_gb":"ok","data_freshness":"stale_14d","watchdog_alive":"ok"}}

3.4 告警升级规则

级别条件通道时效
P0 生存威胁哨兵关键告警/数据源中断/看门狗3次失败/磁盘满托盘通知+企业管理员+GA即时（<5分钟）
P1 效率问题性能退化/哨兵误报率上升/备份延迟/非P0哨兵24h未扫描GA通知（汇总）30分钟内
P2 趋势变化GPI波动/Token消耗超预算/数据量异常周报汇总周报中呈现

3.5 系统健康审计章节

在每次诊断报告中强制增加一章——"系统健康审计"。向老板客观汇报Agent工作状态：过去30天可用率、上次备份时间及结果、数据延迟次数、活跃哨兵数量（共50个中几个在产出Finding）、看门狗重启次数、Agent当前版本号、累计诊断次数。
解决"乌比冈湖效应"——让老板用数据判断"数字员工有没有在偷懒"。数据来自日志，不来自用户感知。
