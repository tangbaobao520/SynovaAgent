# 增长导航系统工程规范 — 研究方案 v2.0

> Synova 第13份权威文档 | 2026-07-14

## 零、为什么诊断之后必须有导航

前12份权威文档构建了从原始数据到诊断报告的完整工程体系。42条因果边可计算、50个哨兵可部署、8位专家可调度、Skill/Tool可按Playbook编排。诊断报告输出"固定成本刚性导致经营杠杆过高，建议推进变动成本化"。

**然后呢？**

Agent工程能力对标中（权威文档07，2026-07-10），P0差距第一条就是"自主性闭环——缺Action闭环"。差距评估表明确标注：Synova当前"哨兵→专家→建议"链路完整，但Action闭环完全缺失。

这不是交互设计问题。是工程系统的缺失。诊断产出了可行动的洞察，但没有系统把这些洞察转化为中层可执行的Goal、追踪执行过程、检测偏离、触发调整。

增长导航系统就是这个Action闭环的工程承载。

## 一、产品定位：为什么这是核心竞争力和高频心脏

### 1.1 两个使用频率的对比

| | 诊断循环 | 导航循环 |
|---|---------|---------|
| 频率 | 每月一次（甚至每季度/每半年） | **每天3-10次/部门** |
| 使用者 | 老板 + GA | **中层负责人** |
| 触发方式 | 哨兵定时 + GA手动 | 中层主动输入方案/提问 + 系统主动推送偏离告警 |
| 输出 | 综合诊断报告（30-60页） | 方案评估报告 + Goal状态 + 告警列表 |
| Token消耗 | 大（全量42边+8专家） | 小（轻量级1专家+3-5边） |

**诊断是低频的深度检查，导航是高频的日常工作流。**

### 1.2 增长导航要解决的核心用户痛点

1. "诊断报告给了三条建议，我不知道先做哪条。" → 三选一确认机制
2. "方案做完了，3个月后回头看，和当初说的完全不一样，但中间没人提醒我。" → 方案级哨兵持续追踪
3. "数据告诉我目标偏差了，但我不知道为什么。" → 证据链追溯 + 已排除混淆因素
4. "每天收到一堆系统推送，我全忽略了。" → 免打扰模式 + 智能告警频率控制
5. "我想知道这个建议执行后到底有没有用。" → 闭环验证机制

### 1.3 竞争壁垒的本质

Palantir可以增加一个盈亏平衡计算功能，零一万物可以训练一个财务诊断模型。但没有任何一个竞争对手可以在短时间内构建一套覆盖七部门的"诊断→建议→Goal→执行追踪→偏离告警→调整→闭环验证"的完整增长导航系统。因为这不只是技术能力——是工程体系+产品哲学+领域知识的深度融合。

## 二、研究目标

以"中层负责人每天打开部门工作台，3秒内知道自己最该做什么"为交付标准。

回答5个核心问题：
1. **Goal是什么？** — 诊断建议的工程化表达（数据结构+生命周期+度量绑定+依赖管理）
2. **Proposal是什么？** — 多路径选择机制（三选一+超时+变更+拒绝+压力测试）
3. **方案级哨兵如何工作？** — 偏离检测三因子模型+基线建立+成本控制+离线适应
4. **中层看到什么？** — 工作台数据模型+数据源映射+nextAction+免打扰+证据链追溯
5. **导航如何与主Agent集成？** — 轻量级再诊断+升级全量诊断+学习循环回流+闭环验证

## 三、第一性原理：导航循环的6个介入节点

不是"用户需要什么功能"，而是**一个目标从设定到完成的自然过程中，系统在哪些节点必须介入**。

### 节点1：目标设定（诊断→Goal）
诊断报告中的actionRecommendations转化为可度量、可分配、有时限的Goal。不是每条建议都自动转——系统判断"这条建议是否具备执行条件"。

### 节点2：路径选择（Proposal→三选一）
同一个根因问题往往有多条解决路径。中层需要看到选项、风险、代价，然后做出选择。但中层可能不选（超时）、可能选后反悔（变更）、可能都不认可（拒绝）。

### 节点3：执行追踪（Goal→方案级哨兵）
Goal进入执行后自动注册方案级哨兵（每个Goal最多1个），基线建立期2-4周（只采集不告警），之后启动三因子偏离检测。

### 节点4：偏离检测（偏差→告警）
三因子模型（阈值偏离+趋势偏离+基线偏离）。单因子→仅记录；双因子→告警。P2→周汇总，P1→周推1次，P0→即推+触发轻量级再诊断。

### 节点5：方案调整（偏离→轻量级再诊断）
轻量级再诊断（1位专家+3-5条边+5分钟超时）。同一Goal触达3次→自动升级全量诊断。

### 节点6：目标关闭（完成→闭环验证）
Goal关闭时关联诊断指标再检查。改善→正向案例；未改善→"已完成但无效"→执行有效性审查。

## 四、研究任务（5章）

**第一章：Goal工程规范**
- 28字段TypeScript接口 + 7态状态机（17条状态转换）
- manifest.json格式（对标哨兵manifest）
- successCriteria/metrics/measurement/dependsOn/conflictsWith全字段
- 闭环验证机制 + 级联依赖 + 冲突检测
- Playbook输出(StandardExpertReport)→Goal字段映射

**第二章：Proposal与三选一确认机制**
- 11态状态机：draft→pending_selection→selected→pending_ga_confirmation→confirmed→executing→completed + expired/disputed/regenerating/ga_rejected
- 非理想路径：超时（5工作日自动选默认）、变更（最多2次→GA介入）、遗忘（7天无信号→提醒→再过7天→通知GA）、中层拒绝（附理由→轻量级再诊断→重新选择→持续→GA裁决）
- 假设压力测试4项：数据审计/风险扫描/机会扫描/假设压力测试（每项含具体Tool/评分/输出格式）

**第三章：方案级哨兵系统**
- 偏离检测三因子模型（阈值/趋势/基线 × any_two告警规则）
- 基线建立等待期（2-4周，只采集不告警）
- 生命周期：注册→基线→活跃→Goal关闭→30天归档→60天物理删除
- 成本控制：每Goal最多1哨兵、每企业最多5活跃Goal
- 离线适应：数据源健康检查前置→中断标记degraded→超20%周期降置信度→恢复后回填
- 告警升级：P2→周汇总/P1→周推1次/P0→即推+轻量级再诊断

**第四章：中层工作台数据模型**
- DepartmentWorkspace完整TypeScript接口（activeGoals/recentAlerts/pendingProposals/diagnosticsReferenced/nextAction）
- 数据源映射表——每个字段精确到42边参数/compute contractId/哨兵ID/GraphStore节点类型+更新频率+降级策略
- nextAction生成规则（基于偏离状态/优先级/截止日期的决策树）
- 免打扰规则引擎（P0/P1/P2频率矩阵+用户自定义+融合规则+屏蔽历史）
- 证据链弹窗（偏差值→最近3条哨兵Finding→已排除混淆因素→原始诊断引用）

**第五章：与主Agent和Skill/Tool体系集成**
- 导航循环在主Agent(L2)中的5循环架构位置
- 诊断报告→Proposal→Goal的字段级映射+触发时机+筛选规则
- 轻量级再诊断完整工程边界（1专家+3-5边+5分钟+GoalAdjustmentProposal）
- 轻量级→全量升级协议（3次触发+超周期偏离→自动升级→可推翻最初诊断）
- 导航→学习循环的回流接口（Goal关闭→知识条目→PKB→跨企业聚合）
- 与哨兵/Skill/PolicyEngine(D38)的具体集成API
- 代码改动清单（修改7+新增7）

## 六、关键设计原则

1. **不增加中层负担。** 显式反馈一键操作。隐式反馈自动运行。沉默反馈追问频率保守。
2. **数据源绑定必须有身份。** 不是"从哨兵获取"，是"从sentinel-{id}的latestResult.{field}读取"。
3. **阈值不在空气中。** 方案哨兵用基线建立期回答"20%偏离合理吗"。
4. **Goal不是孤立的。** dependsOn + conflictsWith + 级联依赖检测 + 冲突告警。
5. **闭环验证不是事后诸葛亮。** Goal关闭时自动检查关联诊断指标——完成不等于有效。
6. **免打扰不是不管。** 所有被过滤的告警保留历史，系统保护中层的时间而非放弃注意力。
7. **每次偏离都是学习机会。** 导航循环的全部执行数据回流到知识体系（PKB/联邦进化/ME偏差模式库）。
