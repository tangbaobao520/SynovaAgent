# 企业循环溢出导航系统 — 研究方案 v2.0

> 权威文档15 | 2026-07-14
> 定位：表达层的最后一公里——把42条边的计算结果组织为老板能理解的"子循环溢出"语言
> 核心突破：子循环不是固定枚举，是运行时动态注册的可配置拓扑结构

---

## 零、为什么13份文档之后还需要这一份

前13份权威文档构建了完整的诊断计算基础设施。42条边在计算因果传导。50个哨兵在检测断裂点。8位专家在推理根因。增长导航在追踪Goal执行。

但所有这些计算的结果，最终呈现给老板的是什么？一份诊断报告。"Q2利润下降了15%，根因是固定成本刚性，建议推进变动成本化。"

**老板看完之后，他知道问题所在。但他不知道：如果我往这里投钱，会不会有正向溢出？我的循环在哪个环节溢出了价值、哪个环节在泄漏？**

这不是"诊断"——是"导航"。但现有的增长导航系统（权威文档13）解决的是"诊断建议→Goal→执行追踪"，权威文档05解决的是"怎么推送信号"。

这份文档填补的是：**在计算层和交互层之间，增加一个内容编排层——把raw计算结果组织为动态子循环溢出指标。**

---

## 一、核心思想：池-阀-流-溢出模型

**企业 = 一个将输入资源通过一系列转化活动变为对外部更有价值的输出，并从输出中捕获价值回注到输入的正反馈循环系统。这个循环的净溢出，就是利润。**

池（Pool）= 存储状态。阀（Valve）= 控制流量的决策点。流（Flow）= 池之间的流动。溢出（Overflow）= 输出价值 - 重新注入 = 企业创造的净价值。

企业增长停滞的根本原因，是这个循环在某个阀位置断裂——输入不足、转化效率衰减、或系统摩擦力过大吞噬了本该溢出的利润。

## 二、核心设计：子循环动态注册框架（不是固定枚举）

### 2.1 设计原则

**子循环不是硬编码的固定列表。** 不是"现金流/客户/人才/产品"四个——那只是一个起点。每个行业的子循环拓扑不同：餐饮连锁有"门店复制循环"，建筑企业有"工程交付循环"，SaaS有"ARR增长循环"。

**新增子循环 = 新增JSON配置文件，不修改任何代码。** 对标哨兵manifest.json和Playbook YAML的文件驱动哲学。系统启动时扫描、加载、注册。

### 2.2 子循环判定框架（不是"觉得重要就加"）

什么应该被建模为一个独立子循环？三个条件——来自现有42条边正交性检验的扩展：

1. **输入独立性**：该循环的输入是否具有独立来源，不完全是其他循环的副产品？
2. **转化独特性**：该循环的转化活动是否涉及不同的42边组（与其他循环的边组重叠度 < 50%）？
3. **溢出不可约简性**：该循环的溢出是否不能被其他已有循环的溢出组合解释（残差 > 阈值）？

满足三个条件 → 独立子循环。仅满足两个 → 可能是已有循环的"子阀"——在已有循环内增加细分监测，而非新增独立循环。

### 2.3 循环配置JSON格式

```json
{
  "cycleId": "store-replication",
  "name": "门店复制循环",
  "description": "单店盈利 → 复制开新店 → 规模效应 → 更强单店盈利",
  "applicableIndustries": ["餐饮", "零售", "连锁"],
  "nodes": {
    "input": ["cash-pool", "talent-pool"],
    "conversion": ["store-operations", "site-selection"],
    "output": ["store-profit", "customer-base"],
    "reflow": ["profit-reinvestment", "brand-equity"]
  },
  "edges": {
    "acquisitionValve": ["E-05", "E-07"],
    "allocationValve": ["E-13"],
    "conversionValve": ["E-23", "E-28"],
    "deliveryValve": ["E-30", "E-31"],
    "recycleValve": ["E-37"]
  },
  "overflowFormula": "store_profit - new_store_investment - operating_cost",
  "dataMaturity": {
    "minimumDataWindow": "6_months",
    "maturityStages": {
      "learning": { "window": "0-6_months", "usesIndustryBaseline": true },
      "active": { "window": "6-12_months", "confidence": "medium" },
      "mature": { "window": ">12_months", "confidence": "high" }
    }
  },
  "mapping": {
    "42edges": ["E-13", "E-23", "E-30", "E-34", "E-37", "E-38"],
    "compute": ["computeStoreProfit", "computeROIC"],
    "sentinels": ["profit-health", "cash-runway"]
  },
  "crossCyclePropagation": {
    "from": "store-profit",
    "to": "profit-reinvestment",
    "via": "E-37",
    "estimatedLag": "3-6_months"
  }
}
```

### 2.4 加载机制

- 系统启动时扫描 `cycles/` 目录下所有 `*.cycle.json` 文件
- 根据 `applicableIndustries` 字段匹配当前企业行业 → 仅加载匹配的配置
- 多级优先级：企业自定义(`cycles/custom/{enterpriseId}/`) > 行业模板(`cycles/industry/{industry}/`) > 系统预置(`cycles/builtin/`)
- 加载失败 → 标记degraded + 写入L4事件流 → 不阻塞系统启动

### 2.5 同一行业不同商业模式的差异化

循环拓扑相同但参数不同——通过企业参数覆盖表实现：

```json
{
  "enterpriseId": "wowbaby",
  "cycleId": "store-replication",
  "parameters": {
    "newStoreInvestment": 300000,
    "storeProfitTarget": 80000,
    "reinvestmentRatio": 0.6,
    "breakevenMonths": 6
  },
  "weights": {
    "customerSatisfaction": 0.8,
    "storeProfit": 0.6
  }
}
```

瑞幸和星巴克使用同一套循环配置（单店模型+现金流），但阈值参数不同。差异通过企业参数覆盖表处理。

### 2.6 配置由谁来做（三层分工）

**第一层：系统预置（15-20个行业模板）**
- 覆盖最常见行业（餐饮/零售/制造/SaaS/建筑/物流等）
- 每个模板包含该行业的核心循环定义
- 覆盖80%客户需求

**第二层：GA配置工作台（无代码）**
- GA从预置模板选择 → 调整参数 → 保存为企业实例
- 预置不满足 → 组合已有循环 → 保存为新组合
- 组合也不满足 → 通过界面拖拽式构建新循环（边+节点+溢出公式）

**第三层：研发深度定制（需代码）**
- GA工作台无法满足 → 需要新的42边或compute函数
- 属系统扩展，按标准流程新增

## 三、溢出指标与数据成熟度

### 3.1 溢出公式的参数必须可追溯到42边

每个子循环的溢出公式中，每个参数显式标注数据来源：

```json
{
  "overflowParams": [
    {
      "name": "store_profit",
      "source": "compute",
      "sourceId": "COMPUTE-STORE-PROFIT-V1",
      "isEstimated": false,
      "confidence": "high"
    },
    {
      "name": "new_store_investment",
      "source": "42edge",
      "sourceId": "E-13.capital_allocation",
      "isEstimated": false,
      "confidence": "high"
    },
    {
      "name": "operating_cost",
      "source": "manual",
      "sourceId": "GA_INPUT",
      "isEstimated": true,
      "confidence": "medium",
      "estimatedBy": "GA"
    }
  ]
}
```

### 3.2 数据成熟度状态

溢出指标的数据来源不对称——不同子循环的最小数据窗口不同。必须显式标注，不能让老板看到空值。

- **学习期**（数据不足6个月）：使用行业基准作为占位，标注"学习期"
- **活跃期**（6-12个月）：有初步置信度，标注"中等可靠性"
- **成熟期**（>12个月）：完全可用，标注"高可靠性"

当溢出指标处于"学习期"时，仪表盘上显示的是"行业参考值"而不是"你的企业的值"——并明确告知用户这个区别。

### 3.3 承诺清单：投入建议引擎的诚实边界

系统必须诚实地告诉用户它**能做什么**和**不能做什么**。

**能做的**：
- 传导方向模拟：回答"往这里投钱，溢出是正向还是负向趋势"
- 传导路径展示：展示投入如何通过因果链影响到终点子循环
- 相对效果排序：在给定的N个子循环中，哪个的投入边际溢出最高

**不能做的**（需要至少12个月历史干预数据后才可以启用）：
- 精确财务预测：不能回答"投入100万，3个月后回报150万"
- 最优投入量：不能回答"最优投入是73.5万"——只能给出方向+量级区间

这个承诺清单显示在投入建议引擎的每次输出中："以下模拟基于当前因果边参数计算，仅指示传导方向，不构成精确财务预测。"

## 四、跨子循环传导与滞后时间

### 4.1 传导的滞后时间必须显式标注

老板最关心的是"我招了人，多久能看到效果"。如果系统只说"会改善"，不说"大概要6个月"，老板会在第3个月时认为系统判断失误。

每条因果边在第42边体系中增加 `action_effect_lag` 字段：
- E-38（人才留存→知识保护）：3-6个月
- E-15（人才部署→执行效率）：1-3个月
- E-17（激励对齐→执行效率）：1个月

当一条传导路径涉及多条边时，累计滞后 = 各边滞后之和。溢出仪表盘展示传导时间线——"预计3个月后人才循环溢出转正，6个月后客户循环溢出开始改善"。

### 4.2 溢出监控循环的计算周期

不同子循环的溢出变化节奏不同——不能统一14天。绑定到业务周期：

- 现金流循环：每周（波动快，需要及时感知）
- 客户循环：月度或季度（LTV是季度级指标）
- 人才循环：月度（人均产出短期波动是噪音）
- 产品循环：月度（新功能采纳率有统计延迟）

仪表盘上标注每个子循环的"数据更新周期"——让老板理解为什么不同子循环的更新频率不同。这不是系统延迟，是业务本质。

## 五、投入建议引擎的执行约束

### 5.1 不只是"投多少钱"——还要标注"能不能执行"

引擎输出格式：

```json
{
  "recommendation": "增加人才循环投入，招聘3名核心开发",
  "direction": "positive",
  "estimatedEffect": {
    "range": [0.05, 0.15],
    "unit": "客户循环溢出改善比例",
    "timeHorizon": "6-9_months"
  },
  "confidence": "medium",
  "executionPrerequisites": [
    { "type": "talent_market", "check": "目标技能人才市场供给充足", "status": "verified" },
    { "type": "team_capacity", "check": "现有团队有onboarding带宽", "status": "unverified" }
  ],
  "executionRisks": [
    "如果3个月内无法招到目标技能人才，建议的预计效果不成立"
  ]
}
```

## 七、研究任务（6章）

### 第一章：循环配置规范与动态加载机制
- 循环判定框架（输入独立性/转化独特性/溢出不可约简性）
- 循环配置JSON Schema + 加载器（对标sentinel-loader）
- 企业参数覆盖表 + 行业模板管理

### 第二章：溢出仪表盘动态生成
- 基于循环配置动态生成溢出热力图
- 数据成熟度状态标注（学习期/活跃期/成熟期）
- 跨子循环传导时间线

### 第三章：投入建议引擎
- 传导方向模拟（不是精确预测）
- 承诺清单：能做什么/不能做什么
- 执行约束因子标注

### 第四章：溢出驱动的顶层Loop Engineering
- 溢出监控循环的调度优先级（在诊断周期结束时触发，优先级高于导航循环）
- 计算周期与子循环业务周期绑定
- 与五循环的接口

### 第五章：行业模板管理与GA配置工作台
- 系统预置15-20个行业模板
- GA无代码配置流程
- 三层分工（预置→GA工作台→研发）

### 第六章：与现有体系集成
- 与42边/交互蓝图/增长导航/系统集成的具体接口

## 八、验收标准

1. 循环配置JSON Schema可被Loader正确解析，新增子循环=新增JSON文件
2. 至少4个出厂商内置子循环模板（现金流/客户/人才/产品）+ 2个行业专用模板（门店复制/ARR增长）
3. 溢出公式每个参数标注数据来源（42边/compute/manual），估值参数标注置信度
4. 投入建议引擎输出限定为传导方向和量级区间，不输出精确预测值
5. 溢出仪表盘展示数据成熟度状态，不同子循环的不同更新周期被显式标注
6. 与权威文档14 MVS的扩展集成——溢出监控是MVS之后的第一个扩展目标
