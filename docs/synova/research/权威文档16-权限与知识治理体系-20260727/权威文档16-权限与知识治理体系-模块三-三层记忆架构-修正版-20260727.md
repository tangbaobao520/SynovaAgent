# 模块三：三层记忆架构 (修正版)

> 行业实践确认: Hermes、Claude Code、Codex 全部使用文件驱动记忆。
> 组织记忆和部门记忆走文件——天然 git 版本化、人工可编辑。
> 个人记忆保留 SQLite——适合个人会话历史。

---

## 零、行业对标：为什么文件驱动

在 07 号权威文档 (Agent工程能力对标) 中, 我们对 Hermes、Claude Code、OpenClaw 三款开源 Agent 做了详细的架构分析。三者在记忆实现上的共同模式:

| Agent | 记忆存储 | 模式 |
|-------|---------|------|
| Hermes | `.hermes/memory/` (tasks/knowledge/decisions/patterns/context 五个子目录) | 文件驱动, Agent 从文件加载上下文, 写回文件供其他 Agent 消费 |
| Claude Code | `.codex/task-briefs/` + `.codex/contracts/` + `.codex/self-reports/` + Iron Law 0-5 (23条错误清单) | 文件驱动, 合同存档器做跨Agent交接, 上下文注射器做知识注入 |
| Codex (本系统) | `.codex/signals/` + `.codex/settings/` + `hook-check-memory.sh` + 合同存档器 | 文件驱动, 控制塔6组件全部走信号文件 |

**无一使用 SQL 做 Agent 记忆。** 文件驱动的天然优势:
- 版本化: git diff / git log 免费提供版本链, 不需要写代码
- 人工可读: 管理员可以打开 Markdown 文件直接编辑, 不需要 UI
- 冲突检测: git diff 免费提供, 不需要写检测逻辑
- 回滚: git revert 免费提供, 不需要写回滚代码
- 跨 Agent 共享: 文件是 Agent 之间的天然通信协议

---

## 一、三层定义 (修正版)

| 层 | 存储 | 可见范围 | 写入者 | 优先级 |
|----|------|---------|--------|:---:|
| 组织记忆 | `.codex/enterprise/facts/{category}/{key}.md` (文件驱动) | 全企业 | 管理员确认的 active 企业事实 | 最高——专家硬约束 |
| 部门记忆 | `.codex/enterprise/departments/{dept-id}/context.md` (文件驱动) | 本部门全员 | 部门 manager + Goal 关闭自动提取的部门级经验 | 中 |
| 个人记忆 | `agent-memory-store.ts` (SQLite, 已有) | 仅自己 | 本人 + Agent 自动 | 低 |

**关键变化:** 组织记忆和部门记忆从 SQLite `agent_memory` 表迁移到 `.codex/enterprise/` 文件目录。`agent-memory-store.ts` 中的 `enterprise_fact` 类型降级为仅供个人记忆使用。

## 二、组织记忆文件格式

每个企业事实是一个 Markdown 文件, YAML front matter 携带元数据:

```markdown
---
key: cash_runway
category: FINANCE
status: active        # pending | active | conflicted | expired
confidence: 1.0
source: admin_confirmed
created_by: admin_zhang
approved_by: admin_zhang
approved_at: 2026-07-27T10:00:00Z
version: 3
tags: [cash, runway, finance]
expires_at: null
---

# 现金跑道

公司当前现金跑道为 6 个月 (基于 2026年6月财务数据)。

计算依据: 月均现金消耗率 = (期初现金 - 期末现金) / 6 = 85万/月。
现金储备 = 510万。跑道 = 510/85 = 6.0 个月。
```

管理员可以直接编辑这个文件——改内容、改 status、改 confidence。git 自动跟踪每一次变更。

## 三、企业管理事实的审批流程 (文件驱动版)

```
系统/专家/GA 写入 → 生成 .codex/enterprise/facts/{category}/{key}.md
  → status: pending, confidence: 0.5-0.7
  → 出现在管理员的待审批文件列表中 (扫描 status=pending 的 .md 文件)
  → 管理员审核
    → 修改 status: active, confidence: 1.0, 填写 approved_by/approved_at
    → 修改 status: rejected, 填写驳回理由
    → 直接编辑文件内容后确认

status: active 的事实 → 被 expert-file-loader 加载并注入专家提示词
status: pending/conflicted 的事实 → 不注入
```

---

## 四、冲突检测 (文件驱动版)

系统定期扫描 `.codex/enterprise/facts/` 目录下同 category 的 active 文件, 检测数值矛盾或逻辑冲突。检测到冲突时, 将冲突双方的文件 status 从 active 改为 conflicted——但不在文件中直接修改——而是在文件末尾追加 `<!-- CONFLICT: 与 {other_key}.md 存在数值矛盾 -->` 注释, 并在管理员界面展示问题文件列表。

管理员解决冲突后, 手动将被驳回的文件 status 改为 expired, 保留被确认的文件 status 为 active。冲突追溯通过 git log 自动完成——不需要额外代码。

---

## 五、版本与回滚 (文件驱动版)

不需要版本链字段。git 提供完整的版本历史:

```bash
git log -- .codex/enterprise/facts/FINANCE/cash_runway.md
git diff HEAD~1 -- .codex/enterprise/facts/FINANCE/cash_runway.md
git checkout HEAD~1 -- .codex/enterprise/facts/FINANCE/cash_runway.md  # 回滚
```

管理员不需要学新工具——git 是他们已经在用的版本控制。

---

## 六、部门记忆

格式同组织记忆，存储在 `.codex/enterprise/departments/{dept-id}/context.md`。manager 可以编辑、系统自动追加 (如 Goal 关闭提取的经验)。跨部门信号机制不变。

---

## 七、个人记忆 (不变)

`agent-memory-store.ts` 保留 SQLite 实现——适合个人会话历史、偏好、对话上下文。不需要文件驱动——个人记忆不需要跨 Agent 共享或 git 版本化。

---

## 八、expert-file-loader 的加载逻辑修正

当前代码从 `agent-memory-store.ts` 的 SQL 查询加载企业事实。修正后:

```
扫描 .codex/enterprise/facts/ 目录
  → 只加载 status=active 的 .md 文件
  → 按文件修改时间排序 (最近修改的优先)
  → 预算管理: 按总内容长度截断 (避免超出 token 限制)
  → 注入专家 system prompt 顶部
```
