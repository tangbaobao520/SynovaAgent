# 模块二：企业事实治理

> 企业事实是注入到专家 system prompt 顶部的硬约束。如果这个起点错了, 所有专家的结论都会错。

---

## 一、什么是企业事实

企业事实通过 expert-file-loader.ts 注入到每一位专家的 system prompt 最顶部, 标注"企业事实(硬约束——你必须基于以下事实推理)"。只有 status=active 的事实才注入专家提示词。

---

## 二、事实来源与初始可信度

| 来源 | 初始状态 | 初始置信度 | 写入权限 |
|------|---------|----------|---------|
| 管理员手动确认(通过审批) | active | 1.0 | 管理员 |
| 哨兵系统自动调整阈值 | pending | 0.5 | 系统自动 |
| Goal关闭自动提取的经验 | pending | 0.6 | 系统自动 |
| 专家诊断结论中的模式发现 | pending | 0.7 | 系统自动 |
| GA的observation | ga_observation | 0.6 | GA(不可修改/不可删除) |

---

## 三、审批机制——管理员智能辅助

每条pending事实提交给管理员时, 系统自动展示:

- **来源**: 谁/哪个系统组件产生的这条事实
- **置信度**: 系统计算的初始置信度
- **影响范围**: 此事实将影响N位专家的诊断分析
- **建议**: 明确标注建议来源——基于数据分析(该阈值在过去6个月的数据分布中处于合理区间, 置信度0.85) 或 基于模式匹配(该阈值与同行业企业的典型值一致, 置信度0.6)。管理员据此区分技术层面的建议和内容层面的建议, 避免将系统对数据质量的判断误认为是对内容正确性的背书

---

## 四、事实生命周期

```
系统/专家/GA写入 -> pending -> 管理员审核
  -> 确认 -> active -> 注入专家提示词
  -> 驳回 -> rejected -> 退回来源
  -> 修改 -> 管理员编辑后确认 -> active

active事实 -> 可被新pending覆盖(新版本) -> 可被管理员手动expired -> TTL到期自动expired
```

---

## 五、事实冲突检测与裁决

两条active事实可能矛盾: 现金跑道6个月 vs 现金跑道12个月。系统每日扫描active事实, 检测同领域内是否存在数值矛盾或逻辑冲突。

冲突发生时: 两条事实都标记为conflicted, 不注入专家提示词。同时, 系统追溯并标注所有在冲突期间使用了该事实的诊断报告——报告顶部自动追加警告: 本报告的部分结论基于已被标记为冲突的企业事实(事实ID: XXX)。在该事实冲突被管理员解决之前, 报告中的相关建议可能不可靠。

**裁决权归属:** 由管理员裁决。若管理员无法裁决(如CEO自己确认了一条事实而财务管理员确认了另一条), 升级到上一级(创始人)。若创始人和管理员为同一人, 系统自动选择置信度较高的事实作为默认, 并提示管理员复核。

---

## 六、版本管理与回滚

- 每次UPDATE不覆盖旧值——新建一行, 通过version_id链指向前一版本
- 管理员可查看任一事实的完整版本历史
- 管理员可回滚到任一历史版本——回滚操作记录为新版本, 不删除中间版本

---

## 七、管理员信息独裁的外部审计制衡

增加外部审计模式: GA或独立董事(若企业设定)可查看pending事实及其审批历史——但不具备审批权。外部审计者看到的是: 哪些事实被系统自动提出却被管理员拒绝、哪些事实被管理员主动修改了内容。独立董事没有审批权——但当某些事实被反复拒绝成为一种可见的模式, 这本身就构成了一种制衡。
