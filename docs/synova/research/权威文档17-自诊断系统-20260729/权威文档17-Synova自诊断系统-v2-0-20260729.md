## 概念设计层 (保留为设计参考——实现见控制塔 v3 FINAL)

### 一、六条件完成度定义

一个任务真正完成当且仅当满足六个条件: 代码存在, 接线完整, 测试存在, 路径可达, 依赖可用, 无已知缺陷。任务完成度 = 已满足条件数 / 6。系统完成度 = 所有任务的加权平均值。

### 二、版本化快照系统

`.codex/snapshots/{timestamp}/`——每次 `check-gates-v2.py` 运行时创建新快照, 不覆盖历史数据。30天每日+90天每周+归档。趋势=两个快照的diff。

### 三、自诊断四层验证

L1(物理存在性, 30秒)→L2(接口契约, 2分钟)→L3(行为正确性, 5分钟)→L4(集成一致性, 10分钟)。四层独立阻断。

### 四、Iron Law 进化

自诊断循环发现的偏差——能匹配到已知 Iron Law 则自动标注编号——不能匹配则生成候选 Iron Law, 推送给创始人审核。审核通过后加入 AGENTS.md, 后续自动执行。

## v2 新增——产品级定位与进化体系集成

### 五、自诊断系统的双重身份

自诊断系统不是"研发工具"——是**Synova 产品的内置能力**。它在两种模式下运行:

**研发模式 (开发环境):** 检测代码完成度——任务是否满足六条件、门禁是否全绿、接线是否完整。运行时机: git push / 合并请求 / 每日定时。使用者: 创始人 + Dev Doc Agent。

**产品模式 (客户环境):** 检测运行健康度——数据管道是否仍在流动、哨兵扫描是否仍然准确、诊断结论质量是否在退化。运行时机: 每次诊断完成后 + 每日定时。使用者: 企业管理员 + GA。

同一套六条件判定引擎和快照系统——两种模式复用。区别在于检测对象和阻断方式。

### 六、产品模式的检测维度

| 维度 | 检测内容 | 检测方式 | 降级处理 |
|------|---------|---------|---------|
| 数据管道健康 | 最近7天内有新数据流入 GraphStore？数据源的连接状态？ | `src/ingest/` 监控 + GraphStore 增量查询 | 标记诊断报告顶部: "数据管道在过去X天无新数据——诊断结论基于过期数据" |
| 哨兵准确度 | 哨兵产出的 Finding 是否和 GA 验证的结论一致？哨兵误报率趋势？ | 哨兵 Finding 和 GA 反馈的交叉对比 | 误报率 >30% 的哨兵自动降低权重——其 Finding 不再触发 P0 告警 |
| 诊断质量退化 | 最近 3 次诊断报告的 GA 评分趋势？是否有连续的"无用"评分？ | GA 验证标记 + 诊断报告质量评分 | 连续 3 次"无用"→ 自动标记系统为"需 GA 深度审查"——不阻断运行但告警 |
| 循环运行状态 | 6 个业务循环是否全部在运行？是否有循环超过 3 个周期无输出？ | Gate 13 静默检测 (已有) | SYSTEM_SILENCE 告警——已有机制 |
| 资源使用 | 内存/磁盘/CPU 是否在安全范围内？是否有泄漏趋势？ | 系统资源监控 | 即将触及上限时提前告警——不是等到崩溃 |

### 七、产品模式的阻断规则

**关键差异: 产品模式不阻断系统运行——只标记诊断报告的可信度。**

| 检测结果 | 动作 |
|---------|------|
| 所有维度正常 | 诊断报告顶部: "系统健康度: 正常——本次诊断结论可信" |
| 1-2 个维度退化 | 诊断报告顶部: "系统健康度: 部分退化(数据管道无新数据流入)——本次诊断结论仅供参考" |
| 3+ 个维度退化 | 诊断报告顶部: "系统健康度: 严重退化——本次诊断结论不可信, 请联系管理员检查系统状态" |

这不是"阻止系统运行"——是"诚实告诉用户这状态下的报告有多可信"。和 Gate 13 的区别: Gate 13 只检测系统是否活着——产品自诊断检测系统是否"准确地活着"。

### 八、与现有进化体系的集成

Synova 有四套进化系统, 各自进化不同类型的知识——互补, 不冲突:

| 进化系统 | 进化的对象 | 驱动数据 | 触发条件 |
|---------|----------|---------|---------|
| middle-evolution-engine (D92) | 诊断规则 (哨兵阈值, 专家置信度, Goal 公式) | 企业中层反馈——同类型信号 >=3次 | 自动——每次中层反馈聚合后 |
| GA 反馈 (权威文档16) | 专家诊断结论 (错误根因, 遗漏因素, 过度判断) | GA 手动纠错记录 | 手动——GA 提交纠错后, 管理员审批 |
| 联邦知识 (权威文档16) | 跨企业共享的诊断模式 | 多企业验证——>=2家企业产生相似改善 | 自动——满足验证条件后 |
| **自诊断进化 (新增)** | **工程和运营质量规则** | **自诊断循环发现的偏差模式** | **自动——偏差匹配不到已知 Iron Law 时生成候选** |

四套系统分别进化四个层次的知识:
- middle-evolution 进化"如何更准地诊断企业"
- GA 反馈进化"人类专家如何纠正 AI 的错误"
- 联邦知识进化"哪些经验可以跨企业共享"
- 自诊断进化"Synova 自己如何变得更可靠"

### 九、联邦知识的自诊断扩展

自诊断进化发现的模式——例如"数据管道连续 3 天无新数据但哨兵仍报告正常"——如果被 >=2 家企业验证, 可以作为**运营质量信号**进入联邦知识库。这是联邦知识的一个新维度——不只是"企业的增长模式", 还包括"Synova 自身的质量模式"。

联邦知识库的 `pkb_domain` 字段增加 `'synova_operations'` 值——专门存储 Synova 自身的运营质量知识。这些知识的脱敏规则与企业业务知识的脱敏规则相同——去掉企业标识、保留模式特征。

#### 10.2 诊断报告的可信度标记

`ProductHealthReport` 的输出注入到诊断报告生成流程:

```
诊断报告生成 → ProductHealthEngine.aggregate_health()
  → healthy: 报告顶部 "系统健康度: 正常——本次诊断结论可信"
  → degraded: 报告顶部 "系统健康度: 部分退化(原因)——本次诊断结论仅供参考"
  → critical: 报告顶部 "系统健康度: 严重退化——本次诊断结论不可信"
```

#### 10.3 自诊断进化的 Iron Law 候选生成

`DeviationReport` 中的偏差——每次自诊断循环运行后——和 AGENTS.md 中的 48 条 Iron Law 做模式匹配:
- 匹配成功 → 标注铁律编号
- 匹配失败 → 生成候选 Iron Law (JSON 格式, 写入 `.codex/candidates/iron-law-{id}.json`)
- 创始人审核 → 通过则加入 AGENTS.md; 拒绝则标记为 rejected

```json
{
  "id": "candidate-IL-49",
  "pattern": "数据管道连续3天无新数据但哨兵仍报告正常",
  "detection_rule": "graphStore.newNodesInLastDays(3) == 0 AND sentinelHealth.status == 'green'",
  "severity": "P0",
  "first_observed": "2026-07-29T08:00:00Z",
  "recurrence_count": 2,
  "status": "pending_review"
}
```
