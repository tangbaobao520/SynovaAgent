## 二、第一性原理推导

Synova 部署在企业内部——不是 SaaS, 没有运维团队后台监控。Gate 13 检测"系统是否还活着"——但回答不了"系统产出的诊断结论是否还准确"。

如果一个企业在使用 Synova 六个月后, 数据管道悄然停止、哨兵扫描开始重复使用过期数据、专家诊断结论的质量因为数据质量退化而下降——但系统仍然在"正常运行"(Gate 13 绿灯)——企业管理者无法知道这些。他只能等 GA 下一次来访时发现"这次的诊断结论和上次完全一样"——但那是几个月后了。

**自诊断系统的第一性原理: 一个部署在企业内部、没有运维团队的持续运行系统——必须具备诊断自身运行健康度的能力。这不是"锦上添花"——这是"没有它, 系统的长期可靠性是不可知的"。**

### 3.2 研发模式 vs 产品模式

| 维度 | 研发模式 | 产品模式 |
|------|---------|---------|
| 检测对象 | 代码完成度(六条件) | 运行健康度(五维) |
| 运行时机 | git push / 合并请求 / 每日定时 | 每次诊断完成后 + 每日定时 |
| 阻断方式 | CI 阻断 | 标记诊断报告可信度——不阻断系统 |
| 使用者 | 创始人 + Dev Doc Agent | 企业管理员 + GA |

### 3.3 诊断报告可信度标记

```
healthy   → "系统健康度: 正常——本次诊断结论可信"
degraded  → "系统健康度: 部分退化(数据管道无新数据流入)——本次诊断结论仅供参考"
critical  → "系统健康度: 严重退化——本次诊断结论不可信, 请联系管理员"
```

### 3.4 自诊断进化与现有进化系统的关系

四套系统进化不同层次——互补, 不冲突:

| 系统 | 进化对象 | 数据来源 | 与自诊断的关系 |
|------|---------|---------|-------------|
| middle-evolution | 哨兵阈值, 专家置信度, Goal 公式 | 中层反馈(同类型 >=3 次) | 不冲突——middle-evolution 进化诊断规则, 自诊断进化质量规则 |
| GA 反馈 | 专家诊断结论纠错 | GA 手动纠错记录 | 不冲突——GA 反馈是自诊断进化中"哨兵准确度"维度的重要数据源 |
| 联邦知识 | 跨企业诊断模式 | >=2 企业验证 | 互补——自诊断进化发现的模式可作为联邦知识的新维度(`synova_operations`) |
| 自诊断进化 | 工程和运营质量规则 | 自诊断偏差模式 | 本系统 |
