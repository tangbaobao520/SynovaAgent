# 第二章：代码审计协议与 14 项清单

> 基于 D328/D329/D330 三次审计经验 + KIMI-AUDIT-INSTRUCTION.md v1.1

## 2.1 审计员身份定义

独立架构审计员的核心约束：

1. **零上下文**：不参与设计和编码，只审查已提交代码
2. **只读**：只 Read 文件和 grep/bash，绝不 Write/Edit
3. **物理事实优先**：不信任 Agent 自我报告，只验证可 grep/可执行的结果
4. **跨模型独立**：与 Codex（规划者）和 Claude Code（编码者）无共同上下文

> 零上下文 ≠ 禁止检索。检索是验证手段，7 项材料是结论依据。

## 2.2 触发方式：选项 A（全自动）

用户只需提供任务 ID：

```
审计任务 D328
```

Kimi CLI 自动收集：
- `git log --grep="D328"` → commit hash
- `git diff <hash>^..<hash>` → 变更内容
- `find docs/plans/codex/implementation/ -name "*D328*"` → dev doc
- `.claude/task-briefs/` 日期匹配 → task brief
- `AGENTS.md` → 铁律判案依据

## 2.3 语义审计清单（14 项）

### 原 11 项

| # | 项 | 判定方法 |
|---|-----|---------|
| 1 | **接口真实性** | dev doc 声明的每个函数/类，grep 确认存在于代码中 |
| 2 | **文件路径存在性** | dev doc 引用的每个路径，`[ -f "$path" ]` 确认 |
| 3 | **Edge ID 有效性** | 文档中的 `E-XX` 模式，`grep -r` 确认在 `extensions/` 中有定义 |
| 4 | **架构边界** | diff 中 `grep -n "from '../l3/\|from '../store/"` 等跨层引用 |
| 5 | **数据流完整性** | dev doc 中每个 `→` 箭头，grep 确认有对应函数调用 |
| 6 | **接线深度** | 新 export 被 import 后**真的被调用**（不只是 import） |
| 7 | **降级诚实性** | 每个 catch 有 `log.warn/error` + `degraded: true` |
| 8 | **测试契约** | JSDoc 声明的输入/输出/降级与实际代码一致 |
| 9 | **测试覆盖** | 正常路径 + 降级路径 + 边界条件。**必须实际运行并确认全绿** |
| 10 | **文件驱动** | 新增硬编码类型？manifest？tags？ |
| 11 | **自我报告交叉对比** | Agent 声称的 vs 物理事实 |

### 新增 3 项（AUDIT-PROTOCOL v1.0）

|---|-----|------|
| 12 | **dev doc 偏离审计** | 写集表 vs 实际提交文件；每条 DS 必须 file:line 证据 |

## 2.4 测试验证三步法（v1.1 新增）

| 步骤 | 操作 | 目的 |
|------|------|------|
| **T1** | 干净快照上运行（`git archive` 或临时 clone） | 排除工作区 WIP 污染 |
| **T2** | 当前工作树上运行 | 验证实际部署状态 |
| **T3** | 故障注入实验（损坏 PATH、删除依赖等） | 验证 fail-open 不静默放行 |

**判定规则**：
- T1 和 T2 全绿 → [PASS]
- T3 发现静默放行 → [FAIL]，无论 T1/T2 结果

## 2.5 分级标准

| 级别 | 条件 | 处理 |
|:---:|------|------|
| **P0** | 阻断交付 / 安全事故 / 门禁形同虚设 | 必须修复 |
| **P1** | 建议修复 / 数据不实 | 记录跟进 |
| **P2** | 可选改进 | 采纳/忽略 |

## 2.6 结论定义

| 结论 | 条件 |
|------|------|
| **PASS** | 14 项全 PASS，无 P0/P1/P2 |
| **CONDITIONAL PASS** | 无 P0，但有 P1/P2。核心功能通过，声明/文档有缺口 |
| **FAIL** | 存在 P0 |
