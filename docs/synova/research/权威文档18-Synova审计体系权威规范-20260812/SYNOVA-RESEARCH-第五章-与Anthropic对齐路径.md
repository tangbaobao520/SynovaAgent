# 第五章：与 Anthropic 对齐路径

> 差距分析 + 两周 Sprint 升级计划

## 5.1 Anthropic 的审计哲学

Anthropic 的核心方法：**把 LLM 的判断转化为可脚本验证的约束。LLM 只负责脚本检不出的盲区。**

| 层级 | Anthropic 做法 | 我们的当前状态 | 差距 |
|------|--------------|-------------|------|
| **代码审计** | 脚本跑 80%（接口/测试/边界），K3 只跑 20%（语义盲区） | K3 跑 100%（14 项全人工） | 差 80% 自动化 |
| **文档审计** | 脚本扫描 `<claim>` 证据，K3 审 10-20 个高风险 CLAIM | K3 读 17 份全文 | 差自动化筛选 |
| **报告格式** | JSON（机器可读，可 diff）+ Markdown（自动生成） | Markdown（人读） | 差可复现性 |
| **触发方式** | pre-commit/CI 自动触发 | 人工输入"审计任务 DXXX" | 差自动化 |
| **成本** | ¥0-5/次 | ¥5-20/次 | 差 3-4 倍 |

## 5.2 为什么不是一步到位

Anthropic 的体系是 **3-4 年工程化沉淀** 的结果。我们当前是 **Phase 0-1 验证假设** 阶段。

**正确的迭代顺序**：

```
Phase 0（现在）: K3 人工审计 → 证明"独立审计能发现盲区" ✅ 已完成
Phase 1（本周）: 审计经验 → 沉淀为脚本规则 → 控制塔升级
Phase 2（下月）: <claim> 标签普及 → doc-audit 自动验证
Phase 3（季度）: 脚本跑 80%，K3 只跑 20% → 接近 Anthropic
```

**每次 K3 审计的价值不是"发现 bug"，而是"发现一种新类型的盲区，然后把它变成控制塔的自动化规则"。**

## 5.3 两周 Sprint 对齐路径

### Sprint 1（本周）：脚本化 80% 的物理检查

| 任务 | 当前（K3 人工） | Sprint 1 目标 | 节省 |
|------|--------------|-------------|:---|
| 接口真实性（#1） | K3 grep | 脚本 grep | 100% |
| 文件路径存在性（#2） | K3 `[ -f ]` | 脚本 `[ -f ]` | 100% |
| Edge ID 有效性（#3） | K3 grep | 脚本 grep | 100% |
| 架构边界（#4） | K3 grep | 脚本 grep | 100% |
| 数据流完整性（#5） | K3 grep | 脚本 grep（部分） | 50% |
| 接线深度（#6） | K3 手动追踪 | 脚本静态分析（有限） | 30% |
| 降级诚实性（#7） | K3 grep | 脚本 grep catch + log | 80% |
| 测试覆盖（#9） | K3 跑测试 | CI 自动跑测试 | 100% |
| dev doc 偏离（#12） | K3 手动对比 | 脚本对比写集表 | 50% |
| 版本编排（#14） | K3 手动检查 | 脚本检查 VERSION.md/tag | 80% |

**Sprint 1 后，K3 只需审**：
- #8 测试契约（JSDoc 语义一致性）
- #10 文件驱动（新增硬编码类型的语义判断）
- #11 自我报告交叉对比（需要理解声称 vs 事实的语义差异）
- #13 控制塔执行审计（bypass.log 的语义分析）

**从 14 项降到 4 项，成本从 ¥15-20 降到 ¥3-5。**

### Sprint 2（下周）：`<claim>` 标签 + JSON 双轨

| 任务 | Anthropic 特征 | Sprint 2 目标 |
|------|--------------|-------------|
| 文档审计触发 | 修改文档时 pre-commit 自动触发 | 组 13 集成 doc-audit |
| 文档验证 | 脚本扫描 `<claim>` 证据 | doc-audit --scan-all |
| 报告格式 | JSON 可 diff | Markdown + JSON 双轨输出 |

**Sprint 2 后，权威文档审计从"K3 读全文"变成"脚本扫 CLAIM + K3 审高风险项"。**

## 5.4 长期目标（季度）

| 指标 | 当前 | Sprint 1 | Sprint 2 | 季度 |
|------|:---|:---|:---|:---|
| 代码审计成本 | ¥15-20 | ¥5-8 | ¥3-5 | ¥1-3 |
| 代码审计自动化率 | 0% | 70% | 70% | 85% |
| 文档审计成本 | ¥20-50（全文） | ¥20-50 | ¥5-10（CLAIM） | ¥2-5 |
| 文档审计自动化率 | 0% | 0% | 60% | 80% |
| 触发方式 | 人工 | 人工 | pre-push 半自动 | CI 全自动 |

## 5.5 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 旧文档是否迁移 | ❌ 不迁移，只注册表 | 17 份文档迁移成本 > 价值，注册表足够管理偏差 |
| `<claim>` 粒度 | 只标"已实现/部分实现"声明 | 每句话都标维护成本不可接受 |
| JSON 报告是否替代 Markdown | 双轨并存 | Markdown 人读，JSON 机器 diff，不互相替代 |
| K3 是否保留人工触发 | ✅ 保留，但最小化 | 高风险任务仍需 K3 语义审计，常规任务脚本自动化 |
