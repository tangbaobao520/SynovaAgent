## 6.1 防线缺口收割的定义

每份审计报告末尾固定章节：

> **"本次发现的问题（若有），控制塔哪一道防线本该拦住？为什么没拦住？缺什么？"**

产出填入控制塔"待补"区，凑够 5-8 次触发**控制塔健康审计**。

## 6.4 控制塔健康审计触发条件

AUDIT-PROTOCOL.md v1.0 §7 定义：

> 5-8 次审计后，触发控制塔健康审计——审计审计者自身。

**当前进度**：3 次审计（D328/D329/D330）。再 2-5 次后触发。

**健康审计内容**：
1. 审计协议本身是否有盲区？（K3 审 K3 的审计方法）
2. 防线缺口是否被有效收割？（L4 产出是否转化为控制塔升级）
3. 审计成本是否持续下降？（脚本化率是否提升）
4. 审计是否成为新的瓶颈？（审计延迟是否阻塞交付）

## 6.5 防线缺口的闭环原则

**发现 → 记录 → 修复 → 验证 → 归档**

```
审计发现 bypass.log 空窗
        ↓
L4 防线缺口收割：记录缺口
        ↓
控制塔待补区：标记 P0
        ↓
Codex 写 D331 dev doc：修复方案
        ↓
Claude Code 编码：实现修复
        ↓
K3 审计 D331：验证修复是否有效
        ↓
审计报告归档：缺口状态更新为"已修复"
```

**关键规则**：
- P0 缺口未修复前，**阻断后续任务合并**（已在 synova-audit-dispatcher.sh 中实现）
- 缺口修复后，**必须在下次审计中验证**（不能"声称已修复"就关闭）
- 重复出现的同类缺口，**升级严重度**（第一次 P1，第二次 P0）
