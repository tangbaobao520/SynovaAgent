## 二、优先级判据（可判定，换人可重算）

对每个缺口，依次套用，**命中即定级，不打分**：

| 判据 | 问题 | 命中 → 定级 |
|---|---|---|
| **A** | 缺了它，客户现场**装不上/用不了**？ | **P0** |
| **B** | 缺了它，产品**核心卖点不成立**（如"提前预警"）？ | **P0** |
| **C** | 缺了它，**已发生的缺陷无法被发现**（机制层）？ | **P0** |
| **D** | 缺了它，就会**丢客户数据或数据不可回溯**（资产生命线）？ | **P1** |
| **E** | 企业采购/合规**必然问到**（审计、用量、权限）？ | **P1** |
| **F** | 只影响体验/效率，不阻塞交付？ | **P2** |
| **G** | DSH 有，但我方**有意不做**（写明理由）？ | **不做** |

> **判据 A/B/C 是"产品能不能成立"级；D/E 是"能不能卖给企业"级；F 是"好不好用"级。**
> 注意：**A/B/C 之间不再排序**——它们都是"不可绕过"，谁先做看依赖（见 §四）。

## 四、依赖图与批次（CTO 排期用）

```
第 0 批（立刻，无依赖）
├─ P0-4 不变量机制 …… 机制层；先立它，后续所有任务的验收都能挂上它
├─ P0-3 HTTP 代理 …… 独立，部署刚需
├─ D-1 验证基础设施（GS 场景 + e2e 进 CI）…… 独立，但是后面所有"验收"的前提
└─ P2-2 时间上下文 …… 成本极低，顺手

第 1 批（依赖第 0 批的"验收能力"）
├─ P0-1 指标时序存储 …… 新表 + 唯一写入口
│     ↓
├─ P0-2 趋势算法接线 …… 必须在 P0-1 之后（没有燃料接不了）
│     ↓
└─ C-1 参数标定与收敛 …… 必须在 P0-1 之后（护城河的地基）
       ↓
     C-2 咨询交付流程 / C-3 行业模板 …… 依赖 C-1 的垂直深度

第 2 批（企业采购必需，可并行）
├─ P1-1 凭据管理
├─ P1-2 搜索
├─ P1-3 遥测/用量/出账
├─ P1-4 迁移链
├─ P1-5 设置运行时修改 + C-4 多客户配置包
└─ P1-6 可解释性/轨迹

第 3 批（P2，按客户需求触发）
└─ spill / 文档转换 / webhook / 联网检索
```

**三条排期原则**：
1. **机制先于功能**：P0-4（不变量）与 D-1（验证）排最前，因为它们决定"后面每一项任务能不能被验收"——**没有它们，后面所有任务的"完成"都只是 grep 命中**（这是已发生三次事故的根因）；
2. **时序先于参数**：**P0-1 → C-1** 的顺序不能反。参数标定需要历史测量值，先做参数库会无数据可标；
3. **P0 内部不排序，按依赖走**：A/B/C 三类都是"不可绕过"，谁先做看依赖，不看主观权重。

### 7.4 新发现的安全缺陷：`search()` 缺租户过滤（有时间锚的 P1）

**证据**：`session-store.ts:534` 两条 SQL 均为 `WHERE m.content LIKE ?` / `WHERE agent_messages_fts MATCH ?`，**无 `WHERE s.org_id = ?`**；而同一 SQL **SELECT 了 `s.org_id`**（说明字段在，只是不用于过滤）。

**但设计本身是支持隔离的**：`agent_sessions.org_id TEXT NOT NULL`（`:185`）+ 索引 `idx_agent_session_org`（`:204`），INSERT（`:293`）与读（`:302`/`:337`）都带 org_id。
→ **所以这是"设计有、实现漏"，不是"没有隔离设计"。**

**严重度**（关键判断）：
- **当前实际风险 = 0**（`customer-config/` = 0，只有 1 个租户）；
- **第 2 个客户上线起 = P0**（跨租户数据泄露）。

**→ 定级建议**：**P1，锚点为「第 2 个客户接入前必须修」**。这比单纯标 P0/P1 更可执行——它是一个**有截止条件**的任务。

### 7.5 已解决的阻塞：turn/step 边界由谁产出

数据层任务书报告"答不上"的一项（缺口 5 轨迹的前置）。**院长补核结论**：

| 边界 | 产出方（天然持有该边界） | 证据 |
|---|---|---|
| **turn 边界** | **`ConversationEngine`** —— `processMessage()`（`:581`）/ `processMessageStream()`（`:740`）/ `startDiagnosis()`（`:796`） | 一次用户输入 → 一次回复，这就是一轮 |

### 8.2 院长裁定 ②：P0-1（工具 schema 进请求体）必须先于 P0-4（不变量机制）

### 9.4 ★ P0-4 的第一条不变量：DSH 的形状（CTO 可直接照此写）

> 创始人复核追问「这条断言你加入文档了吗」→ 已在 `自研缺陷修复.md §7.5` 与 `基础设施层 §1(e)`，**但总纲作为 CTO 入口文件此前没有 → 现补上**（本总纲也是四份文件里唯一同时含判据与批次的一份，断言放这里最便于派工）。

**DSH 的实际代码**（`dsh-agent-loop/lib/invariant.js:24-25`，全文仅 42 行）：

```js
const expected = session.deriveMessages();
if (JSON.stringify(options.messages) !== JSON.stringify(expected))
  fail(`llm request for session "${String(session.id)}" diverges from the
        dispatch-time durable derivation (log-reconstruction desync)`);
```

**它验证的是什么**：**「发出去的请求 == 日志能重建出的请求」**。

**为什么这一条能防住 P0-1**：
> P0-1 的现象是 **`tools` 从未进入 HTTP 请求体**（`base.ts:139-147` 的 body 只有 model/messages/temperature/max_tokens）。
> 而 T-D2（压缩入日志）修好后，**日志里有 `tools`**。
> → **只要 body 少一项，两边就不相等 → 断言立刻失败。**
> **这正是 grep 判据原理上做不到、而运行时断言天然能做到的那一类检查**（见 §7.4 的方法论区分）。

**配套的前置断言同样值得抄**（`dsh-agent-loop/lib/invariant.js:18-22`）：请求必须被 `Object.isFrozen`；必须带 `sessionId`；`sessionId` 必须指向**活着的** session。

**我方落地形状**（基础设施层已给）：
- 新增 `src/invariants/companions/*.invariant.ts`，**每个域一个伴生文件**，形状照 DSH：`export const onXxx = ({ fail }) => {...}`
- **首批 3 条伴生 ≈ 200 行**（`42 行 × 3` + 我方事件名适配）
- **硬前置：必须先修 P0-1**（否则断言在生产中一次都不会被触发 → **新机制自己就会变成"机制在场但不接线"**，见 §8.2 裁定）

**一条更深的洞察（基础设施层取证所得，我取用）**：
> `dsh-credentials/lib/invariant.js:13-19` 的 docstring **显式声明「这条不变量只检查什么、不检查什么」** ——
> **「显式声明不检查什么」比「检查什么」更重要**，因为它把"防护边界"变成可审计的事实，防止后人误以为它覆盖了更多。

**两条必须避开的 DSH 弱点**（基础设施层实测）：
1. **异步 listener 的违规会被吞成 warn**（DSH docstring 自陈"invariant checks on this event must not be async functions"）→ **我方必须在类型上禁止伴生 install 返回 Promise**；
2. **只挂注册表 = 零保护** → **必须加启动断言「注册数 ≥ 3」**。
