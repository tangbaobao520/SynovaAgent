## 二、P1 缺陷逐项修复任务（10 项）

### T-D1 韧性层零生产调用（429/503 第一次就失败）

- **缺陷**：`src/llm/retry-middleware.ts`（417 行，37 个测试用例）**在生产零调用方** —— 全仓 import 只有两个测试文件；生产 LLM 调用是**10 处 `provider.chat` 直调**（`tool-loop-executor.ts:61,185,296`、`diagnosis.ts:283`、`conversations.ts:124`、`context-engine.ts:308`、`background-review.ts:130,146`、`extractor.ts:67,119,170`、`synova-diagnosis-engine-impl.ts:300`），provider 层**只有熔断无重试**（`providers/base.ts:121,126-128`）
- **判据**：**B**（线上遇 429/503，用户看到的是第一次就失败）
- **影响**：重试/退避/jitter/超时二分这套工程**全部不生效**
- **修复方向**：把 10 处 `provider.chat` 收敛到一个**唯一出口**（含重试），或经 provider 层接管
- **落地位置**：新增 `src/llm/llm-gateway.ts`（唯一出口）或改造 `providers/base.ts` 的 `chat()`；10 处调用点逐个替换
- **方式**：**自建**（零依赖；算法已在 `retry-middleware.ts`，不需要借鉴 DSH）
- **验收（穿真实入口，禁 grep）**：① mock HTTP 层返回 503 两次后 200 → 断言最终成功且调用 3 次；② 断言 429 的 `Retry-After` 被采纳（**注意：该项此前发现 `providerRetryAfterMs` 无人消费，一并修**）；③ 真实入口：跑一次对话，人工断网一次，断言重试日志出现
- **依赖**：第 0 项（CI 能跑生产入口）
- **工作量**：3–10 天（10 处收敛 + 与现有熔断顺序对齐 + 测试）
- **⚠️ 附注**：另有 4 处语义改窄需一并记账（`callWithResilience` 违背"永不抛"自述、`totalTimeoutMs` 实为"每次尝试"、上游取消被归类为 `UNKNOWN`、退避 `sleep()` 不可取消）

### T-D2 压缩不入日志（replay 取不回"模型当时看到什么"）

- **缺陷**：`session_events.event_type` 的 CHECK **只有 6 个类型，结构上装不下 compaction 事件**（`src/store/session-store.ts:220`）；全仓 grep `shadowedSeqs`/`sourceEventSeqs`/`surfaceOp` **零命中**；`shadowedRange` 是**数组下标**不是 seq（`context-compaction.ts:342-363`）；`ContextCompaction` 实例化**未传 `onEvent`**（`conversation-engine.ts:394-399`）
- **判据**：**C**（已发生的可追溯性断裂，且无机制可发现）
- **影响**：日志重放得压缩前历史，**模型实际工作在"摘要+保留尾"上**；摘要正文除 `state_json` 旁路外**只活在内存，进程退出即永久丢失**；`GET /api/sessions/:id` 与 `state_json` 给出**两个不同的会话**
- **修复方向**（数据层已给可执行路径）：接上 `onEvent` + 给 `session_events` 加 compaction 类型（照 `session-store.ts:228-262` 已有的表重建迁移范式）+ 事件携带 `shadowedSeqs`（**seq 而非下标**）
- **落地位置**：`src/agent/context-compaction.ts`（传 `onEvent`）、`src/store/session-store.ts`（事件类型 + 迁移）、`src/agent/conversation-engine.ts:394-399`
- **方式**：自建（**接线 + 一次表迁移，不是重写**）
- **验收**：① 注入超阈值内容触发压缩 → 断言 `session_events` 新增 compaction 事件且含 `shadowedSeqs`；② 从日志 replay → 断言能取回"压缩前的原文"；③ 断言 `GET /api/sessions/:id` 与内部状态**一致**
- **依赖**：与数据层的「turn/step 边界事件」（缺 `SessionEventType` 扩展）**同一处 schema 变更 → 建议合并排期**
- **工作量**：3–10 天

### T-D3 删会话不删诊断报告（隐私问题）

- **缺陷**：`deleteSession` 只删 messages+sessions（`session-store.ts:355-358`）；`diagnosis_checkpoints` **无外键无 CASCADE**（`:266-271`）；**专设的 `deleteDiagnosisCheckpoints`（`:581-583`）全仓无调用者**；报告列表 SQL **不 join 会话表**（`:604-608`）
- **判据**：**D**（客户数据资产；若对外承诺过"彻底删除"则升 **P0**）
- **影响**：删除后报告仍在库、仍能经 API 列出（含完整 `report.summary` 与一页纸）
- **修复方向**：`deleteSession` 里调用已有的 `deleteDiagnosisCheckpoints`；报告列表 SQL 加会话存在性过滤
- **落地位置**：`src/store/session-store.ts:355-358`、`:604-608`
- **方式**：自建（**成本极低——函数已存在，只是没被调用**）
- **验收**：① 建会话+诊断+报告 → 删会话 → 断言 `diagnosis_checkpoints` 无残留行；② 断言报告列表 API **查不到**已删会话的报告
- **依赖**：无
- **工作量**：**1–3 天（性价比最高的一档）**

### T-D4 截断信号到手却丢弃（半截摘要当合格成果落地）

- **缺陷**：`finish_reason` 声明在 wire 类型（`providers/types.ts:78`）**全仓零消费者**，`ChatResult`（`:37-52`）不含该字段
- **判据**：**C**
- **影响**：摘要被 maxTokens 截断时，因"截断的摘要更短"**反而更容易通过影子价校验**（`context-compaction.ts:401-407`）→ 半截摘要当合格成果落地；同一根因：**被截断的助手回复被当成完整回复返回并入库**
- **修复方向**：`ChatResult` 加 `finishReason`；压缩校验拒绝 `length` 截断（DSH 对应处显式拒绝并给 `MAX_TOKENS`，`compaction-basic:341-345`）
- **落地位置**：`src/providers/types.ts:37-52,78`、`src/providers/base.ts`（映射）、`src/agent/context-compaction.ts:401-407`
- **方式**：**①范式复用**（DSH 的拒绝逻辑可参照）
- **验收**：① mock 返回 `finish_reason: 'length'` 的摘要 → 断言压缩**被拒绝**且标记 degraded；② 断言被截断的助手回复**不被当作完整回复**入库
- **依赖**：无
- **工作量**：1–3 天

### T-D5 降级信号自遮蔽（用户消息"进模型没进日志"时不报）

- **缺陷**：`addMessage` 成功即重置 `lastDegraded`（`session-store.ts:377-383`），而路由层在**第 2 次写成功后才检查**（`routes/conversations.ts:249/255/260`）
- **判据**：**C**
- **影响**：写失败信号被同轮后一次成功写入抹掉，`STORE_DEGRADED` 帧**不会发**。**且该行为被测试固化为预期**（`session-event-log.test.ts:146-164`）——**测试在保护缺陷**
- **修复方向**：让 `addMessage` **透传已有的 `AppendEventResult`**（返回值已编码失败）
- **落地位置**：`src/store/session-store.ts:377-383`、`src/routes/conversations.ts:249/255/260`、`tests/store/session-event-log.test.ts:146-164`（**测试预期要改**）
- **方式**：自建（成本极低）
- **验收**：① 注入一次写失败 + 一次写成功 → 断言 `STORE_DEGRADED` **仍被发出**；② 断言那条固化缺陷的测试**已改写**
- **依赖**：无
- **工作量**：**1–3 天**

### T-D6 `im-inbound.ts:195` 调不存在的方法（IM 历史恢复静默空转）

- **缺陷**：`im-inbound.ts:195` 调 `addToHistory`（全仓 grep **仅此一处**），且写作手法是先 `as unknown as` 再可选链
- **判据**：**C**
- **影响**：IM 通道"恢复会话历史"**是静默空转** → 模型每轮只看到当前一句
- **修复方向**：接上真实的历史读取（或显式删除该"恢复"意图，不留假动作）
- **落地位置**：`src/l1/im-inbound.ts:195`
- **方式**：自建
- **验收**：① 经 IM 通道发两轮消息 → 断言第 2 轮模型上下文**含第 1 轮**；② 断言无 `as unknown as` 逃逸
- **依赖**：无
- **工作量**：**1–3 天**

### T-D7 `ToolGuard` 计数跨轮永不清零（第 3 次同参调用起永久 block）

- **缺陷**：`src/l3/tool-guard.ts:78` 计数 + 会话级引擎缓存（`routes/conversations.ts:226,235`）→ 跨轮累积永不清零
- **判据**：**B**（对话能力被自己的守卫永久锁死）
- **对照**：DSH 是**连续语义 + 新用户消息清链**（`dsh-repeat-tool-reminder:1481,1513-1516`）
- **修复方向**：改为"连续相同调用"语义；新用户消息清链
- **落地位置**：`src/l3/tool-guard.ts:78`
- **方式**：**①范式复用**（DSH 语义可参照；阶梯我方已正确压缩为 `[2 提醒, 3 阻断]`，**保留**）
- **验收**：① 同参调用 2 次 → 断言提醒；3 次连续 → 断言阻断；② **中断后（新用户消息）再调 → 断言计数已清零、不再阻断**
- **依赖**：无
- **工作量**：1–3 天

### T-D8 不可信包裹空转（有调用点但永远返回原值）

- **缺陷**：`isUntrustedTool` 只认 `web_*`/`browser_*`/`mcp_*` 前缀，而真实外部工具注册名是 `brave_*`/`github_*`（`src/mcp/tool-registration.ts:34,60`）→ `wrapUntrustedResult` **有调用点但永远返回原值**；另有 in-band 绕过：`tools.ts:309` 内容含 `<untrusted_tool_result` 字面量即跳过包裹
- **判据**：**C**（安全机制形同虚设）
- **修复方向**：前缀判据改为**按连接器/MCP 来源**判定（而非硬编码前缀）；in-band 绕过改为**转义**而非跳过
- **落地位置**：`src/agent/tools.ts:301-327`、`src/mcp/tool-registration.ts:34,60`
- **方式**：自建
- **验收**：① 注册一个 `brave_search` 工具 → 断言其结果**被包裹**；② 构造内容含 `<untrusted_tool_result` 的结果 → 断言**仍被包裹**（或字面量被转义）
- **依赖**：无
- **工作量**：1–3 天

### T-D9 工具调用/结果不入日志（事后无法回答"它当时调了什么"）

- **缺陷**：`tool.executed` 只记 `{toolName, success}`，**无 callId / 入参 / 结果**
- **判据**：**C**
- **对照**：DSH 有 `tool/call` + `tool/result` + `sourceEventSeqs`（`dsh-agent-loop:685-711`）
- **修复方向**：事件补 `callId` / 入参摘要 / 结果摘要（**注意与 T-D2 的 schema 变更合并**）
- **落地位置**：`src/agent/tool-loop-executor.ts`、`src/store/session-store.ts`（事件类型）
- **方式**：**①范式复用**
- **验收**：① 跑一次含工具调用的对话 → 断言日志中有 callId 与入参；② 由 callId 能关联到对应结果
- **依赖**：与 T-D2 合并（同一 schema 变更）
- **工作量**：3–10 天（含 schema）

### T-D10 重试事件从不落盘

- **修复方向**：**二选一** —— ①**删除**（避免审计时被"存在即生效"误导）；②**改为组 5b 调用它**（去重、单点维护）。**不要留两个实现**
- **验收**：断言只有一处 engine-core 桥接检测逻辑；且故意造一个桥接文件 → 断言 **pre-commit 拦住**
- **工作量**：**1 天以内**

## 七、⚠️ 复核中的重大发现：门禁**已有**「接线完整性」检查，但判据抓不到这一类

> 本节是复核过程中最有价值的发现，**它同时纠正了我此前一个说法**（我说过"没有机制能发现这类缺陷"——更准确的表述在 7.3）。

### 7.1 事实：组 4 存在，而且它就是做这件事的

`scripts/pre-commit-check.sh` 的 **13 组门禁里，组 4 就叫「接线完整性」**（原 5、11 合并）：

| 子项 | 实现 | 判据 |
|---|---|---|
| **4a. 新 export 被引用** | `grep -rn "\b${name}\b" src/`，排除 `.test.` 与自身 | **"符号在 src/ 里出现过吗"** |
| **4b. 接线深度：import 了但从未调用** | 只在 **`src/server.ts` / `src/index.ts` / `src/agent/synova-agent.ts` 三个文件**里 grep 是否有**调用点**（非 import） | **"这 3 个入口里调过吗"** |

**且脚本自己写明了这个简化**（`:655-657` 原文）：
> *"V3.8 简化: bash 只验证'被引用'这个物理事实"*
> *"Anthropic 原则: bash 退回到物理事实——'这个符号在文件外部出现过吗？'；**调用链正确性、分阶段接线 → agent 自检和 plan.json 负责**。"*

### 7.2 为什么它抓不到今天的 8 个缺陷（逐项对照）

| 缺陷 | 4a 结果 | 4b 结果 | 漏过的原因 |
|---|---|---|---|
| **P0-1** `tools` 未进请求体 | ❌ 通过 | ❌ 通过 | `toOpenAITools` **确实被引用了**（`tool-loop-executor.ts:62`）→ 4a 满足；而 4b 只看 3 个入口文件，**`tool-loop-executor.ts` 不在其中** |
| **P1-A7** 韧性层零生产调用 | ❌ 通过 | ❌ 通过 | 4a 排除了 `.test.`，但**只被测试引用**的情形 4b 覆盖不到（它只查那 3 个入口） |
| **P1-1** 压缩不入日志 | ❌ 通过 | ❌ 通过 | 压缩逻辑**被调用了**（`conversation-engine.ts:394-399`）——**问题是它没传 `onEvent`**，属"调用点的参数缺一项"，**任何 grep 判据都看不见** |
| **P1-2** 删会话不删报告 | ❌ 通过 | ❌ 通过 | `deleteDiagnosisCheckpoints` **存在且被 export**，只是**没有调用者** → 4a 会报？**不报**，因为符号名在 `session-store.ts` 外部出现过（测试里） |

### 7.3 结论（修正我此前的表述）

> **不是"没有机制"，而是「有机制（组 4），但判据类型不对」。**
> **`grep` 判据在原理上分不清「被引用」与「生效」**，而今天的 8 个缺陷**全部**是"被引用了、或注释声称了，但引用处没生效 / 参数缺一项 / 只被测试引用"。

**而且项目已经意识到 bash 的局限**（注释自陈"调用链正确性 → **agent 自检**和 plan.json 负责"）——
**但"agent 自检"是约定型的**（依赖执行者遵守），这正是今天 8 个缺陷漏过去的通道。

### 7.4 一个必须说清的精细区分（方法论级）

**同一个 grep 手法，在两组门禁里的有效性完全不同**：

| 用于 | 例子 | 有效性 |
|---|---|---|
| **检测「不该存在的东西是否存在」** | 铁律 46/47：桥接文件检测（`grep "engine-core"`） | ✅ **有效** —— 桥接文件的特征就是"import 指向 engine-core"，**出现即违规** |
| **检测「该生效的是否生效」** | 组 4：接线完整性（`grep 符号名`） | ❌ **无效** —— "符号出现过"与"符号被正确使用"是两件事 |

> **→ 这就是为什么 engine-core 防回潮门禁（组 5b）有效，而接线门禁（组 4）失效** —— 不是执行力度问题，是**判据适用性问题**。
> **可派工的推论**：**凡是"该生效"类的检查，判据必须是运行时断言（不变量），不能是 grep。**

### 7.5 对「第 0 项 + P0-4」的论证强化（这是本节的目的）

**此前的论证**：需要一个机制来发现"写了没接上"。
**现在的论证（更强）**：
> **项目已经尝试过用 grep 做接线检查（组 4，两层）；它抓不到，且项目自己承认把"调用链正确性"交给了"agent 自检"（约定型）。**
> **而约定型会被绕过 —— 今天有 8 个实例。**
> **所以「运行时不变量 + 穿生产入口的验收」（第 0 项 + P0-4）不是锦上添花，而是被现有门禁的失效所证明的必需品。**

**具体到 P0-4 的第一条不变量，照 DSH 的形状**（基础设施层已取证）：
> `dsh-agent-loop/lib/invariant.js`（42 行）在 `llm/stream` 上比对「**发出去的请求 == `session.deriveMessages()` 从日志重建出的请求**」
> —— **这条断言若已存在，P0-1 不可能发生**（因为 body 少了 `tools` 会立刻不相等）。
