### 2. 借鉴什么

**(a) API 形状：`register(包名, installer)`，归因用完整 npm 包名。**

```js
// dsh-invariants/lib/index.js:80-82
register(packageName, installer) {
  if (packageName.length === 0 || packageName.trim() !== packageName || /\s/.test(packageName))
    throw new Error("invariants: packageName must be non-blank and contain no whitespace");
  if (this.registrations.has(packageName)) throw new Error(`invariants: package "${packageName}" is already registered`);
```
installer 的签名是 `(ctx, fail) => void | Promise<void>`（`lib/types/index.d.ts:27-37`），`fail` 是**已经绑定了归属**的报告函数：

```js
// dsh-invariants/lib/index.js:92-94
const installInvariant = (childCtx) => installer(childCtx, (message) => {
  throw new InvariantError(packageName, message);
});
```

```js
// dsh-invariants/lib/index.js:12-27
var InvariantError = class extends Error {
  code = "INVARIANT";        // ← 稳定机器码
  packageName;               // ← 完整 npm 包名
  constructor(packageName, message) {
    super(`invariant violated by "${packageName}": ${message}`);
    this.name = "InvariantError";
    this.packageName = packageName;
  }
};
```

**要点：归属不是「顺手加的参数」，而是类型上的一等公民**——`InvariantFailure` 的类型是 `(message: string) => never`（`index.d.ts:25`），**报告即必抛，没有「只记一笔」的返回路径**。

**(b) 注册生命周期：子作用域 + 失败原子回滚。** `dsh-invariants/lib/index.js:88-114`：启用时在子 fiber 里跑 installer（`:96`），子插件失败 → `await child.dispose()` 后重抛（`:99-102`）；注册被拒 → 名字保留被原子收回（`:110-113`）；返回的 disposer 同时管注册与保留（`:103-109`）。**「损坏的检查不允许留下半截监听器」**这条纪律值得照抄——我方若把不变量写成裸 `if (x) throw` 散在业务代码里，就不会有这个性质。

**(c) 开关与过滤器在启动时编译一次，非法条目直接启动失败。** `lib/index.js:29-41` `compilePatterns`：空串、带首尾空白、重复、非法正则 → **抛错**（不跳过）；`:67-71` `selected()` 三态（`enabled` → allowlist 命中 → blocklist 排除，blocklist 优先）。**非法配置不允许被静默跳过**。

**(d) 失败姿态：fail-closed（同步抛），且 DSH 用一个专门的分发模式保护它。**
- `fail()` 直接 `throw`（`:92-94`）。
- cordis 的 `emit` 是**同步 map**：`cordis/lib/index.js:281` `this.dispatch("emit", args).map((cb) => cb(...args));` → 同步 listener 里抛出的 `InvariantError` **会冒到 emit 的调用方**。
- 但 DSH 有若干「容器化 fan-out」的 seam（凭据、设置、LLM 流、tool 提醒等），它们**主动吞掉常规异常、唯独放行 `code === 'INVARIANT'`**。实测全树 **14 处**：

```
./dsh-credentials/lib/types/index.js:160        ./dsh-settings/lib/types/index.js:556,612
./dsh-credentials/lib/index.js:144              ./dsh-settings/lib/index.js:540,578
./dsh-authorization/lib/types/index.js:205      ./dsh-settings-file/lib/index.js:234
./dsh-llm/lib/types/index.js:254                ./dsh-llm/lib/index.js:1783
./dsh-repeat-tool-reminder/lib/index.js:789     ./dsh-tmux-context/lib/index.js:790
./dsh-credentials-local/lib/index.js:702
```

完整形状见 `dsh-credentials/lib/types/index.js:147-169`：

```js
fanOut(event, subject) {
    let invariantFailure;
    const args = [event, subject];
    for (const listener of this.ctx.events.dispatch('emit', args)) {
        try {
            const returned = listener(subject);
            if (returned != null && typeof returned.then === 'function') {
                void Promise.resolve(returned).then(undefined, (error) => {
                    this.warnListenerFailure(event, subject, error);   // ← 异步失败：只 warn
                });
            }
        }
        catch (error) {
            if (error?.code === 'INVARIANT') { invariantFailure ??= error; continue; }  // ← 放行
            this.warnListenerFailure(event, subject, error);
        }
    }
    if (invariantFailure !== undefined) throw invariantFailure;   // ← 全部 listener 跑完后重抛
}
```

**所以精确的失败姿态是：`INVARIANT` = 「不可吞」标记 → 归属操作 fail-closed；常规监听器异常 → 容器化只 warn（不污染已提交操作的结局）。**

**(e) 最重要的一条：DSH 的断言对象是「真实事件流上的持久关系」，不是「函数有没有被调用」。** `dsh-agent-loop/lib/invariant.js` 全文的判据只有一句是本质的：

```js
// dsh-agent-loop/lib/invariant.js:24-25
const expected = session.deriveMessages();
if (JSON.stringify(options.messages) !== JSON.stringify(expected))
  fail(`llm request for session "${String(session.id)}" diverges from the dispatch-time durable derivation (log-reconstruction desync)`);
```

**它验证的是「发出去的请求 == 日志能重建出的请求」。这正是我方 P0-1 事故（工具 schema 从未进请求体）需要的那个断言——它不可能靠 grep 通过，因为它比的是运行时的两个真实值。**

配套的前置断言同样值得抄（`:18-22`）：请求必须被 `Object.isFrozen`；必须带 `sessionId`；`sessionId` 必须指向**活着的** session；`messages` 必须是冻结数组。这些都是**便宜的、每次调用都跑的**结构断言。

**(f) 显式声明「不检查什么」比检查什么更重要。** `dsh-credentials/lib/invariant.js:13-19` 的 docstring：这条不变量**只**检查「提交事件不能在服务已死之后发出」，而「`describe` 与 `resolve` 是否一致」明确**排除**（那是异步 provider I/O，归各 provider 自己的测试）。**这条纪律直接对我方有用**——我方过去的失败模式之一就是「断言写得太宽 → 经常误报 → 被人关掉」。

**(g) 装配是可读的一等公民。** `dsh-sdk-minimal/cordis.patch.yml:104-118`：注册表 + 4 个核心伴生（`dsh-session/invariant`、`dsh-agent/invariant`、`dsh-scope/invariant`、`dsh-agent-loop/invariant`）作为 5 条独立条目列出，且注册表条目**在伴生之前**（`dsh-sdk-minimal/cordis.patch.yml:104-118`）。「一个组合里到底开了哪些不变量」是可以在配置文件里一眼看全的。

### 5. 方式判定

**①范式复用（读源码自研，零依赖）。**

理由三条：
1. **代码量极小**：`dsh-invariants/lib/index.js` 123 行，其中真正是「注册表逻辑」的约 `:43-121`（79 行），再去掉 cordis 的 `Service`/`ctx.effect`/`ctx.plugin` 调用（`:60,88,96`），净逻辑约 40 行。重写成本 < 引入依赖成本。
2. **G1 守卫**：②包复用需要创始人豁免 G1。而 `dsh-invariants` 的 peer 是 `@deepseek-ai/cordis`（`package.json` peerDependencies），复用必然把 cordis 拖进来 → 不是「一个小依赖」，是**一个插件框架**。豁免的代价远超收益。
3. **私有化/数据不出域**：不变量断言会读到会话内容与请求体。DSH 的实现里有 `ctx.logger`、cordis 的事件总线——这些都是「外部框架掌握我方内部数据流」的形态。自研可以让断言**永不落盘内容**（只落 owner + 计数 + 脱敏摘要）。

### 6. 验收标准

**总纪律：全部穿过真实生产入口（`src/server.ts` 启动的进程 + `POST /api/conversations/:id/messages`），不接受 grep。**

| # | 验收项 | 判定方式 | 反例（必须不做的事） |
|---|---|---|---|
| 1-a | **负向：不变量能真的拦住** | 在一个专用分支上注入一次违规（让 provider 组装请求时丢掉 `tools`）；打一次真实对话请求。**判定：该请求返回 5xx，且响应体/日志含 `invariant violated by "llm.agent-loop":`**（含 owner 名） | 不许出现「返回 200 但日志里有 WARN」——那就是 fail-open，不算通过 |
| 1-b | **正向：不误报** | 正常一轮对话 + 一次真实工具调用（打真实 provider，走 `POST /api/conversations/:id/messages`）。**判定：200，且 `GET /healthz` 的 `invariants.lastFailure === null`** | 不许出现「为了不误报把断言关掉/放宽到恒真」——已有前车之鉴（`代码质量对比/LLM基础设施层-自研vsDSH.md` 记录 1 处恒真断言） |
| 1-c | **反接线探针（专治三次事故）** | `GET /healthz` 返回 `invariants.registered >= 3`；且每条不变量有 `hitCount` 计数器。**判定：跑完 1-b 之后至少 3 条不变量 `hitCount > 0`** | 若 `registered == 0` 或全部 `hitCount == 0` → **启动即失败**（照 `dsh-invariants/lib/index.js:63-64` 的「非法配置不跳过」姿态） |

### 2. 借鉴什么

**(a) 定位：「库而非插件」——因为传输策略每个进程只有一个答案。**
`lib/types/index.d.ts:9-12`：
> "This is a library, not a plugin: transport policy has one answer per process, so there is nothing for a composition to mount, swap, or scope."

**这条判定对我方直接有用**：不要把代理做成一个可插拔的 provider，做成启动期一次解析的进程级策略。**导出只有 4 个函数**（`index.d.ts:14`）：`installProxyFromEnvironment` / `proxyRouteFor` / `proxyEnvironmentForChild` / `clearedProxyEnv`。

**(b) 单一答案源：一个 `proxyForUrl(policy, url)`，dispatcher 的 factory 也调它。**
```js
// dsh-http-proxy/lib/index.js:390-392
return new Agent({ factory(origin, options) {
    const proxy = proxyForUrl(policy, new URL(origin.toString()));
    ...
```
`policy.d.ts` 的 docstring 把动机写得很清楚：「the single answer both the installed dispatcher and `dsh-web-fetch-http` consult, so a URL can never be pinned to a resolved address by one and tunnelled by the other」。**这条是「两处解析漂移」的根治方案**——我方现在恰恰是零解析，一旦引入就极容易写成两处（一处判要不要代理、一处真的连），必须一次写对。

**(c) 解析顺序（含 Node/undici 都不推导的那一条）。** `policy.d.ts` 的 `resolveProxyPolicy`：**scheme 自己的变量 → `ALL_PROXY` → （仅 HTTPS）回退到 HTTP 代理**。README.zh 补了关键一句：「其中第一条 Node 与 undici 都不会自行推导」。大小写策略：**小写优先、大写兜底，空值视为未设置**（`POLICY_ENV_NAMES`，`policy.d.ts`）。

**(d) loopback 用「整网段判定」，不是列表匹配。**
```js
// dsh-http-proxy/lib/index.js:19-24
const LOOPBACK_NO_PROXY = ["localhost", "127.0.0.1", "::1", "[::1]"];
```
但 `isLoopbackHost()`（`:198-203`）额外覆盖 `*.localhost`、`::`、`0.0.0.0`，以及**整个 `127.0.0.0/8`**（`:186` 注释 + `:195` 说明：「四个字面量条目匹配不到 `127.0.0.2`、`127.0.0.0/8` 的其余部分、以及 IPv4-mapped 写法」）。`::1` 与 `[::1]` **两个都列**，因为「undici 的匹配器把裸 `::1` 读成 host `:` port `1`，因此永不绕过」（`:16-17`）。**我方有 electron + 本地 server + 一堆 `BASE` 指向 localhost 的工具（`src/tools/*.ts` 大量 `${BASE}/api/...`），这条直接防回环。**

**(e) CIDR 不支持，必须改写成后缀形式。** `policy.d.ts` 的 `bypassesProxy` docstring：「CIDR notation is not matched — an operating system's bypass list often carries `10.0.0.0/8`, which must be rewritten as suffixes」。→ **客户给一份含 CIDR 的 `NO_PROXY` 时，我方要么先改写、要么明确报错，不能静默不匹配。** DSH 选了「静默不匹配 + 文档说明」，我方在私有化场景下应更严（见「不借鉴」）。

**(f) 不可用值 → 报告并降级，不阻止启动。**
```js
// dsh-http-proxy/lib/index.js:44-52（拒绝清单：socks/socks4/socks4a/socks5/socks5h）
// :99  kind: "socks"
```
README.zh「失败处理」：「该变量可能是用户为其他工具导出的，不应因此阻止 agent 启动」。**这条我认同且要抄**——但要用**告警 + 健康检查暴露**而不是静默（见第 6 项验收）。

**(g) 子进程环境：用户原样写的值要还原，未指定的 scheme 才带解析值。** `proxyEnvironmentForChild()`（`install.d.ts`）：README.zh「设计理念」第 2 点解释了动机——「用户为 `curl` 设置的 SOCKS 代理绝不会被替换成为其他 scheme 指定的 HTTP 代理」；而「两种大小写都未指定的 scheme 则携带解析值，否则子进程的路由会与父进程分歧：Node 的 `NODE_USE_ENV_PROXY` 不读 `ALL_PROXY`」。**还有一条极细的保护**：当子进程收到的某个值是本包拒绝过的（例如留给 curl 的 SOCKS URL）→ **不再设置 `NODE_USE_ENV_PROXY`**，因为「Node 在该标志下会在运行程序之前先解析 `HTTP_PROXY`/`HTTPS_PROXY`，遇到这类值直接退出」→ 宁可不代理也要让子进程能起来。

**(h) dispose 的语义不算计：关 dispatcher 用 `close` 而不是 `destroy`**，让已派发的请求跑完（`install.d.ts` 的 `ProxyRoute` docstring）。

### 2. 借鉴什么

**(a) 两个不相交的键空间——这是整个设计的支点。**
`dsh-credentials/lib/types/types.d.ts:11-46`：
- `CredentialRef` = 品牌化的 **POSIX 环境变量名**（如 `DEEPSEEK_API_KEY`）。回答「这个变量名背后是什么」——**可分层**：进程 env > provider-managed store > `.env` 文件。
- `CredentialKey` = 品牌化的 `<scope>/<id>`（如 `llm-pi-ai/openai-codex`）。回答「这个插件为这个 id 持有什么凭据」——**不可分层**，因为「授权 grant 没有环境可读」。存在性就是全部事实。

docstring 解释了为什么 scope 是**所有者**而不是域：「两个服务于同一 provider 名的插件会互相读到对方的 payload，而未安装插件留下的记录无法与活的分辨」。

**(b) seam 只暴露「值以外」的一切——结构上不给值留有位置。**
```ts
// dsh-credentials/lib/types/index.d.ts
export interface CredentialRecordInfo {
    configured: boolean;            // 是否已存
    kind?: CredentialRecord['kind']; // 'api-key' | 'grant'
    writable: boolean;               // modifyRecord 现在能否成功
}
```
`CredentialInfo` 的 docstring：「The view has no slot a value could ride in, which is what lets the whole read half cross the Remote wire.」（`index.d.ts` 内）。**这不是「约定不要返回值」，是类型上放不下值。**

**(c) 轮换语义 = 每次操作重新 resolve，消费者禁止跨操作缓存。**
`index.d.ts` 的 `resolve` docstring：
> "Resolution is per call: consumers re-resolve at each operation and must not cache across operations — that per-operation read is what makes a changed credential reach the next operation without a restart."

README.zh:91 说得更直白：「需要该密钥的请求使用它当前存储的值，因此轮换密钥会作用于紧随其后的下一次请求——无需重启，无需改配置。」
**这是本项对我方最重要的知识**：轮换不是「定时刷 token」的复杂机制，而是**「不要缓存」这一条纪律 + 一个 per-call API**。

**(d) 唯一写路径 `modifyRecord(key, mutate)` = 跨进程串行化的 read-modify-write。**
```ts
/**
 * Serialized read-modify-write over one record — the only write path.
 * `mutate` sees the record as it stands at the moment the write is exclusive...
 * Exclusion holds across processes where the backing store supports it, which is
 * what makes a token refresh safe: two processes rotating one refresh token
 * concurrently would otherwise lose whichever wrote first.
 */
abstract modifyRecord(key: CredentialKey, mutate: (current: CredentialRecord | undefined) => Promise<CredentialRecord | undefined>): Promise<CredentialRecord | undefined>;
```
实现（`dsh-credentials-local/lib/index.js:549-560`）：
```js
return withFileLock(this.spec.filename, async () => {
    await this.reconcileFromDisk();
    const current = this.records.get(key);
    const next = await mutate(current);
    if (next === undefined) return current;
    ...
    await writeFileAtomic(this.spec.filename, nextText, { mode: 384, dirMode: 448 });  // 0o600 / 0o700
```
**为什么我们缺这一条很重要**：我方 `src/agent/atomic-write.ts` 有 `.tmp → rename`（`:52,89`）**但没有文件锁**（实测 `grep -n "lock\|flock\|O_EXCL" src/agent/atomic-write.ts` 只命中 `rotateBackups` 与 `.tmp`）。多进程/多实例下凭据写入是 last-write-wins。

**(e) 磁盘安全：明文但权限 fail-closed。** `dsh-credentials-local/lib/index.js:90-107`：
```js
async function assertOwnerOnly(filename) {
    let mode;
    try { mode = (await stat(filename)).mode; }
    catch (error) { if (!isENOENT(error)) throw error; await canonicalizeWatchPath(filename); return; }
    if (process.platform === "win32") return;

```
**「启动时检查权限，不合格就拒绝启动，并给出可执行命令」**——这是私有化交付里最有用的一个姿态。写入侧 `mode: 384 / dirMode: 448` = `0o600` / `0o700`（`:557-559, 574-583, 620-623`）。

**(f) 外部编辑热重载 + 解析失败不回显敏感内容。** `chokidar` 监听（`:447-469`）；YAML 解析错误的处理有一条很细的讲究（`isENOENT` 附近）：「Describe one YAML parse failure without quoting the source. The parser's own message embeds the offending line, which here holds a secret.」→ **只报错误码 + 行列，不报原文**。

**(g) 未提交不通知 + INVARIANT 放行。** `notifyUpdated` 的 docstring：「Providers call this only after the write or reload actually committed, so a broken observer can never make a durable change look failed.」+ 第 1 项里的 `fanOut` 形状。

### 2. 借鉴什么

**(a) 「热生效 / 需要重启」是注册期的显式声明，并且向配置 UI 暴露。**
```ts
// dsh-settings/lib/types/index.d.ts:20
export type SettingsApplies = 'live' | 'restart';
// :66  SettingsDescriptor.applies: SettingsApplies;   // 「Owner's declared effect timing」
```
**这是本项最重要的知识。** 创始人说「客户自行改配置，不重启」——**技术上不可能做到所有字段都热改**（例如监听端口、数据库路径）。DSH 的答案不是「假装全都能热改」，而是**让每个字段的所有者声明 `applies`，并在配置 UI 上把这个声明显示给客户看**。**这条直接可以落地成产品行为：客户在 UI 上看到某个字段标着「需重启」，就不会改完发现没生效然后来投诉。**

**(b) `SettingsDescriptor` 把 `value` / `base` / `user` 三个视图分开，`user` 的存在性就是「被用户覆盖」的事实来源。**
```ts
// dsh-settings/lib/types/index.d.ts:49-73（节选）
export interface SettingsDescriptor {
    ns: SettingsNamespace;
    schema: unknown;                    // schema.toJSON()，给 UI 渲染表单
    value: unknown;                     // 当前解析结果
    revision: number;                   // ← 乐观并发
    base?: unknown;                     // 注册者的 composition 层（detached）
    user?: unknown;                     // ← 磁盘上的原始 user section
    applies: SettingsApplies;
    secrets?: RedactedSecret[];         // 仅在 redactSecrets 时出现
}
```
解析顺序明确写在 `index.d.ts:3-6`：**`schema defaults → registrant base → user document section`**。

**(c) 乐观并发：`revision` + `expectedRevision`。**
```ts
export declare class SettingsConflictError extends Error {
    readonly code = "SETTINGS_CONFLICT";
    readonly expected: number;
    readonly actual: number;
}
```
（`index.d.ts:117-136`）。**两个 UI / 两个进程同时改不互相覆盖**——这正是我方 `config-layers.ts` 缺的（它有 provenance，但没有 revision）。

**(d) 三种写形态 + per-namespace 串行化。** `update(patch)` / `replace(section)` / `mutate(ops: SettingsPathOp[])`（`index.d.ts:253-282`），后者的 `SettingsPathOp` 是 path-addressed edit（`:136-152`，`{path: readonly string[]}`）。docstring：并发更新**按调用顺序串行**（"concurrent updates apply in call order"）。

**(e) 跨字段校验独立于 schema，且「坏 section 保留上一次好值」。**
```ts
// dsh-settings/lib/types/index.d.ts:22-48（节选）
/**
 * Reject a resolved section the owner could not act on, for constraints its
 * schema cannot express — a cross-field requirement...
 * Throwing here refuses the *write* that produced the value, so a caller learns
 * at `update`/`replace`/`mutate` instead of storing something that would
 * silently disable the owner.
 *
 * Once the owner is registered, a stored section that fails this keeps the
 * namespace's last good value and warns, exactly as a schema failure does,
 * so an externally edited document cannot strand a running owner.
 */
validate?: (value: T) => void;
```
**「写入时拒绝；外部编辑时保上一次好值 + warn」——两种入口两种姿态，这个区分是私有化交付的关键**（客户会绕过 UI 直接改文件）。

**(f) 密钥脱敏：schema 驱动 + 侧车。** `lib/types/redact.js:1-6` 的模块 docstring + `:80-84` 的 `redactSecrets(schema, value)` 返回 `{value, secrets}`；`RedactedSecret = {path, set}`（`:20-22` 附近）。walker 只递归 `object`/`dict`/`array`（`:23-58`）。配置 UI 拿到的是「某个路径上有没有值」，可以渲染 write-only 输入框而**永远拿不到值**。

**⚠️ 同处有一个 DSH 自己写明的缺陷，我方必须补上**：
```js
// dsh-settings/lib/types/redact.js:56-59
default:
    // TODO(settings-wire-redaction): Fail closed instead — a secret reachable
    // only through a union, intersection, or transform is returned verbatim
    // here, with nothing recording that it was missed.
    return value;
```
**union / intersection / transform 里的 secret 会原样穿过，而且没有任何记录说它被漏了。** 我方要做成 **fail-closed**：遇到未知容器类型 → **抛错或返回一个「不可渲染」标记**，绝不放行。

| # | 验收项 | 判定方式 |

| 4-a | **热生效（不重启）** | `PATCH /api/config/<ns>` 改一个 `applies: 'live'` 且**有可观测行为差**的字段（例如某个工具的 `maxInlineBytes`、或某个 connector 的超时）。**判定：同一进程，下一次真实业务请求的行为按新值变**（用行为差断言，不许读内存变量） |

### 2. 借鉴什么

**⚠️ 首先必须挑明一个判定（这是本项最关键的一句话）：**

**`dsh-webhook` 是「入站（收 webhook）」，不是「事件订阅（发出）」。**
- `lib/types/index.d.ts:1` 的模块描述：「Fire-and-forget webhook rule registry and Workspace-backed Session runtime.」
- `lib/types/index.d.ts` 的 `WebhookRuntime`：**只有两个公开方法** —— `register(rule)`（`:23`）与 `dispatch(delivery)`（`:31`，「Start every currently matching rule and return **before any callback settles**」）。
- `lib/types/types.d.ts` 的 `WebhookRule.run(delivery, signal)` → `WebhookSessionRequest | null`；`VerifiedWebhookDelivery` 含 `receivedAt: number`（**Host 接收时间**）。
- `index.d.ts:11`：「Session creation is the only built-in action.」

**结论：DSH 侧没有出站事件订阅/投递保证机制。** 我方要的「事件订阅」如果指的是「把系统内的事件推给客户的系统（飞书/钉钉/邮件/自建 webhook）」，**DSH 无对应物**，属 **③自建**。所以本项应拆成 **5a（入站验签 + 事件路由，可借鉴 DSH）** 与 **5b（出站订阅/投递保证，自建）**。**这一条请 CTO 直接据此拆单，不要合成一个任务。**

**(a) 「已验证」是类型上的事实，不是注释。** 规则收到的参数类型**就叫** `VerifiedWebhookDelivery<K>`（`types.d.ts:9-20`），`WebhookRule.run(delivery: Readonly<VerifiedWebhookDelivery<K>>, ...)`。**验签不可能被忘记，因为类型上给不出别的形状。** 这条直接对应我方事故类型（机制存在但没接线）：**把「必须做的事」编码进类型，而不是写进文档。**

**(b) provider-neutral 运行时 + provider-specific 适配器两层。**
```ts
// dsh-webhook/lib/types/types.d.ts:2-3
/** Provider adapters add their normalized event type through declaration merging. */
export interface WebhookEventMap {}
```
运行时不认识 GitHub；GitHub 的认识全在 `dsh-webhook-github` 里（`Config` 的 `source`/`path`/`secretEnv`/`maxBodyBytes`，`lib/index.js:161-166`）。

**(c) 三个 brand 类型防串用，且**不假装去重**。** `lib/types/brand.d.ts`：
```ts
export type WebhookRuleId = Branded<'WebhookRuleId'>;
export type WebhookSourceId = Branded<'WebhookSourceId'>;
/** Identifies one provider delivery. The runtime assigns no deduplication semantics. */
export type WebhookDeliveryId = Branded<'WebhookDeliveryId'>;
```
**「runtime assigns no deduplication semantics」是诚实的设计**：重放同一 delivery 会**再次**运行规则（README.zh 明写：「`deliveryId` 仅是来源信息；重复交付会再次运行规则」）。**我方私有化交付下不能接受这一条**（客户会重放），所以这也是必须加严的点。

**(d) 验签全流程（`dsh-webhook-github/lib/types/handler.js`，逐条可抄）：**

| 步骤 | 代码位置 | 姿态 |
|---|---|---|
| 方法必须 POST | `handler.js:63-66` | 405 + `Allow: POST` |
| Content-Type 严格 `application/json`（可带 `charset=utf-8` 一个参数） | `handler.js:22-32, 67-69` | 415 |
| **先读有界 body，再验签** | `handler.js:70` + `body.js:20-50` | 见下 |
| 三个 header 都必须**恰好出现一次** | `handler.js:7-13` + `71-73` | 用 `request.headersDistinct[name]`，`values?.length !== 1` → 400 |
| secret 从凭据 seam 取 | `handler.js:74-77` | `ctx.credentials.resolve(config.secretEnv)`；缺失 → **503**（不是 401！） |
| 验签 | `handler.js:78-86` | `new Webhooks({secret}).verify(body, signature)`；异常被吞（"verification errors carry no response detail safe or useful to the sender"）；失败 → **401 且不回显原因** |
| 载荷解析 | `handler.js:36-51` | `JSON.parse` 单独 try；必须是非数组对象；必须能过 `snapshotJsonValue`（无损 JSON）否则 400 |
| 派发 | `handler.js:92-99` | `ctx.webhookRuntime.dispatch(delivery)`；失败 → 503 |
| 响应 | `handler.js:100` | **`respond(response, 202)`** —— 在**任何规则回调 settle 之前**返回 |
| 兜底 | `handler.js:101-110` | 未知异常 → **503 + 通用文案**（不泄漏内部） |

**(e) 有界 body 读入（`dsh-webhook-github/lib/types/body.js:20-50`）—— 这一段质量很高，值得逐条抄：**
- `Content-Length` 必须是严格十进制（`/^(0|[1-9]\d*)$/`）否则 400；超出上限直接 413 并 **`request.resume()`**（排干，不留半读 socket）。
- 流式累加，每块检查 `size > maxBodyBytes` → 413 + `resume()`。
- 流被中断 → 400「request body was aborted」。
- 用 `new TextDecoder("utf-8", { fatal: true })` —— **非法 UTF-8 → 400**（不是替换成 U+FFFD 后继续）。

**(f) `secretEnv` 在 schema 层就带着「这是引用不是值」的标记。**
```js
// dsh-webhook-github/lib/index.js:161-166

    source: z.string().required(),
    path: z.string().required(),

```
另有 `assertConfig`（`:168-171`）做 schema 表达不了的校验：`path` 必须是绝对、非根、无尾斜杠、无 query/fragment。

**(g) 规则回调用 `AbortSignal`，disposer 先隐藏再中止再排空。** `index.d.ts:20`「awaitable effect disposer that aborts and drains this rule's active callbacks」；README.zh：「注册是一项 effect。它的可等待 disposer 会先隐藏规则，再中止并排空活动回调。回调必须观察所提供的 signal；忽略取消的同进程代码无法被安全强制停止。」

### 5. 方式判定

| 子项 | 判定 | 理由 |
|---|---|---|
| 5a 入站验签 | **①范式复用** | 验签本体 20 行（`createHmac` + `timingSafeEqual`，我方 `auth.ts:193-198` 已有同型写法）；运行时语义（类型保证已验证、provider/适配器两层、brand 防串用）是**知识**；②包复用要拖 7 个 peer |

| 5b 出站订阅 | **③自建** | **DSH 无对应物**（实测确认：`dsh-webhook` 只有 `register`/`dispatch` 两个方法，都是入站方向）；且 DSH 明确不做重试/幂等/持久化——这三样恰是 5b 的全部内容 |

### 6. 验收标准

| # | 验收项 | 判定方式 |
|---|---|---|
| 5-a | **正签名 → 动作被触发** | 用真实 secret 算签名，`curl` 打 `POST /api/webhooks/:source` → **判定：202，且副作用可观测**（新建了待办/触发了诊断 run/写了一条会话）。**不许只断言状态码** |
| 5-b | **错签名 → 零副作用** | 篡改一个字节的签名 → **判定：401，且副作用计数为零**（查库/查待办列表）。**不许只断言 401** |
| 5-c | **重放幂等（我方加严）** | 同一 `source + deliveryId` 连打三次 → **判定：动作恰好执行一次**（DSH 明确不做这条，我方必须做） |
| 5-d | **超大 body** | 打一个超过 `maxBodyBytes` 的 body → **判定：413，且连接被正常关闭**（无半读 socket 泄漏；用 `ss`/`lsof` 或连接数断言） |
| 5-e | **secret 未配置 → 不降级** | 去掉 secret 配置 → **判定：503**；反例：**绝不能**降级成「不验签放行」 |
| 5-f | **非法 UTF-8** | 打一个含非法 UTF-8 字节的 body → 判定：400（不是替换后继续） |
| 5-g | **重名 header** | 打两个 `x-hub-signature-256` header → 判定：400（不是取第一个） |
| 5-h | **出站投递保证（5b）** | 目标端点先返回 500 两次再返回 200 → **判定：最终投递成功且有重试记录**；目标端点一直 500 → **判定：进死信表，不无限重试** |

## 缺口 6：超长输出 / 溢出处理

> **⚠️ 本项必须先建立的概念区分（任务明确要求）：`spill` 与 `output-retention` 是两个不同的机制，不是一个机制的两半。**

| | `dsh-output-retention` | `dsh-spill` 家族 |
|---|---|---|
| **是什么** | **一个库**（不是插件、不是服务） | **一个服务定义 + 一个后端 + 一个策略插件** |
| **解决什么** | 「什么留下了、什么漏了」——**工具输出的上限** | 「超长文本存到哪、怎么取回」——**溢出落盘** |
| **是否用 ctx/注册/发事件** | **都不用**。`lib/index.js:18-21` 明写："deliberately a library, not a cordis service or plugin: it takes no ctx, registers nothing, and emits no events" | 是：`ctx.spillStore` 服务 + `tools/post-execute` waterfall 监听器 |
| **输入/输出** | 喂 chunk/item → 出 `RetainedText{text,truncated,omittedBytes}` / `RetainedItems{items,truncated,seen,kept,omitted}` | 喂 `{owner, source, suggestedName, content}` → 出 `SpillRef{locator, bytes, retrievalHint}` |
| **谁知道业务语义** | **调用方**（工具自己）。DSH 明确：「file grouping, line numbering, exit codes, provider error states, per-line preview truncation, spill files, and the model-facing prose」全归工具 | 策略插件只管「什么时候 spill」；后端只管「存到哪」 |
| **是否改变模型看到的东西** | 不改变。它只报告 | **改变**：把模型可见结果换成预览 + notice |
| **谁负责降级** | 调用方 | 调用方（策略插件当尽力而为处理） |

**两者如何组合**：`dsh-spill-policy` 引用 `TextRetainer`（来自 `output-retention`）来生成预览（`dsh-spill-policy/lib/index.js:8` `import { TextRetainer, describeOmitted } from "@deepseek-ai/dsh-output-retention";`）。**即：retention 提供「怎么切」，spill 提供「切下来的存哪」。**

### 2. 借鉴什么

**(a) `output-retention` 的三个硬工程质量（可逐行照抄）：**

1. **按字节不按字符**：`TextRetainer` 的 cap 与 `omittedBytes` 都是**字节**（`lib/index.js:132-133`「Bytes, not characters: caps and `omittedBytes` are byte counts for process/body safety」）。
2. **UTF-8 边界修复 —— 绝不引入 replacement char**：
```js
// dsh-output-retention/lib/index.js:109-117
function trimTrailingPartialUtf8(bytes) {
    let i = bytes.length - 1;
    while (i >= 0 && (bytes[i] & 192) === 128 && bytes.length - i <= 3) i--;
    if (i < 0) return bytes;
    const lead = bytes[i];
    const expected = lead < 128 ? 1 : lead < 224 ? 2 : lead < 240 ? 3 : lead < 248 ? 4 : 0;
    if (expected === 0) return bytes;
    return bytes.length - i < expected ? bytes.subarray(0, i) : bytes;
}
// :122-126  trimLeadingContinuationUtf8 —— 去掉开头的 continuation 字节
// :225      只在实际发生截断时才修边界；未截断则原样解码
```
3. **有界内存**：`TextRetainer` 最多持有 `prefixCap + suffixCap + 一个 chunk`（`:136-137`）；后缀用滑动窗口，老 chunk 被丢弃（`:187-201`）。**大流不累积。**

**(b) 「漏了多少」必须是精确数，且类型上区分「精确」与「未知」。**
```js
// dsh-output-retention/lib/index.js:85-97（ItemRetainer.finish）
return {
    items: this.items,
    truncated,
    seen: this.seen,
    kept: this.items.length,
    omitted: truncated ? { kind: "exact", count: this.omittedCount } : { kind: "none" }
};
```
```js
// dsh-output-retention/lib/index.js:261-267
function describeOmitted(omitted, unit) {
    switch (omitted.kind) {
        case "none": return "";
        case "exact": return `Omitted ${omitted.count} ${unit}.`;
        case "unknown": return `More ${unit} were omitted.`;
    }
}
```
**`unknown` 这个 discriminant 是为「调用方没给数」准备的**——它让上层有机会诚实，也让「假装知道」在类型上不自然。**这一条对我方报告层的诚实标注纪律直接相关。**

**(c) `truncated` 的语义被严格定义，不被滥用。**
```js
// dsh-output-retention/lib/index.js:12-16
* In particular `RetainedText.truncated`/`RetainedItems.truncated` means "the retainer omitted
* otherwise-available content because of a budget" — NOT "the upstream was incomplete".
* Permission failures, skipped binaries, provider partial failures, and unreadable candidates
* stay in tool-domain fields, never folded into `truncated`.
```
**「预算导致的截断」与「上游本身就不完整」是两件事，不许混。** 我方 E5 已发现「准确率仅哨兵告警级有机制、诊断级无口径」——这种混同正是把三态压成两态的典型。

**(d) seam 边界写得极其清楚（`dsh-spill/lib/index.js:22-51`）：**
```js
* The Service Definition is deliberately minimal: `saveText` and nothing else. It owns NO
* retention policy (that is `@deepseek-ai/dsh-output-retention`), NO tool-result
* replacement (that is `@deepseek-ai/dsh-spill-policy`), and NO retrieval or
* search API.
...
* Semantics every implementation must honor:
* - `saveText` REJECTS on a real storage failure (permissions, ENOSPC, backend unavailable);
*   the caller decides how to degrade.
* - Storage is scoped by the request's owner session; the backend chooses a private (not
*   world-readable) location and a collision-free name derived from — never equal to — the
*   caller's `suggestedName`.
```
**「一个方法，别无其他」+「在 seam 处拒绝，绝不静默降级」+「降级是调用方的责任」——三条都是可以直接照抄到接口设计里的纪律。**

**(e) 后端的路径安全（`dsh-spill-local/lib/index.js:50-108`）—— 这一段是安全工程教科书级别：**

function encodeSegment(raw) {
    if (raw.length === 0) return "~";
    if (raw === ".") return "~002E";
    if (raw === "..") return "~002E~002E";
    let out = "";
    for (let i = 0; i < raw.length; i++) {
        const code = raw.charCodeAt(i);
        const ch = String.fromCharCode(code);
        out += ch !== "~" && /^[A-Za-z0-9._-]$/.test(ch) ? ch : "~" + code.toString(16).toUpperCase().padStart(4, "0");
    }
    return out;
}

| # | 验收项 | 判定方式 |
|---|---|---|
| 6-a | **模型面有界**（穿真实入口） | 构造必然 > cap 的真实工具结果（让某个工具读一个 5MB 文件）。**判定：在**假 provider** 侧抓真实出站请求体，该 tool 消息的字节数 ≤ cap + notice 长度**。⚠️ **必须抓真实请求体**（不是读内存变量），因为这一条同时是我方 P0-1 的对偶验证 |

### 2. 借鉴什么

**(a) 注入内容的确切形状（三行，`lib/index.js:148`）：**
```js
return `Time sampled while preparing turn ${turn}, step ${step}: ${formatTimestamp(now, formatter, timeZone)}\n${browserText}\nElapsed since the preceding ${baseline}: ${elapsed}.`;
```
- 行 1：**结构化的时间戳**
- 行 2：本次请求的时区策略
- 行 3：**距上一条的耗时，且明确写出基线是什么**（`baseline` 取值见上：step 1 是 `model-visible message`，后续 step 是 `step context`）

**「不写基线的时间差是无意义的」——这条纪律对我方报告层直接相关**（我方报告到处是「环比」，但基线的定义常常不写）。

**(b) 时间戳格式：ISO 形 + 数字偏移 + `[IANA]` 后缀，机器可解析。**
```js
// dsh-time-context/lib/index.js:68-86
function createTimestampFormatter(timeZone) {
    return new Intl.DateTimeFormat("en-US", {
        ...timeZone === void 0 ? {} : { timeZone },
        year: "numeric", month: "2-digit", day: "2-digit",
        hour: "2-digit", minute: "2-digit", second: "2-digit",
        hourCycle: "h23", timeZoneName: "longOffset"
    });
}
// :88-98
function formatTimestamp(now, formatter, timeZone) {
    const parts = Object.fromEntries(formatter.formatToParts(now).map((part) => [part.type, part.value]));
    const offset = parts.timeZoneName.replace(/^GMT$/, "GMT+00:00").slice(3);   // "GMT+08:00" → "+08:00"
    return `${parts["year"]}-${parts["month"]}-${parts["day"]}T${parts["hour"]}:${parts["minute"]}:${parts["second"]}${offset}[${timeZone}]`;
}
```
产出形如 `2026-09-19T02:06:00+08:00[Asia/Shanghai]`。**`[IANA]` 后缀是关键**：光有偏移无法区分「夏令时前后」与「不同时区恰好同偏移」。**我方报告要标「数据时点」，格式必须到这个颗粒度。**

**(c) 时区三分支 + `mixed` 时明确要求模型澄清。** `lib/invariant.js` 的 `deriveBrowserTimeZoneContext`：
```js
// 唯一的浏览器时区 → resolved
// 多个 → { kind: "mixed", timeZones: [...] }
// 没有 → { kind: "missing" }
```
```js
// lib/invariant.js 的 renderBrowserTimeZoneContext
case "resolved": return `Browser time zone for this request: ${context.timeZone}. Interpret otherwise-unqualified dates and times in this zone.`;
case "mixed":    return `Browser time zone for this request: mixed ${JSON.stringify(context.timeZones)}. Ask the user to clarify otherwise-unqualified dates and times.`;
case "missing":  return "Browser time zone for this request: unavailable. Ask the user to clarify otherwise-unqualified dates and times.";
```
**比默认套一个时区诚实得多。**

**(d) 时区值的严格校验（`lib/invariant.js:14-27`，也是 `lib/index.js` 里同一段逻辑）：**
```js
const IANA_TIME_ZONE = /^[A-Za-z][A-Za-z0-9_+.-]*(?:\/[A-Za-z0-9_+.-]+)+$/;
// 必须是 canonical UTC 或 IANA Area/Location
canonical = new Intl.DateTimeFormat("en-US", { timeZone: value }).resolvedOptions().timeZone;
if (canonical !== value) throw new TypeError(`browser time zone must be canonical: ${JSON.stringify(value)}`);
```
**注意最后的「canonical 必须与原值逐字相同」**——它挡掉了 `US/Eastern` 这类别名与 `asia/shanghai` 这类大小写变体。**这一条对「报告时区标注必须唯一确定」很有用。**

**(e) 每步注入 + `refreshIntervalMs` 降频。** `Config`（`lib/index.js:114-117`）：
```js
const Config = z.object({ timeZone: z.string(), refreshIntervalMs: z.number() });
```
README.zh：「正的 `refreshIntervalMs` 会抑制距最近一次注入不足该毫秒数的注入；省略或设为 `0` 时，每个信号尚未中止且将进入步骤的合格 pre-step 都会注入。」

**(f) 慢钟保护 + 紧凑时长格式。** `formatDuration`（`lib/index.js:119-133`）支持 `d h m s`；README.zh「模型能得到什么」：「缺少基线时报告 `unavailable`，挂钟时间倒退时把经过时长钳制为零」。

**(g) 它是可选插件（非默认）。** README.zh:12：「本插件需主动启用：默认组合不启用它」。→ **时间注入是「有成本的东西」（每步多一条 user 消息），不能默认开。** 我方若做，也要是可配的。

### 3. 不借鉴什么

### 2. 借鉴什么

**(a) 有界转换的完整设计（`dsh-office-to-pdf`）—— 这一块与 E5 的「成本要算到规模化」直接相关：**

`lib/types/queue.js`（245 行）的 `ConversionQueue`：
- `generation`：provider 生命周期标识，**引擎或字体被替换时旧 generation 全部作废**（`:90`）。
- 准入控制：`maxConcurrentConversions: 2`、`maxQueuedJobs`、`maxInputBytes: 52428800`、`maxOutputBytes: 104857600`（README.zh 配置表）。
- **前台/后台优先级**：`request.priority === "foreground"` 时可**移除排队的后台任务**腾位置（`:147-148`）；「只要仍有前台任务排队，后台任务就继续等待」（README.zh）。
- **按内容摘要共享转换**：`sha256(精确源字节)` 作 cache key，**跨不同源路径共享**（README.zh）。LRU 保留 8 个 PDF / 128 MiB / 64 个源别名。
- **最后一个读取方离开即释放**：同一源的最后一个读者离开时立刻释放在途定位信息。
- **取消是共享的**：最后一个读取方取消 → 取消共享工作；单个读取方取消只释放自己。

**我方适用点**：我方若做文档解析/转换，**必须**有这套（否则一个 500MB 的 PPT 能把服务打死）。**「按内容摘要共享」这一条对同一份客户材料被反复上传的场景特别有用。**

**(b) 输出校验（`lib/index.js:64-82`）—— 20 行，可以直接抄：**
```js
if (!(await lstat(path)).isFile()) throw new OfficeToPdfError("invalid-output", "The converter output is not a regular file.");
// ...
if (info.size > limit) throw new OfficeToPdfError("output-too-large", "The converted PDF exceeds maxOutputBytes.");
// :81
if (length !== info.size || !pdf.subarray(0, 8).toString("ascii").match(/^%PDF-\d\.\d/u) || !pdf.subarray(-1024).toString("ascii").trimEnd().endsWith("%%EOF"))
    throw new OfficeToPdfError("invalid-output", "The converter did not produce a complete PDF.");
```
**「文件头 `%PDF-x.y` + 文件尾 `%%EOF` 双向校验 + 大小与 stat 一致」——三段式。** 我方 `src/ingest/knowledge-ingest-bridge.ts:4` 声明了「PDF/DOCX/Excel 上传 → 自动解析」，但**没有这种校验**。

**(c) 错误码分类（`lib/types/errors.js`，14 行）：**`invalid-document` / `unsupported-format` / `input-too-large` / `output-too-large` / `invalid-output` / `timeout` / `unavailable` / `failed`。**「错误必须可分类」让人能区分「客户文件有问题」与「我们的服务有问题」——私有化交付里这个区分直接决定工单归谁。**

**(d) 「无效安装资源绝不启用回退」**：`lib/index.js` 附近 + README.zh「引擎元数据无效、必需资源缺失和转换错误会拒绝请求，不会切换引擎」。**「不静默降级到另一个引擎」——因为保真度差异会让客户看到不同结果。** 这条判定纪律值得抄到所有「有多个实现」的地方。

#### 结论层（对商业线判断的修正）

**修正 1：「源码可得性有瑕疵」这个描述对 C++ helper 层面不成立。**
`bin/libreoffice-kit`（93,600 字节的 Mach-O）的源（`worker.cxx`，10,545 字节）+ 编译命令（`build-helper.mjs`）+ 引擎 revision + 24 个 patch + 第三方许可文件**都在 tarball 里**。**MPL-2.0 意义上的「Corresponding Source」对这部分是做到了的。**

**修正 2：真正的问题收窄为两件具体的事，而不是「整体有瑕疵」。**
- **(i) `libreoffice-kit` 适配器自身的 `src/*.ts` 不在 tarball 里。** tarball 只有 `lib/index.js`（924 行 ESM JS）与 `lib/worker.js`（800 行 JS）——**对 JS 而言，「可直接修改的形式」是否等于「TypeScript 源」是一个判断问题，不是显然的违规**。MPL-2.0 定义 Source Code Form 为「the form of the work preferred for making modifications」；我**倾向**认为对 TS 项目而言 TS 源是首选形式，**但这条我标为「判断，非事实」**。
- **(ii) 履行 §3.2(a) 的「告知义务」依赖那个仓库可达。** 我**无法验证**它可达（F5）。**如果不可达，则义务无法履行**——这正是商业线担心的那件事，我认为**担心成立，但落点应该精确到「仓库可达性」这一条**。

**修正 3：MPL-2.0 是文件级 copyleft，不传染我方自研代码。** 我方自研代码不受影响（`dsh-office-to-pdf` 是 MIT；对 kit 是独立进程调用，不是链接）。**真正要做的只有两件**：(a) 在交付物里附 `NOTICE` + `licenses/`；(b) 写清「如何取得 Corresponding Source」（指向 LibreOffice core 的 revision + patch 集）。**而这两件事的可行性完全取决于 (ii)。**

**所以准确的判定是：不是「不能用」，而是「不必冒这个风险」**——见下替代方案。
