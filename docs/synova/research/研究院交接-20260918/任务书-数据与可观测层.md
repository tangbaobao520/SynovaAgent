### 2. 借鉴什么

**① 后端契约只有 `kv` 一个分面，没有 `log` 分面**——`dsh-storage/lib/types/backend.d.ts:15-24` 的 `StorageBackend` 只有可选 `kv?: KvFacet` 和 `close()`；`:79-88` 的 `KvUnit.loadAll()` 返回 `{ tables: Record<string, Record<string, unknown>>; global: unknown }`。**推断**：这正是"用 KV 冒充时序"的失败样本，恰好告诉我方不该走这条路——时序数据一旦塞进 KV，聚合查询就只能全表扫。

**② 写链模型（Per-domain write chain）**——`dsh-storage-domain/README.zh.md:88-89` 明确："内存具有最终决定权；介质是持久投影……每次写入都在每个领域一条的写入链上排队：先到达后端持久状态，再变更内存，然后发出 `domain/changed`；被拒绝的后端写入不会触碰内存"。**这是我要抄的核心**：我方指标写入应当有"先落盘、后改内存视图、再发变更事件"的三段顺序，而不是反过来。

**③ 原子发布协议**——`dsh-storage-json/lib/index.js:25-40`：
```js
async function writeAtomic(path, data) {
  const tmp = join(dirname(path), `.${randomUUID()}.tmp`);
  const handle = await open(tmp, "wx", 384);      // 0o600
  await handle.writeFile(data, "utf8");
  await rename(tmp, path);                         // 原子替换
  await fsyncDirectory(dirname(path));             // 崩溃可持久
```
`:42-46` 是 `fsyncDirectory` 的实现。**这是可迁移纪律**（虽然我方走 SQLite，但 rollup 落盘/导出文件仍会用到）。

**④ SQLite 侧的 schema 归属与派生索引纪律**（`dsh-session-query-sqlite/lib/index.js:41-118`）：`PRAGMA application_id` 认领数据库（`:53-57`）、未知用户表直接拒绝（`:74-77`）、schema 版本不符**原地重置派生表**（`:78-81`）、`PRAGMA user_version = 8` 作为版本断言（`:117`）。这套"派生索引可以被丢掉重建，权威数据不动"的定位，正好匹配指标 rollup 层。

### 3. 不借鉴什么

- **`kv` 唯一分面**：`dsh-storage/lib/types/backend.d.ts:26-39`——没有范围查询、没有二级索引、没有时间维度。当时序存储借鉴会踩空。
- **单根 `$DSH_HOME`**：`dsh-storage-json` 的 `root` 必需且**不回退到 `process.cwd()`**（`README.zh.md:36`），单部署根目录。我方多租户（`agent_sessions.org_id`，`session-store.ts:185`）需要按 org 隔离，不能单一 root。
- **单进程所有权**：`dsh-storage-json/README.zh.md:143` 明写"没有跨进程写锁"；`dsh-session-query-sqlite/README.zh.md:147` 明写"每个索引路径必须仅归一个进程中的一个服务所有"。我方有 `graceful-shutdown.ts` 与多实例部署路径，这条必须改。
- **无跨表事务/无二级索引/无多段键**：`dsh-storage-domain/README.zh.md:152` 把这三条列在"已知限制"。我方指标层必须自己定索引策略。
- **无数据迁移**：`dsh-storage-domain/README.zh.md:153`——"领域的已存版本与 spec 不同时打开被拒（`version-mismatch`），修改 schema 需要手工迁移"。这正是我们缺口 6 要单独解决的洞，不能指望存储层兜。
- **`single` 布局整单元重写**：`dsh-storage-json/README.zh.md:141` 自己承认"每次写入都重新发布完整单元文件"，并在"开发备注"里承认"第二个消费方以千条记录规模落到本后端，重写成本会比预期更早显现"（`:151`）。指标是高写入量场景，**必然踩这个坑**。

### 5. 方式判定

**③ 自建**（DSH 无对应）。

理由：DSH 全家族没有任何时序存储包（本文取证扫描了 `dsh-storage` / `dsh-storage-domain` / `dsh-storage-json` / `dsh-session-query-sqlite`，`kv` 是唯一分面，`dsh-storage/README.zh.md:131` 甚至把 `log` 分面列为"延期工作"）。**范式可借鉴（写链 + 原子发布 + 派生索引定位），数据模型必须自建。**

### 2. 借鉴什么

**① 8 个字段的口径定义（可直接抄的表）**——`dsh-session-stats/README.zh.md:40-47`：

| 字段 | 口径 |
|---|---|
| `turns` | 含至少一个已关闭步的不同轮次；被拒绝或空轮不计 |
| `steps` | 已关闭的步（完成/失败/取消/max-tokens 全计入） |
| `llmMs` | 组装出消息的步的模型墙钟时间之和 |
| `toolMs` | 匹配的 `tool/call` → `tool/result` 墙钟时间之和 |
| `ttftMs` / `ttftSteps` | 首 token 延迟之和及其承载步数 |
| `decodeMs` / `decodeTokens` | 上报用量的步的解码墙钟时间与提供方输出 token 之和 |

**② 折叠规则的关键选择：以 `step/end` 而非 `assistant/message` 计步**——`projection.js:6-11` 解释得很清楚："`step/end` 是步生命周期权威，循环对每个进入的步在 `finally` 里恰好追加一条，因此完成、失败、取消与 max-tokens 的步都会落地一条。若改按已组装的 assistant 消息计数，则会多算 max-tokens 的 usage 宿主消息（空内容、被排除在 surface 之外），并少算被取消的步（在消息组装前已中止）。" **这条推理对我方直接适用**——我方 `session_events` 目前没有 step 概念，抄这个口径的前提是先把 step 边界补上（见缺口 5）。

**③ usage 的防御式归一**——`projection.js:59-64`：
```js
function usageOutputTokens(usage) {
  if (typeof usage !== 'object' || usage === null) return null;
  const value = usage.outputTokens;
  return typeof value === 'number' && Number.isFinite(value) && value >= 0 ? value : null;
}
```

### 2. 借鉴什么

**① schema 的完整设计（可直接抄）**——`dsh-session-query-sqlite/lib/index.js:82-118`，三张表：`search_state`（单例 + `global_generation`，`:85-90`）、`persisted_sessions`（会话元数据 + `revision` + `generation`，`:92-104`）、FTS5 虚表 `persisted_docs`（`:106-116`）：
```sql
CREATE VIRTUAL TABLE IF NOT EXISTS persisted_docs USING fts5(
  text, session_id UNINDEXED, seq UNINDEXED, type UNINDEXED,
  time UNINDEXED, surface UNINDEXED, codepoint_length UNINDEXED,
  tokenize = 'unicode61'
)
```
**关键设计：元数据列用 `UNINDEXED`**——只存不建倒排，倒排只给 `text` 一列。这避免了"给每个过滤维度建一份索引"的空间浪费。`:119-147` 是连接本地 TEMP 表 `live_docs` 的同构 schema（实时数据遮蔽持久化基库）。

**② 字面短语即数据（防 FTS5 语法注入）**——`README.zh.md:90`："调用方查询文本被引成一个 FTS5 短语，查询语法保持惰性；保留高亮标记在索引前从文档中剥离。" 实现位置 `lib/index.js:283-291`（引成一整个 phrase + 剥离保留标记）。`:67` 还有谓词预算的显式拒绝（`> 14` 谓词或 `> 32766` 绑定即 `SESSION_QUERY_INVALID_FILTER`，`:159-168`），这是**防 DoS 的工程纪律**。

**③ 排序确定性**——`lib/index.js:826`、`:832-833`：
```sql
ORDER BY match_count DESC, document_length ASC, time DESC, seq DESC
LIMIT ? OFFSET ?
```
`README.zh.md:61` 解释："实际 FTS5 高亮匹配 span 更多的在前，然后文档更短的在前，事件时间、会话 id 与 seq 打破平局。" **不用 bm25（它不稳定），用可复现的四元组**——这个选择我方该抄。

**④ 世代绑定游标（宁可失败也不给错页）**——`lib/index.js:1063-1075`：游标 base64url 编 JSON，含 `version`/`instance`/`scope`/`fingerprint`/`offset`/`generation`；`:1070` 校验身份不匹配即 `INVALID_CURSOR`；`:1071` **generation 不符即 `SESSION_QUERY_STALE_CURSOR`**。`README.zh.md:89`："每次语料库变化都会递增世代；游标携带其创建时的世代，宁可陈旧失败也不返回偏移后的页面。" **这是分页正确性的正解**，比"用 offset 分页然后在数据变化时给出错页"强得多。

**⑤ 摘要按 Unicode 码点截断**——`lib/index.js:321-323`、`:894`，配置 `snippetChars` 默认 240 且"按 Unicode 码点计算"（`README.zh.md:50`）。我方是中文场景，`substr` 按字节截断会把汉字劈开（我方现状见下方第 2 问的反例）。

**⑥ 派生索引的自我认领与自愈**——`lib/index.js:53-61`、`:74-81`、`:117`：`application_id` 认领（1146308689）、未知用户表拒绝、版本不符**原地重置**、`user_version = 8` 作为断言。`README.zh.md:87`："FTS 行存放在专用可丢弃数据库中；这里的代码从不打开 session-persistence 数据库。"

### 3. 不借鉴什么

- **同步阻塞查询**：`DatabaseSync` 在 MATCH 期间阻塞 JS 线程且无法中断已运行语句（`README.zh.md:145`）。我方是 HTTP 服务 + 并发用户，不能照抄这个执行模型；但**我方 `better-sqlite3` 天生同步**（`package.json:58`），这条对我们是既有约束，需要在路由层做限流而不是在存储层解决。
- **单一所有者派生索引 / 不支持多进程**：`README.zh.md:147`。我方多租户部署下必须改。
- **"无调用方授权——这是上下文范围内的可信服务"**：`README.zh.md:144`。**我方绝对不适用**：多租户下搜索必须带 `org_id` 过滤，否则就是一个跨租户数据泄露洞。
- **`unicode61` tokenizer 不做中文分词**：DSH 自己承认"匹配 token 与短语，而非任意子字符串：`AI` 不匹配 token `BRAID`"（`README.zh.md:63`），并把 trigram 备选方案记为"经实测后被否决"（`:159`，理由是索引体积）。**但它否决 trigram 的前提是英文为主**——中文场景下这个否决不成立。
- **`dsh-session-query` 的 trace/readEvent 全套**（`lib/index.js:1177-1210`）：我方不需要"事件前后 N 条窗口读取"，那是为客户端分页服务的设计。

### 5. 方式判定

**① 范式复用**（读源码自研，零依赖）。

理由：DSH 的 FTS5 用法底层就是 SQLite 的 FTS5（我方已有 `better-sqlite3` ^12.11.1，`package.json:58`，**原生支持 FTS5 与 trigram tokenizer**）。DSH 的价值在**用法与纪律**（`UNINDEXED` 列、字面短语引号、确定性排序、世代游标、码点截断），这些是设计知识而非代码。**不选②**：`dsh-session-query-sqlite` 依赖 `node:sqlite` 的 `DatabaseSync`（`lib/index.js:50`）并挂 Cordis 生命周期，与我方 `better-sqlite3` 栈不一致，引包等于引第二个 SQLite 驱动。

## 缺口 6：会话格式迁移链

### 1. DSH 参考

### 2. 借鉴什么

**① 相邻迁移契约（这才是可迁移的核心）**——`types.d.ts:35-46`：
```ts
export interface SessionFormatMigration {
    readonly name: string;
    readonly fromVersion: number;
    readonly toVersion: number;
    /** Convert one header without reading event bodies. */
    migrateHeader(header: SessionFormatHeader): SessionFormatHeader;
    /** Create the stateful body stage for one source artifact. */
    createStage(input: SessionFormatMigrationStageInput): SessionFormatMigrationStage;
    /** Refuse any header that the adjacent target writer cannot emit. */
    validateTargetHeader(header: SessionFormatHeader): void;
}
```
四个要点：**① 只允许相邻版本（`fromVersion`/`toVersion` 差 1）；② header 迁移不需要读 body（`migrateHeader` 独立）；③ body 迁移是有状态 Stage（`createStage`/`transformEvent`/`finish`）；④ 迁移必须能拒绝它写不出的目标 header（`validateTargetHeader`）。**

**② 迁移链在构造时校验「唯一且无缺口」**——`dsh-session-format/README.zh.md:58`："迁移链在构造时校验唯一且无缺口的顺序。" **推断**：这排除了"V1→V3 直达但不覆盖 V1→V2→V3 中间态"这类漏洞。`types.d.ts:58-64` 的 `SessionFormatChainOptions` 只有 `currentVersion` / `migrations` / `restoreCurrentHeader`——**没有"跳级迁移"的入口**，从类型上就无法表达。

**③ 流式、不复制中间产物**——`README.zh.md:12`："一次还原会让调用方拥有的已解析值流经有状态 Stage，不复制或冻结中间产物。" `types.d.ts:108-113` 的 `SessionFormatMigrationContext` 是同步输出通道（`emitEvent` / `emitRun`）。**这是大日志（我方诊断会话可能上千事件）不爆内存的关键。**

**④ 可恢复解码策略是显式的、一次性选择**——`types.d.ts:74`（`SessionFormatRecovery = 'strict' | 'recoverable'`）、`:73-92`（`createDecoder(header, recovery)`）。`README.zh.md:48`："可恢复解码器返回已接受的逻辑前缀。编解码器可以丢弃一个格式错误或序号不连续的行及其未提交后缀，但**后续成功解码的 `turn/end` 会使原始问题成为致命错误**。" **"截断可以容忍，但轮次成功闭合就不能忍"——这条比"遇到坏行就抛"或"遇到坏行就跳过"都更精确。**

**⑤ 校验强度分级**——`README.zh.md:46`：`validation: 'current'`（执行所有已安装的 current 校验）vs `'transformed'`（历史迁移后执行已发布的校验）。**历史数据用历史校验器，当前数据用当前校验器**——避免"用新规则去判旧数据"的假阳性。

**⑥ 版本标识与文件命名规范**——`types.d.ts:10-20` 的 `SessionFormatHeader` 把 `version`/`id`/`createdAt`/`parentSession`/`isSeeded`/`delegationDepth`/`agentPreset` 一起定死；`dsh-session-format/lib/types/filename.d.ts` 是 `session[.vN].jsonl` 的规范命名。**注意 header 里带 `format_version` 并进入遥测属性**（`dsh-session-telemetry/lib/types/index.d.ts:68` 的 `session.format_version`）。

### 3. 不借鉴什么

- **物理层不属于这个库**：`README.zh.md:12` 明说"物理分帧、压缩、不可变 generation 命名、排他发布和 Cordis 生命周期行为不属于本库"。**我方是 SQLite 表不是 JSONL 文件**，整个物理层（分帧、generation、原子发布）都不适用。
- **最终当前历史仍常驻内存**：`README.zh.md:101`（已知限制）——"流式处理只保留有界中间状态，但返回的当前事件数组和必需的序号重映射表仍为 O(事件数)"。我方若在启动时全量迁移会占用可观内存。
- **仅支持相邻整数版本，不暴露 span / 稳定事件身份 / 通用引用重写代数**（`README.zh.md:102`）。我方的 `seq` 是每会话自增整数（`session-store.ts:219-223` 的 `UNIQUE(session_id, seq)`），跨会话引用（`parent_session`）的迁移它**明确不做**——我方若有跨会话引用必须自建。
- **它的迁移是"读时迁移"，不是"写时批量升级"**：`catalog.createRestore(physicalHeader, ...)` 在**读取时**把旧格式转成当前格式（`README.zh.md:44`），原始文件保持不变。我方要想清楚：是"读时迁移"还是"一次性升级旧库"——**两者对备份/回滚的要求完全不同**。

### 6. 验收标准

**先说清我方现状（这是本节最有价值的发现）：我方有版本机制，但有 3 个具体缺陷，且没有任何"格式版本"概念。**

证据（`src/store/schema-migration.ts` 全文 89 行）：

**缺陷 1（事实·严重）：读当前版本用 `ORDER BY updated_at DESC LIMIT 1`，而 `updated_at` 是秒级 `datetime('now')`。**
```js
// :52-61
CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL, updated_at TEXT NOT NULL DEFAULT (datetime('now')))
const row = db.prepare('SELECT version FROM schema_version ORDER BY updated_at DESC LIMIT 1').get()
const currentVersion = row?.version ?? 0;
```
`:81` 每次迁移后 `INSERT INTO schema_version (version) VALUES (?)`——**同一秒内跑完两条迁移，两条行的 `updated_at` 相同，`LIMIT 1` 取哪条是不确定的**。→ 正确做法是 `SELECT MAX(version)`。

**缺陷 2（事实）：版本号会被"空转"前进，导致跳版。**
```js
// :69-75
const pending = migrations.filter(m => m.version > currentVersion && m.version <= SCHEMA_VERSION);
if (pending.length === 0) {
  db.prepare('INSERT INTO schema_version (version) VALUES (?)').run(SCHEMA_VERSION);   // ← 直接写 SCHEMA_VERSION
  log.info({ schemaVersion: SCHEMA_VERSION }, 'Schema 版本已初始化');
  return;
}
```
场景：`migrations[]` 里只有 version=1 的迁移，但 `SCHEMA_VERSION = 2`，且库里 `currentVersion = 0`。此时 `pending = [migration#1]`，正常。**但若库里 `currentVersion = 1`（迁移#1 已跑）而 version=2 的迁移文件还没写进数组（比如 `SCHEMA_VERSION` 先被 bump 了），`pending` 为空 → 直接把版本写成 2 → 未来真正的 v2 迁移永远不会执行。** → **这是一个"版本先于实现"就永久丢迁移的洞。**

**缺陷 3（事实）：迁移条目数与版本号不强制一致。**
`migrations[]`（`:33-36`，1 条）与 `SCHEMA_VERSION`（`:19`，= 2）在数值上不匹配，代码不做断言。**没有任何地方校验"注册的迁移覆盖 1..SCHEMA_VERSION 的每一级"**——这正是 DSH `dsh-session-format` 在构造时校验"唯一且无缺口"（`README.zh.md:58`）要解决的问题。

**缺陷 4（事实）：没有数据格式版本。** 全树 grep `format_version` / `formatVersion` / `SESSION_FORMAT` 在 `src/store/` 下**零命中**（仅 `schema-migration.ts` 自己的 `schema_version` 元表）。我方会话记录里**没有"这条会话是按哪版格式写的"的标记**——而 DSH 的 header 里 `version` 是强制字段（`types.d.ts:11`），甚至进遥测属性（`dsh-session-telemetry/lib/types/index.d.ts:68`）。**这意味着我方将来若改 `payload_json` 的结构，无法判断一条旧记录的 payload 是哪一版写的。**

**验收（可判定）：**

1. **版本读取正确性（穿真实 DB）**
   ```bash
   # 造 3 条 updated_at 相同的 schema_version 行
   sqlite3 <db> "INSERT INTO schema_version(version, updated_at) VALUES (1,'2026-09-19 12:00:00'),(2,'2026-09-19 12:00:00'),(3,'2026-09-19 12:00:00');"
   # 跑 reconcileSchema（通过真实启动：pnpm start / pnpm mvp）
   ```
   断言：读到的是 `3`（`MAX(version)`），且**不重复执行任何迁移**。改造前预计读出 1 或 2（不确定）。
2. **无缺口校验**：注册一个 `migrations[]` 覆盖 1、3 但缺 2 的配置，断言 **进程启动即失败**（不是静默跳过）。对齐 DSH `README.zh.md:58`"构造时校验唯一且无缺口"。
3. **降级路径可判定**：让一条迁移的 `up()` 抛异常，断言 ① 进程不启动（`:86` 已有 `throw err`，是对的）；② `schema_version` 表**没有**被写入该失败的版本号（当前 `:81` 在 `up()` 之后，是对的——这条是**已验证为正确**的，验收是防回归）。
4. **格式版本标记存在性（新能力）**：新建的每条会话记录里带 `format_version`，且 `GET /api/sessions/:id` 返回它。
5. **迁移可重放**：备份一个旧库 → 用新版本启动 → 断言所有 `migrations[]` 都执行过（查 `schema_version` 有 1..N 全部行）且业务查询正常。
