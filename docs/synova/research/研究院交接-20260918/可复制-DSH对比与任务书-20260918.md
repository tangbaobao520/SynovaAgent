## 一、为什么做这件事（否则你会做偏）

创始人的原始提问是：

> 「把核心能力构建在 DSH 架构上、封装成 Synova，是否比自研 agent 运行时更好？」

**这个问法自带一个陷阱**：它把"换成 DSH 内核"当成了目标。照它做，会得出"应该用 DSH 重写"的结论——**而这是错的**。

正确的问题结构是**分层**的（这是本院独立校验后，与你们 2026-08-20 施工图**逐条吻合**的结论）：

| 层 | 该不该用 DSH | 理由 |
|---|---|---|
| **通用工程层**（会话持久化 / agent 循环 / 子 agent / LLM 适配） | **该用** | 继续自研是重复造轮子 |
| **核心能力层**（SOG-Core / 六阶段诊断 / 专家 / 哨兵 / 参数库） | **绝不该** | **这是护城河**（"参数库 + 验证过的因果"才是墙，runtime 不是） |
| **产品形态层**（客户看到的界面） | **不该换** | DSH 是开发者 harness 形态；客户是中小企业老板 |

**而且这个决策你们已经做过了**：`docs/synova/research/DSH迁移施工图-20260820/` 已定终态 **A 形态 = DSH 壳 + Synova 核心独立服务 + MCP 边界**，含四阶段与 **Stage 3 双重入场券**。
