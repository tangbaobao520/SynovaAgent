# 复盘：插件推荐失误，与第三方代码准入标准

> 日期：**2026-09-19**
> 触发：创始人质询 —— *"所以你让我装的这三个插件几乎是没人用的东西，你这不是瞎搞吗，你是这么审查的么，你这个院长怎么当的"*
> 结论：**创始人判断正确，且实际严重程度高于其表述。本文件是错误分析 + 立即处置 + 可复用准入标准，不是检讨书。**
> 关联：[插件尽调-三个第三方控制插件-20260919.md](插件尽调-三个第三方控制插件-20260919.md)（该文 §七 的「guard 留用」结论已由本文件更正）

## 一、结论先行

1. **错误定性**：我在**未做任何客观核验**的情况下，把三个第三方插件推荐给你并写了安装脚本。核验后：**三个包的月下载量为 188 / 336 / 310 次**，而同生态真正在用的插件是 **72,003 / 112,965 / 264,705 次/月** —— **差 2–3 个数量级**。
2. **这不是"审查不严"，是"没有审查"**。我读了 README 就把作者自述当作了能力证据。
3. **处置**：**三个全部卸载**。不是只卸 tower —— guard / bench 同属一个 2★ 项目，我上一轮"guard 可以留"的结论**与我自己的论证自相矛盾**（见 §三·错误 4）。
4. **我没有立刻给替代品**，理由见 §六：上一轮的错误就是"快速给推荐"，重复同样动作只会重复同样的错。替代路径需要先验证。
5. **已建立准入门槛**（§五），此后任何第三方代码进入你的机器必须过这三道关。
6. **最根本的一条（2026-09-19 追加，见错误 6）**：官方**本来就有 Agent Teams，且已在你的机器上运行**（`~/.dsh/profiles/web/package.json` 第 44 行）；官方 Web 任务板只是**没启用**。我的搜索方向从根上错了 —— **该先穷尽第一方文档与设置页，再谈第三方生态。**

## 三、错误的结构（逐条，这比道歉重要）

### 错误 1：顺序反了 —— 先推荐，后审查

我是**先写了安装脚本**，等你追问 `dsh-plugins-tower` 出处时才去核验，才发现 2/3 不在市场列表里。
**正确顺序：核验 → 推荐 → 安装。** 结果我做了：推荐 → 安装 → （被你追问）→ 核验。

### 错误 2：把 README 当证据

我给的理由是"这些是现成方案，能力对得上你的缺口" —— 依据全是**作者自己写的 README**。
**README 是作者的广告，不是证据。** 我自己在研究院五条铁律里写着"来源与日期""区分事实/推断/猜测"，却对"让第三方代码进你机器"这个决策用了远低于自己标准的方法。

### 错误 3：绕过了现成的筛选工具（这次最不可原谅）

生态里**本来就有两个专门干这件事的工具**，我一个都没用：

| 工具 | 月下载/星 | 它本来能告诉我什么 |
|---|---|---|
| `dsh-market`（市场，**4,173★**、45.9 万/月） | 市场 UI 自带 **star 数、top/new 排序、兼容性过滤**（`engines.dsh` 声明）和 2300+ 插件目录 | **如果我在市场里按 star 排序找，2★ 的项目根本不会出现** |
| `AdamPlatin123/dsh-plugin-radar`（**1,466★**） | 自我定位：*"安装前就知道哪个能用，不用自己踩坑"*；**k8s 运行级实测 13,659 个插件**、15 分钟快照、按 runner 版本分离判定（可用/需适配/在测） | 能直接给我"这个插件在当前 DSH 版本上实测是否可用" |

**我给了你一条绕过市场筛选、凭我自己检索的路径。这是这次失误的核心 —— 不是判断力不够，是流程完全没走。**

### 错误 4：逻辑自相矛盾

我在尽调文件 §四 里刚写下：*"市场收录 ≠ 质量认证……收录只代表有人提了 PR"*；
然后在 §七 里用 **"guard 在精选列表里"** 作为**留用的理由**。
**同一份文件里，我既论证了"在列表里不算数"，又拿"在列表里"当依据。** 这条自相矛盾你有理由不接受我任何结论。

### 错误 5：把一个"真空"当成了"价值"

我把 tower 的价值论证建立在"官方没有 worktree 隔离和审查门禁"上。
但核验后发现：**1,728★ 的 `dsh-agent-teams` 也不做 git/worktree 隔离**（其 README 里 `worktree` / `git branch` / `merge` / `隔离` 命中均为 **0**）。
**一个 4,173★ 市场 + 1,728★ 主流方案 + 官方三边都不提供的能力，只有 188 次/月的项目声称提供 —— 更可能的解释是"这个能力不是真需求"，而不是"我发现了别人没发现的真空"。** 我把后者当了真，这是**基础推理错误**。

### 错误 6（最根本的一条）：搜索方向错了 —— 没先穷尽第一方

**创始人 2026-09-19 截图质疑**：设置页「官方」分类下明摆着「智能体团队 Beta」+「智能体团队 Web 界面 Beta」，*"扯蛋，官方都出了团队版插件了"*。

核验结果，创始人正确：

1. **官方 Agent Teams 早就在运行。** `~/.dsh/profiles/web/package.json` **第 44 行** bundles 含 `@deepseek-ai/dsh-experimental-agent-team-profile`。**本会话里的 `spawn_teammate` / `team_task_*` / `send_message` / `wait_agent` 全部由它提供** —— 我做的一切协作都跑在官方 Agent Teams 之上。
2. **那个我读过两遍的文件，答案在 20 行之外。** 我读 `package.json` 时只读了 `dependencies` 段，**没读 `dsh.profile.bundles` 段**（第 22–48 行）。
3. **我没读官方包目录里的 `README.zh.md`** —— 那是第一方穷尽式文档（`kind: package-reference`），里面逐条写明了 roster / 共享任务板 / blocker / readiness / **write scope 重叠 warning** / 成员会话导航 / "挺过崩溃与重启"。
4. **正确顺序本应是**：① 官方包 README → ② 设置页有哪些官方开关 → ③ 官方 remote/API → ④ 才轮到第三方生态。

**这一条比前五条更根本**：前五条是"审得不严"，这一条是"**根本审错了地方**"。我查遍 npm 包名、第三方仓库、下载量、stars、精选列表收录情况，**却漏掉了第一方文档和设置页**。

**已写入 [官方智能体团队-能力清单与启用方式-20260919.md](官方智能体团队-能力清单与启用方式-20260919.md)。**

## 四、立即处置

```bash
dsh plugin --profile web remove dsh-plugins-tower
dsh plugin --profile web remove dsh-plugins-guard
dsh plugin --profile web remove dsh-plugins-bench
```

执行后重启 `dsh web`（guard 已在当前会话生效，本会话里的 `guard_*` / `bench_*` / `tower_*` 工具会随之消失）。

**保留不动**：`@linxin666/dsh-client-ui-task-board`（264,705 次/月）—— 它在真实使用量级上，是你现有控制塔的基础。
**保留行为**：`~/.dsh/guard/` 下已有的审计记录**不必删**（无害，且有历史价值）；若确认不要，手动删该目录即可。

> ⚠️ 卸载必须在**沙箱外**执行（院长会话内 `~/.dsh` 为只读，`dsh plugin` 会报 `EPERM`）。

## 五、第三方代码准入标准（此后强制）

**任何要装到你机器上的第三方插件，三道关缺一不可。任一道不过，不进安装脚本。**

### 关 1：客观使用量（硬门槛）

| 指标 | 门槛 | 查法 |
|---|---|---|
| npm 月下载量 | **≥ 5,000** | `curl -s https://api.npmjs.org/downloads/point/last-month/<pkg>` |
| GitHub stars | **≥ 100** | `api.github.com/repos/<owner>/<repo>` |
| 最后提交 | **≤ 60 天前** | 同上 `pushed_at` |
| 许可 | **有明确 SPDX 许可** | 同上 `license` |
| 版本史 | **≥ 3 个版本**（证明在维护） | `registry.npmjs.org/<pkg>` |

> 本次三个包：**5 项全不达标**。
> 门槛取值的依据：生态真实基准线见 §2.1/§2.2（主流插件在 7 万–46 万/月、1,400–4,200★）。5,000/月 与 100★ 已在主流之下留了一个数量级的宽容。

### 关 2：运行级可用性（不靠作者自述）

- 查 `dsh-plugin-radar` 的**实测判定**（可用 / 需适配 / 在测）与对应 runner 版本
- 查 `dsh-market` 卡片上的 `engines.dsh` 兼容性声明
- **不采信 README 里的能力描述作为可用性证据**

### 关 3：安全面（我方独立复核，不外包）

- 是否联网（`fetch` / `http` / `https` / `net`）
- 是否碰凭据（`ssh` / `credential` / `apiKey` / `token` / `process.env`）
- 是否执行外部命令（`child_process` / `exec` / `spawn` 的实际调用点）
- 是否写工作区之外（`homedir`）
- 代码量是否小到**院长能全文读完**（本次 1,596 行可读，这条是唯一做到的）

### 附加纪律

- **凡推荐第三方代码，必须先出核验数据再出推荐**，顺序不可颠倒。
- **凡我给的建议，若与前文自己的论证冲突，以论证为准并显式更正**（本次错误 4 的教训）。
- **优先路径：先在 `dsh-market` 按 star 排序、在 `dsh-plugin-radar` 看实测状态**，再谈具体候选；不自行检索后就推荐。

## 七、对你更重要的一个推论（与插件无关）

**"M8 共享竞争事故"的解法，不该指望插件。**

依据：连 1,728★ 的社区主流方案 `dsh-agent-teams` 都不做 worktree 隔离；官方 `dsh-experimental-agent-team` 也不做（`worktree`/`git`/`review` 命中 0）。

**那么该用什么？**
1. **官方机制**：不同并行 session 用**不同 workspace**（你已有的 handover 机制正是 workspace+preset+permission 三元组）
2. **流程纪律**：**同一时间只允许一个 session 改代码**——这零成本、零依赖、且比任何插件都确定
3. **真要 git 层隔离**：用 `git worktree` 命令**手工做**（我不需要第三方代码替你执行 `git worktree add`）

**结论（置信度：中高）**：把"防止并行冲突"交给**纪律 + 官方 workspace 机制**，比交给任何插件都稳。**这也意味着我原本推荐 tower 的那个理由本身站不住。**
