# DSH Agent team 与 Win 侧 Claude Code 代码质量对比（独立评估）

> 研究日期：2026-09-22 | 研究员：技术线（shanhe-tech 预设）
> 性质：创始人直派专项——为「未来用什么工具编码」决策提供独立证据。
> **独立性声明：本研究未参考 K3 审计结论、未参考 `Synova-k3独立审计` 目录、未参考 `audit/` 下任何他人审计报告。全部证据来自 git 元数据、AST 实测、双盲评审（作者身份对评审员隐藏）与研究员深读。**

---

## 结论先行

1. **两组代码质量在同一量级（置信度：高）**。双盲评审组间差 0.11–0.13 分（5 分制），远小于组内方差（最低 3.2 与最高 4.88 都出现在同一组内）；真缺陷归因 11 vs 12 行基本打平；测试密度 89 vs 85/千行持平。**「换工具能带来代码质量跃升」这个假设不成立。**

2. **DSH 侧有微弱但一致的整体优势（置信度：中）**。四个独立维度同向：盲评均分 +0.11/+0.13、提交原子性（4.6/2.1 vs 6.8 文件/提交）、任务号可追溯率（48% vs 32%）、规格兑现（D702 一次通过 vs D701 合并后一轮返修，样本仅 1 对）。

3. **差异的本质是失败模式与风格，不是能力**：
   - **Win（Claude Code）的失败模式**：编排层巨型函数（352 行 `check`、716 行 loop-handlers）、入口校验与实现脱节（`Number()||0` 假 critical）、fail-open 复发（读失败当不存在）。
   - **DSH 的失败模式**：边界值遗漏（`limit:200` 分页截断、`hours.length===24` 阈值放大 24 倍、`maxScheduleMs=0` 恒告警）、越权防护依赖外部挂载、解析设计脆弱（curl `__STATUS__:` 分割）。
   - DSH 强在：防御纵深、注释契约、降级语义、可靠性补偿（写后复读验证）。Win 强在：类型断言克制（as 密度 9.1 vs 15.7/千行）、圈复杂度控制（4.22 vs 4.91）、纯函数设计。

4. **对工具选择决策的含义**：代码质量本身不构成选择依据。真正拉开差距的是**共享的工程体系**（spec 文化 + 共享门禁 + 审计流程）——两组都过了同一套 pre-commit/CI，底线差异已被门禁抹平，盲评里两组的注释纪律都是全场最强维度（4.73/5）且高度同源。工具选择应基于本对比未覆盖的因素：成本、并行吞吐、上下文管理能力、与既有体系的耦合度。

## 一、问题

SynovaAgent 仓库在 2026-08-14 至 2026-09-13 期间由两条并行编码线共同推进：
- **Mac 侧 DSH Agent team**（DeepSeek Harness，提交身份 synova-mac / synova-dsh / dsh-cto / synova-cto）
- **Win 侧 Claude Code**（Windows 机器，提交身份 Synova-Win / ClawOrg-Win）

问题：**两条线产出的代码，哪边质量更高？差距是本质的还是风格性的？**——结论将直接决定未来主力编码工具的选择。

## 二、假说

**H0（工作假说，评估前预设）**：两组代码质量在同一量级，差异主要体现在风格与流程纪律而非代码本体。
（若被证伪，则接受任一方向的质量优势结论。）

## 三、方法论（权威框架）

| 维度 | 框架来源 |
|---|---|
| 质量模型 | ISO/IEC 25010（可维护性/可靠性/安全性子特性） |
| 复杂度 | McCabe 圈复杂度（TypeScript Compiler API 5.9.3 AST 精确计算） |
| 函数/嵌套纪律 | McConnell《Code Complete》ch.7/ch.17；《Clean Code》函数章 |
| 代码异味 | SonarQube 分类（长函数、深嵌套、重复块、magic number） |
| 评审流程 | Google Engineering Practices（Code Review 指南）——**双盲评审**（作者身份对两位评审员隐藏）+ 评分者间一致性检验（Spearman ρ） |
| 缺陷归因 | SZZ 思路（fix 提交回溯引入者 blame）+ 语义分类（剔除重构噪音） |
| 可信度控制 | 行级 blame 归属（非文件级猜测）、度量工具误差修正记录、外部事实交叉核实（评审员须核实 server.ts 挂载链后才许下安全结论） |

1. `docs/synova/setup/MACBOOK-SETUP.md`（D318）：Mac 身份 `Synova-Mac`，Win 身份 `Synova-Win`，机器归属靠 per-clone `user.name`。

**分组**：DSH 组 = synova-mac/synova-dsh/dsh-cto/synova-cto（8/14 后）；Win 组 = Synova-Win/ClawOrg-Win；ClawOrg（早期 mac Claude，82,054 存活行）排除；tangbaobao520（创始人 PR 合并身份）不计入。

## 四、证据

### 4.1 静态度量（AST 实测）

| 指标 | DSH | WIN | 优方 |

| 最大缩进深度 | 5 | **8** | DSH |
| as 断言密度 | 15.7/千行 | 9.1/千行 | WIN（均无 as-any） |
| console.log | 5 | 9 | DSH 微优 |
| 注释/代码比 | 37.3% | 24.9% | 量差，质见盲评 |
| 跨文件重复率（5-gram） | 0.2% | 1.5% | DSH 微优（均健康） |
| 空指针 catch | 0（修正后） | 0（现存） | 平 |

**度量工具误差修正记录**（方法可信度的一部分）：
- 初版嵌套计数器把 else-if 链判为深嵌套（DSH「11 层」假信号）→ 改物理缩进实测：DSH ≤5，WIN 最深 8。
- 初版空 catch 检测漏 catch 块内部注释 → 人工核验后 DSH 两处「裸空catch」均系误报（一为块内注释、一为进程清理合理容错）。Win 曾有空 catch 被铁律 24 门禁抓回补修（`fix(D487)`，2026-08-28）——门禁有效性的直接证据。

### 4.2 缺陷归因（SZZ 式回溯 + 语义去噪）

全量 818 个 fix 前缀提交中 334 个触碰非测试 TS，被修行 blame 回溯引入者：

| 口径 | DSH | WIN | 判读 |
|---|---|---|---|
| 粗口径（所有 fix 删除行） | 645 行（41.4/千行） | 205 行（20.6/千行） | 表面 DSH 差——**系噪音** |

真缺陷双方都有实锤：DSH `7e44c02e`（入口失败误绿）、`27b153b7`（字段语义挪用）；WIN `c11fbb1b`（**3 个哨兵 31 处类型错被 D752 门禁暴露**）、`0e97b20b`（mcp 空 catch）。

### 4.4 编译与安全

- 当前 HEAD 28 个 tsc 错误：25 个在 `_extinct/` 退役目录（tsconfig 不覆盖），3 个活跃错误全部归 **ClawOrg 遗留**（`server.ts:464-465`、`ima.ts:143`）→ **两组存活代码均通过类型检查**。
- 安全反模式扫描（eval/exec 拼接/硬编码密钥/SQL 拼接/路径穿越）：两组均零命中。DSH 19 处 `process.exit` 全在 CLI 脚本（正当），服务端零命中。

### 4.5 双盲评审（12 文件，两位评审员独立打分，作者身份隐藏）

分组揭示后（A=DSH，B=WIN）：

| 评审员 | DSH 组均分 | WIN 组均分 | 差 |
|---|---|---|---|
| R1（ISO 25010/SonarQube 框架） | 4.29 | 4.18 | +0.113 |
| R2（Google CR/Clean Code 框架） | 4.38 | 4.25 | +0.125 |
| **评分者间一致性** | **Spearman ρ = 0.727** | | 良好 |

**关键事实**：
- 全场最高分 DSH `ga-auth.ts`（4.88/4.7，中国墙设计）与 WIN `interest-coverage.ts`（4.88/4.6，假值路径封堵）**并列**——两组都能产出优秀代码。
- 全场最低分是 WIN `aggregate.ts`（3.25/3.2）：352 行 `check` 函数、8 段同构复制、入口校验只查 `finNodes[0]` 而归一化全量 `Number()||0` 静默归零——**字符串 `'abc'` 通过存在性检查后变 0，触发 critical「资本周转率过低」假警报**，恰是该文件头注释自己声称要堵的路径。
- DSH 最弱 `assert.ts`（3.75/4.3）：curl `-w '__STATUS__:'` 混合输出解析脆弱（响应体含该标记即错乱）、`validateExpectDoc` 判空后未 return。
- **交叉确认**（两位评审员独立抓到同一问题，可信度高）：aggregate 的 NaN 假 critical、ga-calibration 的 `limit:200` 硬编码分页截断（用户 offset 参数算而不用）、loop-handlers 的 `props.metrics as` 零校验断言产 NaN 静默、decision-record 的 fail-open（读失败与不存在同返 null——仓库 K3 P0-3 事故同型复发）。
- **双评审的独特价值**：DSH `self-check.ts` 被两位评审员**各自发现一个不同的真 bug**——R1 抓到 `hours.length===24` 边界（每小时执行的哨兵陈旧阈值放大 24 倍）、R2 抓到 `maxScheduleMs=0` 时 H3 恒告警（与文件自身「宁缺毋滥」契约矛盾）。
- 共性（非差异）：两组都呈「叶子层优秀、编排层塌陷」双峰——≤197 行纯函数/小模块均分 4.68，编排/聚合层均分 3.71；注释纪律都是全场最强维度（4.73/5）且高度同源（契约 JSDoc + 决策编号 + 铁律引用）。

### 4.6 研究员独立深读（交叉验证）

- DSH `path-dependency/computes/detect.ts`（180 行）：三层降级设计完整；瑕疵：L88 `Math.max(...values())` 大图 spread 栈溢出风险（外层 catch 兜住降级，不致命）。
- WIN `wacc.ts`（102 行）：纯函数、学术来源引用、三重 guard，未见瑕疵——但负权益（资不抵债）场景双 computes 均未设防（盲评交叉确认）。
- WIN `loop-handlers.ts`（716 行）：实为规整的 5 组 setDeps/Handler 依赖注入模板，可测试性设计良好；写后复读验证是全场最成熟的可靠性工程。
- WIN `conflict-scanner.ts`：8 层嵌套系 O(n²) 对撞检测的算法性嵌套（非失控）；CLI 用 `process.exitCode` 比 DSH 的硬 `process.exit` 更优雅。

### 4.7 规格-实现一致性（同构任务对照）

D701（Win 执行）与 D702（DSH 执行）：同号段相邻任务、同一 spec 作者（Codex）、同期派发——理想对照样本。
- **D701（Win）**：最终兑现 spec（251 行源码 + 9 测试用例 > 要求的 ≥5），但经历一轮「合并后自审发现真 bug」——`randomUUID()` 当 record.id 而真实 store 恒生成 `node-<uuid>` 忽略 props.id，**假 store 测试「蒙混过关」**，合并后才修复（spec §3.2 第 5 点自审如实记录）。
- **D702（DSH）**：spec 全项兑现（{ok,error} 返回、8 调用点全消费、S-15 round-trip 断言、17 用例），**一次通过无返修**。
- 后续效应：D701 事故催生了 S-15「真实依赖语义对照」规则并写进后续所有 spec——**单次失败被流程吸收为资产**，这是这套体系的胜利，不是某个工具的。

## 五、反例与失效条件

1. **任务类型未完全对齐**（最重要的反例来源）：Win 承担了更多 agent 核心编排（loop-handlers）与哨兵聚合（aggregate 438 行）——编排层天然难写，双峰塌陷可能是任务分配的结果而非工具能力。D701/D702 同构对照部分缓解（DSH 一次过 vs Win 一轮返修），但样本仅 1 对。
2. **存活偏差**：行级归属只覆盖 6.9k 行存活代码；两组已删除/重写的代码（往往是最差的部分）未评估。DSH 的 15.6k 行 TS 新增只存活 21%，WIN 10k 行存活 29%——删除原因未逐条考证。
3. **评审员同源**：两位盲评员由同一研究员派生（同模型血统），ρ=0.727 的部分一致性可能来自共同的评分偏好，不能视为完全独立。
4. **语义分类手工桶**：缺陷归因的「待判」53/59 行未逐一人工细读，若其中分布失衡，打平结论可能偏移。
5. **工具版本混合**：Win 侧 8/14–9/13 期间 Claude Code 具体模型版本未考证（Co-Author 签名仅见 Claude/Claude Opus 4.8 两类）；DSH 同期亦在迭代。
6. **什么证据会让我改变结论**：① 同构任务对照扩到 10+ 对后 Win 一次通过率追平/反超 DSH；② 按 P0 级缺陷/千行统计出现 ≥2 倍系统性差距（任一方向）；③ 编排层任务在两组间重新均分后盲评组间差消失（证明差异全由任务难度驱动）。

## 六、结论

**H0 基本成立：两组代码质量在同一量级（置信度：高）**。任何关于「某工具的代码质量显著更好」的说法在当前证据下不成立。

**DSH 侧存在微弱但方向一致的优势（置信度：中）**——体现在流程卫生（原子提交、可追溯性、防伪绿基建）与规格兑现稳定性上，而非代码本体。代码本体上是风格互补：DSH 重防御纵深与契约注释，Win 重类型克制与复杂度控制；两者的高分文件同分并列，低分文件各有各的失败模式。

**对「未来用什么工具编码」的决策输入（本对比职权范围内）**：
1. 不应以「代码质量」为由二选一——差距不构成决策依据。
2. 若单选：DSH 的流程纪律优势（原子提交、任务号、场景基建）在大仓协作里有复利，但此优势部分来自环境配置而非模型能力，理论可被任何工具复制。
3. 本对比**未覆盖**的决策变量同样重要：API 成本、并行吞吐、上下文长度、多 session 管理、与既有 DSH 系的耦合迁移成本——建议按技术线成本框架另行评估。
4. 真正被本对比证实的护城河不是工具，是**共享工程体系**（spec 文化 + 双机同门禁 + 事故进流程）——它把两个不同工具的产出拉到了同一质量带。切换工具的风险远小于拆掉这套体系的风险。
