判断一（修正）：管理经济学是"理论语言层"，但"第一大脑"的定位需要本体层的结构性扩展。

管理经济学教材内容（弹性、盈亏平衡、NPV）本身不产生新边——它们作为compute函数落地。但 Synova 的产品定位——"像专业咨询师一样诊断 + 作为企业第一大脑辅助各职能部门执行"——需要本体层扩展：6个新实体（Action/Task、CustomerTier、PriceEvent、SupplierRisk、RoleCriticality、Scenario）、3条新边（BRAND_BUILDS、COUPLES、CUMULATIVE_LEARNING）、补齐4个v2.4已定义但缺失的实体（Sensing/Assumption/ExternalBaseline/AdversarialFrame）。合计新增6实体+3边，补齐4已有实体。

判断二（维持）：79%的管理经济学核心计算可直接实现——但需本体层数据支撑。

22个A/B级数据可得性的公式可以在当前ERP/财务数据基础上直接计算。但其中弹性计算依赖PriceEvent实体（追踪价格变动事件序列），否则永远数据不足；边际分析依赖成本分类的准确性（GA配置）。本体层实体的补齐是compute函数能正常运行的数据前提。不是"先做compute还是先做本体"——是两者必须同步。

判断三（维持）：管理经济学是Palantir和零一万物无法模仿的差异化——但真正的壁垒不在语言层，在"全部门决策辅助"的完整度。

Palantir的客户需要自己搭建Ontology来分析数据；零一万物的"销冠AI"只覆盖销售场景。Synova的"第一大脑"覆盖七个职能部门乘以五个决策类型的完整矩阵——这需要本体层有足够的实体和边来承载每个部门的因果链路。竞争对手可以快速增加一个盈亏平衡计算功能，但无法快速复制一个覆盖全部门的因果本体层。

修正总结：本体层需要新增 6实体 + 3边 + 补齐4已有实体 = 合计13项

五路研究整合时的原始判断——"管理经济学的7个模块中，6个是纯专家推理知识，不产生新的本体层边或实体"——是错误的。这个判断只考虑了管理经济学教材内容本身（弹性公式、盈亏平衡、NPV），没有考虑 Synova 的产品定位："像专业咨询师一样做诊断 + 作为企业的第一大脑辅助各职能部门执行"。

7.3 新增实体和边的业务理由详述

Action/Task（P0）——为什么是"第一大脑"的前提

专业咨询师的工作不是"出完报告就走人"——他们追踪建议的执行效果。Synova作为"驻扎在企业内部的第一大脑"，如果不能回答"上次诊断的5条建议执行了3条，效果如何"——它就只是一个"出报告的AI"，不是"企业的第一大脑"。Action实体是Synova从诊断系统升级为执行导航系统的本体层前提。

BRAND_BUILDS边（P0）——为什么16条边不够

市场部的核心日常决策——品牌预算分配——在当前16条边中没有直接因果建模。PRODUCES边覆盖"活动→产出"（短期），但品牌建设到营收转化的长期滞后效应（6-18个月）需要一个专门的边来建模。这不仅是JTBD需求（U-JTBD-0009品牌战役ROI、U-JTBD-0039种草vs收割分配），更是"第一大脑"对市场部的价值证明——如果市场总监问"我花的钱效果在哪"，Synova不能只说"品牌很重要"，需要用本体层的因果边+滞后期参数给出量化回答。

CustomerTier + PriceEvent（P0）——为什么不是"已有结构的扩展"

这两个实体看起来是Client实体和财务数据的"扩展"，实际上它们代表了本体层的粒度升级——从"企业有客户""企业有价格"升级为"企业把客户分为ABC三层且在追踪每次价格变动的弹性效应"。这不是数据层面的细化，是诊断能力层面的跃迁——没有CustomerTier，销售部的日常决策（"A类客户上个月贡献了多少利润"）无结构数据支撑；没有PriceEvent，管理经济学最经典的弹性分析永远数据不足。

SupplierRisk（P1）——为什么采购部需要独立的风险实体

DEPENDS_ON边只表达"生产线依赖供应商A"，不表达"依赖供应商A有多危险"。供应商A的交付准时率从98%跌到85%——在DEPENDS_ON边的视角里一切正常（关系还在）。但采购总监需要立刻知道"这个供应商在恶化，而且它是我前三的供应商，如果断供两条产线会停"。SupplierRisk实体扩展Supplier——交付准时率、质量合格率、财务健康度、最近涨价幅度——这些不是"供应商的属性"（不是Supplier实体上添几个字段），而是一个持续更新的风险评估对象，每次采购事件（交货延迟、质量退货、涨价通知）都触发其更新。数据源：B-C级。准时率/合格率从ERP采购模块获取；财务健康度需GA评估或第三方数据。

RoleCriticality（P1）——为什么key-person-risk哨兵不够

key-person-risk哨兵能检测"这个人离职可能造成风险"，但它的输出是瞬时的（一次计算一个分数），不持久化、不可积累、不可跨时间比较。RoleCriticality实体把这个计算结构化持久化——四维度（信号中心性×决策影响面×技能不可替代性×产出直接影响），每个维度有计算方法和数据源，每次组织变动（入职/离职/调岗/重组）自动重新计算。HR总监做裁员决策时不是问"谁重要"，而是问"每个人的重要性是怎么构成的"——一个高信号中心性低技能稀缺的人可以备份，一个高技能稀缺低信号中心性的人不应该裁。没有RoleCriticality，裁员的"第一大脑"辅助就是一句空话。数据源：B级——全部四维数据从本体层图遍历获取，不依赖外部数据。

Scenario（P2）——为什么情景模拟需要持久化

专业咨询师的标志能力——"如果原材料涨价20%，利润会怎样"——在Synova中当前是一次性LLM调用，模拟完即丢。Scenario实体把每次模拟结构化存储：假设条件列表、模拟结果（利润变化X%、BEP从Y移到Z、安全边际从A%缩小到B%）、六个月后自动对比实际经营数据——"我们上次预测原材料涨20%，实际涨了15%，利润实际比预测多3个百分点"。每一次模拟的偏差都在为下一次模拟提供校准数据。这个实体是Synova从"AI问答"升级为"预测系统"的本体层前提——没有历史模拟记录的系统无法证明自己的预测能力在进步。数据源：A-B级。假设条件来自用户输入+EXTERNAL_ASSUMPTION_BINDS边，模拟结果由compute函数+专家推理生成，实际结果从事后经营数据中提取。

JSON Schema规划路径

这6个职能部门的实体目前为设计提案阶段——无JSON Schema文件。规划路径为 extensions/ontology/functional/{entity-name}.json，与已有的 resource/activity/outcome 目录并列。T8任务（新实体创建）启动时按此路径创建。每个实体的Schema需包含：allowedProperties、consumed_by_sentinels（对应哨兵清单见路线B独立产出）、data_source_grade（数据可得性等级见路线E独立产出）。
