# Synova 权威文档跨文档一致性审计计划 v2.0

> 审计范围: 21 个文档组, ~120 个研究文件
> 审计目标: 发现跨文档的术语冲突、数据契约断裂、架构矛盾、数字不一致
> 执行策略: 前三轮由编码 Agent (Claude Code) 执行, 其余轮次由研究 Agent 执行, Claude Code 抽查复核
> 产出物: 独立 HTML 仪表盘 — 完整不一致清单 + 修复路线图 + 术语标准表 + 数据契约图谱 + 修复状态追踪表

## 零、审计前置规则

### 0.1 基准文档优先级

当矛盾发生时, 以基准文档为准。基准优先级从高到低:

| 层级 | 基准文档 | 覆盖范围 |
|------|---------|---------|
| 定义层 | 01 (本体层因果体系) | 42 边定义、节点池、因果链 — 01-02-03-3D-13-15 链路的最终基准 |
| 实例化层 | 03 (哨兵-计算-本体) | 哨兵类型、compute 函数规格 — 当 3D 或 13 引用哨兵/compute 时以 03 为准 |
| 时间基准 | 07 (Agent 工程能力对标) | 快/中/慢 时间尺度定义 |
| 专家基准 | 03 S1 (哨兵规范中的专家部分) | 专家 ID 列表、触发条件、路由规则 |
| 安全基准 | 08 (安全隐私权限) | 安全架构、权限模型、脱敏规则 |
| 架构基准 | AGENTS.md V4.5.0 (已锁定) | 五层架构分层 (L1-L5)、模块边界 |

### 0.2 证据锚定规则

每条不一致发现必须包含:
- **文档 A 引用**: 文件名 + 章节号 + 原文前 100 字符
- **文档 B 引用**: 文件名 + 章节号 + 原文前 100 字符
- **不一致点**: 一句话描述具体冲突

### 0.3 修复优先级规则

| 严重度 | 定义 | 处理 |
|--------|------|------|
| P0 | 数据契约断裂 — 上游定义的下游不消费, 或消费了不存在的字段 | 24h 内修复, 以定义层文档为准 |
| P1 | 术语或数字不一致 — 导致开发困惑但不会让系统崩溃 | 本周内统一, 向定义层对齐 |
| P2 | 文档过期或版本时间差 | 下次文档更新时同步 |

### 0.4 审计独立性

- 前三轮 (术语/数据契约+03↔3D/架构) 由编码 Agent (Claude Code) 独立执行
- 第四至九轮由研究 Agent 执行
- 第一、二、三、五轮的发现必须由编码 Agent 抽查验证 (每轮抽 20%)

## 二、九轮审计 + 两个专项检查

### 第一轮: 术语一致性 (全 21 组) — 编码 Agent 执行

**目标**: 同一概念在所有文档中使用相同名称。

**术语分组定义** (审计前确认):
- 组 1 (因果边): "42 条因果边" / "42 条边" / "42 边" / "42-edge" — 同一概念
- 组 2 (图存储): "GraphBridge" / "GraphStore" / "GraphBridgeLike" / "GraphStoreLike" — 需区分: GraphBridge 是类名, GraphStoreLike 是接口名, 两者不能混用
- 组 3 (哨兵): "哨兵" / "Sentinel" / "sentinel" — 同一概念, 大小写差异
- 组 4 (目标): "Goal" / "goal" / "增长目标" / "Goal 工程" — 同一概念, 中英文差异
- 组 5 (循环): "子循环" / "循环" / "Loop" / "业务循环" — 同一概念 (但需区分"子循环"和"顶层调度循环")
- 组 6 (溢出): "溢出" / "Overflow" / "溢出监控" — 同一概念
- 组 7 (专家): 8 位专家名称 — strategy/org/finance/tech/marketing/action/business_model/knowledge 在所有文档中一致

- 组 10 (时间): "快/中/慢" / "fast/medium/slow" — 同一概念
- 组 11 (MVS): "MVS" / "最小可用系统" / "Minimum Viable System" — 同一概念

## 三、两个专项检查 (穿插在审计中)

### 专项 A: 42 边消费完整性审计

**问题**: 01 定义了 42 条边，但下游文档 (02/03/13/15) 各自只消费了一个子集。哪些边从未被任何下游文档引用？

**方法**: 提取 01§二 的 42 条边 ID 列表 → 在 02/03/13/15/3D 中搜索每条边 ID → 标注每条边的消费状态 (被消费/仅定义/不确定)

### 专项 B: CT 附录 A 组件 ID 存在性验证

**问题**: CT 附录 A 的 17 个门禁引用了大量组件 ID (文件名、函数名、接口名)。这些 ID 在对应的权威文档中是否真实存在？

**方法**: 提取 CT 附录 A 中的所有组件引用 (如 Gate 5 的 `expert-autonomy.ts:38`, Gate 8 的 `goal-store.ts → createGoal()`) → 在每个引用目标文档中验证存在性
