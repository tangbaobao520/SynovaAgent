## 零、第一性原理推导：为什么是三个循环

**增长不可简化的底层只有三种资源类型——资金、需求（客户）、人力。**

这三种资源各自形成完整的获取→转化→回流闭环，且彼此不能相互替代：
- 钱买不来客户忠诚（资本积累 ≠ 客户锁定）
- 客户忠诚替代不了决策质量（市场份额 ≠ 组织能力）
- 人力不能直接替代资本（人才密度 ≠ 资金效率）

42 条因果边是这三种资源在企业内流动的具体路径。资本边的偏离只能由"钱"这个维度的完整因果链来解释：获取困难传导到分配不均、再传导到回流不足——把这条链截成两段分配给 finance 和 business_model 各自分析，得到的结论是碎片化的。客户边和人才边同理。

因此，按循环组织专家不是"优化"，是资源类型决定的唯一正确解。

**行业差异影响的是三个循环的相对权重，不是循环的存在性。** 知识密集型企业的知识流动权重更高，但它仍然需要资本循环（现金流不会因为是律所就自动健康）。资源型企业的资本循环权重更高，但它仍然需要客户循环（没有客户需求就没有资源开采的价值）。三个循环始终存在，权重因行业而异——通过 profiles 配置文件表达。

## 五、关键修正（外部评审反馈）

### 5.1 host 的聚合信号感知能力

**原始设计：** host 0 哨兵、0 compute，完全不消费原始信号——从专家接收诊断结论后合成报告。

**修正：** host 不分析单条边，但消费全量边偏离的聚合信号——资本循环、客户循环、人才循环各自的综合偏离指数（由 direction-monitor 计算并产出为 `cycle_deviation_index`）。host 根据这三个指数决定调度优先级：哪个循环的偏离指数最高，先激活对应的核心专家。这不是"对每条边做深度分析"——是"感知三个循环的宏观健康状态以决定调度顺序"。这才是 Graph 架构——host 根据当前状态决定下一个激活的节点。

技术实现：direction-monitor 已计算三大类别的偏离率（`DirectionReport.categories` 中每个 category 的 `deviationRate`）。host 消费这个字段，不需要新增哨兵或 compute。

### 5.2 host 作为一致性合成器（非仲裁者）

三个核心专家对同一条边可能得出不同方向的分析。host 不选择"谁的结论是对的"——它区分重叠区域和分歧区域：

- **重叠区域（高置信度）：** 两个以上核心专家的结论方向一致 → 标注"多视角交叉验证，置信度提升"
- **分歧区域（标注不确定性）：** 两个以上核心专家的结论方向不一致 → 标注"不同分析维度对此判断存在分歧"，暴露分歧而非隐藏

这比强制裁决更诚实——企业增长瓶颈本身的复杂性决定了它不可能在所有维度上都给出唯一明确的诊断方向。host 的职责是让用户看到完整的分析全貌，包括不一致的部分。

### 5.3 action 降级后的追踪职责

action 降级为 host 内部工具函数（负责 Goal 格式转换）。但其原有的"建议效果追踪"职责回归最初触发该 Goal 的核心专家。技术机制：每次 Goal 完成时，将执行结果写入该 Goal 对应核心专家的回访队列。资本循环专家提出的建议，由资本循环专家在下次诊断时主动验证——不是检查"省了多少钱"，而是检查"固定成本降低后资本回报率是否确实改善了"。

> 迁移清单已同步更新（见 §七）。

### 5.4 tech 保留在核心层

tech 当前覆盖 E-09/E-10/E-24/E-28/E-29/E-32/E-35——横跨知识流动、基础设施、技术健康、商业模式支撑、客户渠道。它不是"技术边分区"专家，而是"三类循环中技术因素影响"的跨循环专家。目标方案中 tech 保留在核心层，角色重新定义为"分析技术因素如何影响资本/客户/人才三个循环"。

### 5.5 行业专家"半激活"模式（明确版）

行业专家不消费原始哨兵数据，不做独立诊断。输入是核心专家的诊断结论（不是原始边数据），输出是"通用诊断→行业特定行动建议"的翻译。在 Graph 中的位置：核心专家输出 → host 合成 → host 调用行业专家做输出适配 → 最终诊断报告。这不是一个 Agent 节点——是 host 的输出适配器。实现方式：profiles YAML 中定义的行业专家以 prompt 模板注入 host 的输出合成阶段，不注册为独立的 Agent 实例。

### 5.6 E-11 和 E-12 的归属

E-11 和 E-12 属于资本获取链的资源约束边——描述企业在获取外部资金时面临的限制条件。目标方案中明确分配给资本循环专家，增加这两条边的覆盖声明。

### 5.7 三个循环推导链（完整版）

见 §零。

## 六、最终 7 位配置

| 层 | 专家 | 状态 | 从当前哪些专家合并/重组 |
|----|------|------|----------------------|
| host | 主 Agent / 诊断主持人 | 始终激活 | host（保留，增加聚合信号感知 + 一致性合成） |
| 核心 | 资本循环专家 | 始终激活 | finance + business_model（合并为 13 条边覆盖 + 21 个 compute）+ E-11/E-12 |
| 核心 | 客户循环专家 | 始终激活 | marketing + strategy（合并为 16 条边覆盖 + 14 个 compute） |
| 核心 | 人才循环专家 | 始终激活 | org + knowledge（合并为 16 条边覆盖 + 9 个 compute） |
| 核心 | 技术基础设施专家 | 始终激活 | tech（保留 7 条边 + 5 个 compute + 重新定义为跨循环视角） |
| 扩展 | 财务结构专家 | P0 激活 | 从 finance 剥离纯深度分析 |
| 扩展 | 竞争与战略专家 | P0 激活 | 从 strategy 剥离竞争定位深度 |

**核心专家的工作方式：** 每位核心专家不是"只处理自己分类的边"，而是"从自己的视角看全部 42 条边"。资本循环专家问：这条边如何影响资本循环？客户循环专家问：这条边如何影响客户循环？人才循环专家问：这条边如何影响人才循环？这保证 42 条边的覆盖是完整的——不会出现"某些边没有被任何专家分析"。

**host 的调度逻辑：** direction-monitor 产出三个循环的偏离指数。host 根据偏离指数决定调度优先级——偏离最高的循环优先激活核心专家。核心专家产出结论后，host 判断是否需要激活扩展专家（P0 条件：偏离持续 3 个周期以上、偏离度 >1.5σ）。host 合成三个视角的结论，标记重叠区域和分歧区域。

**合并前必须执行的分析视角冲突审计：**
- finance 和 business_model 对"资本回报率"的计算和"再投资比率"的归因逻辑是否一致？
- marketing 和 strategy 对"市场份额"的测量口径和"竞争定位"的评估框架是否冲突？
- org 和 knowledge 对"组织学习"的定义和"知识流动"的测量方式是否兼容？

**冲突裁决规则：** 保留两种视角，在诊断结论中标注互补关系——"观点A（X视角）+ 观点B（Y视角）"，不做非此即彼的选择。如果两个视角的结论方向完全相反，标记为"需要额外数据验证的高不确定性区域"。

**行业专家实现方式：** profiles YAML 中定义的行业专家以 prompt 模板注入 host 的输出合成阶段，不注册为独立的 Agent 实例——它们不消费原始数据，不做独立诊断，只做诊断结论的行业特定翻译。
