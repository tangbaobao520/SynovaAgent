时序查询强制使用observed_at或valid_from，不是created_at。 created_at是系统写入时间——当数据延迟补录时（6月补录3月数据），created_at=6月但valid_from=3月。如果用created_at计算"过去3个月的趋势"，会得到完全错误的结果。 2.2.1 时间字段定义 字段 含义 来源 valid_from 数据记录的业务有效周期起点 源数据日期列 / 用户标注周期 valid_to 数据记录的业务有效周期终点 valid_from+1周期（默认可由系统推算） observed_at 数据实际被观测/采集的时间点 源数据日期列 / 文件上传时间 created_at 系统写入时间（事务时间） 系统自动生成 2.2.2 数据延迟补偿策略 延迟幅度 策略 observed_at与valid_from差距 正常纳入 时序计算，标注late_arrival 差距 7-30天 纳入 但降低权重（weight=0.5） 差距 > 30天 不纳入 实时基线计算，仅在历史回测中可用 2.3 数据版本保留策略 层级 保留内容 策略 Layer 1: 当前+最近3个 完整数据：value + source_origin + observed_at + confidence 永久保留（用于时序诊断的差分计算） Layer 2: 更早历史 摘要：superseded_at + superseded_by + conflict_resolution 压缩保留（不保留完整数据值，仅保留版本切换记录） Layer 3: GA可配置 覆盖Layer 2的默认策略 企业级客户可要求"永久保留所有版本"（审计合规需求） "忠实记录" ≠ "永不删除"。 不丢弃真实的历史信号，但不在存储中无限保留所有版本的完整副本。默认保留最近3个完整版本，更早的压缩为版本切换摘要。 2.4 GraphStore节点Schema 每个数据节点 = 概念节点池中的节点类型，携带统一Schema： 字段 类型 必填 说明 node_id string (UUID) 是 节点唯一标识 type string 是
