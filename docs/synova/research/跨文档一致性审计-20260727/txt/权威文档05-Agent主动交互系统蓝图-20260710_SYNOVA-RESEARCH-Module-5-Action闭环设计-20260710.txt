Action不是对话中的一段文本描述，不是Trello卡片——它是带有因果锚点的、可追踪的、可验证的执行承诺。Action在系统中是一级实体，与节点(Entity)、边(Edge)、哨兵(Sentinel)、信号(Signal)同级。 5.1.1 Action数据结构 interface Action { id: string; // "ACT-20260710-001" source: { conversationId: string; // 创建此Action的对话ID signalId: string; // 触发此Action的哨兵信号ID causalEdges: string[]; // 关联的42边ID，如["E-23","E-13"] }; enterpriseId: string; // 所属企业 responsibleRole: 'CEO' | 'VP' | 'GA' | 'DEPARTMENT'; department?: string; // 部门（中层Action时必填） description: string; // 人类可读的执行描述 targetValue: { // 预期效果 metric: string; // 如"毛利率" currentValue: number; targetValue: number; // 如30%（从当前27.8%恢复到30%） tolerance: number; // 容差范围，如±1% }; deadline: Date; // 预期完成日期 status: 'proposed' | 'accepted' | 'in_progress' | 'verified' | 'abandoned'; tracking: { // 追踪信息 createdAt: Date; acceptedAt?: Date; lastCheckedAt?: Date; metricSnapshots: { date: Date; value: number }[]; // 定期快照 }; verificationResult?: { verified: boolean; actualValue: number; deviation: number; // 实际 vs 目标偏差 verifiedAt: Date; autoVerified: boolean; // 是否系统自动验证 }; loopNodeId?: string; // 关联的Loop Engineering任务节点ID parentActionId?: string; // 如果是子Action（拆解后的子任务） crossDeptActions?: string[]; // 跨部门关联的Action ID（多部门协同场景） } 5.1.2 Action状态机 状态 含义 转入条件 可转出到 proposed 建议已提出，等待确认 Agent在对话中建议行动 → 用户说"接受" → 系统创建Action（初始状态） accepted（用户确认）/ abandoned（用户说"不做"） accepted 已确认，等待执行 用户确认Action（可指定负责人+截止日期） in_progress（开始执行）/ abandoned（取消） in_progress 执行中，系统定期追踪 到达截止日期前N天自动转入 / 用户手动标记为"开始执行" verified（验证通过）/ abandoned（放弃）/ in_progress（继续） verified 已执行且效果验证通过 系统检测到target metric达到目标值（容差范围内） / GA手动验证 —（终态） abandoned 已放弃 用户主动取消 / 超过截止日期2倍且无操作 —（终态，但可被新Action引用为前置条件） 5.2 Action生命周期追踪 5.2.1 创建 → 确认 → 执行 → 验证 的完整链路 创建 ：用户在对话中说"接受方案一"或"执行这个建议"→ 系统从建议中提取Action数据结构（目标值、关联42边、预估效果）→ 创建Action对象 确认 ：Agent回复"已创建行动项。负责人：[从对话推断或用户指定]。截止日期：[从对话推断或默认2周]。确认后，我将持续追踪执行效果。" 执行追踪 ：系统定期（每天/每周，依据Action的deadline）查询该Action关联的42边参数。在Action追踪面板中展示： targetValue.metric 的当前值 vs 目标值。如果检测到偏离（如已过预期恢复时间但值未回升），触发"执行偏离预警" 验证 ：系统自动检测 |currentValue - targetValue| → Action自动标记为verified。如果自动验证无法确认（数据缺失/多因素混杂），GA手动验证。 5.2.2 中层行动看板（部门导航循环中的呈现） 行动项 负责人 状态 目标指标 当前值 截止 ACT-001：B产品提价8% 销售VP李 执行中 毛利率≥30% 28.1% (+0.3%) 7月24日 ACT-002：缩短采购审批层级 CFO王 已确认 采购响应 17天（旧） 8月1日 ACT-003：C产品线扩产可行性 运营VP张 建议中 产出可行性报告 — 7月17日 5.3 Action与Loop工程的关系 Action不是独立的任务管理系统——它是Loop Engineering循环的 "执行单元" 。每个Action对应一个循环中的任务节点。 Action类型 所属循环 循环如何消费Action 企业级行动 （老板从全景诊断中确认） 🔄 企业诊断循环 → 循环在下一次诊断中检查Action的target metric是否改善 → 如未改善→标记"Previous Action Ineffective"，提示调整策略 部门级行动 （中层从部门导航中确认） 📊 部门导航循环 → 循环在每次方案提交/执行追踪时检查Action进度 → 偏离>15%→预警推回部门负责人 → 连续2次偏离→升级到老板 GA校准Action （GA在面板中标记错误后的跟进） 🧬 GA进化循环 → 循环检查GA纠错是否被采纳 → 采纳后3个周期内检查该哨兵准确率是否提升 → 未提升→标记为"校准无效"，触发人工审查 系统恢复Action （自检循环发现断裂后生成） ⚙️ 系统自检循环 → 循环检查Action恢复状态 → L1自动重试失败→L2半自动→L3手动 → 恢复后写入系统健康日志 知识更新Action （行业知识基座更新后的跟进） 📚 知识积累循环 → 循环在更新后标记哪些哨兵的基线发生变化 → 触发GA确认 → 确认后应用于诊断 5.4 跨部门协同Action 5.4.1 触发条件 当两个以上部门的信号指向同一个企业级JTBD时（如"利润下降"需要销售+运营+财务数据），触发跨部门Action生成。 5.4.2 跨部门Action的交互流程 检测 ：信号排序器检测到销售VP、CFO、运营VP三方的哨兵信号同时指向"利润下降"这个JTBD 合并 ：去重合并器生成复合因果故事——"销售端：客户A流失风险 + 财务端：原材料成本上升 + 运营端：B产品线毛利率下降——三者共同指向利润压力" 推送到共享空间 ：不是在三人各自的对话中分别触达——而是创建一个"跨部门决策提示"，推送到三人共同的决策空间（如"决策群聊"或"会议准备区"） 跨部门Action创建 ：共享空间中的Action同时标记三位负责人——如"ACT-CROSS-001：协同制定B产品线成本优化+定价调整方案。参与方：销售VP李（定价）+ CFO王（成本）+ 运营VP张（生产效率）" 追踪 ：跨部门Action的每次进度更新，三方同时收到更新通知。如果任一方的子Action延迟，另两方自动收到提醒。 5.4.3 跨部门Action的数据结构扩展 Action.crossDeptActions = ["ACT-001", "ACT-002", "ACT-003"]; // 关联的三个部门级Action // 跨部门Action本身有一个"协调者"角色——默认是老板或GA // 协调者可以看到所有子Action的进度和依赖关系 5.5 与现有架构的对接 组件 架构位置 消费的上游 服务的下游 Action Store L5存储层（新增：ActionStore） 对话引擎（创建Action）、GA面板（手动创建） L2 Action追踪器、Loop管理器、中层看板 Action追踪器 L2编排层
