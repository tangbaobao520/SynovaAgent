# CTO 健康仪表盘：判定与 spec 兼容（D744）

## 触发场景

`gen-cto-health.py` 是 CTO 开工先读的仪表盘生成器。两个缺陷同时存在：

1. **崩溃**：`task-state/D600.json` 的 `spec` 是**字符串**（历史格式直接写路径），而代码写死
   `(d.get("spec") or {}).get("path")` → `AttributeError: 'str' object has no attribute 'get'` → **生成器 exit 1，整个仪表盘不生成**。
2. **假绿**：审计判定用全文子串，顺序是 `CONDITIONAL PASS > PASS > FAIL`。而报告正文的**证据行**天然同时含 PASS 与 FAIL
   （实证 D393 正文有 `PASS:3 WARN:883 FAIL:435`；D503 报告里 `CONDITIONAL PASS` 是**另一个任务**的判定）
   → 真判定 FAIL 被吞，**P0 阻断在 CTO 仪表盘上显示为通过**。

## 决策内容

**修法（两层，缺一不可）**：
1. **结论行优先** —— 取「同时含判定词（结论/判定/verdict）**与**判定值（PASS/FAIL）的第一行」作为作用域；
   只含关键词不含值的行（目录、表头）不算 —— 否则会落到没有判定的行上，判定退化成 `?`（D503/D515 实测踩到）。
   无结论行才回退全文（不放松，只是不再被证据行带偏）。
2. **同一作用域内 FAIL 先于 PASS** —— `CONDITIONAL PASS` 仍最高（它自带 PASS 子串，须先行判定）。

**spec 两态**：`dict → .get("path")`；`str → 直接当路径`；其他 → `None`。
**兼容不放松**：取到路径后仍走同一套「工作区存在 + 已提交 HEAD」仓库态校验（D412 口径）。

## 实测影响（量化）

| | 修复版 | 退化版（全文作用域）|
|---|---|---|
| D393 | FAIL | FAIL |
| D503 / D515 / D549 / D572 | **FAIL** | **CONDITIONAL_PASS**（被吞）|
| FAIL 行数 | **34** | 14 |

→ 修复前有 **20 行**把 FAIL 显示成了通过或非 FAIL。这正是「CTO 看到假绿」的规模。

## 实测踩坑（反向验证自身）

首次反向验证**无效**：我把判定逻辑整段替换时脚本崩了（exit 1），而 `docs/synova/CTO-HEALTH.md` 保持上一次的产物 →
grep 到的全是**旧值**，看起来「改不改都一样」。教训：**反向验证必须先确认被测脚本 exit 0**，再读产物；
拿崩溃进程的陈旧输出做对比 = 自欺。第二次只退化「作用域」单项，其余不变，结论才成立。
