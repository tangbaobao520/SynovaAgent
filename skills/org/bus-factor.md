# 关键人依赖量化分析 (Bus Factor)

## 适用场景

组织诊断开始时自动运行。检测到以下信号强触发：单人维护核心系统、某项工作只有一人了解全貌、关键知识未文档化。企业 < 10 人时 Bus Factor 本身可能较低且难以消除——标注"小团队结构性依赖"而非直接标高风险。

## 方法步骤

1. 调用 `query_graph` 检索组织架构数据，识别知识分布热点（谁参与了多少项目、谁在关键流程中不可替代）
2. 对每个关键角色/流程计算 Bus Factor——多少人掌握该工作的全貌
3. 按 RULES.md 评分表判定：BF=1 🔴 极高风险，BF≤2 🟡 高风险，BF 3-5 🟢 健康，BF>5 ✅ 理想
4. 调用 `key_person_risk` 工具输出风险评估报告
5. 对每个 🔴 风险点输出具体建议：文档化关键流程 / 轮岗 / 配对工作 / 自动化

## 输出格式

```
Bus Factor 报告:
  核心系统运维: BF=1 → 🔴 极高风险 (仅张工掌握全部配置)
  客户对账流程: BF=2 → 🟡 高风险 (李姐和王姐两人知道)
  产品路线图: BF=3 → 🟢 健康 (三人各自有不同片段)
  知识文档覆盖: 23% 的关键流程有文档 (应 > 80%)
  项目推荐:
    - 张工的核心系统配置 → 文档化 (2周内) + 至少1人跟随学习 (本月)
    - 客户对账流程 → 编写操作手册 (1周内)
```

## 判断标准

- BF=1 的每个实例必须有一个具体建议，不允许无建议空过
- 文档覆盖率 < 50% → 🟡 高风险标注，即使当前 BF 健康（知识只存在于人脑中）
- 同一人的 BF 风险点 ≥ 3 个 → 标记为"超级关键人"，风险等级提升一级
- BF 评估后 60 天内复查，如果高风险点未改善则升级为组织风险

## 常见陷阱

- 只算人数不算备份质量——"两个人知道"不等于"两个人都有完整知识"，标注"部分/全量知识掌握"
- 忽略工具锁定的 Bus Factor——只有某人会用的工具/脚本也是依赖，标注"工具锁定"
- 对管理者给出 BF=1 但认为"正常"——CEO 或创始人 BF=1 是小企业常态，标注"结构性依赖，业务连续性风险"而非"人员风险"
